# UX-разъяснение редактора скоринга: вкладки «Шкалы» и «Показатели»

**Статус:** Пояснение к эскизу (не нормативная спецификация)  
**Дата:** 2026-06-01 (синхронизировано: сетка «вариант × шкала»; реверс убран; корректность в «Вопросах»)  
**Эскиз:** `docs/wireframes/approved/prd2-prd5-scoring-tabs.html`  
**Сквозная модель:** `docs/specs/scoring-model.md`

## Назначение и как читать

Этот документ объясняет задуманный пользовательский опыт редактора скоринга и снимает
замечание рецензента о неинтуитивности интерфейса. Он не описывает новые экраны — он
расшифровывает уже существующие состояния эскиза `docs/wireframes/approved/prd2-prd5-scoring-tabs.html`
и привязан к ним напрямую: каждое упоминание элемента ниже соответствует реальной подписи в
одном из состояний эскиза (переключаются кнопками в верхней мета-панели: «Шкалы: список /
вклады / композит/пересчёт / диапазоны / ошибка / пусто / предпросмотр»,
«Показатели: список + DnD / карточка / конструктор / ошибка / пусто», а также «readonly»,
«loading», «Пояснения»).

Документ предназначен для двух читателей: автора теста, который настраивает скоринг впервые
или собирает сложный сертификационный сценарий, и проектировщика интерфейса, который
проверяет, что задуманная модель читается без обращения к спецификации. Терминологическая
опора — `docs/specs/scoring-model.md` (сквозная модель скоринга). Латинские идентификаторы,
имена полей API и выражения DSL (`scale.*`, `controls_status`, `countScales`, `answer_score`)
приводятся как есть.

Как читать: начните с раздела «Ментальная модель» и таблицы четырёх понятий — это устраняет
основной источник путаницы. Дальше идёт карта интерфейса, пошаговые потоки и разбор каждой
точки трения.

## Ментальная модель за 30 секунд

Главный принцип платформы: машинерия скоринга общая, а конкретный тест — это ДАННЫЕ в ней.
Платформа не знает слов «компетенция руководителя», «версия набора» или «секция»: всё это
выражается через четыре общих понятия. Новую сущность заводят только под новый общий
механизм, полезный многим тестам, а не под один тест.

Расчёт результата — это конвейер. На каждом шаге значение одного типа превращается в значение
следующего:

```text
вопрос -> балл вопроса (число) -> вклад в шкалу -> агрегация шкалы = raw
-> диапазоны на raw -> уровень   (пересчёт итога — параллельное отображаемое значение)
-> показатель (формула) -> управление статусом / передача в LMS
```

Расшифровка шагов:

- вопрос возвращает ЧИСЛО (а не только «верно/неверно»): балл по рубрике своего типа (0..5 по
  варианту ответа в MBI; 0/1/2/3 с частичным баллом в сертификационном тесте для руководителей);
- балл становится вкладом в шкалу (с весом; на первом этапе без условий) ЛИБО вкладом служит
  значение другой шкалы (композиция);
- вклад вопроса в шкалу = сумма значений активных единиц: `Σ (value × weight)` (правило
  по умолчанию; множественный выбор складывает значения всех выбранных опций);
- агрегация сворачивает вклады выбранной операцией (`сумма` по умолчанию; доступны `среднее` /
  `взвешенное` / `макс` / `мин`; `взвешенное` берёт вес с ребра);
- пересчёт итога переводит `raw` в значение: `none` / `percent` / `inverse` (вся шкала
  обратная); `linear` (a·raw+b) — точка расширения, на этапе-1 скрыта; по умолчанию пересчёт не
  нужен;
- диапазоны (`bands`) применяются к `raw` шкалы (не к `percent`) и дают символьный уровень
  (`low`/`mid`/`high`, `passed`/`failed`);
- показатель — формула над шкалами, темами и другими показателями (число / строка / булево);
- показатель через «Управление статусом курса» может переопределить статус прохождения, а
  значения шкал и показателей выгружаются в LMS.

Порядок шагов гарантирует, что шкалы готовы до показателей, а показатели — до фиксации статуса.

## Четыре понятия и чем они различаются

Это главный источник непонимания: на экране встречаются слова «балл», «вклад», «шкала»,
«показатель», и автор пытается понять, какое из этих чисел в итоге суммируется. Различающее
правило для каждого — в последнем столбце.

| Понятие | Что это | НЕ путать с (правило различения) |
| --- | --- | --- |
| Корректность / балл вопроса | Свойство ВОПРОСА (раздел «Вопросы»): верный вариант и стандартный балл (`correctJson`/`answer_score`). Это ось ПРАВИЛЬНОСТИ — для стандартного балла и гейта прохождения. | Со вкладом в шкалу. Правило: корректность задаётся в вопросе и ОРТОГОНАЛЬНА вкладам; в шкалы `answer_score` НЕ наследуется (вклады — явные числа в сетке). |
| Шкала | Именованное значение = агрегат ВКЛАДОВ. Опционально имеет пересчёт, интерпретационные диапазоны и выгрузку в LMS. Листовая шкала собирает баллы вопросов; составная (композит) агрегирует другие шкалы. | С Показателем. Правило: шкала АГРЕГИРУЕТ вклады (сумма/среднее/...) и может иметь диапазоны, но формулу не пишет и статус прохождения переопределять не может. |
| Вклад (ячейка «вариант × шкала») | `question_measurements`: ЯВНОЕ число — вклад варианта ответа в шкалу (`value_json`). Пусто = не влияет; 0 и отрицательные допустимы. Один вариант может вкладывать в несколько шкал с разными числами (мультишкальность). | С формулой и нормализацией. Правило: вклад — это ДАННЫЕ (число в ячейке сетки), а не формула. Корректность варианта — отдельная ось (раздел «Вопросы»); пересчёт применяется ПОСЛЕ агрегации, к шкале целиком. |
| Показатель | Именованное значение = произвольная формула над шкалами, темами и другими показателями; тип число / строка / булево. Опционально управляет статусом курса и выгружается в LMS. | Со Шкалой (и с композитом). Правило: композит — это всё ещё шкала (структурная агрегация, формула не пишется); показатель — произвольная формула и ЕДИНСТВЕННОЕ место «Управления статусом курса». |

Отдельно про доставку: вариативность (разным обучающимся — разные вопросы) обеспечивается
банком вопросов и выдачей подмножества. Это свойство доставки, а не скоринга, и отдельной
сущности «версия/форма» оно не требует: шкала суммирует те вклады, что фактически поступили.

## Карта интерфейса по вкладкам

Скоринг живёт в двух вкладках редактора теста (`Состав` · `Настройки` · `Оформление` ·
`Структура` · `Шкалы` · `Показатели`). Порядок вкладок отражает зависимость: показатели
ссылаются на шкалы, поэтому шкалы задают первыми.

Вкладка «Шкалы». Слева — вертикальный рейл «Список шкал / Вклады вопросов» (тот же паттерн, что
в «Настройках»: `ou-drawer__split` + `ou-drawer__rail`), справа — контент выбранного раздела.
Два раздела рейла:

- раздел «Список шкал» (состояние «список»): заголовок «Шкалы теста» с кнопкой «Добавить
  шкалу» и карточки шкал (свёрнутые «EE — Эмоциональное истощение», «D — Отстранённость» и
  раскрытая «AD — Обесценивание достижений»). В раскрытой карточке — поля «Ключ» и «Метка»,
  селект «Агрегация», сегмент «Источник: Вопросы / Другие шкалы», селект «Пересчёт итога»,
  селект «Передавать в LMS», таблица «Диапазоны (пороги) → уровень» с кнопкой «Добавить
  диапазон» и переключатель «Показывать результат обучающемуся». Базовый балл за ответ на
  карточке шкалы НЕ настраивается — это свойство вопроса (вкладка «Состав»). Здесь же живёт
  композит (состояние «композит/пересчёт»): та же карточка с «Источником» в положении «Другие
  шкалы», селектом «Агрегация» (`сумма`/`среднее`), списком-переключателями «Дочерние шкалы»,
  «Пересчётом итога» = «Нет» и блоком «Предпросмотр диапазонов → уровень»;
- раздел «Вклады вопросов» (состояние «вклады»): баннер покрытия и ВЕРТИКАЛЬНЫЙ СПИСОК
  раскрывающихся карточек вопросов. Свёрнутая карточка: тип вопроса + чипы ВСЕХ шкал теста
  (яркий = вопрос вкладывает, блеклый = нет) + точка покрытия. Раскрытая — СЕТКА «вариант ×
  шкала»: строки = варианты ответа, столбцы = все шкалы теста, ячейка = число-вклад (пусто = не
  влияет; допустимы 0 и отрицательные). Первая колонка (варианта) закреплена; шкалы
  прокручиваются при большом числе. Верный вариант ПОДСВЕЧЕН (read-only) + ссылка «Редактировать
  вопрос». По-вопросной строки итогов нет. Состояние «предпросмотр» («Предпросмотр расчёта»)
  показывает на демо-наборе таблицу `Шкала` · `raw` · `percent` · `уровень` ·
  `scale.* (доступно в показателях)` — это и есть итоги по шкалам.

Почему сетка, а не матрица-галочки: атом — `(вариант × шкала) → число`, а не `(вопрос × шкала)`.
Один вариант может вкладывать в несколько шкал с разными числами; членство — производное (есть
непустая ячейка). Корректность — ортогональная ось, живёт в «Вопросах».

Вкладка «Показатели». Заголовок «Показатели результата» с кнопкой «Добавить показатель»:

- список с DnD (состояние «список + DnD»): свёрнутые карточки («ee_high — EE на уровне high»,
  «burnout_category — Категория выгорания») с рукояткой «Перетащить», кнопками «Удалить
  показатель» и «Развернуть». Заголовок раздела помечен «· порядок вычисления»;
- карточка (состояние «карточка»): поля «Имя» и «Метка», селекты «Тип» и «Управление статусом
  курса», сегмент «Конструктор / DSL», поле «Формула DSL», баннер валидации, переключатель
  «Показывать результат обучающемуся» и селект «Передавать в LMS»;
- конструктор (состояние «конструктор»): селекты «Шаблон», «Условие», оператор сравнения, поле
  «Порог», поле «Сгенерированная формула (только чтение)» и кнопка «Перейти в DSL-редактор».

## Потоки автора

### Сценарий A — MBI (3 шкалы, инверсия AD, разметка вкладов, 1 показатель-категория)

1. Открыть вкладку «Шкалы», под-вид «Список шкал». Нажать «Добавить шкалу». Заполнить «Ключ» =
   `ee`, «Метка» = «Эмоциональное истощение», «Агрегация» = «Сумма», «Источник» =
   «Вопросы».
2. В таблице «Диапазоны (пороги) → уровень» кнопкой «Добавить диапазон» завести строки: 0–14 /
   `low`, 15–24 / `mid`, 25–45 / `high`. Включить «Показывать результат обучающемуся» при необходимости.
3. Повторить для шкалы `d` (диапазоны 0–4 / `low`, 5–9 / `mid`, 10–25 / `high`).
4. Завести шкалу `ad`: «Агрегация» = «Сумма», «Пересчёт итога» = «Инверсия».
   Диапазоны вводятся по возрастанию `raw`: 0–27 / `high`, 28–32 / `mid`, 33–40 / `low` (для
   инверсной шкалы нижний `raw` несёт уровень `high`).
5. Переключиться на раздел «Вклады вопросов». Раскрыть карточку вопроса и в сетке вписать
   число-вклад каждого варианта в нужную шкалу-столбец (EE / D / AD); пустая ячейка = не
   влияет. Баннер покрытия гаснет, когда у вопроса есть хоть один вклад. (Корректность — в
   разделе «Вопросы».)
6. Открыть вкладку «Показатели», нажать «Добавить показатель». «Имя» = `burnout_category`,
   «Тип» = «Строка», «Управление статусом курса» = «Нет».
7. В сегменте «Конструктор / DSL» выбрать «DSL» и в поле «Формула DSL» ввести многоветочный
   `IF(countScales([...], "high") = ...)`. Баннер «Синтаксис корректен. Тип возврата — строка.»
   подтверждает результат.
8. Состоянием «предпросмотр» проверить расчёт на «Демо-ответе»: таблица покажет
   `raw`/`percent`/`уровень`, а баннер — итоговую строку `result.burnout_category`.

Композиция, пересчёт `linear` и «Управление статусом курса» в MBI не используются.

### Сценарий B — сертификационный тест для руководителей (листы -> композит -> пороги -> вердикты -> сертификация)

1. Завести листовые шкалы по под-темам: «Агрегация» = «Сумма», «Источник» = «Вопросы».
   Шкала суммирует вклады вариантов (см. шаг 2); корректность вопроса — в разделе «Вопросы».
2. На «Вкладах вопросов» раскрыть карточку вопроса и в сетке «вариант × шкала» вписать
   число-вклад каждого варианта в нужные шкалы-столбцы (0/1/2/3; для «обратного» пункта —
   отрицательное число); пустая ячейка = не влияет.
3. Задать порог раздела: в таблице «Диапазоны (пороги) → уровень» завести два диапазона с
   уровнями `failed` (0…порог−1) и `passed` (порог…max). «Уровень» — произвольная строка,
   которую вводит автор.
4. Собрать составную компетенцию: «Добавить шкалу», переключить «Источник» на «Другие
   шкалы», в списке «Дочерние шкалы (суммируются)» включить нужные дочерние шкалы
   переключателями, «Агрегация» = «Сумма». «Пересчёт итога» оставить «Нет» (equating
   в сертификационном тесте для руководителей (2026) не применяется). Задать диапазон
   `passed`/`failed` на компетенцию.
5. Во вкладке «Показатели» завести булевы показатели «пройдено по компетенции»: «Тип» =
   «Булево», «Управление статусом курса» = «Нет». Формула вида `scaleById("comp1").level =
   "passed"`.
6. Завести финальный показатель-сертификацию: «Тип» = «Булево», формула-конъюнкция через
   «Перейти в DSL-редактор» (`AND(...)`), «Управление статусом курса» = «Успех (success_status)».
7. В списке с DnD держать финальный показатель ПОСЛЕДНИМ: `var("...")` видит только показатели
   выше. Рукояткой «Перетащить» расставить порядок вычисления.
8. Проверить на «предпросмотре», что финальный показатель верно переключает статус курса для
   пограничного «Демо-ответа».

## Неинтуитивные места и как UX их снимает

### Ячейка сетки — это число-вклад; пусто = не влияет

Что снимает: ячейка на пересечении «вариант × шкала» — ЧИСЛО, которое этот вариант ответа даёт в
эту шкалу. Пусто = вариант не влияет на шкалу (ребра нет); `0` = влияет, но вклад 0; минус =
вычитает. Никаких галочек: членство вопроса в шкале — производное (в столбце есть непустая
ячейка). Один вариант может вкладывать в несколько шкал с разными числами — просто впишите числа
в нужные столбцы. Что знать автору: вписал число — вариант вкладывает; стёр — перестал.

### Привязка вопросов — в разделе «Вклады вопросов», а не в карточке шкалы

Что сбивает: автор ищет, где привязать вопросы, внутри раскрытой карточки шкалы. Что снимает:
привязка живёт в разделе «Вклады вопросов» рейла (слева: «Список шкал» / «Вклады вопросов»). В
карточке шкалы задаются только её собственные поля. Что знать автору: сначала создайте шкалы в
разделе «Список шкал», затем переключитесь во «Вклады вопросов», раскройте вопрос и впишите
числа-вклады в нужные столбцы-шкалы.

### Нормализация «Инверсия» (AD): что именно инвертируется

Что сбивает: слово «Инверсия» в селекте «Пересчёт итога» без формулы рядом; неясно,
ломаются ли диапазоны. Что снимает: пересчёт применяется к ИТОГОВОМУ `raw` шкалы (после
агрегации всех вкладов), а не к ответам. «Инверсия» означает `percent = (max − raw)/(max −
min)·100`, то есть высокий `raw` даёт низкий процент. Что знать автору: диапазоны всё равно
применяются к `raw` буквально и перечисляются по возрастанию `raw`, поэтому для AD нижний
диапазон 0–27 несёт уровень `high`. Это видно в состоянии «предпросмотр»: строка «AD
(инверсная)» с `raw 22`, `percent 45`, уровнем `high` — корректна, и сравнивать `percent`
инверсной шкалы с прямой напрямую нельзя.

### Формула — только в «Показателях»; в шкалах формул нет

Что сбивает: автор ищет поле формулы на шкале (чтобы выразить вес или вердикт) и, не находя,
решает, что поле спрятано. Что снимает: шкала настраивается ТОЛЬКО структурно — «Агрегация»,
«Источник», диапазоны, переключатели. Поля формулы у шкалы нет намеренно. Что знать
автору: любая произвольная логика (категория, вердикт, условие, вес-как-выражение) пишется
единственно во вкладке «Показатели» (сегмент «Конструктор / DSL»). Если задача не сводится к
«агрегация + источники» — это показатель.

### Конструктор собирает только одно условие; конъюнкцию пишут в DSL

Что сбивает: в состоянии «конструктор» есть один селект «Условие», один оператор сравнения и
одно поле «Порог» — нет кнопки «+ условие» и связок `AND`/`OR`. Автор, которому нужна
конъюнкция (сертификация = «пройдены все разделы»), упирается в тупик и не понимает, как
собрать многоусловную формулу. Что снимает: конструктор предназначен для ОДНОГО простого
сравнения (источник, оператор, порог) — например, порог на тему или шкалу; он лишь
генерирует стартовое выражение в поле «Сгенерированная формула (только чтение)». Что знать
автору: для нескольких условий нажмите «Перейти в DSL-редактор» и используйте `AND(...)` /
`OR(...)` (например `AND(scaleById("c1").level = "passed", scaleById("c2").level = "passed")`);
конструктор перенесёт первое условие, остальные дописываются в DSL.

### Композит — это шкала с источником «Другие шкалы», а не отдельная сущность

Что сбивает: для составной компетенции нет отдельной кнопки «Добавить композит»; главная для
сертификационного теста руководителей операция выражается незаметным переключением внутри уже
созданной карточки. Признак «лист
vs композит» виден только у РАСКРЫТОЙ карточки (подзаголовок «сумма дочерних шкал»), а в
свёрнутом списке составная шкала выглядит как листовая. Что снимает: составная (rollup) шкала —
это обычная шкала, у которой «Источник» переключён на «Другие шкалы»; она агрегирует
(`сумма` или `среднее`) значения отмеченных переключателями дочерних шкал из списка «Дочерние
шкалы». Что знать автору: отдельной сущности «композит» нет — выберите «Агрегация» = «Сумма»
(или «Среднее») и отметьте дочерние шкалы; вложенность любой глубины (компетенция →
под-компетенции → листы), в список дочерних попадают и другие составные шкалы. Взвешенную или
экстремум-комбинацию дочерних шкал (`weighted_avg`/`max`/`min`) композит не делает — она
пишется формулой показателя, который дочерние шкалы уже видит.

### Нормализация и пересчёт: none / percent (+ inverse) на первом этапе

Что снимает: «Пересчёт итога» — независимое опциональное поле; на первом этапе
работают «Нет» и «Проценты» (с направлением «Инверсия»). Композит в эскизе намеренно показан с
«Пересчётом итога» = «Нет»: в сертификационном тесте для руководителей оценка идёт по сырой сумме
против абсолютного порога раздела, никакого `a·raw+b` не требуется. Линейный пересчёт `a·raw+b`
(калибровка/equating) и `custom` — документированные точки расширения, в сертификационном тесте
для руководителей (2026) не применяются и в UI первого этапа не отгружаются; пол (clamp) живёт
внутри линейного пересчёта, отдельного поля нет. По умолчанию
пересчёт — `нет`/`проценты`.

### Корректность — в «Вопросах»; вклады в шкалы — явные числа

Что сбивает: автор ищет на шкале или во «Вкладах», где задать «верный ответ». Что снимает:
корректность варианта и стандартный балл задаются в самом ВОПРОСЕ (раздел «Вопросы»). Во
«Вкладах» верный вариант только ПОДСВЕЧЕН (read-only) + ссылка «Редактировать вопрос». Вклады в
шкалы — ОТДЕЛЬНЫЕ явные числа в сетке; `answer_score` в шкалы НЕ наследуется. Что знать автору:
правильность — одна ось (в «Вопросах»), вклады в шкалы — другая (числа в сетке); они независимы.

### Инверсия шкалы (per-ребро реверс убран)

Что снимает: ВСЯ шкала инверсна (MBI AD) — это «Пересчёт итога» = «Инверсия» на карточке шкалы
(после агрегации, влияет на `percent`). Отдельного per-ребро «перевернуть вклад» БОЛЬШЕ НЕТ —
его заменяют явные значения в сетке с поддержкой ОТРИЦАТЕЛЬНЫХ чисел (хочешь вычесть — поставь
минус; хочешь зеркало — впиши зеркальные числа). Что знать автору: целиком инверсная шкала —
«Инверсия» в «Пересчёт итога»; «обратный» вклад одного варианта — просто отрицательное число.

### Диапазоны -> уровень: «Метка» против «Уровень»

Что сбивает: в таблице «Диапазоны (пороги) → уровень» есть и «Метка» (Высокий/Средний/Низкий),
и «Уровень» (`high`/`mid`/`low`), и неясно, какой из них машинный код и можно ли вписать свой.
Что снимает: «Уровень» — произвольная строка-код, которую вводит автор (`high`/`mid`/`low` —
лишь пример, для прохождения подойдут `passed`/`failed`); она публикуется в `scale.{key}.level`
и используется в формулах показателей. «Метка» — человекочитаемое название того же диапазона
для показа обучающемуся. Диапазоны сопоставляются с `raw`.

### Баннеры покрытия и ошибок

Что сбивает: баннер «Шкала D: 1 из 5 вопросов пока без вклада — проверьте покрытие.» называет
шкалу, но в матрице непонятно, какой именно вопрос не покрыт, потому что «—» встречается и
легитимно. Что снимает: разделение по ролям — мягкое предупреждение покрытия идёт жёлтым
баннером (роль `status`), а блокирующая ошибка — красным баннером «Есть ошибки в шкалах.
Сохранение заблокировано до их исправления.» (роль `alert`), под которым поле «Ключ»
подсвечено как невалидное с сообщением «Ключ «ee» уже используется другой шкалой…». Что знать
автору: жёлтое — это «проверьте», красное — «сохранение заблокировано».

## Рекомендации по интуитивности

Ниже — улучшения аффордансов. Часть уже внесена в эскиз (помечено «реализовано»); остальное —
предложения к согласованию.

- Композит без точки входа (частично; delivery-поля добавлены). Когда «Источник» переключён на «Другие шкалы»,
  показывать в карточке и подзаголовке тег «композит» (в том числе в СВЁРНУТОМ виде), а в
  пустом состоянии и подсказке упоминать, что rollup создаётся переключением источника, а не
  отдельной кнопкой.
- «Уровень» читается как закрытый перечень (блокер). Сделать «Уровень» в строке диапазона
  видимо редактируемым полем и подсказать, что значение произвольное (`passed`/`failed` и
  т. п.), публикуется в `scale.{key}.level`.
- «Управление статусом курса» как место сертификации (блокер). Рядом с селектом дать
  поясняющий текст, что «Успех» пишет в `cmi.success_status`, и что это единственное место
  переопределения итога курса; при «Тип» ≠ «Булево» селект делать недоступным с подсказкой
  «доступно только для типа Булево» ДО ошибки, а не после. Превентивно предупреждать про
  правило «не более одной «Успех» на тест».
- Сетка вкладов (реализовано). «Вклады вопросов» = вертикальный список карточек; раскрытая
  карточка — сетка «вариант × шкала» с явными числами (пусто = не влияет, 0 и отрицательные);
  все шкалы столбцами, чипы яркий/блеклый; верный вариант подсвечен + «Редактировать вопрос»;
  per-ребро реверс убран; строки итогов нет (итоги в «Предпросмотре»).
- Конструктор по умолчанию и единый переключатель (высокая). Открывать новый показатель в
  режиме «Конструктор», а кнопку «Добавить показатель» вести сразу в конструктор; в состоянии
  «конструктор» заменить одностороннюю кнопку «Перейти в DSL-редактор» на тот же двусторонний
  сегмент «Конструктор / DSL»; в конструкторе предусмотреть добавление второго условия для
  конъюнкции либо явно направлять в DSL для `AND(...)`.
- Симметрия ошибок и порядок вычисления (высокая). Добавить в состояние «ошибка» показателя
  верхний баннер-сводку «Есть ошибки в показателе. Сохранение заблокировано до их исправления.»
  по образцу шкал; в списке показателей у раздела «порядок вычисления» дать заметку, что
  `var("…")` видит только показатели выше, и валидацию при перетаскивании зависимого показателя
  выше его источника.
- Зависимость вкладок и readonly (средняя). На пустом состоянии «Показатели» подсказать
  «сначала задайте шкалы во вкладке Шкалы»; в баннере readonly сделать «создайте новую версию»
  действующей кнопкой или ссылкой. Для статус-точек карточек документировать семантику цвета
  (зелёный/жёлтый/красный/серый) в подсказке или коротким словом статуса.

## Журнал приёмки эскиза (вопросы на понимание)

Фиксация разрывов ясности, всплывших при приёмке. Каждый пункт — дата, вопрос автора,
вердикт и предложение к проработке.

### 2026-06-01

- Вопрос: «Почему в поле "Агрегация" только "Сумма" (вкладка Шкалы, карточка шкалы)?»
  Вердикт: чрезмерное урезание UI — `avg`/`weighted_avg`/`max`/`min` были скрыты из селекта
  только потому, что референсные тесты (MBI, сертификационный тест для руководителей) используют лишь сумму. Это не основание
  убирать функцию из универсальной платформы.
  Решение (2026-06-01): расширяем селект до пяти операций (`сумма` по умолчанию, `среднее`,
  `взвешенное`, `максимум`, `минимум`); `взвешенное` берёт вес с ребра «вопрос × шкала».
  `threshold`/`formula` остаются убранными — они дублируют диапазоны и слой «Показатели»
  (вырезаны по корректности слоёв, не по скоупу). Следствие: каждая операция — ветка
  scales-движка + golden-векторы + покрытие в эмите интеракций; в авторском UI операция
  показывается только когда движок её считает. Эскиз, сквозная модель и PRD-5 обновлены.
- Вопрос: «Как изменится состояние "Шкалы", если выбрать "Другие шкалы" в "Источник"?»
  Ответ: шкала становится композитом — вместо привязки вопросов появляется блок «Дочерние
  шкалы (суммируются)» (переключатели других шкал теста), матрица «Вклады вопросов» к ней не
  применяется; остальное (ключ, метка, диапазоны, пересчёт, передача в LMS, показ
  обучающемуся) остаётся свойствами шкалы. Разрывы ясности к проработке:
  (1) состояние «композит/пересчёт» в эскизе опускает «Ключ»/«Метку» и показывает диапазоны
  как read-only «Предпросмотр» вместо редактируемой таблицы — это упрощение эскиза, а не
  правило: композит — полноценная шкала, нужны те же поля идентичности и редактируемая
  таблица диапазонов;
  (2) после расширения агрегации до пяти операций композит остаётся `sum`-only (метка
  «(суммируются)», §9.3) — РЕШИТЬ: получает ли композит селект «Агрегация» (`avg`/`max`/`min`
  над дочерними шкалами) или `sum`-only закрепляется намеренно;
  (3) композит-шкала не должна появляться столбцом в матрице «Вклады вопросов» (в неё нельзя
  «отметить вопрос») — в эскизе это взаимодействие не показано;
  (4) список дочерних шкал должен исключать саму шкалу и предотвращать циклы (A→B→A) —
  валидация в эскизе не показана.
  Решение (2026-06-01) по (2): композит получает агрегацию `sum`+`avg`; `weighted_avg`/`max`/
  `min` остаются слоем «Показатели» (дочерние шкалы видны формуле). Граница та же, что у
  `threshold`/`formula`: структурный роллап — на шкале, взвешенная/экстремум/условная
  комбинация — формулой показателя. Эскиз (селект «Агрегация» Сумма/Среднее в карточке
  композита), сквозная модель §9.3 и PRD-5 §5.1 обновлены. Пункты (1), (3), (4) — доработка
  эскиза, остаются в журнале.
- Вопрос: «Диапазоны (пороги) — как работают?»
  Ответ: таблица сопоставляет значение шкалы символьному уровню. Строка: `min`/`max` (границы),
  «Метка» (человекочитаемое имя для обучающегося), «Уровень» (машинный код-строка в
  `scale.{key}.level` для формул показателей; если опущен — Core генерит `band_N`). Интервалы
  не пересекаются, перечисляются по возрастанию, непокрытые значения → «Без интерпретации»
  (`level = null`). КЛЮЧЕВОЕ: диапазоны сопоставляются с `raw`, а НЕ с `percent`/пересчётом —
  пересчёт даёт параллельное отображаемое значение (AD: `raw 22 → percent 45 → high`, потому
  что `raw 22 ∈ [0,27]`).
  Исправлено: сквозная модель (§4 конвейер, §10.8) и UX-конвейер показывали «пересчёт →
  диапазоны», что противоречило PRD-5 §5.2–5.3 и эскизу; приведено к «диапазоны на `raw`,
  пересчёт параллельно».
  Разрыв ясности к проработке (downstream от решения про `avg`): при `sum` `raw` целочисленный
  и смежные целочисленные диапазоны (0–27, 28–32) покрывают всё; при `avg`/`weighted_avg` `raw`
  дробный (27.4) и попадает в зазор `(27, 28)` → «Без интерпретации». Нужен контракт границ для
  непрерывного `raw` (полуинтервалы `[min, max)` встык) и правило inclusive/exclusive +
  out-of-range = `null`; сверить с биннингом `process_burnout_export.py`.
- Вопрос: «В LMS отправляется уровень (диапазон), а не посчитанное значение?»
  Ответ: для ШКАЛЫ — да: `cmi.interactions[scale_{key}].learner_response = band.label`
  («Высокий»), и именно метка попадает в Excel-столбец «Ответ» (PRD-5 §8.2–8.3). Код уровня
  («high») и числа `raw`/`percent` уходят только в `suspend_data.custom.scale.{key}`, которое
  в стандартный Excel НЕ попадает. Число всё же выгружаемо: ПОКАЗАТЕЛЬ экспортирует
  `learner_response = {value as string}` (PRD-2 §7.2), поэтому числовой показатель
  `scaleById("x").raw` кладёт само число столбцом. Асимметрия по дизайну: шкала отдаёт
  интерпретированную метку-вердикт, показатель — само значение.
  Разрыв ясности к проработке: шкала БЕЗ диапазонов (чисто числовая) — метки нет; что тогда в
  `learner_response`? §8.2 определяет только случай с band. Решить: fallback на `raw`/`percent`
  строкой ЛИБО закрепить правило «для числа в столбце — показатель, а не шкала».
- Вопрос: «Переключатель "Показывать результат обучающемуся" — что именно показывать и когда?»
  Ответ: управляет ТОЛЬКО отображением на странице результатов обучающегося; к LMS отношения
  не имеет (это отдельный «Передавать в LMS», переключатели ортогональны). ЧТО: шкала → блок
  `data-slot="scale-results"` (имя шкалы + интерпретированный уровень `displayLabel` «Высокий»;
  в payload также `raw`/`percent`/`level`); показатель → блок `data-slot="result-variables"`
  (значение по типу: строка как есть, число — 2 знака, булево — Да/Нет, `null` — «Не рассчитано»).
  КОГДА: на странице результатов после завершения теста, если в шаблоне есть слот. Caveat:
  рантайм-рендер test-scope слотов (`scale-results`/`result-variables`) — известный render gap
  (PRD-1 §1.9), отложен в C2; LMS-выгрузка от него не зависит (C1).
  Разрывы ясности к проработке: (1) ЧТО именно показывает блок шкалы недоопределено (только
  метка «Высокий» или имя + `raw` + `percent` + `level`) — автор включает тоггл, не зная формат
  для обучающегося; (2) шкала без диапазонов + показ — метки нет, что выводить (`raw`/`percent`?);
  (3) в редакторе нет превью вида обучающегося — состояние «предпросмотр» это авторский расчёт
  (`raw`/`percent`/`level`), а не то, что увидит обучающийся.
- Вопрос/фидбек: «Вклады вопросов — не понятно ничего, кроме того, что вопрос можно привязать
  к шкалам.» Диагноз: матрица доносит только проводку «вопрос→шкала», но прячет, ЧТО по ней
  течёт. Неочевидно: (а) галочка несёт балл ИЗ ВОПРОСА (`answer_score`, вкладка «Состав»), а не
  число из матрицы; шкала суммирует баллы отмеченных; (б) «Веса по ответам» — опциональный
  override (иное число per вариант / реверс), нужен редко; «Веса заданы» = override настроен;
  (в) баннер говорит жаргоном («без вклада»/«покрытие») и его триггер неясен («1 из 5» намекает
  на ожидаемое покрытие, которое автор нигде не объявлял); (г) связь с «Составом» (где живёт
  балл) невидима. Предложение к проработке (ячейки ОСТАЮТСЯ галочками, числа в ячейки НЕ
  возвращаем): вводная строка-микрокопия над матрицей («Отметьте, в какие шкалы идёт балл
  вопроса; сам балл задаётся в вопросе на вкладке «Состав»; «Веса по ответам» — только если
  нужно иное число»), заголовок последнего столбца «Особые веса», переформулировать баннер без
  жаргона и с однозначным триггером (пустая шкала ЛИБО вопрос-сирота, выбрать что проверяем).
- Директива: «Хочу видеть настройки вкладов в самой матрице галочек; недопустимо прятать их во
  вложенных диалогах/модалках.» Решение (2026-06-01): принят ГИБРИД. Матрица «вклады»
  перестроена: добавлен read-only столбец «Балл вопроса» (из «Состав»), бейджи «реверс»/«особые
  веса» в строке, веса по вариантам редактируются ИНЛАЙН раскрытием строки (зона ПОД строкой), а
  не на отдельном экране. Отдельное состояние s-measurements удалено; кнопка «веса» убрана из
  навбара, «предпросмотр» перенесён в группу «Шкалы». Модель данных (`question_measurements`,
  `value_json`, `reverse`) НЕ менялась — изменилась только подача (инлайн вместо drill-in).
  Рекомендация «Drill-in в «Веса по ответам»» снята как решённая. Эскиз, wf-notes и
  UX-компаньон обновлены.
- Вопрос: «"Уровень" (high/mid/low) в диапазонах — откуда берётся?» Ответ: вводит АВТОР; это
  произвольный код per диапазон (`high`/`mid`/`low` — пример для MBI; для прохождения
  `passed`/`failed`), публикуется в `scale.{key}.level` для формул показателей; пусто → Core
  генерит `band_N` (PRD-5 §5.3). Разрыв ясности: «Уровень» отрисован статичным чипом `ou-tag`,
  читается как закрытый перечень, а не редактируемое поле автора (= рекомендация-блокер
  «"Уровень" читается как закрытый перечень»).
- Вопрос: «Метка и Уровень — не дубль?» Ответ: НЕ дубль — разные потребители: «Метка» (`label`)
  идёт на показ обучающемуся и столбцом в LMS (`learner_response`), проза/локализуемая;
  «Уровень» (`level`) идёт в формулы (`scale.{key}.level`), стабильный машинный код. Это
  разделение код/отображаемое-имя (как value vs display у enum): стабильный код позволяет
  переименовать показ, не ломая формулы. Рекомендация: не заставлять заполнять оба — сделать
  «Метку» ОПЦИОНАЛЬНОЙ (пусто → показывается «Уровень»); простой диапазон = одно поле, оба —
  только когда показ и код реально разные.
- Разрыв ясности (эскиз): НЕТ состояния добавления/редактирования диапазона. Таблица
  «Диапазоны → уровень» показывает строки статично (`min`/`max`/«Метка» — текст, «Уровень» —
  чип) + кнопки «Добавить диапазон»/удалить, не ведущие никуда. Предложение: инлайн-
  редактирование строк прямо в таблице — «Добавить диапазон» вставляет редактируемую строку
  (`min`/`max`/«Метка»/«Уровень»), существующие правятся там же; «Метка» опциональна. Один
  state закрывает и редактируемость «Уровня», и вопрос дубля.
  Реализация (2026-06-01): добавлено состояние `s-bands-edit` (навбар «диапазоны») — строки
  диапазонов редактируемые (поля `min`/`max`/«Метка»/«Уровень»), новая строка добавляется
  инлайн, «Уровень» — поле ввода (не чип), «Метка» помечена опциональной. Открытый дефект к
  доработке: ширина столбцов — поля `min`/`max`/«Уровень» слишком широкие, столбцы
  «Уровень»/«Действия» обрезаются по правому краю; нужно сузить числовые/код-поля.
- Вопрос: «Что такое "Перевернуть вклад"?» Ответ: пометка «обратный (reverse-keyed) пункт» для
  конкретной шкалы — балл варианта инвертируется ДО суммы по `v = (max + min) − raw` (для 0–5:
  5→0, 0→5). Нужен для пунктов, сформулированных в ОБРАТНУЮ сторону от измеряемого (напр. Q4
  «понимаю коллег» — позитивный пункт; в шкалу AD-выгорания идёт перевёрнутым). Флаг per ребро
  (вопрос × шкала): пункт может быть обратным для одной шкалы и прямым для другой. НЕ путать с
  «Инверсия» («Пересчёт итога»), которая переворачивает ВСЮ шкалу после агрегации (scoring-model
  §10.4). Разрыв ясности: подпись «Перевернуть вклад» не самоочевидна (пользователь спросил) —
  добавить инлайн-подсказку («балл варианта считается наоборот, 5→0; для обратно-сформулированных
  пунктов») и/или термин «обратный пункт».
- Редизайн «Вкладов» (2026-06-01, ОТМЕНЯЕТ все более ранние «вклады»-решения как ИСТОРИЧЕСКИЕ:
  инлайн-матрица, hybrid, drill-in, галочки/«Веса по ответам», per-ребро реверс, столбец «Балл
  вопроса»). Диагноз: матрица «вопрос × шкала» из галочек моделировала НЕ ТОТ
  атом — реальная единица `(вариант × шкала) → число`; галочка не выражает мультишкальность (один
  вариант → разные числа в разные шкалы) и сливает ортогональную ось корректности.
  Решение: «Вклады» = вертикальный список карточек вопросов; раскрытая карточка — СЕТКА
  «вариант × шкала» (строки = варианты, столбцы = ВСЕ шкалы теста, ячейка = явное число
  `value_json`: пусто = не влияет, 0 и отрицательные допустимы; членство — производное). Один
  вариант может вкладывать в несколько шкал с разными числами. Корректность — в разделе
  «Вопросы»: верный вариант подсвечен (read-only) + «Редактировать вопрос»; здесь не правится.
  Per-ребро реверс УБРАН (отрицательные значения заменяют); scale-level «Инверсия» осталась.
  По-вопросной строки итогов НЕТ (best-practice: Qualtrics/QTI/Storyline — сумма по столбцу для
  одиночного выбора вводит в заблуждение; итоги по шкалам — в «Предпросмотре»). Все шкалы =
  столбцы (без «+ шкала»); чипы шкал в шапке яркий/блеклый. Базовый `answer_score` в шкалы НЕ
  наследуется. Источник правды: вопрос («Вопросы») = текст + варианты + корректность + балл;
  тест → Шкалы → Вклады = числа per (вариант × шкала). Блокер реализации: durable ID единиц
  (shuffle ON). Обновлено: эскиз (s-contributions, wf-notes, DS-хелперы), PRD-5 §4/§6/§9,
  scoring-model §9/§10, UX-компаньон.
