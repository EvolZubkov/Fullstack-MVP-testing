# Runbook — выкладка PRD-13 (ролевая модель доступа)

Порядок включения ролевой модели (5 ролей, владелец и гранты тестов, конфиг-суперадмин) с
возможностью поэтапного отката (BR-13). Нормативные документы:
[role-model.md](../specs/access-control/role-model.md),
[acceptance-matrix.md](../specs/access-control/acceptance-matrix.md).

## Принцип безопасной выкладки

Серверное ядро прав уже в основной ветке (Фазы 2-3): каждый эндпоинт защищён
`requirePermission`, область тестов — `requireTestScope`. На время перехода действует
транзиционный fallback: пользователь без строк в `user_roles` получает роль из устаревшего
столбца `users.role` (`author` -> «Администратор», `learner` -> «Обычный пользователь»). Поэтому
выкладка не отнимает доступ до миграции данных, а откат возможен на каждом шаге.

## Предусловия

- В `.env` задан `SUPERADMIN_EMAILS` (список адресов суперадминов через запятую). Пустое
  значение допустимо, но тогда суперадминов нет — назначение роли «Администратор» будет
  некому выполнить.
- Доступ к БД для применения миграции (`DATABASE_URL`).
- Зелёный прогон `npm run check` и `npm test`.

## Шаг 1. Миграция схемы и данных (`016_prd13_rbac_roles.sql`)

Миграция аддитивна (новые объекты, существующие данные не разрушаются):

- таблица `user_roles` (многие-ко-многим пользователь -> роль);
- столбец `tests.owner_id` (владелец теста, nullable);
- таблица `test_access_grants` (гранты `edit`/`assign`, уникальность по `test_id` + `user_id`);
- бэкфилл: `author` -> `administrator`, `learner` -> `learner` в `user_roles`; `owner_id`
  остаётся `NULL` (назначается администратором позже через панель «Общий доступ»).

Применение: `npm run db:push` (drizzle) либо прямой прогон SQL `migrations/016_prd13_rbac_roles.sql`.
Проверка: в `user_roles` появились строки для всех активных пользователей.

## Шаг 2. Перезапуск сервера (автопровижининг суперадминов)

При старте `provisionSuperadmins` заводит недостающие аккаунты из `SUPERADMIN_EMAILS` БЕЗ
строк в `user_roles` (права суперадмина приходят из конфигурации) с временным паролем —
аккаунт задаёт пароль через сброс. Существующие аккаунты не трогаются. Удаление адреса из
`SUPERADMIN_EMAILS` снимает права суперадмина при следующем запросе (без остаточного админа).

## Шаг 3. Приёмка

Прогнать автотесты трека и сверить [acceptance-matrix.md](../specs/access-control/acceptance-matrix.md):

```bash
npx vitest run tests/access client/src/features/tests/list/__tests__/tests-list.test.tsx
npm run lint:md
```

Точечно проверить ключевые кросс-ролевые сценарии из матрицы (автор-чужой-тест, менеджер-без-
гранта, назначение роли «Администратор» не-суперадмином -> 403).

## Откат

- Откат приложения: вернуть предыдущую версию кода. Транзиционный fallback оставляет
  `users.role` рабочим, поэтому доступ не теряется.
- Объекты БД из шага 1 аддитивны и безопасны: их можно оставить при откате кода (новые
  таблицы/нулевой столбец не влияют на старую логику).
- Точечный откат по домену: домены Фазы 3 независимы; при проблеме в одном домене правится
  его роутер, не затрагивая остальные.

## Шаг 4 (финальный — T-10). Снятие legacy

Реализован в коде 2026-06-08: снят fallback `legacyRoleToStored` в
`server/services/access.ts`, удалены мёртвые `requireAuthor`/`requireLearner`, миграция
`017_prd13_drop_users_role.sql` удаляет столбец `users.role`. На dev уже применено.

На проде применять `017` ТОЛЬКО после стабильного периода и подтверждённой приёмки (необратимо
по столбцу). Предусловие миграции: у каждого аккаунта есть строка в `user_roles` (проверка — в
шапке `017`). После T-10 единственный источник ролей — `user_roles` плюс конфиг-суперадмин.
