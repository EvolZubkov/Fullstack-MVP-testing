# Runbook: устранение утечки секретов и ротация ключей (Фаза 0)

## Назначение

Пошаговый регламент устранения утечки секретов из репозитория `test-builder` и ротации
скомпрометированных ключей. Соответствует Фазе 0 плана `docs/plans/PLAN_ARCHITECTURE_REQUIREMENTS.md`
и разделам 9.3, 9.4 эталона требований.

## Контекст находки

- В индексе git отслеживался файл `.env copy` с реальными секретами: `DATABASE_URL`,
  `ENCRYPTION_PASSWORD`, `ENCRYPTION_SALT`, `SESSION_SECRET`, `SMTP_PASS` и почтовый адрес.
- Дополнительно отслеживался `docker/build/config/deploy.env` с внутренними данными
  инфраструктуры (внутренний IP, SSH-пользователь, пути), хотя каталог `docker/build/`
  должен игнорироваться.
- В файле-шаблоне `docker/build/env/.env.example` (который остаётся в репозитории) были
  захардкодены реальные значения: пароль PostgreSQL и учётные данные SMTP. Файл вычищен
  до плейсхолдеров, но скомпрометированные значения остаются в истории git.
- Файл `.env` присутствовал в истории коммитов (есть коммиты `Delete .env`).
- Удалённые репозитории: `origin` (vvlad1973) и `upstream` (EvolZubkov) на GitHub — секреты
  следует считать раскрытыми публично.

## Что уже выполнено в репозитории

Эти шаги сделаны и закоммичены локально (без push):

- `.gitignore` ужесточён: `.env*` с исключением `!.env.example` — ловит `.env copy` и подобные.
- Файлы выведены из-под версионирования (локальные копии на диске сохранены):
  - `git rm --cached ".env copy"`
  - `git rm --cached "docker/build/config/deploy.env"`

## Что обязан выполнить оператор

Ниже — шаги, требующие доступа к провайдерам, базе данных и правам на удалённый репозиторий.
Выполнять в сервисном окне.

### Шаг 1. Ротация секретов на стороне провайдеров

Все значения из `.env copy` считаются скомпрометированными. Сменить:

- Пароль пользователя PostgreSQL (и обновить `DATABASE_URL`).
- Пароль/токен приложения SMTP-ящика на стороне почтового провайдера (обновить `SMTP_PASS`).
- `SESSION_SECRET` — сгенерировать новый (все текущие сессии станут недействительны):

  ```bash
  node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
  ```

- `ENCRYPTION_PASSWORD` и `ENCRYPTION_SALT` — сгенерировать новые (см. шаг 2, требуется
  ре-шифрование email в БД):

  ```bash
  node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
  ```

### Шаг 2. Ре-шифрование email при смене ключей шифрования

Смена `ENCRYPTION_PASSWORD` / `ENCRYPTION_SALT` делает все ранее зашифрованные email
в таблице `users` нечитаемыми. Колонка `email_hash` (SHA-256) от ключей не зависит и не меняется,
поэтому поиск по email продолжает работать.

Порядок:

1. Не меняя пока рабочий `.env`, запустить пробный прогон (без записи), передав старые и новые ключи:

   ```bash
   DATABASE_URL="<тот же, что в .env>" \
   OLD_ENCRYPTION_PASSWORD="<текущий>" OLD_ENCRYPTION_SALT="<текущий>" \
   NEW_ENCRYPTION_PASSWORD="<новый>"  NEW_ENCRYPTION_SALT="<новый>" \
   DRY_RUN=true npm run reencrypt-emails
   ```

   В Windows PowerShell переменные задаются через `$env:`:

   ```powershell
   $env:DATABASE_URL="<...>"; $env:OLD_ENCRYPTION_PASSWORD="<...>"; $env:OLD_ENCRYPTION_SALT="<...>";
   $env:NEW_ENCRYPTION_PASSWORD="<...>"; $env:NEW_ENCRYPTION_SALT="<...>"; $env:DRY_RUN="true";
   npm run reencrypt-emails
   ```

2. Убедиться, что отчёт показывает `DRY RUN ok` и число строк совпадает с числом пользователей.
   Если скрипт сообщает об ошибке расшифровки — указаны неверные OLD-ключи, ничего не записано.
3. Сделать резервную копию БД.
4. Повторить запуск с `DRY_RUN=false` — изменения применяются в одной транзакции.
5. Прописать новые `ENCRYPTION_PASSWORD` / `ENCRYPTION_SALT` (и остальные ротированные значения)
   в рабочий `.env` и перезапустить приложение. Проверить вход и отображение email.

### Шаг 3. Очистка секретов из истории git

Секреты остаются в истории даже после удаления файлов и вычистки шаблонов. Переписать историю
(пример с `git filter-repo`):

Полностью удалить из истории файлы, которые в репозитории не нужны:

```bash
git filter-repo --invert-paths --path ".env" --path ".env copy" --path "docker/build/config/deploy.env"
```

Затем затереть конкретные скомпрометированные литералы, которые встречались и в файлах,
которые мы сохраняем (например, в `docker/build/env/.env.example`). Подготовить файл
`replacements.txt` со строками вида `СТАРОЕ==>УДАЛЕНО` (по одной на каждое реальное значение:
пароль БД, пароль SMTP, прежние `SESSION_SECRET`, `ENCRYPTION_PASSWORD`, `ENCRYPTION_SALT`) и применить:

```bash
git filter-repo --replace-text replacements.txt
```

После переписывания истории:

- Принудительно обновить ветки в `origin`:

  ```bash
  git push origin --force --all
  git push origin --force --tags
  ```

- Учесть форк `upstream` (EvolZubkov): секреты могли распространиться туда и в кэш GitHub.
  Ротация ключей (шаги 1-2) обязательна независимо от чистки истории — это основная защита.
- Предупредить всех, у кого есть клоны: им потребуется заново склонировать репозиторий.

Внимание: переписывание истории и `--force` push необратимы и затрагивают удалённый репозиторий.
Выполнять только после согласования.

- В `git ls-files` отсутствуют файлы с секретами (`.env copy`, `deploy.env` и подобные).
- Все скомпрометированные секреты заменены на стороне провайдеров и в рабочем `.env`.
- Email в БД успешно расшифровывается новым ключом; вход работает.
- История git очищена и удалённые репозитории обновлены (после согласования).
