# Медиатека: реестр, защищённая раздача и переиспользование файлов

Статус: требования согласованы 2026-08-01. Документ фиксирует принятые решения и их обоснование;
реализация не начата.

## 1. Повод

Работа с файлами в системе не формализована. Загрузка одна на всё
([`server/middleware/upload.ts`](../../../server/middleware/upload.ts)), она кладёт файл в
`uploads/media/` под обезличенным именем `<timestamp>_<uuid>.<ext>` и на этом заканчивается.
Следствия, проверенные по коду:

- **исходное имя теряется** — у автора нет человекочитаемого дескриптора файла, из-за чего
  импорт медиа не смог войти в PRD-14 и был вынесен в отдельный будущий PRD;
- **реестра нет** — в базе у вопроса лежит только `mediaUrl` + `mediaType`
  ([`shared/schema.ts:263-264`](../../../shared/schema.ts)), у страниц и оформления такие же
  строки-адреса внутри JSON; узнать «где используется файл» неоткуда;
- **раздача `/uploads` статична и без авторизации**
  ([`server/routes.ts:81`](../../../server/routes.ts)); политика области ссылки-приглашения её
  намеренно пропускает ([`server/middleware/magic-scope.ts:10`](../../../server/middleware/magic-scope.ts));
- **переиспользования нет** — кнопка «Выбрать из медиатеки» подписана в
  [`design-section.tsx:985`](../../../client/src/features/tests/editor/sections/design-section.tsx)
  и нарисована в утверждённом эскизе PRD-7, но никуда не ведёт; один и тот же файл заливается
  повторно;
- **дедупликации, владения и сборки сирот нет** — удалённый вопрос оставляет файл на диске навсегда;
- **PDF обратной связи некуда положить** — [PRD-32](../../specs/prd-32/feedback-assets-delivery.md)
  заблокирован именно отсутствием хранилища и сам предлагает решать это вместе с медиатекой.

Работа давно значится в [дорожной карте](../../ROADMAP.md) позицией «PRD-N (Медиатека и импорт
медиа)» с рекомендованным порядком «реестр -> UI -> модель ссылки -> импорт -> сквозное»
(см. также [PRD-14 §5.3](../../specs/prd-14/questions-import-export.md)).

## 2. Охват

В охвате — **все файлы автора**: медиа вопросов, изображения контентных страниц, фоны и
иллюстрации оформления, PDF-вложения обратной связи. Единый реестр, единая раздача, единый
механизм прав. Разделение по типам потребителей отвергнуто: иначе PRD-32 породил бы второй
механизм хранения рядом с первым.

Вне охвата первого этапа:

- импорт медиа книгой Excel (PRD-14) — реестр создаёт для него предпосылку, но сам импорт
  проектируется отдельно;
- гранты доступа к отдельному файлу — модель данных обязана их допускать, реализация позже;
- объектное хранилище (MinIO / S3) — см. §7.

Файлы шаблонов оформления (PRD-3, `uploads/templates/<id>/`) в охват не входят: у них свой
жизненный цикл, своя валидация и свой реестр `templates`.

## 3. Принятые решения

| Развилка | Решение | Почему |
| --- | --- | --- |
| Охват | Все файлы автора в одном реестре | Иначе PRD-32 создаёт второй механизм хранения |
| Модель ссылки | Канонический адрес `/api/media/<id>` | Тип поля в базе не меняется; массовая миграция строк в JSON не нужна |
| Владение | Этап 1: владелец + видимость `private`/`shared`. Гранты — позже | Согласовано с PRD-15, но без избыточной гранулярности на старте |
| Защита раздачи | Аутентификация + видимость + связь с доступным контентом | Ученик не имеет ни владения, ни авторской роли — его пускает только связь |
| Индекс использования | Пишется при сохранении + полная сверка по требованию | Один обходчик на оба пути, две реализации не разъедутся |
| Удаление | Запрет с отчётом «где используется» (`409`), сироты удаляются свободно | Прямой прецедент `content-guard` в PRD-15 |
| Хранилище | Файловая система за портом `MediaStore` | Объектное хранилище пока решало бы проблему, которой нет (§7) |

## 4. Модель данных

### 4.1 Таблица `media_assets`

| Поле | Назначение |
| --- | --- |
| `id` (uuid, PK) | Он же адрес: `/api/media/<id>` |
| `checksum` (sha256, hex) | Дедупликация содержимого |
| `storage_key` | Ключ в хранилище: `media/<ab>/<cd>/<sha256>.<ext>` |
| `mime_type`, `byte_size` | Факты о файле |
| `kind` | `image` / `audio` / `video` / `document` |
| `original_name` | Исходное имя, которое сегодня теряется |
| `title` | Необязательное авторское название; по умолчанию `original_name` без расширения |
| `owner_id` | Владелец (nullable: наследие, см. §5) |
| `visibility` | `private` / `shared` |
| `created_at` | Аудит |

`kind = document` вводится сразу, не «на будущее»: без него PRD-32 не закрыть, а фильтр загрузки
сегодня пропускает только `image/*`, `audio/*`, `video/*` и PDF отвергает.

Раскладка `storage_key` по двум байтам контрольной суммы нужна, чтобы не держать десятки тысяч
файлов в одной директории. В объектном хранилище шардирование по префиксу не требуется, но и не
мешает — ключ переносится как есть.

### 4.2 Два слоя дедупликации

Это разные вещи, и смешивать их нельзя:

- **физический слой** адресуется контрольной суммой: повторная загрузка того же содержимого не
  пишет второй файл;
- **логический слой** заводит запись реестра на пару «содержимое + владелец».

Если бы запись была одна на контрольную сумму, личный файл одного автора стал бы доступен другому
просто потому, что тот загрузил такой же файл байт в байт. Повторная загрузка того же файла тем же
автором возвращает существующий актив. Физический файл удаляется, когда на его контрольную сумму
не осталось ни одной записи реестра.

### 4.3 Неизменяемость актива

Содержимое актива **нельзя заменить по месту**. «Заменить картинку» означает загрузить новый актив
и переставить ссылку в живом контенте.

Это следствие модели удаления, и без него защита была бы половинчатой: запрет удаления оберегает
опубликованный снимок PRD-15 от исчезновения картинки, но подмену содержимого по тому же адресу
он не ловит — строка в снимке при этом не меняется вовсе.

### 4.4 Таблица `media_usages`

| Поле | Назначение |
| --- | --- |
| `asset_id` | Ссылка на актив |
| `entity_type` | `question`, `content_page`, `test_design`, `test_feedback`, `topic_feedback`, `scale_feedback`, `snapshot` |
| `entity_id` | Идентификатор сущности |
| `field` | Где именно внутри сущности (для отчёта «где используется») |

Уникальность по всем четырём полям.

## 5. Адресация и совместимость

Канонический адрес — `GET /api/media/<id>`, без расширения: тип и имя для скачивания отдаёт
маршрут заголовками.

Адрес живёт **под `/api`** намеренно: политика области ссылки-приглашения полицирует только
`/api/*` ([`magic-scope.ts:10`](../../../server/middleware/magic-scope.ts)), и адрес вне `/api`
потребовал бы дублировать эту политику вторым механизмом. Загрузка уже живёт по
`/api/media/upload` — раздача встаёт рядом.

Совместимость со старыми адресами:

1. разовая миграция индексирует всё содержимое `uploads/media/`; владелец неизвестен и остаётся
   пустым (наследие), видимость — `shared`;
2. статика `/uploads` **выключается целиком**, старые адреса обслуживает тот же защищённый
   маршрут по `storage_key`;
3. строки в базе массово не переписываются — вместо этого обходчик `collectMediaRefs`, который и
   так вызывается при сохранении сущности, попутно приводит найденные адреса к каноническому виду.

Наследие вымывается по мере редактирования контента, а не одной рискованной миграцией по чужим
структурам JSON.

## 6. Раздача и права

### 6.1 Правило доступа

Файл отдаётся, если верно хотя бы одно:

1. запрашивающий — владелец актива, администратор или суперпользователь;
2. актив имеет видимость `shared` и у запрашивающего есть авторская роль (`hasAuthoringRole`) —
   это доступ «к библиотеке», ради переиспользования;
3. актив используется в контенте, доступном запрашивающему.

Третье правило — единственное, по которому файл видит учащийся: ни владения, ни авторской роли у
него нет.

### 6.2 Как считается третье правило и чего это стоит

`media_usages` даёт «актив -> сущности». Доступность сущности разрешают уже существующие службы —
`test-access`, `topic-access` и назначения. Для вопроса это путь «вопрос -> темы -> разделы тестов
-> назначения»: один запрос с соединениями, не скан.

Но это разрешение доступа **на каждую картинку**, поэтому в дизайн сразу входит кеш решения в
памяти процесса, сбрасываемый при перезаписи индекса. Без кеша экран с десятью изображениями даёт
десять разрешений доступа.

### 6.3 Что теряется вместе со статикой

Express-статика бесплатно давала запросы по диапазонам. Без них аудио и видео не перематываются, а
Safari видео вообще не начинает играть. Маршрут обязан реализовать:

- `Range` (частичный ответ `206`);
- `ETag` по контрольной сумме;
- `Cache-Control: private`.

Приватный кеш экономит байты, но проверку прав не отменяет: ответ `304` всё равно проходит через
маршрут.

## 7. Хранилище: порт `MediaStore`

Объектное хранилище (MinIO / S3) в этой работе **не вводится**. Основания проверены по коду и по
развёртыванию:

- **реплик приложения не может быть и по другой причине**: сессии живут в памяти процесса
  (`memorystore`, [`server/routes.ts:36,63`](../../../server/routes.ts)), поэтому вторая реплика не
  увидит вошедшего пользователя. Общий диск для нескольких экземпляров — главный довод за
  объектное хранилище — решал бы проблему, которой сейчас нет;
- **главная выгода S3 уже отвергнута решением по защите**: подписанные ссылки отдают файл мимо
  приложения, а принятое правило требует проверки прав на каждый запрос, то есть байты в любом
  случае идут через приложение;
- **весь код читает файлы синхронно**: упаковщик SCORM (`fs.readFileSync`), `template-package`,
  `template-render`. Переход на сеть сделал бы эти пути асинхронными по всему периметру — работа,
  не относящаяся к медиатеке.

Вместо этого вводится узкий порт `MediaStore`:

- `put(поток) -> storage_key`
- `openRead(storage_key, диапазон?)`
- `stat(storage_key)`
- `remove(storage_key)`

Реестр, права, индекс использования и дедупликация работают исключительно со `storage_key` и о
файловой системе не знают. Замена реализации на S3-совместимую — один модуль, без правки таблиц и
маршрутов.

**Условия пересмотра** (записаны, чтобы решение не пересматривалось на ощупь): несколько реплик
приложения — но сначала придётся вынести сессии из памяти, это независимый блокер; объём, который
неразумно держать в одном volume и бэкапить целиком; раздача видео по диапазонам под нагрузкой, где
Node проигрывает nginx или объектному хранилищу.

## 8. Индекс использования и жизненный цикл

### 8.1 Один обходчик на оба пути

`collectMediaRefs(сущность)` возвращает список ссылок на медиа внутри сущности. Он вызывается:

- при сохранении — переписать строки этой сущности в индексе, в той же транзакции, что и контент;
- при полной пересборке — административная операция, которая заодно поставляет список сирот и
  отчёт о расхождениях.

Одна реализация на оба пути выбрана намеренно: две разошлись бы, и разошлись бы молча, а врал бы
индекс в сторону отказа в доступе. Прецедент такой сверки в системе есть — `template-registry`
синхронизирует базу с диском при старте.

### 8.2 Удаление

Запрос на удаление сверяется с индексом: есть использования — `409` со списком «где именно», ровно
как `content-guard` в PRD-15, включая сухой прогон. Сирота удаляется свободно.

Опубликованный снимок PRD-15 считается использованием наравне с живым контентом: иначе выданная
версия могла бы лишиться картинки задним числом.

## 9. Потребители

| Потребитель | Что меняется |
| --- | --- |
| Упаковщик SCORM | Вместо резки строки — резолв идентификатора через реестр и чтение через `MediaStore`. Путь в ZIP: `assets/media/<id>.<ext>`. Ветка `data:` остаётся, легаси-префикс `/uploads/` поддерживается до вымывания |
| PDF-отчёт | Правок по существу нет, адрес нормализуется |
| Снимки PRD-15 | Защищены сочетанием «запрет удаления» + «неизменяемость актива» (§4.3) |
| Обратная связь (PRD-32) | Вложение становится обычным активом `kind = document`; фильтр загрузки расширяется на `application/pdf`; `scormHref` заполняется при упаковке |
| Книга Excel (PRD-14) | `original_name` + `title` дают человекочитаемый дескриптор. Сам импорт — отдельная работа |

Побочная выгода для упаковщика: сегодня он выводит путь на диске из строки URL и потому обязан
защищаться от `../`
([`media-assets.ts:49-79`](../../../server/scorm/builders/media-assets.ts)). После перехода на
`storage_key` из реестра такой строки в горячем пути нет вовсе.

Внутри SCORM-пакета адреса относительные и прав нет — так было и раньше, это не регресс.

- **Раздел «Медиатека»** в авторской навигации: список с фильтрами «мои / общие», по типу и

- **Выбор из библиотеки** в существующих местах загрузки — кнопка «Выбрать из медиатеки» уже

## 11. Этапы

Порядок обязателен: каждый следующий этап опирается на предыдущий.

| Этап | Содержание |
| --- | --- |
| Э1 | Реестр `media_assets` + порт `MediaStore` + дедупликация; загрузка пишет реестр; миграция индексирует существующие файлы |
| Э2 | Маршрут `/api/media/:id` с правами, `Range` и `ETag`; статика `/uploads` выключается, легаси-адреса обслуживаются тем же маршрутом |
| Э3 | `collectMediaRefs`, индекс при записи, полная пересборка, «где используется», запрет удаления, отчёт о сиротах |
| Э4 | Потребители: упаковщик SCORM, отчёт, неизменяемость актива и снимки |
| Э5 | Медиатека: эскиз, экран, выбор из библиотеки в местах загрузки |
| Э6 | PRD-32: вложения обратной связи поверх медиатеки |
| Позже | Импорт медиа в книге Excel (PRD-14); гранты доступа к отдельному файлу |

## 12. Риски

| Риск | Митигация |
| --- | --- |
| Э2 выключает статику и ломает тихо: остался потребитель на прямом пути — автор видит битую картинку, а не ошибку | Легаси-адреса обслуживаются тем же маршрутом; тест проходит по всем местам хранения медиа и проверяет, что каждый адрес разрешается |
| Разрешение доступа на каждую картинку замедляет экран с множеством изображений | Кеш решения в памяти процесса, сброс при перезаписи индекса (§6.2) |
| Индекс расходится с действительностью и молча отказывает в доступе | Один обходчик на запись и на сверку; административная пересборка с отчётом о расхождениях (§8.1) |
| Растеризация PDF в вебе идёт через `new Image()` с `crossOrigin="anonymous"` ([`export-pdf.ts:176-177`](../../../shared/report/export-pdf.ts)); поведение с защищённым маршрутом надо подтвердить, а не предполагать | Точка приёмки: выгрузка PDF-отчёта в вебе после Э2 |
| Появление новой точки хранения медиа мимо `collectMediaRefs` | Пересборка индекса ловит расхождение; проверка обходчика входит в приёмку каждого этапа, который добавляет поле с медиа |

## 13. Приёмка

- Загрузка одного и того же файла дважды даёт один физический файл и — для одного автора — один
  актив.
- Личный файл автора A не отдаётся автору B; общий отдаётся.
- Учащийся получает картинку вопроса назначенного ему теста и не получает картинку из теста, к
  которому доступа не имеет.
- Прямой запрос `/uploads/media/<файл>` после Э2 не отдаёт файл в обход прав.
- Аудио и видео перематываются (частичный ответ `206`).
- Удаление используемого файла отвечает `409` со списком мест; удаление сироты проходит.
- Экспорт SCORM собирает пакет с медиа из реестра, пакет играется в локальном плеере.
- PDF-отчёт в вебе печатает картинки автора.
- Опубликованный снимок сохраняет свои изображения после того, как автор заменил их в живом
  контенте.
