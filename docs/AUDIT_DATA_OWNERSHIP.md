## Резюме

Гипотеза подтверждается частично.

Что подтверждается: асимметрия модели реальна и создаёт практические риски. Тесты — владельческие
(`tests.ownerId` + гранты `test_access_grants`), а темы, вопросы и папки — глобальный пул без владельца.
Любой автор может изменить или удалить чужую тему/вопрос, на которых построены чужие владельческие тесты,
в том числе опубликованные; выдача и оценивание читают вопросы «вживую», поэтому последствия наступают
немедленно и молча. Кроме того, ключи правильных ответов всех вопросов доступны на чтение и выгрузку
любому автору.

Что не подтверждается: сам по себе общий банк вопросов — не ошибка проектирования. Это осознанное,
задокументированное решение PRD-13 (`role-model.md`, область действия «нет» для `topics.manage` и
`questions.manage`) и стандартный паттерн LMS-систем: банк вопросов с переиспользованием между тестами
и авторами (прямой аналог — question bank в Moodle с раздельными правами «использовать» и «управлять»).
Персональные силосы без механизма обмена фрагментировали бы банк и породили дубли.

Главный вывод: корень проблемы — не отсутствие владения как таковое, а отсутствие двух защитных
механизмов поверх общего контента:

1. Ссылочной защиты — никто не проверяет, используется ли тема/вопрос в чужих тестах, прежде чем
   разрешить изменение или удаление.
2. Неизменяемости опубликованного — опубликованный тест не зафиксирован, его фактическое содержимое и
   скоринг меняются вместе с банком.

Предложение о владении на уровне темы (раздел 4.2, вариант Б) оценено как обоснованное при наличии
требования конфиденциальности ключей между командами авторов: оно закрывает находку F-10, органично
расширяет уже работающий паттерн «владелец + гранты» и совпадает с единицей зависимости тестов —
секции ссылаются именно на темы. При этом оно не отменяет необходимости базового укрепления
целостности (уровень 1) и не решает проблему изменяемости опубликованных тестов (решается только
снапшотом при публикации, уровень 3а).

Предложение о переносе оценочной специфики на уровень теста (раздел 4.3) также оценено как
обоснованное и частично уже реализованное: шкалы и вклады вопросов (PRD-5), показатели результата
(PRD-2), квоты выдачи (PRD-11) и политика пересдач (PRD-6) уже привязаны к тесту. Вне этого принципа
остаются `points` и градуированная оценка `scoringJson` (PRD-10) на вопросе — их корректировка меняет
результаты всех тестов, использующих вопрос. Принято решение о полном выносе: цена и градуировка
удаляются из вопроса, на вопросе остаётся только контент (формулировка, варианты, признак
корректности). Совместимость с динамической выдачей (секции ссылаются на темы, и вопрос, добавленный
в тему позже, должен получать цену в уже настроенных тестах) обеспечивается цепочкой значений по
умолчанию на стороне самого теста: переопределение по вопросу -> дефолт секции -> дефолт теста ->
системное умолчание «1 балл за корректный ответ, частичный зачёт не начисляется». Сложность вопроса
остаётся характеристикой вопроса с возможностью переопределения в конкретном тесте.

Снапшот теста при публикации (3a) принят как целевое системное решение. Следствия: режим публикации
пересматривается — опубликованный тест не принимает изменений до переопубликации, в UI вводится явное
состояние «опубликован, есть неопубликованные изменения»; идущие попытки при переопубликации по
умолчанию доигрываются на снапшоте своей версии, а экстренная переопубликация с прерыванием попыток —
отдельное административное действие (попытка не списывается из лимита PRD-6). Детальная модель — в
разделе 4.4.

## Легенда серьёзности

- Высокая — нарушение целостности или конфиденциальности данных, воспроизводимое штатными действиями
  обычной роли; тихое (без ошибок и предупреждений) воздействие на чужие данные.
- Средняя — несоответствие модели разграничения или утечка сверх необходимого; есть смягчающие факторы.
- Низкая — дефект гигиены данных без прямого ущерба.
- Информационно — зафиксированное и осознанно отложенное ограничение; приводится для полноты картины.

## 1. Текущая модель владения (как есть)

### 1.1 Сущности с владельцем

| Сущность | Механизм | Где реализовано |
| --- | --- | --- |
| `tests` | `ownerId` (nullable; NULL = доступ только админам) | `shared/schema.ts:250-280` |
| `test_access_grants` | гранты `edit`/`assign` на тест, выдаёт только AD/SU | `shared/schema.ts:288-297` |
| Проверка объектного доступа | `canReadTest`/`canEditTest`/`canDeleteTest`/`canAssignTest` | `server/services/test-access.ts` |
| Фильтрация списков | `readableTestScope` (владение + гранты, у AD/SU — всё) | `server/services/test-access.ts:113-132`, применение `server/routes/tests.ts:196-200` |
| Middleware | `requireTestScope(action)` после `requirePermission` | `server/middleware/test-scope.ts` |

Модель PRD-13: владелец редактирует, публикует, экспортирует и удаляет свой тест; грант `edit` даёт
редактирование без удаления; грант `assign` — назначение и просмотр результатов. Гранты управляются
централизованно администратором.

### 1.2 Сущности без владельца

| Сущность | Колонка владельца | Фильтрация списков | Разрушающие операции |
| --- | --- | --- | --- |
| `topics` | нет (`shared/schema.ts:101-107`) | нет — все темы всем авторам | удаление/правка любым автором (`server/routes/topics.ts:91-117`) |
| `questions` | нет (`shared/schema.ts:182-203`) | нет — все вопросы всем авторам | удаление/правка любым автором (`server/routes/questions.ts`) |
| `folders` | нет (`shared/schema.ts:95-99`) | нет | любым автором |
| `test_folders` | нет (`shared/schema.ts:205-210`) | нет | любым автором |

Доступ ограничен только способностью (capability) `topics.manage` / `questions.manage` /
`folders.manage`, которой обладает каждый автор, администратор и суперадминистратор. Объектных проверок
нет вовсе: ни владения, ни проверки использования.

Для сравнения: у `groups` и `users` колонка `createdBy` есть (`shared/schema.ts:31`) — авторство
контентных сущностей не фиксируется даже для аудита.

### 1.3 Test-scoped дочерние сущности (последовательная часть модели)

`content_pages`, `result_variables`, `scales`, `question_measurements` привязаны к тесту по `testId`
с каскадным удалением и защищены через `requireTestScope` в своих роутерах. Эта часть модели
консистентна: доступ к дочерней сущности следует за доступом к тесту-родителю.

### 1.4 Цепочка зависимостей и точки заморозки

Цепочка: `tests -> test_sections (topicId) -> topics -> questions (topicId)`.

- `test_sections.topicId` не имеет FK-ограничения (`shared/schema.ts:336-356`) — при удалении темы
  остаются висячие секции.
- Выдача вопросов при старте попытки — живое чтение `getQuestionsByTopic(section.topicId)`
  (`server/routes/attempts.ts:115-139`); пустой пул не считается ошибкой, секция молча выдаёт
  0 вопросов, имя удалённой темы отображается как `Unknown`.
- Оценивание — живое чтение текущей строки вопроса: адаптивный ответ `server/routes/attempts.ts:367-373`,
  завершение попытки `server/routes/attempts.ts:713-724`. Колонка `attempts.testVersion`
  (`shared/schema.ts:390`) записывается, но ничего не фиксирует — вопросы не версионированы.
- Точки заморозки существуют только постфактум: `resultJson.detailedAnswers` фиксирует формулировку и
  правильный ответ в момент завершения (`shared/schema.ts:744-760`); SCORM-пакет запекает вопросы в
  момент экспорта; телеметрия SCORM снапшотит ответы (`shared/schema.ts:994-1024`). Живая веб-доставка
  не защищена ничем.

### 1.5 Задокументированность решения

Общий банк — осознанное решение, а не упущение:

- `role-model.md:71-74` — для `topics.manage`, `questions.manage`, `questions.importExport`,
  `folders.manage` область действия указана как «нет» (без объектного scope).
- PRD-14 явно проектирует импорт «в общий банк» (`docs/specs/prd-14/questions-import-export.md`),
  лист Questions книги Excel не имеет привязки к тесту.
- Отложенные пункты зафиксированы: глубокий scope аналитических агрегатов
  (`acceptance-matrix.md:82-85`), организации и scoping менеджеров (PRD-13, раздел «Перспектива вне
  объёма»).

## 2. Оценка текущей парадигмы

### 2.1 Преимущества

- Переиспользование контента. Один вопрос/тема служит многим тестам разных авторов; нет дублей,
  правка опечатки делается один раз. На этом построен PRD-14 (импорт в общий банк) и механика выдачи
  по темам (PRD-11, квоты по тегам).
- Простота модели и реализации. Нет грантов на контент, нет UI управления доступом к банку, нет
  миграций владения; порог входа для автора минимален.
- Последовательность с корпоративным сценарием «одна команда — один банк»: пока авторы доверяют друг
  другу, модель работает без накладных расходов.
- Соответствие отраслевой практике: общий банк вопросов — типовой паттерн LMS (Moodle question bank,
  банки вопросов в корпоративных конструкторах тестов).

### 2.2 Ограничения

- Модель доверия «все авторы равны над всем контентом» перестаёт работать при нескольких независимых
  командах авторов или внешних авторах-подрядчиках.
- Нет даже аудита авторства (`created_by`) — невозможно ответить «кто создал/правил этот вопрос»
  средствами данных (частично закрывается журналом аудита действий, но не атрибутом сущности).
- Нет понятия «где используется» — ни API, ни UI не показывают, какие тесты зависят от темы/вопроса.
- Конфиденциальность ключей отсутствует как класс: `correctJson` всех вопросов читается любым автором
  и выгружается в Excel целиком (`questions.importExport`).
- Асимметрия с тестами: владельческая модель тестов создаёт у автора ожидание «мой тест защищён»,
  которое не выполняется — содержимое теста (вопросы) защищено не его владением, а ничем.

### 2.3 Риски

Риски детализированы в находках раздела 3; сводно:

- Целостность: тихое разрушение чужих опубликованных тестов удалением темы/вопроса (F-1, F-3, F-8).
- Корректность оценивания: правка вопроса меняет скоринг идущих и будущих попыток всех тестов (F-2).
- Конфиденциальность: ключи ответов доступны всем авторам; аналитика и дизайн теста читаются шире
  заявленной модели (F-5, F-6, F-10).
- Эксплуатация: случайная FK-защита даёт непредсказуемые 500 вместо понятного отказа (F-4).

### 2.4 Вердикт по гипотезе

Формулировка «ломает логику» верна в следствиях, но неточна в причине. Логику ломает не отсутствие
владения темами/вопросами, а отсутствие защитных инвариантов поверх общего контента: ссылочной защиты
и неизменяемости опубликованного. Введение владения — один из способов получить эти инварианты
(и единственный способ закрыть конфиденциальность ключей), но без ссылочной защиты владельческие темы
сами по себе проблему целостности не решают: владелец темы точно так же может удалить вопрос под
чужим опубликованным тестом.

### 3.2 Детализация

#### F-1. Удаление общего контента без проверки использования (Высокая)

`DELETE /api/topics/:id` и `POST /api/topics/bulk-delete` требуют только `topics.manage`
(`server/routes/topics.ts:91-117`). `storage.deleteTopic()` вручную каскадирует удаление всех вопросов
темы (`server/storage.ts:823-838`). Ни владение, ни использование темы в чужих тестах не проверяются.
Опубликованный тест другого автора при следующей попытке молча выдаёт секцию с 0 вопросов
(`server/routes/attempts.ts:115-139`). Аналогично для удаления отдельного вопроса.

#### F-2. Изменяемость опубликованного: живое оценивание (Высокая)

Попытка хранит только `questionIds` в `variantJson`; проверка ответа и финальное оценивание читают
текущую строку вопроса из БД (`server/routes/attempts.ts:367-373`, `713-724`). Правка `correctJson`,
вариантов или баллов вопроса немедленно меняет результат идущих и будущих попыток каждого теста,
выдающего этот вопрос, включая опубликованные. Удалённый в середине попытки вопрос молча исчезает из
знаменателя оценки. Заморожены только уже выгруженные SCORM-пакеты и уже завершённые результаты.
Оценочные параметры — цена `points` и градуированная оценка `scoringJson` (PRD-10) — также живут на
вопросе и общие для всех тестов (`shared/schema.ts:189,202`): корректировка под один тест меняет
балльность остальных.

#### F-3. Тихое разрушение шкал чужих тестов (Высокая)

`question_measurements.question_id` объявлен `ON DELETE CASCADE` (миграция
`migrations/009_prd5_scales_question_measurements.sql`, `shared/schema.ts:1276-1289`). Удаление
вопроса любым автором без предупреждения удаляет вклады этого вопроса в шкалы (PRD-5) во всех тестах
всех владельцев.

#### F-4. Случайная и непрозрачная ссылочная защита (Средняя)

`content_pages.topic_id` имеет реальный FK на `topics` (миграция
`migrations/002_prd1_templates_content_pages.sql`). Если у какой-то темы есть topic-scoped страницы,
удаление темы падает на FK и роут возвращает общий `500 Failed to delete topic`
(`server/routes/topics.ts:98-100`). Защита срабатывает частично (только при наличии страниц), с
неверным статусом и без объяснения причин — пользователь не может понять, почему удаление «сломалось».

#### F-5. Аналитика без объектного scope (Средняя)

`/api/analytics/combined`, `/summary`, `/combined-full`, `GET /analytics/attempts/:attemptId`,
`/export/filters`, `POST /export/excel`, `/export/excel-lms`, общий `/api/analytics` и scorm-агрегаты
защищены только capability `analytics.read`/`analytics.export` без фильтрации через
`readableTestScope` (`server/routes/analytics/combined.ts`, `attempts.ts`, `export.ts`, `general.ts`,
`scorm.ts`). Автор видит и выгружает результаты тестов, которыми не владеет. Ограничение зафиксировано
как отложенное в `acceptance-matrix.md:82-85` — находка повышает его приоритет, поскольку усиливает
общий разрыв модели разграничения.

#### F-6. Чтение дизайна теста шире модели (Средняя)

`GET /api/tests/:id/design` (`server/routes/tests.ts:476`) и `GET /api/tests/:id/screen-template/:screen`
(`server/routes/tests.ts:274`) защищены только `requireAuth` — любой аутентифицированный пользователь
читает настройки оформления любого теста. Смежно: `canReadTest`
(`server/services/test-access.ts:31-40`) не содержит ветки «тест назначен пользователю»,
предусмотренной `role-model.md` п. 6.4 — при наивном навешивании `requireTestScope("read")` на эти
эндпоинты сломается рантайм ученика. Сначала привести `canReadTest` в соответствие с моделью, затем
закрывать эндпоинты.

#### F-7. Отсутствие аудита авторства контента (Средняя)

У `groups` и `users` есть `createdBy`; у контентных сущностей (`topics`, `questions`, `folders`,
`test_folders`) — нет. Невозможно ни отобразить «мои вопросы», ни ограничить разрушающие операции
создателем, ни расследовать инцидент по данным. Это базовая колонка, нужная любому из вариантов
развития модели (раздел 4).

#### F-8. Гигиена удаления темы (Низкая)

`storage.deleteTopic()` удаляет вопросы и `topic_courses`, но не `topic_events` (осиротевшие строки) и
не трогает `test_sections` с этим `topicId` (висячие секции, отображаются как `Unknown`).

#### F-9. Однотенантность (Информационно)

Понятия организации нет; менеджеры видят всех пользователей и группы. Осознанно отложено
(PRD-13, «Перспектива вне объёма»; `docs/AUDIT_ARCHITECTURE_REQUIREMENTS.md`). Приводится, потому что
выбор модели владения темами (раздел 4.2) стоит делать с оглядкой на возможное появление тенантов.

#### F-10. Конфиденциальность ключей ответов (Средняя)

`GET /api/questions` возвращает строки вопросов целиком, включая `correctJson`, любому обладателю
`questions.manage` (каждому автору); `questions.importExport` позволяет выгрузить весь банк с ключами
в Excel. В текущей модели это «по построению», но при нескольких командах авторов или внешних авторах
превращается в канал утечки ключей. Смежные каналы, которые скоупингом контента не закрываются: SCORM-пакет
содержит ключи в самом пакете (клиентская проверка ответов — ученик технически может извлечь ключ из
выгруженного архива), `detailedAnswers` в результатах попытки.

## 4. Предложения по модификации

Предложения разбиты на четыре блока. Уровень 1 — фундамент, нужный при любом дальнейшем выборе.
Уровень 2 — выбор целевой модели доступа к контенту (два альтернативных варианта). Раздел 4.3 —
перенос оценочной специфики на уровень теста (ортогональная мера, сочетается с любым вариантом).
Уровень 3 — структурные изменения с отдельным обоснованием.

### 4.1 Уровень 1. Базовое укрепление целостности (обязательный фундамент)

Состав:

- Колонка `created_by varchar(36) NULL` для `topics`, `questions`, `folders`, `test_folders`
  (аддитивная миграция по образцу `groups.createdBy`; legacy-строки остаются NULL с политикой
  «разрушающие операции над NULL-контентом — только администратор»).
- Запрос «где используется»: `getTestsUsingTopic(topicId)` (join `test_sections` -> `tests`, вернуть
  id/название/владельца/статус) и `getTestsUsingQuestion(questionId)` (через тему вопроса +
  `question_measurements`). Индекс по `test_sections.topic_id`.
- Ссылочная защита: на DELETE/bulk-delete (и на правку, меняющую оценивание) темы/вопроса, который
  используется тестами, недоступными актору на запись, — отказ `409` со списком зависимых тестов.
  Реализация — middleware по образцу `server/middleware/test-scope.ts`.
- Проверка выполнимости выдачи (единый сервис): по теме/вопросу и предполагаемой мутации проверяет
  каждый зависимый тест — пул не меньше `drawCount`, выполнимость квот по тегам, наполненность
  адаптивных уровней, целостность вкладов шкал. Обязательный охват — матрица граничных случаев ниже;
  вызывается из одиночных, массовых и импортных путей и при публикации теста (естественное место —
  расширение `server/services/flow-policy-validator.ts`).
- Ограничение разрушающих операций: удалять/править контент может создатель и администратор
  (до выбора модели уровня 2 — мягкая политика, конфигурируемая).
- Закрытие F-4 (вместо случайного FK-500 — осмысленный 409 с причинами), F-8 (доудаление
  `topic_events`, запрет или зачистка висячих `test_sections`), F-5 (фильтрация аналитики через
  `readableTestScope`, объектная проверка attempt-by-id), F-6 (выровнять `canReadTest` с role-model
  п. 6.4, затем закрыть `/design` и `/screen-template` объектной проверкой).
- Документация: правки начинаются с `role-model.md` (разделы 3 и 9), как предписывает сам документ.

#### Матрица граничных случаев деградации (обязательный охват защиты)

Политика по умолчанию: если затронут опубликованный тест — блокировка `409` со списком зависимых
тестов и причин (с административным переопределением); если только черновики — предупреждение без
блокировки.

| № | Сценарий | Эффект сегодня | Правило предотвращения |
| --- | --- | --- | --- |
| E-1 | Удаление вопросов темы, после которого пул меньше `drawCount` секции опубликованного теста | Секция молча выдаёт меньше вопросов, знаменатель оценки сжимается | Блокировка для опубликованных, предупреждение для черновиков |
| E-2 | Удаление темы, используемой в опубликованных тестах (находка F-1) | Секция выдаёт 0 вопросов, имя темы `Unknown`, висячие `test_sections` | Блокировка; удаление возможно после исключения темы из тестов |
| E-3 | Удаление или перетегирование вопросов, делающее квоты `drawBlueprintJson` (PRD-11) невыполнимыми | Выдача нарушает квоты или молча сжимается | Проверка выполнимости квот по тегам по каждому зависимому тесту |
| E-4 | Правка `difficulty` (или переопределения в тесте), опустошающая уровень адаптивной выдачи | Адаптивный уровень остаётся без вопросов | Проверка минимального пула по уровням адаптивных тестов |
| E-5 | Удаление вопроса, имеющего вклады в шкалы (находка F-3) | Каскад `question_measurements` тихо разрушает шкалы PRD-5 чужих тестов | Блокировка при вкладах в опубликованных или чужих тестах |
| E-6 | Удаление или перетегирование вопросов, обнуляющее агрегаты формул PRD-2 по тегам | Показатели считаются по пустому множеству | Предупреждение со списком затронутых показателей; блокировка для опубликованных |
| E-7 | Правка состава вариантов вопроса, используемого опубликованными тестами | Протухают переопределения цены (`contentHash`), идущие попытки оцениваются по новой структуре | Предупреждение + пометка устаревших переопределений; полная защита — только снапшот (3a) |
| E-8 | Удаление вопроса во время идущих попыток | Вопрос молча исчезает из знаменателя оценки (`attempts.ts:713-724`) | Блокировка при активных попытках либо фиксация знаменателя по варианту попытки |
| E-9 | Сжатие пула темы при секциях с `drawAll` | `drawCount` не нарушен, но тест молча становится короче | Предупреждение (блокировка не требуется) |
| E-10 | Массовые операции (`bulk-delete`) и импорт PRD-14 в режиме замены | Обходят одиночные проверки | Те же проверки во всех мутирующих путях; dry-run импорта показывает влияние до применения |
| E-11 | Перевод темы в `private` (вариант Б) при использовании чужими тестами | Доставка не страдает (инвариант), но владельцы тестов теряют редактирование секций | Не блокировать; индикатор недоступной темы в редакторе теста |
| E-12 | Публикация теста с заведомо невыполнимой выдачей (обратная сторона E-1/E-3/E-4) | Деградация закладывается в момент публикации | Publish-time валидация выполнимости выдачи |
| E-13 | Отзыв гранта на тему у автора, чьи тесты её используют (вариант Б) | Тест работает (инвариант), но автор теряет видимость содержимого собственного теста; живая выдача продолжает открывать ему новые вопросы темы | Мягкий отзыв по умолчанию (производное чтение в контексте теста); жёсткий — только через разрешение зависимостей; полное отсечение — снапшот 3a (модель в разделе 4.2) |

Случаи E-1 - E-10 закрываются одним сервисом проверки выполнимости выдачи (см. состав выше); E-12 —
вызов того же сервиса при публикации; жёсткий отзыв гранта (E-13) использует его же для перечисления
зависимостей. Проверка обязана работать от эффективного состояния (с учётом переопределений сложности
из раздела 4.3). Существующий dry-run импорта PRD-14 — готовая точка встраивания для E-10.

Затрагиваемые файлы: `shared/schema.ts`, новая миграция, `server/storage.ts`,
`server/routes/topics.ts`, `server/routes/questions.ts`, `server/routes/folders.ts`,
`server/routes/analytics/*`, `server/routes/tests.ts`, `server/services/test-access.ts`,
`docs/specs/access-control/role-model.md`.

Миграции: только аддитивные, без backfill. Трудоёмкость: 4-8 человеко-дней с тестами (включая сервис
выполнимости выдачи). Риски: трение
от блокировки удаления в малых инсталляциях (смягчение — 409 со списком блокеров и админский
override); политика NULL-создателя должна быть явно описана.

### 4.2 Уровень 2. Целевая модель доступа к контенту (выбор из двух вариантов)

#### Вариант А. Общий банк + разделение прав «использовать» и «управлять»

Сохранить единый банк, разделить capability на `*.use` (видеть и использовать контент в своих тестах —
остаётся у каждого автора) и `*.manage` (создавать/править/удалять — своё + администратор всё).
Прямой аналог — модель прав question bank в Moodle.

- Закрывает: защиту от правки/удаления чужого (вместе с уровнем 1).
- Не закрывает: F-10 — читать вопросы (включая ключи) по-прежнему могут все авторы, иначе они не
  смогут использовать банк.
- Изменения: каталог способностей `shared/access/*`, `role-model.md`, точки `requirePermission` в
  роутерах контента, фильтры «мои/все» в UI банка.
- Трудоёмкость: 1.5-3 человеко-недели. Риски: минимальные; UX почти не меняется.

Вариант А уместен, когда все авторы — одна доверенная команда и требования конфиденциальности ключей
между авторами нет.

#### Вариант Б. Владение на уровне темы (предложение заказчика)

Отказ от глобального банка без введения новой агрегирующей сущности: единицей владения и доступа
становится тема. Вопросы наследуют область видимости через свою тему (`questions.topicId` уже
существует). Тема — естественная единица скоупа именно в этой системе: секции тестов ссылаются на
темы (`test_sections.topicId`), поэтому гранулярность доступа совпадает с единицей зависимости
тестов, а проверка при сохранении теста выполняется напрямую по `topicId` секции, без дополнительных
связей.

Предлагаемая схема (зеркально работающему паттерну тестов PRD-13):

- Колонки `topics.owner_id varchar(36) NULL` и `topics.visibility` (`private` | `shared`).
- Таблица `topic_access_grants` (`topic_id`, получатель — пользователь или группа, `access_level`
  из `use` | `manage`, `granted_by`) — по образцу `test_access_grants` (`shared/schema.ts:288-297`).
  Гранты на группу (таблица `groups` уже есть) обязательны в первой же версии — без них модель
  утонет в индивидуальных грантах (см. риски).
- Семантика: `use` — видеть тему и её вопросы, использовать в своих тестах; `manage` — CRUD вопросов
  темы и правка самой темы; владелец — полный доступ, передача владения администратором, как у
  тестов. `visibility = shared` — тема видна всем авторам на уровне `use`; `manage` — по владению и
  грантам.

Точки контроля доступа:

- Фильтрация списков `GET /api/topics`, `/api/questions` по видимым актору темам (паттерн
  `readableTestScope`, но для тем).
- Валидация при сохранении теста: секции могут ссылаться только на доступные актору темы.
- Импорт PRD-14: сопоставление тем по имени — только в видимой импортёру области; если тема не
  найдена — создаётся новая с владельцем-импортёром. Экспорт — только видимые темы.
- Шаблон книги Excel и инспекция листов — без изменений.

Критический инвариант: путь доставки и оценивания (выдача вопросов при старте попытки, грейдинг,
уже собранный SCORM-пакет) права на тему НЕ проверяет. Ученик проходит тест по назначению; доступ к
теме — конструкт времени авторинга. Иначе отзыв гранта у автора обрушит опубликованные тесты,
собранные на этой теме.

Честная оценка заявленного плюса (нивелирование утечки ключей):

- Подтверждается: F-10 между авторами закрывается — автор без доступа не видит ни вопросов, ни
  ключей чужих приватных тем ни в API, ни в экспорте. Поверхность доступа к ключам сокращается с
  «все авторы» до «авторы с доступом к теме». Это единственный из рассмотренных вариантов, дающий
  такой эффект.
- Ограничения эффекта: отзыв гранта не отзывает уже увиденные ключи (автор мог выгрузить тему, пока
  имел доступ); утечка ключей ученикам через SCORM-пакет — отдельный канал, скоупингом не решается
  (клиентская проверка ответов в пакете — архитектурное свойство SCORM-экспорта); результаты с
  `detailedAnswers` показывают ключ уже после завершения попытки.

Издержки и риски варианта Б:

- Разрастание грантов: при сотнях тем и нескольких командах авторов доступы превращаются в большое
  число индивидуальных записей. Смягчения, в порядке приоритета: гранты на группы; `visibility =
  shared` для общекорпоративных тем; массовые операции в UI (выдать доступ к набору тем разом).
  Если темы начнут исчисляться сотнями с пакетной выдачей доступов — вернуться к агрегирующей
  сущности «банк» как надстройке над темами; на текущем масштабе она избыточна.
- Фрагментация и дубли: автор, не видящий чужую тему, создаст её аналог. Частично купируется
  политикой одноимённости (ниже) и админским отчётом о дублях.
- Административная нагрузка: принято (решение BRD) — гранты на свою тему выдаёт и отзывает сам
  владелец, администратор — на любые; модель выдачи одновременно унифицирована и для тестов
  (BRC-27 уточняет BR-08 PRD-13: владелец теста также выдаёт гранты на свои тесты). Единое правило
  «владелец — на своё, администратор — на любое» снимает админ-бутылочное горлышко.
- Кросс-тематические тесты: тест использует несколько тем; при потере гранта тест продолжает
  работать (инвариант доставки). Чтобы автор при этом не терял видимость содержимого собственного
  теста, отзыв гранта оформляется по полной модели — см. блок «Отзыв гранта при использовании темы»
  ниже.
- Миграция: legacy-темы получают `owner_id = NULL`, `visibility = shared` — поведение в день один
  не меняется; новые темы — владелец-создатель. Видимость новой темы по умолчанию: принято (решение
  BRD) — `private` с одношаговой операцией «сделать общей»; это соответствует заявленному драйверу
  конфиденциальности и безопасному умолчанию.

Отзыв гранта при использовании темы в тестах (модель полной защиты):

Блокировать отзыв по умолчанию — неверное решение, по трём причинам. Во-первых, проблема заложника:
владелец темы не может отозвать доступ, пока получатель держит хотя бы одну секцию на этой теме, —
выданное право фактически становится бессрочным, что противоречит самому драйверу конфиденциальности.
Во-вторых, с грантами на группы блокировка неработоспособна: исключение пользователя из группы
пришлось бы запрещать из-за тестов любого её участника. В-третьих, блокировка не решает настоящую
задачу: доставка читает вопросы темы вживую, поэтому даже полностью скрытая из банка тема продолжает
«утекать» отозванному автору через его же тест — ученики получают в выдаче новые вопросы, автор видит
их в результатах попыток. Полная защита требует фиксации содержимого или разрыва связи, а не запрета
отзыва.

Рекомендуемая модель — два режима отзыва плюс системное решение:

- Мягкий отзыв (по умолчанию): грант переходит в состояние «отозван, используется» — тема исчезает
  из банка для получателя, её нельзя добавлять в новые тесты и секции, но для уже существующих
  тестов получателя сохраняется производное право чтения «тема в контексте моего теста»: состав
  секции, просмотр вопросов выдачи, статистика по вопросам. Доставка не меняется. Полуразрушенное
  состояние «владелец теста не видит содержимого собственного теста» не возникает.
- Жёсткий отзыв (административный): тот же сервис выполнимости выдачи (матрица E) возвращает `409`
  со списком зависимых тестов и явными вариантами разрешения — заменить или удалить секции на теме;
  снять зависимые тесты с публикации; сменить владельца теста; материализовать снапшот содержимого
  в тест. Принудительный отзыв без разрешения зависимостей — только административным переопределением
  с записью в журнал аудита.
- Системное решение — снапшот при публикации (3a): опубликованный тест доставляется из
  зафиксированного снапшота, поэтому отзыв любого режима не влияет на доставку и действительно
  отрезает получателя от будущих изменений темы; для повторной публикации с обновлённым составом
  требуется действующий грант. Это единственный механизм, который одновременно сохраняет работу
  теста, прекращает доступ к будущему контенту и не превращает отзыв в заложника зависимостей —
  ещё один аргумент поднять приоритет 3a.

Политика одноимённых тем (рекомендация по лучшим практикам):

- Жёсткая глобальная уникальность имён при скоупинге вредна: автор не видит чужую приватную тему,
  и отказ «такая тема уже есть» одновременно блокирует легитимное создание и раскрывает
  существование невидимого контента (канал утечки информации о чужой области).
- Рекомендуемая политика: предупреждение без блокировки при совпадении нормализованного имени
  (обрезка пробелов, регистр, повторные пробелы, е/ё) с темой в видимой автору области — «такая
  тема уже есть, использовать её?»; жёсткая уникальность — только внутри области одного владельца
  (частичный уникальный индекс по `owner_id` + нормализованное имя).
- Дубли между невидимыми друг другу областями — зона администратора (он видит всё): периодический
  отчёт о дублях по всему банку с предложением слияния, а не отказ автору при создании.

Судьба папок:

- Папки уже сейчас чисто организующая (косметическая) сущность: структуру тестов определяют темы
  (`test_sections.topicId`), папки лишь группируют отображение (`topics.folderId`,
  `folders.parentId`).
- При скоупинге тем потребность в папках снижается — каждый автор видит меньше тем. Папки
  сохраняются как общая организующая структура без владения; UI скрывает папки, не содержащие
  видимых актору тем. Базовые меры уровня 1 (`created_by`, ограничение разрушающих операций)
  к папкам применяются как и прежде.
- Если в будущем чужие пустые ветки начнут мешать, папки можно сделать персональными без миграции
  контента — отдельное косметическое решение, не влияющее на модель доступа.

Затрагиваемые файлы: `shared/schema.ts` + 1 миграция, `server/storage.ts`,
`server/routes/topics.ts`, `questions.ts`, `folders.ts`, `server/routes/workbook.ts` и
`server/services/workbook-import.ts` (сопоставление тем в видимой области), новый сервис доступа к
темам (по образцу `server/services/test-access.ts`), клиент: фильтры «мои / доступные / общие»,
управление грантами темы, предупреждение об одноимённости.

Трудоёмкость: 2-3.5 человеко-недели (меньше банковой компоновки — нет новой агрегирующей сущности и
backfill привязки контента). Риски управляемы при соблюдении инварианта доставки, shared-миграции
legacy-тем и грантах на группы с первой версии.

### 4.3 Перенос оценочной специфики на уровень теста (предложение заказчика)

Идея: вопрос — только контент (формулировка `prompt`, варианты `dataJson`, отметка правильного
ответа `correctJson`, медиа, обратная связь); всё, что влияет на результаты теста, — в самом тесте.
Цель — исключить деградирующее влияние тестов друг на друга при корректировке оценивания. Мера
ортогональна выбору варианта А/Б и может выполняться отдельной фазой.

Что уже соответствует этому принципу (система наполовину устроена именно так):

- Шкалы и вклады вопросов в шкалы — на тесте: `scales.testId`, `question_measurements`
  (`test_id`, `question_id`, `scale_id`) — PRD-5.
- Показатели результата — на тесте: `result_variables.testId` — PRD-2.
- Квоты выдачи по тегам — на секции теста: `test_sections.draw_blueprint_json` — PRD-11.
- Политика пересдач — на тесте: `tests.retake_policy_json` — PRD-6.

Что сегодня живёт на вопросе и влияет на результат всех тестов (`shared/schema.ts:182-203`):

- `points` — цена вопроса (целое, по умолчанию 1);
- `scoringJson` — градуированная оценка PRD-10 (веса вариантов или ступенчатая таблица);
- `difficulty` — используется адаптивным режимом;
- косвенно `tags` — классификация, питающая квоты PRD-11 и формулы PRD-2.

Принятая модель: полный вынос оценки из вопроса. `points` и `scoringJson` удаляются из `questions`
(после миграции); вопрос несёт только контент — формулировку, варианты, признак корректности, медиа,
обратную связь. Вся цена — свойство теста.

- Цепочка цены на стороне теста: переопределение по конкретному вопросу -> дефолт секции -> дефолт
  теста -> системное умолчание. Системное умолчание принято: 1 балл за полностью корректный ответ,
  частичный зачёт не начисляется (бинарная проверка точного совпадения — текущее поведение при
  отсутствии `scoringJson`, FR-02 PRD-10, что упрощает миграцию). Новая таблица
  `test_question_scoring` (`test_id`, `question_id`, `points`, `scoring_json`, `difficulty`,
  `pinned_content_hash`) — прямой аналог уже существующей `question_measurements`, паттерн проверен
  PRD-5; плюс `test_sections.default_points` и `tests.default_question_points` (для адаптивного
  режима, где выдача идёт по уровням, а не по секциям, действует дефолт теста).
- Совместимость с динамической выдачей: секции ссылаются на темы, а не на конкретные вопросы, поэтому
  вопрос, добавленный в тему после настройки теста, автоматически получает цену из дефолтов самого
  теста — ручная донастройка существующих тестов не требуется, принцип «вся оценка в тесте» не
  нарушается. (Отраслевой аналог — Moodle с переопределением балла на слоте квиза; предлагаемая
  модель строже: у вопроса нет даже значения по умолчанию.)
- Привязка к контенту: переопределение градуированной оценки ссылается на конкретные варианты ответа
  (веса вариантов); при правке состава вариантов вопроса переопределения тестов могут устареть.
  На вопросе уже есть `contentHash` (`shared/schema.ts:198`) — переопределение пиннится к хешу,
  редактор показывает признак «настройка устарела» при расхождении.
- Миграция: backfill перед удалением колонок — в `test_question_scoring` копируются только значения,
  отличающиеся от системного умолчания (цена не равна 1 либо настроена градуировка), для каждого
  теста и каждого вопроса тем его секций; дефолты секций/теста не заполняются — действует умолчание
  «1 балл, без частичного зачёта». Удаление колонок из `questions` — отдельной завершающей миграцией
  после проверки паритета результатов.
- Сложность: `difficulty` остаётся характеристикой вопроса (базовое значение, обеспечивающее
  сопоставимость заданий между тестами), но может переопределяться в конкретном тесте — колонка
  `difficulty` в `test_question_scoring`. Адаптивный подбор обязан учитывать эффективную сложность
  (переопределение теста поверх значения вопроса) — затрагивается логика выдачи по уровням.
  `tags` — контентная классификация, остаётся на вопросе без переопределений.

Что закрывает и что нет:

- Закрывает оценочную часть F-2: корректировка цены или градуировки под один тест перестаёт влиять
  на остальные. В сочетании с владением темами (вариант Б) контент защищён от чужой правки, а
  оценивание изолировано по тестам.
- Не закрывает контентную часть F-2: формулировка и `correctJson` остаются общими — их правка
  по-прежнему меняет все тесты; полная фиксация — только снапшот при публикации (3a).

Затрагиваемое: `shared/schema.ts` + две миграции (backfill, затем удаление колонок); движок проверки
`server/utils/check-answer.ts` и `shared/scoring/*` (приём эффективной цены извне);
`server/services/result-compute.ts`; адаптивная выдача по уровням (`shared/draw/`, адаптивный рантайм —
учёт эффективной сложности при переопределении); сборка SCORM-пакета `server/scorm/builders/test-json.ts` —
запекание эффективных цен в данные пакета (проверять рантайм-плеером: прецедент непрокинутых в пакет
полей уже был в PRD-10/11); книга Excel PRD-14 — колонки оценки уходят из глобального листа Questions
в test-scoped лист (учесть, пока трек импорта активен); клиент: карточка вопроса теряет поле цены и
конструктор градуировки (`questions.tsx`, `scoring-builder.tsx` переезжает в редактор теста),
редактор теста получает дефолты и переопределения по вопросам секций.

Трудоёмкость: 2.5-3.5 человеко-недели. Риски: паритет результатов до и после миграции (обязательная
проверка существующими golden-тестами скоринга и сверкой пересчёта попыток); рост числа настроек в
редакторе теста (смягчение — цепочка дефолтов и массовое выставление); устаревание переопределений
при правке вопросов (смягчение — пиннинг к `contentHash`); цепочка «переопределение -> секция ->
тест» должна быть явно видна в UI, иначе автор не поймёт действующую цену.

### 4.4 Уровень 3. Структурные изменения

3a — снапшот теста при публикации (версионирование) — принят как целевое решение. Единственное
полное решение F-2: без него правка вопроса (при любой модели доступа к контенту) продолжает менять
опубликованные тесты; также завершает модель отзыва грантов варианта Б (E-13) и системно закрывает
E-7/E-8. Детальная модель — ниже. 3b — организации/тенанты — остаётся отложенным.

#### Модель публикации со снапшотами (3a, целевое решение)

Жизненный цикл:

- Рабочая версия теста всегда редактируема — публикация не блокирует редактор. Публикация = создание
  снапшота версии N (таблица `test_snapshots(test_id, version, content_json, published_at,
  published_by)`); доставка обслуживается только снапшотом.
- Правки после публикации (настройки теста, состав секций, а также изменения пулов тем владельцами
  контента) не влияют на доставку до переопубликации. Переопубликация = снапшот версии N+1.
- Снапшот хранит разрешённые эффективные значения: вопросы выдачи целиком (формулировка, варианты,
  ключи), цены, вычисленные по цепочке раздела 4.3, переопределения сложности, шкалы, показатели,
  квоты, страницы контента. Следствия: доставка самодостаточна (не зависит от живого банка); 3a
  развязан с 4.3 (формат снапшота не зависит от того, где живут цены); веб-доставка начинает вести
  себя как уже выгруженный SCORM-пакет — единая ментальная модель с PRD-12.

Состояния в UI (обязательная индикация):

- «Черновик» — снапшота нет, доставки нет.
- «Опубликован» — рабочая версия совпадает со снапшотом.
- «Опубликован, есть неопубликованные изменения» — рабочая версия разошлась со снапшотом; действие
  «Опубликовать изменения». Признак изменений из двух источников: правки самого теста (отслеживаются
  точно) и дрейф пулов тем (вычисляется сравнением `contentHash` вопросов и состава пулов со
  снапшотом — показывается как «содержимое тем обновилось»).

Идущие попытки при переопубликации:

- По умолчанию — доигрывание на своей версии: попытка при старте пиннит версию снапшота
  (`attempts.testVersion` становится реальным пином), продолжается и оценивается по ней даже после
  выхода N+1; новые попытки стартуют на N+1. Попытки не ломаются, оценивание детерминировано,
  знаменатель зафиксирован (системное закрытие E-8).
- Экстренная переопубликация (отдельное осознанное действие, администратор или владелец): идущие
  попытки прерываются и аннулируются, попытка не списывается из лимита PRD-6, ученик получает
  уведомление с предложением пройти заново. Применение — инциденты (утёкший ключ, грубая ошибка в
  вопросе), не штатный путь.
- Аналитика получает разрез по версии снапшота; вопросные статистики читаются из снапшота, а не из
  живого банка.

Хранение и сопутствующее:

- Снапшоты удерживаются, пока на них ссылаются попытки (плюс актуальный); рост объёма — риск,
  смягчение — сжатие `content_json` и политика удержания для версий без ссылок.
- Экспорт SCORM читает актуальный снапшот (а не живой банк) — устраняется расхождение «пакет
  собран из других данных, чем играет веб».
- Правила матрицы E уровня 1 сохраняются: для черновиков (их доставка-предпросмотр живая) и как
  защита переходного периода до внедрения 3a; после внедрения E-7/E-8 закрываются снапшотом
  автоматически.

Затрагивает: рантайм попыток (старт/ответ/завершение читают снапшот), адаптивный режим, аналитику,
экспорт SCORM, редактор теста (состояния, действие переопубликации, индикатор дрейфа). Трудоёмкость:
4-7 человеко-недель (модель публикации + политика идущих попыток + аналитика по версиям).

#### Организации и тенанты (3b, остаётся отложенным)

Скоупинг пользователей, групп, тем и тестов по организации. Остаётся отложенным (PRD-13,
«Перспектива вне объёма») до появления реального мультиорганизационного требования; выбор варианта Б
в уровне 2 упрощает будущий переход (владельческие темы естественно скоупятся организацией
владельца).

## 6. Рекомендация и очерёдность

1. Уровень 1 выполнить безусловно и в первую очередь: он закрывает самые острые риски целостности
   (F-1, F-3, F-4, F-8) по матрице граничных случаев E-1 - E-13 (раздел 4.1), уже признанные долги
   разграничения (F-5, F-6) и создаёт данные авторства (F-7), без которых ни один вариант уровня 2
   невозможен. Все изменения аддитивны.
2. Уровень 2: выбор между А и Б определяется одним вопросом — есть ли требование конфиденциальности
   ключей между командами авторов. Заявленный драйвер предложения (нивелирование утечки ключей
   неавторизованным авторам) — именно это требование; при его подтверждении рекомендуется вариант Б
   (владение на уровне темы) с обязательными условиями: инвариант «доставка не проверяет права на
   тему», legacy-темы остаются общими (`visibility = shared`), гранты выдаются в том числе на группы,
   предупреждение об одноимённых темах — без блокировки и только в видимой автору области, отзыв
   гранта — по двухрежимной модели (мягкий по умолчанию с производным чтением, жёсткий — через
   разрешение зависимостей), без блокировки отзыва. Если требование не подтверждается — достаточно
   варианта А как более дешёвого.
3. Перенос оценочной специфики на уровень теста (раздел 4.3) выполнить полным выносом: `points` и
   `scoringJson` удаляются из вопроса, действующая цена определяется цепочкой на стороне теста
   (переопределение по вопросу -> дефолт секции -> дефолт теста -> системное умолчание «1 балл за
   корректный ответ, без частичного зачёта»), что закрывает и динамическую выдачу по темам.
   Сложность остаётся на вопросе с возможностью переопределения в тесте. Мера ортогональна выбору
   А/Б и может идти отдельной фазой; изменения книги Excel (колонки оценки из листа Questions в
   test-scoped лист) согласовать с активным треком PRD-14.
4. Уровень 3a (снапшот при публикации) принят как целевое решение — оформить отдельным PRD по модели
   раздела 4.4: состояния «опубликован / опубликован, есть неопубликованные изменения»,
   переопубликация, доигрывание идущих попыток на своей версии, экстренная переопубликация с
   аннулированием без списания попытки. Рекомендуемое место в очерёдности — сразу после уровня 1 и
   до (или вместе с) вариантом Б: модель отзыва грантов опирается на снапшоты, а формат снапшота с
   разрешёнными значениями развязывает его с переносом цены (4.3). 3b (организации) оставить
   отложенным.
5. Последовательность работ: уровень 1 -> 3a (модель публикации со снапшотами) -> вариант Б
   (правка `role-model.md`: владение темами, новые способности, матрица -> согласование эскизов UI:
   фильтры тем, гранты, предупреждение об одноимённости -> реализация фазами: схема + API ->
   фильтрация и валидация -> UI -> импорт/экспорт PRD-14); перенос оценки (раздел 4.3) —
   параллельной или следующей фазой.
