# BRD: Расширение возможностей генерации SCORM-пакетов

**Версия:** 2.0  
**Статус:** Черновик  
**Технический контракт:** [Платформа SCORM-шаблонов](spec-template-platform.md)

---

## 1. Контекст и постановка задачи

Test Builder генерирует SCORM 2004 4th Edition пакеты с ограниченной визуальной
вариативностью, без полноценных контентных страниц между блоками и с базовой моделью
расчёта результата. Референсный проект Articulate Storyline показывает, что для
корпоративных сертификаций нужны:

- управляемые шаблоны плеера и страниц;
- контентные и системные страницы внутри общего потока прохождения;
- гибкая логика переходов, блокировок, таймеров и переменных;
- пользовательские показатели результата и передача этих данных в LMS;
- многомерные измерения компетенций, где один вопрос может влиять на одну или несколько шкал.

**Цель:** расширить SCORM-генератор до уровня, достаточного для корпоративных курсов и
сертификаций, сохранив контролируемую архитектуру Core и единую механику внутренних и
внешних шаблонов.

---

## 2. Ключевые архитектурные решения

### 2.1 Единая шаблонная платформа

Встроенные и внешние шаблоны используют один контракт:

- `manifest.json`;
- `shell.html`;
- макеты страниц;
- частичные шаблоны;
- локальные CSS/JS/ресурсы внутри SCORM ZIP;
- браузерный рендерер шаблонов;
- Runtime API для `template.js`;
- правила курса.

Отдельные механики для встроенных и внешних шаблонов не создаются. Различаться может только
источник файлов: адаптер встроенного источника или адаптер загруженного источника.

### 2.2 Исполнение только в браузере

Шаблон исполняется только в браузере обучающегося внутри SCORM-пакета.

Сервер не выполняет HTML/JS шаблона и не рендерит EJS. Сервер:

- валидирует шаблон;
- хранит метаданные;
- копирует выбранный шаблон в SCORM ZIP;
- добавляет Core runtime и данные теста.

### 2.3 Разделение ответственности Core и шаблона

**Core владеет:**

- состоянием теста;
- навигацией;
- ответами;
- оценкой;
- состоянием обратной связи;
- восстановлением сессии;
- стандартными интерактивами вопросов;
- SCORM API;
- telemetry;
- финальными защитами для критичных действий.

**Шаблон владеет:**

- макетом оболочки;
- макетами разных типов страниц;
- визуальным языком;
- локальными ресурсами;
- дополнительным поведением через `template.js`;
- декларативными правилами шаблона для технического/визуального поведения.

### 2.4 Макет шире, чем цвета и шрифты

Шаблон описывает не только параметры оформления, но и макет:

- оболочку курса (`shell.html`);
- макет вопросов;
- макет контентных страниц;
- макет результатов;
- опциональный макет стартовой страницы;
- опциональные системные страницы;
- частичные шаблоны для навигации, прогресса, header/footer.

Стандартные интерактивы вопросов в MVP остаются за Core и вставляются в контролируемый слот
`data-slot="question-interaction"`.

### 2.5 Гибкий движок прохождения

Core должен поддерживать несколько политик прохождения без развилки на отдельные runtime:

- `legacy_flat`: текущее поведение, при котором вопросы выбираются из разделов и перемешиваются в
  общий плоский список;
- `section_linear`: разделы проходятся последовательно, с явными стартовыми страницами, вопросами и
  страницами результата раздела;
- `section_router`: обучающийся возвращается на страницу-маршрутизатор после каждого раздела,
  видит пройденные разделы и результаты по ним, а итоговый результат открывается после выполнения
  политики завершения;
- `section_graph`: переходы между разделами и страницами определяются правилами курса;
- `adaptive_by_section`: адаптивная выдача вопросов внутри разделов с переходами между разделами.

Раздел (`section`/`topic`) является не только контейнером вопросов, но и сценарным узлом:

```text
section start -> section questions -> section result -> transition -> next section/results
```

Старые тесты без явной `flowPolicy` должны продолжать экспортироваться и проходиться как
`legacy_flat`.

### 2.6 UI только после согласованных wireframes

Любая функциональность, которая добавляет или меняет авторский, административный или learner-facing
UI, не передаётся в frontend-разработку без предварительно подготовленных и явно согласованных
wireframes.

Wireframes должны покрывать:

- основной пользовательский сценарий;
- пустые состояния;
- loading/saving состояния;
- ошибки API и валидации;
- read-only/disabled состояния, если применимо;
- ключевые edge cases, влияющие на поведение пользователя.

Если во время разработки меняется сценарий, состав полей, порядок действий или состояние экрана,
изменение возвращается на повторное согласование wireframes до продолжения UI-реализации.

## 3. Анализ референса Storyline

Референс содержит не только визуальную оболочку, но и runtime-логику:

- переменные доступа и результатов (`Test_Blocked`, `Blocks_Done`, `Result_*`);
- условия и переходы;
- выдачу вопросов и расчёт статуса по отдельным разделам;
- страницу-маршрутизатор, с которой обучающийся выбирает раздел, возвращается после прохождения и
  видит статус/результат разделов;
- стартовые страницы разделов и страницы результатов разделов;
- таймеры;
- SCORM commit/reset;
- блокировки;
- предупреждения о нескольких вкладках;
- слайды результатов и сертификации.

Вывод: простого HTML/CSS-шаблона недостаточно. Требуется гибрид:

- базовая no-code логика через правила курса;
- возможность расширения кодом через `template.js` и Runtime API;
- явная модель потока прохождения с разделами, промежуточными результатами и политиками переходов;
- будущая фаза расширенных шаблонных интерактивов для переопределения механики вопросов.

## 4. Бизнес-требования

### BR-01: Шаблонная платформа SCORM

**Проблема:** внешний вид, навигация и структура страниц жёстко связаны с текущим Core.
Невозможно создавать разные корпоративные плееры без разработки.

**Требования:**

| ID | Требование |
| --- | --- |
| BR-01-01 | Система поддерживает единую механику встроенных и внешних шаблонов согласно [spec-template-platform.md](spec-template-platform.md) |
| BR-01-02 | Шаблон исполняется только в браузере обучающегося внутри SCORM-пакета |
| BR-01-03 | Шаблон содержит `manifest.json`, `shell.html`, макеты, опциональные частичные шаблоны, ресурсы, скрипты и правила |
| BR-01-04 | Сервер не выполняет код шаблона при экспорте |
| BR-01-05 | Автор выбирает шаблон и параметры через UI без ручного JSON |
| BR-01-06 | Параметры шаблона поддерживают dot-keys, группы, значения по умолчанию, валидацию и CSS-переменные |
| BR-01-07 | Core предоставляет прогресс по вопросам и страницам; шаблон выбирает активный прогресс через `progress.mode` |
| BR-01-08 | Тестовая `navigationPolicy` имеет приоритет над возможностями шаблона |
| BR-01-09 | Тесты без настроек используют `default` и сохраняют обратную совместимость |

### BR-02: Контентные и системные страницы

**Проблема:** текущий поток содержит только вопросы и не позволяет вставлять учебный материал
или служебные экраны.

**Требования:**

| ID | Требование |
| --- | --- |
| BR-02-01 | Автор может добавлять контентные страницы до/после темы |
| BR-02-02 | Поддерживаются типы `intro`, `info`, `summary`, `html` |
| BR-02-03 | Контентные страницы входят в общий поток страниц, но не влияют на оценку вопросов |
| BR-02-04 | HTML-контент проходит серверную санитизацию и вставляется только через контролируемые слоты |
| BR-02-05 | Медиа контентных страниц упаковываются в SCORM ZIP как локальные ресурсы |
| BR-02-06 | Системные страницы шаблона объявляются в `manifest.systemPages[]` и не считаются учебными страницами |
| BR-02-07 | Автопереход реализуется через Core/Rules/Runtime API, а не через произвольный серверный рендер |

### BR-03: Правила курса и runtime-логика

**Проблема:** Storyline-подобные сценарии требуют условий, переменных, переходов, таймеров и
SCORM-действий. Кодом шаблона можно покрыть всё, но авторам нужен no-code слой.

**Требования:**

| ID | Требование |
| --- | --- |
| BR-03-01 | Система поддерживает практичный MVP правил курса согласно технической спецификации |
| BR-03-02 | Правила теста хранят бизнес-логику теста в таблице `course_rules` |
| BR-03-03 | Правила шаблона хранят только техническое/визуальное поведение в `rules/template-rules.json` |
| BR-03-04 | Конвейер исполнения: состояние Core -> `template.js beforeRules` -> правила шаблона -> правила теста -> `template.js afterRules` -> финальные защиты Core |
| BR-03-05 | Условия правил хранятся как JSON-дерево выражений |
| BR-03-06 | Действия хранятся как JSON-объекты действий; значения могут быть деревом выражений |
| BR-03-07 | `template.js` получает Runtime API для расширенной логики, но не поддерживает прямой доступ к внутренностям Core |
| BR-03-08 | SCORM-операции шаблона и правил выполняются через `TestBuilder.scorm` |

### BR-04: Пользовательские показатели результата

**Проблема:** LMS получает только стандартный балл, а корпоративные сценарии требуют
компетентностных флагов, индексов, допусков и категорий.

**Требования:**

| ID | Требование |
| --- | --- |
| BR-04-01 | Автор задаёт пользовательские показатели результата через визуальный конструктор и расширенный DSL |
| BR-04-02 | Пользовательские показатели вычисляются после стандартной оценки |
| BR-04-03 | Значения публикуются в пространстве имён `result.*` после события `result:calculated` |
| BR-04-04 | Значения могут отображаться обучающемуся на макете результатов |
| BR-04-05 | Значения передаются в LMS через `suspend_data` и/или псевдо-`interactions` |
| BR-04-06 | Ошибка формулы не прерывает завершение теста и сохраняется в диагностике |

### BR-05: Внешние шаблоны

**Проблема:** корпоративные заказчики и подрядчики должны создавать новые шаблоны без изменения
кода системы.

**Требования:**

| ID | Требование |
| --- | --- |
| BR-05-01 | Администратор загружает внешний шаблон ZIP |
| BR-05-02 | Система выполняет структурную валидацию и браузерную smoke-проверку |
| BR-05-03 | Внешние URL в шаблоне запрещены; все ресурсы локальны внутри ZIP |
| BR-05-04 | Встроенные и внешние шаблоны экспортируются и валидируются по одному контракту |
| BR-05-05 | В UI доступны статический предпросмотр и живой предпросмотр на демонстрационном курсе |
| BR-05-06 | В SCORM ZIP попадает только выбранный шаблон |
| BR-05-07 | При runtime-ошибке шаблона Core показывает встроенный экран ошибки |

### BR-06: Гибкий поток прохождения и многомерные измерения

**Проблема:** текущая логика теста использует разделы как источник выборки вопросов и как единицу
финального расчёта, но не как явные сценарные блоки прохождения. Референс требует стартовых страниц
разделов, переходов между разделами, промежуточных результатов и сценариев ветвления. Дополнительно
корпоративные оценки требуют, чтобы один вопрос мог измерять одну или несколько компетенций
одновременно, независимо от обычной правильности ответа.

**Требования:**

| ID | Требование |
| --- | --- |
| BR-06-01 | Core поддерживает `flowPolicy`, определяющую режим прохождения: `legacy_flat`, `section_linear`, `section_router`, `section_graph`, `adaptive_by_section` |
| BR-06-02 | Отсутствие `flowPolicy` означает `legacy_flat` и сохраняет текущее поведение существующих тестов |
| BR-06-03 | В `legacy_flat` вопросы выбираются по разделам, затем могут перемешиваться в общий плоский список, как в текущем SCORM runtime |
| BR-06-04 | В секционных режимах Core строит поток раздела: стартовые страницы раздела, вопросы раздела, страницы результата раздела, переход к следующему узлу |
| BR-06-05 | Раздел имеет явное состояние: `notStarted`, `inProgress`, `completed`, `passed`, `failed`, `locked` |
| BR-06-06 | Core рассчитывает результат раздела сразу после завершения вопросов раздела и публикует его до показа `content.summary` |
| BR-06-07 | Правила курса могут реагировать на события `section:started`, `section:completed`, `section:resultCalculated` |
| BR-06-08 | Правила курса могут выполнять переходы `nav.goToSection`, `nav.goToPage`, `nav.nextSection`, `nav.retrySection`, `nav.goToResults` с финальными защитами Core |
| BR-06-09 | Поддерживаются независимые политики порядка: порядок разделов, порядок вопросов внутри раздела, глобальное перемешивание для legacy-режима |
| BR-06-10 | Вопрос может быть экзаменационным, измерительным или смешанным: правильность ответа и вклад в шкалы/компетенции хранятся отдельно |
| BR-06-11 | Система поддерживает сущности шкал/компетенций с типом, правилами агрегации, нормализацией и интерпретационными диапазонами |
| BR-06-12 | Один вопрос или один вариант ответа может давать вклад в несколько шкал с разными весами и условиями |
| BR-06-13 | Результаты шкал публикуются в отдельном пространстве имён `scale.*` и могут использоваться пользовательскими показателями `result.*` |
| BR-06-14 | LMS получает стандартный балл отдельно от секционных результатов, шкал и пользовательских показателей |
| BR-06-15 | UI автора должен явно показывать, какие шкалы измеряет вопрос и как вклад зависит от выбранного ответа |
| BR-06-16 | В режиме `section_router` Core показывает страницу-маршрутизатор со списком разделов, их статусами и результатами, а переход к итоговому результату разрешает только после выполнения политики завершения |
| BR-06-17 | После завершения раздела в режиме `section_router` Core возвращает обучающегося на страницу-маршрутизатор, а не автоматически переводит в следующий раздел |
| BR-06-18 | Состояние страницы-маршрутизатора, результаты разделов и доступность итогового результата должны восстанавливаться из `suspend_data` при повторном открытии SCO |

### BR-07: Ограничение повторного прохождения и период охлаждения

**Проблема:** для части корпоративных курсов требуется запретить повторное прохождение ранее
чем через заданное количество календарных дней после последней полноценной попытки. WebTutor
возвращает дату попытки без времени, поэтому ограничение рассчитывается по датам, без часов.
Доступные данные о попытках зависят от внутренних endpoint'ов и могут меняться при обновлениях
LMS, поэтому проверка не должна быть жёстко зашита в глубину SCORM runtime.

**Требования:**

| ID | Требование |
| --- | --- |
| BR-07-01 | Автор или администратор может включить `retakePolicy` для теста и задать период охлаждения в календарных днях |
| BR-07-02 | Период охлаждения задаётся в настройках теста без пересборки кода runtime; UI показывает дату следующего доступного прохождения без ручных расчётов |
| BR-07-03 | Проверка допуска выполняется до старта полноценной попытки и до вызова SCORM `Initialize`, если выбран режим `before_internal_start` |
| BR-07-04 | При активном ограничении Core показывает `block-wall`/системную страницу блокировки и не запускает прохождение |
| BR-07-05 | Заблокированный запуск не должен писать `cmi.*`, менять SCORM-статусы или создавать признаки полноценной попытки со стороны пакета |
| BR-07-06 | Допуск к старту вычисляется через `eligibilityPlugin` с чётким контрактом `context -> allowed true/false` |
| BR-07-07 | Если `eligibilityPlugin` не задан, Core всегда считает допуск разрешённым (`allowed = true`) |
| BR-07-08 | Выбор `eligibilityPlugin` и его конфигурации хранится в настройках конкретного теста; разные тесты могут использовать разные plugins |
| BR-07-09 | Источник даты последней полноценной попытки выбирается внутри плагина, например `webtutor_cooldown`, `suspend_data_cooldown`, `custom` |
| BR-07-10 | Для WebTutor-плагина полноценная попытка определяется не по факту открытия курса, а по настраиваемому фильтру записей: статус, прогресс, дата последнего использования и/или признаки завершения |
| BR-07-11 | Встроенный WebTutor-плагин должен поддерживать администрируемую конфигурацию endpoint'ов, параметров запроса, имени курса, правил фильтрации и правил парсинга даты |
| BR-07-12 | Хрупкая LMS-specific логика размещается в явном адаптере/плагине, доступном для быстрой правки администратором или внедренцем, а не внутри общего Core |
| BR-07-13 | Плагин возвращает нормализованный результат: `allowed`, `reason`, `source`; для заблокированного cooldown, если дату можно вычислить, результат должен содержать `availableDate` в формате `YYYY-MM-DD` |
| BR-07-14 | Core передаёт `availableDate` на `block-wall`/системную страницу блокировки; `nextAllowedDate` допускается как совместимый alias для старых шаблонов и диагностики |
| BR-07-15 | Если плагин недоступен или возвращает ошибку, политика ошибки задаётся настройкой: `failOpen` или `failClosed` |
| BR-07-16 | UI администратора должен показывать активную retake-политику, источник данных, текущую версию адаптера и результат тестовой проверки на выбранном пользователе/курсе |
| BR-07-17 | Все решения retake gate логируются в диагностике runtime без записи персональных данных сверх необходимого минимума |
| BR-07-18 | `suspend_data` может использоваться только как best-effort источник внутри той же SCORM registration; для строгого cooldown между новыми попытками нужен внешний/LMS-specific источник |

### BR-08: Рефакторинг редактора параметров теста

**Проблема:** настройки теста стали центральной точкой сборки сценария: режим теста, темы,
выборка вопросов, проходные правила, адаптивные уровни, ограничения попыток, стартовый контент,
оформление, контентные страницы, экспорт и будущие `flowPolicy`/`retakePolicy`. Сейчас эти зоны
редактируются фрагментарно: базовый wizard находится в монолитной странице тестов, а часть новых
настроек вынесена в отдельные диалоги рядом с карточкой. Это ухудшает предсказуемость UX,
усложняет валидацию и повышает риск регрессий при добавлении новых PRD.

**Требования:**

| ID | Требование |
| --- | --- |
| BR-08-01 | Автор редактирует все параметры теста в едином редакторе с понятной информационной архитектурой, а не через набор разрозненных кнопок на карточке; создание и редактирование теста открываются в одном wide Drawer |
| BR-08-02 | Редактор разделяет настройки на устойчивые доменные разделы: основное, темы/структура, правила прохождения, адаптивность, старт/контент, оформление, публикация/экспорт |
| BR-08-03 | Стандартный и адаптивный режимы используют общий контейнер редактора, но имеют специализированные формы только там, где различается доменная модель |
| BR-08-04 | Переключение режима теста не должно молча уничтожать сохранённые настройки другого режима; система показывает последствия и сохраняет черновик до явного подтверждения |
| BR-08-05 | Валидация выполняется на уровне доменной модели до отправки API: draw count, проходные пороги, адаптивные диапазоны сложности, количество вопросов, ссылки и обязательные поля |
| BR-08-06 | Frontend использует typed DTO/mappers для преобразования между API, формой и payload, без ручной сборки больших `any`-объектов внутри страницы списка |
| BR-08-07 | Backend предоставляет атомарные операции сохранения настроек теста и связанных сущностей; частично сохранённое состояние не должно появляться при ошибке адаптивных уровней или секций |
| BR-08-08 | Список тестов показывает только краткие основные действия; расширенные настройки открываются через редактор, вкладки или единое меню действий |
| BR-08-09 | Все изменения редактора покрываются компонентными, unit и API-тестами на create/edit, standard/adaptive, режимные переключения и ошибки API |
| BR-08-10 | Перед frontend-реализацией должны быть согласованы wireframes для desktop/mobile, пустых состояний, ошибок, unsaved changes и сценариев с большим числом тем |

## 9. Риски и митигации

| Риск | Вероятность | Митигация |
| --- | --- | --- |
| Внешний шаблон ломается в браузере | Средняя | Браузерная smoke-проверка, живой предпросмотр, экран ошибки Core |
| Шаблон конфликтует с бизнес-логикой | Средняя | Области разрешений, правила теста после правил шаблона, финальные защиты Core |
| LMS плохо показывает пользовательские данные | Высокая | Дублирование в `suspend_data` и `interactions` |
| HTML-контент вызывает XSS | Высокая | Серверная санитизация и запрет сырой HTML-интерполяции |
| Правила курса превращаются в полный Storyline-движок | Средняя | Практичный MVP и отдельный документ оценки будущей целесообразности |
| Большие ресурсы раздувают ZIP | Средняя | Лимиты загрузки, запрет внешних URL, предупреждения по размеру |
| Новый flow ломает старые тесты | Высокая | `legacy_flat` как режим по умолчанию, golden-тесты на старые SCORM-пакеты |
| Секционные переходы конфликтуют с правилами | Средняя | Финальные защиты Core, детерминированный порядок правил, диагностика принятого перехода |
| Многомерные шкалы сложно объяснить автору | Средняя | UI матрицы вкладов, предпросмотр расчёта на демо-ответах, предупреждения о непокрытых шкалах |
| Шкалы смешиваются со стандартным баллом | Средняя | Раздельные пространства `score/section/scale/result`, явные настройки публикации в LMS |
| WebTutor endpoint или формат данных меняется | Высокая | LMS-specific eligibility plugin вынесен в явный адаптер с администрируемой конфигурацией, версией и тестовой проверкой |
| Заблокированный запуск ошибочно считается попыткой | Средняя | Gate выполняется до внутренней кнопки старта и до SCORM `Initialize`; полноценная попытка определяется по фильтру статуса/прогресса, а не только по открытию курса |
| Cooldown невозможно строго обеспечить через `suspend_data` | Высокая | `suspend_data` помечается как best-effort источник; строгий режим требует WebTutor/LMS-specific или внешнего источника |
| Редактор теста становится слишком сложным для поддержки | Высокая | Декомпозиция на доменные вкладки/модули, typed DTO, мапперы, централизованная валидация и компонентные тесты |
| Добавление новых PRD ломает существующее редактирование теста | Высокая | Единый контракт `TestEditorModel`, regression suite на standard/adaptive create/edit и explicit migration strategy для новых настроек |
