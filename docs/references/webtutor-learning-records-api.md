# WebTutor: чтение учебных записей учащегося (источник PRD-6 cooldown)

Опорный материал по недокументированному API WebTutor (портал
`university.rt.ru`, вендор WebSoft), который питает retake-гейт PRD-6.
Контракт вскрыт и подтверждён на живом портале 2026-07-16.

## Зачем

PRD-6 cooldown должен запускаться после ЛЮБОЙ завершённой попытки курса
(и «Пройден», и «Не пройден»). Дата последней попытки берётся из учебных
записей учащегося. Тупиковые источники, проверенные и отвергнутые:

- Карточка курса (`get_metadata` ClientBridge) отдаёт дату только для
  «Пройден» (маркер `best_learn_step_success`) — провал не ловит.
- Плитки (`extjs_tile_collection_data.html`) — XAML без дат.
- `/oapi/course_player_library/GetCourseLearningStructure` — требует
  отдельный SessionId, недоступный из пакета (не secid, не cookie `SessionID`).
- `cmi.suspend_data` / `adl.data` — WebTutor их между попытками не хранит.

## Рабочий контракт (подтверждён)

Endpoint (POST, той же сессией, `credentials: include`):

```text
POST /pp/Ext5/extjs_json_collection_data.html?_dc=<ts>
Content-Type: application/x-www-form-urlencoded; charset=UTF-8
X-Requested-With: XMLHttpRequest
```

Поля тела (form-urlencoded):

| Поле | Значение |
| --- | --- |
| `secid` | 32-hex сессионный токен, скрапится со страницы портала |
| `collection_code` | `rostelecom_catalog_data_grid` (грид с колонками-датами) |
| `parameters` | `;`-строка (см. ниже) |
| `referer_url` | текущий URL |
| `page` / `start` | пагинация (`1` / `0`) |
| `limit` | размер страницы (напр. `500`) |

Строка `parameters`:

```text
cur_person_id=;sSearchWord=<название курса>;sRoles=all;iCount=;sCatalogName=learning
```

Важно: `cur_person_id` можно оставить ПУСТЫМ — endpoint определяет учащегося
по сессионной cookie. Скрапить person_id не требуется (подтверждено:
запрос с пустым `cur_person_id` вернул 384 записи вызывающего).

Ответ:

```json
{ "success": true, "total": 384, "results": [ { "...": "..." } ] }
```

## Поля записи

| Поле | Смысл |
| --- | --- |
| `name` | название курса; у РАЗНЫХ назначений одного курса совпадает |
| `object_id` / `id` | идентификатор учебной записи (у каждого назначения свой) |
| `state` | `Пройден` / `Не пройден` — ОБА суть завершённая попытка |
| `last_usage_date` | дата последнего обращения, `dd.MM.yyyy` |
| `start_usage_date` | дата назначения |
| `progress` | `X из Y баллов` — это НЕ проценты, для завершённости не годится |

Ответ отсортирован `last_usage_date DESC`.

## Правила отбора (как настроен гейт)

- Завершённость определяется полем `state` (`Пройден` / `Не пройден`),
  НЕ прогрессом.
- Дата-заглушка `31.12.9999` = открытое назначение, которое не проходили —
  отбрасывается.
- Разные назначения одного курса = один курс: матчинг по `name` (не по
  `object_id`), берётся самая поздняя дата среди всех назначений.

Название курса для матчинга = заголовок теста (`TEST_DATA.title`), который наш
билдер кладёт в `<organization><title>` манифеста; WebTutor берёт имя курса
оттуда. Автора предупреждает баннер в редакторе (блок «Ограничить повторное
прохождение»): ограничение сработает только если курс в LMS назван так же.

### Почему по имени, а не по object_id (вариант B отклонён)

Матч по `object_id` текущего запуска был бы надёжнее (снял бы зависимость от
совпадения имён), но на портале он невыполним, подтверждено зондами:

- В контексте запущенного SCO (`/cplayer2/<id>/part?session_id=…&part_code=…`)
  доступны `session_id`, `part_code`, `pathId` — но НИ ОДИН из них не совпадает с
  `object_id` записей грида. Прямой связки «запуск -> запись грида» нет; грид
  ключуется только по `name`.
- Курс-специфичный источник `/oapi/course_player_library/GetCourseLearningStructure`
  требует валидную oapi-сессию: cplayer2 сначала зовёт `InitCoursePlayer` (он и
  выдаёт SessionId), поэтому прямой вызов падает с `error 9 Invalid SessionId`.
  Повторять `InitCoursePlayer` из гейта рискованно (может задеть живую сессию
  проигрывателя), а грид всё равно джойнится только по имени. Выгода не оправдала
  риск и сложность.

Конфиг — `shared/eligibility/registry.ts` (плагин `webtutor_cooldown`,
config `webtutor_catalog_default`). Рантайм — `server/scorm/template/app/
eligibility/gate.js` (`webtutorEvaluate`). Чистая логика фильтра —
`shared/eligibility/plugins.ts` (`selectLastAttemptDate`).

## Зонды (для отладки на портале)

Запускать в консоли работающего SCORM-модуля (та же сессия, same-origin).

- `scripts/wt-attempts-probe.js` — ОСНОВНОЙ. Самораскрывающийся: сам добывает
  `secid` и (при необходимости) `cur_person_id`, `object_id` не нужен. Дёргает
  коллекцию и печатает «курс -> статус -> дата последней попытки» по всем курсам.
  Подтверждает весь тракт, которым пользуется гейт.
- `scripts/webtutor-probe.js` — диагностика КАРТОЧКИ курса (`get_metadata`).
  Исторический/вспомогательный: карточка как источник отвергнута (pass-only),
  но зонд полезен, если понадобится разобрать её XAML.
- `scripts/wt-object-probe.js` — исследование контекста ЗАПУСКА (вариант B).
  Запускать в консоли фрейма `cplayer2`; снимает `session_id`/`part_code`/`pathId`
  и проверяет, джойнятся ли они с `object_id` грида (не джойнятся — см. выше).
- `scripts/wt-assignment-boundary-probe.js` — граница НАЗНАЧЕНИЯ против границы
  ПОПЫТКИ (PRD-31). Двухпроходный: первый прогон снимает состояние записей в
  `localStorage`, второй (после пройденной попытки) показывает разницу и отвечает,
  переходит ли запись в завершённое состояние уже после ПЕРВОЙ попытки
  многопопыточного назначения. Заодно печатает полный список полей записи (вдруг
  появился признак текущего назначения) и origin всех фреймов (открытый риск §8
  доверенной даты).

Локальная приёмка без портала: `npm run scorm:player` + фикстура
`scripts/_build-cooldown-scorm.ts` (мок коллекции отвечает как боевой endpoint).
