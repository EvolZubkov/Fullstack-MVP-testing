## 1. Зачем этот документ

Документ фиксирует ОБЩУЮ (абстрагированную) модель расчёта результатов теста, в которую
укладываются и простые сценарии (несколько шкал плюс одна итоговая категория), и сложные
(оценка компетенций с под-компетенциями, пересчётом баллов и итоговым вердиктом). Примеры
организации модели под разные классы тестов — в §6.

Ключевой принцип: **платформа предоставляет общую машинерию, а конкретный тест — это ДАННЫЕ
в ней.** Сущности вроде «компетенция», «версия набора», «секция», «таблица калибровки» в схему
НЕ вводятся — они выражаются через общие понятия ниже. Новая сущность
оправдана только тогда, когда это новый ОБЩИЙ механизм, полезный многим тестам, а не одному.

## 2. Понятия (3 основных + 1 ортогональное)

### 2.1 Вклад варианта (и балл вопроса)

Вариант ответа даёт в шкалу ЧИСЛО — ЯВНЫЙ вклад в сетке «вариант × шкала» (`value_json`, §9.2):
пусто = не влияет, допустимы 0 и отрицательные. Это покрывает и простые опросники (0..5 по
варианту), и градуированные веса с частичным баллом за множественный выбор и сопоставление.
Отдельно у вопроса
есть свой `answer_score`/корректность (стандартный балл, ось ПРАВИЛЬНОСТИ) — он в шкалы НЕ
наследуется. Шкала суммирует явные вклады из сетки.

### 2.2 Шкала

Именованное значение = агрегат ВКЛАДОВ. Вклад — это:

- балл вопроса (с опциональным условием и весом), ЛИБО
- значение ДРУГОЙ шкалы (композиция).

Опционально у шкалы есть:

- пересчёт (нормализация, заданная формулой — см. §3);
- интерпретационные диапазоны (`bands`), дающие символьный уровень;
- передача в LMS (`scorm_target`): значение шкалы и, при заданных диапазонах, уровень
  (PRD-5 §8.2).

Шкала, чей вклад — только балл вопросов, называется ЛИСТОВОЙ. Шкала, чей вклад — другие
шкалы, называется СОСТАВНОЙ (композиция). Граф композиции «шкала -> дочерние шкалы» обязан быть
ацикличным (§10.9).

### 2.3 Показатель

Именованное значение = формула над шкалами, темами и другими показателями. Опционально:

- управление статусом курса (`controls_status` -> `success`/`completion`);
- передача в LMS.

Показатель отличается от шкалы ролью: шкала агрегирует вклады и может иметь диапазоны;
показатель — это произвольная формула (число, строка или булево) и единственное место,
откуда можно переопределить статус прохождения.

### 2.4 Банк вопросов, выдача и сопоставимость (ортогонально скорингу)

Вариативность выдачи (разным обучающимся — разные вопросы) обеспечивается банком вопросов и
выдачей подмножества. Это свойство ДОСТАВКИ, а не скоринга: шкала суммирует те вклады, что
фактически поступили.

ВАЖНО про сопоставимость сырого балла. Сумма по случайному подмножеству зависит от того,
какие вопросы выпали (разный максимум и разная трудность), поэтому сырой балл сопоставим
между обучающимися только при одном из условий:

- **фиксированные альтернативные формы** — заранее собранные равноценные наборы; обучающемуся
  выдаётся одна форма (на повторной попытке — другая). Сопоставимость достигается тем, что
  формы пропилотированы и приняты равноценными;
- **выдача по бланку (стратифицированная)** — каждая выдача тянет фиксированную структуру (по
  N вопросов на под-тему/уровень трудности), случайность только внутри страты;
- **уравнивание (equating)** — пересчёт балла на форму к общей шкале (см. §3); коэффициенты —
  откалиброванные ДАННЫЕ из пилота, не произвольные числа.

Чистая случайная выдача N из неоднородного банка БЕЗ одного из этих условий даёт
несопоставимый балл и для сертификации не годится. Нормировка в проценты (балл/максимум)
снимает только различие максимумов, но не различие трудности.

## 3. Нормализация как формула

Нормализация шкалы — это единая «формула пересчёта» `raw -> значение`. Все практические
случаи являются её частными видами:

- `identity` — значение равно `raw`;
- `percent` — линейная нормализация в проценты (с учётом направления `positive`/`inverse`);
- `linear` — `a * raw + b` с отсечением (`max(0, .)`), коэффициенты `a`, `b` — ДАННЫЕ автора;
- иные выражения над `raw` в пределах разрешённой грамматики.

Коэффициенты пересчёта — это литералы в формуле (конфигурация теста), а не отдельная
сущность «калибровка». Диапазоны (`bands`) применяются к `raw` шкалы (до пересчёта);
пересчёт/`percent` — параллельное отображаемое значение, НЕ вход диапазонов (PRD-5 §5.2–5.3).

Пересчёт `linear`/`custom` — ОПЦИОНАЛЬНЫЙ инструмент (equating форм). Он нужен не всегда: во
многих сертификационных тестах выравнивающие коэффициенты осознанно не используются — берётся
сырой балл против абсолютного порога на раздел. Поэтому платформа должна
ПОДДЕРЖИВАТЬ пересчёт-формулу, но не делать её обязательной; по умолчанию нормализация —
`identity`/`percent`.

## 4. Конвейер расчёта

```text
вопрос -> балл вопроса (число)
       -> вклад в шкалу (условие/вес) ИЛИ вклад от другой шкалы (композиция)
       -> агрегация шкалы (sum/avg/...) = raw
       -> от raw: диапазоны -> уровень; ПАРАЛЛЕЛЬНО пересчёт итога -> отображаемое значение
       -> показатели (формулы над шкалами)
       -> управление статусом (controls_status) и выгрузка в LMS
```

Порядок гарантирует, что значения шкал доступны показателям до их расчёта, а показатели —
до фиксации статуса (детали — в PRD-5 и PRD-2).

## 5. Спец-сущности тестов укладываются в общие примитивы

Ничто из перечисленного НЕ требует отдельной сущности в схеме:

| Что выглядит как спец-сущность | Чем является в модели |
| --- | --- |
| Составная компетенция (роллап) | Шкала-композиция (агрегат над дочерними шкалами) |
| Несколько версий/форм набора | Банк вопросов и случайная выдача |
| Калибровка `a*raw+b` | Формула нормализации шкалы; коэффициенты — данные |
| Под-компетенция с порогом | Обычная шкала с диапазоном «passed» |
| Под-темы внутри раздела | Организация контента (темы), а не шкала |
| «Пройдено по компетенции» | Показатель типа boolean |
| Итоговая сертификация | Показатель boolean плюс `controls_status=success` |
| Частичный балл (множественный/сопоставление) | Правило оценки типа вопроса |

## 6. Примеры организации расчётной модели

Ниже — типовые СПОСОБЫ скомпоновать примитивы §2 (шкалы, композиты, показатели, нормализация,
диапазоны) под разные классы тестов. Это шаблоны компоновки, а не привязка к конкретным
методикам: каждый описывает, КАК организован расчёт, а не ЧТО измеряет отдельный тест. Различие
тестов внутри одного шаблона — это ДАННЫЕ (состав шкал, числа в сетке, формулы показателей).

### 6.1 Многошкальный опросник с итоговой категорией (профиль)

- несколько ЛИСТОВЫХ шкал; вклад — явные числа по вариантам (Likert `0..N`); обратные пункты —
  отрицательными значениями или `direction = inverse` на всей шкале;
- агрегация `sum`, нормализация `percent`/`none`; диапазоны `bands` -> уровень (`low`/`mid`/`high`);
- 1 ПОКАЗАТЕЛЬ — формула над УРОВНЯМИ шкал, дающая строковую категорию или профиль;
- композиция, пересчёт `linear`, управление статусом обычно НЕ нужны.

Где встречается: психометрические опросники, типологии личности, индексы вовлечённости/выгорания.

### 6.2 Компетентностная сертификация с роллапом и вердиктом

- листовые шкалы по под-навыкам: градуированные баллы, опциональный пересчёт `linear` (equating),
  диапазон `passed`/`failed`;
- СОСТАВНЫЕ шкалы — роллап под-навыков в компетенцию (источник «другие шкалы», `sum`/`avg`);
- boolean-показатели «пройдено по компетенции» (формула над уровнем компетенции);
- 1 показатель-сертификация — конъюнкция условий плюс `controls_status = success`;
- вариативность выдачи — банк и стратифицированная выдача (§2.4).

Где встречается: корпоративная сертификация компетенций, профессиональный credentialing.

### 6.3 Взвешенный знаниевый экзамен по разделам

- листовая шкала на РАЗДЕЛ: вклад = балл правильного варианта, заданный явно в сетке (численно
  равен баллу задания, но в шкалу попадает явно, §10.3); агрегация `sum`, нормализация `percent`;
- минимум на раздел — диапазоны `bands` на каждой шкале раздела;
- общий ВЗВЕШЕННЫЙ итог — показатель (взвешенная формула над разделами; в композите взвешивание
  не делается — это слой «Показатели», §9.3);
- показатель «сдал» — boolean: итог >= проходного И каждый раздел прошёл минимум, плюс
  `controls_status`;
- доменный отчёт — `scorm_target` на шкалах разделов.

Где встречается: стандартизованные и blueprint-экзамены, IT-сертификации с доменными баллами.

### 6.4 Рубричная (критериальная) оценка

- шкала на КРИТЕРИЙ: агрегирует баллы рубрики (например, `0..3` за пункт); нормализация
  `none`/`percent`;
- диапазоны `bands` отображают `raw` в буквенную оценку (`A`/`B`/`C`/`D`) или уровень владения;
- средний балл по критериям — составная шкала `avg` (GPA-подобно) либо показатель;
- 1 показатель — итоговая оценка/уровень (строка), опционально `controls_status`.

Где встречается: критериально-ориентированное оценивание, рубрики, проектная/портфолио-оценка.

### 6.5 Диагностика уровня по навыкам (placement)

- листовая шкала на НАВЫК (по типам заданий); нормализация `percent`; диапазоны -> уровень
  навыка (`A1..C2`, `novice..expert`);
- итоговый уровень размещения — показатель (минимум/формула над уровнями навыков: слабейший
  навык ограничивает итог; экстремум живёт в показателе, §9.3);
- рекомендация (трек обучения) — строковый показатель по итоговому уровню.

Где встречается: диагностические/placement-тесты, языковые уровни (CEFR-подобно), карта пробелов.

Один набор понятий §2 описывает все эти классы — от плоского опросника до многоуровневой
сертификации — без новых сущностей.

## 7. Что нужно обобщить в платформе

Всё перечисленное — общие механизмы (полезны многим тестам), а не доработки под конкретный
тест:

1. **Композиция шкал** — вкладом в шкалу может быть значение другой шкалы (роллап любой
   конечной глубины; граф композиции ацикличен — §10.9). Простой опросник этим не пользуется.
2. **Нормализация как формула** — `identity`/`percent`/`inverse`/`linear` как частные виды
   одного пересчёта; коэффициенты — данные.
3. **Градуированная оценка вопроса** — вопрос возвращает число по своей рубрике; единственное
   место, где требуется доработка модели вопроса.
4. **Банк и случайная выдача** — свойство доставки, снимающее необходимость в «версиях».

Механизмы `controls_status` (PRD-2) и интерпретационные диапазоны `bands` (PRD-5) уже
предусмотрены и в обобщении не нуждаются.

## 8. Инвариант на будущее

Если для нового теста возникает желание завести новую СУЩНОСТЬ — почти наверняка это должно
быть ДАННЫМИ в одном из четырёх понятий (§2). Новая сущность оправдана только тогда, когда
появляется новый ОБЩИЙ механизм, полезный многим тестам, а не одному. Это правило защищает
схему от разрастания под конкретные методики.

## 9. Механика настройки (концепт авторинга)

Концепт того, как автор настраивает скоринг. Главный принцип: **большинство настроек —
структурные (выпадающие списки и отметки), а формулу автор пишет ТОЛЬКО там, где логика не
сводится к «агрегация + источники».** «Расчёт агрегата» в типовом случае — это не формула.

Три поверхности (предполагаемые вкладки редактора теста; точная разметка — этап эскизов):

1. **«Шкалы»** — список измеряемых величин и конфигурация каждой.
2. **«Вклады вопросов»** (внутри «Шкал») — сетка «вариант × шкала» (явные числа-вклады).
3. **«Показатели»** — формулы над шкалами и управление статусом.

### 9.1 Настройка шкалы (структурно)

Поля одной шкалы: агрегация (`сумма`/`среднее`/`взвеш.`/`макс`/`мин`); источник (`вопросы` ИЛИ
`другие шкалы` — композит); пересчёт итога (`нет`/`проценты`/`инверсия`, опционально);
пороги/диапазоны -> уровень; показывать результат обучающемуся; передавать в LMS. Базовый балл
за ответ на шкале НЕ настраивается — это свойство вопроса (§10.3). У листовой шкалы агрегации
доступны все пять (`сумма`/`среднее`/`взвеш.`/`макс`/`мин`, `сумма` по умолчанию); у композита —
`сумма`/`среднее` (§9.3); из пересчёта на первом этапе — `нет`/`проценты` (§10.5).

```text
Шкала: Финансы                              показывать результат обучающемуся: [x]
Агрегация:    [ сумма v ]   Источник: (o) вопросы  ( ) другие шкалы
Пересчёт итога:[ нет v ]    Пороги: raw >= 7 -> «пройден» / иначе «не пройден»
Передавать в LMS: [ столбцом в отчёте v ]
```

Линейный пересчёт `a*raw+b` (поля `a`, `b` — данные автора) — точка расширения, на первом
этапе скрыт; во многих тестах не требуется (выравнивающие коэффициенты не используются).

### 9.2 Вклады вопросов (сетка «вариант × шкала»)

«Вклады вопросов» — вертикальный список раскрывающихся карточек вопросов. В раскрытой карточке —
СЕТКА: строки = варианты ответа (для `matching`/`ranking` — пары/позиции), столбцы = ВСЕ шкалы
теста, ячейка = число (`value_json`):

- ПУСТО = вариант не влияет на эту шкалу (ребра нет);
- число = ЯВНЫЙ вклад единицы в шкалу; допустимы `0` (вклад 0) и ОТРИЦАТЕЛЬНЫЕ (вычитает);
- членство «вопрос -> шкала» — производное (есть непустая ячейка в столбце).

Один вариант может вкладывать в несколько шкал с РАЗНЫМИ числами (мультишкальность) — отдельные
строки `question_measurements` (по строке на `(scale_id, единица)`); формулу автор не пишет.
Базовый `answer_score` в шкалы НЕ наследуется. Корректность здесь НЕ редактируется — верный
вариант подсвечивается (read-only), правка в разделе «Вопросы» (§10.2–10.3). Условия
(`condition_json`) отложены (§10.5).

### 9.3 Агрегат над шкалами (композит) — тоже структурно

Составная шкала (например, роллап компетенции) = та же шкала с источником `другие шкалы`:
агрегация `сумма` или `среднее` плюс отметка дочерних шкал. Формула не пишется. `взвеш.`/`макс`/
`мин` к композиту НЕ применяются: дочерние шкалы уже видны слою «Показатели», поэтому
взвешенную или экстремум-комбинацию пишут формулой показателя, а не агрегацией шкалы.

### 9.4 Показатели (единственное место формул)

Формула нужна там, где логика не сводится к агрегации: итоговая категория, условия, вердикт.
Показатель: имя, тип (`число`/`строка`/`булево`), формула (конструктор или DSL-редактор),
управление статусом (`controls_status`), выгрузка. Примеры: сертификация —
`AND(scaleById("fin").raw >= 7, ...)` плюс `controls_status=success`; итоговая категория —
`IF(countScales(...) ...)` -> строка.

### 9.5 Где формула, где нет

| Что настраивается | Как |
| --- | --- |
| Корректность / стандартный балл | в вопросе (раздел «Вопросы»): есть верный вариант или нет |
| Вклад варианта в шкалу | явное число в ячейке сетки «вариант × шкала» (пусто = не влияет; 0 и отрицательные допустимы) |
| Мультишкальность (вариант в неск. шкал) | разные числа варианта в разных столбцах-шкалах сетки |
| Композит (роллап под-шкал) | структурно: агрегация `сумма`/`среднее` + источник «шкалы» |
| Пересчёт `a*raw+b` | поля `a`, `b` (опционально, расширение) |
| Порог «пройден/не пройден» | диапазоны на шкале |
| Категория / сертификация / условия | формула в «Показателе» |

Те же три поверхности масштабируются от простого опросника (3 шкалы + 1 показатель) до
компетентностной сертификации (листовые шкалы + композиты + показатели-вердикты), без новых
сущностей.

## 10. Нормативные правила и границы модели

Точные правила расчёта, на которые опираются движок и валидация. Применимы ко всем классам
тестов из §6.

### 10.1 Правило суммы (множественный выбор)

Вклад вопроса в шкалу = `Σ (value × weight)` по всем ФАКТИЧЕСКИ выбранным единицам ответа,
ведущим в эту шкалу, где `value` — явное число из сетки «вариант × шкала» (допускает 0 и
отрицательные). Одиночный выбор — вклад одной выбранной единицы; множественный — сумма всех
выбранных (без `max`, без дедупликации); сопоставление/ранжирование — по парам/позициям
(единицы определены в §10.11). Это `aggregation = sum` (по умолчанию).

### 10.2 Правильность и вклад — разные слои

Точное совпадение «всё-или-ничего» остаётся гейтом ПРАВИЛЬНОСТИ (стандартный балл,
`checkAnswer`), а не правилом вклада. Неверный ответ НЕ обнуляет вклад в шкалу. Произвольная
логика (категория, вердикт, условие) пишется только в показателях; у шкалы поля формулы нет.
Частично верный множественный выбор даёт `0` по правильности (§10.10).

### 10.3 Корректность и вклады — раздельно

Корректность варианта и стандартный балл (`correctJson`/`answer_score`) — свойство САМОГО ВОПРОСА
(раздел «Вопросы»), а не шкалы и не «Вкладов»:

- знаниевый вопрос: есть верный вариант (стандартный балл / гейт прохождения);
- опросник (Likert): верного нет.

Вклады в шкалы задаются ОТДЕЛЬНО и ЯВНО — числом в сетке «вариант × шкала» (§9.2); базовый
`answer_score` в шкалы НЕ наследуется. На «Вкладах» корректность только показывается (подсветка
верного варианта + ссылка «Редактировать вопрос»). Мультишкальность (один вариант в разные
шкалы с разными числами) — это разные ячейки сетки, не условия и не режим на шкале.

### 10.4 Инверсия шкалы

Инверсия задаётся на уровне ВСЕЙ шкалы: `direction = inverse` («Пересчёт итога»). `percent`
инвертируется пост-агрегации; диапазоны применяются к `raw` как есть.

Инверсию ОТДЕЛЬНЫХ пунктов (смешанная шкала, где часть вопросов «обратные») выражают явными
ОТРИЦАТЕЛЬНЫМИ числами в сетке «вариант × шкала»: чтобы вычесть — минус, чтобы зеркалить —
зеркальные числа. Отдельного per-ребро флага в модели нет.

### 10.5 Операции агрегации и нормализации

Поддерживаемые операции расчёта:

- агрегация: пять операций (`sum` по умолчанию, `avg`/`weighted_avg`/`max`/`min`);
  `avg`/`weighted_avg` делитель — число вкладывающих ВОПРОСОВ (не строк) / `Σ weight`;
  `weighted_avg` берёт вес с ребра «вопрос × шкала». Для композита (источник «другие шкалы») —
  `sum`/`avg`; взвешенную или экстремум-комбинацию дочерних шкал даёт слой «Показатели». Порог
  «пройден/не пройден» выражается диапазонами `bands`, произвольная агрегация — формулой
  показателя;
- нормализация: `none` и `percent` (с учётом `direction`); `linear`/`custom` (`a*raw+b` с полом
  `max(0, .)`) — точка расширения; пол (clamp) живёт внутри `linear`/`custom`, отдельного поля нет;
- условия вклада (`condition_json`) — точка расширения; многошкальность выражается отдельными
  per-option строками сетки.

### 10.6 Вне охвата модели

Negative marking / «правильный минус неправильный»; зачёт корректно НЕ выбранных дистракторов;
choose-N с нормализацией `points·selected/N`; ипсативная валидация; z-нормирование на
популяцию; argmax/outcome как слой вклада (это формула показателя); IRT/Rasch и оценка
параметров заданий — платформа потребляет только ГОТОВЫЕ данные (пороги, линейные коэффициенты
уравнивания, в пределе таблицу пересчёта `custom`), но не оценивает параметры и не считает θ;
free-text/numeric/hotspot.

### 10.7 Два пререквизита (до scale-стороны)

1. Градуированный `checkAnswer`: сейчас возвращает строго 0/1; нужна рубрика по типам (веса
   опций, по-парные тиры, кредит позиции), дефолт = текущее бинарное поведение (старые тесты
   бит-идентичны). `answer_score` бесполезен, пока балл вопроса не станет числом.
2. Стабильные ID единиц: варианты/пары/позиции адресуются индексом массива; нужны durable ID
   (или index-remap миграция) до под-вопросной маршрутизации.

### 10.8 Иерархия слоёв

Это не три равноправных слоя, а конвейер из четырёх уровней:

- КОРРЕКТНОСТЬ / БАЛЛ ВОПРОСА (`correctJson`/`answer_score`) — свойство ВОПРОСА (раздел
  «Вопросы»), отдельно от вкладов;
- ВКЛАД (`question_measurements`) — РЕБРО «вариант -> шкала» (явное число `value_json`),
  входной фасет ШКАЛ, а не сосед показателей;
- ШКАЛА — узел-агрегат (`raw = Σ`; диапазоны НА `raw` -> level; пересчёт — параллельное
  отображаемое значение; публикация `scale.*`);
- ПОКАЗАТЕЛЬ (`result_variables`) — отдельный слой произвольной логики над `scale.*`
  (формула + `controls_status`, публикация `result.*`).

В авторском UI это кодируется уровнями: «Шкалы» и «Показатели» — верхние табы-пиры; «Список
шкал» и «Вклады вопросов» — два под-раздела (рейл) таба «Шкалы». Вклады принадлежат миру шкал,
показатели — отдельный мир.

### 10.9 Ацикличность графа вычисления

Композиция шкал и ссылки показателей образуют граф зависимостей; он обязан быть АЦИКЛИЧНЫМ
(DAG). Защита — на трёх уровнях:

- **составные шкалы** — граф «шкала -> дочерние шкалы» проверяется при сохранении; цикл (в т.ч.
  самоссылка) и ссылка на несуществующую дочернюю шкалу — БЛОКИРУЮЩАЯ ошибка валидации
  (PRD-5 §11). Вычисление топологическое: дочерние шкалы считаются до родительской;
- **показатели** — ссылка `var()` разрешена только на показатель с МЕНЬШИМ `sort_order`
  (PRD-2): порядок монотонный, цикл невозможен по построению, расчёт идёт по `sort_order`;
- **между слоями** циклов нет по конвейеру (§4, §10.8): `scale.*` считается до `result.*`, а
  шкалы на показатели не ссылаются.

Runtime НЕ полагается только на валидацию: движок расчёта обходит граф с защитой от повторного
входа (множество посещённых / предел глубины), чтобы цикл в данных (legacy, ручная правка,
recovery) не приводил к бесконечной рекурсии, а давал контролируемую ошибку.

### 10.10 Частичная корректность (множественный выбор)

Когда в `multiple`/`matching`/`ranking` выбрана лишь ЧАСТЬ верных единиц, две оси результата
считаются независимо:

- **вклад в шкалу** = `Σ (value × weight)` по фактически выбранным единицам (§10.1): выбор
  подмножества даёт сумму вкладов этого подмножества — отдельного «частичного» правила нет;
- **стандартный балл** = `0`, если выбранный набор не совпал с эталоном ТОЧНО (лишняя или
  недостающая единица — уже `0`); промежуточного значения нет (§10.2). На оси правильности
  «частично верно» эквивалентно «неверно».

Градуированный балл (дробное значение по доле верных, со штрафом за неверные) в этой модели
НЕ вычисляется: для него `checkAnswer` должен возвращать число из `[0, 1]` вместо `0`/`1`, а
это отдельный механизм — PRD «Градуированная оценка ответа» (BRD BR-09, ROADMAP §0.2). До его
выпуска:

- `answerState.scoreRatio` (spec-template-platform §10) всегда `0` или `1`, статус `partial`
  («Частично правильно») не наступает;
- условие `answer.scoreRatio >= N` (PRD-5 §4.4) не имеет промежуточных значений.

### 10.11 Единица вклада для matching и ranking

Вклад формируется по фактическому ОТВЕТУ: единица «активна», если обучающийся её образовал, и
учитывается один раз; корректность ортогональна (§10.2). Тип единицы и её `source_key`
(PRD-5 §9.2) зависят от типа вопроса:

- `matching` — единица = направленная ПАРА `(leftId -> rightId)` (`matching_pair`). Ответ —
  набор пар (по одной на каждый левый элемент); активна каждая РЕАЛЬНО составленная пара. Ячейка
  сетки привязана к конкретной паре, поэтому автор оценивает и верное сопоставление
  (`l1 -> r1` -> +2), и диагностичное неверное (`l1 -> r3` -> вклад в шкалу «типовая ошибка»);
- `ranking` — единица = РАЗМЕЩЕНИЕ `(itemId @ позиция)` (`ranking_position`). Ответ — позиция
  каждого элемента; активно фактическое размещение. Ячейка привязана к паре «элемент +
  позиция», поэтому «X на 1-й позиции» и «X на 3-й» могут вкладывать разное.

Дальше действует правило суммы §10.1: в шкалу идёт `Σ (value × weight)` по активным единицам с
непустой ячейкой в её столбце (у `matching` их не больше числа левых элементов, у `ranking` —
числа элементов). Условие `answer.rankingPosition(itemId) <= N` (PRD-5 §4.4) — отложенный ярлык
для оценки «топ-N» без перечисления каждой пары «элемент + позиция».
