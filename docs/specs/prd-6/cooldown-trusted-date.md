# PRD-6: доверенный источник даты для retake-кулдауна

Дополнение к [retake-cooldown-gate.md](retake-cooldown-gate.md) (§4.2). Согласовано 2026-07-29, код не начат.

## 1. Проблема

Календарная формула кулдауна (`retake-cooldown-gate.md` §4.1) принимает два входа: дату последней попытки и
«сегодня». В SCORM-пакете «сегодня» берётся с машины ученика — `todayIso()` в
`server/scorm/template/app/eligibility/gate.js` вызывает `new Date()`. Перевод системной даты вперёд на
`cooldownPeriodDays` снимает блокировку.

Дата последней попытки этой уязвимости не подвержена: её отдаёт WebTutor
(`docs/references/webtutor-learning-records-api.md`), подделать её из браузера нельзя.

Веб-хост уязвимости не имеет: решение принимает сервер (`server/services/retake-gate.ts`, вызовы в
`server/routes/attempts.ts` и `server/services/home/assigned.ts`) по серверным часам и по `attempts.finished_at`.
Единственное чтение локальных часов на вебе — `daysUntilIsoDate` в `client/src/pages/learner/cooldown-format.ts`,
и оно косметическое: влияет только на строку «через N дн.», запрет старта от него не зависит.

## 2. Границы задачи

Закрываем: обход переводом системных часов и подменой часового пояса.

Не закрываем: DevTools, правку JS в распакованном пакете, подмену ответов сети. Клиентский гейт принципиально
обходится технически подготовленным пользователем; полный запрет требует серверного вердикта и в этот объём не
входит (решение зафиксировано 2026-07-29: полная защита не оправдана).

Отклонённые варианты:

- NTP. Из браузера недостижим (UDP/123). HTTP-сервисы времени — внешние URL, запрещены NFR-07, недоступны из
  контура портала и не дают гарантии выше, чем часы самого сервера LMS, которые и так синхронизированы по NTP.
- Серверный подписанный вердикт от нашего хоста. Требует сетевой доступности нашего сервера из LMS, CORS и
  отдельной политики безопасности по NFR-07; превращает сетевой сбой в «курс закрыт для всех».
- High-water mark даты в `suspend_data` и запечённая дата сборки пакета. Ловят только перевод даты назад, который
  ученику невыгоден. Кода без пользы не пишем.

## 3. Решение: SCORM-пакет

### 3.1 Источник «сегодня»

Календарный день берётся из HTTP-заголовка `Date` ответа портала — это часы сервера LMS. Заголовок читается
только для same-origin ответов, что для гейта выполняется по построению: он уже ходит на портал за SECID и за
коллекцией учебных записей.

### 3.2 Дата едет на существующем запросе

Гейт уже забирает страницу портала ради SECID (`resolveSecid`). Вводится мемоизированный
`fetchPortalChrome(url)`: один `fetch(url, { credentials: 'include', cache: 'no-store' })` на URL за время жизни
гейта, результат `{ text, dateHeader }`. Из него читают и SECID, и `cur_person_id` (когда `personIdSource`
настроен), и резолвер даты.

Итог по числу обращений к LMS: на штатной конфигурации (`shared/eligibility/registry.ts`, `personIdSource` не
задан — учащийся определяется сессионной cookie) было и остаётся ОДНО обращение к странице портала, новых
запросов ноль. На конфигурации, где администратор задал `personIdSource` с тем же endpoint, было два, станет
одно.

### 3.3 Порядок вызовов и деградация

`buildContext(td)` становится асинхронным и до запуска плагина резолвит `runtime.todayDate`:

1. `fetchPortalChrome(secidSource.endpoint || '/')`, заголовок `Date`, преобразование в UTC-календарный день.
2. Заголовок отсутствует, не парсится, ответ не same-origin, запрос упал или не уложился в собственный таймаут
   2500 мс — откат на клиентские часы, то есть текущее поведение.

Общий бюджет гейта `GATE_TIMEOUT_MS` (5000 мс, NFR-06) не меняется; резолв даты имеет отдельный таймаут внутри
этого бюджета, чтобы медленный портал не мог подвесить старт.

Отдельного `failClosed` для источника даты не вводим: он превращает сетевую икоту в блокировку курса для всех.

### 3.4 Граница суток

День вычисляется как UTC-календарный из серверного timestamp. Часовой пояс клиента не участвует.

Обоснование: если считать день по поясу клиента (`Intl`), обход переводом часов закрывается, но открывается обход
переводом пояса — TZ вида UTC+14 даёт «завтра» без касания часов. Серверный timestamp плюс UTC-день не берут от
машины ученика ничего.

Осознанное следствие: кулдаун истекает в 03:00 МСК, а не в 00:00. Веб-хост уже работает по UTC
(`toIsoDateUTC(new Date())`), так что площадки выравниваются.

## 4. Решение: веб-хост

Правка согласованности, не защиты. Сервер добавляет в блок `retakeGate` ответа стартового экрана
(`server/routes/attempts.ts`) поле `daysUntil` рядом с `availableDate`, вычисленное по серверной дате. Клиент
(`client/src/pages/learner/take-test.tsx`) показывает пришедшее значение.

`daysUntilIsoDate` и его тесты из `client/src/pages/learner/cooldown-format.ts` удаляются; `fmtIsoDateHuman`
остаётся. После правки в клиентской логике кулдауна не остаётся ни одного вызова `new Date()`.

Домашняя страница (PRD-25) отдаёт `blockedUntil` и обратный отсчёт не показывает — изменений не требует.

## 5. Общая математика

В `cooldownDecision` (`shared/eligibility/engine.ts` и JS-твин
`server/scorm/template/app/eligibility/engine.js`) добавляется санитарная нормализация: если
`todayDate < lastAttemptDate`, за «сегодня» принимается `lastAttemptDate`. Состояние невозможное, значит часам
верить нельзя.

На серверном пути поведение не меняется (`today` там всегда не меньше `finished_at`). Твины остаются в паритете,
это проверяет `tests/eligibility-engine-port.test.ts`.

## 6. Диагностика

`glog` гейта дополняется одной строкой перед решением: источник даты (`network` / `client`), серверный timestamp,
клиентский, расхождение в секундах. Первый живой запуск в LMS читается с консоли за один прогон, без итераций
«поправили — перезалили». Персональных данных строка не несёт (NFR-05).

## 7. Подтверждено на живом портале

Пробник выполнен в консоли `https://university.rt.ru` 2026-07-29:

| Факт | Значение |
| --- | --- |
| Тип ответа | `basic` (same-origin), HTTP 200 |
| Видимые заголовки | `accept-ranges, cache-control, connection, content-type, date, strict-transport-security, transfer-encoding, x-content-type-options, x-frame-options` |
| `Date` | `Wed, 29 Jul 2026 05:36:48 GMT` |
| Расхождение с часами машины | -1 с |
| Повтор через 1.5 с | `Date` изменился — кэш и прокси не отдают старый ответ |
| Календарный день | сервер(UTC) = клиент(локальный) = `2026-07-29` (прогон в 08:36 МСК) |

Вывод: механизм на портале работает, расхождения часов портала и рабочих машин пренебрежимы.

## 8. Открытый риск: origin фрейма курса

Пробник выполнен в контексте страницы портала. Не подтверждено, что **фрейм запущенного курса** имеет тот же
origin: в консоли портала виден чужой курс с собственным `scorm-driver` и `CrossDomainRouter`, то есть вендор
закладывался на возможность раздачи контента с отдельного хоста.

Если контент курсов раздаётся не с `university.rt.ru`, то `fetch('/')` из пакета уходит не на портал — и тогда
неработоспособно не только чтение даты, но и весь существующий `webtutor_cooldown` (скрапинг SECID, POST
коллекции). Это находка крупнее текущей задачи и требует пересмотра §4.2 основной спеки.

Проверка — одна строка в консоли верхнего фрейма при открытом курсе:

```js
Array.from(document.querySelectorAll('iframe')).forEach((f) =>
  console.log(f.src ? new URL(f.src, location.href).origin : '(about:blank)', '|', f.src));
```

Шаг обязателен перед началом реализации SCORM-части. Веб-часть (§4) и общая математика (§5) от него не зависят.

## 9. Локальный стенд вместо живого WebTutor

Живой WebTutor для отладки недоступен. Эмулятор портала в `scripts/scorm-player.mjs` уже существует с PRD-6
фазы 1 и раздаёт с одного origin:

- страницу-заглушку портала с 32-hex SECID и `cur_person_id` в разметке;
- endpoint коллекции учебных записей `/pp/Ext5/extjs_json_collection_data.html` с настраиваемой записью
  (`name`, `state`, `last_usage_date` в формате `dd.MM.yyyy` по контракту из
  `docs/references/webtutor-learning-records-api.md`), управляемой панелью мока;
- собранный SCORM-пакет.

Не хватает единственного: возможности развести часы сервера и машины. Добавляется флаг `--server-date=` (и
переменная окружения `SCORM_PLAYER_SERVER_DATE`), проставляющий заголовок `Date` ответов стенда.

## 10. Проверка и приёмка

Юнит-тесты:

- разбор заголовка `Date` в UTC-календарный день, включая невалидное и отсутствующее значение;
- откат на клиентские часы по каждой ветке деградации (нет заголовка, HTTP-ошибка, не same-origin, таймаут);
- мемоизация запроса портала: один сетевой вызов на URL;
- санитарная нормализация `today < lastAttemptDate` в обоих твинах плюс существующий тест паритета.

Приёмка на стенде (§9): часы стенда — текущая дата, системная дата машины переведена вперёд на
`cooldownPeriodDays + 1`, гейт обязан остаться заблокированным. Обратный кейс: часы стенда за горизонтом
кулдауна, машина отстаёт — старт разрешён.

Приёмка веба: Playwright, стартовый экран с активным кулдауном, строка «через N дн.» соответствует серверной дате
при переведённых часах браузера.

## 11. Требования

| ID | Требование |
| --- | --- |
| FR-TD-01 | «Сегодня» в SCORM-гейте берётся из заголовка `Date` same-origin ответа портала |
| FR-TD-02 | Недоступность заголовка не блокирует старт: откат на клиентские часы |
| FR-TD-03 | Календарный день вычисляется в UTC; часовой пояс клиента не участвует |
| FR-TD-04 | Обращение к странице портала мемоизируется; число запросов к LMS не растёт |
| FR-TD-05 | `todayDate < lastAttemptDate` нормализуется до `lastAttemptDate` в общем движке |
| FR-TD-06 | Веб-хост отдаёт `daysUntil` с сервера; клиент не читает локальные часы |
| NFR-TD-01 | Резолв даты укладывается в собственный таймаут 2500 мс внутри бюджета NFR-06 |
| NFR-TD-02 | Диагностика называет источник даты и расхождение часов без персональных данных |
