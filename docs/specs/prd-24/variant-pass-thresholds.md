# PRD-24: Пороги прохождения по вариантам

**Версия:** 1.0
**Статус:** ТРЕБОВАНИЯ СОГЛАСОВАНЫ 2026-07-23 (спецификация и план приняты) — реализация не начата.
**Дата:** 2026-07-23
**Связанные документы:** [PRD-17](../prd-17/question-set-variants.md) (варианты выдачи —
предмет, к которому привязан порог),
[PRD-7](../../wireframes/approved/prd7-editor-settings-tab.html) (эскиз вкладки
«Настройки» — правила прохождения темы), [PRD-10](../prd-10/graded-answer-scoring.md) (цена ответа —
базис порога «сумма баллов»), [PRD-15](../prd-15/content-ownership.md) (оценка — свойство
теста, снапшоты публикации), [PRD-14](../prd-14/questions-import-export.md) +
[спецификация формата](../questions-import/format.md) (книга Excel),
[PRD-18](../prd-18/debug-test-player.md) (встроенный отладчик),
[scoring-model.md](../scoring-model.md) (сквозная модель расчёта)
**Основание:** PRD-17 D-6 и §9 — «пер-вариантная калибровка порогов вне охвата PRD-17,
возврат к ней — предмет отдельного будущего PRD»; риски PRD-17 R-8/R-9 (неравные варианты
против общего абсолютного порога). Настоящий PRD закрывает часть этого долга — **пороги**,
не коэффициенты.

## Терминология

- **Вариант** — вариант теста по PRD-17: скурированный автором набор вопросов темы,
  выдаваемый целиком; хранится в `test_sections.form_set_json.forms[]`, ключ — стабильный
  `formId`.
- **Правило прохождения темы** — существующая настройка раздела
  (`test_sections.topic_pass_rule_json`) с источниками «Как у теста» / «Индивидуальное
  правило» / «Не проверять отдельно» (PRD-7).
- **Правило «по вариантам»** — новый, четвёртый источник правила прохождения темы:
  порог задаётся отдельно на каждый вариант темы и применяется к тому варианту, который
  фактически выпал обучающемуся.
- **Выданный вариант** — вариант, выпавший в этой попытке по этой теме (`formId` из
  `attempts.variant_json.sections[]` в вебе, из состояния рантайма в SCORM).

## 1. Обзор

### 1.1 Повод

Правило прохождения темы сегодня резолвится без знания того, какой вариант выпал
([shared/scoring/pass-rule.ts](../../../shared/scoring/pass-rule.ts) —
`resolveTopicRule(raw, overall)`). На тему приходится ровно один порог, общий для всех её
вариантов.

Для типа «Сумма баллов» это содержательный дефект: цена вопроса — свойство теста
(PRD-15 блок D), градуированное начисление (PRD-10) делает вклад вопроса дробным, поэтому
два варианта из восьми вопросов легко расходятся по достижимому максимуму баллов. Один
абсолютный порог на такие варианты означает разные шансы у обучающихся — ровно риск R-9
в PRD-17, зафиксированный там как принятый, потому что порог «остаётся на разделе».

Для типа «Процент» разрыв мягче (процент нормирован на выданное), но варианты могут
отличаться по составу и сложности, и автору нужна возможность развести планку.

PRD-17 оставил это место сознательно (D-6). Настоящий PRD его занимает в минимальном
объёме: **порог на вариант**, без калибровочных преобразований сырого балла.

### 1.2 Граница

| Подмеханика | Веб-хост | SCORM-пакет |
| --- | --- | --- |
| Знание выданного варианта при оценке | есть (`variant_json.sections[].formId`, PRD-17 FR-08) | появляется в этом PRD: рантайм начинает пиннить `formId` в состоянии |
| Пороги по вариантам | да | да |
| Ротация вариантов | да | нет (NFR-17, деградация PRD-17) — на пороги не влияет |

Порог по вариантам работает на обеих площадках одинаково: правило резолвится единым
движком `shared/scoring/pass-rule.ts`, который оба хоста уже используют (PRD-18).

### 1.3 Метрики успеха

| Цель | Метрика |
| --- | --- |
| Справедливость абсолютного порога | по каждому варианту порог задаётся своим числом; тема зачитывается по порогу ВЫДАННОГО варианта |
| Паритет площадок | веб и SCORM выносят одинаковый вердикт по теме на одинаковых данных (parity-тест) |
| Обратная совместимость | темы без правила «по вариантам» оцениваются в точности как сегодня |
| Прозрачность | автор видит в отладчике, какой вариант выпал и какой порог к нему применён |
| Сохранность в обмене | правило переживает экспорт и импорт книги Excel без потерь |

## 2. Пользователи

- **Автор теста** — на теме в режиме вариантов выбирает правило «По вариантам» и задаёт
  на каждый вариант тип порога и значение.
- **Методолог** — в отладчике (PRD-18) видит выпавший вариант и применённый к нему порог.
- **Обучающийся** — получает вердикт по теме, посчитанный по порогу своего варианта; на
  экране результатов подпись «Требуется: …» соответствует выданному варианту.

## 4. Модель данных

Новых таблиц и колонок нет. Расширяется существующий union правила прохождения темы,
хранимый в `test_sections.topic_pass_rule_json` (`jsonb`, миграция не требуется).

```text
test_sections.topic_pass_rule_json:
  { source: 'inherit_overall' }                                  # как сегодня
  { source: 'custom', type: 'percent'|'absolute', value: number } # как сегодня
  { source: 'none' }                                             # как сегодня
  { source: 'by_variant',                                        # НОВОЕ
    byForm: { [formId: string]: { type: 'percent'|'absolute', value: number } } }
```

Схема (Zod, `shared/schema.ts` рядом с `passRuleSchema`; сейчас union правила темы описан
только в клиентских типах — переносится в общий источник):

```ts
topicPassRuleSchema = z.discriminatedUnion("source", [
  z.object({ source: z.literal("inherit_overall") }),
  z.object({ source: z.literal("custom"), type: z.enum(["percent", "absolute"]), value: z.number() }),
  z.object({ source: z.literal("none") }),
  z.object({
    source: z.literal("by_variant"),
    byForm: z.record(z.string(), z.object({
      type: z.enum(["percent", "absolute"]),
      value: z.number(),
    })),
  }),
]);
```

- **Ключ — `formId`.** Тот же стабильный идентификатор, на котором держится ротация
  (PRD-17 D-8/R-3). Позиционный индекс отвергнут по той же причине: правка набора
  вариантов не должна переадресовывать пороги.
- **Хранение на разделе, не на варианте.** Порог — предмет ОЦЕНКИ, а `form_set_json` —
  предмет ВЫДАЧИ; кроме того, `form_set_json` пересобирается импортом книги
  (`buildFormSet`), и пороги внутри него терялись бы при каждом импорте.
- **Отдельная таблица не заводится:** данные всегда читаются вместе с разделом,
  самостоятельных запросов по ним нет.
- **Снапшоты** сериализуют раздел целиком, правило замораживается вместе с
  `form_set_json` — расхождения «порог от новой редакции, состав от снапшота» не возникает
  (FR-15).

## 5. Резолвинг и оценка

### 5.1 Контекст выдачи в движке

`resolveTopicRule` получает третий, необязательный аргумент — контекст выдачи:

```text
resolveTopicRule(raw, overall, ctx?):
  ...                                              # существующие ветки без изменений
  if raw.source == 'by_variant':
      entry = ctx?.formId ? raw.byForm[ctx.formId] : undefined
      if entry: return { type: entry.type == 'percent' ? 'percent' : 'count', value: entry.value }
      return overall                               # деградация, FR-09
```

Возвращаемое значение — прежнее `{ type: 'percent'|'count', value } | null`; `checkPassRule`
не меняется. То есть за пределами резолвинга ни один потребитель не узнаёт о новом
источнике — это ключевое свойство решения.

### 5.2 Точки передачи `formId`

| Хост | Источник `formId` | Точка |
| --- | --- | --- |
| Веб, итог попытки | `attempts.variant_json.sections[].formId` | `AggregateSection` в `server/routes/attempts.ts` |
| Веб, результат раздела | то же | обработчик результата раздела в `server/routes/attempts.ts` |
| SCORM, итог и раздел | `state.variant.sections[].formId` (пиннится при выборе, FR-08) | `calculateResults` / `computeSectionResult` в `resultsPage.js` |
| SCORM, подпись «Требуется: …» | то же | `viewResults.js` |

`AggregateSection` получает необязательное поле `formId`; `aggregateStandardResult`
прокидывает его в `resolveTopicRule`. Секции без вариантов передают `null` — поведение не
меняется.

### 5.3 Деградация (FR-09)

Правило «по вариантам» не резолвится, если выданный вариант неизвестен или его нет в карте:

- попытка, начатая до PRD-17 (в `variant_json` нет `formId`);
- состояние SCORM-сессии, сохранённое до этого PRD (нет пина в `suspend_data`);
- вариант удалён автором после старта попытки в живом (не опубликованном) тесте.

Во всех случаях применяется ОБЩЕЕ правило теста — то же, что дало бы «Как у теста».
Выбор обоснован тем, что тема остаётся под проверкой (падение в «нет гейта» тихо
отключило бы контроль), а редактор не даёт сохранить тест с непокрытым вариантом
(FR-13), поэтому для нормально настроенных живых тестов ветка недостижима.

### 5.4 Манифест SCORM (FR-17)

`imsss:minNormalizedMeasure` в манифесте — статические метаданные секвенсинга, тогда как
вердикт считает рантайм. Для правила «по вариантам» единого числа нет, поэтому берётся
МИНИМУМ нормализованных порогов по вариантам темы: `percent / 100` для процентного и
`value / Σ баллов варианта` для абсолютного (сумма считается на этапе сборки пакета, где
цена вопроса уже резолвится). Более строгое значение могло бы заблокировать обучающегося,
который прошёл по правилу своего варианта.

## 6. Валидация

На сохранении теста (клиент — блокирующая валидация редактора; сервер — схема раздела):

- источник `by_variant` допустим только при заданном `form_set_json` с ≥2 вариантами
  (FR-02); иначе — ошибка. Адаптивный режим теста гасит варианты (PRD-17), поэтому
  источник там недоступен;
- `byForm` покрывает ВСЕ варианты темы: непокрытый вариант — ошибка (иначе оценка молча
  ушла бы в деградацию §5.3);
- ключ `byForm`, не соответствующий ни одному варианту темы, — ошибка (осиротевшая
  запись);
- `type: 'percent'` → значение в диапазоне 0..100;
- `type: 'absolute'` → значение не больше достижимого максимума баллов ЭТОГО варианта
  (сумма эффективных цен его вопросов). Это уточнение существующей проверки, которая
  сегодня сравнивает порог темы с максимумом всего банка темы и потому пропускает
  недостижимые пороги.

Синхронизация с набором вариантов (FR-12) выполняется в редакторе при правке набора:
добавление варианта заводит запись (значение наследуется от прежнего правила темы —
из «Индивидуального правила», иначе из общего правила теста), удаление варианта удаляет
запись, отключение режима вариантов нормализует правило в «Как у теста».

## 7. Пользовательский интерфейс

Поверхность — существующая таблица «Правила прохождения тем» в подразделе «Правила
прохождения» вкладки **«Настройки»** редактора теста
([basic-settings-section.tsx](../../../client/src/features/tests/editor/sections/basic-settings-section.tsx)).
Эскиз — доработка `approved/prd7-editor-settings-tab.html`: раскладка, заголовки и
существующие контролы сохраняются один в один, дельта минимальна.

- В выпадающем списке «Правило прохождения темы» у темы в режиме вариантов появляется
  четвёртый пункт — **«По вариантам»**. У остальных тем список прежний (три пункта).
- При выборе «По вариантам» раскрывается та же вложенная строка таблицы, что и у
  «Индивидуального правила», но вместо одной пары контролов в ней — по строке на вариант:
  метка варианта («Вариант 1»), «Тип» (`Процент` / `Сумма баллов`), «Порог».
- Подсказка под блоком показывает достижимый максимум баллов варианта — иначе автор не
  может осмысленно выставить абсолютный порог.
- Ошибки валидации адресуются полю варианта, как сегодня адресуются поля
  `passRules.byTopic[...]`.

Все контролы — DS-примитивы (`Select`, `NumberInput`, `tb-table`), новых локальных
классов не вводится.

## 8. Обмен через Excel (FR-14)

Книга теста получает восьмой лист — **`Пороги вариантов`**, по образцу листа `Квоты`
(та же кардинальность «раздел → N дочерних записей», та же связь по имени раздела):

`Раздел` (имя темы, как на листе `Структура`) · `Вариант` (номер варианта, 1-based — та же
нумерация, что в колонке `Варианты` листа `Вопросы`) · `Тип порога` (`Процент` /
`Сумма баллов`) · `Порог` (число).

На листе `Структура` колонка `Тип порога` принимает новое значение **`По вариантам`**
(алиасы импорта: `по вариантам`, `by_variant`), колонка `Порог` при этом пуста.

- **Ключ — номер, не `formId`.** Идентификаторов вариантов в книге нет и не появляется:
  варианты позиционны (PRD-17 D-10), экспорт переводит `formId` в номер по той же таблице
  соответствия, которую уже строит для колонки `Варианты`, импорт — обратно, после сборки
  `form_set_json`.
- **Порядок импорта:** лист читается ПОСЛЕ сборки набора вариантов, иначе номер не к чему
  привязать. В цепочке §12.5 спецификации формата он встаёт после `Структура` + `Квоты`.
- **Ошибки:** номер варианта, отсутствующий среди объявленных на листе `Вопросы`, —
  ошибка строки (остальные строки импортируются); тип порога раздела `По вариантам` при
  неполном покрытии вариантов — ошибка раздела. Книга не должна быть обходом валидации
  редактора.
- Отсутствие листа или его пустота — не ошибка (как у `Квоты`): лист просто пропускается.

Контракт листа фиксируется в §12.8 [спецификации формата](../questions-import/format.md).

## 9. Совместимость

- Правило `by_variant` опционально; темы без него оцениваются прежним кодом без изменений.
- Пин `formId` в состоянии SCORM добавляется как необязательное поле: сессии, сохранённые
  до этого PRD, читаются без ошибки и оцениваются по §5.3.
- Попытки, завершённые до этого PRD, уже содержат посчитанный результат — пересчёт не
  выполняется, историческая аналитика не меняется.
- Отладчик PRD-18 сегодня восстанавливает `formId` сопоставлением множества выданных
  идентификаторов; после появления пина он читает пин, а сопоставление остаётся запасным
  путём для старых состояний.
- Книга без листа `Пороги вариантов` импортируется как сегодня.

## 10. Вне охвата

- **Калибровочные преобразования сырого балла** (пер-вариантные коэффициенты вида
  `1.25 · raw − 7.89` из постобработчика РТК) — по-прежнему вне охвата (PRD-17 D-6).
  Этот PRD даёт РАЗНЫЕ ПОРОГИ, а не преобразование шкалы.
- **Пороги по вариантам для ОБЩЕГО правила теста** — общий порог остаётся одним на тест:
  тест-уровневой связки вариантов нет (PRD-17: вариант выбирается по каждой теме
  независимо), поэтому «вариант теста целиком» не определён.
- **Пер-вариантные диапазоны шкал и показателей** (PRD-5/PRD-2) — не затрагиваются.
- **Автоматическое выравнивание вариантов** (подбор порога по сложности) — ручная
  настройка автором; авто-балансировка возможна как будущее расширение.
- **Переименование вариантов** — метка остаётся авто-нумерованной (PRD-17 D-10).

## 11. Решения

| # | Вопрос | Решение |
| --- | --- | --- |
| D-1 | Где хранить пороги: в правиле темы или в наборе вариантов | В правиле темы (`topic_pass_rule_json`). Порог — предмет оценки, а не выдачи; `form_set_json` пересобирается импортом книги, и пороги в нём терялись бы |
| D-2 | Ключ порога — позиция варианта или `formId` | `formId` (PRD-17 D-8/R-3): правка набора не должна переадресовывать пороги |
| D-3 | Поведение при неизвестном выданном варианте | Деградация к общему правилу теста (FR-09): тема остаётся под проверкой, а редактор не даёт создать такую конфигурацию |
| D-4 | Формат в книге Excel | Отдельный лист `Пороги вариантов` по образцу `Квоты` (§8). Отвергнуты: список в ячейке `Порог` (собственный мини-синтаксис, смена типа колонки) и разворот `Структура` построчно (ломает инвариант «строка = раздел») |
| D-5 | Нужен ли тип «Процент» на вариант, если процент уже нормирован | Да: варианты различаются составом и сложностью, автору нужна возможность развести планку. Заказчиком заявлены оба типа |
| D-6 | `minNormalizedMeasure` в манифесте при правиле «по вариантам» | Минимум нормализованных порогов по вариантам (§5.4): метаданные секвенсинга не должны быть строже реального правила |
| D-7 | Смешение типов внутри одной темы (вариант 1 — процент, вариант 2 — баллы) | Разрешено: типы независимы по вариантам (FR-03). Запрет не даёт выигрыша, а ограничивает калибровку |
| D-8 | Показывать ли обучающемуся метку выпавшего варианта на экране результатов | РЕШЕНО (2026-07-23): НЕТ. Варианты обучающемуся не показываются (как сегодня); подпись «Требуется: …» отражает порог его варианта без названия варианта |
| D-9 | Где живёт отчёт «распределение попыток и проходимости по вариантам» | РЕШЕНО (2026-07-23): за пределами PRD-24 — в треке [BRD «Аппарат психометрической аналитики тестов»](../brd-psychometric-analytics.md), где вариант (`formKey`) уже измерение выборки (PA-29 — надёжность по фиксированным формам PRD-17). PRD-24 даёт данные (пин `formId` в попытке), отчёт строит аналитический трек |

## 13. Риски

| # | Риск | Митигация |

| R-1 | Расхождение веб ↔ SCORM в вердикте темы | Единый движок резолвинга (FR-07) + parity-тест на правило «по вариантам» в обеих средах |
