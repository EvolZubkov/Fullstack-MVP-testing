# PRD-22: Поля контентной страницы и последовательности страниц

**Версия:** 1.0
**Статус:** РЕАЛИЗОВАН (не закоммичен). Закрыты все этапы: Э0 (откат несогласованных правок),
Э1 (эскиз), Э2 (контракт типов, `settings[]`, валидация, колонка `settings_json`), Э3 (ядро
последовательностей и блок `page.*`), Э4 (рендер на всех трёх поверхностях + шаблон

поле идентификатора, предпросмотр изображения, режимы ввода через новый компонент ui-kit

Остаётся приёмка в живом редакторе после применения миграции к базе стенда и обновление

## 1. Обзор

### 1.1 Контекст

Поводом стал дефект: шаблон `certification` объявляет вариант страницы «Галерея: карточка», но
автор не может выбрать его в «Структуре». Разбор показал, что дефект — следствие трёх системных
пробелов, а не единичная ошибка.

Первое: авторская страница жёстко приравнена к одному виду варианта (`kind: "info"`), поэтому
вариант с любым другим видом невидим в каталоге добавления. Галерею завели отдельным видом
страницы, чего платформа не поддерживает: значения `kind` ограничены перечнем БД, а
рендер галереи существует отдельной веткой только в SCORM-рантайме — на веб-хосте такая страница
рисуется пустой карточкой.

Второе: галерея настраивается ключами `pillsTotal`, `pillCurrent`, `showBack`, `nextLabel`,
`backgroundImage`, которые не объявлены ни в одном манифесте. Автор физически не может их
задать: форма страницы строится по `placeholders[]`, а этих ключей там нет. Они существуют
только в демонстрационных данных предпросмотра.

Третье: количество точек навигации и текущая позиция вводятся вручную числами. Система, которая
знает порядок страниц, перекладывает арифметику на автора — и при любой правке структуры числа
устаревают молча.

Общий корень: контракт «что автор может настроить на странице» не выражен в шаблоне и не
проверяется кодом. Перечень типов полей ведётся в двух несинхронизированных местах (форма
редактора и рендерер), тип поля в манифесте не валидируется вовсе — опечатка в типе даёт
однострочный ввод вместо ожидаемого контрола, без единой диагностики.

### 1.2 Цель

1. Отменить отдельный вид страницы «галерея»: галерея — это вариант обычной информационной
   страницы со своим макетом.
2. Сделать состав редактируемых свойств страницы производным ИСКЛЮЧИТЕЛЬНО от манифеста
   шаблона: редактор структуры не имеет собственных полей.
3. Разделить контракт по природе: `placeholders[]` — содержимое, вставляемое в макет;
   `settings[]` — свойства страницы, управляющие её поведением и оформлением.
4. Ввести перечень типов полей с валидацией манифеста и однозначной привязкой типа к контролу.
5. Ввести последовательности страниц: индикатор навигации и позиция вычисляются системой из
   структуры, а не вводятся автором.

Ограничение, действующее на все пять целей: структура теста и раскладка формы страницы НЕ
меняются. Всё новое умещается в уже реализованный интерфейс — списком полей, объявленных
вариантом (FR-04, FR-20).

### 1.3 Метрики успеха

| Цель | Метрика |
| --- | --- |
| Галерея доступна автору | Вариант «Галерея: карточка» присутствует в каталоге «Добавить страницу» |
| Нет полей вне контракта | Ни одно поле формы страницы не создаётся кодом редактора |
| Точки вычисляются | Ни один шаблон и ни одна страница не хранят количество и номер точки |
| Паритет хостов | Галерея рендерится идентично в SCORM-пакете, на веб-хосте и в предпросмотре |
| Контракт проверяется | Шаблон с неизвестным типом поля не принимается при загрузке и активации |
| Интерфейс не переизобретён | Вкладка «Структура» не изменена; в форме страницы отличие от текущей одно — предпросмотр изображения |

## 2. Пользователи

### 2.1 Разработчик шаблона

Объявляет в манифесте варианта поля содержимого (`placeholders[]`) и свойства страницы
(`settings[]`), включая обязательность и значения по умолчанию. Решает, содержит ли макет
индикатор навигации. Получает валидацию контракта при загрузке шаблона.

### 2.2 Автор теста

Заполняет в «Структуре» только те поля, которые объявил вариант. Объединяет подряд идущие
страницы в последовательность (галерею), задавая идентификатор; количество точек и текущую
позицию не вводит.

### 2.3 Ученик

Видит индикатор навигации и кнопку возврата на страницах, макет которых их содержит.

## 3. Функциональные требования

### 3.1 Вид страницы и каталог вариантов

- **FR-01.** Отдельного вида страницы «галерея» нет. Галерея — вариант информационной страницы
  (`kind: "info"`) с собственным макетом. Значение `gallery` исключается из перечня видов
  вариантов.
- **FR-02.** Каталог «Добавить страницу» формируется из вариантов авторских видов. Вариант,
  объявленный шаблоном и не относящийся к системным видам, обязан быть доступен автору.
- **FR-03.** Вид страницы, сохраняемый при создании, наследуется от варианта, к которому
  страница привязана.

### 3.2 Контракт полей: содержимое и свойства

- **FR-04.** Форма страницы в «Структуре» состоит исключительно из объявленного вариантом:
  `placeholders[]` (содержимое) и `settings[]` (свойства страницы). Редактор не добавляет
  собственных полей. Режим «Произвольный HTML» в объём настоящего PRD не входит и остаётся
  как есть.
- **FR-05.** Типы `placeholders[]`: `text`, `textarea`, `richText`, `html`, `image`,
  `resultField`.
- **FR-06.** Типы `settings[]`: `number`, `boolean`, `select`, `text`, `image`, `sequence`.
- **FR-07.** Настройка может объявлять значение по умолчанию (`default`) и обязательность
  (`required`).
- **FR-08.** Значение по умолчанию подставляется при создании страницы. Незаполненная
  обязательная настройка блокирует сохранение структуры тем же механизмом, что и незаполненный
  обязательный плейсхолдер; очистка поля обязательной настройки даёт ошибку и не обходит
  обязательность.

### 3.3 Перечень типов и валидация

- **FR-09.** Перечень типов полей объявляется однократно в общем коде и питает обе стороны:
  контрол редактирования и правило отрисовки значения.
- **FR-10.** Привязка «тип поля — контрол» задаётся полным отображением по перечню: отсутствие
  контрола для объявленного типа является ошибкой сборки, а не деградацией поля в
  однострочный ввод. Ветка «по умолчанию» в обоих механизмах удаляется.
- **FR-11.** Валидация манифеста проверяет тип каждого поля по перечню и совместимость его
  атрибутов (например, `select` без списка вариантов — ошибка).
- **FR-12.** Валидация выполняется при ЗАГРУЗКЕ и при АКТИВАЦИИ шаблона. Невалидный шаблон не
  принимается и не активируется; сообщение содержит ключ варианта и ключ поля.
- **FR-13.** Ранее установленные шаблоны продолжают работать, но помечаются как невалидные с
  указанием причины. Страница, чьё поле имеет неизвестный тип, показывает явную диагностику
  вместо подмены контрола.

### 3.4 Последовательности страниц

- **FR-14.** Свойство `sequence` — идентификатор последовательности. Введённое автором имя и
  есть идентификатор; скрытых технических ключей нет.
- **FR-15.** Поле идентификатора показывается автору только у варианта, который объявил
  свойство `sequence`. Не объявлено — поля нет, и точки для страницы не строятся, даже если
  идентификатор сохранён в данных.
- **FR-16.** Идентификатор выбирается из списка идентификаторов, уже использованных в тесте,
  либо создаётся новый. В список попадают только идентификаторы страниц, чей текущий вариант
  объявляет `sequence`.
- **FR-17.** УЧАСТОК СТРУКТУРЫ — отрезок страниц между структурными элементами: «До теста»,
  «Перед темой N», «После темы N», «После теста». Зона «После теста» делится границей «Итоги
  теста» на два участка. Последовательности разных участков не объединяются, даже если идут
  подряд в потоке прохождения. Участок — понятие ЯДРА для вычисления отрезков; в интерфейсе он
  не отображается и новых элементов структуры не порождает.
- **FR-18.** ПОСЛЕДОВАТЕЛЬНОСТЬ — максимальный отрезок подряд идущих страниц одного участка с
  одинаковым непустым идентификатором. Страница с другим идентификатором прерывает отрезок;
  следующая серия с тем же идентификатором образует новую последовательность.
- **FR-19.** Последовательность требует не менее двух страниц. Отрезок из одной страницы точек
  не даёт; страница отображается как обычная.
- **FR-20.** Структура теста НЕ меняется: список страниц, зоны, порядок, перетаскивание и
  все прочие элементы вкладки «Структура» остаются как есть. Последовательность — не объект
  структуры и не отображается в списке; она целиком выводится из значения свойства.
- **FR-21.** При переносе страницы её идентификатор сохраняется вместе с ней; принадлежность
  к последовательности пересчитывается по новому положению автоматически.

### 3.5 Контекст рендера страницы

- **FR-22.** Ядро передаёт контентной странице вычисленный блок: `page.dots` (точки отрезка с
  признаком текущей), `page.dotIndex`, `page.dotsTotal`, `page.canGoBack`.
- **FR-23.** Показывать индикатор навигации или нет — определяет макет варианта. Страница вне
  последовательности получает пустой набор точек и деградирует до простой.
- **FR-24.** `page.canGoBack` отражает ФАКТИЧЕСКУЮ возможность возврата в текущем режиме
  прохождения, включая возврат к странице-маршрутизатору с первой страницы раздела, а не только
  наличие предыдущей страницы участка.
- **FR-25.** Ключи `pillsTotal`, `pillCurrent`, `showBack` удаляются из значений страницы:
  первые два вычисляются (FR-18, FR-22), третий следует из FR-24.
- **FR-26.** `nextLabel` становится настройкой типа `text` со значением по умолчанию «Далее».
- **FR-27.** `backgroundImage` становится настройкой типа `image`; ядро применяет её как фон
  корневого элемента экрана.

### 3.6 Хранение, экспорт, публикация

- **FR-28.** Значения настроек хранятся в новой колонке `content_pages.settings_json` (jsonb, по
  умолчанию пустой объект), отдельно от содержимого.
- **FR-29.** При смене варианта идентификатор последовательности сохраняется, даже если новый
  вариант свойство не объявляет.
- **FR-30.** Настройки включаются в данные SCORM-пакета наравне с содержимым и проходят ту же
  санитизацию: значения типа `text` экранируются, значения типа `image` проверяются как ссылка
  на медиа. Без этого сборщик медиа не упакует фон страницы и в пакете останется битая ссылка.
- **FR-31.** Снапшот публикации включает настройки страницы; изменение настройки учитывается
  при определении расхождения опубликованной версии с текущей.

### 3.7 Ввод содержимого: режимы поля и объём HTML

- **FR-32.** Текстовое поле содержимого имеет переключатель режимов ввода: ПРОСТОЙ ТЕКСТ,
  ФОРМАТИРОВАННЫЙ ТЕКСТ, HTML. Тип поля в манифесте задаёт ПОТОЛОК: `html` — доступны все три
  режима, `richText` — простой и форматированный, `text`/`textarea` — только простой. Автор
  может понизить уровень, но не повысить.
- **FR-33.** В режиме форматированного текста показывается ЕДИНАЯ для всех полей и шаблонов
  панель: полужирный, курсив, зачёркнутый, маркированный и нумерованный списки, ссылка,
  очистка форматирования. Набор фиксирован системой; `allowedMarks` и `allowedBlocks`
  исключаются из контракта манифеста (объявления в существующих шаблонах перестают что-либо
  значить и вычищаются при обновлении).
- **FR-34.** Запрещённые конструкции не сохраняются: в режиме HTML сохранение отклоняется с
  ошибкой, перечисляющей найденное, — автор видит исходный код и правит его сам. В режимах
  простого и форматированного текста запрещённое вычищается в момент ВСТАВКИ (нормализация
  буфера обмена), поэтому до сохранения дело не доходит и ошибка не возникает.
- **FR-35.** Объём допустимого HTML не расширяется и не сужается: он равен тому, что задаёт
  санитизация — удаляются `<script>`, `<iframe>`, `<svg>`, `<object>`/`<embed>`/`<link>`/`<meta>`,
  атрибуты `on*`, `javascript:` и внешние `http(s)` в `src`/`href`; остальная разметка проходит.
  Полная таблица — [руководство §8.2](../../guides/template-development.md). Дополнительные
  перечни разрешённых или запрещённых тегов не вводятся.
- **FR-36.** Ресурсы ШАБЛОНА (изображения, стили) адресуются ОТНОСИТЕЛЬНЫМ путём ровно так,
  как они лежат в пакете шаблона (`images/logo.png`), — и в содержимом страницы, и в САМИХ
  МАКЕТАХ шаблона. Базовый путь подставляет ядро при отрисовке: внутри SCORM-пакета — каталог
  `template/` (для запасных макетов — `template-default/`), на веб-хосте — маршрут раздачи
  файлов шаблона (FR-37). Подстановка едина для всех путей отрисовки: рантайм пакета,
  экран веб-хоста, набор предпросмотра шаблона и предпросмотр реестра шаблонов (PRD-3).
  Внешние `http(s)://` в `src`/`href` остаются запрещёнными; медиа автора адресуются
  абсолютным `/uploads/media/…`, поэтому относительный путь однозначно означает ресурс шаблона.
- **FR-37.** Веб-хост отдаёт файлы шаблона по маршруту, доступному и для ВСТРОЕННЫХ шаблонов:
  сегодня статикой раздаются только `/uploads` и `/docs`, поэтому ссылка на ресурс встроенного
  шаблона указывать некуда.

## 4. UX и экраны

Все изменения происходят ВНУТРИ формы страницы, которая раскрывается в существующем списке
структуры. Сам список, зоны и порядок не меняются (FR-20).

Раскладка формы НЕ переизобретается: это тот же список полей в раскрытой строке, который
реализован сегодня. Новых заголовков, колонок и разделителей не вводится.

- Поля идут одним списком в порядке объявления: сначала `placeholders[]`, затем `settings[]`.
  Вариант без настроек даёт форму, неотличимую от сегодняшней.
- Поле «Идентификатор последовательности» — выбор из значений, уже использованных в тесте,
  плюс создание нового. Подсказка под полем сообщает размер отрезка, в том числе состояние
  «в последовательности одна страница» (точки не строятся, FR-19).
- Поле типа `image` показывает миниатюру предпросмотра загруженного изображения (сегодня
  показывается только имя файла).
- Текстовое поле содержимого получает переключатель режимов (простой текст / форматированный
  текст / HTML) в пределах потолка, заданного типом поля, и панель форматирования в режиме
  форматированного текста (FR-32, FR-33). Это ЕДИНСТВЕННОЕ, кроме предпросмотра изображения,
  изменение вида формы; состав и порядок полей остаются прежними.
- Карточка шаблона в реестре показывает состояние валидности; невалидный шаблон нельзя
  активировать.

Состояния формы (поля варианта, выбор идентификатора, незаполненная обязательная настройка,
поле неизвестного типа) зафиксированы в утверждённом эскизе
[prd22-page-fields-sequences.html](../../wireframes/approved/prd22-page-fields-sequences.html);
он же содержит DS Mapping и таблицу поведения, не выразимого статикой.

## 5. Контракт манифеста

Вариант контентной страницы объявляет содержимое и свойства раздельно:

```json
{
  "key": "gallery.card",
  "label": "Галерея: карточка",
  "kind": "info",
  "pageKind": "content.info",
  "layoutFile": "layouts/gallery.html",
  "placeholders": [
    { "key": "header", "type": "text", "label": "Заголовок" },
    { "key": "cardText", "type": "richText", "label": "Текст карточки" },
    { "key": "image", "type": "image", "label": "Изображение" }
  ],
  "settings": [
    { "key": "sequenceId", "type": "sequence", "label": "Последовательность страниц" },
    { "key": "nextLabel", "type": "text", "label": "Подпись кнопки", "default": "Далее" },
    { "key": "backgroundImage", "type": "image", "label": "Фон страницы" }
  ]
}
```

Почему отдельный раздел, а не признак у плейсхолдера. Плейсхолдер участвует в построении
скелета страницы: ядро создаёт по региону `data-placeholder` на каждый объявленный плейсхолдер,
поэтому поле-настройка на общем контентном макете отрисовалось бы как видимый текст. Выразить
настройку плейсхолдером можно было бы, добавив признак «не выводить в скелет», и это дешевле —
хранение осталось бы в `values`, без новой колонки и без правок экспорта, санитизации и
снапшотов. Решение принято в пользу отдельного раздела осознанно: контракт разделён по природе
(содержимое против поведения), а цена — перечисленные правки — учтена в FR-28, FR-30, FR-31 и в
таблице рисков.

Правила контракта:

- поле `settings[]` необязательно; его отсутствие означает, что у страниц этого варианта нет
  настраиваемых свойств;
- добавление раздела обратно совместимо, повышение версии контракта шаблонов не требуется;
- перечень допустимых типов и их атрибутов фиксирован (FR-05, FR-06, FR-11);
- макет варианта отвечает за наличие индикатора навигации и кнопки возврата; данные для них
  ядро передаёт всегда (FR-22).

## 6. Модель данных

| Объект | Изменение |
| --- | --- |
| `content_pages.settings_json` | Новая колонка jsonb, по умолчанию пустой объект (FR-28) |
| `content_pages.kind` | Значение `gallery` не вводится; перечень остаётся прежним (FR-01) |
| Значения страницы | Ключи `pillsTotal`, `pillCurrent`, `showBack` удаляются (FR-25) |

Миграция данных не требуется: страниц с видом «галерея» в базе быть не может — платформа не
позволяла их создать.

Обновление шаблона `certification` (Э4 меняет его манифест) выполняется в двух шагах:
версия в репозитории приезжает вместе с кодом, а загруженная копия и запись реестра
обновляются ВРУЧНУЮ — администратор загружает новый ZIP через раздел «Шаблоны» после деплоя.
Автоматического переимпорта при выкате не вводится. До ручного обновления активный шаблон
помечен невалидным и продолжает работать (FR-13); пункт «загрузить новую версию шаблона
`certification`» входит в примечания к релизу.

## 7. Граница и зависимости

В объём НЕ входит:

- изменение вкладки «Структура» как таковой: список страниц, зоны, порядок, перетаскивание,
  групповые операции остаются в утверждённом и реализованном виде (FR-20);
- доработка отладочного плеера (PRD-18): последовательность проверяется обычным рендером
  страницы и визуальной оценкой, отдельного представления участка и отрезка в инспекторе не
  вводится;
- режим «Произвольный HTML» и его перевод на объявление вариантом;
- параметры оформления шаблона (`params[]`) и их перечень типов;
- контейнерная группировка страниц как объект структуры (обсуждалась и отклонена в пользу
  идентификатора последовательности; при появлении потребности вводится поверх этой модели).

Зависимости и затрагиваемые области: реестр шаблонов и его валидация (PRD-3), общий рендер и
паритет хостов (PRD-12), сборщик потока страниц и участков (PRD-4/8/19), снапшоты публикации
(PRD-15), отладочный плеер (PRD-18).

| Этап | Содержание | Статус |
| --- | --- | --- |

| Э1 | Эскиз формы страницы: поля варианта одним списком, поле идентификатора, предпросмотр изображения, диагностика полей, режимы ввода с панелью форматирования и ошибка в режиме HTML | Выполнен, утверждён |
| Э2 | Контракт: перечень типов, `settings[]`, валидация при загрузке и активации, колонка `settings_json` | Выполнен |
| Э3 | Ядро: нарезка участков, вычисление отрезков и блока `page.*`, единый код для обоих хостов | Выполнен |
| Э4 | Рендер: удаление отдельной ветки галереи в рантайме и предпросмотре, перевод макета на плейсхолдеры и `page.*`, обновление шаблона `certification` в репозитории (загруженная копия — вручную после деплоя) | Выполнен; приёмка на локальном плеере пройдена |
| Э5 | Редактор: контролы по перечню типов, поле идентификатора последовательности, предпросмотр изображения, переключатель режимов ввода с панелью форматирования и нормализацией вставки | Выполнен; проверка в живом редакторе — после применения миграции к dev-базе |
| Э7 | Ресурсы шаблона: подстановка базового пути в содержимом И в макетах на обоих хостах (рантайм пакета, экран веб-хоста, наборы предпросмотра), маршрут раздачи файлов шаблона на вебе (FR-36, FR-37) | Выполнен; приёмка на dev и на локальном плеере пройдена |

Исходный дефект закрывается на Э4 как следствие: вариант «Галерея: карточка» становится
обычной информационной страницей и попадает в каталог добавления.

## 9. Риски

| Риск | Проявление | Мера |
| --- | --- | --- |
| Настройки не попадут в пакет | Сборка страницы в данные пакета идёт по явному списку полей; фон не будет упакован сборщиком медиа, ссылка сломается в LMS | FR-30, приёмка на локальном плеере |
| Санитизация настроек не определена | Подпись кнопки попадает в разметку непроверенной строкой | FR-30, правило санитизации по типу настройки |
| Регресс возврата в режиме маршрутизатора | Кнопка возврата исчезнет на первой странице раздела, откуда сегодня можно вернуться к маршрутизатору | FR-24 |
| Окно рассинхрона при выкате | Код с жёсткой валидацией приезжает раньше обновлённой загруженной копии шаблона; активный шаблон помечается невалидным | Принято осознанно: копия обновляется вручную через раздел «Шаблоны» сразу после деплоя. Шаблон в это время работает (FR-13); шаг входит в примечания к релизу |
| Прирост непокрытого кода | Перечень типов, валидация, вычисление отрезков, новые контролы при пороге покрытия 80% | Тесты закладываются в каждый этап |
| Редактор форматированного текста | В дизайн-системе нет ни редактируемой области, ни панели форматирования: компонент, нормализация вставки и переключение режимов пишутся с нуля — самый ёмкий пункт Э5 | Эскиз (состояние `s-rich`) закрыт до кода; компонент добавляется В UI-KIT (`RichTextEditor`), локальный шим в продукте не заводится |
| Ссылки на ресурсы шаблона рвутся между хостами | Один и тот же относительный путь ведёт в разные места: `template/` в пакете и каталог шаблона на вебе; у встроенных шаблонов файлы вообще не раздаются | FR-36, FR-37; приёмка обоих хостов на одной странице с картинкой из шаблона |
| Нечем диагностировать | При расхождении точек участок и отрезок не видны в инспекторе | Специальное представление НЕ вводится: последовательность проверяется обычным рендером страницы в отладочном плеере, визуально |

## 10. Открытые вопросы

Открытых вопросов нет: решения приняты по всем пунктам разбора, включая организационные.

Закрыто при финализации:

- доработка отладчика не требуется — последовательность проверяется обычным рендером страницы
  и визуальной оценкой (раздел 7, таблица рисков);
- загруженная копия шаблона `certification` обновляется вручную через раздел «Шаблоны» после
  деплоя; автоматический переимпорт не вводится (раздел 6, таблица рисков).
