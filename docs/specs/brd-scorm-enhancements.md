## 1. Контекст и постановка задачи

Test Builder генерирует SCORM 2004 4th Edition пакеты с ограниченной визуальной
вариативностью, без полноценных контентных страниц между блоками и с базовой моделью
расчёта результата. Референсный проект Articulate Storyline показывает, что для
корпоративных сертификаций нужны:

- управляемые шаблоны плеера и страниц;
- контентные и системные страницы внутри общего потока прохождения;
- управляемый поток прохождения: переходы между разделами, блокировки, таймеры;
- пользовательские показатели результата и передача этих данных в LMS;
- многомерные измерения компетенций, где один вопрос может влиять на одну или несколько шкал.

**Цель:** расширить SCORM-генератор до уровня, достаточного для корпоративных курсов и
сертификаций, сохранив контролируемую архитектуру Core и единую механику внутренних и
внешних шаблонов.

## 2. Ключевые архитектурные решения

### 2.1 Единая шаблонная платформа

Встроенные и внешние шаблоны используют один контракт:

- `manifest.json`;
- `shell.html`;
- макеты страниц;
- частичные шаблоны;
- локальные CSS/JS/ресурсы внутри SCORM ZIP;
- браузерный рендерер шаблонов;
- Runtime API для `template.js`.

Отдельные механики для встроенных и внешних шаблонов не создаются. Различаться может только
источник файлов: адаптер встроенного источника или адаптер загруженного источника.

### 2.2 Исполнение только в браузере

Шаблон исполняется только в браузере обучающегося внутри SCORM-пакета.

Сервер не выполняет HTML/JS шаблона и не рендерит EJS. Сервер:

- валидирует шаблон;
- хранит метаданные;
- копирует выбранный шаблон в SCORM ZIP;
- добавляет Core runtime и данные теста.

### 2.3 Разделение ответственности Core и шаблона

**Core владеет:**

- состоянием теста;
- навигацией;
- ответами;
- оценкой;
- состоянием обратной связи;
- восстановлением сессии;
- стандартными интерактивами вопросов;
- SCORM API;
- telemetry;
- финальными защитами для критичных действий.

**Шаблон владеет:**

- макетом оболочки;
- макетами разных типов страниц;
- визуальным языком;
- локальными ресурсами;
- дополнительным поведением через `template.js`;
- декларативными правилами шаблона для технического/визуального поведения.

### 2.4 Макет шире, чем цвета и шрифты

Шаблон описывает не только параметры оформления, но и макет:

- оболочку курса (`shell.html`);
- макет вопросов;
- макет контентных страниц;
- макет результатов;
- опциональный макет стартовой страницы;
- опциональные системные страницы;
- частичные шаблоны для навигации, прогресса, header/footer.

Стандартные интерактивы вопросов в MVP остаются за Core и вставляются в контролируемый слот
`data-slot="question-interaction"`.

### 2.5 Гибкий движок прохождения

Core должен поддерживать несколько политик прохождения без развилки на отдельные runtime:

- `legacy_flat`: текущее поведение, при котором вопросы выбираются из разделов и перемешиваются в
  общий плоский список;
- `section_linear`: разделы проходятся последовательно, с явными стартовыми страницами, вопросами и
  страницами результата раздела;
- `section_router`: обучающийся возвращается на страницу-маршрутизатор после каждого раздела,
  видит пройденные разделы и результаты по ним, а итоговый результат открывается после выполнения
  политики завершения;
- `section_graph`: графовые переходы между разделами — _вне охвата_ (зависели от снятого движка правил, см. BR-03);
- `adaptive_by_section`: адаптивная выдача вопросов внутри разделов с переходами между разделами.

Раздел (`section`/`topic`) является не только контейнером вопросов, но и сценарным узлом:

```text
section start -> section questions -> section result -> transition -> next section/results
```

Старые тесты без явной `flowPolicy` должны продолжать экспортироваться и проходиться как
`legacy_flat`.

### 2.6 UI только после согласованных wireframes

Любая функциональность, которая добавляет или меняет авторский, административный или learner-facing
UI, не передаётся в frontend-разработку без предварительно подготовленных и явно согласованных
wireframes.

Wireframes должны покрывать:

- основной пользовательский сценарий;
- пустые состояния;
- loading/saving состояния;
- ошибки API и валидации;
- read-only/disabled состояния, если применимо;
- ключевые edge cases, влияющие на поведение пользователя.

Если во время разработки меняется сценарий, состав полей, порядок действий или состояние экрана,
изменение возвращается на повторное согласование wireframes до продолжения UI-реализации.

## 3. Анализ референса Storyline

Референс содержит не только визуальную оболочку, но и runtime-логику:

- переменные доступа и результатов (`Test_Blocked`, `Blocks_Done`, `Result_*`);
- условия и переходы;
- выдачу вопросов и расчёт статуса по отдельным разделам;
- страницу-маршрутизатор, с которой обучающийся выбирает раздел, возвращается после прохождения и
  видит статус/результат разделов;
- стартовые страницы разделов и страницы результатов разделов;
- таймеры;
- SCORM commit/reset;
- блокировки;
- предупреждения о нескольких вкладках;
- слайды результатов и сертификации.

Вывод: простого HTML/CSS-шаблона недостаточно. Требуется гибрид:

- декларативный сценарий прохождения (поток, разделы, политики завершения) вместо no-code движка правил;
- возможность расширения кодом через `template.js` и Runtime API;
- явная модель потока прохождения с разделами, промежуточными результатами и политиками переходов;
- будущая фаза расширенных шаблонных интерактивов для переопределения механики вопросов.

## 4. Бизнес-требования

### BR-01: Шаблонная платформа SCORM

**Проблема:** внешний вид, навигация и структура страниц жёстко связаны с текущим Core.
Невозможно создавать разные корпоративные плееры без разработки.

**Требования:**

| ID | Требование |
| --- | --- |
| BR-01-01 | Система поддерживает единую механику встроенных и внешних шаблонов согласно [specs/spec-template-platform.md](./spec-template-platform.md) |
| BR-01-02 | Шаблон исполняется только в браузере обучающегося внутри SCORM-пакета |
| BR-01-03 | Шаблон содержит `manifest.json`, `shell.html`, макеты, опциональные частичные шаблоны, ресурсы и скрипты |
| BR-01-04 | Сервер не выполняет код шаблона при экспорте |
| BR-01-05 | Автор выбирает шаблон и параметры через UI без ручного JSON |
| BR-01-06 | Параметры шаблона поддерживают dot-keys, группы, значения по умолчанию, валидацию и CSS-переменные |
| BR-01-07 | Core предоставляет прогресс по вопросам и страницам; шаблон выбирает активный прогресс через `progress.mode` |
| BR-01-08 | Тестовая `navigationPolicy` имеет приоритет над возможностями шаблона |
| BR-01-09 | Тесты без настроек используют `default` и сохраняют обратную совместимость |

### BR-02: Контентные и системные страницы

**Проблема:** текущий поток содержит только вопросы и не позволяет вставлять учебный материал
или служебные экраны.

**Требования:**

| ID | Требование |
| --- | --- |
| BR-02-01 | Автор может добавлять контентные страницы до/после темы |
| BR-02-02 | Поддерживаются авторские типы страниц (`info`, `html`) и системные узлы границ раздела — введение, обзор, итоги раздела (уточнено PRD-19: прежние `intro`/`summary` заменены системными узлами) |
| BR-02-03 | Контентные страницы входят в общий поток страниц, но не влияют на оценку вопросов |
| BR-02-04 | HTML-контент проходит серверную санитизацию и вставляется только через контролируемые слоты |
| BR-02-05 | Медиа контентных страниц упаковываются в SCORM ZIP как локальные ресурсы |
| BR-02-06 | Системные страницы шаблона объявляются в `manifest.systemPages[]` и не считаются учебными страницами |
| BR-02-07 | Автопереход реализуется через Core/Runtime API, а не через произвольный серверный рендер |

### BR-03: Логика теста задаётся сценарием (движок правил снят)

**Снято 2026-07-05.** Универсальный движок правил курса (no-code «событие → условие →
действие», таблица `course_rules`, конвейер `beforeRules`/`afterRules`, изменяемые переменные
времени прохождения) выведен из охвата: продукт — конструктор тестов, а не курсов. Логика
прохождения теста задаётся декларативным **сценарием** (`flowPolicy`: `flowMode`,
`completionPolicy`, `sectionUnlockRules`, `passDecisionPolicy` — BR-06 / PRD-4 / PRD-8 / PRD-19);
результат — шкалами (BR-06-11 / PRD-5) и показателями (BR-04 / PRD-2); адаптивное ветвление —
уровнями (adaptive). Из прежних требований BR-03 сохраняются только два, как часть контракта
Runtime API:

| ID | Требование |
| --- | --- |
| BR-03-07 | `template.js` получает Runtime API для расширенной логики, но не поддерживает прямой доступ к внутренностям Core |
| BR-03-08 | Поддерживаемые SCORM-операции шаблона выполняются через `TestBuilder.scorm` |

### BR-04: Пользовательские показатели результата

**Проблема:** LMS получает только стандартный балл, а корпоративные сценарии требуют
компетентностных флагов, индексов, допусков и категорий.

**Требования:**

| ID | Требование |
| --- | --- |
| BR-04-01 | Автор задаёт пользовательские показатели результата через визуальный конструктор и расширенный DSL |
| BR-04-02 | Пользовательские показатели вычисляются после стандартной оценки |
| BR-04-03 | Значения публикуются в пространстве имён `result.*` после события `result:calculated` |
| BR-04-04 | Значения могут отображаться обучающемуся на макете результатов |
| BR-04-05 | Значения передаются в LMS через `suspend_data` и/или псевдо-`interactions` |
| BR-04-06 | Ошибка формулы не прерывает завершение теста и сохраняется в диагностике |

### BR-05: Внешние шаблоны

**Проблема:** корпоративные заказчики и подрядчики должны создавать новые шаблоны без изменения
кода системы.

**Требования:**

| ID | Требование |
| --- | --- |
| BR-05-01 | Администратор загружает внешний шаблон ZIP |
| BR-05-02 | Система выполняет структурную валидацию и браузерную smoke-проверку |
| BR-05-03 | Внешние URL в шаблоне запрещены; все ресурсы локальны внутри ZIP |
| BR-05-04 | Встроенные и внешние шаблоны экспортируются и валидируются по одному контракту |
| BR-05-05 | В UI доступны статический предпросмотр и живой предпросмотр на демонстрационном курсе |
| BR-05-06 | В SCORM ZIP попадает только выбранный шаблон |
| BR-05-07 | При runtime-ошибке шаблона Core показывает встроенный экран ошибки |

### BR-06: Гибкий поток прохождения и многомерные измерения

**Проблема:** текущая логика теста использует разделы как источник выборки вопросов и как единицу
финального расчёта, но не как явные сценарные блоки прохождения. Референс требует стартовых страниц
разделов, переходов между разделами, промежуточных результатов и сценариев ветвления. Дополнительно
корпоративные оценки требуют, чтобы один вопрос мог измерять одну или несколько компетенций
одновременно, независимо от обычной правильности ответа.

**Требования:**

| ID | Требование |
| --- | --- |
| BR-06-01 | Core поддерживает `flowPolicy`, определяющую режим прохождения: `legacy_flat`, `section_linear`, `section_router`, `adaptive_by_section` |
| BR-06-02 | Отсутствие `flowPolicy` означает `legacy_flat` и сохраняет текущее поведение существующих тестов |
| BR-06-03 | В `legacy_flat` вопросы выбираются по разделам, затем могут перемешиваться в общий плоский список, как в текущем SCORM runtime |
| BR-06-04 | В секционных режимах Core строит поток раздела: стартовые страницы раздела, вопросы раздела, страницы результата раздела, переход к следующему узлу |
| BR-06-05 | Раздел имеет явное состояние: `notStarted`, `inProgress`, `completed`, `passed`, `failed`, `locked` |
| BR-06-06 | Core рассчитывает результат раздела сразу после завершения вопросов раздела и публикует его до показа `content.summary` |
| BR-06-07 | Правила курса могут реагировать на события `section:started`, `section:completed`, `section:resultCalculated` |

### BR-07: Ограничение повторного прохождения и период охлаждения

**Проблема:** для части корпоративных курсов требуется запретить повторное прохождение ранее
чем через заданное количество календарных дней после последней полноценной попытки. WebTutor
возвращает дату попытки без времени, поэтому ограничение рассчитывается по датам, без часов.

### BR-09: Градуированная оценка ответа («Цена ответа»)

**Проблема:** для `multiple`/`matching`/`ranking` стандартный балл вычисляется по принципу «всё
или ничего» (точное совпадение с эталоном -> `1`, иначе -> `0`), поэтому частично верный ответ
получает `0`. Корпоративные и образовательные сценарии требуют частичного балла («Цена ответа»:
веса опций или ступенчатая таблица «условие → балл»), а runtime уже резервирует поля `scoreRatio` и статус `partial`
под эту возможность ([scoring-model.md](./scoring-model.md) §11). Дизайн и реализация —
[PRD-10](./prd-10/graded-answer-scoring.md) (Этап 10).

**Требования:**

| ID | Требование |
| --- | --- |
| BR-09-01 | Для типов `multiple`/`matching`/`ranking` автор может включить градуированную «Цену ответа» (частичный балл), а не строго `0`/`1` |
| BR-09-02 | Балл `s ∈ [0, sMax]`, `scoreRatio = s / sMax`; «Цена ответа» настраивается по типу: веса опций (`single`) либо СТУПЕНЧАТАЯ таблица «условие → балл» над счётчиками `(c, x, T)` с полом `max(0, ·)` (`multiple`/`matching`/`ranking`) |
| BR-09-03 | Градуированный балл относится к оси КОРРЕКТНОСТИ и не влияет на вклады в шкалы, которые задаются отдельно явными числами (BR-06-10, [scoring-model.md](./scoring-model.md) §10.11) |
| BR-09-04 | Runtime публикует `scoreRatio` и статус `partial` («Частично правильно») в контракте шаблона, в показ обучающемуся и в LMS стандартными CMI-полями SCORM 2004 |
| BR-09-05 | Exact-match остаётся поведением по умолчанию; тесты и вопросы без включённой градуированной оценки сохраняют текущий расчёт без изменений (обратная совместимость) |

### BR-10: Квоты выдачи вопросов по тегам

**Проблема:** выдача вопросов на тему равномерно случайна (`shuffle(вопросы темы).slice(0, drawCount)`),
поэтому нельзя гарантировать требуемый объём вопросов определённой ПОДТЕМЫ (напр. в РТК внутри
раздела «Финансы» — `finance_base`/`finance_metrics`/`finance_invest`). Подтемы выражаются тегами
вопросов (`questions.tags`); нужна опциональная квота выдачи по тегам. Это ДОСТАВКА, ортогональная
скорингу. Дизайн — [PRD-11](./prd-11/tag-draw-quotas.md) (Этап 11).

**Требования:**

| ID | Требование |
| --- | --- |
| BR-10-01 | Автор может задать на теме опциональную квоту выдачи `[{ тег, количество }]`; подтема = значение `questions.tags` (новой сущности/иерархии тем не вводится) |
| BR-10-02 | Квота не задана → текущая равномерная выдача без изменений (обратная совместимость) |
| BR-10-03 | Квота задана → на каждый тег по режиму: `exact` — РОВНО `count`, `min` — НЕ МЕНЕЕ `count` (случайный отбор внутри тега) в пределах общей выборки `drawCount`; остаток — случайный из вопросов без `exact`-тегов; вопрос с несколькими квота-тегами засчитывается один раз |
| BR-10-04 | Если вопросов с тегом меньше квоты — НЕблокирующее предупреждение (в редакторе и в выдаче); выдаётся сколько есть |

### BR-12: Фиксированные варианты выдачи (формы) и ротация на повторе

**Проблема:** существующая выдача на тему — равномерно случайна (BR-10 без квот) или
стратифицирована по тег-квотам (BR-10). В обоих случаях состав формы — случайная комбинация,
не воспроизводимая и не курируемая автором. Корпоративная сертификация (эталон-источник —
РТК «Обновление сертификации для руководителей») требует другой механики: внутри раздела —
несколько ФИКСИРОВАННЫХ, заранее скурированных автором **вариантов** (= наборов вопросов); при
старте теста каждому разделу случайно выпадает один вариант целиком; при повторной попытке
выпадает ДРУГОЙ вариант (ротация), независимо по каждому разделу. Фиксированный состав нужен под
воспроизводимость и пер-вариантную калибровку порогов; ротация — чтобы повтор шёл по другому
набору. Тег-квоты (BR-10) этого не дают: они стохастические и не гарантируют конкретный состав.
Дизайн — [PRD-17](./prd-17/question-set-variants.md) (Этап 13).

**Граница реализуемости (фиксируется по факту проверки WebTutor):** выбор фиксированного варианта
stateless и работает на обоих хостах (веб + SCORM-пакет); ротация «другой вариант на повторе»
требует памяти о прошлых попытках. WebTutor не предоставляет cross-attempt-хранилище
(`adl.data` недоступен — см. NFR-17), поэтому ротация реализуется в СЕРВЕРНОМ (веб) хосте, где
история попыток доступна; в автономном SCORM-пакете ротация деградирует до случайного варианта
каждую попытку (возможен повтор). Это известное ограничение хоста, а не дефект.

**Требования:**

| ID | Требование |
| --- | --- |
| BR-12-01 | Автор может задать на разделе (`test_sections`) опциональный набор из ≥2 вариантов; каждый вариант — именованный набор вопросов (подмножество банка темы), курируемый автором |
| BR-12-02 | «Варианты теста» — отдельный РЕЖИМ выдачи темы. Не задан → текущая выдача без изменений (равномерная или тег-квоты BR-10, из всего банка); обратная совместимость. Задан → контролы выдачи из всей темы (объём выборки, «все вопросы», тег-квоты) не применяются — источником становится выпавший вариант |
| BR-12-03 | Вариант задан → при старте прохождения темы ей случайно выпадает один вариант; его вопросы выдаются ЦЕЛИКОМ (весь набор), в случайном порядке. Темы выбирают варианты независимо; вариант привязан к ТЕМЕ, а не к тесту в целом |

### BR-20: Материалы обратной связи (внешняя ссылка)

**Проблема (историческая):** автор прикладывал файл (например, PDF) к обратной связи — темы,
уровня шкалы, исхода показателя, — редактор показывал вложение и позволял сохранить, но загрузка
файла на сервер не была реализована с самого начала: при сохранении файл выбрасывался, в модель
уходил только дескриптор. Вскрыто реализацией BR-17 — первой работой, которая попыталась
показать вложения обучающемуся.

**Первый проход (PRD-32, реализовано и принято 2026-08-02):** вложение стало обычным активом
медиатеки — загрузка PDF (до 5 МБ) с сервера, канонический адрес `url = /api/media/<id>`, индекс
использования и права ученика для пяти мест хранения обратной связи (тест, раздел, тема, шкала,
показатель), показ в блоке «Материалы» на обоих хостах. Заодно закрыт независимый дефект
медиатеки: до этого решения медиа, загруженное ПОСЛЕ появления медиатеки, в SCORM ZIP не
попадало вовсе.

**Пересмотр (PRD-42, реализовано и влито 2026-08-05):** приёмка вскрыла, что относительный адрес
`/api/media/<id>` не резолвится вне живой страницы — ни в отдельном PDF-файле (у него нет
браузерного origin), ни из SCORM-пакета (упаковщик переписывает адрес на путь ВНУТРИ ZIP, не
существующий вне пакета). Вместо резолвинга адреса на лету решение изменило саму модель: загрузка
файла УБРАНА, вложение обратной связи — ЧИСТО ВНЕШНЯЯ ссылка {название, url}, по образцу уже
существующих секций «Курсы» и «Мероприятия» того же редактора. Материал больше не хранится
системой и не попадает в SCORM ZIP как локальный ресурс: автор указывает готовый `http(s)`-адрес,
и этот же адрес используется на обоих хостах и в PDF-отчёте без перекладки. Трек закрыт этим
решением. Дизайн — [PRD-32](./prd-32/feedback-assets-delivery.md),
[PRD-42](./prd-42/feedback-assets-links-only.md) (Этап 25).

**Требования (по факту принятых решений):**

| ID | Требование |
| --- | --- |
| BR-20-01 | Вложение обратной связи — внешняя ссылка {название, url}, а не файл, физически хранимый системой; загрузка файла для этого назначения не предусмотрена |
| BR-20-02 | Требование «вложение — локальный ресурс внутри SCORM ZIP» (NFR-03, BR-05-03) на материалы обратной связи НЕ распространяется — осознанное исключение, симметричное уже существующим внешним ссылкам «Курсы»/«Мероприятия»: материал не является ресурсом ШАБЛОНА |
| BR-20-03 | Право перейти по ссылке не отличается от права видеть саму обратную связь; отдельного контроля доступа к файлу не вводится, поскольку файла как отдельной сущности больше нет |
| BR-20-04 | Ссылка — часть текста обратной связи и переносится в снимок публикации вместе с остальным содержимым теста/темы/шкалы/показателя, без отдельной обработки |
| BR-20-05 | Дескрипторы, сохранённые по первому решению (PRD-32, `url: /api/media/<id>`), не мигрируются и не блокируются валидацией: строка остаётся редактируемой, но ссылка в PDF-отчёте у неё остаётся БИТОЙ, пока автор не заменит адрес вручную на настоящий `http(s)`-URL — принятый технический долг, не дефект |
| BR-20-06 | Обходная дорога прежней редакции («материалы кладутся ссылкой до закрытия трека») стала ПОСТОЯННЫМ решением, а не временной мерой: дальнейшего перехода на файловое хранение не запланировано |

**Повод:** сверка продуктового позиционирования («клиент загружает любой сложный психологический

**Существо требования:** по каждой позиции перечня ниже принять и зафиксировать решение —

### BR-22: Единый вход по корпоративной учётной записи (SSO)

**Приоритет: внеочередной.** Основание — [конкурентный анализ](../reports/ANALYSIS_COMPETITORS.md)
2026-08-01: отсутствие единого входа относится к ОТСЕКАЮЩИМ критериям корпоративной закупки. Такой
критерий снимает продукт с рассмотрения независимо от его прочих достоинств, то есть блокирует
ценность всех остальных треков разом. Направление — [«Пройти отсечки закупки»](../reports/ANALYSIS_COMPETITIVE_DIRECTIONS.md).

**Проблема:** войти в систему сегодня можно только паролем либо по одноразовой ссылке-приглашению.
Корпоративный заказчик требует вход по учётной записи своего каталога как условие приобретения, а не
как удобство: пароль в стороннем сервисе означает второй контур учётных данных, который служба
безопасности обязана согласовать отдельно. У прямого конкурента SSO заявлен.

**Требования:**

| ID | Требование |
| --- | --- |
| BR-22-01 | Поддерживается вход через внешнего поставщика идентификации по стандартному протоколу; конкретный протокол и их число определяет PRD |
| BR-22-02 | SSO — ДОПОЛНИТЕЛЬНЫЙ способ входа, а не замена существующих: вход паролем и доступ по ссылке-приглашению сохраняются. Внешний участник (BR-21 / PRD-28) во внешнем каталоге не заводится и продолжает приходить по ссылке |
| BR-22-03 | Сопоставление внешней учётной записи с локальной однозначно и не опирается на отображаемое имя. Адрес почты хранится зашифрованным, а ищется по хешу — механизм сопоставления обязан работать в этой модели, а не в обход неё |
| BR-22-04 | Роли и объектные области доступа остаются за моделью BR-13: поставщик идентификации подтверждает ЛИЧНОСТЬ, а не права. Перенос групп или ролей из внешнего каталога — опция, решение о ней принимает PRD |
| BR-22-05 | Автоматическое создание учётной записи при первом входе по умолчанию ЗАПРЕЩЕНО: иначе каталог заказчика порождает учётные записи без владельца и без назначений. Разрешение — явное решение PRD с указанием, кто становится владельцем |
| BR-22-06 | При входе и при погашении ссылки-приглашения идентификатор сессии пересоздаётся. Требование закрывает известный технический долг: сегодня ни один из двух путей входа этого не делает, и пробел системный — чинить обе точки надо одновременно |
| BR-22-07 | Вне охвата: собственный поставщик идентификации, федерация между заказчиками, SCORM-пакет (внутри пакета вход — дело LMS, а не наше) |

### BR-23: Согласие на обработку персональных данных и срок хранения

**Приоритет: внеочередной.** Основание — тот же конкурентный анализ: формальное соответствие
относится к отсекающим критериям. Дополнительно требование снимает известный технический долг и
разблокирует BR-21 / PRD-28.

**Проблема:** экрана согласия не существует. Страница первого входа отправляет признак согласия
жёстко зашитым значением, а подготовленные строки интерфейса не используются нигде. Срок хранения
персональных данных не определён. У штатного сотрудника основание обработки — трудовые отношения,
и пробел для него не критичен; у внешнего участника единственное основание — согласие, которого
фактически никто не даёт. Хуже того, внешний участник **никогда не увидит экран первого входа**,
потому что в систему не входит: он приходит по ссылке. Его имя и адрес почты при этом остаются
в базе бессрочно.

**Требования:**

| ID | Требование |
| --- | --- |
| BR-23-01 | Согласие фиксируется ЯВНЫМ действием субъекта. Зашитое в код значение признака недопустимо ни при каких условиях |
| BR-23-02 | Момент запроса согласия обязан покрывать участника, который в систему НЕ входит: согласие берётся на границе начала прохождения, а не только на первом входе |
| BR-23-03 | Хранится факт согласия, его дата и ВЕРСИЯ текста, на который человек согласился. Без версии невозможно доказать содержание согласия задним числом |
| BR-23-04 | Срок хранения персональных данных определяется явно, вместе с действием по его истечении: удаление, обезличивание с сохранением результата или бессрочное хранение. Молчаливое «бессрочно» решением не считается |
| BR-23-05 | Отказ от согласия — определённый сценарий с понятным исходом, а не тупик и не молчаливый пропуск |
| BR-23-06 | Согласие встраивается в существующий экран старта прохождения; отдельного шага у обучающегося не появляется |
| BR-23-07 | Право субъекта на отзыв согласия и на удаление своих данных определяется явно: что происходит с уже сданными попытками и с результатами, на которые опирается аналитика |

| BR-24-01 | Профиль по нескольким шкалам показывается ОДНОЙ диаграммой — на экране итогов завершённой попытки и в отчёте о результатах (BR-16) |
| BR-24-02 | Луч диаграммы соответствует шкале; расстояние от центра — доля значения от объявленного диапазона шкалы БЕЗ переворота по благоприятному направлению. Оценка уровня несётся цветом и текстовой меткой, а не длиной луча |
| BR-24-03 | Трёхпозиционная видимость BR-17 соблюдается: скрытая шкала на диаграмму не попадает; при показе уровня без значения луч огрубляется до интервала, чтобы графика не раскрывала скрытый балл |
| BR-24-04 | Диаграмма ДОПОЛНЯЕТ карточки шкал, а не заменяет их: толкование и рекомендации остаются текстом |
| BR-24-05 | Показ включается ЯВНЫМ решением автора, независимо для экрана итогов и для отчёта; по умолчанию выключен, существующие тесты вида не меняют |
| BR-24-06 | Диаграмма рисуется только при трёх и более видимых шкалах. Для обучающегося отказ молчаливый, автору редактор объясняет причину |
| BR-24-07 | Диапазон шкалы ХРАНИТСЯ и записывается до попытки; вычисление его в момент показа недопустимо — результат обязан оставаться воспроизводимым после правки состава вопросов (NFR-21) |
| BR-24-08 | Диаграмма одинакова на обоих хостах и в отчёте; расхождение считается дефектом. Скрипты и внешние библиотеки не используются: разметка живёт внутри LMS и растеризуется при печати |
| BR-24-09 | Вне охвата первого этапа: темы как источник лучей, групповой профиль и сравнение попыток (BR-21-09, BR-21-10), сквозной профиль по нескольким тестам |

### BR-25: Адаптивное тестирование по модели IRT

**Место в очереди: ПОСЛЕ психометрики.** Требование не может быть начато раньше, чем банк заданий
откалиброван: последовательность — CTT ([BRD психометрической аналитики](./brd-psychometric-analytics.md))
-> IRT -> адаптивная выдача. Это не приоритет и не отсрочка, а **зависимость по данным**: без
оценённых на реальных ответах параметров задания требование нереализуемо в принципе.

**Проблема двойная.**

_Терминологическая._ Существующий адаптивный режим — лестница по уровням сложности: у уровня есть
диапазон сложности, число заданий и порог; зачёт уровня двигает на уровень вверх, провал — на уровень
вниз, исход темы — достигнутый уровень. Сложность задания при этом **назначена автором вручную**
(`questions.difficulty`, 0–100) и ни на чём не откалибрована. В отрасли термин «адаптивное
тестирование» устойчиво занят другим: выбором следующего задания по модели IRT с оценкой способности
и стандартной ошибкой измерения. Расхождение названия и содержания создаёт репутационный риск на
демонстрации методисту заказчика и в закупке, где «адаптивность» может стоять в спецификации.

_Продуктовая._ Настоящей адаптивной выдачи нет ни у одного из шести рассмотренных конкурентов
(см. [конкурентный анализ](../reports/ANALYSIS_COMPETITORS.md) и
[мировой эталон](../reports/ANALYSIS_WORLD_BEST_PRACTICE.md)). Это единственная позиция, где
психометрика конвертируется не в отчёт для методиста, а в возможность продукта.

**Требования:**

| ID | Требование |
| --- | --- |
| BR-25-01 | Существующий уровневый режим СОХРАНЯЕТСЯ как самостоятельный и не заменяется: он решает обучающую задачу (довести обучающегося до уровня, выдав ресурсы уровня), а не измерительную |
| BR-25-02 | Точное описание существующего режима фиксируется в документации и во внешних материалах: маршрутизация по порогам между полосами сложности. Термин «адаптивное тестирование» без пояснения вовне не используется |
| BR-25-03 | Адаптивная выдача по модели IRT вводится ТОЛЬКО на откалиброванном банке; условие старта измеримо (объём наблюдений на задание, проверка соответствия модели) и задаётся PRD, а не берётся на глаз |
| BR-25-04 | Оценка способности выдаётся со СТАНДАРТНОЙ ОШИБКОЙ измерения; критерий остановки — достижение заданной точности либо предел длины теста |
| BR-25-05 | Правило выбора задания учитывает ограничения по содержанию (спецификация теста — квоты BR-10) и контроль экспозиции задания; без этого адаптация ломает и покрытие тем, и безопасность банка |
| BR-25-06 | Результаты испытуемых, получивших РАЗНЫЕ наборы заданий, сопоставимы между собой — это цель введения режима, а не побочный эффект |
| BR-25-07 | Разделение сред: калибровка выполняется на сервере по накопленным наблюдениям; в SCORM-пакет параметры заданий ЗАПЕКАЮТСЯ, а оценка способности считается в рантайме. Обновление калибровки внутри выданного пакета невозможно — пакет живёт с параметрами на момент сборки |
| BR-25-08 | Деградация обязательна: при недостаточной калибровке или невыполнимости режима тест играется фиксированной формой либо существующим уровневым режимом, а не отказом |
| BR-25-09 | Вне охвата: многоступенчатый тест (MST) как отдельный дизайн, эквивалентирование форм, автоматическая сборка формы под спецификацию по параметрам IRT |

### BR-26: Управление экспозицией заданий

**Место в очереди: после накопления данных.** Как и BR-25, требование зависит не от приоритета,
а от наличия наблюдений: пока о выдаче заданий ничего не известно, управлять нечем. Часть требований
(предупреждение об ожидаемой экспозиции, равномерность распределения вариантов) данных НЕ требует и
может быть выполнена раньше остального.

**Проблема.** Экспозиция задания — доля испытуемых, которым оно было выдано, — не измеряется и не
управляется. Чем выше экспозиция, тем вероятнее утечка содержания задания, после которой оно
измеряет уже не подготовку, а доступ к утечке. Сегодня выдача равномерно случайна в рамках квот,
счётчика выдач нет, и банк вырабатывается незаметно для автора: при банке 25 и выдаче 20 экспозиция
каждого задания около 80% с первого же потока.

**Ограничение, определяющее форму решения.** Классический контроль экспозиции (Sympson-Hetter и
родственные вероятностные методы) опирается на ОБЩИЙ счётчик по всей популяции. В автономном
SCORM-пакете такого счётчика нет и быть не может: пакет не знает ничего за пределами текущего
запуска, а телеметрия опциональна и по замыслу отключаема. Поэтому управление экспозицией переносится
на этап СБОРКИ пакета, а рантайм получает уже готовую статическую поправку. Разбор ограничений и
рычагов — в [мировом эталоне §5.1](../reports/ANALYSIS_WORLD_BEST_PRACTICE.md).

**Требования:**

| ID | Требование |
| --- | --- |
| BR-26-01 | Экспозиция измеряется: доля попыток, в которых задание было выдано, вычисляется по накопленным наблюдениям (веб-прохождения, телеметрия SCORM, импорт выгрузок из LMS) и показывается автору |
| BR-26-02 | Источником наблюдений признаётся ИМПОРТ ВЫГРУЗОК ИЗ WEBTUTOR — единственный путь получить данные там, где телеметрия выключена, а прохождение идёт в LMS заказчика. Формат обмена и ключ сопоставления задания ОБЩИЕ с психометрикой ([BRD психометрики](./brd-psychometric-analytics.md), OQ-01/OQ-02): двух разных импортов не заводится, один поток данных питает и психометрику, и экспозицию |
| BR-26-03 | Автор предупреждается об ОЖИДАЕМОЙ экспозиции при настройке выдачи и при сборке пакета. Величина вычислима заранее из размера страты и объёма выдачи и наблюдений НЕ требует — это требование выполнимо немедленно |
| BR-26-04 | Показатель экспозиции задания ЗАПЕКАЕТСЯ в пакет, и рантайм учитывает его при выдаче: внутри страты вероятность выбора зависит от накопленной экспозиции, «горячие» задания выпадают реже. Это не контроль в реальном времени, а перенос накопленного знания в статическую поправку на момент сборки |
| BR-26-05 | Поправка действует ВНУТРИ существующих ограничений выдачи: квоты по тегам (BR-10) и правила отбора не нарушаются. К фиксированным вариантам (BR-12) поправка не применяется — состав варианта задан автором |
| BR-26-06 | Поправка не смещает трудность выдачи: взвешивание выполняется так, чтобы систематически не вымывать лёгкие или трудные задания (ограничение отношения весов либо взвешивание внутри полос сложности). Требование прямо связано с сопоставимостью форм и не может быть опущено «на первое время» |
| BR-26-07 | Экспозиция — СТАТИСТИКА, а не содержание: она не входит в хеш содержания задания и не делает опубликованные снимки устаревшими (прецедент — авторский порядок выдачи, BR-18). Значение берётся на момент СБОРКИ пакета, а не на момент публикации версии |
| BR-26-08 | Распределение фиксированных вариантов между обучающимися делается РАВНОМЕРНЫМ без глобального счётчика — детерминированным выбором по идентификатору обучающегося из LMS. Это отдельная от экспозиции мера: она не снижает долю показов, но устраняет перекос случайного выбора и вырожденную ротацию в пакете (BR-12, NFR-17) |
| BR-26-09 | Деградация обязательна: без данных об экспозиции выдача работает как сегодня (равномерно случайная в рамках квот); при банке, из которого выдаётся почти всё, поправка не применяется |
| BR-26-10 | Вне охвата: вероятностные методы контроля экспозиции реального времени (Sympson-Hetter и родственные) — в автономном пакете невозможны; вывод задания из оборота решением системы; «окно банка» и переиздание пакета как отдельная модель издания |

### BR-27: Импорт и экспорт по IMS QTI

**Место в очереди: данных не требует.** В отличие от BR-25 и BR-26, требование не зависит ни от
психометрики, ни от накопленных наблюдений: работа целиком лежит в нашей зоне контроля и может
выполняться параллельно любому другому этапу.

**Проблема.** Единственный формат обмена содержанием — книга Excel собственного формата (BR-11).
Из этого следует двойное ограничение. На **входе** банк вопросов заказчика к нам можно только
перепечатать или вручную привести к нашей книге, а именно накопленный банк — главное, что удерживает
заказчика в существующем инструменте. На **выходе** содержание вынимается только в наш формат, то
есть продукт выглядит как замок, ровно в том месте, где автономный SCORM-пакет служит обратным
аргументом. Встроенный конструктор WebTutor обменивается тестами по IMS QTI: это ЕДИНСТВЕННАЯ
позиция сравнения, где он объективно сильнее нас
(см. [сравнение с WebTutor и iSpring §2.5](../reports/ANALYSIS_WEBTUTOR_ISPRING.md)). Отраслевой
стандарт обмена САМИМИ заданиями — QTI 3.0; по этой оси у нас ноль форматов обмена при одном формате
доставки, и сверка с эталоном относит позицию к «высокая применимость, делать»
(см. [мировой эталон §3 и §10](../reports/ANALYSIS_WORLD_BEST_PRACTICE.md)).

**Граница, определяющая форму решения.** Стандарт описывает ЗАДАНИЯ и тесты, но не описывает нашу
выдачу и наш расчёт: квоты по тегам (BR-10), фиксированные варианты (BR-12), сценарий прохождения
(BR-06), вклад в шкалы (BR-06-10/12), «Цена ответа» (BR-09) в его терминах не выражаются. Поэтому
обмен по стандарту не может и не должен подменять внутренний обмен: книга Excel остаётся форматом
переноса БЕЗ потерь, QTI отвечает за перенос содержания между СИСТЕМАМИ.

**Требования:**

| ID | Требование |
| --- | --- |
| BR-27-01 | Система импортирует и экспортирует задания по IMS QTI. Импорт первичен по ценности (забрать накопленный банк заказчика без ручного переноса), экспорт обязателен как отсутствие замка: содержание, внесённое в систему, должно выниматься в отраслевом формате, а не только в нашем |
| BR-27-02 | Единица обмена первой очереди — ЗАДАНИЕ и пакет заданий (банк), импортируемый в тему. Обмен ТЕСТОМ как сценарием (разделы, правила прохождения, выдача) в первую очередь не входит: наша выдача и наш расчёт в терминах стандарта не выражаются, и перенос «половины теста» ввёл бы обе стороны в заблуждение сильнее, чем его отсутствие |
| BR-27-03 | Объявляется и документируется ПРОФИЛЬ соответствия: принимаемые и выпускаемые редакции стандарта, перечень взаимодействий, правил обработки ответа и метаданных. Заявление «поддерживаем QTI» шире объявленного профиля не делается ни в материалах, ни в UI |
| BR-27-04 | Выпуск — в QTI 3.0 как актуальной редакции стандарта; приём — в тех редакциях, которые РЕАЛЬНО выпускают контрагенты (в первую очередь WebTutor), а не только в актуальной. Состав принимаемых редакций определяется по файлам-образцам, полученным от систем-источников и заведённым в репозиторий как эталоны приёмки; документация вендора доказательством не считается. **С 2026-08-06 стенд WebTutor доступен — образцы выгрузки можно получить фактически, и это предпочтительный путь определения состава редакций** |
| BR-27-05 | Отображение наших типов вопросов на взаимодействия стандарта фиксируется таблицей в ОБЕ стороны (одиночный и множественный выбор, сопоставление, ранжирование, шкала) и ведётся в спецификации формата обмена — тем же способом, что контракт книги Excel (BR-11-04) |
| BR-27-06 | Взаимодействия и правила обработки ответа вне профиля не импортируются МОЛЧА: задание отклоняется с понятной построчной причиной, остальные задания импортируются, обновление по идентификатору идемпотентно. Правила диагностики и идемпотентности BR-11-05 распространяются на QTI без изменений |
| BR-27-07 | Свойства, у которых в стандарте нет выражения — вклад в шкалы (BR-06-10/12), «Цена ответа» (BR-09), условная обратная связь, теги-подтемы (BR-10), принадлежность вариантам выдачи (BR-12) — при экспорте либо переносятся штатным механизмом расширений и метаданных стандарта, либо ЯВНО объявляются теряемыми. Автор видит перечень того, что не уйдёт в файл, ДО выгрузки; молчаливая потеря недопустима |
| BR-27-08 | QTI НЕ заменяет книгу Excel: обмен без потерь внутри системы и между нашими инсталляциями остаётся за форматом BR-11. Оба контракта ведутся синхронно с кодом; второго источника истины по модели вопроса не заводится |
| BR-27-09 | Пакет обмена несёт медиа задания. Так как импорт медиа выведен из BR-11 в отдельный будущий PRD «Медиатека» (BR-11-06), первая очередь импортирует задания БЕЗ медиа с явной диагностикой пропущенных ресурсов; полноценный приём медиа выполняется вместе с медиатекой и отдельным решением не дублируется |
| BR-27-10 | Содержание задания из внешнего файла — HTML недоверенного происхождения: оно проходит ту же серверную санитизацию и запрет внешних URL, что и контентные страницы (NFR-05, NFR-03). Импортированное задание не получает прав, которых нет у заведённого вручную |
| BR-27-11 | Импортированные задания попадают в общую модель владения и прав: тема-владелец, автор записи, объектные права (PRD-13/PRD-15). Импорт не является обходным путём мимо контроля доступа и мимо контроля целостности содержания (PRD-15) |
| BR-27-12 | Обмен обратим на нашем подмножестве: задание, выпущенное системой и импортированное обратно, даёт то же содержание (round-trip); расхождение на подмножестве считается дефектом — как в BR-11-01 |
| BR-27-13 | Приёмка выполняется на РЕАЛЬНЫХ файлах сторонних систем (приём) и на выпуске, проверенном схемой или валидатором стандарта (выпуск). «Читаем то, что сами написали» доказательством переносимости не является |
| BR-27-14 | Вне охвата первой очереди: собственные переносимые взаимодействия (PCI), доступностные расширения APIP, обмен РЕЗУЛЬТАТАМИ прохождения (QTI Results Reporting — это другая ось, её закрывают xAPI/cmi5), собственные (не шаблонные) правила обработки ответа и адаптивные задания стандарта |

### BR-28: Листинг кода в тексте задания

**Проблема:** автор не может показать участнику фрагмент исходного кода без потери смысла.
Набранный в поле вопроса листинг приезжает участнику как обычный абзац: пропадают ведущие пробелы
(не значимы для инлайн-разметки), пропорциональный шрифт заменяет моноширинный, а типографический
проход подменяет символы (прямые кавычки на «ёлочки», дефис между пробелами на тире). Вопрос «что
выведет этот фрагмент» — базовая механика ИТ-аттестации, недоступная сегодня. Вскрыто конкурентным
анализом (сравнение со StartExam, §4.1): у конкурента вставка кода — штатное средство оформления
задания наравне с изображениями и формулами LaTeX. Формулы LaTeX — соседний пробел из того же
анализа, но отдельная задача, в охват не входит. Дизайн — [PRD-33](./prd-33/code-listing.md)
(Этап 33).

**Статус требований:** зафиксирован только ПОВОД и препятствия в существующей разметке
(`shared/text/`, единой на веб-хост и SCORM-пакет); требования не собирались, форма решения не
согласована, эскизов нет.

**Вопросы, которые проектирование обязано закрыть первыми (не требования):**

| ID | Вопрос | Почему важен |
| --- | --- | --- |
| BR-28-01 | Синтаксис: обратные кавычки как в markdown или собственная запись | Обратные кавычки сегодня ничего не значат и уже могут встречаться в текстах — риск задним числом изменить смысл существующего содержимого |

### BR-29: Защита текста задания от копирования

**Проблема:** участник выделяет текст задания и вариантов ответа и уносит его — в поисковую строку
прямо во время попытки, в переписку, в файл, — и тогда утекает не один вопрос, а банк целиком.
Сегодня этому не противостоит ничто: ученический экран ведёт себя как обычная веб-страница. Вскрыто
конкурентным анализом ([сравнение с рынком](../reports/ANALYSIS_COMPETITORS.md) §4.4,
[матрица StartExam](../reports/ANALYSIS_STARTEXAM_MATRIX.md) §9): у конкурентов защита от
копирования есть, у нас — нет, а единственная общая мера против списывания — уникальная выдача
каждому (BR-10/BR-12). Требования согласованы 2026-08-02, включая переформулировку задачи (см.
ниже); код не начат, экранные элементы водяного знака и заглушки скрытия требуют эскиза. Дизайн —
[PRD-34](./prd-34/copy-protection.md) (Этап 34).

**Граница задачи, принятая явно:** «запретить копирование» технически недостижимо ни в браузере,
ни против держателя SCORM ZIP (в пакете разметка и ключи лежат внутри архива открытым текстом).
Запрет снимка экрана недостижим отдельно: ни у веб-платформы, ни у SCORM-пакета в чужой LMS-рамке
нет средства исключить окно из захвата, а PrintScreen браузеру не виден вовсе. Постановка задачи —
не запрет, а ПОВЫШЕНИЕ ЦЕНЫ бытового копирования штатными средствами экрана и АТРИБУЦИЯ утечки
через снимок экрана, когда сам снимок предотвратить нельзя.

**Требования:**

| ID | Требование |
| --- | --- |
| BR-29-01 | Автор включает защиту тремя НЕЗАВИСИМЫМИ настройками теста: базовая защита периметра (умолчание ВКЛ — распространяется и на уже существующие тесты), водяной знак (умолчание ВЫКЛ), скрытие задания при потере окном фокуса (умолчание ВЫКЛ) |
| BR-29-02 | Периметр защиты перечислен поимённо по слотам макета (текст задания, варианты ответа, обратная связь, медиа задания, подсказка) и экрану обзора целиком; результаты, содержательные страницы, стартовый экран и PDF-отчёт защите не подлежат |
| BR-29-03 | Базовая защита — пять мер без перехвата горячих клавиш: запрет выделения, подавление контекстного меню, перехват `copy`/`cut`, подавление перетаскивания мышью, исключение из печати. На попытку копирования участник видит короткое сообщение; запись о попытке НЕ ведётся — трек не вводит наблюдения за участником |
| BR-29-04 | Водяной знак — читаемая обезличенная строка (идентификатор и время, без ФИО и почты), не перекрывающая содержимое; место объявляет макет, разметку и контраст — ядро. Знак обязателен на экране итогов теста независимо от базовой защиты (там же раскрываются правильные ответы при `showCorrectAnswers`) |
| BR-29-05 | Скрытие при потере фокуса закрывает задание заглушкой при уходе на другую вкладку и возвращает автоматически, без действия участника; ход попытки (таймер, ответы) не затрагивается — мера прячет, а не наказывает |
| BR-29-06 | В отладочном прогоне (BR-13) и в предпросмотре шаблона (BR-05) базовая защита и скрытие при потере фокуса НЕ действуют — автор обязан читать и копировать текст своего вопроса; водяной знак при этом показывается с заглушкой вместо идентификатора |
| BR-29-07 | Мера — ОДНА реализация на оба хоста через общий построитель периметра (PRD-12) и применяется инлайн-свойствами, чтобы не зависеть от каскада CSS шаблона; загруженный внешний шаблон (BR-05), ничего не знающий про защиту, получает её в полном объёме |
| BR-29-08 | На сенсорных экранах мера действует по всему периметру единообразно, включая выделение по долгому нажатию — без послаблений для одиночного выбора |
| BR-29-09 | Настройки проходят полный контур: схема теста, редактор, снимок публикации (BR-06/PRD-15), запекание в SCORM-пакет. Книга Excel (BR-11) настройки уровня теста сегодня не переносит вообще — общий пробел, не специфичный для защиты, и в охват BR-29 не входит |
| BR-29-10 | Формулировка «текст скопировать нельзя» приёмочным критерием не является; принята граница — против держателя ZIP мера не работает, и это осознанная плата, а не дефект |

### BR-30: Компактность состояния прогона в SCORM-пакете

**Проблема:** состояние прогона SCORM-пакета целиком лежит в `cmi.suspend_data`, и туда попадает
не только то, что нужно для продолжения прерванной попытки, но и ПОЛНОЕ содержимое выданных
вопросов — дословно, дважды (в каждой завершённой попытке и в снимке текущего прогона). Тест на
25 вопросов даёт 35-75 тысяч символов на одну завершённую попытку при пределе `cmi.suspend_data` в
SCORM 2004, равном 64000, а предела на рост массива попыток НЕТ. Переполнение проявляется не
ошибкой, а МОЛЧА: LMS обрезает строку, разбор падает, и одновременно обнуляются счётчик попыток,
история, таймер (BR-14) и оба барьера допуска (BR-07/BR-19). Требования согласованы 2026-08-03,
реализация не начата. Дизайн — [PRD-36](./prd-36/run-state-compactness.md) (Этап 35).

**Требования:**

| ID | Требование |
| --- | --- |
| BR-30-01 | Состояние прогона не содержит содержимого вопросов (текстов, вариантов, эталонов, обратной связи, адресов медиа); вопрос адресуется ПОЗИЦИЕЙ в статичном `TEST_DATA` пакета, а не идентификатором |
| BR-30-02 | История завершённых попыток не хранится списком: только счётчик, сводка лучшей попытки и сводка последней (для барьера BR-19); размер состояния не зависит от числа выполненных попыток |
| BR-30-03 | Повопросная детализация (выдача, ответы, статусы) хранится ТОЛЬКО у лучшей попытки — единственного потребителя, которому она нужна (сборка `interactions` для LMS) |
| BR-30-04 | Бюджет состояния — 4096 символов (предел `cmi.suspend_data` в SCORM 1.2, пятнадцатикратный запас на 2004); при приближении к бюджету жертвуется НЕ прогон в работе, а сначала повопросная детализация лучшей попытки, затем сама сводка — с обязательной диагностикой, без молчаливой потери |
| BR-30-05 | Поля механизмов допуска и таймера (BR-07, BR-14, BR-19) сохраняются в прежнем виде и прежней семантике; изменяется только форма истории попыток |
| BR-30-06 | Состояние версионируется; пакет, собранный до BR-30, продолжает работать со своим форматом, а пакет после BR-30 приводит старый формат к новому при первом запуске без потери счётчика попыток, лучшей и последней попытки, якоря таймера и обеих дат барьеров |
| BR-30-07 | Отладочный плеер (BR-13) показывает состояние нового формата, включая занятую долю бюджета |

### BR-31: Профиль экспорта SCORM 1.2

**Проблема:** инструмент выгружает единственный профиль — SCORM 2004 4th Edition. Конкурентный
анализ относит это к пробелам: iSpring и WebTutor принимают и отдают SCORM 1.2 наравне с 2004,
AICC, xAPI и cmi5, а SCORM 1.2 остаётся самым распространённым профилем в корпоративных LMS.
Заказчик с LMS, принимающей только 1.2, получает от нас пакет, который его платформа не запустит.
Трек заведён 2026-08-03 по итогам технического разбора: продуктового решения о запуске НЕТ —
нужен заказчик с такой LMS, а профиль 1.2 ДЕГРАДИРОВАННЫЙ по объективным причинам стандарта, не
по недоработке. Дизайн — [PRD-37](./prd-37/scorm12-export-profile.md) (Этап 36).

**Условие входа:** нереализуемо без BR-30 — предел `cmi.suspend_data` в SCORM 1.2 (4096 символов)
на порядок меньше того, что сегодня туда пишется.

**Требования:**

| ID | Требование |
| --- | --- |
| BR-31-01 | Профиль экспорта выбирается автором при выгрузке пакета; профиль 2004 остаётся умолчанием, пакеты 2004 не меняются после появления профиля 1.2 |
| BR-31-02 | Точка ветвления профиля — ОДНА: адаптер среды выполнения (`API`/`LMS*`-методы вместо `API_1484_11`/`Initialize`) и построитель манифеста (схема 1.2, без элементов упорядочивания `imsss` и без скрытия навигации LMS). Сборка данных экспорта, отрисовка, оценивание, шаблоны и телеметрия НЕ ветвятся |
| BR-31-03 | Перекладка модели данных на словарь 1.2 (баллы, статусы, типы взаимодействий, форматы длительности, поля CMI) выполняется по зафиксированной таблице соответствия и покрывается тестами пословарно; значения вне словаря 1.2 не отправляются |
| BR-31-04 | Автор предупреждается о перечне УТРАЧИВАЕМЫХ при выборе профиля 1.2 возможностей ДО выгрузки: раздельные вердикт/завершение схлопываются в один статус, пороги по темам и по вариантам (BR-12-07/PRD-24) не выражаются манифестом, навигация LMS не скрывается, водяной знак (BR-29) без `learner_id` теряет идентификатор, длинные ответы усекаются до 255 символов |
| BR-31-05 | Отладочный плеер (BR-13) и локальные средства приёмки воспроизводят выбранный профиль, включая заглушку среды выполнения 1.2 — иначе профиль остаётся непроверяемым до реальной LMS |
| BR-31-06 | Заявление о поддержке SCORM 1.2 не выходит за перечень утрат из BR-31-04 ни в материалах, ни в UI — тот же принцип объявленного профиля, что и BR-27-03/NFR-24 для QTI |

| NFR-13 | Отказоустойчивость retake gate | Ошибка plugin не должна ломать загрузку пакета; поведение определяется политикой `failOpen`/`failClosed` и сопровождается понятным сообщением/диагностикой |
| NFR-14 | UI-процесс | UI-разработка начинается только после подготовки и явного согласования wireframes для основных, пустых, loading/saving, ошибочных и read-only состояний |
| NFR-15 | Поддерживаемость редактора | Авторский редактор теста декомпозирован на доменные модули с typed DTO, чистыми мапперами и тестируемыми правилами валидации |
| NFR-16 | UX целостность | Основные и расширенные настройки теста доступны из единого редакторского сценария; карточка теста не должна становиться контейнером для растущего набора независимых кнопок |
| NFR-17 | Граница хоста (cross-attempt) | WebTutor не предоставляет SCORM-пакету cross-attempt-хранилища (`adl.data` недоступен, `cmi.suspend_data` живёт только within-attempt). Механики, требующие памяти между попытками (ротация вариантов BR-12, anti-repeat), реализуются в серверном хосте; в автономном пакете — деградация до stateless-поведения с явной диагностикой |
| NFR-18 | Точность плеера отладки | Встроенный плеер собирает пакет тем же пайплайном, что production-экспорт (общий `generateScormPackage` и общий сборщик `ExportData`, применённый шаблон оформления теста), но ВСЕГДА из живого состояния теста; расхождение с реальной LMS ограничено отсутствием SN-секвенсирования и cross-attempt-стора и явно документируется (BR-13) |
| NFR-19 | Изоляция отладки | Прогоны плеера не порождают записей в `attempts`, `scorm_packages`, `scorm_attempts`, `scorm_answers` и не влияют на аналитику; сборка отладочного пакета не активирует телеметрию (BR-13) |
| NFR-20 | Один источник выбора варианта | Вид отчёта и вид экрана разрешаются ОДНОЙ общей функцией для всех хостов и для предпросмотра: расхождение выданного документа с тем, что видел автор, недопустимо (BR-16) |
| NFR-21 | Неизменность выданного | Артефакты по попытке, выданной из опубликованного снапшота (экраны, отчёт, применённые пороги), собираются данными И вариантом ИЗ ВЫДАЧИ; позднейшие правки автора не меняют их задним числом (BR-16, PRD-15) |
| NFR-22 | Доверенное время | Решения о допуске (период охлаждения, интервал между попытками) принимаются по доверенному источнику времени, а не по системным часам клиента (BR-19) |
| NFR-23 | Одна модель допуска | Барьеры допуска вычисляет общий движок; хост поставляет ему только факты и не содержит собственной копии правила — иначе один переключатель снова начнёт значить на хостах разное (BR-19) |
| NFR-24 | Границы соответствия обмена | Заявляемое соответствие внешнему стандарту ограничено ОБЪЯВЛЕННЫМ профилем: редакции, взаимодействия и правила обработки ответа перечислены; выпуск проверяется схемой или валидатором стандарта, приём — реальными файлами сторонних систем. Формулировки в материалах и в UI за профиль не выходят (BR-27) |

## 7. Приоритизация этапов

**Внеочередной приоритет: Этапы 27 и 28.** Номер этапа фиксирует порядок ЗАВЕДЕНИЯ требования, а не
очередь исполнения. Этапы 27 (единый вход) и 28 (согласие на обработку данных и срок хранения)
выполняются ПЕРЕД остальными незакрытыми этапами независимо от своих номеров. Основание —
[конкурентный анализ](../reports/ANALYSIS_COMPETITORS.md) 2026-08-01: оба относятся к отсекающим
критериям корпоративной закупки, то есть их отсутствие снимает продукт с рассмотрения раньше, чем
дело дойдёт до сравнения по существу, и тем самым обесценивает результат всех остальных этапов.
Развёрнутое обоснование и порядок вложений — в
[направлениях развития](../reports/ANALYSIS_COMPETITIVE_DIRECTIONS.md).

## 9. Риски и митигации

| Риск | Вероятность | Митигация |
| --- | --- | --- |
| Внешний шаблон ломается в браузере | Средняя | Браузерная smoke-проверка, живой предпросмотр, экран ошибки Core |
| Шаблон конфликтует с бизнес-логикой | Средняя | Ограниченный Runtime API шаблона, финальные защиты Core |
| LMS плохо показывает пользовательские данные | Высокая | Дублирование в `suspend_data` и `interactions` |
| HTML-контент вызывает XSS | Высокая | Серверная санитизация и запрет сырой HTML-интерполяции |
| Большие ресурсы раздувают ZIP | Средняя | Лимиты загрузки, запрет внешних URL, предупреждения по размеру |
| Новый flow ломает старые тесты | Высокая | `legacy_flat` как режим по умолчанию, golden-тесты на старые SCORM-пакеты |
| Секционные переходы дают некорректный маршрут | Средняя | Финальные защиты Core (валидация перехода), детерминированный сценарий, диагностика принятого перехода |
| Многомерные шкалы сложно объяснить автору | Средняя | UI матрицы вкладов, предпросмотр расчёта на демо-ответах, предупреждения о непокрытых шкалах |
| Шкалы смешиваются со стандартным баллом | Средняя | Раздельные пространства `score/section/scale/result`, явные настройки публикации в LMS |
| Градуированный балл смешивают с вкладами в шкалы | Средняя | Раздельные оси: корректность (`scoreRatio`) и вклад (`value_json`); exact-match по умолчанию, рубрика включается явно |
| WebTutor endpoint или формат данных меняется | Высокая | LMS-specific eligibility plugin вынесен в явный адаптер с администрируемой конфигурацией, версией и тестовой проверкой |
| Заблокированный запуск ошибочно считается попыткой | Средняя | Gate выполняется до внутренней кнопки старта и до SCORM `Initialize`; полноценная попытка определяется по фильтру статуса/прогресса, а не только по открытию курса |
| Cooldown невозможно строго обеспечить через `suspend_data` | Высокая | `suspend_data` помечается как best-effort источник; строгий режим требует WebTutor/LMS-specific или внешнего источника |
| Редактор теста становится слишком сложным для поддержки | Высокая | Декомпозиция на доменные вкладки/модули, typed DTO, мапперы, централизованная валидация и компонентные тесты |
| Добавление новых PRD ломает существующее редактирование теста | Высокая | Единый контракт `TestEditorModel`, regression suite на standard/adaptive create/edit и explicit migration strategy для новых настроек |
| Импорт/экспорт вопросов теряет данные или ломает round-trip | Высокая | Единая спецификация формата, синхронная с кодом; golden round-trip тесты на каждый тип вопроса; обратная совместимость старого формата |
| Импорт медиа вводится раньше формализации процесса работы с медиа | Средняя | Импорт медиа вынесен из BR-11 в отдельный будущий PRD «Медиатека» (BR-11-06); в контракт файла PRD-14 медиа не входит |
| Встроенный плеер расходится с CLI-плеером (две копии RTE-шима/инспектора) | Средняя | Единый общий модуль шима/инспектора для CLI и сервиса; CLI-скрипт потребляет тот же источник (BR-13-06) |
| Отладочный прогон попадает в учебную аналитику/телеметрию | Средняя | Сборка с выключенной телеметрией; отсутствие записи в `attempts`; состояние только в `localStorage`; явная пометка «прогон отладки» (BR-13-04, NFR-19) |
| Успешный прогон в плеере воспринимается как гарантия работы в WebTutor | Высокая | Документация и UI-пометка границы точности (нет SN/cross-attempt/реального retake-gate); приёмка в WebTutor остаётся обязательной для соответствующих механик (BR-13-08, NFR-18) |
| Сборка пакета на каждый прогон тяжела для больших тестов | Низкая | Лимит NFR-02 (генерация ≤30 с); кэш сессии по токену; пересборка только при смене версии/правках |
