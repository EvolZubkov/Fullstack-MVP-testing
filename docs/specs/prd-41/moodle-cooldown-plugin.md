# PRD-41: Moodle cooldown plugin

**Версия:** 0.1
**Статус:** Предложен; требует исследования — реализация не начата
**Дата актуализации:** 2026-08-04
**Связанные документы:** [PRD-6](../prd-6/retake-cooldown-gate.md) (контракт eligibility-плагина
и рантайм retake gate), [PRD-21](../prd-21/eligibility-plugin-registry.md) (администрируемый
реестр eligibility-плагинов)
**Зависимости:** контракт `EligibilityPlugin` и рантайм retake gate из PRD-6, архитектура
реестра плагинов из PRD-21 — переиспользуются без изменений

## 1. Обзор

### 1.1 Контекст

PRD-6 поставил рантайм retake gate и первый eligibility-plugin `webtutor_cooldown`, который
получает дату последней полноценной попытки из WebTutor и решает, разрешён ли повторный запуск
курса. Для курсов, размещённых в Moodle, такого провайдера нет. PRD-21 явно оставляет добавление
новых провайдеров-плагинов вне своего охвата («по отдельному запросу») — этот запрос и есть
PRD-41.

Ключевое отличие Moodle от WebTutor: `webtutor_cooldown` исполняется в браузере SCO и читает
данные через same-origin cookies текущей WebTutor-сессии. У Moodle нет аналогичного паттерна —
доступ к данным о прохождении обычно идёт через Moodle Web Services (REST API с токеном), что
может потребовать другой модели исполнения плагина.

### 1.2 Цель

Дать тестам, размещённым в Moodle, доступ к тому же cooldown-гейту (PRD-6) через новый
eligibility-plugin `moodle_cooldown`, не изменяя Core и рантайм-гейт.

### 1.3 Что переиспользуется без изменений

- Контракт `EligibilityPlugin` (`key`, `version`, `evaluate(context) -> EligibilityResult`) —
  PRD-6 §3.4.
- Рантайм-последовательность гейта `before_internal_start`, блок-стена, `failOpen`/`failClosed` —
  PRD-6 §4.3, §4.5.
- Паттерн администрируемого реестра плагинов и конфигураций — PRD-21.

Ничего из перечисленного в этом PRD не пересматривается; `moodle_cooldown` — ещё один провайдер
рядом с `webtutor_cooldown`, `suspend_data_cooldown`, `custom`.

## 2. Пользователи

Роли не меняются относительно PRD-6 §2: автор теста выбирает plugin и конфигурацию,
администратор/внедренец настраивает endpoint'ы и токен, обучающийся видит блок-стену при активном
cooldown. Новых ролей PRD-41 не вводит.

## 3. Открытые вопросы (предмет исследования)

Ниже — вопросы, на которые нужно ответить на боевом/тестовом Moodle до того, как можно будет
писать функциональные требования и модель данных. Исследование выполняется отдельно, не в рамках
этой сессии.

| ID | Вопрос | Почему важно |
| --- | --- | --- |
| OQ-01 | Где исполняется плагин — в браузере SCO (как `webtutor_cooldown`, same-origin) или на сервере Core (вызов Moodle Web Services по токену)? | Определяет всю архитектуру плагина. Зависит от того, передаёт ли Moodle `courseId`/`userId`/сессионные куки внутрь SCORM-фрейма так же, как WebTutor. |
| OQ-02 | Какой способ аутентификации к Moodle Web Services использовать — постоянный service-token (Web Services → External services) или OAuth2? | Определяет модель хранения секрета в конфигурации плагина (аналог `eligibility_plugin_configs.config_json` из PRD-21) и требования к безопасности. |
| OQ-03 | Какой Web Services API возвращает «полноценную попытку» и дату её завершения — `core_completion_get_activities_completion_status`, `gradereport_user_get_grade_items`, `mod_scorm_get_scorm_attempt_count`/`get_scorm_scoes` или другой? | Аналог `attemptFilter`/`last_usage_date` из `webtutor_cooldown` (PRD-6 §3.3, §4.2) — без него нельзя определить `availableDate`. |
| OQ-04 | Как плагин получает `courseId`/`cmid`/`userId` конкретного запуска изнутри SCO? | Без этого плагин не может сформировать запрос к Moodle API для конкретного обучающегося/курса. |
| OQ-05 | Успевает ли серверный вызов к Moodle API уложиться в NFR-06 PRD-6 (5 сек P95)? | Гейт блокирует показ кнопки «Начать курс» до получения решения; сетевая задержка сервер→Moodle может быть выше, чем клиент→WebTutor. |
| OQ-06 | Как множественные SCORM-registration/попытки в Moodle влияют на подсчёт «полноценной попытки»? | В WebTutor понадобилась отдельная поправка (PRD-6 §9.1: Initialize/Terminate без записи `cmi.*` не должен становиться полноценной попыткой) — нужно проверить, есть ли аналогичная проблема в Moodle. |
| OQ-07 | Какой минимальный scope прав нужен токену (какие функции Web Services включать в external service)? | Принцип наименьших привилегий; риск раскрытия данных других пользователей/курсов при избыточном scope. |

## 4. Вне охвата (сейчас)

- Функциональные требования и модель данных `moodle_cooldown` — формулируются после ответов на
  §3.
- Регистрация `moodle_cooldown` в администрируемом реестре PRD-21 — после того как определится
  модель исполнения (OQ-01).
- Любая интеграция с Moodle кроме cooldown (импорт/экспорт оценок, SSO, синхронизация курсов) —
  не в скоупе PRD-41.

## 5. Следующие шаги

1. Проверить вопросы §3 на боевом/тестовом Moodle (вне этой сессии).
2. По результатам — продолжить брейншторминг и оформить §1.3, §3–§5 в разделы «Ключевые понятия»,
   «Функциональные требования», «Модель данных» по образцу PRD-6.
