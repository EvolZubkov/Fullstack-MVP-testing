## 1. Обзор

### 1.1 Контекст

Для типов `multiple`/`matching`/`ranking` рантайм считает стандартный балл по принципу «всё или
ничего»: точное совпадение с эталоном даёт `1`, любое отклонение — `0`
([resultsPage.js](../../../server/scorm/template/app/render/resultsPage.js) `checkAnswer`).
Частично верный ответ получает `0`. Это блокирует класс сертификационных и образовательных
тестов, где задание оценивается градуированно (0/1/2/3) по рубрике.

Ближайший потребитель — РТК-сертификация руководителей (идёт на платформу сразу после релиза).
Её внешний pandas-обработчик выставляет балл за вопрос по ступенчатой рубрике и суммирует баллы
в балл раздела против абсолютного порога. Без градуированной оценки этот тест не реализуется на
платформе без доработки.

### 1.2 Что подтверждено эталоном (РТК-2026)

Сверка реального ключа `key_NEW_15-08-25.xlsx` (208 вопросов) и обработанного pandas-результата:

- **одиночный с весами** (ключ с префиксом `%`, напр. `%A2B1C1D0`): балл = вес выбранной опции
  (0/1/2). АДДИТИВНО; уже выразимо сеткой «Вклады вопросов», новый механизм НЕ требуется;
- **множественный**: ступенчатая рубрика над `(верных, неверных)`. НЕ аддитивна — лишняя
  неверная опция понижает тир (`ABD` при эталоне `AD` -> `1`, а не `2`);
- **сопоставление**: ступенчатая рубрика над `(верных пар, всего пар)` (`2/3`, `3/3`);
- **одиночный обычный**: бинарно (0/1) — рантайм уже умеет.

Вывод: реальный кодовый пробел — ступенчатая (тировая) оценка `multiple` и `matching`. Это
уточняет BR-09-02 («доля верных со штрафом»): фактическое правило — тировая таблица, доля —
её частный случай.

### 1.3 Метрики успеха

| Цель | Метрика |
| --- | --- |
| РТК-тест реализуется без внешней постобработки | golden-тест против `key_NEW` + pandas-результата зелёный (Стадия 6) |
| Обратная совместимость | все существующие тесты бит-идентичны (рубрика по умолчанию — бинарная) |
| LMS получает частичный балл | `scoreRatio`/`partial` публикуются стандартными CMI-полями SCORM 2004 |

## 2. Пользователи

- **Автор теста** — включает и настраивает рубрику для вопроса (веса опций или тировая таблица);
  по умолчанию рубрика бинарная и настройки не требует.
- **Разработчик шаблона** — получает `scoreRatio`/`partial` в публичном контексте и стандартных
  CMI-полях; рубрику не настраивает.
- **Обучающийся** — видит частичный балл и статус «Частично правильно» там, где включена
  градуированная рубрика.

## 3. Функциональные требования

| ID | Требование | Основание |
| --- | --- | --- |
| FR-01 | Вопрос даёт стандартный балл `s ∈ [0, sMax]` по РУБРИКЕ своего типа; `scoreRatio = s / sMax` | §11.1, BR-09-02 |
| FR-02 | Рубрика по умолчанию — БИНАРНАЯ (`sMax = 1`); вопрос/тест без рубрики считается как сейчас (бит-идентично) | §11.8, BR-09-05 |
| FR-03 | `single`: рубрика «по весам опций» — балл = вес выбранной опции, `sMax = max(вес)` | §11.3 |
| FR-04 | `multiple`: рубрика «тировая» — балл по тировой таблице над счётчиками `(c, x, T)`; неаддитивна | §11.4 |
| FR-05 | `matching`: рубрика «тировая» — балл `f(c, P)` по верным парам; единица — `matching_pair` | §11.5, §10.11 |
| FR-06 | `ranking`: та же тировая модель над `(c, N)`; дефолт — полное совпадение порядка | §11.6, §10.11 |
| FR-07 | Тировая таблица — упорядоченный список `{when, score}`, первое совпадение, иначе `0`; пол `s = max(0, ·)` | §11.2, §11.8 |
| FR-08 | Градуированный балл — ось КОРРЕКТНОСТИ; на вклады в шкалы (`question_measurements`) не влияет | §10.3, BR-09-03 |
| FR-09 | Стандартные баллы агрегируются по теме/разделу как `Σ s`; при бинарных рубриках `Σ s` = «число верных» | §11.7 |
| FR-10 | Порог раздела — pass-rule (`count`/`percent`) на `Σ s` раздела, без выравнивающих коэффициентов | §11.7 |
| FR-11 | Сертификация — показатель (PRD-2): «1 балл за пройденный раздел; все разделы -> завершение» + `controls_status=success` | §11.7, §9.4 |
| FR-12 | Runtime публикует `scoreRatio` и статус `partial` в контракт шаблона, показ обучающемуся и LMS (CMI 2004) | BR-09-04 |
| FR-13 | Рубрика проходит валидацию: веса/баллы числовые `>= 0`, предикаты тиров над `{c,x,T,P,N}`, `sMax > 0` | §11.2 |

## 4. Модель данных

Рубрика — поле вопроса (ось правильности), отдельное от `question_measurements` (вклады в шкалы).

Концептуальная форма (точная схема — Стадия 1):

```text
question.rubric (опционально; отсутствие = бинарная):
  kind: 'binary' | 'weighted_options' | 'tiered'      # default 'binary'
  weights?: number[]                                  # weighted_options (single), по индексам опций
  tiers?: [ { when: Predicate, score: number } ]      # tiered (multiple/matching/ranking)
  sMax?: number                                       # иначе выводится: max(weights) | max(tier.score)

Predicate (конъюнкция условий над счётчиками ответа):
  all: [ { lhs: 'c'|'x', op: '=='|'>='|'<='|'<'|'>', rhs: number | 'T' | 'P' | 'N' } ]
```

Счётчики по типам (§11.2): `c` — верные выбранные единицы, `x` — неверные выбранные, `T` —
эталонные единицы (всего верных опций / пар `P` / элементов `N`).

Хранение: расширение `questions.correct_json` или отдельное поле — решается на Стадии 1
(durable id единиц — пререквизит §10.7 #2 для `matching`/`ranking`).

## 5. Рантайм и конвейер

- `checkAnswer(q, answer)` возвращает `s ∈ [0, sMax]` вместо `0`/`1`; при отсутствии рубрики —
  текущее бинарное поведение (FR-02). Изменение в обоих представлениях парити: монолитный
  `server/scorm/assets/app.js` и/или модульный
  [resultsPage.js](../../../server/scorm/template/app/render/resultsPage.js).
- Оценщик тировой таблицы: вычислить счётчики `(c, x, T/P/N)` по типу, пройти `tiers` сверху
  вниз, вернуть `score` первого совпадения, иначе `0`, затем пол `max(0, ·)`.
- Агрегация `Σ s` по теме включается в существующий расчёт результата; pass-rule раздела
  читает `Σ s` (FR-09, FR-10).
- Конвейер (§4 scoring-model): балл вопроса -> тема/раздел -> pass-rule -> показатель
  (сертификация, `controls_status`) -> LMS.

## 6. Экспорт и LMS

- `test-json` переносит `rubric` в TEST_DATA пакета (Стадия 3).
- `scoreRatio` и `partial` публикуются стандартными CMI-полями SCORM 2004 (FR-12, NFR-04).
- Итог раздела и сертификация уходят в LMS через механику показателей PRD-2 (`result.*`,
  псевдо-интеракции, override статуса).

## 7. UI (редактор рубрик)

Стартует ПОСЛЕ согласования эскизов (NFR-14). Содержание (детали — Стадия 0b, эскизы):

- переключатель рубрики в карточке вопроса (по умолчанию «Точное совпадение»);
- `single`: ввод весов по опциям (read-only подсветка верного варианта сохраняется);
- `multiple`/`matching`/`ranking`: конструктор тировой таблицы (условия над счётчиками + балл),
  с пресетами (напр. «РТК: всё+0 лишних / частично / провал»);
- предпросмотр балла по гипотетическому ответу;
- состояния: основное, пустое, loading/saving, ошибка валидации, read-only.

## 8. Совместимость и миграция

- Отсутствие `rubric` = бинарная рубрика, `sMax = 1` -> текущий расчёт без изменений
  (FR-02, NFR-10).
- Миграция не меняет существующие вопросы; рубрика добавляется опционально.
- Durable id единиц `matching`/`ranking` — пререквизит (§10.7 #2); при индексной адресации
  возможен index-remap (оценить на Стадии 1).

## 9. Тестирование

- **Golden РТК (Стадия 6):** воспроизвести балл за вопрос и балл раздела против
  `key_NEW_15-08-25.xlsx` + `report_processed_pandas_*.xlsx` (выверенная фикстура: одиночный с
  весами, множественный тировый, сопоставление тировое, абсолютные пороги, сертификация 6
  разделов).
- **Совместимость:** существующие golden/`scorm-export`/`mbi-golden` остаются зелёными
  (бинарный дефолт).
- **Юнит:** оценщик тировой таблицы (граничные `c/x/T`), веса опций, пол `max(0, ·)`,
  агрегация `Σ s`.
- **Парити:** TS-источник и JS-порт `checkAnswer` дают одинаковый балл.

## 11. Вне охвата

- Negative marking, зачёт неотмеченных дистракторов, `choose-N` нормализация — §10.6.
- IRT/Rasch, оценка параметров заданий, θ — платформа потребляет готовые данные (§10.6).
- Выравнивающие коэффициенты `a*raw+b` по формам — ТЗ-2026 их убрало; опция на будущее (§3).
- Композитные шкалы и глобальная библиотека шкал — отдельный трек (PRD-5 отложенное).
