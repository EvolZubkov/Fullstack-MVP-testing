## Терминология

**«Цена ответа»** — сколько баллов приносит ответ на ОДИН вопрос. Это уровень НИЖЕ правил
прохождения и лишь меняет их вход:

```text
цена ответа (вопрос)  →  правило прохождения темы  →  правило прохождения теста / показатель
```

Сегодня цена ответа зашита как «всё или ничего» (`checkAnswer` = 0/1). PRD-10 делает её
настраиваемой (частичный балл). Правила прохождения тем/теста (`topic_pass_rule_json`,
`overall_pass_rule_json`) НЕ меняются — меняется только их вход. Термин «рубрика» в этом
документе не используется.

## Статус реализации (на 2026-06-03)

**Не начата.** Нормативная модель зафиксирована в [scoring-model.md](../scoring-model.md) §11.
Настоящий PRD — план реализации на согласование (Стадия 0a). UI-стадии (редактор цены ответа)
стартуют только после согласования эскизов (NFR-14, BR-08-10).

## 1. Обзор

### 1.1 Контекст

Для типов `multiple`/`matching`/`ranking` рантайм считает стандартный балл по принципу «всё или
ничего»: точное совпадение с эталоном даёт `1`, любое отклонение — `0`
([resultsPage.js](../../../server/scorm/template/app/render/resultsPage.js) `checkAnswer`).
Частично верный ответ получает `0`. Это блокирует класс сертификационных и образовательных
тестов, где задание оценивается градуированно (0/1/2/3).

Ближайший потребитель — РТК-сертификация руководителей (идёт на платформу сразу после релиза).
Её внешний pandas-обработчик выставляет балл за вопрос по ступенчатому правилу и суммирует баллы
в балл раздела против абсолютного порога. Без градуированной цены ответа этот тест не реализуется
на платформе без доработки.

### 1.2 Что подтверждено эталоном (РТК-2026)

Сверка реального ключа `key_NEW_15-08-25.xlsx` (208 вопросов) и обработанного pandas-результата:

- **одиночный с весами** (ключ с префиксом `%`, напр. `%A2B1C1D0`): балл = вес выбранной опции
  (0/1/2). АДДИТИВНО; уже выразимо сеткой «Вклады вопросов», новый механизм НЕ требуется;
- **множественный**: ступенчатая цена ответа над `(верных, неверных)`. НЕ аддитивна — лишняя
  неверная опция понижает ступень (`ABD` при эталоне `AD` -> `1`, а не `2`);
- **сопоставление**: ступенчатая цена ответа над `(верных пар, всего пар)` (`2/3`, `3/3`);
- **одиночный обычный**: точное совпадение (0/1) — рантайм уже умеет.

Вывод: реальный кодовый пробел — ступенчатая оценка `multiple` и `matching`. Это уточняет
BR-09-02 («доля верных со штрафом»): фактическое правило — ступенчатая таблица, доля —
её частный случай.

### 1.3 Метрики успеха

| Цель | Метрика |
| --- | --- |
| РТК-тест реализуется без внешней постобработки | golden-тест против `key_NEW` + pandas-результата зелёный (Стадия 6) |
| Обратная совместимость | все существующие тесты бит-идентичны (цена ответа по умолчанию — точное совпадение) |
| LMS получает частичный балл | `scoreRatio`/`partial` публикуются стандартными CMI-полями SCORM 2004 |

## 2. Пользователи

- **Автор теста** — настраивает цену ответа для вопроса (веса опций или ступенчатая таблица);
  по умолчанию способ — «точное совпадение», настройки не требует.
- **Разработчик шаблона** — получает `scoreRatio`/`partial` в публичном контексте и стандартных
  CMI-полях; цену ответа не настраивает.
- **Обучающийся** — видит частичный балл и статус «Частично правильно» там, где задана частичная
  цена ответа.

## 4. Модель данных

Цена ответа — поле вопроса (ось правильности), отдельное от `question_measurements` (вклады в
шкалы). Стоит на уровень ниже правил прохождения тем/теста и лишь меняет их вход (см.
«Терминология»).

Концептуальная форма (точная схема — Стадия 1):

```text
question.scoring (опционально; отсутствие = точное совпадение):
  kind: 'exact' | 'weighted' | 'tiered'               # default 'exact'
  weights?: number[]                                  # weighted (single), по индексам опций
  tiers?: [ { when: Predicate, score: number } ]      # tiered (multiple/matching/ranking)
  sMax?: number                                       # иначе выводится: max(weights) | max(tier.score)

Predicate (конъюнкция условий над счётчиками ответа):
  all: [ { lhs: 'c'|'x', op: '=='|'>='|'<='|'<'|'>', rhs: number | 'T' | 'P' | 'N' } ]
```

Счётчики по типам (§11.2): `c` — верные выбранные единицы, `x` — неверные выбранные, `T` —
эталонные единицы (всего верных опций / пар `P` / элементов `N`).

Хранение: расширение `questions.correct_json` или отдельное поле — решается на Стадии 1
(durable id единиц — пререквизит §10.7 #2 для `matching`/`ranking`).

## 5. Рантайм и конвейер

- `checkAnswer(q, answer)` возвращает `s ∈ [0, sMax]` вместо `0`/`1`; при отсутствии цены ответа
  — текущее поведение «точное совпадение» (FR-02). Изменение в обоих представлениях парити:
  монолитный `server/scorm/assets/app.js` и/или модульный
  [resultsPage.js](../../../server/scorm/template/app/render/resultsPage.js).
- Оценщик ступенчатой таблицы: вычислить счётчики `(c, x, T/P/N)` по типу, пройти `tiers` сверху
  вниз, вернуть `score` первого совпадения, иначе `0`, затем пол `max(0, ·)`.
- Агрегация `Σ s` по теме включается в существующий расчёт результата; правило прохождения
  раздела читает `Σ s` (FR-09, FR-10).
- Конвейер (§4 scoring-model): балл вопроса -> тема/раздел -> правило прохождения -> показатель
  (сертификация, `controls_status`) -> LMS.

## 6. Экспорт и LMS

- `test-json` переносит `scoring` в TEST_DATA пакета (Стадия 3).
- `scoreRatio` и `partial` публикуются стандартными CMI-полями SCORM 2004 (FR-12, NFR-04).
- Итог раздела и сертификация уходят в LMS через механику показателей PRD-2 (`result.*`,

## 7. UI (редактор цены ответа)

Стартует ПОСЛЕ согласования эскизов (NFR-14). Содержание (детали — Стадия 0b, эскизы):

- переключатель способа цены ответа в карточке вопроса (по умолчанию «Точное совпадение»);
- `single`: ввод весов по опциям (read-only подсветка верного варианта сохраняется);
- `multiple`/`matching`/`ranking`: КОНСТРУКТОР ступенчатой таблицы (решение 2026-06-03) — автор
  сам задаёт строки «условие (порог над `c`/`x`/`T`) -> значение (балл)», порядок строк =
  приоритет (первое совпадение); пресеты опциональны как заготовка, но базовый режим — ручной
  конструктор;
- предпросмотр балла по гипотетическому ответу;
- состояния: основное, пустое, loading/saving, ошибка валидации.

## 8. Совместимость и миграция

- Отсутствие `scoring` = «точное совпадение», `sMax = 1` -> текущий расчёт без изменений
  (FR-02, NFR-10).
- Миграция не меняет существующие вопросы; цена ответа добавляется опционально.
- Durable id единиц `matching`/`ranking` — пререквизит (§10.7 #2); при индексной адресации
  возможен index-remap (оценить на Стадии 1).

## 9. Тестирование

- **Golden РТК (Стадия 6):** воспроизвести балл за вопрос и балл раздела против
  `key_NEW_15-08-25.xlsx` + `report_processed_pandas_*.xlsx` (выверенная фикстура: одиночный с
  весами, множественный ступенчатый, сопоставление ступенчатое, абсолютные пороги, сертификация
  6 разделов).
- **Совместимость:** существующие golden/`scorm-export`/`mbi-golden` остаются зелёными
  (дефолт «точное совпадение»).
- **Юнит:** оценщик ступенчатой таблицы (граничные `c/x/T`), веса опций, пол `max(0, ·)`,
  агрегация `Σ s`.
- **Парити:** TS-источник и JS-порт `checkAnswer` дают одинаковый балл.
