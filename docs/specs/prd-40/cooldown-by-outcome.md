# PRD-40: Период охлаждения по исходу попытки

**Версия:** 1.0
**Статус:** Реализовано и влито в main 2026-08-05
**Связанные документы:** [PRD-6](../prd-6/retake-cooldown-gate.md) (retake gate, барьер A),
[PRD-31](../prd-31/attempt-interval.md) (единая модель допуска, барьер B)
**Зависимости:** PRD-6 (`retakePolicy`, `EligibilityEngine`, плагин `webtutor_cooldown`),
PRD-31 (единый резолв назначения/попытки на обоих хостах)

## 1. Обзор

### 1.1 Контекст

Барьер A (PRD-6/PRD-31 §2.2) — календарный кулдаун МЕЖДУ назначениями — сейчас настраивается одним
числом `cooldownPeriodDays`, одинаковым независимо от того, чем закончилась последняя попытка
предыдущего назначения: учащийся, проваливший тест, ждёт повторного допуска столько же, сколько и
учащийся, успешно его сдавший. Часть тестов (аттестации, сертификации) требует развести эти два
случая: например, короткое окно на пересдачу после провала (дать быстро доучиться и попробовать
снова) и длинное окно после успеха (не пускать сдавать тот же тест ради коллекционирования баллов).

### 1.2 Цель

1. Дать автору теста переключатель «разделять период охлаждения по исходу попытки», по умолчанию
   выключенный (обратная совместимость: существующие тесты не меняют поведение).
2. При включённом переключателе — два независимых значения периода вместо одного: для случая, когда
   последняя попытка предыдущего назначения была ПРОЙДЕНА, и для случая, когда она была НЕ ПРОЙДЕНА.
3. Определять исход единообразно на обоих хостах через общее чистое ядро (как остальная математика
   барьеров PRD-6/PRD-31).
4. Заодно убрать `suspend_data_cooldown` — единственный альтернативный плагин барьера A, который не
   пишет исход (и вообще ничего) в проде: ни один живой тест им не пользуется, добавлять ему
   разделение по исходу означает поддерживать код, которым никто не пользуется.

### 1.3 Метрики успеха

| Цель | Метрика |
| --- | --- |
| Разделение применяется | При включённом переключателе оба хоста выбирают число дней по исходу последней попытки ДРУГОГО назначения |
| Обратная совместимость | Тест без переключателя (весь существующий парк) не меняет поведение и экспорт |
| Единая семантика | Общий чистый резолвер даёт одинаковый вердикт на веб- и SCORM-хосте по одинаковым фактам (golden-тест паритета) |
| `suspend_data_cooldown` снят | Плагин отсутствует в реестре, рантайм-ветка удалена, ни один тест не ссылается на него |

## 2. Пользователи

Роли те же, что в PRD-6 (§2): автор теста включает переключатель и задаёт два значения вместо
одного; администратор/внедренец при необходимости правит `passedStateIn` в конфигурации плагина
`webtutor_cooldown` (новое поле фильтра, наравне с уже существующим `stateIn`); учащийся видит тот же
экран блокировки, что и раньше — просто число дней в нём теперь зависит от исхода его прошлой
попытки.

## 3. Ключевые понятия

### 3.1 Расширение `retakePolicy`

```json
{
  "enabled": true,
  "cooldownPeriodDays": 30,
  "cooldownByOutcome": true,
  "cooldownPeriodDaysPassed": 90,
  "cooldownPeriodDaysFailed": 7,
  "gateMode": "before_internal_start",
  "eligibilityPlugin": { "key": "webtutor_cooldown", "configId": "webtutor_catalog_default", "failPolicy": "failOpen" },
  "blockedPageId": "system.blocked"
}
```

- `cooldownByOutcome` (boolean, по умолчанию `false`) — переключатель разделения. Выключен = старое
  поведение, `cooldownPeriodDays` — единственный действующий период (как в PRD-6).
- `cooldownPeriodDaysPassed` / `cooldownPeriodDaysFailed` (целое 1–3650) — обязательны, когда
  `enabled && cooldownByOutcome`. `cooldownPeriodDays` в этом режиме не используется рантаймом, но
  может оставаться в объекте (не обнуляется автоматически при включении переключателя — UI просто
  скрывает его).

### 3.2 Резолв периода — `resolveCooldownDays`

Новая чистая функция ядра (parity-паттерн PRD-6/PRD-31: `shared/eligibility/engine.ts` +
JS-двойник `server/scorm/template/app/eligibility/engine.js`, паритет проверяется
`tests/eligibility-engine-port.test.ts`):

```text
resolveCooldownDays(policy, passed: boolean | null): number | null

если !policy.cooldownByOutcome:
    вернуть policy.cooldownPeriodDays

если passed === true:
    вернуть policy.cooldownPeriodDaysPassed

если passed === false:
    вернуть policy.cooldownPeriodDaysFailed

если passed === null (исход последней попытки не определён):
    вернуть БОЛЬШЕЕ из cooldownPeriodDaysPassed и cooldownPeriodDaysFailed
```

Ветка `passed === null` — осознанно консервативный выбор: неопознанный/нестандартный статус LMS не
должен ДАВАТЬ учащемуся более короткое окно ожидания, чем оба настроенных автором значения. Сама
формула кулдауна (`cooldownDecision` — разница календарных дат) не меняется: `resolveCooldownDays`
только выбирает, КАКОЕ число дней в неё передать; вызывающие места (плагин `webtutor_cooldown`,
веб-барьер A) находят число дней ДО вызова `cooldownDecision`.

### 3.3 Источник исхода

| Хост | Источник `passed` |
| --- | --- |
| SCORM (`webtutor_cooldown`) | Запись WebTutor, выигравшая отбор `attemptFilter` (та же запись, чья дата уже используется как `lastAttemptDate`): `passed = true`, если её `state` входит в новое поле фильтра `passedStateIn`; `false`, если запись прошла `stateIn` (значит завершённая), но не входит в `passedStateIn`; `null`, если `passedStateIn` не задан в конфигурации |
| Веб | `resultJson.overallPassed` попытки с максимальным `finishedAt` среди попыток ДРУГИХ назначений (`outside`, PRD-31 §3) — той же попытки, чья дата уже определяет `lastAttemptDate` |

`passedStateIn` — новое поле `WebtutorAttemptFilter` (`shared/eligibility/plugins.ts`), аналогичное
уже существующему `stateIn`, но сужающее список до подмножества «пройден». Дефолтный сид
(`shared/eligibility/registry.ts`, конфигурация `webtutor_catalog_default`) получает
`passedStateIn: ["Пройден"]` — значение уже подтверждено вживую на портале как текст статуса «сдан».

### 3.4 Удаление `suspend_data_cooldown`

Плагин `suspend_data_cooldown` (PRD-6 §4.6, best-effort источник даты из `suspend_data`) полностью
убирается:

- запись реестра (`shared/eligibility/registry.ts`);
- рантайм-функция `suspendDataCooldownDecide` (`shared/eligibility/plugins.ts` + JS-двойник);
- ветка `suspendDataCooldown` в `runPlugin()` и функция `suspendEvaluate` в
  `server/scorm/template/app/eligibility/gate.js` (единственная, что читает
  `cmi.suspend_data.retake.lastCompletedDate` — на проверку 2026-08-04 в проде это поле никто не
  пишет, значение всегда отсутствует);
- предупреждение «best-effort» в панели автора (второго best-effort-плагина не остаётся, баннер
  теряет смысл);
- упоминания в спеке PRD-6 (§3.5 пример реестра, §4.6 целиком) и тестах.

Проверено на dev-копии прод-данных 2026-08-04: ни один тест не ссылается на `suspend_data_cooldown`
(`retake_policy_json->'eligibilityPlugin'->>'key'`), удаление не ломает существующие настройки.
После удаления в реестре остаётся один активный плагин — `webtutor_cooldown`. Селект «Способ проверки
(плагин)» в панели автора сознательно НЕ убирается (решение 2026-08-04): выбор с одним вариантом —
приемлемый визуальный шум, трогать этот участок UI вне охвата задачи.

## 4. Функциональные требования

| ID | Требование |
| --- | --- |
| FR-01 | Автор может включить `cooldownByOutcome` независимо от прочих настроек `retakePolicy` |
| FR-02 | При включённом `cooldownByOutcome` обязательны оба значения `cooldownPeriodDaysPassed`/`cooldownPeriodDaysFailed` (1–3650) |
| FR-03 | При выключенном `cooldownByOutcome` (в т.ч. для существующих тестов) поведение и экспорт байт-в-байт совпадают с текущими (кроме удаления `suspend_data_cooldown`, см. FR-07) |
| FR-04 | Оба хоста (веб и SCORM) резолвят число дней барьера A через общее ядро `resolveCooldownDays` по факту исхода последней попытки другого назначения |
| FR-05 | Неопределённый исход (`passed === null`) резолвится в БОЛЬШЕЕ из двух настроенных значений |
| FR-06 | Экран блокировки показывает РЕЗОЛВЛЕННОЕ число дней (`retake.cooldownPeriodDays`), без изменений в шаблонах/DSL — значение приходит через существующий путь `result.data.cooldownPeriodDays` |
| FR-07 | Плагин `suspend_data_cooldown` удалён из реестра, рантайма и панели автора; существующие тесты (ни один не выбирал этот плагин на момент разработки) не ломаются |
| FR-08 | `webtutor_cooldown` определяет исход последней полноценной попытки через новое поле фильтра `passedStateIn`; отсутствие поля в конфигурации — `passed = null` (попадает в FR-05) |

## 5. Модель данных

### 5.1 `tests.retake_policy_json` — новые поля

См. §3.1. Миграция схемы БД не требуется (колонка `jsonb`), только правка Zod-схемы
`retakePolicySchema` (`shared/schema.ts`):

```ts
cooldownByOutcome: z.boolean().default(false),
cooldownPeriodDaysPassed: z.number().int().min(1).max(3650).optional(),
cooldownPeriodDaysFailed: z.number().int().min(1).max(3650).optional(),
```

`superRefine`: если `enabled && cooldownByOutcome`, оба новых поля обязательны (issue на каждое
отсутствующее); если `enabled && !cooldownByOutcome`, требование к `cooldownPeriodDays` не меняется
(как сейчас).

### 5.2 `EligibilityContext.retakePolicy` (`shared/eligibility/types.ts`)

Расширяется тремя опциональными полями (зеркало §5.1); `cooldownPeriodDays` становится опциональным
на уровне типа контекста (может отсутствовать, когда включён `cooldownByOutcome`).

### 5.3 `WebtutorAttemptFilter` (`shared/eligibility/plugins.ts`)

Новое поле `passedStateIn?: string[]` — см. §3.3.

### 5.4 `AttemptFact` (`server/services/retake-gate.ts`)

Новое поле `passed: boolean | null`, заполняется на всех местах сборки массива из `resultJson`:
`server/routes/attempts.ts` (три участка построения фактов для `decideRetake`) и
`server/services/home/assigned.ts`.

`defaultRetakePolicy()` и `readRetakePolicyFromApi()` получают дефолты/чтение трёх новых полей по
образцу уже существующей обработки `attemptInterval`.

## 7. Совместимость и миграция

- Тест без `cooldownByOutcome` (весь существующий парк) не меняет поведения (FR-03).
- Тест, ссылавшийся на `suspend_data_cooldown` — на 2026-08-04 в проде нет ни одного; если такой
  появится между написанием спеки и релизом, `eligibilityPlugin.key` перестанет резолвиться в
  реестре и барьер A для него схлопнется в `core_default` (`allowed = true`, как для любого
  неизвестного/не найденного плагина, PRD-6 §3.4) — не крах, но требует ручной проверки при
  релизе.
- Компенсирующая миграция БД не нужна — оба барьера читаются из `retake_policy_json` без изменения
  структуры хранения.

## 9. Критерии приёмки

- [ ] Тест без `cooldownByOutcome` — экспорт и поведение не отличаются от текущих.
- [ ] Тест с `cooldownByOutcome` — веб блокирует первую попытку нового назначения на число дней,
      зависящее от исхода последней попытки предыдущего назначения (пройдена/не пройдена).
- [ ] Тот же сценарий воспроизведён в SCORM-пакете (плагин `webtutor_cooldown`, локальный стенд с
      засеянными записями).
- [ ] Исход, который не удалось определить (`passedStateIn` не сконфигурирован, либо статус LMS не
      входит ни в `stateIn`, ни в `passedStateIn`), даёт БОЛЬШЕЕ из двух значений.
- [ ] Экран блокировки показывает верное число дней без правок шаблонов.
- [ ] Панель автора: переключатель, два поля, валидация обязательности при включённом переключателе.
- [ ] `suspend_data_cooldown` отсутствует в реестре, рантайме, панели автора; связанные тесты и
      секция спеки PRD-6 актуализированы.
- [ ] Golden-тест паритета TS/JS для `resolveCooldownDays` зелёный.

## 10. Решённые вопросы

| Вопрос | Решение |
| --- | --- |
| Разделять период по умолчанию или только по явному переключателю? | Только по явному переключателю, по умолчанию выключен (совместимость) |
| Разделение нужно для обоих плагинов барьера A? | Только для `webtutor_cooldown` — второй плагин (`suspend_data_cooldown`) не пишет исход и в проде не используется, поэтому удаляется целиком, а не расширяется |
| Что делать с исходом, который не удалось определить? | Брать БОЛЬШЕЕ из двух значений (консервативный выбор, не сокращает окно) |
| Убирать ли селект плагина из панели автора после того, как останется один вариант? | Нет, оставить как есть — вне охвата задачи |
