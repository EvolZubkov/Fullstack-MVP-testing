# Спецификация: ревизия шаблона «Стандартный» на разметку ui-kit

Статус: черновик на согласование
Дата: 2026-07-25
Связанные документы: [PRD-12 (паритет веб/SCORM)](prd-12/web-runtime-parity.md),
[платформа шаблонов](spec-template-platform.md),
[PRD-7 (шаблоны оформления)](prd-7/), [PRD-23 (темы шаблона)](../plans/PLAN_PRD23_TEMPLATE_THEMES.md),
[PRD-18 (плеер/отладчик)](prd-18/), [PRD-19 (навигация/структура)](prd-19/)

## 1. Задача и границы

Две поставленные задачи по шаблону «Стандартный»:

1. Перевести ученические экраны на дизайн-систему UniversityRT (компоненты `ou-*` и
   токены `--ou-*`), убрав собственный CSS-слой шаблона, который вручную дублирует DS.
2. Эффективнее использовать площадь экрана: перейти от вытянутой вертикальной колонки
   с вложенными рамками к модели «сцена» (закреплённые шапка и панель действий,
   скроллится только тело, контент занимает ширину).

Источник вида — эталонная разметка ui-kit, переданная заказчиком и отрендеренная
статикой в [docs/wireframes/prohozhdenie/](../wireframes/prohozhdenie/). Разметка
воспроизводит все 20 вариантов страниц шаблона (см. раздел 3).

Границы:

- В работе только шаблон `server/scorm/templates/default` и обвязка ученических
  экранов в веб-хосте. Ученический рантайм SCORM и отладчик (PRD-18) получают тот же
  вид автоматически (раздел 6).
- НЕ трогаем: контракт контекста как публичный API (`shared/template/context.ts`) —
  расширяем аддитивно; логику прохождения (flowPolicy, шкалы, показатели, PRD-2/5/6/10/11);
  состав и порядок экранов (PRD-19).
- Шаблон `templates/certification` остаётся на прежней основе до отдельной задачи.

## 2. Текущее состояние

Рендеринг ученических экранов уже унифицирован (PRD-12). Единый framework-free
рендерер `shared/template/` (`dsl.ts` — mustache-подмножество, `render-screen.ts`,
`renderers.ts`, контракт `context.ts`) рисует экраны из ОДНИХ макетов шаблона на обоих
хостах:

- веб импортирует рендерер напрямую (Vite) и монтирует в Shadow DOM
  (`client/src/components/template-screen.tsx`);
- SCORM получает его IIFE-бандлом `TBTemplate` (`runtime-entry.ts` →
  `server/scorm/builders/shared-runtime.ts`);
- отладчик (PRD-18) проигрывает живой SCORM-пакет, поэтому наследует вид без правок.

Шаблон `default` состоит из:

- `layouts/*.html` — макеты (mustache-подмножество: `data-placeholder`, `data-slot`,
  `data-path`, `{{#if}}`, `{{#each}}`, `data-action`);
- `styles/theme.css` + `styles/base.css` — ~1120 строк собственного CSS. `theme.css`
  объявляет палитру (`--primary`, `--background`, `--card`, `--muted`, `--accent`,
  `--success`, `--destructive`, `--font-sans` …) HSL-тройками; `base.css` реализует
  компоненты (`.tb-pills`, `.option`, `.matching-board`, `.ranking-board`,
  `.results-ring`, `.progress-bar`, `.btn` …), которые в DS уже есть;
- `manifest.json` — 20 вариантов страниц (`contentTemplates`) + параметры оформления.

Палитра теста (PRD-7/PRD-23) приходит на оба хоста как CSS-переменные: параметры
`primaryColor`/`backgroundColor`/… маппятся в `--primary`/`--background`/… через
`shared/template/params-css.ts`; per-theme переопределения — через
`shared/template/theme-css.ts`. Собственный CSS шаблона читает их как `hsl(var(--x))`.

Ключевая особенность, влияющая на объём работ: **интерактив вопроса
(варианты/доска/ранжирование) эмитится НЕ макетом, а рантайм-кодом хоста** — в веб это
JSX-строки в `client/src/pages/learner/template-question-screen.tsx`, в SCORM —
JS-строки в `server/scorm/template/app/render/*` и `.../single.js` и т.п. Оба хоста
эмитят одинаковые классы (`.option`, `.match-*`, `.rank-*`) двумя независимыми
реализациями. Общий сегодня — только движок DnD (`shared/template/dnd`) и модель
сопоставления.

### 3.1. Канонический состав из движка: система против автора

Состав и место каждого экрана определяет движок последовательности
(`shared/flow/page-sequence.ts`) и фазовый рендер (`contentFlow.js` /
`mainRender.js` / `adaptiveRender.js`), а НЕ выбор автора. Разделение строгое:
системные экраны привязаны к потоку и выдаются движком; автор вне системного
потока добавляет только информационные страницы (в четырёх размещениях: тест-скоуп
«До теста» / «После теста» и пер-топик «перед темой» / «после темы»).

Системные экраны (движок; автор не вставляет и не удаляет):

| Экран (layout) | Фаза / узел | Когда выдаётся |
| --- | --- | --- |
| `start` | phase `start` | заход в тест |
| `question` | phase `question` | вопрос из последовательности |
| `router.menu` | phase `router` | `flowMode = router_by_topics`; хаб — терминус зоны «До теста» (`isRouter`) |
| `section-intro` (`intro`) | пер-топик системный узел | «Введение раздела» перед темой (PRD-1 §4.3); авто-план по одной строке на тему |
| `review` | phase `review` | обзор ответов на завершении раздела/теста (PRD-19 D) |
| `section-results` | phase `sectionResults` | итоги раздела после секции (PRD-19 D5) |
| `results` / `results.adaptive` | phase `viewResults` / финал адаптива | завершение теста |
| `system.transition` | адаптив, между вопросами | `showDifficultyLevel` + смена УРОВНЯ внутри темы; авто-продолжение 2.5с |
| `system.blocked` | гейт доступа | попытки исчерпаны или действует кулдаун (PRD-6) |

Сценарии адаптива (PRD-4): реально поддержаны только **по темам** —
`adaptive_by_section` (`linear_by_topics`) и `adaptive + router` (§4.7); каждая
тема — своя лесенка уровней (`adaptive_levels`), старт со среднего, движение
вверх/вниз по порогу; итог — **по теме** (`results.adaptive`). Сценарий «весь тест
плоским смешанным потоком» — `adaptive + linear_flat` («Flat adaptive») —
**отложен в отдельный будущий PRD** (PRD-4, blocked/deferred). Поэтому в текущем
составе `system.transition` — это смена уровня ВНУТРИ темы (тема, по которой
определяется уровень, называется на экране); кросс-темный переход
(`topicTransition`) относится к отложенному flat-адаптиву.

Состояния поверх системных экранов (НЕ отдельные layouts):

- проверка ответа (верно/неверно + подсветка) — на `question`, при `showCorrectAnswers`;
- модалка «Завершить раздел/тест?» (FR-09) — поверх `review`/`question`.

Авторские информационные страницы (kind `info` / `gallery` / `html`; ставятся в 4
размещения, `SYSTEM_FLOW_KINDS` в поток как страница не попадают):

| Вариант манифеста | Layout | Примечание |
| --- | --- | --- |
| `info.text` (± `-lead`) | `content.text` | `lead` — плейсхолдер, показывается/скрывается |
| `info.image-left` (± `-lead`) | `content.image-left` | |
| `info.image-right` (± `-lead`) | `content.image-right` | |
| `gallery.*` (6) | `gallery.*` | последовательность с точками (`sequenceId`) |
| `html` | авторская разметка | без шаблонного варианта — проходит как есть |

Легаси / граница (не обычная страница). `summary` (`summary.result`) — граница
результатов в зоне «После теста»: помечает позицию встроенного экрана результатов
и сам НЕ рендерится, страницей итога является экран `results` (`buildAfterZone`).
Kind легаси — миграции 034/035 замещают старые `intro`/`summary`. Страницы ПОСЛЕ
границы (`postResultsPages`) рисуются уже за экраном результатов.

### 3.2. Несогласованности рантайма, выявленные при сверке (задачи)

1. Обратная связь в итогах несогласована между `results.html` (агрегирует
   `recommendedCourses`/`recommendedEvents` общим списком от непройденных тем) и
   `results.adaptive.html` (`feedback` + `recommendedLinks` по темам, без
   мероприятий) — при ЕДИНОМ источнике `topics.feedback_json { text, links,
   events }` и настройке `feedbackMode`. Свести оба `result-context`-билдера и
   макета к единому составу «фидбэк по теме = текст + курсы + мероприятия»,
   одинаковому для стандартного и адаптивного режимов.
2. `system.transition` титулуется вердиктом последнего ответа
   (`buildTransitionContext` → `isCorrect` → «Правильно!»/«Неправильно») и несёт
   `topicTransition` («переход к теме»). Но в текущем адаптиве (только по темам)
   переход — это смена УРОВНЯ внутри темы: вердикт одного ответа с заголовка убрать,
   назвать тему, по которой определяется уровень, а «переход к теме» не показывать
   (это событие отложенного flat-адаптива). Сам `buildTransitionContext` привести к
   этому — либо развести на две ветки (смена уровня / переход темы во flat).
3. `summary` и легаси-`intro` — устаревшие kinds (миграции 034/035). В новой модели
   `summary` не рендерится (страница итога — экран `results`), `intro` —
   пер-топик системный узел «Введение раздела».

### 3.3. Модель сцены

Общая модель («сцена») для всех: корень `.ou.ou--dark|light` высотой в окно,
`display:flex;flex-direction:column`; шапка и подвал закреплены, тело
(`flex:1;overflow:auto`) — единственная область скролла.

Ключевые решения эталонной разметки (переносятся как есть):

- контент-колонка `width:75%` (у медиа и сопоставления `100%`, вопрос ограничен
  `max-width:71%`);
- варианты — `ou-radio-card` с `flex:1;min-height:52px`, делят высоту тела поровну,
  интервал 4px; поэтому четыре варианта всегда помещаются без скролла;
- контролы: одиночный — `ou-radio`, множественный — `ou-check`, ранжирование —
  `ou-rank`, сопоставление — `ou-match`;
- шапка в два ряда: логотип + название (`display-s`) + подзаголовок; справа таймеры
  `ou-timer--digital` («тест», «раздел» — `is-critical`); ниже карта вопросов
  `ou-quiz--m --circle` + легенда, счётчик отвеченных справа; полоса прогресса 3px по
  нижней кромке шапки;
- размер шрифта вопроса (20–32px) и варианта (14–20px) масштабируется по длине текста;
- подвал: «Назад» / «К обзору ответов» слева; «Пропустить» + основное действие
  (`ou-btn--l`) справа.

Свет и тьма приходят из токенов DS без отдельного CSS: переключение достигается сменой
класса `ou--dark`/`ou--light` на корне. Это ровно цель PRD-23 (обе палитры из одного
источника).

## 4. Архитектура интеграции

### 4.1. CSS: вендоринг DS вместо собственного слоя

`styles/theme.css` + `styles/base.css` (1120 строк) заменяются на:

1. вендоринг `vendor/ui-kit/css/university-rt.css` в пакет (в zip и в Shadow DOM
   веб-хоста) — единый источник токенов и компонентов;
2. тонкий слой шаблона `styles/theme.css` — ТОЛЬКО мост палитры (раздел 4.4) и
   немногие правила сцены, которых нет в DS (см. 4.6).

Сборка пакета (`styles.css.ejs` → `styles.css`) склеивает DS + тонкий слой. Вес: DS в
zip ~45 КБ сжатых; вырос по сравнению с текущим, но убирает 1120 строк дубля.

Правки: `server/services/template-render.ts` (веб отдаёт DS + слой),
`server/scorm/builders/*` (пакет кладёт DS), `template-screen.tsx` (инъекция DS в
Shadow DOM: DS написан под `.ou` на элементе, а не под `:root`/`body` — маппинг уже
делается для текущего CSS, надо перенастроить под `.ou`).

### 4.2. Макеты: переписать в mustache-подмножество по эталону

Эталонная разметка — React (dc-runtime). Рендерер шаблона framework-free
(mustache-подмножество), поэтому макеты переписываются на тот же DOM и классы, что в
эталоне, но в синтаксисе `dsl.ts`. Переписываются (по одному на вариант либо
параметрически): `question.html` (+ типы), `router.menu`, `start.html`, `review.html`,
`section-intro.html`, `section-results.html`, `results.html`, `summary.*`,
`content.*`/`gallery.*` (info/gallery × text/image-left/image-right × lead).

Динамические списки, которые эталон строит в JS (`renderVals`): точки карты, варианты,
точки галереи — в макете выражаются через `{{#each}}` по данным контекста; статусные
классы (`is-answered`/`is-flagged`/`is-current`) приходят из контекста.

### 4.3. Интерактив: вынести эмиссию HTML в общий слой

Сейчас HTML вариантов/доски/ранжирования эмитится в двух местах (веб-JSX и SCORM-JS) —
это единственный шов, где «единый источник» не выполняется. Чтобы новые классы
(`ou-radio-card`/`ou-check`/`ou-rank`/`ou-match`) не разъехались между хостами, эмиссию
надо перенести в `shared/template/renderers.ts`: одна функция на тип вопроса, отдающая
разметку эталона; оба хоста вызывают её и делегируют `data-action`. DnD уже общий
(`shared/template/dnd`), модель сопоставления — тоже; добавляется общая разметка.

### 4.4. Мост палитры PRD-7/PRD-23 → токены DS

Разметка живёт на `--ou-*`, а брендирование теста приходит в `--primary`/`--background`/…
Чтобы брендирование сохранилось, тонкий `theme.css` шаблона кладёт мост: акцентную рампу
DS выводит из `--primary` теста тем же приёмом, каким её строит сам DS (рампа
`--ou-purple-400..700` через `color-mix`), поверхности — из `--background`/`--card`,
границы — из `--border`. Тогда:

- параметры манифеста, `cssVars` и панель «Оформление» НЕ меняются;
- темы PRD-23 (светлая/тёмная/авто) работают как есть — они уже переопределяют те же
  переменные-источники;
- по умолчанию (тест не задал палитру) действует штатная палитра DS.

Это ключевая точка интеграции и главный риск (раздел 8): нужно подтвердить, что вывод
рампы через `color-mix(in oklch)` даёт приемлемый бренд-цвет и работает в браузере LMS.

### 4.5. Размер шрифта по длине

Эталон масштабирует шрифт функцией `fit(len, max, min, from, per)`. CSS `clamp` не умеет
считать длину текста, поэтому величина вычисляется в общем коде:
`shared/template/` получает чистую `fitFont()`, контекст-билдер проставляет
`questionFont`/`optionFont` в контекст, макет подставляет их инлайном. Оба хоста берут
одну функцию — размеры совпадают. Это сохраняет единый источник и точность эталона.

### 4.6. Шрифт и остаточный CSS сцены

- Брендовый шрифт `RostelecomBasis` вендорится в пакет с `@font-face` (сейчас в zip нет
  ни одного шрифта, `--ou-font-family-base` уезжает на системный). Веб уже подключает
  шрифт из `client/src/styles/vendor`.
- Немногие правила сцены, которых нет в DS (флекс-колонка корня, `flex:1` вариантов,
  сетка «медиа + ответы», точки галереи), живут в тонком `theme.css` шаблона на токенах
  `--ou-*`, без цветовых литералов.

## 5. Единый источник: веб / SCORM / отладчик

После правок все три хоста рисуют экраны из одних артефактов:

- **макеты + CSS + контекст** — общие для веба (импорт) и SCORM (IIFE-бандл);
- **интерактив** — общий после выноса эмиссии в `shared/template/renderers.ts` (4.3);
- **отладчик (PRD-18)** проигрывает живой пакет, собранный тем же
  `buildScormExportData`, — вид наследуется, правок по существу не требуется;
- **офлайн-превью шаблона** и реестр «Шаблоны» рендерят через тот же `renderScreenInto`;
  панель действий приходит из общего билдера с демо-состоянием.

- `server/scorm/templates/default/layouts/*.html` — переписать все макеты (раздел 4.2);

## 7. Приёмка

- Браузерная приёмка (playwright/CDP) всех 20 вариантов в обеих темах — обязательна
  (юнит/jsdom недостаточны).
- Паритет: один и тот же тест в веб-хосте и в SCORM-пакете даёт идентичный DOM/вид на
  каждом из 20 вариантов и пяти типов вопроса.
- Гард цветовых литералов (`tests/ds-color-compliance.test.ts` и линтер эскизов) —
  зелёный: цвет только из `--ou-*` или палитры теста.
- Отладчик (PRD-18): сцена корректна в узком iframe.
- Порог покрытия юнит-суита не краснеет; при необходимости — тесты на `fitFont()` и
  общую эмиссию.

## 8. Риски и открытые вопросы

- **Браузер WebTutor.** Токены DS и мост палитры используют `color-mix(in oklch, …)` —
  нужен Chrome 111+ / Safari 16.2+. Если в LMS браузер старше, потребуется запасная
  палитра или предвычисление рампы на сборке. Проверка локальными выгрузками
  (живого WebTutor нет).
- **ChoiceCard в ui-kit.** В исходниках DS есть более новый React-компонент
  `ChoiceCard`, но его CSS не попал в собранный `university-rt.css`. Используем
  существующий `ou-radio-card`; заявку в DS на сборку `ChoiceCard` — отдельно.
- **Мост палитры.** Вывод акцентной рампы из одного `--primary` теста через `color-mix`
  надо проверить на реальных брендах (РТК-оранжевый и т.п.), чтобы `soft`/`container`/
  `hover` читались.
- **Два визуальных языка.** Пока `certification` на прежней основе, в системе живут два
  вида; свести — отдельной задачей.
- **Вес пакета.** DS добавляет ~45 КБ сжатых; приемлемо, но зафиксировать.
- **Вынос эмиссии интерактива** затрагивает и веб, и SCORM-рантайм — самый крупный
  по риску шаг; делать под браузерную приёмку паритета.
