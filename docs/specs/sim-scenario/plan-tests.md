# Сценарий в ИС: план встраивания в тесты

Статус: на согласование, 2026-10-06. Дополнено в тот же день: пункт-сценарий берёт сценарий
из темы-банка — случайный с поправкой на экспозицию или фиксированный.

Основа — готовые контракт и плеер: [exchange-format.md](exchange-format.md),
[result-format.md](result-format.md), `shared/sim/`. Здесь — как сценарий становится частью
продукта: вопрос, тест «Сценарий» и пункт роутера.

## 1. Решения владельца

| Вопрос | Решение, 2026-10-06 |
| --- | --- |
| Тип вопроса | «Сценарий»: содержимое — контракт сценария, изображения — в медиатеке |
| Тип теста | Третий режим теста — «Сценарий»: один пункт-сценарий, без тем и разделов |
| Банки сценариев | Сценарии — вопросы типа «Сценарий», разложенные по темам, как обычный банк. Тема и есть банк сценариев |
| Что запускает пункт | Пункт-сценарий ссылается на ТЕМУ. Выдача — на выбор автора: случайный сценарий темы с поправкой на экспозицию (PRD-55) или фиксированный сценарий этой темы |
| Что выдаётся из темы | ТОЛЬКО сценарии. Прочие вопросы темы-банка пункт-сценарий не выдаёт и не учитывает ни в пуле, ни в экспозиции, ни в снимке; тема может одновременно служить обычным разделом другого теста |
| SCORM-пакет | Случайная выдача — в пакет запекается весь пул с весами; фиксированная — только выбранный сценарий |
| Старт теста «Сценарий» | Стартовая страница с заданием и правилами; «Начать» сразу разворачивает плеер на весь экран |
| Финал теста «Сценарий» | Окно результата плеера → обычный экран итогов теста (балл, вердикт, текст по исходу, отчёт, сертификат) |
| Сценарии в роутере | Отдельная сущность «сценарии теста» рядом с разделами, не вид раздела |
| Место в хабе | Наравне с темами: один список в порядке автора, у сценария те же свойства пункта — обязательность, правила разблокировки, результат пункта; повторный запуск — по правилу теста «менять ответ» |
| Редактор сценария | Сильно позже; сценарий загружается архивом `.scenario.zip` |

## 2. Модель данных

| Что | Как |
| --- | --- |
| `questions.type` | Новое значение `simulation`. `dataJson` — `scenario.json` контракта, где пути `media/…` заменены идентификаторами медиатеки. Признаки типа — в `shared/questions/question-type.ts` и зеркале `qtype.js` |
| `tests.mode` | Новое значение `scenario` рядом с `standard` и `adaptive` |
| `test_scenarios` | Новая таблица: `id`, `test_id`, `topic_id` (банк сценариев), `question_id` (фиксированный сценарий; `null` — случайный), `title`, `required`, `time_limit_minutes`, `image`, порядок. В тесте «Сценарий» — ровно одна строка; в тесте с роутером — сколько угодно. Пул пункта — вопросы типа `simulation` этой темы; прочие вопросы темы пункт не видит |
| Выбор сценария | Фиксированная выдача — сценарий `question_id`, поправки на экспозицию нет: состав задал автор, как у вариантов PRD-17 (PRD-55 FR-20). Случайная — один сценарий из пула: `computeWeights` + `weightedPick(pool, 1, …)` из `shared/draw/exposure.ts` — тот же код, что выбирает вопросы раздела. Выбор делается на старте попытки и фиксируется в ней, как состав формы раздела; повторный запуск пункта в той же попытке играет тот же сценарий |
| Экспозиция | Выбранный сценарий — выдача по PRD-55 при ЛЮБОМ способе выдачи: счётчик `question_exposure` растёт на старте попытки (веб) и телеметрии (пакет). Веб берёт веса по живым счётчикам, пакет — запечённые при сборке. Новая попытка — новый выбор |
| Ключ пункта роутера | Сейчас правила разблокировки и состояние хаба ключуются `topicId`. Вводится общий ключ пункта: `topic:<id>` и `scenario:<id>`; голый `topicId` читается как `topic:<id>`, поэтому старые тесты не мигрируют |
| Порядок пунктов хаба | `router.itemOrder` — список ключей пунктов. Нет — сначала темы в нынешнем порядке, затем сценарии |
| Снимок публикации | Включает пункты-сценарии и содержимое сценариев, которые они могут выдать: весь пул у случайной выдачи, один сценарий у фиксированной |
| Ответ в попытке | Результат плеера (`SimResult`) — ответ на вопрос-сценарий. Протокол целиком — в ответ и телеметрию, в `cmi.suspend_data` — только итог |
| Оценка | Балл = цена × доля цели (`success` — 1, `partial` — `goal.share`, если тест засчитывает частично, иначе 0) − штрафы по цепочке «система → тест → вопрос», не ниже нуля |

## 3. Этапы

Каждый этап заканчивается проверкой и согласованием; следующий начинается по команде.

### Э0. Эскизы

По нашему порядку работы — до кода интерфейса. Состояния:

1. Ящик вопроса: тип «Сценарий», загрузка архива `.scenario.zip`, проверка при импорте с
   перечнем ошибок, «Сыграть» для проверки.
2. Ящик теста: режим «Сценарий» — выбор темы-банка сценариев вместо структуры и выдача: случайный
   сценарий темы (число сценариев в пуле и ожидаемая экспозиция «каждый сценарий темы увидят около
   N% участников», PRD-55 FR-33) или фиксированный сценарий (выбор сценария темы и «Сыграть»).
3. Ящик теста с роутером: «Добавить сценарий» в структуре, общий список тем и сценариев с
   перетаскиванием порядка, свойства пункта-сценария (название в меню, тема-банк, выдача, обязательность,
   лимит, картинка).
4. Хаб у участника: карточка сценария рядом с карточками тем, состояния «не начат», «завершён»,
   «закрыт правилом». Хаб, как и для тем, говорит, ЧТО пункт закрыт, а не КАК он пройден.
5. Стартовая страница теста «Сценарий»: задание и правила; затем полный экран.

### Э1. Вопрос «Сценарий» и импорт архива

Тип вопроса, загрузка `.scenario.zip` в ящике вопроса (проверки контракта на сервере, изображения
в медиатеку), «Сыграть» — тот же плеер в окне. Вопрос пока нельзя положить в тест.

### Э2. Тест «Сценарий» в вебе

Режим `scenario`, таблица `test_scenarios`, выбор темы-банка в ящике теста, выдача случайного сценария
с поправкой на экспозицию или фиксированного, учёт выдачи, старт → полный экран →
результат → итоги теста. Сохранение результата в попытку, оценка со штрафами, общий лимит времени
теста на панели плеера, досрочный выход. Снимок публикации.

### Э3. Сценарии в роутере в вебе

Ключ пункта и порядок пунктов, правила разблокировки и обязательность для сценариев, карточка в
хабе, возврат в хаб, результат пункта, повторный запуск по правилу «менять ответ».

### Э4. SCORM-пакет

Бандл плеера в пакете, запекание сценариев с изображениями (весь пул с весами экспозиции у
случайной выдачи, один сценарий у фиксированной), выбор сценария в рантайме тем же алгоритмом,
тест «Сценарий» и роутер в рантайме пакета, взаимодействие `performance`, телеметрия протокола.
Проверка на стенде WebTutor — полный экран там уже подтверждён.

### Э5. Оценка и аналитика

Блок «Штрафы сценариев по умолчанию» во вкладке «Оценка», окно «Оценка вопроса в тесте» для
сценария, разбор по сценам, таблица ловушек «Типичные ошибки», карта промахов. Экспозиция и медиана
времени сценария в аналитике банка — как у вопросов (PRD-55 FR-31 - FR-32).

Позже, отдельными треками: редактор сценария, телефонная раскладка, свой рекордер.

## 4. Защита от расхождения сценария и раздела

Сценарий — второй вид пункта теста рядом с разделом. Главная опасность — место, которое знает
только разделы и молча пропускает сценарий: хаб не покажет карточку, правило разблокировки не
сработает, снимок публикации потеряет сценарий, книга Excel сотрёт его при переносе. Защита
строится так, чтобы такое место нельзя было написать незаметно.

1. **Один тип пункта.** В `shared/test-items.ts` — `TestItem = { kind: "topic", … } | { kind:
   "scenario", … }` с общими свойствами пункта (ключ, обязательность, лимит времени, картинка,
   порядок). Пункты теста выдаёт одна функция `listTestItems`; хаб, правила разблокировки, политика
   завершения, результаты пунктов, снимок, выдача, SCORM и аналитика берут пункты только из неё, а
   не из `sections` напрямую.
2. **Исчерпывающий разбор.** Ветвление по виду пункта идёт через `matchTestItem(item, { topic,
   scenario })`: обработчик для каждого вида обязателен, а проверка `never` в конце не даст
   скомпилировать код, если появится третий вид. Цепочки `if (item.kind === "topic")` без ветки
   для сценария запрещены — это тот же класс ошибок, что разобран в PRD-26 для типов вопросов.
3. **Реестр мест.** `ITEM_CONSUMERS` — список модулей, которые работают с пунктами теста; у каждого
   записано решение по сценарию: «обрабатывает» или «неприменимо — потому что …». Архитектурный
   тест проходит по коду и падает, если модуль читает разделы теста (`testSections`, `sections`,
   `topicId` в потоке и роутере), но в реестре его нет. Новое место без явного решения в ветку не
   попадёт. Образец — тест признаков типов вопроса, требующий решения по каждому признаку.
4. **Круговые тесты.** Тест с темами и сценариями проходит без потерь по кругу: сохранение →
   снимок публикации → книга Excel → импорт → SCORM-сборка. Пункты, их порядок и свойства на
   выходе совпадают со входом.
5. **Паритет хостов.** Один набор прохождений проигрывается и в вебе, и в рантайме пакета;
   результаты (`SimResult`) и состояние хаба должны совпасть побайтно.
6. **Одинаковые правила для обоих видов.** Обязательность, разблокировка, завершение хаба и
   результат пункта считаются одним кодом для темы и для сценария; вид пункта влияет только на то,
   что запускается по карточке.

## 5. Риски

- **Второй вид пункта роутера.** Хаб, правила разблокировки, результаты разделов, снимки,
  аналитика и импорт книги Excel сегодня знают только разделы. Каждое место нужно найти и научить;
  опасность — тихо пропущенное место, где сценарий просто не учтётся. Защита — общий тип «пункт
  роутера» и тест, перечисляющий все места, где он нужен.
- **Один движок на два хоста.** Веб и SCORM обязаны вести себя одинаково — паритет хостов
  проверяется одним набором сценариев на обоих.
- **Медиа.** Сценарий — десятки изображений; стенд режет загрузку больше 1 МБ на файл. Пакет со
  случайной выдачей несёт ВЕСЬ пул пункта, поэтому его вес растёт с размером банка; фиксированная
  выдача несёт один сценарий. Импорт архива проверяет размеры
  заранее; ящик теста показывает суммарный вес пулов.
- **Маленький банк.** Пул из одного-двух сценариев выдаётся почти каждому участнику — сценарий
  быстро становится известен. Защита та же, что у вопросов: ожидаемая экспозиция видна автору при
  настройке пункта (PRD-55 FR-33).
- **Книга Excel.** Тест «Сценарий» и сценарии роутера должны переноситься книгой без потерь —
  иначе это класс ошибок «книга тихо стирает новое поле».
