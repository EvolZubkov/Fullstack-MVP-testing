# PRD-64: Единый вход (SSO)

**Версия:** 0.1
**Статус:** Требования собраны 2026-09-23, к согласованию; эскизов и кода нет
**Дата актуализации:** 2026-09-23
**Связанные документы:** [PRD-13](../prd-13/role-based-access-control.md) (роли живут только
в `user_roles`; SSO их источником не становится), [PRD-28](../prd-28/external-participant.md)
(внешний участник — учётная запись без пароля, SSO его не касается),
[PRD-52](../prd-52/test-review.md) (рецензент приходит по персональной ссылке без роли),
[PRD-9](../prd-9/crypto-password-hashing.md) (пароли scrypt — остаются для тех, кто не в домене),
[PRD-62](../prd-62/proctoring-integration.md) (образец: контракт провайдера плюс реестр
конфигураций вместо ветвлений в ядре)
**Место в плане:** [ROADMAP §0.0.7](../../ROADMAP.md#007-порядок-работ-переприоритизация-2026-09-23),
пункт 2 — «самая дешёвая из отсечек закупки, не зависит ни от чего в продукте»
**Зависимости:** нет жёстких. Экран согласия на обработку данных (техдолг) и SSO пересекаются
в одной точке — первый вход (§10), но друг друга не блокируют

## 1. Обзор

### 1.1 Повод

Корпоративный заказчик требует вход по доменной учётной записи **как условие, а не как удобство**:
служба безопасности не согласует систему, где сотрудники заводят отдельный пароль, а увольнение
человека не закрывает ему доступ автоматически. В конкурентном срезе это отсекающий критерий
закупки, закрытый у StartExam и открытый у нас.

Сегодня входов три: пароль (scrypt, PRD-9), ссылка-приглашение с областью действия и персональная
ссылка рецензента (PRD-52). Ни один не связан с каталогом пользователей заказчика.

### 1.2 Цель

Дать установке возможность принимать вход через внешний провайдер идентификации (IdP) заказчика,
не меняя ролевую модель, не отменяя существующие входы и не создавая второго источника правды
о правах.

### 1.3 Границы

**В охвате:** веб-хост. **Вне охвата:** SCORM-пакет — у него нет входа вовсе: пакет играет внутри
сессии чужой LMS, и участник уже аутентифицирован ею.

### 1.4 Принцип, на котором держится вся спецификация

**IdP отвечает на вопрос «кто это», система отвечает на вопрос «что ему можно».** Роли остаются
в `user_roles` (PRD-13), объектные права — в грантах (PRD-15). SSO не становится источником прав;
он становится источником личности. Нарушение этого принципа даёт два источника правды о доступе
и делает разбор инцидента невозможным.

## 2. Кого это касается

| Кто | Вход после внедрения |
| --- | --- |
| Сотрудник заказчика (автор, разработчик, администратор, менеджер, учащийся из штата) | SSO. Пароль остаётся доступным, пока установка не переведена в режим «только SSO» (§8.2) |
| **Внешний участник** (PRD-28, `is_external`) | Не меняется: у него нет пароля и нет учётной записи в домене; единственный вход — ссылка назначения |
| **Рецензент по гранту** (PRD-52) | Не меняется: персональная ссылка на один тест. Требовать от внешнего эксперта доменную учётную запись — значит отменить сценарий |
| **Конфигурационный суперадмин** (`SUPERADMIN_EMAILS`) | Не меняется: признак вычисляется по адресу и от способа входа не зависит |

## 3. Протоколы

| Протокол | Решение | Обоснование |
| --- | --- | --- |
| **OpenID Connect**, Authorization Code + PKCE | **Основной** | Современный корпоративный стандарт, поддержан Keycloak, ADFS, Azure AD и российскими IdP; discovery-документ снимает половину ручной настройки |
| **SAML 2.0**, Web Browser SSO | **Профиль второй очереди** | Реальность многих корпоративных контуров: у заказчика может стоять только он. Заводится тем же контрактом провайдера, что и OIDC |
| Implicit flow, Resource Owner Password Credentials | **Запрещены** | Первый небезопасен и объявлен устаревшим; второй требует, чтобы пароль домена вводился в наше поле — ровно то, от чего уходим |
| LDAP / Active Directory напрямую | Вне охвата | Требует хранить доменные учётные данные или держать связь с контроллером домена; корпоративная практика — IdP поверх каталога |

**FR-01.** Ядро обращается к внешнему входу только через контракт провайдера: `key`, `version`,
`buildAuthorizationUrl(state)`, `exchangeCallback(params)` → нормализованный профиль личности.
Имя протокола и вендора не встречается нигде, кроме адаптера и конфигурации — так же, как
в реестре eligibility-плагинов (PRD-21) и в контракте прокторинга (PRD-62).

## 4. Связывание личности

Самое ответственное место: ошибка здесь означает, что человек войдёт под чужой учётной записью.

### 4.1 Якорь связи

**FR-02.** Устойчивый якорь — **идентификатор субъекта в IdP** (`sub` для OIDC, `NameID` для
SAML), а не адрес почты: адрес меняется при смене фамилии и переиспользуется после увольнения.
Связь хранится отдельной сущностью `user_identities`: провайдер, субъект, дата связывания,
уникальность по паре (провайдер, субъект).

**FR-03.** Адрес почты — **вторичный якорь, применяемый один раз**, при первом входе, чтобы
связать доменную учётную запись с уже существующей у нас. Основание в коде готово: `users`
хранит зашифрованный адрес и `email_hash` — SHA-256 от приведённого к нижнему регистру адреса
с уникальным индексом, поиск по нему детерминирован (`hashEmail`, `server/utils/crypto.ts`).

**FR-04.** После связывания совпадение по адресу **не проверяется повторно**: сменившийся в IdP
адрес не должен ни отвязывать учётную запись, ни находить чужую.

### 4.2 Правила первого входа

| Ситуация | Поведение |
| --- | --- |
| Субъект уже связан | Вход под связанной учётной записью |
| Субъект не связан, адрес совпал с активной учётной записью | Связывание и вход; в журнал — запись о связывании с указанием провайдера |
| Субъект не связан, адрес совпал с учётной записью **внешнего участника** (`is_external`) | Связывание **запрещено**: внешний участник и сотрудник — разные сущности. Вход отклоняется с внятной причиной |
| Субъект не связан, адреса нет в системе | По политике подготовки учётных записей (§5) |
| Адрес из IdP **не подтверждён** (`email_verified = false`) | Связывание по адресу запрещено: иначе чужой аккаунт получается заявлением произвольного адреса в IdP |

**FR-05.** Связывание по адресу выполняется **только для учётной записи в состоянии `active`**.
Учётная запись `inactive` или с истёкшим `expires_at` в SSO не пускается: отключение сотрудника
не должно обходиться входом через домен.

## 5. Подготовка учётных записей

**FR-06.** Установка выбирает одну из трёх политик; значение по умолчанию — первое.

| Политика | Что делает | Кому подходит |
| --- | --- | --- |
| **Только заведённые** (`strict`) | Вход только тем, у кого учётная запись уже есть. Неизвестный субъект получает отказ с предложением обратиться к администратору | Аттестация с ограниченным кругом: состав участников известен заранее |
| **Создавать учащегося** (`jit_learner`) | Неизвестный субъект получает новую учётную запись с ролью `learner` и без каких-либо грантов | Массовое обучение внутри компании |
| **Создавать по соответствию групп** (`jit_mapped`) | То же, плюс роли выдаются по соответствию групп IdP ролям системы (§6) | Крупная установка с выстроенным каталогом групп |

**FR-07.** Ни при какой политике автоматически не выдаются **объектные права**: владение темами
и тестами, гранты на редактирование, назначение и рецензирование остаются ручными (PRD-15).
Автоматическая выдача прав на содержимое по группе домена — способ незаметно раздать доступ
к банку вопросов.

## 6. Роли

**FR-08.** Соответствие «группа или утверждение IdP → роль системы» задаётся администратором как
таблица правил и применяется **только при политике `jit_mapped`**. Правило описывает: имя
утверждения, ожидаемое значение, выдаваемую роль.

**FR-09.** Синхронизация ролей при каждом входе **настраивается отдельно** и по умолчанию
выключена: включённая, она делает IdP источником правды о ролях и отменяет ручные назначения при
следующем входе. Выключенная — назначает роли один раз при создании.

**FR-10.** Роль `superuser` через соответствие групп не выдаётся **никогда**. Единственные её
источники — `user_roles`, назначенные человеком, и конфигурационный список адресов.

## 7. Сессия и выход

**FR-11.** Успешный вход по SSO **пересоздаёт сессию** (регенерация идентификатора) до записи
в неё сведений о пользователе. Это закрывает вход как последнюю точку известного пункта
технического долга о пересоздании сессии при смене уровня доступа и снимает фиксацию сессии.

**FR-12.** Срок сессии не меняется: 24 часа, как сегодня. Срок жизни токенов IdP на длительность
нашей сессии не влияет — токен нужен один раз, для установления личности.

**FR-13.** Выход из системы завершает нашу сессию и, если провайдер это поддерживает и настройка
включена, перенаправляет на выход у провайдера (RP-initiated logout). Отсутствие поддержки
не должно ломать выход у нас.

**FR-14.** Единый выход по инициативе провайдера (back-channel logout) — **вне первой очереди**,
но точка расширения предусматривается: сессии должны быть завершаемы по идентификатору субъекта.

## 8. Сосуществование с существующими входами

### 8.1 По умолчанию

**FR-15.** Появление SSO не отключает ни один существующий способ входа. Экран входа получает
кнопку провайдера рядом с полями пароля; ссылки назначения и рецензирования работают как прежде.

### 8.2 Режим «только SSO»

**FR-16.** Установка может запретить вход по паролю. Запрет **не распространяется** на:

- внешних участников (у них пароля нет — они входят по ссылке назначения);
- рецензентов по персональной ссылке (PRD-52);
- конфигурационных суперадминов — иначе отказ провайдера запирает систему целиком.

**FR-17.** При включённом режиме «только SSO» восстановление пароля и письмо-приглашение
с паролем не отправляются: предлагать человеку пароль, которым он не сможет войти, — дефект.

## 9. Администрирование и перенос

**FR-18.** Настройка провайдера живёт в интерфейсе администратора, а не в переменных окружения:
адрес discovery-документа или метаданных, идентификатор клиента, секрет, область запроса,
соответствие утверждений, политика подготовки учётных записей, режим «только SSO».

**FR-19.** Секрет клиента хранится зашифрованным, в интерфейс после сохранения не возвращается
(только признак «задан») и **не попадает** ни в снимок публикации, ни в книгу Excel, ни в перенос
теста между установками (PRD-48).

**FR-20.** Предусматривается проверка настройки без выхода из административного экрана: пробный
запрос discovery-документа и разбор полученных ключей с внятным сообщением об ошибке. Настройка,
которую нельзя проверить до первого живого входа, порождает обращения в поддержку.

## 10. Согласие и персональные данные

**FR-21.** Первый вход через SSO **не обходит** сбор согласия на обработку данных: если для
способа входа по паролю согласие требуется, оно требуется и здесь. Отсутствие экрана согласия —
открытый технический долг; SSO его не создаёт и не отменяет, но и не должен становиться дырой,
через которую человек попадает в систему, ничего не подписав.

**FR-22.** Из профиля IdP запрашивается и сохраняется **минимум**: идентификатор субъекта,
адрес почты и отображаемое имя. Должность, подразделение, телефон и фотография не запрашиваются
до появления сценария, который их требует.

## 11. Безопасность

**FR-23.** Обязательны: PKCE (`code_challenge_method=S256`), параметр `state` с проверкой
на возврате, `nonce` в запросе и сверка его в идентификационном токене.

**FR-24.** Подпись идентификационного токена проверяется по ключам провайдера с кешированием и
**обработкой ротации**: неизвестный идентификатор ключа вызывает повторное получение набора
ключей, а не отказ.

**FR-25.** Проверяются издатель, аудитория, срок годности и время выпуска с допуском на
расхождение часов не более минуты.

**FR-26.** Отказ провайдера, недоступность discovery-документа и неверная подпись дают отказ
во входе с записью в журнал. **Деградация «пустить без проверки» запрещена** — это отключение
аутентификации отказом стороннего сервера.

**FR-27.** Журнал входов фиксирует: провайдер, субъект, результат, причину отказа, момент
связывания учётной записи. Персональные данные в журнале — в том же объёме, что и сегодня.

## 12. Вне охвата

- SCORM-пакет (входа не имеет).
- SCIM и любая иная синхронизация каталога пользователей: увольнение закрывает доступ тем, что
  IdP перестаёт пускать, а не тем, что мы удаляем учётную запись.
- Многопровайдерность на одной установке (несколько IdP одновременно) — точка расширения
  заложена контрактом, но первая очередь одна установка равно один провайдер.
- Двухфакторная аутентификация на нашей стороне: это задача IdP.
- LDAP/AD напрямую.

## 13. Открытые вопросы

| ID | Вопрос | Почему важен |
| --- | --- | --- |
| OQ-01 | Какие IdP должны поддерживаться на первой установке и какой протокол у них фактически включён? | От ответа зависит, начинать с OIDC или сразу делать SAML |
| OQ-02 | Политика подготовки учётных записей по умолчанию для нашего сценария аттестации | `strict` безопаснее, но требует предварительной загрузки состава участников |
| OQ-03 | Нужен ли режим «только SSO» на первой очереди | Он ужесточает эксплуатацию: ошибка в настройке запирает всех, кроме суперадминов |
| OQ-04 | Что делать с уже заведёнными паролями при переходе на SSO: гасить, оставлять, помечать устаревшими | Затрагивает PRD-9 и письма-приглашения |
| OQ-05 | Требуется ли соответствие групп IdP **группам системы** (а не только ролям) | Группы участвуют в назначениях; автоматическое членство в группе меняет, кому назначен тест |

## 14. Приёмка

Принимается в браузере на живом провайдере, а не на заглушке.

| Сценарий | Ожидание |
| --- | --- |
| Первый вход известного сотрудника | Учётная запись связана по адресу, роли не изменились, сессия пересоздана |
| Повторный вход после смены адреса в IdP | Вход под той же учётной записью: якорь — субъект, а не адрес |
| Вход неизвестного субъекта при политике `strict` | Отказ с внятной причиной, учётная запись не создана |
| Вход отключённого сотрудника (`inactive`) | Отказ |
| Попытка связать субъект с учётной записью внешнего участника | Отказ |
| Вход внешнего участника по ссылке назначения при включённом режиме «только SSO» | Работает |
| Вход рецензента по персональной ссылке при включённом режиме «только SSO» | Работает |
| Недоступность провайдера | Отказ во входе, не «пустить без проверки»; существующие сессии не рвутся |
| Ротация ключей провайдера | Вход проходит после автоматического обновления набора ключей |
