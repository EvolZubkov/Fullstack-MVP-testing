# PRD-33. Листинг кода в тексте задания

Статус: необходимость подтверждена владельцем продукта 2026-08-01. Требования не собирались,
форма решения не согласована, эскизов нет. Документ фиксирует ПОВОД, фактическое состояние кода
и препятствия, которые обязаны попасть в проектирование, чтобы работа не начиналась с чистого листа.

## 1. Повод

Автор не может показать участнику фрагмент исходного кода. Вопрос «что выведет этот фрагмент» —
базовая механика ИТ-аттестации, и сегодня она недоступна: набранный в поле вопроса листинг
приезжает участнику как обычный абзац с потерянными отступами и подменённой пунктуацией.

Вскрыто при конкурентном анализе (см. [сравнение со StartExam](../../reports/ANALYSIS_STARTEXAM_MATRIX.md),
§4.1): у конкурента «вставка кода» заявлена как средство оформления содержимого задания наряду
с изображениями и формулами LaTeX. У нас разметка текста задания есть — но это подмножество markdown
для форматирования (жирный, курсив, ссылка), и кода в нём нет.

Формулы LaTeX — соседний пробел из того же анализа, но **отдельная задача**: другой движок рендера,
другая аудитория, другая стоимость. В охват этого PRD они не входят.

## 2. Что есть сегодня

Разметка авторского текста живёт в `shared/text/` — одна реализация на веб-хост и на SCORM-пакет
(в пакет попадает через `shared/template/runtime-entry.ts` -> глобал `TBTemplate`).

| Звено | Состояние |
| --- | --- |
| Инлайн-разметка (`renderInlineMarkdown`) | Жирный, курсив, ссылка `[подпись](url)`, автоссылка на URL и e-mail, переносы строк через `<br>`. Блочных тегов не производит |
| Блочная разметка (`renderBlockMarkdown`) | Абзацы `<p>` с полным инлайн-подмножеством внутри |
| Машинный путь (`stripMarkdown`) | Снятие разметки для выгрузок, хеширования и подбора кегля |
| Читательский путь (`renderPlainText`) | Снятие разметки плюс типографика — экран обзора и PDF-отчёт |
| Инлайн-код, блок кода | **Отсутствуют в грамматике полностью** |
| Хранение | Авторский текст лежит в базе как plain text с маркерами; разметка производится на рендере |
| Безопасность | Экранирование выполняется ДО генерации тегов, поэтому набор выходных тегов фиксирован и авторский текст не может внести чужую разметку |

Практическое следствие: листинг, набранный в поле вопроса, теряет ведущие пробелы (они не
значимы для инлайн-рендера), получает пропорциональный шрифт вместо моноширинного, а
типографический проход подменяет в нём символы — см. [§3.1](#31-типографика-разрушает-код).

## 3. Препятствия, которые нельзя обойти

Раздел существует, чтобы проектирование не наступило на них по очереди. Каждый пункт проверен
по коду.

### 3.1 Типографика разрушает код

`shared/text/typography.ts` применяется к каждому текстовому сегменту и делает три вещи, каждая
из которых для кода фатальна:

- прямые кавычки заменяются на «ёлочки»: `printf("hi")` превращается в `printf(«hi»)`;
- дефис между пробелами становится длинным тире: `a - b` превращается в `a — b`;
- короткие русские слова склеиваются со следующим неразрывным пробелом.

Значит, код обязан **миновать типографический проход целиком**. Механизм для этого в модуле уже
есть: ссылки маскируются служебным символом до прохода и подставляются обратно после. Код логично
маскировать тем же способом.

### 3.2 Порядок экранирования и подсветка эмфазы

Эмфаза применяется после экранирования, ко всей строке. В коде это ломает то, что кодом и является:
`*ptr` станет курсивом, `a ** b` — жирным. Код обязан быть изъят из строки ДО `applyEmphasis`, а не
после. Экранирование при этом остаётся обязательным — снимать его нельзя ни при каких условиях.

### 3.3 Инлайн против блока: текст вопроса рендерится в заголовок

Текст вопроса попадает в `<h2 class="tb-scene__qtitle">` (`layouts/question.html`), поэтому
`renderInlineMarkdown` намеренно не производит блочных тегов. `<pre>` внутри `<h2>` — невалидная
разметка, и это не придирка: браузер её перестроит, а раскладка сцены поедет.

Развилка, которую предстоит пройти:

- либо блок кода допускается только там, где рендер блочный (поля контентной страницы), а в вопросе
  разрешён только инлайн-код;
- либо текст вопроса получает блочный контейнер вместо заголовка — а это правка ОБОИХ поставляемых
  шаблонов, их макетов и стилей, плюс совместимость с уже загруженными внешними шаблонами (PRD-3).

Первый путь дешевле и не трогает контракт шаблонов; второй закрывает исходный сценарий («что
выведет фрагмент» требует именно блока). Решение — продуктовое, не техническое.

### 3.4 Автоподбор кегля не рассчитан на моноширинный текст

`shared/template/fit-font.ts` выбирает `--tb-question-fs` и `--tb-answer-fs` по ДЛИНЕ текста в
символах, снятой через `stripMarkdown`. Для листинга эта метрика неверна дважды: моноширинный
символ шире пропорционального, а перенос строки в коде значим и не даёт тексту переливаться.
Без отдельного правила листинг либо вылезет за сцену, либо ужмёт заголовок вопроса до нечитаемого.

### 3.5 Изменение грамматики двигает `content_hash`

`stripMarkdown` участвует в хешировании контента вопроса. Хеш, в свою очередь, пинится в
`test_question_scoring.pinned_content_hash` (PRD-15) и питает индикатор устаревших переопределений
оценки. Если новая грамматика изменит результат `stripMarkdown` для уже существующих текстов,
индикатор загорится на вопросах, которых никто не трогал.

Прецедент решения уже есть: PRD-30 сознательно не включил `order_index` в `content_hash` ровно
по этой причине. Требование к проектированию: **грамматика обязана быть обратно совместимой на
существующих текстах** — символы, которые сегодня ничего не значат, не должны задним числом стать
маркерами кода.

### 3.6 Экран обзора и PDF-отчёт снимают разметку

`renderPlainText` (обзор перед завершением, PDF-отчёт PRD-27) отдаёт голый текст с типографикой.
Для листинга это возвращает нас к §3.1: в отчёте код снова окажется с «ёлочками». Нужно решить,
показывается ли листинг в этих представлениях и в каком виде.

### 3.7 Стили нужны в двух шаблонах и в дизайн-системе

Моноширинный блок требует токенов и правил в компонентном источнике CSS обоих поставляемых
шаблонов (`server/scorm/templates/<id>/styles/theme.css` + `base.css`), откуда генерируется
`styles.css` пакета. Готового `ou-*`-примитива под листинг в дизайн-системе, судя по всему, нет —
проверять по `university-rt.css`, и если его действительно нет, примитив добавляется в ui-kit,
а не подменяется локальным классом.

Отдельно: рантайм печатает часть стилей инлайном, и инлайн перебивает `theme.css` — правило
для листинга нужно закладывать с учётом этого, а не полагаться на каскад.

### 3.8 Обмен через книгу Excel

Импорт и экспорт вопросов (PRD-14) гоняет текст задания через ячейку. Многострочный листинг с
ведущими пробелами обязан пережить круговой рейс без потерь — сегодня это не проверялось,
потому что переносы в тексте задания встречались редко и отступы не были значимы.

## 4. Что предстоит решить

| Вопрос | Почему важен |
| --- | --- |
| Синтаксис: обратные кавычки для инлайна и ограждённый блок, как в markdown, или собственная запись | Обратные кавычки привычны, но сегодня они ничего не значат и уже могут встречаться в текстах — прямой риск §3.5 |
| Где допускается блок кода: только контентная страница или и текст вопроса | Развилка §3.3; во втором случае правятся макеты обоих шаблонов |
| Допускается ли код в вариантах ответа | Вариант ответа — заголовок карточки, там только инлайн |
| Подсветка синтаксиса: нужна ли, и если да — с указанием языка или без | Подсветка тянет в пакет стороннюю библиотеку; сегодня в пакет вендорятся только html2canvas и jsPDF |
| Поведение длинной строки: перенос или горизонтальная прокрутка | На узкой сцене (мобильная адаптация) это разные раскладки |
| Что показывать в обзоре и в PDF-отчёте | §3.6 |
| Как вводится листинг в редакторе: обычное поле или отдельный элемент управления | Вставка кода из среды разработки проходит через `paste-markdown` и `html-to-markdown` — надо понять, что происходит с отступами |
| Копирование листинга участником | Может быть и удобством, и способом списать — вопрос продуктовый |

## 5. Вне охвата

- Формулы LaTeX — соседний пробел, отдельная задача.
- Автопроверка исполняемого кода (компиляция, прогон тестов) — ни у нас, ни у конкурента такого
  нет; настоящий листинг это не заменяет и не требует.
- Открытые задания со свободным ответом — отдельный пробел из того же анализа.
- Медиатека и импорт медиа — существующий будущий PRD.
