## 1. Контекст и постановка задачи

Сейчас в системе две роли — `author` и `learner` (`shared/schema.ts`). Роль `author`
совмещает несовместимые обязанности: производство контента, администрирование
пользователей и групп, назначение тестов, управление шаблонами, просмотр логов и
SCORM-пакетов. Любой автор обладает полным набором административных прав, разделения внутри
роли нет, отдельной фигуры администратора и суперадминистратора не существует.

Это создаёт три бизнес-проблемы:

- невозможно делегировать операционные задачи (назначение тестов, ведение групп) без
  выдачи прав на правку всего контента;
- невозможно ограничить автора его собственными тестами — каждый автор видит и правит
  любой тест;
- нет привилегированной фигуры с гарантированным доступом, задаваемой вне приложения.

Аудит требований архитектуры от 2026-06-07 отмечает раздел 6 «Аутентификация и управление
доступом» как выполненный частично: RBAC присутствует, но без разделения привилегий и
без фильтрации по принадлежности. Настоящий BRD закрывает эту часть требования.

**Цель:** перейти от двухролевой модели к пятиролевой с принципом наименьших привилегий,
разграничением доступа к тестам на уровне объекта и привилегированной учётной записью,
задаваемой в конфигурации.

## 2. Бизнес-цели и метрики

| Цель | Метрика |
| --- | --- |
| Разделение обязанностей по ролям | 0 случаев, когда операционная задача требует прав на правку контента |
| Принцип наименьших привилегий | Каждая роль имеет только права, необходимые для её задач (см. матрицу) |
| Контроль доступа к тестам | Автор правит только свои и разрешённые тесты; менеджер назначает только разрешённые |
| Привилегированный доступ вне приложения | Суперадминистратор задаётся конфигурацией и не назначается через UI |
| Управляемое назначение ролей | Роль «Администратор» назначает только суперадминистратор |
| Безопасная миграция | 0 пользователей теряют доступ к необходимым функциям при переходе |

## 3. Заинтересованные роли (бизнес-уровень)

| Роль | Бизнес-задача |
| --- | --- |
| Суперадминистратор | Гарантированный полный контроль системы, назначение администраторов, аварийный доступ |
| Администратор | Эксплуатация системы: пользователи, группы, доступ к тестам, шаблоны, контент |
| Автор | Производство и сопровождение тестов и банка вопросов |
| Менеджер по обучению | Организация обучения: группы, обучаемые, назначения, контроль результатов |
| Обычный пользователь | Прохождение назначенного обучения и просмотр своих результатов |

Полные определения и состав прав — в [матрице полномочий](./access-control/role-model.md).

## 4. Ключевые решения

### 4.1 Пять ролей и две оси прав

Модель состоит из пяти ролей. Производство контента (Автор) и доставка обучения (Менеджер)
— две независимые оси, объединяемые на уровне Администратора. Суперадминистратор
надстраивается над Администратором и добавляет системную конфигурацию.

### 4.2 Суперадминистратор из конфигурации

Суперадминистратор задаётся переменной окружения (массив адресов), вычисляется в рантайме
и не хранится как назначаемое значение роли. Это гарантирует исключительность (нельзя выдать
или повысить через UI) и наличие гарантированного доступа после развёртывания. Учётные
записи из списка автоматически провижинятся при старте без хранимых ролей. Удаление адреса
из списка немедленно прекращает права суперадмина и не оставляет остаточных привилегий —
это закрывает уязвимость «забыли убрать из конфига, доступ сохранился».

### 4.3 Разграничение доступа к тестам

Вводится владелец теста и явные гранты доступа двух уровней — `edit` (для авторов) и
`assign` (для менеджеров). Доступ выдаёт только администратор. Автор правит свои и
разрешённые на правку тесты; удаляет только свои. Менеджер назначает только тесты,
разрешённые на назначение.

### 4.4 Назначение ролей с потолком

Право назначения роли ограничено потолком: администратор назначает вплоть до Автора и
Менеджера, но не Администратора; роль «Администратор» назначает только суперадминистратор;
менеджер задаёт только роль «Обычный пользователь» при создании.

### 4.5 Единый каталог прав

Разграничение строится на именованном каталоге прав (capabilities) и карте «роль -> права»
в общем слое. Серверная проверка выполняется единым механизмом по требуемому праву, а не
россыпью проверок конкретной роли. Это устраняет дублирование и упрощает изменение модели.

### 4.6 Прохождение тестов по факту назначения

Доступ к прохождению определяется фактом назначения теста, а не ролью: любой пользователь,
которому назначен тест, может его пройти и видеть свои результаты.

### 4.7 Несколько ролей у пользователя

Пользователю можно назначить несколько ролей одновременно (например, Автор и Менеджер по
обучению). Права пользователя — объединение прав всех его ролей. Роли хранятся в связи
«многие-ко-многим», назначаются и отзываются по одной с соблюдением потолка (раздел 4.4).
Это устраняет необходимость заводить отдельные учётные записи для совмещения обязанностей.

## 5. Бизнес-требования

| Код | Требование |
| --- | --- |
| BR-01 | Система поддерживает пять ролей: Суперадминистратор, Администратор, Автор, Менеджер по обучению, Обычный пользователь |
| BR-02 | Каждая роль обладает строго определённым набором прав согласно матрице полномочий |
| BR-03 | Суперадминистратор задаётся в конфигурации (массив адресов) и не назначается через UI |
| BR-04 | Учётные записи суперадминистраторов создаются при старте без хранимых ролей; удаление из конфигурации немедленно прекращает их привилегии |
| BR-05 | Тест имеет владельца; владельца меняет только администратор или суперадминистратор |
| BR-06 | Автор правит, публикует и экспортирует только свои тесты и тесты с грантом `edit`; удаляет только свои |
| BR-07 | Менеджер назначает только тесты с грантом `assign` |
| BR-08 | Гранты доступа к тестам выдаёт и отзывает только администратор или суперадминистратор |
| BR-09 | Роль «Администратор» назначает только суперадминистратор |
| BR-10 | Администратор назначает роли вплоть до Автора и Менеджера; менеджер создаёт только обычных пользователей |
| BR-11 | Любой пользователь с назначенным тестом может пройти его и видеть свои результаты |
| BR-12 | Списки и аналитика фильтруются по области видимости роли |
| BR-13 | Миграция не лишает действующих пользователей необходимого доступа |
| BR-14 | Пользователю можно назначить несколько ролей; его права — объединение прав назначенных ролей |

## 6. Границы

### 6.1 В объёме

- Пять ролей и каталог прав.
- Владелец теста и гранты доступа `edit` / `assign`.
- Суперадминистратор из конфигурации с автопровижинингом.
- Правила назначения ролей с потолком.
- Серверное и клиентское разграничение, миграция данных.

### 6.2 Вне объёма (перспектива)

- Понятие «Организация» и разграничение менеджеров по «своим» пользователям и группам
  (требует отдельной проработки и сущности организации; в фазе 1 видимость общая в рамках
  системы).
- Корпоративная аутентификация и единый вход (LDAPS / Kerberos / OIDC) — относится к плану
  требований архитектуры и отдельному треку (см. PRD-9 и аудит).
- Гранулярность прав ниже уровня домена (правка отдельных полей теста).
- Делегирование выдачи доступа владельцу теста.

## 7. Связь с требованиями архитектуры и ИБ

| Требование аудита | Вклад настоящего трека |
| --- | --- |
| Раздел 6: разделение привилегий | Пять ролей и каталог прав вместо роли-«бога» |

| Раздел 6: персонификация и контроль доступа | Назначение ролей с потолком, суперадминистратор из конфигурации |

Парольная политика, управление сеансами и корпоративная аутентификация остаются в ведении
плана требований архитектуры и не входят в этот трек.

## 8. Риски и допущения

| Риск или допущение | Реакция |
| --- | --- |
| Действующие `author` совмещают роли автора и администратора | Миграция переводит их в Администратора с последующим ручным разбором (см. PRD-13, миграция) |
| Legacy-тесты не имеют владельца (колонки не было) | Бэкфилл владельца на суперадминистратора, далее переназначение администратором |
| Ошибочное сужение прав ломает рабочие сценарии | Поэтапный вывод, приёмочные проверки по матрице до включения жёстких запретов |
| Подмена эффективной роли через конфигурацию | Изменение `SUPERADMIN_EMAILS` доступно только на уровне инфраструктуры, не из приложения |
