## 1. Назначение документа

Документ — единый источник истины по ролям и правам в системе. Он фиксирует:

- состав ролей и их определения;
- каталог именованных прав (capabilities);
- карту «роль -> права»;
- матрицу полномочий по функциональным доменам;
- модель разграничения доступа к тестам (владелец и гранты);
- правила назначения ролей с потолками;
- механизм суперадминистратора из конфигурации;
- сопоставление прав с эндпоинтами API.

Серверный и клиентский код реализуют разграничение строго против этого документа.
Изменение прав начинается с правки этого файла.

## 2. Роли

В системе пять ролей. Они не строго линейные: «Автор» (производство контента) и
«Менеджер по обучению» (доставка обучения) — это два ортогональных набора прав, которые
объединяются на уровне «Администратора».

| Код | Роль | Определение |
| --- | --- | --- |
| SU | Суперадминистратор | Полные исключительные права на все функции и системную конфигурацию. Задаётся в конфигурации, через UI не назначается |
| AD | Администратор | Контент (как Автор), администрирование (как Менеджер, полное), управление шаблонами, доступом к тестам, логами и SCORM-пакетами |
| AU | Автор | Темы, вопросы, тесты: создание, изменение, публикация, экспорт. Правит только свои тесты и те, к которым выдан доступ |
| MG | Менеджер по обучению | Создание групп и обычных пользователей, назначение тестов, доступ к результатам. Назначает только тесты, к которым выдан доступ |
| US | Обычный пользователь | Прохождение назначенных тестов, просмотр собственных результатов и истории |

Базовые принципы:

- пользователь может иметь несколько ролей одновременно (например, Автор и Менеджер по
  обучению); его права — объединение прав всех назначенных ролей плюс права
  суперадминистратора, если он задан в конфигурации;
- права набора ролей гейтят само действие (что в принципе разрешено пользователю);
- владелец и гранты гейтят конкретный объект (к какому тесту применимо действие);
- статус учётной записи (`pending` / `active` / `inactive`) действует поверх ролей и
  блокирует вход независимо от прав.

Роли хранятся в связи «многие-ко-многим» (`user_roles`). Значение «Суперадминистратор» в
составе хранимых ролей не используется и вычисляется из конфигурации (раздел 8).

## 6. Разграничение доступа к тестам

### 6.1 Владелец теста

Каждый тест имеет владельца (`tests.ownerId`). Владелец устанавливается при создании
(создатель теста) и меняется только администратором или суперадминистратором.

- Владелец-Автор может править, публиковать, экспортировать и удалять свой тест.
- Удаление и архивирование доступны только владельцу (и AD/SU), но не держателям гранта
  `edit`.

### 6.2 Гранты доступа

Доступ к чужому тесту выдаётся явным грантом в таблице `test_access_grants`.

| Уровень гранта | Кому адресован | Что разрешает |
| --- | --- | --- |
| `edit` | Автор | Правка, оформление, показатели, шкалы, публикация, экспорт SCORM теста |
| `assign` | Менеджер | Назначение теста пользователям и группам, просмотр его результатов |

На пару «тест + пользователь» допускается один грант. Уровень `edit` для целей проверки
области покрывает и `assign`, но фактическое действие всё равно ограничено правами роли
держателя (Автор не назначает, Менеджер не правит).

### 6.3 Кто выдаёт доступ

Гранты доступа и смену владельца выполняют только Администратор и Суперадминистратор
(права `tests.access.grant`, `tests.owner.change`). Владелец-Автор самостоятельно
соавторов не добавляет.

### 6.4 Алгоритм разрешения доступа

Роль определяет допустимость действия, владелец и грант — допустимость для конкретного
теста.

Резолюция работает с набором ролей пользователя: проверяется наличие нужной роли
(`hasRole`), а не равенство единственной роли.

```text
roles(u)          := effective roles of u from user_roles
hasRole(u, R)     := R in roles(u)
hasSuper(u)       := email(u) in SUPERADMIN_EMAILS
isAdminOrSuper(u) := hasSuper(u) OR hasRole(u, AD)

canReadTest(u, t):
  isAdminOrSuper(u)                                           -> true
  hasRole(u, AU) AND (t.ownerId == u.id OR grant(t, u, edit)) -> true
  hasRole(u, MG) AND grant(t, u, assign|edit)                 -> true
  assignedToUser(t, u)                                        -> true
  else                                                        -> false

canEditTest(u, t):
  isAdminOrSuper(u)                                           -> true
  hasRole(u, AU) AND (t.ownerId == u.id OR grant(t, u, edit)) -> true
  else                                                        -> false

canDeleteTest(u, t):
  isAdminOrSuper(u)                                           -> true
  hasRole(u, AU) AND t.ownerId == u.id                        -> true
  else                                                        -> false

canPublishTest(u, t)  := canEditTest(u, t)
canExportScorm(u, t)  := canEditTest(u, t)

canAssignTest(u, t):
  isAdminOrSuper(u)                                           -> true
  hasRole(u, MG) AND grant(t, u, assign|edit)                 -> true
  else                                                        -> false

canReadTestAnalytics(u, t):
  isAdminOrSuper(u)                                           -> true
  hasRole(u, AU) AND canEditTest(u, t)                        -> true
  hasRole(u, MG) AND canAssignTest(u, t)                      -> true
  else                                                        -> false

canGrantAccess(u, t)  := isAdminOrSuper(u)
canChangeOwner(u, t)  := isAdminOrSuper(u)
```

Списки тестов фильтруются по объединению областей всех ролей пользователя: владение и
гранты `edit` (по роли Автора), гранты `assign` (по роли Менеджера), все тесты (по роли
Администратора или суперадминистратору), назначенные тесты (для прохождения). Пользователь
с ролями Автор и Менеджер видит объединение этих областей.

## 7. Состав и назначение ролей

Пользователь обладает набором ролей. Роли назначаются и отзываются по одной; права
пользователя — объединение прав всех его ролей. Управление каждой ролью (выдача или отзыв)
ограничено потолком назначающего.

| Назначающий | Может назначать и отзывать роли | Не может |
| --- | --- | --- |
| Суперадминистратор | Администратор, Автор, Менеджер, Обычный пользователь | Суперадминистратор (только из конфигурации) |
| Администратор | Автор, Менеджер, Обычный пользователь | Администратор, Суперадминистратор |
| Менеджер по обучению | Обычный пользователь (только при создании) | Все остальные |
| Автор, Обычный пользователь | — | Все |

Дополнительные правила:

- роль «Суперадминистратор» через UI не назначается никогда;
- Администратор не может изменять состав ролей или понижать учётную запись
  Суперадминистратора;
- Менеджер задаёт роль только в момент создания пользователя и только «Обычный
  пользователь»; изменение состава ролей существующих пользователей Менеджер не выполняет;
- управление конкретной ролью требует полномочий над ней по потолку: например, отозвать
  роль «Администратор» может только Суперадминистратор;
- набор ролей может быть любой комбинацией (например, Автор и Менеджер по обучению);
  «Обычный пользователь» как отдельная роль избыточен, если у пользователя уже есть любая
  иная роль (прохождение назначенных тестов доступно всем — см. раздел 5 и
  [PRD-13](../prd-13/role-based-access-control.md), FR-23).

Контроль выдачи реализуется через множество назначаемых ролей субъекта и сверку изменений
набора: при правке ролей пользователя сервер вычисляет добавленные и снятые роли и сверяет
каждую из них с этим множеством. UI показывает только назначаемые субъекту роли, но сервер
остаётся источником истины и повторяет проверку.

```text
assignableRoles(actor):
  hasSuper(actor)     -> { AD, AU, MG, US }
  hasRole(actor, AD)  -> { AU, MG, US }                 // без AD
  hasRole(actor, MG)  -> { US } (только при создании пользователя)
  else                -> { }

applyRoleChange(actor, target, requestedRoles):
  if isSuper(target) AND NOT hasSuper(actor)  -> reject 403   // суперадмина правит только SU
  added   := requestedRoles \ currentRoles(target)
  removed := currentRoles(target) \ requestedRoles
  for r in (added UNION removed):
    if r not in assignableRoles(actor)        -> reject 403
  commit
```

Следствие: роль «Администратор» входит в `assignableRoles` только у суперадминистратора,
поэтому выдать или снять её может только он. Значение «Суперадминистратор» в запросе
невозможно — его нет в перечислении ролей `user_roles`.

## 8. Суперадминистратор из конфигурации

- Список суперадминистраторов задаётся переменной окружения `SUPERADMIN_EMAILS` (массив
  адресов через запятую).
- Права суперадминистратора вычисляются в рантайме на каждый запрос: пользователь, чей
  email входит в `SUPERADMIN_EMAILS`, получает права SU независимо от своего набора ролей в
  БД. Статус не кэшируется в сессии, поэтому правка конфигурации действует немедленно.
- При старте приложения для каждого адреса из списка выполняется автопровижининг: учётная
  запись создаётся, если отсутствует, без назначенных ролей (`user_roles` пуст); права SU
  действуют только по совпадению email. Существующим учётным записям автопровижининг роли
  не добавляет.
- Суперадминистратор не хранится как назначаемая роль в `user_roles`, поэтому права SU
  нельзя выдать или отозвать через UI — только правкой конфигурации.
- Исключение учётной записи из `SUPERADMIN_EMAILS` немедленно прекращает права SU; у
  учётной записи остаётся только то, что было явно назначено в `user_roles` (у
  автопровиженной — ничего, доступ сводится к собственному профилю). Это исключает «тихого»
  остаточного администратора после удаления из конфигурации.
- Назначение суперадмину хранимой роли — отдельное журналируемое действие по обычным
  правилам (раздел 7); оно не отменяет принципа: удаление из конфигурации снимает именно
  привилегии суперадмина.

## 10. Глоссарий

- Набор ролей — множество ролей пользователя из `user_roles`; права пользователя —
  объединение прав всех ролей набора плюс права суперадминистратора, если он задан в
  конфигурации.
- Эффективный набор прав — итоговое множество прав пользователя, вычисленное как
  объединение по набору ролей.
- Область (scope) — дополнительная проверка применимости действия к конкретному тесту по
  владельцу или гранту.
- Грант — запись в `test_access_grants`, дающая пользователю доступ уровня `edit` или
  `assign` к конкретному тесту.
- Потолок назначения — максимальная роль, которую данный субъект вправе назначить другому.
