## 1. Принципы плана

- Источник истины по правам — [role-model.md](./role-model.md); код реализует его.
- Сначала чистый общий слой прав (без БД и сети), затем данные, затем сервер, затем клиент.
- Разграничение включается по доменам с приёмочной проверкой, чтобы не потерять доступ.
- Серверная проверка — источник истины; клиентские проверки только скрывают недоступное.
- Поле `users.role` живёт до полного перехода на `user_roles`, затем удаляется.

## 3. Последовательность и зависимости

- Линейный костяк: Фаза 0 -> 1 -> 2 -> 3 -> 4 -> 5.
- T-04 зависит от T-01, T-02, T-03.
- T-15, T-16 зависят от T-05, T-06.
- T-18, T-19 зависят от T-15, T-16.
- T-22 зависит от T-03 и T-13.
- T-25 зависит от T-13 (сервер отдаёт роли и права).
- T-10 (удаление `users.role`) выполняется последним, после Фаз 3 и 4 и приёмки.
- Внутри Фазы 3 домены можно вести параллельно, контролируя каждый приёмкой.

## 5. Риски и меры

| Риск | Мера |
| --- | --- |
| Потеря доступа при ужесточении | Поэтапное включение по доменам, приёмка по матрице до перехода |
| Двойной источник истины ролей | `users.role` удаляется сразу после перехода (T-10) |
| Ошибочный потолок назначения | Серверная проверка diff + `assignableRoles`, тесты AC-07 |
| Кэширование статуса суперадмина | Статус вычисляется на каждый запрос, не хранится в сессии (T-13) |
| Осиротевшие тесты после миграции | Бэкфилл владельца на суперадмина, переназначение администратором |

## 6. Готовность к старту

После согласования этого плана начинаю с Фазы 0 (общий слой прав и golden-тесты) — она не
затрагивает работающий код и БД, поэтому безопасна как первый шаг. Каждую фазу закрываю
приёмкой по соответствующим критериям PRD-13 и согласовываю переход к следующей.
