## 1. Обзор

### 1.1 Контекст

PRD-1 вводит единую платформу шаблонов с исполнением только в браузере, авторский UX и
встроенные шаблоны.
PRD-3 добавляет административный жизненный цикл библиотеки шаблонов: загрузку, проверку,
активацию, деактивацию, обновление, удаление и экспорт стартового ZIP.

Формат шаблона не определяется в PRD-3. Источник истины:
[платформа SCORM-шаблонов](../spec-template-platform.md). Отдельной механики для загружаемых
шаблонов не создаётся.

### 1.2 Цели и метрики

| Цель | Метрика |
| --- | --- |
| Внешний шаблон не ломает экспорт | 0 активированных шаблонов без пройденной smoke-проверки |
| Разработчик может стартовать без доступа к системе | ZIP встроенного шаблона валиден как стартовый шаблон |
| Администратор видит фактическое поведение | 100% загружаемых шаблонов имеют живой предпросмотр на `manifest.preview.demoData` до активации |
| SCORM остаётся воспроизводимым | 100% ресурсов шаблона локальны внутри ZIP |

## 2. Пользователи и роли

### 2.1 Администратор

Загружает, валидирует, активирует, деактивирует, обновляет и экспортирует шаблоны. Не обязан
разрабатывать HTML/CSS/JS, но должен видеть результат smoke-проверки и живой предпросмотр.

### 2.2 Разработчик шаблона

Создаёт ZIP согласно [платформе SCORM-шаблонов](../spec-template-platform.md). Может использовать
HTML, CSS и браузерный `template.js`, но не серверный код и не внешние CDN.

### 2.3 Автор теста

Видит активные шаблоны в галерее и настраивает параметры. Не видит неактивные и не прошедшие
валидацию шаблоны.

## 3. Функциональные требования

### 3.1 Загрузка шаблона

Основной поток:

1. Администратор открывает `/author/templates` (страница доступна роли `author`).
2. Нажимает **"Загрузить шаблон"**.
3. Выбирает ZIP.
4. Система выполняет структурную валидацию.
5. Если структурная валидация успешна, система запускает браузерную smoke-проверку на
   `manifest.preview.demoData`.
6. Администратор видит результаты валидации и smoke-проверки.
7. Если блокирующие ошибки отсутствуют, шаблон можно активировать.
8. Активированный шаблон появляется у авторов.

ZIP с блокирующими ошибками не может быть активирован.

### 3.2 Таблица шаблонов

| Столбец | Описание |
| --- | --- |
| Предпросмотр | `assets.preview` и живой preview по `manifest.preview.demoData` |
| Название | `manifest.name` |
| ID | `manifest.id` |
| Версия | `manifest.version` |
| API | `manifest.templateApiVersion` |
| Тип | Встроенный / Загруженный |
| Статус | Черновик / Активный / Неактивный / Невалидный |
| Валидация | Пройдена / Предупреждения / Провалена |
| Используется | Количество тестов с `design_settings_json.templateId` |
| Обновлён | Дата обновления |
| Действия | Детали / Живой предпросмотр / Экспорт ZIP / Активировать / Деактивировать / Обновить / Удалить |

### 3.3 Панель деталей

Показывает:

- JSON манифеста в режиме readonly;
- список макетов;
- проверку обязательных элементов оболочки и действий;
- проверку обязательных слотов вопросов;
- параметры с типами, группами и значениями по умолчанию;
- возможности шаблона;
- системные страницы;
- статус ресурсов;
- лог smoke-проверки;
- предупреждения.

### 3.4 Живой предпросмотр на демонстрационном наборе данных

После загрузки система предоставляет живой предпросмотр на демонстрационном наборе данных,
объявленном в `manifest.preview.demoData` по контракту технической спецификации.

**Реализация.** Предпросмотр и проверка живут в одном окне (`/author/templates` ->
карточка -> «Предпросмотр и проверка»). Слева — список экранов по **разделам шаблона**:
виды страниц из PRD-1 §4.3 (вводные / учебные / вопросы / итог раздела) плюс системные
поверхности (экран результатов §8.3, системные экраны §5.4) со статус-точкой проверки на
каждом экране. Список покрывает **каждый объявленный контентный вариант** из
`manifest.contentTemplates` (kind `intro` / `info` / `summary`), а не только варианты,
перечисленные автором в `manifest.preview.routes`: записи `preview.routes` задают
демо-привязки и подписи, а любой объявленный вариант, на который нет ссылки в routes,
**дополняется** в список (`buildScreenInputs`), чтобы он тоже рендерился и проходил
smoke-проверку. Каждому экрану присваивается уникальный `id` (ключ варианта при нескольких
вариантах одного раздела), чтобы варианты одного `route` не сливались. Список
**адаптивный**: тип с одним вариантом отрисовки показывается сразу как экран
(«Раздел -> экран», два уровня); сворачиваемый уровень «тип -> варианты отрисовки»
появляется ТОЛЬКО когда у типа 2+ варианта (напр. «Введение» / «Введение 2», либо
«Один вариант» -> «Радио-список»/«Карточки»).

Справа — живой рендер выбранного экрана **тем же** унифицированным рендерером
`renderScreenInto` (`shared/template/render-screen`), что и оба рантайма (паритет PRD-12);
шаблонный CSS изолируется в Shadow DOM. Для `content.summary` («Итог раздела») в `result.*`
подаётся результат **раздела** (§8.2 платформы), который шаблон может показать в т.ч.
кольцевой диаграммой (`core.ringChart`). Файлы для рендера и проверки браузер забирает
через `GET /api/admin/templates/:id/smoke-bundle` (manifest + demo + layouts + css +
`template.js`). Отдельный iframe `preview.html` (как во вкладке «Оформление») здесь не
используется — загруженный шаблон может не содержать `preview.html`.

Кнопка «Активировать» в окне доступна, только когда проверка пройдена и шаблон ещё не
активен; для уже активного шаблона показывается неактивное состояние «Активирован» и
вердикт «Шаблон активен».

Демонстрационный набор данных должен покрывать:

- стартовую страницу;
- `content.intro`;
- `content.info`;
- `question.single`;
- `question.multiple`;
- `question.matching`;
- `question.ranking`;
- `content.summary`;
- результаты;
- `system.locked`, если объявлен;
- навигацию по темам, если объявлена;
- активный прогресс;
- кнопки навигации и действий;
- загрузку `template.js`.

## 4. Валидация

Полный список проверок и обязательных слотов определён в
[платформе SCORM-шаблонов](../spec-template-platform.md). PRD-3 задаёт административное поведение:
какие ошибки блокируют активацию, как показываются результаты и когда запускается smoke-проверка.

### 4.1 Блокирующие ошибки структурной валидации

Шаблон отклоняется, если:

- ZIP повреждён или не является ZIP;
- отсутствует `manifest.json`;
- `manifest.json` невалидный JSON;
- отсутствуют обязательные поля `id`, `name`, `version`, `templateApiVersion`;
- `templateApiVersion` не поддерживается Core;
- `manifest.id` не соответствует `^[a-z0-9-]+$`;
- шаблон с таким ID уже существует при создании;
- отсутствуют referenced files;
- ресурсы содержат внешние URL/CDN;
- макет содержит невалидный DSL;
- `manifest.capabilities`, `manifest.systemPages` или `manifest.params` невалидны;
- поле варианта объявляет неизвестный тип либо несовместимые с типом атрибуты (PRD-22);
- ZIP превышает лимит размера.

Блокирующими являются только нарушения целостности пакета и безопасности: с ними шаблон
нечитаем или небезопасен, и подставить вместо него нечего.

**Отсутствие макета или слота НЕ блокирует активацию.** Экран, который шаблон не объявляет или
объявляет непригодно, рендерится из стандартного шаблона с предупреждением в UI (NFR-06,
PRD-1 §4.3.2). Это касается и оболочки, и макетов страниц, и слотов вопроса, и `page-content`.

Конкретные слоты оболочки и страниц не дублируются в PRD-3 и проверяются валидатором по
технической спецификации.

### 4.2 Предупреждения

Не блокируют активацию, но показываются:

- неиспользуемые параметры;
- неиспользуемые ресурсы;
- отсутствующий макет или слот — с указанием экрана, который будет отрисован из стандартного
  шаблона («Используется вариант из стандартного шаблона», PRD-1 §4.3.2);
- предупреждения консоли в smoke-проверке;
- объявленная возможность с резервным рендерером Core.

### 4.3 Блокирующие ошибки браузерной проверки работоспособности

Целевой контракт — проверка блокирует активацию, если:

- есть необработанная runtime-ошибка;
- оболочка не загрузилась;
- `next`, `answer-submit`, `test-finish` не привязаны к обработчикам;
- стандартные ответы не сохраняются в состояние Core;
- страница результатов не открывается;
- `template.js` ломает Core runtime;
- правила шаблона падают при парсинге или исполнении.

**Реализация (`shared/template/smoke-runner`).** Движок проходит по экранам из
`buildScreenInputs` (системные экраны из `manifest.preview.routes[]` плюс каждый
объявленный контентный вариант `intro`/`info`/`summary` из `contentTemplates`),
рендерит каждый экран через общий `renderScreenInto` в изолированном контейнере и
помечает экран проваленным (`fail`) при:

- необработанном исключении рендера;
- пустом результате рендера;
- ошибке `console.error` во время рендера.

Отсутствие слота экран не проваливает: он даёт предупреждение и fallback на стандартный шаблон
(§4.1, NFR-06). Это относится и к слотам вопроса (`question-text`, `question-interaction`), и к
`page-content` контентных страниц.

`console.warn` даёт неблокирующее предупреждение (`warn`). Дополнительно: `template.js`
проверяется **только компиляцией** (`new Function(src)`, без исполнения — NFR-02).
Проверки привязки обработчиков `next/answer-submit/
test-finish` и сохранения ответов в Core — целевой контракт для фазы расширенных
интерактивов; текущий движок их не выполняет (встроенный `default` рендерит экраны
по-экранно, действия Core навешивает делегированием, см. [PRD-12](../prd-12/web-runtime-parity.md)).

## 5. Управление жизненным циклом

### 5.1 Статусы

```text
draft     загружен, но ещё не активирован
active    видим авторам
inactive  скрыт от авторов
invalid   не прошёл валидацию после обновления или ручной перепроверки
```

### 5.2 Активация

Доступна только если:

- структурная валидация пройдена;
- браузерная smoke-проверка пройдена;
- блокирующие ошибки отсутствуют.

> **PRD-22 (согласован, внедряется поэтапно).** Типы полей вариантов проверяются и при
> ЗАГРУЗКЕ, и при АКТИВАЦИИ: шаблон с неизвестным типом активировать нельзя. Ранее
> установленный шаблон, переставший соответствовать контракту после обновления системы,
> продолжает работать, но получает статус `invalid` с указанием варианта и поля; автору теста
> поле неизвестного типа показывается как диагностика, а не подменяется другим контролом.

### 5.3 Деактивация

При деактивации:

1. Система показывает количество тестов, использующих шаблон.
2. После подтверждения `templates.is_active = false`.
3. Тесты с этим `templateId` переключаются на `default`.
4. Старые параметры сохраняются в `design_settings_json.params`.
5. Автор при открытии вкладки "Оформление" видит баннер:

```text
Шаблон "{name}" был деактивирован. Выбран шаблон по умолчанию. Совместимые параметры сохранены.
```

Операция выполняется транзакционно.

### 5.4 Удаление

Удалить можно только загруженный шаблон, если:

- `is_active = false`;
- шаблон не используется тестами;
- нет активных закреплённых ссылок в будущей enterprise-модели.

### 5.5 Обновление

Обновление через `PUT /api/admin/templates/:id/update`:

- ID должен совпадать;
- `version` должен измениться или администратор подтверждает повторную загрузку той же версии;
- выполняются структурная валидация и браузерная smoke-проверка;
- при успехе файлы заменяются;
- `templateVersion` новых экспортов использует обновлённую версию.

MVP не хранит все старые версии файлов. Закрепление версий остаётся будущим enterprise-режимом.

### 5.6 Параметры при смене/обновлении

MVP-правила:

- совпали `key` и `type` -> значение переносится;
- старый ключ отсутствует -> значение игнорируется/удаляется;
- новый ключ с `default` -> ставится `default`;
- новый ключ без `default` -> автор должен заполнить значение.

UI показывает отчёт о переносе параметров.

### 5.7 Стартовая проверка целостности

При запуске сервера выполняется реконсиляция реестра, чтобы битый или
осиротевший шаблон не мог оказаться активным на проде (`reconcileTemplates`,
`server/template-registry.ts`):

- шипуемые встроенные (`BUILTIN_IDS`, сейчас только `default`) валидируются и
  апсертятся отдельно (`syncBuiltinTemplates`) и здесь пропускаются;
- **осиротевшие встроенные** — id, бывшие встроенными в прежнем билде и больше не
  шипуемые (напр. `corporate`/`minimal`), без каталога на диске — это фантомные
  системные строки: они **удаляются**, а зависимые тесты предварительно переводятся
  на `default` (транзакционно, как каскад деактивации §5.3);
- **загруженные** шаблоны, чьи файлы пропали или не проходят ту же структурную
  валидацию, что и при загрузке, переводятся в `status = 'invalid'`,
  `is_active = false` (не удаляются — это данные автора; удаление только через UI).

Валидные шаблоны автоматически не активируются и не деактивируются — починенный
шаблон автор включает вручную через UI (это заново запускает валидацию и проверку
работоспособности).

**Оптимизация.** Чтобы не перечитывать и не перепроверять файлы каждый запуск,
хранится дешёвый отпечаток источника `source_fingerprint` — SHA-1 по списку
`путь:размер:mtime` всех файлов каталога (только `stat`, без чтения содержимого).
Если отпечаток не изменился с прошлой реконсиляции, шаблон пропускается без
повторной валидации. Сбой реконсиляции не блокирует запуск приложения: ошибка
логируется, сервер поднимается (boot-устойчивость).

## 6. Модель данных

PRD-3 расширяет общий реестр `templates` административными полями жизненного цикла.

Фактическая схема (`shared/schema.ts`, миграция `migrations/014_prd3_template_lifecycle.sql`).
В деплое схема приводится к `shared/schema.ts` через `drizzle-kit push` (см.
`docker/scripts/deploy.sh`); нумерованные SQL-файлы — ручной/исторический след:

```sql
CREATE TABLE templates (
  id                   text PRIMARY KEY,
  name                 text NOT NULL,
  description          text,
  version              text NOT NULL,
  template_api_version text NOT NULL DEFAULT '1.0',
  is_builtin           boolean NOT NULL DEFAULT false,
  is_active            boolean NOT NULL DEFAULT true,   -- author-facing visibility
  status               text NOT NULL DEFAULT 'active'   -- admin lifecycle FSM
                         CHECK (status IN ('draft', 'active', 'inactive', 'invalid')),
  source_type          text NOT NULL DEFAULT 'builtin'
                         CHECK (source_type IN ('builtin', 'uploaded')),
  source_path          text,            -- on-disk root (built-in dir / uploads/templates/<id>)
  manifest             jsonb NOT NULL,
  preview_path         text,            -- зарезервировано; превью сейчас берётся из manifest.assets.preview
  validation_json      jsonb,
  smoke_test_json      jsonb,
  source_fingerprint   text,            -- hash(file path/size/mtime); skip-key для стартовой реконсиляции
  installed_at         timestamp NOT NULL DEFAULT now(),
  created_at           timestamp NOT NULL DEFAULT now(),
  updated_at           timestamp NOT NULL DEFAULT now()
);
```

`source_type = 'builtin'` и `source_type = 'uploaded'` обслуживаются через единый
API реестра шаблонов (NFR-07). Колоночные `default` подобраны под бэкфилл встроенных
(active/builtin); поток загрузки явно ставит `status = 'draft'`, `is_active = false`.
Колонка `preview_path` зарезервирована и пока не заполняется — миниатюра отдаётся из
`manifest.assets.preview` эндпоинтом `GET /:id/preview-image`.

## 7. API

```text
GET /api/admin/templates
```

Список всех шаблонов.

```text
POST /api/admin/templates
```

Загрузка ZIP. Возвращает созданную запись шаблона, статус валидации и статус smoke-проверки.

```text
GET /api/admin/templates/:id
```

Детали: манифест, валидация, smoke-проверка, использование.

```text
PUT    /api/admin/templates/:id/activate
PUT    /api/admin/templates/:id/deactivate
DELETE /api/admin/templates/:id
PUT    /api/admin/templates/:id/update
GET    /api/admin/templates/:id/export
POST   /api/admin/templates/:id/validate
GET    /api/admin/templates/:id/smoke-bundle
POST   /api/admin/templates/:id/smoke-test
GET    /api/admin/templates/:id/preview-image
```

`GET /export` доступен для встроенных и загруженных шаблонов. Экспорт встроенного шаблона должен
возвращать ZIP, валидный как стартовый шаблон.

Все маршруты под `requireAuthor`. Дополнительно к базовому набору реализованы:

- `GET /:id/smoke-bundle` — файлы, нужные браузеру для рендера экранов и проверки
  работоспособности: `{ manifest, demo, layouts (без shell), css, templateJs?, rulesJson? }`.
  Сервер только читает файлы пакета, не исполняет их (NFR-02).
- `POST /:id/smoke-test` — приём отчёта, который сформировал **браузер** (`runSmokeChecks`);
  сервер валидирует форму отчёта, сохраняет в `smoke_test_json` и далее гейтит активацию
  по `ok` (NFR-01). Сервер не запускает проверку сам.
- `GET /:id/preview-image` — стрим `manifest.assets.preview` для карточек реестра
  (путь строго внутри корня шаблона).

## 8. Безопасность и ограничения

| Ограничение | Решение |
| --- | --- |
| Серверное исполнение | Запрещено. Сервер не исполняет JS/HTML шаблона |
| Внешние URL | Запрещены в ресурсах, макетах, скриптах и стилях, на которые ссылается манифест |
| Сырая HTML-интерполяция | Не поддерживается рендерером шаблонов |
| JS шаблона | Разрешён только как браузерный `template.js` внутри SCORM |
| SCORM API | Поддерживаемый путь только через `TestBuilder.scorm` |
| Внутренности Core | Не являются поддерживаемым API |
| Размер ZIP | Лимит задаётся конфигурацией, по умолчанию 20 МБ |

## 9. Нефункциональные требования

| ID | Требование |
| --- | --- |
| NFR-01 | Загруженный шаблон нельзя активировать без пройденной структурной валидации и smoke-проверки |
| NFR-02 | Валидация не исполняет серверный код шаблона |
| NFR-03 | Smoke-проверка выполняется в изолированном контексте браузера |
| NFR-04 | Деактивация и переключение тестов на `default` выполняются транзакционно |
| NFR-05 | В SCORM ZIP попадает выбранный шаблон плюс резервные макеты и стили стандартного шаблона для системных экранов, которые выбранный шаблон не объявляет |
| NFR-06 | Резервное поведение runtime — fallback на стандартный шаблон с предупреждением в UI (PRD-1 §4.3.2), а не блокировка и не экран ошибки Core |
| NFR-07 | Встроенные и загруженные шаблоны используют один реестр шаблонов |

## 11. Решённые вопросы

| Вопрос | Решение |
| --- | --- |
| Внешние шаблоны используют EJS? | Нет |
| Можно ли использовать JS? | Да, только браузерный `template.js` |
| Разрешены CDN? | Нет, все ресурсы локальны |
| Нужно ли класть резервный default-шаблон в SCORM ZIP? | Не целиком. В пакет добавляются только макеты и стили стандартного шаблона для системных экранов, которые выбранный шаблон не объявляет (NFR-05) |
| Нужна ли отдельная механика для встроенных/загруженных шаблонов? | Нет, только разные адаптеры источников |
| Должен ли встроенный шаблон экспортироваться как ZIP? | Да, как стартовый шаблон |
