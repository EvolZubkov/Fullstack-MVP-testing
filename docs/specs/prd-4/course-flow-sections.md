# PRD-4: Гибкий поток прохождения, разделы и переходы SCORM-пакетов

**Статус:** Реализовано (2026-05-29). Правка 2026-07-05: графовый режим `section_graph` и движок
правил сняты (вне охвата — BRD BR-03); логика теста задаётся сценарием (`flowPolicy`).  
**Связанные документы:** [BRD](../brd-scorm-enhancements.md),
[PRD-1](../prd-1/templates-content-pages.md), [PRD-2](../prd-2/result-variables.md),
[PRD-6](../prd-6/retake-cooldown-gate.md), [PRD-8](../prd-8/section-router-flow.md),
[Платформа SCORM-шаблонов](../spec-template-platform.md)  
**Этап BRD:** BR-06, Этап 4  
**Зависимости:** шаблонная платформа и контентные страницы из PRD-1; retake gate из PRD-6
использует границу внутреннего старта попытки

## 1. Обзор

### 1.1 Контекст

Текущий SCORM runtime использует разделы как источник выборки вопросов и как единицу финального
расчёта, но прохождение остаётся плоским: выбранные вопросы всех разделов могут перемешиваться в
общий список. Референс Storyline требует другой модели: разделы имеют стартовые страницы,
собственный набор вопросов, страницу результата и управляемые переходы к другим разделам или
служебным экранам.

PRD-4 вводит общий движок прохождения `courseFlow`, который поддерживает старое поведение и новые
Storyline-подобные сценарии как разные политики одного Core runtime.

### 1.2 Цель

Добавить гибкий поток прохождения:

1. сохранить текущий плоский режим как `legacy_flat`;
2. добавить последовательный секционный режим `section_linear`;
3. выделить router-режим `section_router`, где обучающийся выбирает разделы на общей странице и
   возвращается на неё после каждого раздела;
4. унифицировать адаптивное прохождение по разделам как `adaptive_by_section`;
5. рассчитывать и публиковать результаты раздела до показа страницы `content.summary`.

### 1.3 Метрики успеха

| Цель | Метрика |
| --- | --- |
| Старые тесты не ломаются | 100% существующих SCORM smoke/golden-тестов проходят в `legacy_flat` |
| Авторы используют секционный flow | Доля новых тестов с `section_linear` или `section_router` >= 20% через 3 месяца |
| Переходы диагностируемы | 100% переходов Core пишут принятое решение в runtime diagnostics |
| Восстановление стабильно | Ошибки восстановления секционного состояния < 1% запусков SCORM |

## 2. Пользователи

### 2.1 Автор теста

Выбирает режим прохождения, настраивает порядок разделов, контентные страницы и условия переходов.
Не обязан писать JavaScript.

### 2.2 Методолог / дизайнер курса

Проектирует сценарий сертификации: старт раздела, набор вопросов, результат раздела, повтор,
блокировку, переход к следующему разделу или финальным результатам.

### 2.3 Разработчик шаблона

Получает публичный контекст раздела, результатов раздела и состояния навигации. Отвечает только за
представление, а не за расчёт и принятие бизнес-решений.

## 3. Ключевые понятия

### 3.1.0 Модель «mode × flowMode»

`flowPolicy` использует двумерную ортогональную модель: режим выдачи вопросов
(`mode`) и сценарий навигации (`flowMode`) задаются независимо.

```text
flowPolicy = {
  mode:      "standard" | "adaptive",       // режим выдачи вопросов
  flowMode:  "linear_flat" | "linear_by_topics" | "router_by_topics",  // сценарий навигации
  ...остальные поля (см. §3.1.1)
}
```

Два независимых параметра порождают 6 комбинаций — см. матрицу совместимости в
§3.1.2. Core принимает `(mode, flowMode)` пару, а не одно склеенное значение.
Это позволяет:

1. Поддерживать комбинации, которые не фиксируются плоским enum'ом — в частности
   `adaptive + router_by_topics` (см. §4.7).
2. Эволюционировать каждое измерение независимо — например, добавить
   `flowMode: "graph"` в будущем без размножения adaptive-вариантов.
3. Не ломать существующие тесты — в БД уже хранится двумерная форма через
   `tests.mode` (TestMode) и `tests.flowPolicyJson.mode` (FlowMode из
   [test-editor.types.ts:17](../../../client/src/features/tests/editor/test-editor.types.ts)).

Старые plain-enum значения сохраняют ссылочную нагрузку как «алиасы»:

| Алиас (старое значение) | Новая пара `(mode, flowMode)` |
| --- | --- |
| `legacy_flat` | `(standard, linear_flat)` |
| `section_linear` | `(standard, linear_by_topics)` |
| `section_router` | `(standard, router_by_topics)` |
| `section_graph` | _снят_ (см. §4.5) — вне охвата, зависел от движка правил |
| `adaptive_by_section` | `(adaptive, linear_by_topics)` |
| — | `(adaptive, router_by_topics)` — adaptive+router, см. §4.7 |
| _отложено_ | `(adaptive, linear_flat)` — «flat adaptive», вынесено в отдельный PRD |

Если `flowPolicy` отсутствует, Core обязан использовать
`(mode=standard, flowMode=linear_flat)` (эквивалент legacy_flat).

### 3.1.1 Поля `flowPolicy`

```text
flowPolicy = {
  mode:      "standard" | "adaptive",
  flowMode:  "linear_flat" | "linear_by_topics" | "router_by_topics",
  routerCompletionPolicy?: "all_required_completed" | "all_required_passed",
  sectionUnlockRules?: { [sectionId]: RouterUnlockRule },
  questionOrder?: "fixed" | "shuffle" | "draw_random" | "adaptive",
  sectionOrder?: "fixed" | "shuffle" | "rule_based",
  globalShuffle?: boolean,  // разрешён только при (standard, linear_flat)
}
```

`adaptive`-режим переопределяет `questionOrder` на `"adaptive"` независимо от
выставленного значения.

### 3.1.2 Матрица совместимости и защитные слои

Не все 6 комбинаций `mode × flowMode` валидны. Матрица:

| `mode` ↓ \\ `flowMode` → | `linear_flat` | `linear_by_topics` | `router_by_topics` |
| --- | --- | --- | --- |
| **`standard`** | ✓ supported (legacy_flat) | ✓ supported (section_linear) | ✓ supported (section_router) |
| **`adaptive`** | ✗ **blocked — deferred future PRD** | ✓ supported (adaptive_by_section) | ✓ supported (adaptive+router, §4.7) |

**`adaptive + linear_flat`** — отложено в отдельный будущий PRD «Flat adaptive».
Текущая модель `adaptive.topics[].levels[]` требует секционной привязки шкалы
сложности; общий pool без секционных границ требует другой модели (общая шкала
на тест, без topicId), которая выходит за рамки PRD-4.

**Strict gating для adaptive-режима.** Если `mode === "adaptive"`, **каждая**
section в `test.sections[]` обязана иметь соответствующий элемент
`adaptive.topics[]` с непустым `levels[]`. Тема без настроенных уровней
считается **невалидной** для adaptive-теста — это противоречит самой природе
adaptive-режима (нечего адаптировать). Mixed-режим («одни темы adaptive, другие
standard внутри одного теста») явно запрещён.

**4 слоя защиты от невалидных комбинаций:**

| Слой | Где | Что делает |
| --- | --- | --- |
| **L1 — UI** | `basic-settings-section.tsx` | В `<Select flowMode>` опция `linear_flat` помечается `disabled` + tooltip при `mode === "adaptive"`. При переключении `mode → adaptive` на `flowMode === "linear_flat"` — info-banner «Адаптивный режим требует разделения по темам. Выберите ...» + auto-suggest `linear_by_topics`. При adaptive-режиме каждая section без `levels[]` показывается с warning-маркером в Состав; publish blocked. |
| **L2 — Zod schema** | `shared/schema.ts` `testSettingsSchema` | `.superRefine`: блокирует `(adaptive, linear_flat)` и `adaptive` без полного покрытия sections настройками `levels[]`. Draft не валиден, кнопка «Сохранить» disabled, drawer error-banner. |
| **L3 — API server** | `PUT /api/tests/:id` | Тот же refine на server-side — 422 при попытке прислать невалидное. UI обрабатывает через существующий `saveError`-flow. Защита от curl/scripts/JS-bypass. |
| **L4 — Mapper / legacy data** | `apiToEditorModel` | При чтении сохранённого теста с невалидной комбинацией (legacy data до строгой валидации): auto-fix на ближайшую валидную (`(adaptive, linear_flat) → (adaptive, linear_by_topics)` либо `(adaptive, *) с пустыми levels → (standard, *)`) + warning banner «Конфигурация была авто-исправлена, проверьте настройки» — не блокирует чтение, но дирижит к save. |

**Аргумент к 4-слойной защите:** L1 — UX-первая линия; L2/L3 — single source of
truth для инвариантов (API публичен через curl/scripts); L4 — для реальных
legacy-тестов в БД, которые могут иметь невалидную конфигурацию из старых
кодовых версий до строгого валидатора.

### 3.2 Раздел как сценарный узел

Раздел (`section`) является сценарным узлом, а не только группой вопросов.

```text
section.start
content before section
section.questions
section.resultCalculated
content.summary
section.transition
```

Минимальная модель раздела:

```json
{
  "id": "section-1",
  "topicId": "topic-1",
  "title": "Финансы",
  "questionPolicy": {
    "drawCount": 10,
    "order": "shuffle"
  },
  "passRule": {
    "source": "inherit_overall",
    "type": "percent",
    "value": 70
  },
  "timeLimit": {
    "source": "custom",
    "minutes": 20
  },
  "state": "notStarted"
}
```

`passRule.source = inherit_overall` означает, что раздел использует общее правило теста. Для
лимита времени раздел поддерживает `inherit_test`, `custom` и `none`.

Если одновременно активны общий лимит теста и лимит текущего раздела, Core должен учитывать оба
ограничения:

- истечение лимита раздела завершает или блокирует текущий раздел согласно `flowPolicy`;
- истечение лимита теста завершает всю попытку;
- при одновременном истечении приоритет имеет лимит теста.

Runtime UI должен показывать два подписанных таймера, а не два безымянных значения:

```text
Осталось в теме: 08:25     Всего в тесте: 42:10
```

Ближайшее ограничение получает визуальный приоритет. На router-странице показывается только общий
таймер теста; таймер раздела появляется после входа в раздел.

### 3.3 Страница flow

Core должен строить единый список runtime-страниц, но сохранять принадлежность к разделу.

Типы страниц:

```text
start
system.blocked
content.intro
content.info
question.*
content.summary
results
system.*
```

В `legacy_flat` страницы вопросов могут не сохранять секционную непрерывность, но каждый вопрос
сохраняет `sectionId` и `topicId` для расчёта.

## 4. Функциональные требования

### 4.1 Выбор режима прохождения

Автор настраивает **два независимых параметра** — режим теста (`mode`) и
сценарий прохождения (`flowMode`):

**Режим теста (`mode`):**

| Режим UI | `flowPolicy.mode` |
| --- | --- |
| Стандартный | `standard` |
| Адаптивный | `adaptive` |

**Сценарий прохождения (`flowMode`):**

| Сценарий UI | `flowPolicy.flowMode` |
| --- | --- |
| Линейный (плоский) | `linear_flat` |
| Линейный по темам | `linear_by_topics` |
| Через страницу-маршрутизатор | `router_by_topics` |

Не все 6 комбинаций `(mode × flowMode)` валидны. UI блокирует выбор
`(adaptive, linear_flat)` (отложено в отдельный будущий PRD) — см. §3.1.2
матрицу совместимости и защитные слои.

Для существующих тестов поля не обязательны: при отсутствии `flowPolicy` Core
использует `(standard, linear_flat)` (эквивалент legacy_flat). При первом
сохранении можно записать явные значения, но экспорт должен работать и без них.

### 4.1.1 Граница старта попытки

Core должен различать загрузку SCO и старт полноценной попытки. В режимах, где требуется ранняя
проверка допуска из [PRD-6](../prd-6/retake-cooldown-gate.md), страница `start` может быть показана до
SCORM `Initialize`, а попытка начинается только после внутреннего действия:

```text
SCO loaded -> retake gate -> start page -> "Начать курс" -> SCORM Initialize -> flow start
```

Требования:

- действие `start_course_button` является явным триггером старта попытки;
- до этого действия Core не должен записывать `cmi.*`, если включён `retakePolicy.gateMode =
  before_internal_start`;
- старые тесты без `retakePolicy` могут сохранять прежний lifecycle старта;
- после старта попытки flow работает по выбранному `flowPolicy`.

### 4.2 Политики порядка

Поддерживаемые политики порядка разделов:

```text
fixed
shuffle
rule_based
```

Поддерживаемые политики вопросов внутри раздела:

```text
fixed
shuffle
draw_random
adaptive
```

Поддерживаемые политики общего списка:

```text
none
global_shuffle
```

`global_shuffle` разрешён только для `legacy_flat`, чтобы не разрушать границы разделов в
секционных режимах.

### 4.3 `legacy_flat`

Требования:

- Core выбирает `drawCount` вопросов из каждого раздела;
- Core может перемешать все выбранные вопросы в один список; с 2026-08-03 не перемешивает: разрешение
  осталось нереализованным намерением (политика `global_shuffle` из §4.2 в модель данных не попала, автору
  контрола не давалось), а второй проход по общему списку стирал порядок выдачи темы и расходился с
  веб-хостом, который поперёк тем не смешивает никогда — см. [PRD-30 §6.4](../prd-30/question-order.md);
- экран вопроса показывает тему вопроса как сейчас;
- результаты по разделам считаются после завершения всего теста;
- контентные страницы разделов не вставляются автоматически, если тест явно не переведён в
  секционный flow;
- восстановление сессии хранит плоский список вопросов и `currentIndex`.

### 4.4 `section_linear`

Требования:

- разделы идут в порядке автора;
- вопросы одного раздела не перемешиваются с вопросами другого раздела;
- перед вопросами раздела Core показывает контентные страницы `before_topic`;
- после вопросов раздела Core рассчитывает `sectionResult`;
- после расчёта Core показывает контентные страницы `after_topic`, включая `content.summary`;
- после summary Core переходит к следующему разделу или к финальным результатам.

### 4.5 `section_graph` — снят (вне охвата)

Графовый режим предполагал выбор следующего узла универсальным движком правил курса. Движок
правил выведен из охвата (продукт — конструктор тестов; см. BRD BR-03), поэтому `section_graph`
не реализуется. Нелинейные потребности покрываются структурным сценарием: router-режим
`section_router`, `sectionUnlockRules` (разблокировка раздела по прохождению другого) и
`passDecisionPolicy` (§5.2); адаптивная выдача — режимами `(adaptive, …)` (§4.6/§4.7).

### 4.6 `(adaptive, linear_by_topics)` — adaptive-by-section, линейный обход

Алиас старого `adaptive_by_section`. Требования:

- адаптивная логика выбирает вопросы внутри текущего раздела по шкале сложности
  (`adaptive.topics[i].levels[]`);
- переход на следующий раздел происходит только после завершения текущего
  раздела (см. ниже критерий завершения);
- экран перехода между уровнями и разделами — обычная страница flow или
  системная interstitial-страница;
- результат раздела включает достигнутый уровень, количество отвеченных
  вопросов и рекомендации.

**Критерий завершения adaptive-секции.** Адаптивная сессия раздела продолжается,
пока обучающийся **продвигается** по шкале (на повышение или на понижение).
Сессия завершается на стабильности — когда движение прекратилось (например,
два ответа подряд на одном уровне без изменения направления, либо исчерпан
банк вопросов соответствующего уровня).

Результат раздела:

- **«успешно»** — обучающийся подтвердил **минимальный** уровень компетенции
  (т.е. прошёл `level[0]` с его собственным `passThreshold`). Возвращается
  `achievedLevel: N`, где `N` — последний подтверждённый уровень.
- **«не успешно»** — не подтверждён даже минимальный уровень. Возвращается
  `achievedLevel: null`, `passed: false`.

В обоих случаях раздел считается **завершённым** для целей навигации (см.
§4.7 для router-completionPolicy). Различие — только в `passed` флаге и
доступе к следующему уровню сценария.

**Strict gating.** При `mode === "adaptive"` каждая section теста обязана
иметь непустой `adaptive.topics[].levels[]` (см. §3.1.2). Тема без уровней
**не валидна** для adaptive-теста — это противоречит самой природе
адаптивного режима.

### 4.7 `(adaptive, router_by_topics)` — adaptive в router-навигации

Adaptive в router-навигации. Сценарий обучающегося:

```text
router page → выбор темы → adaptive-сессия темы → результат темы → router page → ...
```

Требования:

- маршрутизатор показывает все sections теста (как в `(standard, router_by_topics)`);
- внутри выбранной темы Core запускает adaptive flow по правилам §4.6;
- после завершения adaptive-сессии Core возвращает обучающегося на router page;
- результат темы (`achievedLevel`, `passed`) фиксируется и используется
  `routerCompletionPolicy` для решения «тест завершён → results».

**Критерий «тема пройдена» для router-completionPolicy.** Тема считается
«пройденной» в смысле router-навигации, если adaptive-сессия завершилась с
`passed: true` (т.е. подтверждён минимальный уровень). См. §4.6 для критерия
успеха adaptive-сессии.

**`routerCompletionPolicy` в adaptive+router:**

| Значение | Когда тест завершается |
| --- | --- |
| `all_required_completed` | Все required-темы завершены (любой `achievedLevel`, включая `null`) |
| `all_required_passed` | Все required-темы со `passed: true` (минимальный уровень подтверждён) |

`sectionUnlockRules` работают как в standard+router: разблокировка темы по
правилу (например, «тема B доступна после прохождения темы A»). Adaptive
не меняет правила unlock.

**Strict gating сохраняется.** Все темы теста обязаны иметь
`adaptive.topics[].levels[]` (§3.1.2). Тема без уровней не валидна — UI
блокирует publish.

**Router page не адаптируется.** Router page — это контент-страница с
`kind: "router"`, рендерится как обычно (не зависит от mode). Меню тем,
прогресс по темам, indicator «текущий уровень» и проч. показываются
обучающемуся без специальной adaptive-логики на самом router'е.

## 5. Runtime-состояние

### 5.1 Состояние раздела

Поддерживаемые состояния:

```text
notStarted
inProgress
completed
passed
failed
locked
skipped
```

Состояние раздела хранится в suspend/session state.

Пример:

```json
{
  "sections": {
    "section-1": {
      "state": "completed",
      "currentPageId": "summary-section-1",
      "attempts": 1,
      "result": {
        "percent": 76,
        "passed": true
      }
    }
  }
}
```

### 5.2 Результат раздела

Core рассчитывает `sectionResult` сразу после завершения вопросов раздела.

Минимальные поля:

```json
{
  "sectionId": "section-1",
  "topicId": "topic-1",
  "title": "Финансы",
  "correct": 7,
  "totalQuestions": 10,
  "earnedPoints": 7,
  "possiblePoints": 10,
  "percent": 70,
  "passed": true,
  "attempts": 1
}
```

Результат раздела доступен:

- макету `content.summary`;
- формулам пользовательских показателей;
- финальному результату курса.

Итоговый статус теста рассчитывается отдельно от результата раздела. Если для теста включены
правила прохождения по разделам, Core должен применять явную `passDecisionPolicy`:

| `passDecisionPolicy` | Итоговый статус теста |
| --- | --- |
| `overall_only` | Зависит только от общего результата теста |
| `overall_and_required_topics` | Требует одновременно общего проходного результата и прохождения всех обязательных разделов по индивидуальному или унаследованному правилу |
| `required_topics_only` | Требует прохождения всех обязательных разделов по индивидуальному или унаследованному правилу; общий результат справочный |
| `all_topics_passed` | Требует прохождения всех выбранных разделов; каждый раздел должен использовать индивидуальное правило или наследовать общее правило теста |

Рекомендованный default: `overall_only`, если правил по разделам нет, и
`overall_and_required_topics`, если включено хотя бы одно правило по разделу.

Обязательность раздела хранится как параметр связи теста с темой/разделом, например
`test_sections.required`. Этот признак используется в `overall_and_required_topics`,
`required_topics_only` и router-flow. Политика `all_topics_passed` проверяет все выбранные разделы
независимо от `required`.

Правило раздела должно иметь явный источник: `inherit_overall`, `custom` или `none`.
`inherit_overall` означает, что раздел использует общий тип и значение правила прохождения теста.
Если общее правило имеет тип `none`, наследование не даёт проверяемого критерия; для политик,
которые требуют прохождения разделов, Core/UI должны требовать `custom` или блокировать сохранение.

### 5.3 Значения раздела (`section.*`)

Core публикует результаты разделов в пространстве:

```text
section.{sectionId}.percent
section.{sectionId}.passed
section.{sectionId}.score
section.{sectionId}.attempts
section.{sectionId}.completed
```

Эти значения сохраняются в `suspend_data` как часть состояния попытки.

## 6. Переходы и защиты Core

Универсальный движок правил и его события/действия сняты (вне охвата — BRD BR-03). Маршрут между
разделами задаёт сценарий (`flowPolicy`, `sectionUnlockRules`, `passDecisionPolicy`), а
корректность каждого перехода гарантируют финальные защиты Core.

### 6.1 Финальные защиты Core

Core может отменить переход, если:

- целевой раздел не существует;
- целевая страница не входит в разрешённый flow;
- переход нарушает `navigationPolicy`;
- раздел заблокирован;
- повтор раздела превышает лимит попыток;
- событие уже завершено и повторное действие создаёт цикл без выхода.

Отменённый переход пишется в диагностику.

## 10. Совместимость и миграция

- Старые тесты без `flowPolicy` используют `legacy_flat`.
- Экспорт старого теста не должен вставлять section intro/summary автоматически.
- При включении `section_linear` UI предупреждает, что вопросы больше не будут перемешиваться между
  разделами.
- Результаты старых попыток остаются читаемыми.
- Восстановление старой сессии использует старый `currentIndex`; восстановление новой сессии
  использует `currentPageId` и `currentSectionId`.

## 11. Нефункциональные требования

| ID | Требование |
| --- | --- |
| NFR-01 | `legacy_flat` сохраняет поведение текущего SCORM runtime |
| NFR-02 | Выборка и перемешивание воспроизводимы в рамках попытки |
| NFR-03 | Runtime не должен зависнуть в цикле переходов без fallback |
| NFR-04 | Восстановление сессии возвращает текущий раздел, страницу, вопрос и ответы |
| NFR-05 | Диагностика содержит причину каждого перехода между разделами |
| NFR-06 | Ошибка при переходе не должна терять ответы обучающегося |
| NFR-07 | В gated-режиме загрузка SCO и показ стартовой страницы не равны старту полноценной попытки до `start_course_button` |

## 12. Критерии приёмки

- [ ] Тест без `flowPolicy` экспортируется и проходит как текущий плоский SCORM.
- [ ] `legacy_flat` выбирает вопросы по `drawCount` и может перемешивать общий список.
- [ ] `section_linear` не смешивает вопросы разных разделов.
- [ ] `content.intro` отображается перед вопросами раздела.
- [ ] `content.summary` отображается после расчёта результата раздела.
- [ ] `section.{id}.percent` и `section.{id}.passed` доступны формулам показателей и сценарию.
- [ ] Невалидный переход блокируется Core и пишется в диагностику.
- [ ] Восстановление сессии открывает тот же раздел и страницу.
- [ ] Финальные результаты включают результаты всех завершённых разделов.
- [ ] В gated-режиме Core не вызывает SCORM `Initialize` до внутренней кнопки **"Начать курс"**.

## 13. Решённые вопросы

| Вопрос | Решение |
| --- | --- |
| Нужно ли ломать старый плоский runtime? | Нет. Он становится режимом `legacy_flat` |
| Контентные страницы автоматически включаются в старые тесты? | Нет. Только при явном секционном flow |
| Кто рассчитывает результат раздела? | Core |
| Кто решает переходы между разделами? | Core по `flowPolicy` и финальным защитам |
| Может ли шаблон сам перейти в раздел? | Только через Runtime API, с проверками Core |
