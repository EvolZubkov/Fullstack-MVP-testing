# PRD-44. Тип вопроса «Распределение баллов между шкалами»

Статус: идея зафиксирована владельцем продукта 2026-08-05, в разговоре, без сбора требований.
Форма решения не согласована, эскизов нет. Документ фиксирует ПОВОД и фактическое состояние
смежных механизмов, чтобы проектирование не начиналось с чистого листа.

## 1. Повод

Идея: новый тип вопроса, в котором учащемуся показывается несколько шкал (компетенций,
ценностей, категорий) и фиксированный максимум баллов на ВСЕ шкалы суммарно; учащийся сам
распределяет этот бюджет между шкалами по своему усмотрению. Это механика constant-sum /
ipsative-распределения, знакомая по форс-чойс опросникам ценностей (например, методика
Шварца) — в отличие от MBI-подобных опросников, которые система уже умеет вести через
PRD-26, здесь один ответ одновременно измеряет несколько шкал, и веса шкал не независимы:
чем больше баллов уходит в одну шкалу, тем меньше остаётся на остальные.

Требования не собирались: неизвестен ни целевой опросник-прецедент, ни то, обязателен ли
режим проверки, ни то, как автор должен привязывать распределение к существующим шкалам
PRD-5.

## 2. Что есть сегодня

Два смежных механизма уже реализованы, но ни один не покрывает задачу:

- **PRD-26 «Шкала»** (`docs/specs/prd-26/scale-question-type.md`, РЕАЛИЗОВАН) — тип вопроса
  `scale`: одно утверждение, выбор ОДНОЙ градации из упорядоченного набора (компонент DS
  `Stepper` в режиме `choice`). Ответ одномерный: индекс одной выбранной градации.
- **PRD-5 «Шкалы и компетенции»** (`docs/specs/prd-5/scales-competency-measurements.md`,
  Реализовано) — расчётный механизм результата, НЕ тип вопроса. Ядро —
  `shared/scales/engine.ts`: каждая единица вклада (`MeasurementSpec`) хранит
  ФИКСИРОВАННОЕ `value`, заданное автором заранее; `isActive()` только решает, сработала ли
  единица (булево — совпал ли выбранный индекс/пара/позиция с `sourceKey`), а итоговый вклад
  всегда `value * weight` — величина ответа учащегося на сам вклад не влияет, влияет только
  то, какие единицы «выстрелили».
- Дизайн-система (`vendor/ui-kit/src/components/Slider.tsx`) уже содержит `Slider` — но
  только одиночное значение или диапазон из двух ползунков (`range`), без понятия «группа
  ползунков с общим бюджетом».
- PRD-26 зафиксировал риск R-1: ветвление по типу вопроса рассыпано примерно по сорока
  файлам (модель, оба рендерера, редактор, книга импорта/экспорта, аналитика, инспектор
  отладчика, снапшоты) — это верхний по значимости риск для ЛЮБОГО нового типа, не только
  для `scale`.

## 3. Препятствия, которые нельзя обойти

Раздел существует, чтобы проектирование не наступило на них по очереди. Каждый пункт
проверен по коду.

### 3.1 Модель вклада в шкалы не рассчитана на вклад, заданный учащимся

`MeasurementSpec.value` — число из настройки автора, не из ответа. Чтобы учащийся сам
задавал величину вклада в шкалу, нужен новый механизм: либо новый `sourceType` с правилом
«вклад = значение, введённое учащимся, а не `m.value`», либо параллельный путь расчёта в
обход `isActive`/`delta = value * weight`. Это правка ядра `shared/scales/engine.ts`
(и его JS-двойника `server/scorm/template/app/scales/engine.js`, который держится в
паритете golden-тестом), а не только нового рендера.

### 3.2 Нет интерактива «фиксированный бюджет на несколько элементов управления»

`Slider` в ui-kit — одиночное значение или диапазон из двух ползунков. Группы связанных
ползунков, где движение одного меняет допустимый максимум остальных, в дизайн-системе нет.
Нужно решить: новый примитив в `vendor/ui-kit` (по правилу «редактируемая зависимость» —
не подменять локальным шимом) или иная механика ввода (числовые поля с остатком, слайдер +
поле).

### 3.3 Понятие «правильности» не определено

PRD-26 явно развёл проверяемый и измерительный режим. Форс-чойс распределение баллов по
природе метода обычно ipsative — единственно верного распределения нет. Открыт вопрос:
существует ли для этого типа проверяемый режим вообще, и если да — что считается «верным»
для континуального распределения (эталонное распределение + допуск? покомпонентное
сравнение?).

### 3.4 Форма данных вопроса: несколько шкал внутри одного вопроса

Существующие типы хранят в `dataJson` линейный список вариантов (`{ options: string[] }`).
Этому типу нужно хранить N ссылок на шкалы (метка, ключ, возможно верхняя граница на
шкалу) и общий бюджет — новая форма `dataJson`, которой в модели прежде не было. Отдельно
не решено, ссылается ли вопрос на существующие шкалы теста (PRD-5) или несёт свой
локальный список категорий, транслируемый в шкалы отдельной настройкой.

### 3.5 Готовность ответа и правило суммы

Сегодняшний гейт готовности (`client/src/pages/learner/answer-gate.ts`) бинарный: ответ дан
или нет. Здесь не решено: вопрос считается отвеченным при ЛЮБОМ распределении бюджета, или
только когда сумма равна максимуму точно; допускается ли остаток; как валидируется
превышение бюджета в интерактиве (запрет ввода сверх остатка или ошибка при попытке
подтвердить).

### 3.6 Книга импорта/экспорта не имеет формата для этой конструкции

Лист «Вклады вопросов» (PRD-5/PRD-14) сопоставляет индекс варианта ответа фиксированному
вкладу в шкалу — колонка «вариант -> шкала -> число». В новом типе набор шкал и бюджет —
содержимое САМОГО вопроса (не производный вклад от выбора), поэтому формат листа
«Вопросы» тоже придётся расширять: как заполнить список шкал вопроса и бюджет в ячейках
Excel-строки.

### 3.7 ~40 точек ветвления по типу вопроса (PRD-26 R-1)

Любой новый тип задевает: перечисление типов в `shared/schema.ts` (четыре места), движок
проверки, движок шкал, оба рендерера (веб напрямую, SCORM-пакет через глобал `TBTemplate`),
редактор вопроса, книгу импорта/экспорта, готовность ответа, аналитику, инспектор
отладчика PRD-18, предпросмотр шаблона, снапшоты публикации PRD-15. У этого типа риск выше,
чем у `scale`: `scale` переиспользовал существующую форму данных (`options: string[]`) и
существующий компонент (`Stepper`), а здесь нова и форма данных (§3.4), и интерактив (§3.2),
и модель вклада (§3.1) — переиспользовать почти нечего.

## 4. Что предстоит решить

| Вопрос | Почему важен |
| --- | --- |
| Шкалы вопроса — ссылки на шкалы теста (PRD-5) или локальный список категорий вопроса | Определяет форму `dataJson` (§3.4) и то, обязателен ли тест со шкалами для использования типа |
| Бюджет — фиксированное число в системе или настраивается автором на вопрос | Простой случай (фикс. 100) дешевле, но менее гибок для разных методик |
| Существует ли проверяемый режим и что в нём «верно» | §3.3; без ответа непонятно, нужна ли вообще ветка проверки |
| Интерактив ввода: связанные ползунки, числовые поля с остатком, или их комбинация | §3.2; технически определяет, нужен ли новый DS-примитив |
| Правило готовности ответа: сумма точно равна бюджету или допускается меньше | §3.5 |
| Как вклад учащегося подставляется в расчёт шкалы: новый `sourceType` в PRD-5 или отдельный путь расчёта в обход `MeasurementSpec` | §3.1; архитектурное решение, определяющее объём правок ядра |
| Формат листа книги для набора шкал вопроса и бюджета | §3.6 |
| Учитывать ли ipsative-смещение (шкалы вопроса математически не независимы — сумма постоянна) в интерпретации шкалы PRD-5 (bands, направление) | Не критично для первой итерации, но заметно методологу; минимум — предупреждение в UI автора |
| Раскладка на узком экране (мобильная адаптация) для группы связанных ползунков | Зависит от выбранного интерактива (§3.2) |

## 5. Вне охвата (кандидаты, зависят от решений раздела 4)

- Матричная раскладка (несколько таких вопросов на одном экране) — по прецеденту PRD-26
  предполагается, что модель «один вопрос — один экран» сохраняется.
- Статистическая коррекция ipsative-данных (учёт встроенной отрицательной корреляции шкал
  при агрегации по многим учащимся) — вопрос психометрической аналитики
  (`docs/specs/brd-psychometric-analytics.md`), не этого типа вопроса.
- Адаптивные тесты сверх общего механизма типов — по прецеденту PRD-26 отдельно не
  прорабатывается, пока не появится конкретный сценарий.

## 6. Связанные работы

- [PRD-26](../prd-26/scale-question-type.md) — ближайший прецедент нового типа вопроса:
  границы, риски ветвления (R-1), решения по измерительному/проверяемому режиму.
- [PRD-5](../prd-5/scales-competency-measurements.md) — модель шкал и вкладов, которую
  затрагивает §3.1.
- [PRD-2](../prd-2/result-variables.md) — показатели `result.*`, потребляющие `scale.*`;
  затронуты, если появится новый способ формирования вклада.
- [PRD-12](../prd-12/web-runtime-parity.md) — единый рендерер: новый интерактив обязан быть
  одним источником разметки на оба хоста.
- [PRD-14](../prd-14/questions-import-export.md) — книга импорта/экспорта: §3.6.
- [PRD-15](../prd-15/content-ownership.md) — снапшоты публикации и `content_hash`: новая
  форма `dataJson` требует проверки, что перенос снапшота и пересчёт хеша учитывают её.
- [PRD-18](../prd-18/debug-test-player.md) — инспектор отладчика: новый тип должен быть
  виден в протоколе прогона наравне с остальными.
- [BRD психометрической аналитики](../brd-psychometric-analytics.md) — потенциальный
  потребитель и источник методологических требований к ipsative-данным.
