# PRD-44: Тип вопроса «распределение баллов»

**Версия:** 1.0
**Статус:** СПРОЕКТИРОВАН 2026-08-06. Требования согласованы с владельцем продукта, реализация не начата.
**Дата:** 2026-08-06

[PRD-12](../prd-12/web-runtime-parity.md) (единый рендер обоих хостов),

[PRD-15](../prd-15/content-ownership.md) (снапшоты публикации),
[PRD-18](../prd-18/debug-test-player.md) (инспектор тестового прогона),
[PRD-19](../prd-19/skip-return-navigation.md) (навигация в попытке),

**Эскиз:** предстоит, фаза 0 (`docs/wireframes/question-allocation.html`).
**Референс:** `docs/references/Опросник ЧИЛ_V3.6_фин.xlsx` — опросник ведущего стиля человекоцентричного
лидерства, 14 блоков по 4 утверждения, бюджет 7 баллов на блок, четыре стиля-шкалы, максимум 98 баллов на
стиль. Механика подсчёта в файле — сумма присвоенных баллов по стилю за все блоки, ведущий стиль равен
максимуму.

## Терминология

- **Вопрос-распределение** — вопрос типа `allocation`: несколько утверждений и общий бюджет баллов,
  который учащийся распределяет между ними по своему усмотрению.
- **Бюджет** — суммарное число баллов вопроса, которое учащийся обязан распределить целиком (референс: 7).
- **Домен варианта** — допустимый диапазон баллов на ОДНО утверждение, `minPerOption..maxPerOption`.
- **Ipsative-измерение** — измерение, в котором сумма по всем шкалам вопроса постоянна, поэтому шкалы
  математически не независимы: прибавка одной означает убыль другой. Правильного распределения не
  существует, сравнивать имеет смысл профиль внутри одного учащегося, а не абсолютные величины между
  учащимися.
- **Рейтинг шкал** — упорядочение группы шкал по нормализованному значению, из которого берутся ведущая
  (первое место) и слабая (последнее место) шкалы.

## 1. Границы

**Входит:**

- Новый тип вопроса `allocation` в модели данных, валидации и типах.
- Новый источник вклада в шкалы, величину которого задаёт учащийся (`option_allocation`), в движке шкал и
  в его JS-двойнике для SCORM-пакета.
- Рендер распределения на ОБОИХ хостах из единого источника разметки.
- Ведущая и слабая шкала в языке формул показателей PRD-2 (раздел 5).
- Импорт и экспорт книги: лист «Вопросы» (три новые колонки), лист «Вклады вопросов» (новое значение
  колонки «Источник»), шаблон книги и лист-справка.
- Редактор вопроса и вкладка «Вклады вопросов» редактора теста.
- Смежные точки: готовность ответа, обзор ответов, аналитика, инспектор тестового прогона PRD-18,
  снапшоты публикации PRD-15, предпросмотр шаблона.

**Не входит:**

- Проверяемый режим (эталонное распределение и частичный балл за близость к нему). Решение владельца
  продукта 2026-08-06: тип остаётся чисто измерительным, проверяемый режим выносится в отдельный PRD.
  Обоснование по референсу — в разделе 3.
- Матричная раскладка: несколько распределений на одном экране. Модель «один вопрос — один экран»
  не меняется (прецедент PRD-26).
- Статистическая коррекция ipsative-смещения при агрегации по многим учащимся — предмет
  [BRD психометрической аналитики](../brd-psychometric-analytics.md).
- Группа шкал как самостоятельная сущность модели: набор шкал для рейтинга задаётся списком ключей прямо
  в формуле показателя (FR-25).

## 2. Модель данных

- **FR-01.** Значение `allocation` добавляется в перечисление типов вопроса в `shared/schema.ts` в
  четырёх местах: колонка `questions.type`, схема детального ответа `detailedAnswerSchema`, схема
  статистики `questionStatsSchema` и колонка `scorm_answers.question_type`. **Миграция базы не
  требуется:** обе колонки объявлены как `text NOT NULL` без ограничения `CHECK` (проверено по
  `drizzle/baseline-existing-db.sql` и всем миграциям по `0013` включительно), перечисление живёт только
  в типах TypeScript и Zod.
- **FR-02.** `dataJson` вопроса-распределения:

  ```json
  { "options": ["...", "..."], "budget": 7, "minPerOption": 0, "maxPerOption": 7 }
  ```

  Список утверждений лежит в том же поле `options`, что у одиночного и множественного выбора, поэтому
  существующие читатели `dataJson.options` (редактор вариантов, колонка книги «Тексты вариантов ответа»,
  подгонка шрифта, предпросмотр) работают без правок.
- **FR-03.** `correctJson` всегда пустой объект `{}`: эталона у типа нет (раздел 3). Значение `null`
  недопустимо — колонка `questions.correct_json` объявлена `NOT NULL`.
- **FR-04.** Ограничения полей: `budget` — целое от 1 до 1000; `minPerOption` и `maxPerOption` — целые,
  `0 <= minPerOption <= maxPerOption <= budget`; число утверждений — от 2 до 10. Умолчания при создании
  вопроса: `minPerOption = 0`, `maxPerOption = budget`.
- **FR-05.** Выполнимость распределения проверяется отдельным правилом:
  `количествоВариантов * minPerOption <= budget <= количествоВариантов * maxPerOption`. Правило
  обязательно и на сохранении вопроса (FR-46), и на импорте книги (FR-40). Без него автор задаёт
  конфигурацию, которую нельзя заполнить ни одним способом: в референсе обсуждается «минимум 2 балла на
  вариант» при четырёх вариантах и бюджете 7, то есть требуется минимум 8 баллов из 7 доступных.
- **FR-06.** Ответ учащегося — `Record<string, number>`: ключ — индекс утверждения в АВТОРСКОМ порядке
  (не в порядке выдачи), значение — присвоенные баллы. Кодировка совпадает с типом «соответствие»,
  поэтому хранение в `attempts`, перенос в снапшот и чтение аналитикой идут существующим путём. После
  первого взаимодействия ответ содержит запись для КАЖДОГО утверждения, включая нулевые: аналитике важно
  отличать «поставил ноль» от «не дошёл до варианта».
- **FR-07.** Порядок утверждений не фиксирован: тип подчиняется общему признаку «Следование вариантов
  ответов» (`questions.shuffle_answers`, умолчание — случайный порядок) и в `hasFixedOptionOrder` НЕ
  добавляется. Ротация утверждений, которую референс ведёт вручную ключом на листе «Механика подсчета
  результатов», обеспечивается этим общим механизмом.
- **FR-08.** Признаки типа объявляются в `shared/questions/question-type.ts` (единственный источник
  правды о типах): `hasOptionList` — да, `isSingleIndexChoice` — нет, `hasFixedOptionOrder` — нет,
  новый признак `distributesBudget` — да. Признак `distributesBudget` используется всеми точками, где
  поведение типа своё, вместо сравнения `type === "allocation"`.

## 3. Оценка

- **FR-09.** Тип всегда измерительный: не проверяется, не приносит баллов, не входит в число возможных
  баллов теста и не влияет на процент и порог зачёта. Поведение совпадает с измерительным режимом
  PRD-26 (FR-08, FR-09, FR-09.1 того документа), включая случай теста, целиком собранного из таких
  вопросов: процент и вердикт скрываются, статусом управляет показатель PRD-2.
- **FR-10.** Градуированная цена ответа PRD-10 к типу не применяется. Заполненные «Балл» и «Цена ответа»
  на листе «Оценка» для такого вопроса — предупреждение импорта, значения сохраняются, но в расчёте не
  участвуют (симметрично FR-25 PRD-26).
- **FR-11.** Обоснование отказа от проверяемого режима зафиксировано как решение, а не как умолчание.
  В референсе эталонного распределения нет ни в каком виде: лист «Механика подсчета результатов» только
  суммирует введённые баллы по стилям и берёт максимум, а инструкция учащемуся гласит «чем больше баллов
  вы присваиваете варианту, тем точнее он описывает ваше обычное поведение». Метод ipsative по природе:
  сумма баллов за блок постоянна у любого испытуемого, поэтому проверяемый режим не дал бы
  дифференциации. Эталон с частичным баллом за близость — предмет отдельного PRD.

## 4. Вклад в шкалы

- **FR-12.** В `shared/scales/engine.ts` добавляется значение `option_allocation` в `MeasurementSpec.sourceType`.
  Правило единицы вклада: `sourceKey` — индекс утверждения; единица активна, когда учащийся присвоил этому
  утверждению ненулевой балл; вклад равен `ответ[sourceKey] * value * weight`.
- **FR-13.** Это первый случай, когда величину вклада задаёт учащийся, а не автор. Сегодня вклад всегда
  равен `value * weight` и от величины ответа не зависит. Изменение локализуется в двух функциях
  (`isActive` и подсчёт активных вкладов в `computeScales`) через общую функцию «вклад единицы при данном
  ответе», которую используют и `computeAnswerContributions`, и `computeScales`; двух путей расчёта не
  появляется.
- **FR-14.** `value` сохраняет смысл коэффициента: `1` означает «балл учащегося равен вкладу в шкалу»
  (случай референса), `-1` — обратный вклад, дробное значение — масштабирование. `weight` сохраняет смысл
  веса при агрегациях `weighted_avg`. Импорт книги проставляет `value = 1`, `weight = 1`, если ячейки
  пусты.
- **FR-15.** `achievableRange` (домен шкалы, из которого считается нормализация в проценты и который
  PRD-29 использует как область определения полос интерпретации) для вопроса-распределения считается
  отдельной ветвью: вклад одного вопроса в шкалу лежит в диапазоне
  `[сумма minPerOption по вариантам этой шкалы; min(budget, сумма maxPerOption по вариантам этой шкалы)]`,
  умноженном на `value * weight`. Верхняя граница ограничена бюджетом, потому что варианты одного вопроса
  делят общий бюджет и не могут достичь своих максимумов одновременно. Для референса это даёт домен
  `0..98` на стиль, что совпадает с примечанием в файле («максимальное кол-во баллов по одному стилю —
  98»).
- **FR-16.** Правки симметрично повторяются в JS-двойнике `server/scorm/template/app/scales/engine.js`;
  паритет удерживается существующим golden-тестом.
- **FR-17.** Проверка соответствия методике выполнена на референсе численно: контрольное заполнение из
  файла, пропущенное через правило FR-12 при `value = weight = 1` и агрегации `sum`, даёт
  Целеустремленный 34, Вдохновляющий 16, Командный 14, Процессный 34 при сумме 98 — совпадение с итогами
  файла (`K16:N16`) полное. Этот расчёт входит в приёмку (A-02).

## 5. Ведущая и слабая шкала

- **FR-18.** Язык формул показателей PRD-2 получает два источника ранга шкалы в форме
  `fn([ключи], место).свойство`:

  ```text
  topScale(["cel","vdo","kom","pro"], 1).key
  bottomScale(["cel","vdo","kom","pro"], 1).value
  ```

  Форма повторяет существующий источник `countScales(["k1","k2"], "level")`, расширенный доступом к
  свойству. Второй аргумент — место в рейтинге, счёт с единицы: `topScale([...], 2)` даёт вторую по
  величине шкалу, `bottomScale([...], 1)` — последнюю.
- **FR-19.** Свойства: `key` (ключ шкалы, строка), `label` (подпись уровня шкалы, строка), `value`
  (нормализованное значение, число), `margin` (отрыв от следующего места, число), `tiedCount` (сколько
  шкал делят это место, число, минимум 1).
- **FR-20.** Рейтинг строится по НОРМАЛИЗОВАННОМУ значению шкалы, а не по `raw`: сырые значения шкал с
  разными доменами несравнимы, а `direction = inverse` уже учтён в нормализованном. Шкалы без значения
  (`hasValue = false`) в рейтинг не входят.
- **FR-21.** Правило ничьей: при равенстве значений выше становится шкала, которая идёт РАНЬШЕ в
  авторском порядке шкал теста (`scales.sort_order`). Правило обязательно и одинаково на всех хостах,
  иначе один и тот же ответ при пересчёте в вебе, в пакете и в снапшоте даст разного лидера.
- **FR-22.** Ничья должна быть видима автору отчёта, а не разрешаться молча. Для этого существуют
  `tiedCount` и `margin`: отчёт ветвится на «два равно выраженных стиля» при `tiedCount > 1` и на
  «стили выражены сопоставимо» при малом `margin`. Требование не умозрительное: в контрольном заполнении
  референса два стиля набрали по 34 балла, а формула файла `MATCH(MAX(...))` вернула тот из них, чья
  колонка левее — то есть выбор ведущего стиля там определяется порядком колонок.
- **FR-23.** Если рейтинг пуст (ни одна из перечисленных шкал не имеет значения) или запрошенное место
  больше числа шкал в рейтинге, источник возвращает `null`; показатель ведёт себя как при любом другом
  неопределённом значении.
- **FR-24.** Валидация формулы: ключи, которых нет среди шкал теста, — ошибка редактирования (как у
  существующих источников по ключу). Отдельно: проверка «строковый показатель возвращает только
  объявленные коды исходов» на свойстве `key` не работает, потому что код приходит из данных, а не
  литералом; в этом случае редактор выдаёт ПРЕДУПРЕЖДЕНИЕ с подсказкой «ключи шкал должны совпадать с
  кодами исходов показателя», а не ошибку.
- **FR-25.** Набор шкал задаётся списком ключей в самой формуле; сущности «группа шкал» не вводится.
  Причина: в тесте могут быть служебные шкалы (например, шкала достоверности), которым в рейтинге стилей
  не место, а явный список делает это решение видимым в тексте формулы.
- **FR-26.** Правки повторяются в JS-двойнике языка формул `server/scorm/template/app/dsl/formula.js`;
  паритет удерживается существующим golden-корпусом PRD-2.

## 6. Рендер обоих хостов

- **FR-27.** Разметка порождается единственной функцией `renderAllocation` в
  `shared/template/question-interaction.ts` — тем же модулем, что и остальные типы. Веб вызывает её
  напрямую, SCORM-пакет — через глобальный `TBTemplate` (новый файл
  `server/scorm/template/app/render/questions/allocation.js` по образцу существующих обёрток, без
  собственной разметки).
- **FR-28.** Строка утверждения: текст, ползунок и числовое поле со степпером, синхронные между собой.
  Над группой — счётчик остатка. Формулировки берутся из референса: «Осталось: N из 7» и, при нулевом
  остатке, «Вы использовали все баллы».
- **FR-29.** Превышение бюджета невозможно по построению: доступный максимум конкретного утверждения в
  каждый момент равен `min(maxPerOption, текущееЗначение + остаток)`, и это ограничение действует
  одинаково для ползунка, ввода с клавиатуры и вставки. Состояния «перебор» не существует, сообщения об
  ошибке для него нет; возможен только недобор.
- **FR-30.** Нижняя граница обеспечивается предзаполнением, а не запретом: при `minPerOption > 0` поля
  стартуют со значения `minPerOption`, счётчик показывает остаток `budget - количествоВариантов * min`,
  опуститься ниже минимума ввод не даёт. Иначе учащийся попадает в тупик, распределив весь бюджет и
  оставив одно утверждение нулём. При `minPerOption = 0` (умолчание и случай референса) предзаполнения
  нет.
- **FR-31.** Готовность ответа: вопрос отвечен тогда и только тогда, когда сумма распределённых баллов
  равна бюджету. Правило реализуется в `hasAnswer` (`client/src/pages/learner/answer-gate.ts`) явной
  веткой, а не через `default`, и зеркалится в рантайме пакета. Нетронутый вопрос и вопрос с частичным
  распределением считаются пропущенными: кнопка отправки заблокирована, счётчик пропущенных и возврат к
  незавершённым вопросам PRD-19 работают штатно.
- **FR-32.** Подсказка типа (подзаголовок под текстом вопроса): «Распределите N баллов между вариантами»,
  где N — бюджет вопроса.
- **FR-33.** Экран обзора и повторного просмотра показывает распределение только для чтения, без разметки
  верности: правильного ответа нет.
- **FR-34.** Доступность и клавиатура: числовое поле — обычный ввод, ползунок — стрелки и `Home`/`End`,
  у каждой пары `aria-label` из текста утверждения, счётчик остатка — область `aria-live`, чтобы
  изменение остатка озвучивалось экранным диктором.
- **FR-35.** Размер подписей утверждений берётся из переменной `--tb-answer-fs`, вычисляемой существующим
  проходом подгонки шрифта; `answerTexts` возвращает для типа тексты утверждений.
- **FR-36.** Раскладка на узком экране задаётся медиазапросом в `theme.css` шаблона — единственном общем
  источнике оформления сцены для обоих хостов. Конкретная раскладка пары «ползунок и поле» утверждается
  на эскизе (фаза 0), отдельного макета для пакета не появляется.

## 7. Книга импорта и экспорта

- **FR-37.** Лист «Вопросы», колонка «Тип вопроса» принимает значение `allocation` на импорте
  (`server/services/questions-import.ts`) и выводит его на экспорте (`server/services/questions-export.ts`).
- **FR-38.** Лист «Вопросы» получает три новые колонки: «Бюджет распределения», «Минимум на вариант»,
  «Максимум на вариант». Для остальных типов колонки пусты; заполненные значения у другого типа —
  предупреждение импорта. Пустые «Минимум» и «Максимум» у типа `allocation` означают умолчания FR-04.
- **FR-39.** Тексты утверждений едут в существующей колонке «Тексты вариантов ответа» через `#`.
  Колонка «Номера правильных ответов» должна быть пуста; заполненная — ошибка строки с понятным текстом.
- **FR-40.** Импорт проверяет выполнимость FR-05 и отвергает строку с текстом, называющим конкретные
  числа: сколько минимально требуется и сколько доступно.
- **FR-41.** Лист «Вклады вопросов» получает новое значение колонки «Источник» — `распределение`
  (рядом с существующими `вопрос`, `вариант`, `пара`, `позиция`). Ключ источника — индекс утверждения с
  нуля, как у источника `вариант`; значение — коэффициент (умолчание 1); вес — множитель (умолчание 1).
  Новых листов книга не получает.
- **FR-42.** Шаблон книги (`server/services/workbook-template.ts`) и лист-справка получают описание типа,
  трёх новых колонок, нового источника вклада и строку примера.
- **FR-43.** Приёмочный сценарий импорта: опросник ЧИЛ из `docs/references` собирается книгой целиком —
  14 вопросов по 4 утверждения, бюджет 7, четыре шкалы с агрегацией «сумма», 56 строк вкладов с
  коэффициентом 1 — и импортируется без ошибок.

## 8. Редактор

- **FR-44.** В выпадающем списке типов (`client/src/features/questions/question-editor-drawer.tsx`)
  появляется «Распределение баллов». Редактор утверждений повторяет редактор вариантов одиночного выбора:
  список подписей с добавлением, удалением и изменением порядка.
- **FR-45.** Карточка вопроса получает три поля: «Бюджет», «Минимум на вариант», «Максимум на вариант».
  Блок правильного ответа для типа скрыт.
- **FR-46.** Валидация при сохранении: FR-04 (границы полей, 2..10 утверждений, непустые подписи) и
  FR-05 (выполнимость) с сообщением, называющим числа.
- **FR-47.** Привязка утверждений к шкалам живёт НЕ в карточке вопроса, а во вкладке «Вклады вопросов»
  редактора теста (`client/src/features/tests/editor/sections/scales-section.tsx`): вопрос несёт только
  утверждения, а строка вклада связывает утверждение со шкалой и коэффициентом. Матрица вкладов
  показывает утверждения вопроса-распределения так же, как варианты одиночного выбора, но подписывает
  ячейку коэффициентом, а не фиксированным вкладом.
- **FR-48.** Во вкладке шкал показывается предупреждение методологического характера, когда шкала
  получает вклад от вопроса-распределения: шкалы, питаемые одним распределением, не независимы — сумма
  постоянна, поэтому полосы интерпретации и направление шкалы следует задавать с учётом этого.
- **FR-49.** Смена типа вопроса на `allocation` и обратно переносит подписи вариантов по существующему
  правилу переноса; бюджет и домен при уходе с типа забываются.
- **FR-50.** Предпросмотр вопроса (`client/src/features/content/question-preview.tsx`), фильтр по типу и
  дерево содержимого получают поддержку нового типа наравне с остальными.

## 9. Смежные точки

- **FR-51.** Аналитика (`server/routes/analytics/*`, `client/src/pages/author/analytics.tsx`): по
  вопросу-распределению строится среднее распределение бюджета по утверждениям; показатели верности к
  типу не применяются. Экспорт попытки показывает вклады ответа существующим механизмом
  `computeAnswerContributions` — распределение даёт несколько дельт от одного вопроса, что механизм уже
  допускает.
- **FR-52.** Инспектор тестового прогона PRD-18 (`server/scorm/debug-player/assets/inspector-compute.js`)
  показывает вектор распределения во вкладках «Протокол» и «Выдача», а вклад в шкалы — во вкладке
  «Шкалы»; поле верности пустое.
- **FR-53.** Снапшоты публикации PRD-15 переносят новую форму `dataJson` без специальной обработки и
  учитывают её в `content_hash`; это фиксируется тестом, а не предполагается.
- **FR-54.** SCORM-телеметрия: взаимодействие пишется с типом `other`, `learner_response` — строка вида
  `0[.]3,1[.]1,2[.]1,3[.]2` (индекс утверждения и присвоенный балл). Тип `numeric` не подходит — ответ
  векторный; тип `matching` семантически ложен.
- **FR-55.** Предпросмотр шаблона в реестре шаблонов (`shared/template/preview-context.ts`) получает
  демонстрационный вопрос-распределение, чтобы администратор видел новый интерактив в проверке
  работоспособности шаблона.
- **FR-56.** Отчёт по попытке (PRD-27) специальных правок не требует: он строится на шкалах и
  показателях, а ведущая и слабая шкала приходят к нему через показатели раздела 5.

## 10. Правки дизайн-системы

- **FR-57.** Пара «ползунок и числовое поле» собирается из существующих примитивов `vendor/ui-kit`
  (`Slider`, `NumberInput`). Группа с общим бюджетом добавляется в дизайн-систему как составной компонент
  (рабочее имя `BudgetAllocation`): счётчик остатка, строки утверждений, синхронизация ползунка и поля,
  ограничение по остатку. Локальный шим вместо правки `vendor/ui-kit` недопустим — зависимость
  редактируемая.
- **FR-58.** Framework-free двойник разметки живёт в `shared/template/question-interaction.ts` (FR-27) и
  повторяет классы компонента; двух источников оформления не появляется.
- **FR-59.** Правки CSS вносятся в ОБЕ копии бандла дизайн-системы (`vendor/ui-kit/css/university-rt.css`
  — источник, `client/src/styles/vendor/` — загружаемая копия), иначе правило не доедет до приложения.
- **FR-60.** На новый компонент добавляется стори в `vendor/ui-kit`.

## 11. Приёмка

- **A-01.** Юнит-тесты: правило вклада FR-12, домен шкалы FR-15, готовность ответа FR-31, ограничение по
  остатку FR-29, предзаполнение FR-30, выполнимость FR-05, разметка `renderAllocation` (снимок),
  источники ранга шкалы FR-18..FR-23 (включая ничью и пустой рейтинг), парсер и валидатор формул FR-24.
- **A-02.** Расчёт на референсе: контрольное заполнение опросника ЧИЛ даёт по шкалам 34 / 16 / 14 / 34
  при сумме 98 и ведущий стиль «Целеустремленный» — совпадение с итогами файла. Проверка выполняется
  тестом на зафиксированных данных, а не вручную.
- **A-03.** Импорт книги ЧИЛ (FR-43) проходит без ошибок; выгрузка обратно даёт те же значения бюджета,
  домена и вкладов.
- **A-04.** Браузерная приёмка веб-прохождения: распределение бюджета ползунком и полем, счётчик остатка,
  невозможность перебора, блокировка отправки при недоборе, узкий экран. Скриншоты сверяются с эскизом.
- **A-05.** SCORM-приёмка: сборка пакета, прохождение в локальном плеере (`npm run scorm:player`) и на
  стенде WebTutor, побайтовое совпадение порождённой разметки с веб-хостом (то же требование, что для
  остальных типов), корректная запись взаимодействия FR-54.
- **A-06.** Тестовый прогон PRD-18: вопрос виден в инспекторе, вклад в шкалы совпадает с серверным
  расчётом.
- **A-07.** Паритет двойников: golden-тесты движка шкал и языка формул зелёные.
- **A-08.** Порог покрытия проекта (80%) не падает.

## 12. Риски

- **R-1.** Ветвление по типу вопроса рассыпано примерно по сорока местам и почти нигде не является
  исчерпывающим `switch` — это цепочки сравнений с литералом, замыкаемые `default` или `return false`.
  Новый тип компилируется и проходит существующие тесты, работая при этом неправильно молча: `default` в
  `hasAnswer` засчитал бы частичное распределение как готовый ответ (сломав FR-31), а `return false` в
  `isActive` обнулил бы все шкалы при полностью заполненном опроснике. Риск для этого типа выше, чем для
  `scale`: у шкалы совпадали и форма данных, и интерактив, здесь новы форма данных, интерактив и модель
  вклада. Мера: признаки типа (FR-08) вместо сравнений с литералом, явный перечень точек ветвления в
  плане реализации и тест-матрица «тип x признак». Общая ревизия классификатора зафиксирована как
  технический долг в [ROADMAP §0.3](../../ROADMAP.md#03-технический-долг).
- **R-2.** Паритет двух JS-двойников (движок шкал, язык формул). Пропущенная правка даёт разные
  результаты в вебе и в пакете. Мера: golden-тесты обоих двойников входят в приёмку (A-07).
- **R-3.** Домен шкалы (FR-15) участвует и в нормализации в проценты, и в полосах интерпретации PRD-29.
  Ошибка здесь смещает не число, а ВЕРДИКТ: маркер уровня встанет не там, где его уровень. Мера:
  отдельные тесты домена на смешанном тесте (распределение вместе с обычными вопросами).
- **R-4.** Ipsative-природа данных. Полосы интерпретации, сравнение шкал между учащимися и любая
  агрегация по выборке требуют оговорки: шкалы связаны постоянной суммой. Мера: предупреждение автору
  (FR-48); статистическая коррекция вынесена в психометрический BRD.
- **R-5.** Новый составной компонент дизайн-системы существует в двух воплощениях — React для авторских
  экранов и framework-free для сцены учащегося. Расхождение даёт разный интерактив на разных экранах.
  Мера: разметка и классы задаются один раз (FR-58), совпадение проверяется снимком разметки.

## 13. Фазы

- **Фаза 0. Эскиз.** Экран учащегося (группа утверждений, счётчик остатка, узкий экран) и карточка
  редактора; согласование и переезд файла в `docs/wireframes/approved/`.
- **Фаза 1. Ядро.** Тип и признаки (FR-01..FR-08), схема `dataJson`, новый источник вклада и домен шкалы
  в движке (FR-12..FR-16), JS-двойник и golden-паритет.
- **Фаза 2. Дизайн-система.** Составной компонент группы распределения, стори, обе копии бандла.
- **Фаза 3. Экран учащегося.** `renderAllocation`, обёртка пакета, счётчик остатка, ограничение по
  остатку, предзаполнение, готовность ответа, клавиатура и доступность, раскладка узкого экрана.
- **Фаза 4. Редактор.** Тип в списке, поля бюджета и домена, валидация, матрица вкладов, предупреждение
  о связанности шкал, предпросмотр и фильтры.
- **Фаза 5. Книга.** Три колонки листа «Вопросы», новый источник листа «Вклады вопросов», шаблон и
  справка, приёмочный импорт ЧИЛ.
- **Фаза 6. Ведущая и слабая шкала.** Источники ранга в парсере, вычислителе и валидаторе формул,
  JS-двойник, правило ничьей и признаки отрыва.
- **Фаза 7. Смежное и приёмка.** Аналитика, инспектор PRD-18, снапшоты, предпросмотр шаблона, браузерная
  и SCORM-приёмка, сборка опросника ЧИЛ целиком и сверка итогов с референсом.
