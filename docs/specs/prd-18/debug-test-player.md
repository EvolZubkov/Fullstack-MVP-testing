## Терминология

- **Плеер отладки** — встроенный в сервис экран, который собирает РЕАЛЬНЫЙ SCORM-пакет из теста
  и проигрывает его в iframe с SCORM 2004 RTE-шимом, окружённым панелями инспектора. Это
  серверно-аутентифицированный аналог CLI-плеера [scorm-player.mjs](../../../scripts/scorm-player.mjs),
  а не отдельный веб-рантайм.
- **Прогон отладки** — одна сессия проигрывания собранного пакета. Полностью ОДНОРАЗОВЫЙ: не
  пишется в `attempts`/аналитику/телеметрию; состояние — в `localStorage` плеера, сбрасывается
  автором.
- **Инспектор** — набор панелей реального времени над запущенным пакетом: коммуникация с LMS
  (RTE-журнал), баллы, шкалы, показатели, фактически выданный набор вопросов, протокол по вопросам.
  Зеркало 5 вкладок CLI-плеера (Протокол / Шкалы / Показатели / Watch / LMS-журнал).
- **Источник версии** — ВСЕГДА живой ЧЕРНОВИК (текущее редактируемое состояние теста);
  опубликованный снапшот не отлаживается (D-4).

Это инструмент **препрод-проверки** (корректность настройки «математики» теста до выгрузки в LMS),
а не учебный сценарий и не замена приёмке в WebTutor (§1.2).

## 1. Обзор

### 1.1 Контекст

Сегодня прогнать собранный тест как обучающийся и в реальном времени увидеть, что пакет сообщает
LMS, какие баллы/шкалы/показатели считаются и какой набор вопросов фактически выдан, можно ТОЛЬКО
из командной строки:

1. `npm run scorm:sample` / `scorm:template` собирает фиктивный пакет в `out/*.zip`;
2. `npm run scorm:player` поднимает локальный плеер на `:5050` с RTE-шимом и инспектором;
3. инспектор показывает Протокол / Шкалы / Показатели / Watch / LMS-журнал.

Это требует репозитория, Node и CLI — недоступно автору и методологу. Внутри сервиса полноценного
прогона нет: предпросмотр статичен (шаблон, страница, расчёт шкал на демо-ответах
[scales-api.ts](../../../client/src/features/tests/editor/scales-api.ts)), а реальный путь
прохождения ([take-test.tsx](../../../client/src/pages/learner/take-test.tsx)) пишет обычную
попытку в `attempts` и аналитику. PRD-18 переносит CLI-плеер с инспектором В СЕРВИС как
аутентифицированную функцию редактора теста.

Ключевой рычаг переиспользования: production-экспорт уже собирает `ExportData` и зовёт
`generateScormPackage` ([tests.ts:918-1065](../../../server/routes/tests.ts#L918-L1065)). Плеер
отладки использует ТОТ ЖЕ сборщик и пайплайн, но ВСЕГДА из живого состояния теста — так автор
отлаживает то, что редактирует прямо сейчас (NFR-18). Для опубликованного теста отгружаемый пакет
собирается из снапшота, поэтому отладку живого состояния следует понимать как «что уйдёт при
следующей публикации», а не как текущий опубликованный снапшот.

### 1.2 Граница реализуемости (NFR-17/NFR-18)

Плеер исполняет РЕАЛЬНЫЙ артефакт пакета, но среда исполнения — шим, а не WebTutor. Что
воспроизводимо и что нет:

| Аспект | Плеер отладки | Реальный WebTutor |
| --- | --- | --- |
| Рендер экранов, выдача, расчёт балла/шкал/показателей, `suspend_data` within-attempt | да (тот же `app.js`/`runtime.js` пакета) | да |
| Коммуникация с LMS (`cmi.*` чтения/записи, completion/success/score) | да (RTE-шим логирует трафик) | да |
| Восстановление сессии within-attempt (resume по `suspend_data`) | да (localStorage) | да |
| Sequencing & Navigation (SN), активное дерево активностей | НЕТ (шим только RTE) | зависит от LMS |
| Cross-attempt-стор, ротация вариантов на повторе (PRD-17) | НЕТ (`adl.data` недоступен; деградация до случайного выбора) | НЕТ (NFR-17) |
| Реальный retake-gate по данным WebTutor (PRD-6) | только МОК ([scorm-player.mjs](../../../scripts/scorm-player.mjs) `/api/mock-webtutor`/ClientBridge) | да |

Вывод: плеер закрывает проверку «математики» теста (выдача, баллы, шкалы, показатели, что уходит в
LMS), но НЕ заменяет приёмку в WebTutor для механик, зависящих от LMS-окружения (SN, cross-attempt,
реальный retake-gate). Это явно документируется и помечается в UI (FR-14, R-3).

### 1.3 Метрики успеха

| Цель | Метрика |
| --- | --- |
| Прогон без CLI | держатель edit-доступа запускает плеер из редактора теста и проигрывает пакет, не скачивая ZIP и не открывая терминал |
| Тот же пайплайн сборки | пакет плеера собран тем же `generateScormPackage` и сборщиком `ExportData`, что `GET /:id/export/scorm`, но всегда из живого состояния теста; для опубликованного теста отгружается снапшот — отладка живой версии = «что уйдёт при следующей публикации» |
| Видимость математики | инспектор показывает в реальном времени `cmi.*`, `score.*`, `scale.*`, `result.*` и фактически выданный набор вопросов (вариант/квоты/перечень/теги) |
| Изоляция | прогон не создаёт записей в `attempts`, `scorm_packages`, `scorm_attempts`, `scorm_answers`; аналитика не меняется |
| Нет дрейфа с CLI | RTE-шим и инспектор — единый источник для CLI- и встроенного плеера |

## 2. Пользователи

- **Автор теста (владелец)** — собирает и отлаживает свой тест: проигрывает, читает инспектор,
  экспортирует протокол.
- **Соавтор / методолог / QA с грантом `edit`** — то же в пределах edit-доступа к тесту; правка
  контента не требуется для отладки, но отдельного «debug-доступа» не вводится (D-2).
- **Администратор/суперпользователь** — доступ по общим правилам RBAC (как у экспорта SCORM).
- **Обучающийся** — НЕ пользователь этой функции: учебный путь остаётся в
  [take-test.tsx](../../../client/src/pages/learner/take-test.tsx).

## 4. Архитектура

Без новых таблиц БД и без новых сущностей хранения. Всё держится на трёх переиспользуемых блоках
(сборщик `ExportData` → `generateScormPackage` → плеер/инспектор) и одной in-memory сессии.

### 4.1 Серверная часть (новый роутер `server/routes/debug-player.ts`)

| Эндпоинт | Назначение |
| --- | --- |
| `POST /api/tests/:id/debug/session` | gate edit-scope; собирает `ExportData` общим сборщиком ИЗ ЖИВОГО состояния теста, зовёт `generateScormPackage({ ..., telemetry: null })`, кладёт ZIP в in-memory `Map<token, { buffer, files, launch, userId, expiresAt }>`, возвращает `{ token, launch, warnings }` |
| `GET /api/tests/:id/debug/play/:token/*splat` | отдаёт файл из распакованного в память пакета (same-origin); в лаунч-HTML инжектирует RTE-шим; gate edit-scope + владение токеном |
| `DELETE /api/tests/:id/debug/session/:token` | удаляет сессию (явный сброс/закрытие) |

**Рефактор сборщика (обязателен для NFR-18).** Тело `GET /:id/export/scorm`
([tests.ts:918-1065](../../../server/routes/tests.ts#L918-L1065)) выносится в сервис
`buildScormExportData(testId, { source }): Promise<ExportData>` (загрузка
секций/тем/вопросов/шкал/показателей/scoring/адаптива/контент-страниц, резолв `templateDir`). Его
используют ОБА: production-экспорт и `debug/session`. Параметр `source` сохраняется для ЭКСПОРТА
(`draft` → live storage, `published` → активный снапшот, как сейчас решает `exportSourceForTest`),
но `debug/session` ВСЕГДА вызывает сборщик с живым источником (`draft`/live) — отлаживается текущее
редактируемое состояние. Единый сборщик устраняет вторую копию логики и гарантирует, что отладка и
экспорт собирают пакет одним и тем же способом.

**Изоляция (NFR-19).** В `debug/session` телеметрия не включается (никакого `?telemetry=true`),
поэтому `scorm_packages`/`scorm_attempts`/`scorm_answers` не создаются. Записи в `attempts` нет —
плеер не дёргает `/attempts/*`. In-memory сессии живут по TTL и чистятся; рестарт сервера их теряет
(допустимо — прогон одноразовый).

### 4.2 Общий модуль плеера (паритет с CLI, FR-13)

RTE-шим и логика инспектора из [scorm-player.mjs](../../../scripts/scorm-player.mjs) выносятся в
общий источник (напр. `server/scorm/debug-player/` — шим-инжектор + клиентские панели инспектора),
который потребляют:

- CLI-плеер `scripts/scorm-player.mjs` (остаётся dev-инструментом, [keep-preview-generator]-логика —
  не выпиливать);
- встроенный плеер (роутер `debug-player.ts` + клиентская страница).

Так поведение отладки (модель `cmi`, журнал трафика, парсинг `suspend_data`, протокол/шкалы/
показатели/выдача) не расходится между хостами. Паритет фиксируется тестом (по образцу
golden-теста близнеца PRD-17, §11 Фаза 5).

### 4.3 Клиентская часть (новая страница/панель в редакторе)

- Точка входа — ПУНКТ в меню действий теста (рядом с экспортом SCORM), без отдельной кнопки
  ([client/src/features/tests/editor/](../../../client/src/features/tests/editor/)); открывает плеер
  в ОТДЕЛЬНОМ ОКНЕ (новая вкладка/окно), не в редакторе (FR-17).
- Окно плеера (макет): по центру — iframe пакета (same-origin,

### 5.1 Статусная панель (FR-19) — методологический минимум, видна всегда

Аудитория панели — автор/методолог (зона ответственности — корректность математики теста, не
LMS-плумбинг). Правило: на панели только то, что отвечает на вопрос «верна ли математика прямо
сейчас» и нужно видеть НЕПРЕРЫВНО (в т.ч. при свёрнутом инспекторе). Всё остальное — во вкладки
инспектора или в заголовок окна. Действия прогона (Пересобрать/Сброс) — в тулбаре окна; экспорт
протокола в CSV — во вкладке «Протокол» (контекстно, без дубля в тулбаре). Размещение панели: НАД
СТЕЙДЖЕМ в левой колонке (не на всю ширину окна), весь статус-контент левым флангом; инспектор
поднят к верху окна и занимает правую колонку с самого верха (его лента вкладок — на уровне
статусной панели).

Постоянные группы:

| Группа | Элементы (пользовательские формулировки) | Источник | Зачем непрерывно |
| --- | --- | --- | --- |
| Прогресс (РЕЖИМО-ЗАВИСИМ) | **Плоский** (`linear_flat`): «вопрос i из N» + мини-бар + тема (разделов-единиц результата нет → пер-секц. статуса не существует). **Секционный** (`linear_by_topics`/`router`): лента статусов разделов — пройденные (% + ✓/✗) + текущий как АКТИВНЫЙ хвост «идёт». **Адаптив:** лента «уровни по темам» — подтверждённые темы (уровень + ✓) + текущая тема АКТИВНЫМ хвостом (уровень + стрелка ↑/↓ + «идёт»); без дублирования (перенос адаптив-бара CLI) | `state.currentIndex`, `flatQuestions`, `topicsState`/`sectionResults`/`levelsState` | в плоском — двусмысленность промежуточных чисел; в секц./адапт. пер-раздельный/пер-уровневый статус — главный выход логики. МАСШТАБ: при многих темах строка СВЁРНУТА — первые чипы + «+N подтверждено» + текущий активный + «осталось K». Клик по «+N» РАСКРЫВАЕТ статусы всех тем ПРЯМО В СТАТУСНОЙ СТРОКЕ (строка переносится на несколько рядов), повторный клик `свернуть` — обратно. НЕ во вкладку |
| Оценка | «N из M» · «%» · «порог K%» · вердикт «Пройден/Не пройден» | `cmi.score.*` (как %), `passRule`, вердикт = `success_status` пакета | главный методологический итог + калибровка порога; вердикт пакета может расходиться с «балл ≥ порога» (секц. гейт) — это баг, виден тут |

Условная группа (алярм, всплывает ТОЛЬКО при сбое):

| Группа | Элементы | Источник | Зачем |
| --- | --- | --- | --- |
| Ошибка расчёта | красный бейдж «Формула шкалы/показателя „…" не вычислена» — в норме отсутствует | `computeTestScales()`/`computeTestResultVariables()` (поля `errors`) | сломанная формула = молчаливый мусор в LMS; ловить сразу |

Перенесено С панели (зона ответственности / не-метрика):

| Что | Куда | Почему не на панели |
| --- | --- | --- |
| Статус для LMS (`completion`/`success`/`entry`) | вкладка «LMS-журнал» | интеграционный плумбинг, не зона методолога; вердикт прохождения уже в «Оценке» |

### 5.3 Дельта к существующему плееру

- **Переиспользуется как есть (5):** Протокол, Шкалы, Показатели, LMS-журнал, Watch → «Состояние».
- **Переносится:** адаптив-бар → группа «Прогресс» статусной панели + детально во вкладку «Выдача»;
  «Сброс попытки» → тулбар окна (+ «Пересобрать»); тоггл «Инспектор» → круглый краевой тоггл
  на левом крае сайдбара (DS `ou-fab`); экспорт CSV — во вкладке «Протокол» (не в тулбаре, без дубля);
  WebTutor-мок-бар → опционально в тулбар (FR-15), не в показатели.
- **Новое (3):** постоянная статусная панель (§5.1); вкладка «Выдача»; вкладка «Результаты».
- **Не переносится:** выбор пакета из `out/` (в сервисе пакет собирается на лету).

«Выдача» — прямой ответ на запрошенный «набор вопросов к выдаче»: автор видит, что именно выпало и
почему (вариант/квоты) в ЭТОМ прогоне. Статистику распределения по N прогонам («аудит выдачи») не
вводим — проблемы выдачи детерминированы и ловятся валидацией редактора (§9, FR-11 снято).

### 5.4 Эталон (подсветка правильных ответов на стейдже)

Debug-тоггл «Эталон» в риббоне стейджа (по умолчанию ВЫКЛ — сначала проходишь как ученик). Подсвечивает
правильные ответы МЕЛКИМ маркером в левом жёлобе варианта, СНАРУЖИ варианта (на подсчёт баллов НЕ влияет).
Ключевое: метка кладётся на РЕАЛЬНЫЙ рендер варианта применённого шаблона (`.option` с радио/чекбоксом,
`.rank-item` с грипом, `.matching`-плитки), не на абстрактные плашки и не через тяжёлые шаблонные
`.correct-answer`/`.incorrect-answer` (они для ученического ревью, для отладки не годятся). Глиф по типу:

- одиночный / множественный — `✓` у правильного варианта;
- ранжирование — правильный порядковый `№` у каждого варианта;
- сопоставление — буквенное кодирование: ответам присвоены `A/B/C`, у каждого промпта — буква его
  правильного ответа (без линий-связей, которые громоздки);
- цена варианта (вес опции, PRD-10) — ТОЛЬКО на ОДИНОЧНОМ выборе (`weighted`, режим «Веса опций»:
  `score = вес выбранного`; `scoring-builder.tsx:105-107`, `schema.ts:201`, `engine.ts:15-16`): мелкая
  подпись «вес N» у каждой опции. Множественный/сопоставление/ранжирование оцениваются `tiered`
  (ступенчатые тиры по счётчикам `c`/`x`/total) — пер-вариантной цены у них НЕТ; на стейдже только
  маркер корректности, а сама тир-таблица — в «Протоколе»/настройках, не на варианте.

Данные «что верно» уже есть в контексте рендера (`correct` по варианту, настройка `showCorrectAnswers`,
`TEST_DATA`); рисуется ЛЁГКИМ debug-слоем общего шаблона (`shared/template`), единым для веб- и
SCORM-хостов. Маркеры — на токенах DS (success/accent); точная тема варианта = применённый шаблон в
рантайме.

## 6. Безопасность и изоляция

- **Доступ.** Тот же gate, что у экспорта: `requirePermission("tests.export.scorm")` +
  `requireTestScope("edit")`. Отдельный grant/роль не вводится (D-2).
- **Токен сессии** привязан к пользователю и тесту; раздача файлов проверяет владение и TTL; чужой
  токен → `404`, просроченный → `410`.
- **Изоляция данных.** Нет записи в `attempts` и SCORM-телеметрию (NFR-19); состояние — только в
  `localStorage` плеера, неймспейсится по `(testId, userId, source)` и сбрасывается.
- **Экспозиция контента.** Как у обычного SCORM-пакета: в собранный пакет попадают вопросы и ключи
  (а в режиме вариантов PRD-17 — все варианты, R-7 PRD-17). Это тот же артефакт, что уходит в LMS,
  и доступен только держателю edit-доступа — новой утечки сверх экспорта нет.
- **Санитизация** HTML контент-страниц и слотов — на стороне `generateScormPackage` (NFR-05),
  плеер ничего не ослабляет.

(`ENGINERING_HANDBOOK/design-system/{AI-AGENT,DESIGN_SYSTEM_RT,DESIGN_SYSTEM_RT_API}.md`); в холсте
эскиза — только реальный UI на DS `ou-*`/`tb-*`, пояснения — в таблицах `wf-notes`/`wf-mapping`.
Канва-источник терминов и стилей — `client/src/styles` (не устаревшие копии в docs).

## 8. Совместимость

- Никаких изменений учебного пути и схемы БД: плеер не трогает `attempts`, новые таблицы не вводит.
- Production-экспорт остаётся как есть по контракту; меняется только то, что его тело переезжает в
  переиспользуемый `buildScormExportData` (поведение эндпоинта `GET /:id/export/scorm` сохраняется,
  покрывается существующими acceptance-тестами SCORM).
- CLI-плеер `scorm-player.mjs` и генераторы `scorm:sample`/`scorm:template` сохраняются; плеер
  начинает потреблять общий модуль шима/инспектора (рефактор без потери функций).
- Снапшоты PRD-15: плеер их НЕ отлаживает — источник всегда живой (D-4). Отгружаемый пакет
  опубликованного теста по-прежнему собирается из снапшота; чтобы отлаженные правки ушли
  обучающемуся, тест нужно ПЕРЕОПУБЛИКОВАТЬ.

## 9. Вне охвата

- **Реальная приёмка в WebTutor** (SN-секвенсирование, cross-attempt-стор, реальный retake-gate по
  данным WebTutor) — не воспроизводится; остаётся за приёмкой в LMS (NFR-18, R-3). Доступен только
  МОК WebTutor-гейта из CLI-плеера для проверки экрана блокировки (FR-15).
- **Отладка опубликованного снапшота / выбор версии-снапшота** — вне охвата: плеер ВСЕГДА отражает
  живое состояние теста (решение 2026-06-26, D-4). Чтобы проверить именно отгружаемую версию
  published-теста — переопубликовать и/или воспользоваться обычным экспортом SCORM.
- **Сохранение/шеринг прогонов отладки** (история debug-сессий, сравнение прогонов) — прогоны
  одноразовые (решение Q3); при будущей потребности — отдельная задача.
- **Запись отладочной попытки в `attempts` с флагом `is_preview`** — отвергнуто (Q3): для
  SCORM-плеера состояние держит сам рантайм (localStorage), запись в БД избыточна.
- **Совместный/многопользовательский прогон** (несколько отладчиков в одной сессии) — вне v1.
- **Аудит выдачи (N-прогонная статистика распределения вариантов/квот)** — СНЯТО (FR-11): проблемы
  выдачи (квота недобирает / битый/пустой вариант / неравные размеры) ДЕТЕРМИНИРОВАНЫ и относятся к
  ВАЛИДАЦИИ РЕДАКТОРА (PRD-11 BR-10-04, PRD-17 §6/FR-18), N-прогонная симуляция её дублирует и
  значимой ценности не несёт. Узкий остаток (стохастика пересечения тегов / `min`-добор; паритет
  «собранный пакет == конфиг») — при будущей потребности отдельной QA-задачей, не в плеере.
- **Автоматические проверки «математики»** (ассерты на ожидаемые баллы/шкалы как тест-кейсы) — вне
  v1; возможное будущее.
- **Отладка медиа/тяжёлых ресурсов на пропускную способность** — вне охвата.

## 10. Решения и открытые вопросы

| # | Вопрос | Решение |
| --- | --- | --- |
| D-1 | Что запускать: веб-предпросмотр, встроенный SCORM-плеер или оба | Встроенный SCORM-плеер с инспектором реального времени (Q1 2026-06-26): нужна коммуникация с LMS/RTE, что даёт только SCORM-рантайм, а не веб-предпросмотр |
| D-2 | Модель доступа к отладке | Переиспользовать edit-доступ (владелец + грант `edit`), как у экспорта SCORM (Q2). Отдельный грант/роль/capability не вводится |
| D-3 | Персистентность прогонов | Полностью одноразовые (Q3): без записи в `attempts`/телеметрию; состояние в `localStorage`; протокол экспортируется CSV |
| D-4 | Версия теста для отладки | ТОЛЬКО живая версия (live storage, текущее редактируемое состояние) — переключателя на снапшот НЕТ (уточнение 2026-06-26: «все текущие изменения должны применяться в сессию»). Снапшот не отлаживается; published уходит обучающемуся из снапшота — для его проверки переопубликовать. Сборка — общий с production-экспортом сборщик |
| D-5 | Retake-gate в отладке | По умолчанию обход/`failOpen` (прогон не блокируется cooldown); опционально — прогон против МОКА WebTutor-гейта для проверки экрана блокировки (FR-15) |
| D-6 | Единый или отдельный код шима/инспектора с CLI-плеером | Единый общий модуль (FR-13), CLI-плеер рефакторится на его потребление; паритет — тестом-близнецом (как PRD-17) |
| D-7 | Размещение и макет плеера | Плеер открывается в ОТДЕЛЬНОМ ОКНЕ (уточнение 2026-06-26); макет: iframe пакета + СВОРАЧИВАЮЩИЙСЯ сайдбар с вкладками инспектора + фиксированная СТАТУСНАЯ панель НАД СТЕЙДЖЕМ в левой колонке (инспектор поднят к верху; ревью 2026-06-27) с основными показателями (FR-17/18/19) |
| D-8 | Шаблон оформления в прогоне | Пакет собирается с ПРИМЕНЁННЫМ к тесту шаблоном (`design_settings_json`), как production-экспорт — отладка на реальном визуальном шаблоне, не на демо/`default` (FR-20) |
| D-9 | Эталон (подсветка правильных ответов) — форма и место (ревью 2026-06-27) | Тоггл-СВИТЧ «Эталон» в риббоне стейджа (по умолч. ВЫКЛ, на баллы не влияет); лёгкий debug-маркер НА РЕАЛЬНОМ рендере вариантов (✓ — одиночный/множественный; № — ранжирование; буквы пар на доске — сопоставление), НЕ на абстрактных плашках и НЕ через тяжёлые `.option.correct-answer`. Цена ответа — в «Протоколе», не на вариантах. ФАКТ ПО КОДУ: пер-вариантная «Веса опций» = `weighted` = ТОЛЬКО одиночный; множественный/сопоставление/ранжирование = `tiered` (тиры по c/x, не пер-вариантная) — `scoring-builder.tsx:105-107`, `schema.ts:201`, `engine.ts:15-16` (FR-21, §5.4) |
| OQ-1 | TTL и лимит числа одновременных in-memory debug-сессий | Задать на фазе реализации (напр. TTL ~30 мин, вытеснение LRU); решить, переживает ли сессия HMR/перезапуск dev-сервера (по умолчанию — нет, прогон одноразовый) |
| OQ-2 | ~~Объём панели «Аудит выдачи»~~ — снято | «Аудит выдачи» убран из охвата (§9): диагностика выдачи — статическая валидация редактора, N-прогонная симуляция дублирует |
| OQ-3 | Куда вынести общий модуль плеера физически (`server/scorm/debug-player/` vs `shared/`) | Уточнить при рефакторинге `scorm-player.mjs`; критерий — общий потребитель CLI + сервер без дублирования |
| OQ-4 | ~~Прогон опубликованного снапшота / выбор версии снапшота~~ — снято | Отлаживается ТОЛЬКО живая версия (D-4); отладка снапшотов вне охвата (§9) |
