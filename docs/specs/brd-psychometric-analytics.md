## 1. Контекст и постановка задачи

Test Builder накапливает результаты прохождений (веб-хост и SCORM-телеметрия из LMS), но раздел
аналитики ограничен описательной статистикой: средний процент, доля сдавших, разбивка по темам,
распределение баллов и доля верных ответов на вопрос. Отсутствует аппарат оценки **качества самих
тестов и заданий** — трудности, дискриминативности, надёжности измерения, работоспособности
дистракторов. Без него автор не может отличить «плохое задание» (двусмысленное, с ошибкой в ключе,
не различающее сильных и слабых) от «трудного, но корректного», а также не может обосновать
проходной балл.

**Цель:** реализовать аппарат психометрической аналитики на базе классической теории тестов (CTT),
работающий на уже доступных данных и на дополнительно импортируемых обезличенных выгрузках из LMS,
и встроить его результаты в авторский раздел аналитики как обратную связь по качеству банка заданий.

## 2. Цели и границы

### 2.1 Цели итерации

- PA-01. Анализ заданий (CTT): эмпирическая трудность, дискриминативность, красные флаги.
- PA-02. Надёжность теста: внутренняя согласованность, стандартная ошибка измерения, доверительный
  интервал вокруг проходного балла.
- PA-03. Анализ дистракторов для заданий с выбором (single/multiple — один/несколько ответов).
- PA-04. Сопоставление заявленной автором трудности с наблюдаемой.
- PA-05. Импорт обезличенных выгрузок из LMS как полноправного источника данных для расчётов.
- PA-06. Учёт объёма выборки (N): любая метрика сопровождается объёмом выборки и уровнем доверия; при
  недостаточном объёме число не выдаётся как факт.

### 2.2 Вне охвата (см. раздел 8)

- Item Response Theory (IRT, теория моделирования ответов на задания): модели Раша/2PL/3PL,
  информационные функции, характеристические кривые.
- Автоматизация оценки валидности (содержательной, критериальной, конструктной).
- Анализ времени на задание как обязательная метрика — время по каждому заданию доступно только
  частично (SCORM) и выносится в задел.

## 3. Источники данных и каноническая модель наблюдений

### 3.1 Три источника

Психометрика считается на объединении трёх источников; каждое наблюдение помечается источником, в
интерфейсе доступен фильтр по источнику.

| Источник | Таблица/канал | Особенности |
| --- | --- | --- |
| Веб-прохождения | `attempts` (`variantJson`/`answersJson`/`resultJson`) | Полная матрица восстанавливается через `checkAnswer`; времени по заданиям нет |
| Телеметрия SCORM | `scormAttempts` + `scormAnswers` | Готовая длинная таблица ответов с `isCorrect`/`points`/`answeredAt` |
| Импорт из LMS | новый канал (раздел 3.3) | Обезличенные выгрузки; псевдонимный ключ респондента; сопоставление заданий |

### 3.2 Каноническая запись наблюдения

Все три источника нормализуются адаптерами в единую **каноническую запись наблюдения**, и только её
читает расчётный движок. Это разрывает связь «аналитика ↔ конкретный источник»:
добавление источника — это ещё один адаптер, а не правка метрик.

Обязательные поля канонической записи:

```text
respondentKey   псевдонимный идентификатор человека (для группировки в матрицу «человек × задание»)
testKey         идентичность теста
formKey         идентичность выданной формы/варианта (для надёжности и нормировки способности)
itemKey         идентичность задания (UUID вопроса) — стабильна между редакциями
itemVersion     версия содержания (psychoHash, см. 4.2); «версия неизвестна» без заморозки
score           набранный балл за задание (0..maxScore)
maxScore        максимально возможный балл за задание
choiceRaw       выбранный вариант(ы) — для анализа дистракторов; опционально
source          web | scorm | import:<batchId>
occurredAt      время наблюдения (для устранения дублей / «первой попытки»); опционально
```

- PA-07. Движок метрик читает только каноническую запись; прямых обращений к `attempts`/`scormAnswers`
  из расчётного слоя нет.

### 3.3 Импорт обезличенных выгрузок из LMS

Телеметрия — не единственный и не основной источник: LMS (в т.ч. WebTutor, который сейчас недоступен
для прямой интеграции) умеет выгружать результаты прохождений, и эти выгрузки должны наполнять массив
данных для аналитики.

- PA-08. Импорт принимает файл Excel (переиспользовать инфраструктуру PRD-14 `workbook`), где строка
  = один ответ одного респондента на одно задание, либо один агрегат «респондент × задание» при
  построчном формате. Конкретная схема листа (колонки, лист, режимы) определяется на этапе PRD.
- PA-09. Данные обезличены: файл несёт только **псевдонимный** `respondentKey` (стабильный в пределах
  выгрузки), без персональных данных (ФИО, e-mail, телефон, табельный номер и т.п. — данные, по
  которым можно установить конкретного человека). Импортёр валидирует отсутствие колонок с
  персональными данными и отклоняет файл при их наличии либо игнорирует лишние колонки по явному
  правилу.
- PA-10. Первичный ключ сопоставления — идентификатор взаимодействия, который SCORM-пакет пишет в
  LMS и который проносится в отчёт: `cmi.interactions.n.id = "q_<questionId>"`
  (`server/scorm/template/app/render/resultsPage.js`). Импорт снимает префикс `q_` и сопоставляет по
  нашему `questionId` (UUID). Ориентир — именно тот результат, что SCORM отправил в LMS.
- PA-10a. Псевдо-взаимодействия с иными префиксами (`topic_*`, `scale_*`, `var_*` — PRD-5/PRD-2) в
  анализ заданий не идут: импорт берёт только `q_`-префиксные строки.
- PA-10b. Если родного идентификатора нет или он искажён (старый пакет, обрезка в LMS) —
  ручной ремаппинг в интерфейсе импорта. Автоподбор по тексту вопроса — только подсказка, не молчаливое
  применение (неверная склейка портит статистику сразу двух заданий).
- PA-10c. Исход в отчёте LMS бинарный: `cmi.interactions.n.result` = correct/incorrect по порогу
  `=== 1`; у SCORM 2004 нет балла на взаимодействие. Из LMS-импорта задания вырождаются в
  дихотомические (`score in {0,1}`, `maxScore = 1`) — допустимо (дихотомия — частный случай), но
  частичный кредит недоступен. Градуированная доля балла есть только у веб-прохождений и телеметрии
  `scormAnswers`.
- PA-10d. `q_<questionId>` — это UUID вопроса, а не `contentHash`: из отчёта LMS известно, какой
  вопрос, но не его редакция. Версия контента для импортов определяется по возможности; при отсутствии
  `contentHash` наблюдения складываются в группу «версия неизвестна» и помечаются, агрегация по
  редакциям (PA-15) для них огрубляется до идентичности вопроса.
- PA-10e. Анализ дистракторов из LMS-импорта возможен, если в выгрузке присутствует выбранный вариант
  (`cmi.interactions.n.learner_response`); при агрегатном формате без него дистракторы недоступны.
- PA-11. Импорт идемпотентен и организован партиями: каждая загрузка — именованная партия (`batchId`)
  с датой/автором; повторная загрузка той же партии не дублирует наблюдения; партию можно включить,
  исключить из выборки или удалить.
- PA-12. Строки, которые не удалось сопоставить с заданием банка, попадают в отчёт импорта как
  «несопоставленные» и не участвуют в расчётах до ручного сопоставления.

Хранение: отдельная таблица импортированных наблюдений (например `imported_responses`) плюс реестр
партий (`import_batches`); живые `attempts`/`scormAnswers` не смешиваются с импортом на уровне
хранения — объединение происходит только в адаптерах канонической модели (3.1).

## 4. Ключевые методологические решения

### 4.1 Единица наблюдения — первая попытка

- PA-13. Единица наблюдения для статистики заданий и надёжности — настройка «только первая попытка»
  (переключатель) с дефолтом включено (`true`): по умолчанию берётся **первая завершённая попытка
  каждого респондента** по данной форме. Обоснование дефолта: повторные попытки нарушают независимость
  наблюдений (эффект научения/запоминания) и смещают дискриминацию и альфу.
- PA-14. При выключенной настройке (режим «все попытки») в коэффициенты идут все завершённые попытки;
  интерфейс выводит предупреждение о нарушении независимости наблюдений. Режим предназначен для
  тестов-тренажёров, где повтор — часть методики. Описательные сводки (динамика, распределения)
  режимом не ограничены.

### 4.2 Идентичность задания и версионирование (корректность при редактировании)

Правка вопроса делает ответы «до» и «после» психометрически разными заданиями. Корректность
гарантируется тем, что статистика агрегируется по отпечатку содержания, зафиксированному в момент
ответа, а не по текущей (возможно, уже изменённой) строке вопроса. Правка законна и не блокируется —
серии наблюдений разделяются по версиям.

- PA-15. Ключ агрегации любой метрики задания — пара (`questionId` — UUID вопроса; `psychoHash` —
  версия содержания). Наблюдения с разными `psychoHash` считаются разными объектами статистики и не
  суммируются.
- PA-15a. `psychoHash` — SHA-256 от полей, влияющих на «как отвечают и как оценивают»: `type`, `prompt`
  (обрезанный), `dataJson` (варианты/пары/элементы), `correctJson` (правильный ответ) и эффективная
  конфигурация оценки (цена + градуированный scoring config, разрешённые через
  `shared/scoring/effective-scoring`). НЕ входят: авторская `difficulty`, `tags`, поля обратной связи
  `feedback*`, `mediaUrl` — они не меняют поведение ответа/оценки, иначе версии дробятся напрасно.
- PA-15b. Порядок вариантов не влияет на версию: `psychoHash` строится по паре «текст варианта ->
  верность», а не по индексам вариантов. Перестановка, сохраняющая правильный ответ, новую версию не
  создаёт (позиционный анализ дистракторов — эффект второго порядка, вне охвата CTT-итерации).
- PA-15c. Обязательно к устранению (существующие пробелы кода): текущий `computeQuestionHash`
  (`server/services/questions-import.ts`) (1) не включает `correctJson` — смена ключа ответа хеш не
  меняет; (2) вычисляется только на Excel-импорте, а на обычном пути create/update вопроса
  (`server/storage.ts`, `server/routes/questions.ts`) не поддерживается (для редакторских вопросов
  `content_hash` = NULL или устаревший). `psychoHash` ДОЛЖЕН включать правильный ответ и
  вычисляться/сохраняться на КАЖДОМ создании и изменении вопроса (слой storage или БД-триггер), иначе
  разделение серий не сработает.

Замораживание версии в наблюдение — по источнику; отсюда разная сила гарантии:

| Источник | Как фиксируется версия | Сила гарантии |
| --- | --- | --- |
| Веб с публикацией (`snapshotId`, PRD-15) | Снапшот замораживает полный контент вопроса (с `correctJson`); попытка приколота к версии — `psychoHash` из снапшота | Сильная |
| Телеметрия SCORM (`scormAnswers`) | Строка встраивает выданные `questionPrompt`/`optionsJson`/`correctAnswerJson` — `psychoHash` пересчитывается из строки | Сильная |
| Веб без снапшота (черновик/preview/легаси) | `attempts` контент не хранит — требуется стамповать `psychoHash` в наблюдение при записи ответа | Средняя (после доработки) |
| Импорт из LMS | Только UUID + бинарный исход, редакция неизвестна — серия «версия неизвестна» | Слабая |

- PA-16. При правке содержания вопроса статистика новой версии начинается заново; в карточке задания —
  селектор версий с датой и объёмом `n` по каждой. Автоматического смешения версий нет.
- PA-16a. Наблюдения без замороженной версии (импорт из LMS; веб-попытки без снапшота) складываются в
  серию «версия неизвестна», помечаются и по умолчанию не смешиваются с версионированными; аналитик
  может явно разрешить смешение на свой риск (согласуется с PA-10d).

### 4.3 Политомическая (градуированная) оценка

Оценка в системе градуированная (PRD-10): `checkAnswer` возвращает долю 0..1, у ответа есть
`points`/`maxScore`. Задания — политомические, не строго дихотомические.

- PA-17. Все метрики оперируют долей балла задания `score/maxScore`, а не бинарным «верно/неверно».
  Текущий порог `=== 1` в аналитике теряет частичный кредит и в новом аппарате не применяется.
- PA-18. Точечно-бисериальная корреляция (для строго дихотомических заданий) заменяется на общий
  случай — корреляцию доли балла задания с баллом-остатком (корреляция задание–остаток), корректно
  работающую и для политомических заданий.

### 4.4 Неоднородная выдача — принятое решение

Выдача неоднородна: случайный набор с квотами (PRD-11), варианты (PRD-17), адаптив. Не каждый
респондент видит каждое задание; суммарные баллы считаются по разным наборам, что ломает базовые
допущения CTT о едином наборе.

**Решение (рекомендация принята):** считать метрики заданий везде, где объём достаточен, с явной
пометкой смещения и с корректной нормировкой:

- PA-19. Способность респондента (для группировки и корреляций) берётся как **доля балла на его
  собственной выданной форме**, а не как сырая сумма — это делает людей с разными наборами и длинами
  форм сопоставимыми.
- PA-20. Дискриминация считается как **корреляция задание–остаток**: доля балла задания против доли
  балла на остальных заданиях именно этой формы (само задание исключается из «остатка»).
- PA-21. Индекс дискриминации методом крайних групп (27%) строится на нормированной способности
  (PA-19); при неоднородной выдаче он помечается как приблизительный.
- PA-22. Для тестов с неоднородной выдачей выводится баннер: «метрики дискриминации ослаблены
  неоднородностью выдачи; читать как ориентир». Для фиксированных форм/полной выдачи банка баннер не
  показывается.

Отвергнутые альтернативы:

- «Только фиксированные формы» — выбрасывает из аналитики ядро продукта (случайная выдача, адаптив),
  покрытие слишком мало.
- «IRT для неполного дизайна» — противоречит охвату итерации (CTT), требует объёма (сотни ответов на
  задание) и библиотеки оценивания; оставлен путём развития (раздел 8), для которого накопление
  импортов из LMS создаёт данные.

### 4.5 Порог объёма и уровни доверия

- PA-23. Каждая метрика сопровождается объёмом `n` (число респондентов, видевших задание / прошедших
  форму) и уровнем доверия:

| Уровень | Порог `n` (задание) | Отображение |
| --- | --- | --- |
| Недостаточно | `n < 30` | Число не выдаётся как факт; метка «недостаточно данных» |
| Ориентировочно | `30 <= n < 100` | Число выводится с меткой ориентировочности |
| Надёжно | `n >= 100` | Число выводится без оговорок |

- PA-24. Коэффициенты надёжности теста (альфа/омега/SEM) требуют минимум порядка `n >= 30`
  респондентов на общем наборе заданий; ниже — не выводятся.

## 5. Каталог метрик итерации

### 5.1 Анализ заданий (CTT)

- PA-25. Эмпирическая трудность задания:

```text
p = mean( score_i / maxScore_i )  по респондентам, видевшим задание
интерпретация: 0.2..0.8 приемлемо; оптимум ~0.5..0.6 (с поправкой на угадывание)
флаги: p < 0.2 (слишком трудное) / p > 0.9 (слишком лёгкое)
```

- PA-26. Дискриминативность — два показателя:

```text
Индекс D (крайние группы 27%): D = p_top27 - p_bottom27  (p — средняя доля балла в группе)
  Эбель: D >= 0.40 отлично; 0.30..0.39 хорошо; 0.20..0.29 приемлемо с доработкой;
         D < 0.20 слабое; D < 0 дефект (ошибка в ключе / двусмысленность)
Корреляция задание-остаток r: доля балла задания против доли балла на остальных заданиях формы
  r >= 0.30 хорошо; r >= 0.20 приемлемо; r < 0 красный флаг
```

- PA-27. Красный флаг отрицательной дискриминации — задание, где сильные ошибаются чаще слабых
  (`D < 0` или `r < 0`): выделяется как приоритет на ревизию (вероятная ошибка ключа/формулировки).

### 5.2 Надёжность теста

- PA-28. Внутренняя согласованность:

```text
Cronbach's alpha = (k/(k-1)) * (1 - sum(var_item) / var_total)
KR-20 — частный случай для строго дихотомических заданий
ориентиры: >= 0.70 приемлемо; >= 0.80 хорошо; > 0.95 — подозрение на избыточность/дубли
```

- PA-29. Надёжность требует общего набора заданий. Для фиксированных форм (PRD-17) альфа считается
  на форме; для случайной выдачи — на общем ядре, если оно есть, иначе помечается «неприменимо к
  случайной выдаче» с пояснением. Омега Макдональда (McDonald's omega) — опциональное уточнение (не
  завышает при неравных нагрузках), кандидат на добавление.
- PA-30. Стандартная ошибка измерения и доверительный интервал порога:

```text
SEM = SD_total * sqrt(1 - alpha)
интервал вокруг проходного балла: cut +/- z * SEM
если порог попадает внутрь интервала — решение «сдал/не сдал» ненадёжно (предупреждение автору)
```

- PA-31. Прогноз Спирмена–Брауна: оценка изменения надёжности при удлинении/укорочении теста
  (сколько заданий нужно для целевой альфы).

### 5.3 Анализ дистракторов

- PA-32. Для заданий с выбором (single/multiple) по каждому варианту ответа:

```text
частота выбора: доля респондентов, выбравших вариант
корреляция варианта с баллом-остатком (выбор варианта как индикатор относительно остатка формы)
правильный вариант: корреляция должна быть положительной
дистрактор: корреляция должна быть отрицательной (его выбирают слабые)
флаги: «мёртвый» дистрактор (частота ~0); «инвертированный» дистрактор
       (положительная корреляция — привлекает сильных; вероятно частично верен / ключ неверен)
```

- PA-33. Для сопоставления/ранжирования (matching/ranking) анализ дистракторов не применяется
  (политомические задания с частичным кредитом) — вместо него работают трудность и дискриминация из
  5.1.

### 5.4 Сопоставление заявленной и наблюдаемой трудности

- PA-34. Наблюдаемая трудность (PA-25) сопоставляется с авторской `difficulty` (0..100). Существенное
  расхождение — сигнал автору (задание оказалось легче/труднее замысла); отображается как отдельный
  индикатор в карточке задания.

## 6. Архитектура

### 6.1 Слои

```text
Адаптеры источников (web / scorm / import)
        -> Каноническая запись наблюдения (раздел 3.1)
        -> Расчётный движок CTT (чистые функции, пригодные к юнит-тестам)
        -> API аналитики (расширение /api/analytics)
        -> Интерфейс: вкладка «Качество заданий / Психометрика» в разделе аналитики теста
```

- PA-35. Расчётный движок — набор чистых функций в `shared/` или `server/services/`, покрытых
  юнит-тестами на эталонных выборках (проверяемые формулы: p, D, задание–остаток, альфа, SEM). Формулы
  — единый источник, без дублей по хостам.

### 6.2 Модель расчёта

- PA-36. Расчёт по требованию с кэшированием результата, без материализованной таблицы метрик.
  Обоснование: объёмы (сотни–тысячи наблюдений) считаются за миллисекунды, а материализация создаёт
  проблему устаревания при дрейфе версий/снапшотов и импорте новых партий. Кэш сбрасывается по
  ключу (тест, версия контента, состав включённых партий, фильтр источника).

### 6.3 Поверхность

- PA-37. Новая вкладка в существующем разделе аналитики теста (`server/routes/analytics/`,
  `client/src/pages/author/`), а не отдельная страница. Реиспользуются фильтры источника/периода.
- PA-38. Экспорт психометрического отчёта в Excel (переиспользовать `analytics/export`).

## 7. Нефункциональные требования и краевые случаи

- PA-39. Обезличенность: импортируемые данные не содержат персональных данных; в хранении и экспорте
  психометрики фигурирует только `respondentKey`.
- PA-40. Область видимости аналитики соблюдает существующие права (`analyticsScope`, владелец/гранты
  теста); импортированные партии наследуют область видимости теста.
- PA-41. Пустые/скудные выборки не приводят к ошибкам: метрики деградируют до «недостаточно данных»,
  а не до `NaN`/`0` как факта.
- PA-42. Устранение дублей: при активной настройке «только первая попытка» (PA-13) повторные
  наблюдения одного `respondentKey` по одной форме сводятся к первой попытке; дубли импорта (одинаковые
  строки внутри партии) отсекаются по `batchId` (PA-11) независимо от режима.
- PA-43. Смешение источников (web/scorm/import) — это разные популяции; интерфейс всегда показывает
  состав выборки по источникам и позволяет считать по каждому отдельно.

## 8. Границы: вынесено за охват

- Item Response Theory (IRT, теория моделирования ответов на задания): модели Раша/2PL/3PL,
  информационные функции задания/теста, характеристические кривые. Путь развития: активируется по
  накоплению объёма (в т.ч. за счёт импортов из LMS) и подключению библиотеки оценивания; каноническая
  модель наблюдений (3.1) под него уже пригодна, так как штатно описывает неполный дизайн выдачи.
- Автоматизация валидности (содержательной/критериальной/конструктной): требует внешних критериев и
  экспертизы. Автоматизируемый фрагмент — матрица содержательного покрытия (тема/тег × задание) — как
  отдельный будущий отчёт.
- Анализ времени на задание: время по каждому заданию есть только в SCORM (дельты `answeredAt`) и
  приблизительно; при потребности — отдельная задача с добавлением такого замера в веб-хост.

## 9. Открытые вопросы

- OQ-01. Решено: формат импорта — Excel (инфраструктура PRD-14 `workbook`). Конкретная схема листа
  (длинная «строка = ответ» и/или агрегатная «строка = респондент × задание») определяется на этапе
  PRD.
- OQ-02. Решено: первичный ключ импорта — идентификатор взаимодействия, отправленный в LMS
  (`cmi.interactions.n.id = "q_<questionId>"`); ручной ремаппинг — запасной путь для искажённых/старых
  выгрузок; автоподбор по тексту — только подсказка. Версия контента — по возможности (PA-10d).
- OQ-03. Решено: «только первая попытка» — настройка (переключатель) с дефолтом `true`; при выключении
  — режим «все попытки» с предупреждением о нарушении независимости (для тестов-тренажёров).

## 10. Глоссарий

- **CTT** — классическая теория тестов.
- **Трудность (p)** — доля набранного балла по заданию; высокое `p` = лёгкое задание.
- **Дискриминативность** — способность задания различать сильных и слабых респондентов.
- **Корреляция задание–остаток (item-rest)** — корреляция балла задания с баллом на остальных
  заданиях формы (задание исключено из остатка).
- **Дистрактор** — неверный вариант ответа в задании с выбором.
- **SEM** — стандартная ошибка измерения; переводит надёжность в баллы для доверительного интервала.
- **respondentKey** — псевдонимный идентификатор респондента, единственный носитель «личности» в
  обезличенных данных.
