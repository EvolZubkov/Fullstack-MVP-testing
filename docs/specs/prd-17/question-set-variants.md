## Терминология

- **Вариант теста** = заранее скурированный автором, именованный **набор вопросов** из банка
  темы, привязанный к **теме** в составе теста (раздел = тема-в-тесте, `test_sections`). Выпавший
  вариант **выдаётся ЦЕЛИКОМ**, в случайном порядке (FR-15) — это фиксированный набор сценария РТК.
  (Подвыборка из варианта — выдать не весь, а `draw_count` — ВНЕ охвата v1, §9.) Термин **«вариант
  теста»** противопоставлен **«варианту оформления»** (PRD-7 `variantKindSchema`:
  `start`/`questions`/`router`/...) — разные сущности, в UI/Excel/доках называются по-разному,
  чтобы снять коллизию слова «вариант». В коде вариант теста — **`form` / `formSet`** (англ.),
  т.к. идентификатор `variant` занят вариантом оформления.
- **ВАЖНО (область действия):** вариант — НЕ на тест целиком, а **на тему**. Набор вариантов
  хранится на разделе (`test_sections`); по каждой теме вариант выбирается НЕЗАВИСИМО, **случайно,
  при старте прохождения этой темы** (ТЗ: «в каждом из разделов выпадает другой вариант»).
  Целостный прогон обучающегося складывается из одного выпавшего варианта на каждую тему;
  тест-уровневой связки «вариант 1 теста = вариант 1 каждой темы» НЕТ. Где по контексту речь о
  конкретной теме, синоним — «вариант темы».
- **Набор вариантов (`formSet`)** = список из ≥2 вариантов на тему.
- **Ротация на повторе** = при повторной попытке теме выпадает вариант, не использованный в
  предыдущих попытках обучающегося по этой теме (анти-повтор на уровне варианта, независимо по
  темам). Это **поведение по умолчанию, без переключателя** (D-9): отключать бессмысленно, а в
  SCORM всё равно не гарантировать. Обеспечивается в веб-сервисе (хранение истории); в SCORM
  невозможна (см. §1.2).

Это механизм **ДОСТАВКИ** (какие вопросы выдать), ортогональный расчёту и «Цене ответа» (PRD-10).
Вариант — отдельный **РЕЖИМ выдачи темы**: при включении «Вариантов теста» контролы выдачи из всей
темы (Все вопросы темы / Вопросов в тест / Квоты по тегам) скрываются, а источником становится
выпавший вариант, выдаваемый целиком.

## 1. Обзор

### 1.1 Контекст

Существующая выдача на тему ([app.js](../../../server/scorm/assets/app.js),
[shared/draw/blueprint.ts](../../../shared/draw/blueprint.ts)) — равномерно случайна либо
стратифицирована по тег-квотам (PRD-11). Оба режима **stateless и стохастичны**: состав формы —
случайная комбинация, не воспроизводимая между попытками и не курируемая автором.

Эталон РТК-сертификации требует иной механики (ТЗ, «Распределение вопросов по вариантам»):

> В каждом из разделов существует по три фиксированных варианта = набора вопросов. Варианты
> выпадают рандомно сотруднику. Если сотрудник совершает повторную попытку пройти тест, ему в
> каждом из разделов выпадает другой вариант.

В файле раскладки столбцы D/E/F = «1/2/3 вариант»; в строке вопроса стоит отметка в колонке того
варианта, к которому он отнесён (вопрос может входить в несколько вариантов). Фиксированный состав
нужен, в частности, под пер-вариантную калибровку порогов в постобработчике
([main.py](../../references/main/main.py), пер-вариантные коэффициенты вида
`corrected = 1.25·raw − 7.89`) — она осмысленна только для ИЗВЕСТНЫХ, неизменных наборов.

Команда ранее **приблизила** этот тест тег-квотами (файл `Сертификация_руководителей_тест_импорт.xlsx`,
листы «Структура»+«Квоты»). Это аппроксимация: квоты дают случайную комбинацию, не гарантируют
конкретный воспроизводимый состав и не дают «другой вариант на повторе». PRD-17 вводит подлинную
механику фиксированных вариантов как отдельный режим.

### 1.2 Граница реализуемости (NFR-17)

| Подмеханика | Веб-хост (сервис) | SCORM-пакет (WebTutor) |
| --- | --- | --- |
| Выбор фиксированного варианта (1 из N) | да (stateless) | да (stateless) |
| Ротация «другой вариант на повторе» | **да** (история попыток на сервере) | **нет** — нет cross-attempt-стора (`adl.data` недоступен), деградация до случайного выбора каждую попытку |

Поэтому полная механика BR-12 реализуется в **серверном (веб) хосте**; SCORM получает
фиксированный выбор без ротации (документированная деградация, §9). Это совпадает с задачей
«реализовать в сервисе».

### 1.3 Метрики успеха

| Цель | Метрика |
| --- | --- |
| Воспроизводимый курируемый состав | при заданном наборе каждая попытка выдаёт ОДИН выпавший вариант ЦЕЛИКОМ (фиксированный набор), в случайном порядке |
| Ротация на повторе (веб) | при ≤N попытках варианты по каждой теме не повторяются; при >N — цикл |
| Обратная совместимость | разделы без набора вариантов выдаются как сейчас (равномерно / тег-квоты), без изменений |
| Покрытие банка прозрачно (FR-18) | автор видит, сколько вопросов темы задействовано в вариантах и сколько осиротевших (ни в одном) |
| Прозрачность целостности | неполный вариант (вопрос ушёл из банка) виден автору и защищён на публикации |

## 2. Пользователи

- **Автор теста** — опционально задаёт на разделе набор вариантов: создаёт ≥2 именованных
  варианта, раскладывает вопросы пула по вариантам (вопрос может входить в несколько); видит
  предупреждения о неравных размерах и о неполных вариантах.
- **Обучающийся** — получает один выпавший вариант целиком; на повторе (в вебе) — другой вариант.

## 4. Модель данных

Без новых сущностей. **Вариант = именованный набор вопросов** (явный список `questionIds` из банка
темы); выпавший вариант выдаётся ЦЕЛИКОМ. В режиме вариантов существующие поля раздела
(`draw_count`/`draw_all`/`draw_blueprint_json`) НЕ применяются (источник — сам вариант, FR-03).
Ротация — поведение по умолчанию, без поля-флага (D-9).

Расширяется `test_sections` одним опциональным `jsonb`; id выпавшего варианта пишется в уже
существующий `attempts.variant_json`.

```text
test_sections.form_set_json (опционально; отсутствие = выдача из всего банка темы, как сейчас):
  forms: [ { id: string, label: string, questionIds: string[] } ]  # forms.length >= 2; questionIds >= 1
  # questionIds варианта = его состав (подмножество банка темы); выдаётся ЦЕЛИКОМ

attempts.variant_json.sections[]: { ..., formId?: string }   # стабильный id выпавшего варианта
  # questionIds в этой секции — состав варианта в случайном ПОРЯДКЕ предъявления (FR-15), запиннены
```

- `questionIds` варианта — подмножество банка темы; пересечение между вариантами разрешено (FR-06).
  Это СОСТАВ (хранение); порядок ПРЕДЪЯВЛЕНИЯ — случайный (FR-15), пиннится в `variant_json`.
- **Ключ ротации.** Чтобы история ротации не «съезжала» при правке/переупорядочивании набора,
  каждый вариант несёт стабильный `id` (а не позиционный индекс); в `variant_json` пиннится
  `formId`, ротация (FR-07) исключает по `formId`, не по позиции (R-3).
- Ротация — поведение по умолчанию: поля `rotateOnRetake` НЕТ (D-9).
- Снапшот публикации сериализует `form_set_json` без изменений (FR-11).

Схема (Zod, в `shared/schema.ts` рядом с `drawBlueprintSchema`):

```ts
formSchema = z.object({
  id: z.string().min(1),               // стабильный id варианта — ключ ротации (R-3)
  label: z.string().min(1).max(100),
  questionIds: z.array(z.string()).min(1),   // состав варианта (подмножество банка темы)
});
formSetSchema = z.object({
  forms: z.array(formSchema).min(2),
});
```

## 5. Логика выбора варианта и выдачи

Один маленький новый чистый модуль `shared/draw/forms.ts` (выбор варианта + перемешивание состава).
Парный JS-рантайм в [app.js](../../../server/scorm/assets/app.js) держится в паритете golden-тестом.

```text
selectForm(forms, { previousFormIds, shuffle }):
  # previousFormIds — id вариантов, выпадавших обучающемуся в прошлых ЗАВЕРШЁННЫХ попытках
  # по ЭТОЙ теме (веб); в SCORM всегда [] (нет cross-attempt-стора).
  candidates = forms.filter(f => !previousFormIds.includes(f.id))
  if candidates.length == 0:                 # все варианты исчерпаны -> цикл (FR-07)
      candidates = forms
  chosen = shuffle(candidates)[0]
  available = chosen.questionIds.filter(id => id в текущем банке темы)  # мягкая нехватка (FR-17)
  questionIds = shuffle(available.slice())   # весь состав, случайный порядок (FR-04/FR-15)
  return { formId: chosen.id, questionIds }
```

Точки вызова:

1. **Старт попытки** ([attempts.ts](../../../server/routes/attempts.ts), цикл по разделам):
   если `section.form_set_json` — собрать `previousFormIds` из завершённых попыток пользователя
   (по `variant_json.sections[].formId`, матч по `topicId`), вызвать `selectForm`, записать `formId`
   и `questionIds` в `variant.sections[]` (FR-08). Если набора нет — как сейчас: `drawSection` по
   всему банку темы.
2. **SCORM-рантайм**: `selectForm(forms, { previousFormIds: [], shuffle })` — случайный выбор без
   ротации (FR-14).

**Момент выбора.** Семантически вариант выпадает «при старте прохождения темы» (FR-04). В
веб-хосте состав попытки строится заранее, поэтому `formId` и выборка по каждой теме пиннятся при
построении попытки — результат эквивалентен (RNG отрабатывает один раз; история ротации берётся
из ПРОШЛЫХ попыток, а не внутри текущей). В SCORM-пакете выбор делается при рендере экрана темы.

История ротации берётся из `attempts` сервера — единственного источника, переживающего попытку
(NFR-17). Парность сервер/SCORM (с точностью до пустой истории в SCORM) фиксируется golden-тестом
порта `selectForm`.

## 6. Валидация

На сохранении раздела:

- `forms.length >= 2`, на вариант `questionIds.length >= 1` — иначе ошибка валидации (пустой
  вариант / меньше двух — сохранение блокируется).
- Каждый `questionId` варианта принадлежит текущему банку темы — иначе вариант неполный (FR-10):
  **предупреждение** (не блокирует сохранение черновика; выдаётся что есть, FR-17), но контроль
  выполнимости PRD-15 (`draw-feasibility`/`content-guard`) защищает ПУБЛИКАЦИЮ (`409` + dry-run).
- Равные размеры вариантов: неравные → **предупреждение** (влияет на честность; см. R-9). Не блокирует.
- Покрытие банка (FR-18): осиротевшие вопросы (ни в одном варианте) → **предупреждение** в строке
  темы (никогда не выдаются). Не блокирует.

  - ВЫКЛ = карточка как сейчас (Все вопросы темы / Вопросов в тест / Квоты по тегам).
  - ВКЛ = контролы выдачи из всей темы СКРЫВАЮТСЯ (источник — выпавший вариант, выдаётся целиком).
- Включён → в строке темы СВОДКА: таблица «Вариант | Вопросов в варианте» + кнопка «Настроить
  варианты…» (открывает модал) + строки итога.
- **Покрытие банка (FR-18):** строка-итог «в вариантах задействовано N из M вопросов темы ·
  K не попали ни в один вариант» с НЕблокирующим бейджем при K>0.
- Редактор вариантов — в МОДАЛЕ `ou-modal--xl` (наборы крупные, как «Обратная связь»):
  - вкладки «Вариант 1…N» (бейдж = размер) + «+ Вариант»;
  - `Transfer` «банк темы ↔ вариант»: панели на ВСЮ высоту формы; кнопки переноса «все» и
    «выбранные» (по 2 в каждую сторону); поиск в каждой панели;
  - строка вопроса: **иконка типа** (как в `content-tree` `TYPE_ICON`: `CircleDot`/`CheckSquare`/
    `Unplug`/`ListOrdered`, с тултипом — БЕЗ дублирования типа текстом), **полный текст** вопроса,
    подтема, **метки вариантов** (в какие варианты уже входит; текущий — акцентом, «—» = ни в один);
  - в подвале — покрытие банка.
  Ротации-переключателя НЕТ (поведение по умолчанию, D-9).
- Состояния (эскиз): включено (+покрытие), выключено, редактор, предупреждение о
  неполном/неравных вариантах, ошибка (<2 вариантов / пустой вариант), Пояснения+DS Mapping.
- DS-примитивы (`ou-switch`/`ou-tabs`/`ou-transfer`/`ou-modal`/`ou-banner`/`ou-tag`/`tb-table`).
  Доработки `ou-transfer` под вопросы (длинный текст с переносом, иконка типа вместо аватара,
  метки вхождения, кнопки «все», панели на всю высоту) — закрывать в ui-kit, не локальным шимом.

Перенос вопросов между вариантами/темами пересекается с будущим инструментом реорганизации тем —
свериться при дизайне.

## 8. Совместимость

- `form_set_json` опционально; отсутствие = сегодняшняя выдача (равномерная / тег-квоты), старые
  тесты не трогаются (NFR-10).
- `attempts.variant_json.sections[].formId` опционально; попытки до PRD-17 и не-вариантные
  разделы его не содержат — чтение истории ротации это терпит (отсутствие = «не участвовал»).
- Адаптивный режим независим (стратификация по сложности через `adaptive_levels`); фиксированные
  варианты — для стандартной (не-адаптивной) выдачи.
- Снапшоты PRD-15: published-доставка читает `form_set_json` из `content_json` снапшота;
  правки банка не меняют состав вариантов в полёте до републикации.

## 9. Вне охвата

- **Подвыборка из варианта** (выдать не весь вариант, а `draw_count` < размера) и **тег-квоты
  ВНУТРИ варианта** — в v1 НЕ выводятся. v1: выпавший вариант выдаётся целиком (OQ-8). Это
  backend-расширение на будущее (вариант как пул + число к выдаче); модель данных его не исключает,
  но UI/движок v1 его не реализуют.
- **Ротация на повторе внутри автономного SCORM-пакета** — нереализуема на WebTutor (NFR-17: нет
  cross-attempt-стора). В пакете — случайный выбор варианта каждую попытку (возможен повтор).
  Полная ротация — только серверный (веб) хост.
- **Пер-вариантная калибровка порогов/коэффициентов** (как `1.25·raw − 7.89` в `main.py`) — **вне
  охвата PRD-17**: бизнес отказался от выравнивания вариантов («Сейчас мы уходим от выравнивания
  вариантов, но в будущем может потребоваться вернуться к этому», ТЗ). Порог остаётся на разделе.
  Модель данных не должна исключать возврат (BR-12-07), но сам возврат — предмет ОТДЕЛЬНОГО
  будущего PRD, не расширение PRD-17.
- **Глобальная библиотека вариантов / переиспользование набора между разделами** — варианты
  скоупятся на раздел (test, topic); общих наборов нет.
- **Авто-генерация вариантов из пула** (напр. сбалансировать по тегам/сложности) — ручное
  курирование автором; авто-балансировка — возможное будущее.

## 10. Решения и открытые вопросы

| # | Вопрос | Решение |
| --- | --- | --- |
| D-1 | Коллизия термина `variant` (шаблон оформления PRD-7) | Разные имена: шаблонное — **«вариант оформления»**, эта механика — **«вариант теста»** (UI/Excel/доки). Код — `form`/`formSet` (идентификатор `variant` занят) |
| D-2 | Режим вариантов vs тег-квоты на разделе | В UI взаимоисключающи: включение «Вариантов теста» скрывает контролы выдачи из всей темы, включая квоты (FR-03). Совмещение (квоты внутри варианта) — вне охвата v1 (§9) |
| D-3 | Выдача в режиме вариантов | Вариант выдаётся ЦЕЛИКОМ (FR-04), в случайном порядке; `draw_count`/`draw_all`/квоты не применяются. Подвыборка из варианта — вне охвата v1 (§9) |
| D-9 | Ротация на повторе — настраиваемая или дефолт | Поведение по умолчанию, без переключателя и без поля `rotateOnRetake`: повтор того же варианта для оценки бессмыслен, а в SCORM не гарантируется. Веб всегда пытается дать другой вариант (FR-07) |
| D-4 | Пересечение вопросов между вариантами | Разрешено (FR-06): хранение явных `questionIds` на вариант это поддерживает; эталон РТК так и делает |
| D-5 | Источник истории ротации | `attempts.variant_json.sections[].formId` сервера (FR-08); SCORM истории не имеет (деградация) |
| D-6 | Пер-вариантные пороги (калибровка `main.py`) | Вне охвата PRD-17 (бизнес убрал выравнивание); возврат — отдельным будущим PRD; модель данных оставляет место (BR-12-07) |
| D-7 | Порядок вопросов в варианте | СЛУЧАЙНЫЙ в рамках темы (FR-15), перемешивается при выдаче и пиннится в `variant_json`; порядок хранения состава ≠ порядок предъявления |
| D-8 | Ключ ротации — позиция или стабильный id | Стабильный `formId` (R-3); позиционный индекс отвергнут как нестабильный при правке набора |
| OQ-1 | Формат вариантов в Excel | РЕШЕНО автором: КОЛОНКА «Варианты» на листе «Вопросы» — в ячейке массив вариантов вопроса через разделитель (как «Теги»). Произвольное число вариантов, multi-membership естественно, привычно автору. Presence значений у вопросов темы = секция использует варианты; число/режим — из «Структура». Хранение остаётся `form_set_json` per section (колонка — представление). Точный разделитель — в спецификации формата (консистентно с PRD-14) |
| OQ-2 | Поведение при изменении размера варианта между попытками одного обучающегося (правка после старта) | Снапшот фиксирует состав на публикации (FR-11); для live/draft — последняя редакция; согласовать на фазе снапшотов |
| OQ-3 | Нужна ли «мягкая» ротация (взвешенный выбор least-recently-used) вместо строгого исключения | v1.0 — строгое исключение + цикл (FR-07); LRU — при необходимости позже |
| OQ-4 | Нехватка вопросов (состав варианта > доступных) | РЕШЕНО автором: выдать всё, что есть, без дублирования (мягко), не блокировать; при норме — ровно количество варианта (R-1) |
| OQ-8 | Модель варианта: фиксированный список ИЛИ пул + число к выдаче | Эволюция: рассмотрена B (пул + число к выдаче, обобщает A). По итогам утверждённого эскиза v1 СУЖЕН до **A: вариант выдаётся ЦЕЛИКОМ** (FR-04/FR-16) — это сценарий РТК. Подвыборка (B) — возможное будущее (§9) |
| OQ-5 | `maxAttempts` > числа вариантов | РЕШЕНО: НЕблокирующе. После исчерпания всех вариантов ротация циклится (ре-рандом среди всех, FR-07). Жёстко связывать `maxAttempts` ≤ числа вариантов НЕ будем (это разные настройки). В редакторе — НЕблокирующее предупреждение: «вариантов меньше, чем попыток — повтор возможен с N+1-й попытки» (R-4) |
| OQ-6 | Учитывать ли НЕзавершённые (брошенные) попытки в истории ротации | РЕШЕНО: только ЗАВЕРШЁННЫЕ (`finishedAt != null`) — как retake gate и счётчик `maxAttempts`. Брошенный показ варианта в историю не идёт; текущая in-progress попытка чтит свой пин при resume, но в историю войдёт лишь по завершении (R-5) |
| OQ-7 | router/section flow: тема запиннена, но не пройдена | РЕШЕНО: вариант идёт в историю ротации только если тема была ФАКТИЧЕСКИ доставлена в той попытке (тема вошла в выданный/отвеченный состав), а не по факту пиннинга. Для линейных потоков (все темы доставляются, как в РТК) — это все темы; для router/адаптивных — только посещённые. Механизм определения «доставлена» — на фазе реализации (R-5) |

## 12. Риски, противоречия и сложности

| # | Риск / противоречие | Суть | Митигация / решение |
| --- | --- | --- | --- |
| R-1 | Нехватка вопросов в варианте (вопрос ушёл из банка) | Состав варианта может стать меньше заявленного количества | РЕШЕНО (OQ-4): выдаём всё, что есть, БЕЗ дублирования, не добивая до числа (мягкая деградация). При штатном составе (вопросов ≥ количества) выдаём ровно количество варианта. На авторском уровне — НЕблокирующее предупреждение об устаревании (R-11) |
| R-2 | ~~Конфликт философии с PRD-11~~ — снят | Раннее опасение, что вариант требует БЛОКИРУЮЩЕЙ гарантии состава вопреки мягкой нехватке PRD-11 | Снято: автор подтвердил мягкую семантику (выдать сколько есть). Оба режима — тег-квоты и варианты — деградируют одинаково мягко; расхождения нет |
| R-3 | Ротация по позиционному индексу нестабильна | Добавление/удаление/переупорядочивание вариантов смещает индексы → история ротации указывает на другой набор | РЕШЕНО: ротация по стабильному `formId`, не по позиции (D-8, §4/§5) |
| R-4 | `maxAttempts` > числа вариантов | «Всегда другой вариант» невыполнимо за пределами N попыток; при 1 варианте + ротация — всегда одно и то же | Цикл после исчерпания (FR-07) + предупреждение автору о соотношении попыток/вариантов (OQ-5) |
| R-5 | Eager-пиннинг «сжигает» вариант в router/section-flow | Состав пиннится при построении попытки, но тема может быть не пройдена (условный/адаптивный поток) → в историю попадёт невиданный вариант | История ротации — только по ФАКТИЧЕСКИ доставленным/начатым темам, не по факту пиннинга (OQ-6/OQ-7) |
| R-6 | Паритет хостов: веб ≠ SCORM | Один и тот же опубликованный тест: в вебе анти-повтор, в SCORM повтор возможен → разный учебный опыт и честность оценки | Принятое ограничение (NFR-17); в авторском UI — явная пометка «ротация работает только при веб-прохождении»; документировать в приёмке |
| R-7 | **SCORM везёт ВСЕ варианты в пакет** | Рантайм выбирает вариант локально → в ZIP попадают вопросы и КЛЮЧИ всех вариантов всех тем (РТК: ~190 вопросов на ~54 выдаваемых) → экспозиция контента + размер пакета | Принять для SCORM (выбор только клиентский); НЕ баковать эталоны ответов сверх необходимого; в вебе отдаётся только выпавший вариант (`correctJson` режется как сейчас). Отметить как известный security-trade-off хоста |
| R-8 | Оценочная валидность без калибровки | Случайный вариант разной сложности + общий АБСОЛЮТНЫЙ порог раздела = неравенство шансов между обучающимися | Принятый бизнесом риск (ТЗ: «уходим от выравнивания вариантов»). Зафиксировать как осознанный; будущая калибровка — отдельный PRD (D-6) |
| R-9 | Неравные размеры вариантов vs абсолютный порог | Порог «≥15 из 16» теряет смысл, если варианты разного размера/макс-балла | Предупреждать о неравных размерах (§6); рекомендовать равный размер; при разных — порог в долях/процентах, а не абсолют |
| R-10 | Высокое пересечение вариантов | Варианты могут делить вопросы (FR-06); при большом пересечении «другой вариант» доставляет почти те же вопросы — свежесть мнимая | Показывать overlap в редакторе; предупреждать при пересечении выше порога |
| R-11 | Целостность при правке банка | Удаление/перенос вопроса из темы делает вариант неполным; правка контента вопроса меняет то, что «зашито» в варианте | feasibility-гейт на публикации + флаг устаревания в редакторе (FR-10, паттерн `pinned_content_hash` PRD-15) |
| R-12 | Resume-детерминизм | И ВЫБОР варианта, и СЛУЧАЙНЫЙ порядок (FR-15) должны переживать восстановление сессии и не «перекатываться» | Пиннить `formId` и перемешанный `questionIds` в `variant_json` (NFR-11); на resume — читать пин, не перевыбирать |
| R-13 | Трудоёмкость и ошибки курирования | РТК: 4 темы × 3 варианта × ~16 = ручная раскладка ~190 связей; легко ошибиться в размере/покрытии | Эффективный transfer-UI (§7), счётчики размера/overlap, импорт Excel (FR-13), предупреждения валидации |
| R-14 | Варианты и тег-квоты не совмещаются в v1 | В режиме вариантов вариант выдаётся целиком, квоты не применяются (D-2/D-3) — теговую структуру варианта (РТК: Стратегия 4 / Продукты 5 / Культура 7) автор обеспечивает РУЧНЫМ курированием состава варианта | Для v1 достаточно: автор кладёт в вариант нужный теговый баланс вручную. Квоты-внутри-варианта — будущее (§9) |
