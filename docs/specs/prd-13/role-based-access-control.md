## 1. Обзор

### 1.1 Контекст

Двухролевая модель (`author` / `learner`) совмещает в роли `author` производство контента
и администрирование. PRD-13 вводит пять ролей с принципом наименьших привилегий,
разграничение доступа к тестам на уровне объекта (владелец и гранты) и
суперадминистратора, задаваемого в конфигурации.

Нормативный состав ролей, прав и матрица — в [role-model.md](../access-control/role-model.md).
PRD-13 описывает функциональные требования, изменения данных, влияние на API и миграцию.

### 1.2 Цель

Заменить роль-«бога» на управляемую модель из пяти ролей, ограничить авторов их тестами,
менеджеров — разрешёнными им тестами, и обеспечить привилегированный доступ вне приложения.

### 1.3 Метрики успеха

| Метрика | Целевое значение |
| --- | --- |
| Доля эндпоинтов, защищённых проверкой по праву | 100% непубличных эндпоинтов |
| Случаи доступа автора к чужому тесту без гранта | 0 |
| Случаи назначения менеджером теста без гранта `assign` | 0 |
| Назначение роли «Администратор» не суперадминистратором | 0 |
| Пользователи, потерявшие необходимый доступ при миграции | 0 |

## 2. Пользователи и роли

### 2.1 Суперадминистратор

Полные исключительные права на все функции и системную конфигурацию. Задаётся в
конфигурации, через UI не назначается. Единственный, кто назначает роль «Администратор».

### 2.2 Администратор

Полный набор прав на контент, пользователей, группы, назначения, шаблоны, доступ к тестам,
логи и SCORM-пакеты. Выдаёт гранты доступа к тестам и меняет владельцев. Назначает роли
вплоть до Автора и Менеджера, но не Администратора.

### 2.3 Автор

Создаёт и сопровождает темы, вопросы и тесты. Правит, публикует и экспортирует только свои
тесты и тесты с грантом `edit`; удаляет только свои. Не управляет пользователями, группами,
назначениями и шаблонами.

### 2.4 Менеджер по обучению

Создаёт группы и обычных пользователей, назначает тесты и контролирует результаты.
Назначает только тесты с грантом `assign`. Не создаёт и не правит тесты, не управляет
шаблонами.

### 2.5 Обычный пользователь

Проходит назначенные тесты, видит свои результаты и историю. Иных прав не имеет.

## 3. Функциональные требования

### 3.1 Каталог прав и карта «роль -> права»

- FR-01. В общем слое (`shared/`) определяется каталог именованных прав (capabilities) и
  карта соответствия «роль -> множество прав» согласно
  [role-model.md](../access-control/role-model.md) (разделы 3 и 4).
- FR-02. Карта прав — единственный источник истины; серверный и клиентский код используют
  её, не дублируя списки прав.

### 3.2 Серверная проверка прав

- FR-03. Вводится middleware проверки по праву (например `requirePermission('tests.edit')`),
  заменяющий россыпь проверок конкретной роли (`requireAuthor` и аналогичные).
- FR-04. Для прав с областью (см. раздел 6 матрицы) проверка дополняется резолюцией
  владельца или гранта по конкретному тесту.
- FR-05. На каждый запрос вычисляется эффективный набор ролей (роли из `user_roles` плюс
  права суперадминистратора по совпадению email из конфигурации); итоговые права —
  объединение прав всех ролей набора.

### 3.3 Суперадминистратор из конфигурации

- FR-06. Список адресов задаётся переменной окружения `SUPERADMIN_EMAILS` (через запятую).
- FR-07. Пользователь, чей email входит в список, получает права суперадминистратора
  независимо от роли в БД.
- FR-08. При старте приложения для каждого адреса выполняется автопровижининг: учётная
  запись создаётся, если отсутствует, без назначенных ролей (`user_roles` пуст);
  существующим учётным записям роли не добавляются.
- FR-09. Права суперадминистратора нельзя выдать или отозвать через UI; статус вычисляется
  на каждый запрос и не кэшируется в сессии, поэтому исключение адреса из `SUPERADMIN_EMAILS`
  немедленно прекращает права SU, оставляя только явно назначенные роли (у автопровиженной
  учётной записи — ни одной). Вход не блокируется, остаточного администратора не возникает.

### 3.4 Назначение ролей

- FR-10. Роли назначаются и отзываются по одной с соблюдением потолка (см. role-model.md,
  раздел 7): суперадминистратор — любые роли кроме суперадминистратора; администратор —
  Автор, Менеджер, Обычный пользователь; менеджер — Обычный пользователь только при
  создании. Отзыв роли требует тех же полномочий, что и её выдача.
- FR-11. Роль «Администратор» назначает только суперадминистратор (право
  `system.roles.assignAdmin`).
- FR-12. Администратор не может изменить или понизить учётную запись суперадминистратора.
- FR-13. Попытка назначить роль выше потолка отклоняется с кодом 403.

### 3.5 Владелец теста

- FR-14. У теста есть владелец (`tests.ownerId`). При создании владельцем становится
  создатель.
- FR-15. Владельца меняет только администратор или суперадминистратор
  (`PATCH /api/tests/:id/owner`).
- FR-16. Владелец отображается в карточке и настройках теста.

### 3.6 Гранты доступа к тесту

- FR-17. Доступ к тесту выдаётся грантом уровня `edit` (для авторов) или `assign` (для
  менеджеров) в таблице `test_access_grants`.
- FR-18. Гранты выдаёт и отзывает только администратор или суперадминистратор
  (`GET/POST/DELETE /api/tests/:id/access`).
- FR-19. На пару «тест + пользователь» допускается один грант.
- FR-20. Появляется административная панель управления доступом к тесту: владелец и список
  грантов с возможностью добавить и отозвать.

### 3.7 Разрешение доступа к тесту

- FR-21. Действия над тестом разрешаются по алгоритму резолюции из role-model.md
  (раздел 6.4): роль допускает действие, владелец или грант допускают конкретный тест.
- FR-22. Удаление и архивирование теста доступны только владельцу (и AD/SU), но не
  держателям гранта `edit`.

### 3.8 Прохождение тестов по факту назначения

- FR-23. Право `attempts.take` доступно любой роли; фактический доступ к прохождению
  определяется наличием назначения теста пользователю, а не его ролью.

### 3.9 Фильтрация списков по области видимости

- FR-24. `GET /api/tests` и аналитика возвращают только тесты в области видимости роли:
  Автор — владение и гранты `edit`; Менеджер — гранты `assign`; Администратор и
  Суперадминистратор — все; Обычный пользователь — назначенные.

### 3.10 Клиентская модель

- FR-25. `ProtectedRoute` и навигация строятся по картам прав, а не по жёсткому списку
  `allowedRoles` из двух значений.
- FR-26. Состав меню и доступных страниц соответствует объединённым правам набора ролей
  пользователя (например, пользователь с ролями Автор и Менеджер видит и контентные, и
  управленческие разделы).
- FR-27. UI скрывает действия, недоступные по правам; сервер остаётся источником истины и
  дублирует проверку.

### 3.11 Несколько ролей у пользователя

- FR-28. Пользователю можно назначить произвольный набор ролей из
  `{ administrator, author, manager, learner }`; права — объединение прав ролей набора.
- FR-29. Редактор пользователя предоставляет множественный выбор ролей; список доступных
  для выдачи и отзыва ролей ограничен потолком текущего субъекта (FR-10).
- FR-30. Стартовая страница пользователя с несколькими ролями определяется приоритетом
  ролей (Администратор, затем Автор, затем Менеджер, затем Обычный пользователь); смена
  активного раздела выполняется через навигацию.

### 3.12 Миграция данных

- FR-31. При миграции значение `users.role` каждого пользователя переносится в `user_roles`
  без потери доступа (действующие `author` получают роль «Администратор» — см. раздел 6).
- FR-32. После перехода столбец `users.role` удаляется; единственный источник истины по
  ролям — `user_roles`.

## 4. Изменения данных (схема)

### 4.1 Роли пользователя (многие-ко-многим)

- Вводится таблица `user_roles`: `id`, `userId` (FK -> `users.id`, cascade), `role`
  (`{ administrator, author, manager, learner }`), `grantedBy` (FK -> `users.id`),
  `grantedAt`. Уникальность по паре `(userId, role)`.
- Значение `superadmin` в перечислении ролей не вводится: суперадминистратор вычисляется
  из конфигурации.
- Поле `users.role` (единственная роль) выводится из эксплуатации: его значение переносится
  в `user_roles` при миграции, далее столбец удаляется во избежание двойного источника
  истины.

### 4.2 Владелец теста

- Добавляется `tests.ownerId` (`varchar(36)`, nullable, FK -> `users.id`).

### 4.3 Таблица грантов доступа

- Создаётся `test_access_grants`: `id`, `testId` (FK, cascade), `userId` (FK, cascade),
  `accessLevel` (`{ edit, assign }`), `grantedBy` (FK -> `users.id`), `createdAt`.
- Уникальность по паре `(testId, userId)`.

### 4.4 Миграция данных

- Перенос текущего значения `users.role` каждого пользователя в строку `user_roles`.
- Бэкфилл `tests.ownerId` значением учётной записи суперадминистратора (по первому адресу
  из `SUPERADMIN_EMAILS`), чтобы тесты не остались без владельца.
- Перевод действующих `author` (см. раздел 6).

## 5. Влияние на API

Полное сопоставление эндпоинтов с правами — в role-model.md, раздел 9. Сводно:

| Группа эндпоинтов | Требуемое право | Область |
| --- | --- | --- |
| Контент (темы, вопросы, папки) | `topics.manage`, `questions.manage`, `folders.manage` | — |
| Тест: чтение и список | `tests.read` | по доступу |
| Тест: создание | `tests.create` | — |
| Тест: правка, оформление, показатели, шкалы | `tests.edit` | edit |
| Тест: публикация, восстановление | `tests.publish` | edit |
| Тест: удаление | `tests.delete` | владелец |
| Тест: экспорт SCORM | `tests.export.scorm` | edit |
| Тест: доступ и владелец (новые эндпоинты) | `tests.access.grant`, `tests.owner.change` | — |
| Назначения | `assignments.manage` | assign |
| Группы | `groups.manage` | — |
| Пользователи: чтение, создание, правка, роли | `users.read`, `users.create`, `users.manage`, `users.role.assign` | потолок роли |
| Аналитика | `analytics.read`, `analytics.export` | по доступу |
| Шаблоны: каталог и админ-реестр | `templates.read`, `adminTemplates.manage` | — |
| SCORM-пакеты | `scormPackages.manage` | — |
| Логи | `logs.read` | — |
| Прохождение и свои результаты | `attempts.take`, `attempts.self.read` | по назначению |

Новые эндпоинты:

- `GET /api/tests/:id/access` — владелец и список грантов;
- `POST /api/tests/:id/access` — добавить грант `{ userId, accessLevel }`;
- `DELETE /api/tests/:id/access/:userId` — отозвать грант;
- `PATCH /api/tests/:id/owner` — сменить владельца.

## 6. Миграция и обратная совместимость

### 6.1 Действующие учётные записи

Существующие `author` де-факто совмещают права автора и администратора. Значение
`users.role` каждого пользователя переносится в `user_roles` (одна строка на пользователя).
Чтобы никто не потерял доступ, все `author` получают роль «Администратор», после чего
команда вручную корректирует наборы ролей: чистым авторам оставляет «Автор», операционным
сотрудникам — «Менеджер» (при необходимости совмещая «Автор» и «Менеджер» в одном наборе),
снимая «Администратор» там, где он не нужен. Учётные записи `learner` получают роль
«Обычный пользователь».

Альтернатива (оставить всех «Авторами» и повышать вручную) отклонена: она временно лишает
действующих администраторов их функций. Решение по умолчанию подтверждается на этапе плана.

### 6.2 Legacy-тесты

У существующих тестов владельца не было. Бэкфилл проставляет владельцем суперадминистратора;
далее администратор переназначает владельцев реальным авторам через UI (в том числе в
рамках понижения ролей по пункту 6.1).

### 6.3 Поэтапное включение

Жёсткие запреты включаются после прохождения приёмочных проверок по матрице, чтобы выявить
сценарии, ошибочно теряющие доступ.

## 7. Критерии приёмки

| Код | Критерий |
| --- | --- |
| AC-01 | Все пять ролей заведены; права соответствуют матрице role-model.md |
| AC-02 | Каждый непубличный эндпоинт защищён проверкой по праву |
| AC-03 | Автор не может открыть на правку, опубликовать или экспортировать чужой тест без гранта `edit` |
| AC-04 | Автор не может удалить тест, владельцем которого не является |
| AC-05 | Менеджер не может назначить тест без гранта `assign` |
| AC-06 | Гранты и смену владельца выполняет только администратор или суперадминистратор |
| AC-07 | Роль «Администратор» назначается только суперадминистратором; иное даёт 403 |
| AC-08 | Менеджер при создании пользователя задаёт только роль «Обычный пользователь» |
| AC-09 | Адрес из `SUPERADMIN_EMAILS` получает права суперадминистратора и автопровижинится при старте |
| AC-10 | Списки тестов и аналитика отфильтрованы по области видимости роли |
| AC-11 | После миграции ни один пользователь не теряет необходимый доступ |
| AC-12 | Пользователь с несколькими ролями получает объединение их прав; меню и доступ отражают объединение |
| AC-13 | Редактор пользователя позволяет выбрать несколько ролей в пределах потолка субъекта |
| AC-14 | Документы markdown проходят markdownlint |

## 8. Перспектива (вне объёма фазы 1)

- Понятие «Организация» и разграничение менеджеров по «своим» пользователям и группам.
- Корпоративная аутентификация и единый вход (см. PRD-9 и план требований архитектуры).
- Делегирование выдачи доступа владельцу теста.
- Гранулярность прав ниже уровня домена.
