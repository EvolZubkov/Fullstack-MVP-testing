## 1. Задача

### 1.1 Что показал разбор

Референсный отчёт устроен как дерево, а не как список: два именованных блока
(«Управленческие компетенции» и «Знания»), внутри каждого — четыре раздела с чипом уровня и
счётчиком «сколько разделов на целевом уровне», а внутри разделов знаний — полосы по подтемам.
Ни одного числа во всём документе: только уровни, полосы и счётчик. Вердикт конъюнктивный —
все восемь разделов должны быть на целевом уровне.

Тест уже собран в сервисе, и книга показывает, какой ценой. Подтемы сделаны одиннадцатью
шкалами, повторяющими одиннадцать тегов, и листом «Вклады вопросов» на 464 строки. Лист проверен
целиком: в 436 вариантных строках (109 вопросов) вклад равен `1/|верных вариантов|` на верных
позициях и нулю на остальных, в 28 парных строках (7 вопросов на сопоставление) — `1/|пар|`,
**без единого исключения**. То есть весь лист механически выводится из колонки «Номера правильных
ответов» — автор руками продублировал то, что в тесте уже записано дважды, и любая правка вопроса
требует синхронной правки вкладов, а рассинхрон ничем не ловится.

Прочие факты книги, на которые опирается спецификация:

- разбиение чистое: вопросов с двумя тегами — 0, вопросов без тега — 32, и это ровно четыре
  раздела компетенций целиком; сумма квот точно равна размеру выборки во всех четырёх знаниевых
  разделах (16, 10, 12, 10);
- выдача детерминирована: разделы работают в вариантном режиме, и все 33 пары
  «вариант x тег» совпадают с квотой ровно, без запаса;
- цена вопроса разная — 1, 2 и 3 балла, ступенчатая цена у 77 вопросов, поэтому балльный
  знаменатель подтемы плавает: семь вопросов «Корпоративной культуры» по квоте могут стоить
  от 7 до 16 баллов в зависимости от выборки;
- два вопроса («Технологии», тег «Цифровая экономика») не входят ни в один вариант и не будут
  выданы никогда — автор об этом ниоткуда не узнает.

### 1.2 Чего не хватает

Три дефицита, и все три — одна и та же нехватка вложенности в модели результата.

1. **Подытога по ключу нет.** Тег доходит только до выдачи: `AggregateQuestion` тегов не несёт,
   а акцессор `tag()` в формулах жив только на бумаге — контекст ему подают пустой
   (`tags: {}` в `server/services/result-compute.ts` и то же самое в `resultsPage.js`), поэтому
   формула с тегом проходит валидацию и молча возвращает нули.
2. **Разделы плоские.** Группировки разделов в блоки нет ни в схеме, ни в контексте рендера, и
   счётчик «пройдено N из M» по группе взять неоткуда.
3. **Карточка темы не имеет вложенного уровня**, а подпись её вердикта зашита в код
   («Пройдено» / «Не пройдено», `shared/template/result-context.ts`), поэтому своя терминология
   методики в отчёт не попадает.

## 2. Решения, которые нельзя пересматривать

1. **Разрез — общий механизм, а не «полосы подтем».** Ядро считает агрегат по абстрактной оси;
   тег — первая и пока единственная зарегистрированная ось. Вторая ось (сложность, тип вопроса,
   тема-владелец) добавляется одной функцией, без изменения структуры данных и без миграции.
2. **Ключ подытога — тройка (область, ось, ключ), и область раздела определяется РАЗДЕЛОМ
   ВЫДАЧИ**, а не темой-владельцем вопроса. Один тег может жить в нескольких разделах; в каждом
   он даёт свою запись, плюс отдельную запись в области теста.
3. **Вердикт всегда в баллах, показ — по выбору автора.** Порог ключа сравнивается с балльной
   долей, той же валютой, что и порог раздела. Иначе переключение вида отображения меняло бы
   вердикт.
4. **Умолчание показа — нормированная база** (вес вопроса равен единице). Знаменатель тогда равен
   числу выданных вопросов с ключом, то есть константе при квоте «Ровно N», и полосы разных
   учеников сравнимы. Балльная база остаётся в записи вторым числом.
5. **Выдача и оценка хранятся раздельно.** Квота живёт в `draw_blueprint_json`, порог ключа — в
   своей структуре. Порог без квоты осмыслен, квота без порога — тем более. В редакторе это одна
   таблица, в данных — две структуры.
6. **Отсутствие новых полей означает сегодняшнее поведение** — на живых тестах, в старых попытках,
   в снимках публикации и в уже собранных SCORM-пакетах.
7. **Гейт по разрезу существует только в области раздела.** Тестовый гейт уже выразим показателем
   с «Управляет статусом»; второй путь к вердикту не заводится.
8. **Ничего из перечисленного не выводится из референса буквально.** Словарь уровней, градиент
   полосы, вёрстка страниц и срок годности результата остаются за границей задачи (§12).

## 3. Модель разреза

### 3.1 Запись разреза

Разрез — агрегат по выданным элементам попытки, сгруппированным по ключу оси в пределах области.

```text
{ scope,          // "test" | "section:<sectionId>"
  axis,           // "tag"
  key,            // значение по оси, например "Персональные данные"
  items,          // сколько выданных вопросов попало в ключ
  answered,       // сколько из них отвечено
  earned,         // сумма заработанных баллов
  possible,       // сумма возможных баллов
  unitEarned,     // сумма долей (earned/possible каждого вопроса), вес вопроса = 1
  unitPossible }  // = items
```

- **FR-01.** Запись считается по ВЫДАННЫМ элементам попытки. Вопрос, не попавший в выдачу, не
  влияет ни на числитель, ни на знаменатель.
- **FR-02.** Значение вопроса в нормированной базе равно `earned/possible` этого вопроса и лежит
  в диапазоне 0…1. Вопрос без возможных баллов (измерительный) в разрез не попадает.
- **FR-03.** Производные величины `percentPoints = earned/possible` и
  `percentUnits = unitEarned/unitPossible` вычисляются ядром, а не шаблоном.
- **FR-04.** Область теста считается отдельным проходом по всем выданным элементам, а не
  суммированием секционных записей. Вопрос, выданный в двух разделах, учитывается дважды: это
  свойство выдачи, и молча его схлопывать опаснее, чем показать как есть.
- **FR-05.** Ключи одного разреза не обязаны разбивать выборку: вопрос может нести несколько
  ключей или ни одного. Сумма записей не обязана сходиться с итогом раздела, и подавать разрез
  как разложение раздела нельзя (см. FR-33, FR-45).

### 3.2 Ось

- **FR-06.** Ось задаётся парой «имя оси, функция извлечения ключей из выданного вопроса».
  В этой редакции регистрируется одна ось: `tag` из `questions.tags`.
- **FR-07.** Регистрация второй оси не требует изменений в хранении, контракте шаблона и
  контексте формул.
- **FR-08.** Редактор, книга Excel и настройки теста в этой редакции говорят только про теги.

## 4. Хранение

| Что | Где | Отсутствие означает |
| --- | --- | --- |
| Записи разрезов попытки | `attempts.result_json`, рядом с `topicResults` | пересчитывается из ответов |
| Пороги ключей | `test_sections.breakdown_rules_json` (новое поле) | ключи информационные |
| Группы разделов | `tests.section_groups_json` (новое) + `test_sections.group_key` (новое) | сегодняшний плоский список |
| Подписи вердикта и заголовок блока | ключи в существующем `design_settings_json.labels` (PRD-49) | подписи шаблона |
| Видимость и база показа разреза | настройки теста (содержание, не оформление) | разрез скрыт |

```json
{
  "axis": "tag",
  "default": { "type": "percent", "value": 60 },
  "keys": {
    "Персональные данные": { "type": "percent", "value": 80 },
    "Антикоррупционная политика": { "type": "none" }
  }
}
```

- **FR-09.** Новых таблиц не заводится.
- **FR-10.** `breakdown_rules_json` хранит только оценку. Состав выдачи по ключам остаётся в
  `draw_blueprint_json` и не дублируется.
- **FR-11.** `tests.section_groups_json` — упорядоченный список `{ key, label, order }`;
  `test_sections.group_key` ссылается на элемент этого списка или пуст.
- **FR-12.** Ключ группы, на который не ссылается ни один раздел, допустим (пустая группа не
  печатается). Ссылка на несуществующий ключ трактуется как отсутствие группы.
- **FR-13.** Видимость разреза — три положения: `hidden`, `bar`, `bar_and_value`; база показа —
  `units` (умолчание) или `points`. Обе настройки на уровне теста, одна на все поверхности.

## 5. Движок

- **FR-14.** Вычисление живёт в новом чистом модуле `shared/breakdown/` и ничего не знает о
  хостах. Модуль едет в общий бандл `shared-runtime`, поэтому JS-двойника для SCORM не будет.
- **FR-15.** `AggregateQuestion` получает необязательное поле `axisKeys`. Веб-хост заполняет его
  из БД, пакет SCORM — из `TEST_DATA`. Теги стандартных разделов туда уже выпекаются
  (`server/scorm/builders/test-json.ts`, условно при непустом списке — их требует
  стратифицированная выдача PRD-11); у адаптивных разделов их нет, и выпечку нужно добавить.
- **FR-16.** Порядок в `aggregateStandardResult`:
  1. разрезы в области каждого раздела;
  2. вердикт темы — порог раздела И все заданные пороги ключей;
  3. разрезы в области теста;
  4. вердикт теста по существующей политике `pass_decision_policy`.
- **FR-17.** Разрезы считаются и для адаптивного результата, поскольку `adaptiveResultAsStandard`
  приводит его к той же форме.
- **FR-18.** Попытка без `axisKeys` даёт пустой список разрезов и ни на что не влияет.

## 6. Гейт по ключам разреза

- **FR-19.** Правило темы получает источник «по ключам разреза». Тема пройдена, когда выполнен
  порог раздела И все заданные пороги её ключей.
- **FR-20.** Порог ключа берётся из `keys[<ключ>]`; при отсутствии — из `default`; при отсутствии
  и его ключ информационный.
- **FR-21.** Порог сравнивается с `percentPoints` независимо от выбранной базы показа (решение 3).
- **FR-22.** Ключ, не появившийся в выдаче (`items = 0`), порогом не проверяется и вердикт темы не
  роняет; при публикации это предупреждение (FR-46).
- **FR-23.** Гейта в области теста нет (решение 7).

## 7. Группы разделов

- **FR-24.** Уровень вложенности ровно один: тест содержит группы, группа содержит разделы.
  Дерева групп нет.
- **FR-25.** Разделы без группы печатаются после всех групп в своём порядке, как сегодня.
- **FR-26.** Ядро считает по группе `passedCount` (разделы с пройденным вердиктом) и `totalCount`
  (разделы с вынесенным вердиктом). Раздел без вердикта в знаменатель не входит.
- **FR-27.** Отсутствие групп даёт ровно сегодняшний плоский список карточек.

## 8. Контракт шаблона

### 8.1 Контекст

```text
result.topicResults[].breakdown[]   // область раздела: внутри карточки темы
  { key, items, answered,
    percent, percentUnits, percentPoints, earned, possible,
    barPercent,                     // округлено для вёрстки
    showValue, valueLabel,          // печатать ли число и готовая подпись
    passed,                         // true | false | null (порога нет)   — с Э2
    passClass, statusLabel }        // подготовлено ядром, как у тем      — с Э2

result.topicGroups[]                // группы разделов                    — с Э3
  { key, label, topics[], passedCount, totalCount, counterLabel }
```

Три поля вердикта (`passed`, `passClass`, `statusLabel`) заполняются только тогда, когда у ключа
есть порог, то есть с Э2; до него их нечем наполнить, кроме `null`. Остальные поля обязаны быть
в строке С САМОГО НАЧАЛА, даже когда шаблон печатает одну полосу: сторонний шаблон из реестра
PRD-3 не может показать «верно 4 из 7», если чисел нет в контексте, а добавление поля позже —
это правка контракта, которую придётся возить по обоим хостам. `showValue` и `valueLabel`
готовит ядро по выбранной базе показа, чтобы раскладка не решала форматирование сама.

- **FR-28.** Разрез в области теста печатается отдельным блоком итогов: новый ключ `breakdown`
  в `ResultsBlockKey`, в умолчании порядка блоков и в манифестном `resultsBlockOrder`. Автор
  двигает и переименовывает его там же, где шкалы и показатели.
- **FR-29.** Группы называются `result.topicGroups`: имя `result.blocks` уже занято списком
  блоков итогов (PRD-49).
- **FR-30.** Шаблон, не знающий ключа `breakdown`, просто его не печатает; контракт не ломается,
  сторонние шаблоны из реестра PRD-3 продолжают работать.
- **FR-31.** Настройка видимости (FR-13) общая для обеих проекций: при `hidden` не печатается ни
  одна. Блочная проекция дополнительно управляется составом и порядком блоков итогов (PRD-49),
  вложенная печатается всегда, когда разрез видим и в карточке темы есть хотя бы один ключ.
- **FR-32.** При `bar` число не печатается ни на одной поверхности, при `bar_and_value` печатается
  величина выбранной базы.
- **FR-33.** Разрез печатается списком ключей и никогда не подписывается как разложение раздела на
  части.

### 8.2 Подписи

- **FR-34.** Новые ключи в существующем словаре надписей PRD-49: `topic.verdict.passed`,
  `topic.verdict.failed`, `results.breakdown`, `group.counter` (формат вида `{passed} / {total}`).
  Умолчания объявляет шаблон, тест хранит только отклонения, выключение — тумблером.

## 9. Формулы

- **FR-35.** `ctx.tags` и `ctx.sections` заполняются по-настоящему на обоих хостах вместо
  сегодняшних пустых объектов.
- **FR-36.** Область раздела адресуется СОСТАВНЫМ ключом того же акцессора:
  `tag("<код или id раздела>::<ключ>")`, а вызов с простым ключом сохраняет смысл «в области
  теста». Грамматика DSL не меняется, поэтому не трогаются ни разборщик, ни его плоский
  JS-двойник, ни золотой корпус. Приём не новый: `topicById()` уже принимает и UUID, и авторский
  код темы, потому что карта контекста заполнена обоими ключами.
- **FR-37.** Переименование тега правит формулы существующим механизмом `shared/formula/rename`.

## 10. Снимки, аналитика, паритет хостов

- **FR-38.** Снимок публикации несёт `section_groups_json`, `breakdown_rules_json` и словарь
  надписей: иначе отчёт по старой попытке поедет от первой же правки теста.
- **FR-39.** Записи разрезов сохраняются в `attempts.result_json`, поэтому доступны аналитике и
  выгрузке без пересчёта. Экраны аналитики в эту редакцию не входят.
- **FR-40.** Веб и пакет считают разрезы одним и тем же кодом; расхождение проверяется зеркальным
  тестом на общем наборе данных.
- **FR-41.** Телеметрия SCORM новых полей не получает.

## 11. Редактор и предупреждения при публикации

- **FR-42.** Таблица «раздел x ключ» показывает в одной строке квоту выдачи, порог и число
  вопросов с этим ключом, попадающих в каждый вариант.
- **FR-43.** Раздел получает поле «блок»; список блоков теста редактируется рядом со структурой.
- **FR-44.** Видимость и база показа разреза живут в настройках теста (содержание), а не в
  оформлении.

Предупреждения при публикации — предупреждения, не запреты:

- **FR-45.** ключи не разбивают выборку раздела (сумма квот не равна размеру выборки либо есть
  выданные вопросы без ключа);
- **FR-46.** задан порог для ключа, который не появляется ни в одном варианте, — гейт недостижим;
- **FR-47.** вопрос не входит ни в один вариант и не будет выдан никогда; заданы одновременно
  квоты и варианты, из-за чего квоты не применяются.

### FR-48. Разрез в адаптивном режиме

Экран итогов адаптивного теста и его отчёт печатают сводный блок области теста — тот же блок,
те же строки и тот же гейт, что в обычном режиме. Состав подблоков этого экрана объявляет
манифест шаблона (`resultsBlockOrder["results.adaptive"]`), разрез стоит в нём последним.

Разрез РАЗДЕЛА в адаптивном режиме не печатается: карточка темы там говорит подтверждённым
уровнем, а не процентом. Доля правильных внутри темы при адаптивной выдаче считается по
неравномерной по уровням выборке, поэтому полоса рядом с «Уровень 2» предлагала бы читателю
смысл, которого у лестницы нет. Блок области теста этой проблемы не имеет — он отвечает на
другой вопрос и с уровнями не спорит.

Следствие для настройки «Где показывать подытоги» (FR-44): в адаптивном тесте значение
«В карточках тем» не печатает ничего. Выбор автора при этом НЕ подменяется молча значением
«блоком» — поле говорит об этом подсказкой. Молчаливая подмена ответа автора хуже честного
ограничения режима.

## 14. Приёмка

1. Тест из книги `workbook_Сертификация_руководителей_в__.xlsx` собирается БЕЗ листа «Вклады
   вопросов» и без одиннадцати шкал, а полосы подтем в отчёте совпадают со снятыми с референса
   значениями с точностью до правил частичного зачёта.
2. Тег, заведённый в двух разделах, даёт три записи: по разделу каждого и одну сводную; сводная
   печатается блоком `breakdown`, секционные — в карточках тем.
3. Порог ключа роняет вердикт темы, а изменение базы показа вердикт не меняет.
4. Тест без единого нового поля даёт побайтово прежний экран итогов и прежний PDF.
5. Веб-хост и SCORM-пакет печатают одинаковые разрезы на одной и той же попытке.
6. Публикация выдаёт все четыре предупреждения на подготовленном тесте-ловушке и ни одного —
   на тесте из книги, кроме предупреждения о двух вопросах вне вариантов.

## 15. Дополнение 2026-09-02: ключ как единица результата

Решение владельца. Компетенция, подтема, любой другой разрез — это ТЕГ ВОПРОСА внутри темы, и
второго уровня группировки для него заводить не нужно. Выдача по тегу уже управляется квотами,
итог по тегу уже считается и хранится с попыткой; не хватает двух вещей, и обе — на самом ключе.

- **FR-49. У ключа нет вердикта вовсе — подтему нельзя провалить.** Ключ не судится ни своим
  порогом, ни порогом темы: он ИНФОРМАЦИОННЫЙ по построению. Считается и показывается только
  итог — доля в процентах или в баллах, по настройке базы, — и только если показ включён.

  Что это отменяет: пороги по ключам (`test_sections.breakdown_rules_json`, FR-09/FR-10) и
  участие ключа в вердикте темы (FR-19 - FR-23). Тема судится своим правилом и только им;
  `applyBreakdownGate` и поле `passed` у записи разреза становятся не нужны, строка разреза
  печатается без метки исхода и без классов `is-pass`/`is-fail`. Предупреждения публикации о
  недостижимом пороге ключа (FR-46) теряют предмет.

  **Совместимость.** У тестов, где пороги ключей заданы (на стенде такой есть: «Стратегия
  компании» — 80 % при пороге темы 70 %), вердикт темы может измениться: тема, проваленная
  из-за подтемы, станет пройденной. По решению владельца это исправление, а не регресс —
  подтема не должна была решать судьбу темы. Сданные попытки не меняются: их результат заморожен
  снимком.

- **FR-50. Обратная связь и рекомендации на ключ.** Ключ получает собственный текст, ссылки на
  курсы, мероприятия и вложения — в том же формате, что и тема (`feedback_json`: `format`,
  `text`, `links`, `assets`, `events`). Редактируется в
  разделе обратной связи редактора, рядом с обратной связью тем. До этой правки текст мог висеть
  только на теме, и поэтому компетенции приходилось заводить темами.

  **Правило выдачи (владелец, 2026-09-03).** Текст ключа выдаётся, когда результат по ключу
  НИЖЕ общего проходного порога теста, — при ЛЮБОМ вердикте теста и темы. Первая редакция
  требования говорила «по правилу исхода ключа», но исхода у ключа больше нет: вердикт ключа
  снят тем же владельцем (ключ считается и показывается, но не судится), и привязывать текст
  стало не к чему. «При любом вердикте» — часть правила: провал по одному ключу внутри сданного
  теста и есть тот случай, ради которого текст пишут; обратная связь ТЕМЫ, которую гасит
  пройденная тема, ведёт себя иначе, и это сознательное расхождение.

  Уточнения реализации: сравнивается доля БАЛЛОВ ключа (порог теста задан в баллах, доля
  вопросов — другая величина); порог, заданный суммой баллов, переводится в долю от
  достижимого; теста без общего порога сравнивать не с чем — тогда условия нет, и текст
  выдаётся везде, где автор его написал. Правило живёт в `shared/breakdown/feedback` и
  работает одинаково на экране итогов, в отчёте и в SCORM-пакете.
- **FR-51 (отклонено).** Счётчик «пройдено N из M ключей» НЕ заводится: если автору нужен
  счётчик по группе, он заводит тему и оперирует темой. Блоки разделов (FR-11, FR-12, FR-24 -
  FR-27) сохраняются как есть для уже собранных тестов, но не развиваются; целевая модель —
  разрез по тегам.

Состав правки при реализации: хранение обратной связи ключа (новая структура рядом с правилами
ключа либо своя таблица), редактор в разделе обратной связи, выдача текста обоими хостами,
заморозка в снимке публикации, лист книги Excel, формат переноса `.tbtest` и SCORM-пакет.

## 16. Дополнение 2026-09-04: подтема судится порогом своей темы

Решение владельца. §15 снял у подтемы вердикт вместе с порогом — и оставил полосу без ориентира:
«Управление рисками — 73 %» не говорит читателю, хорошо это или плохо, а текст обратной связи
пришлось привязывать к общему порогу теста, то есть к порогу, который подтеме никто не назначал.
Критерий при этом в продукте уже есть — порог темы.

Индивидуальные пороги подтем признаны избыточными и вредными: подтема несёт два-четыре вопроса,
и собственный порог на такой выборке означает «ошибся один — провал», а числа автор выставляет
наугад. Автору, которому нужен порог, отличный от порога темы, ответ один: завести отдельную тему.
Тема — сущность, которая уже умеет и порог, и вердикт, и участие в правиле «Тест пройден, если».

- **FR-52. Порог подтемы производный; своих чисел у подтемы нет.** Подтема живёт по правилу своей
  темы:
  - у темы собственный порог («Свой», «По вариантам») — он же порог её подтем;
  - у темы «Как у теста» — порог теста;
  - у темы «Не проверять отдельно» либо порога нет вовсе — у подтем порога нет: тема молчит,
    молчат и её подтемы;
  - строки СВОДНОГО блока (область теста) судятся общим порогом теста: темы у них нет.

  Сравнивается доля БАЛЛОВ подтемы (`percentPoints`) независимо от выбранной базы показа — как
  и вердикт темы, и как правило выдачи текста (FR-21 в силе). Порог, заданный суммой баллов,
  переводится в долю от достижимого в своей области, иначе тест с порогом в баллах остался бы
  без окраски и без текстов. Подтема, не появившаяся в выдаче, в разрезе отсутствует и потому
  ничего не роняет (FR-22 в силе).

  **Адаптивный режим судит подтемы ОБЩИМ порогом теста** — и записи области раздела, и сводные.
  Порога у ступени нет и быть не может, а тексты подтем и цвет полос терять нельзя: до §16
  адаптивный экран выдавал их по тому же общему порогу. Правило остаётся одним на оба режима.
  Общего порога у теста нет — подтемы молчат, как и везде.

  Отменяет: FR-49 в части «ключ не судится ничем» и FR-20 (индивидуальные значения порогов).

- **FR-53. Переключатель «Учитывать подтемы в вердикте темы»** — `tests.breakdown_gate_enabled`,
  булев, по умолчанию ВЫКЛЮЧЕН, один на тест. Выключен: подтема говорит, но не судит (поведение
  §15). Включён: тема не пройдена, когда не выполнено её собственное правило ЛИБО хотя бы одна
  подтема области раздела ниже порога.

  Тема, у которой порога нет, вердикта не выносит и при включённом переключателе (следствие
  FR-52): суд не возвращается вопреки настройке автора. Тема, где нечего оценивать, остаётся без
  вердикта, как сегодня. В вердикт ТЕСТА тема складывается существующей политикой
  `pass_decision_policy` — второго пути к вердикту не заводится. Гейта в области теста нет
  (FR-23 в силе).

  Заменяет FR-19: источник правила темы «по ключам разреза» не возвращается — вместо него один
  переключатель на тест.

- **FR-54. Строка разреза печатает исход.** Запись разреза снова несёт `passed`
  (`true` / `false` / `null` = порога нет), а строка контекста шаблона — `passed`, `passClass`
  (`is-pass` / `is-fail` / пусто) и `requiredLabel` («Нужно 70 %»), который печатается там, где
  автор включил показ значения, и объясняет цвет. Словесной метки исхода у строки нет: строка
  узкая, и слово рядом с процентом дублировало бы цвет.

  Исход вычисляется ОДИН раз, при подведении итога попытки, и хранится в записи; экран итогов,
  PDF-отчёт и SCORM-пакет печатают сохранённое и потому не могут разойтись. Контракт шаблона
  бампится; правятся макеты и стили обоих поставляемых шаблонов.

- **FR-55. Текст подтемы выдаётся по порогу её темы** (уточняет FR-50): текст, ссылки, вложения
  и мероприятия подтемы получает участник, чей результат по этой подтеме ниже порога, вычисленного
  по FR-52, — при любом вердикте теста и темы. В теме без порога текстов подтем нет. Сводный блок
  области теста текстов не даёт: тексты хранятся на разделе.

- **FR-56. Индивидуальные пороги вычищаются из структуры.** Миграция: `DROP COLUMN
  test_sections.breakdown_rules_json` и `ADD COLUMN tests.breakdown_gate_enabled boolean NOT NULL
  DEFAULT false`. Из кода уходят схема `breakdownRulesSchema`, типы `BreakdownRules` и
  `BreakdownThreshold`, резольверы `resolveBreakdownRules` и `breakdownThresholdFor`, приём поля
  маршрутом теста, модель и мутаторы редактора. Из редактора уходят переключатель «Пороги по
  подтемам (тегам)», столбец «Порог» таблицы квот и поля процентов в её строках.

  Предупреждения публикации о недостижимом пороге ключа (FR-46) снимаются окончательно — предмета
  у них больше нет. Взамен одно: переключатель FR-53 включён, а показ подытогов выключен —
  участник получит «Не пройдена» без единой видимой причины.

- **FR-57. Совместимость.** Сохранённые попытки не перерешаются и не перекрашиваются: в их
  записях разреза поля исхода нет, значит `null`, значит строки нейтральны и выданный ранее PDF
  печатается как прежде. SCORM-пакеты и снимки публикации, собранные раньше, флага FR-53 не несут
  — гейт для них выключен. Тест, где автор ничего не включал, даёт прежний экран итогов и прежний
  отчёт. Сохранённые в базе индивидуальные пороги пропадают вместе с колонкой; вердикта они не
  меняли с 2026-09-03, поэтому потеря ни на один результат не влияет.
