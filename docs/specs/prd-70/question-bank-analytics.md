## 1. Обзор

### 1.1 Контекст

Качество вопроса сегодня видно только изнутри теста: таблица «Вопросы» на уровне теста, разбор вопроса,
карточка «Тесты с вопросами под подозрением» в очереди. Вопрос же живёт в теме банка и стоит в нескольких
тестах. Автор темы, который правит вопрос, не видит в «Темах и вопросах», что с ним не так, и не видит, как
вопрос ведёт себя в других тестах. В редакторе вопроса есть только сложность, заданная автором.

Психометрику нельзя считать по банку целиком: оценщик (`buildGrader`) привязан к цене и правилам теста, а
дискриминативность — к сумме баллов внутри выборки теста. Поэтому ось банка — это N расчётов «по тесту»,
выложенных рядом, без общего среднего (решение К1, PRD-56 FR-12).

Отдельно: формы настройки фильтров выглядят по-разному. В банке и «Тестах» — своя карточка с
капс-заголовками и «Сбросить всё», в аналитике — окно «Условия отбора» с «Отменой», в «Пользователях» —
ряд списков без чипов и сброса. Фильтр «Состояние» банка — первый новый фильтр этого трека, поэтому образец
вводится здесь же.

### 1.2 Цель

1. В «Темах и вопросах» видно, какие вопросы требуют ревизии, какие переэкспонированы и какие не
   выдавались, — у вопроса, темы и папки.
2. У вопроса банка есть страница «Статистика»: строка на каждый тест, где вопрос выдавался, и версии
   содержания.
3. В редакторе вопроса автор видит ориентир — какой сложность оказалась у участников.
4. Очередь «Требует внимания» ведёт автора темы к его вопросам на ревизию.
5. Все фильтры продукта, кроме журнала сервера, — одна полоса `FilterBar` и одна панель `FilterPanel`.

### 1.3 Метрики успеха

| Цель | Метрика |
| --- | --- |
| Один признак везде | Вопрос «на ревизии» в банке, в таблице теста и в очереди определяется одной функцией с одинаковыми входами; число в карточке очереди совпадает с длиной списка, который она открывает |
| Без смешения тестов | Ни один экран и ни один ответ API не содержит среднего по тестам, кроме ориентира сложности (§3.4) |
| Банк открывается быстро | Дерево в наборе «Качество» на данных прода открывается не дольше, чем сегодня в «Содержании», плюс 300 мс; признаки не пересчитываются на открытие |
| Статистика вопроса | Страница вопроса банка в 10 тестах открывается не дольше 2 с на данных прода |
| Единый фильтр | Банк, «Тесты», реестр, уровень теста, срезы и «Пользователи» используют `FilterBar` + `FilterPanel`; окно `RegistryFilterDialog` и карточки `ct-filterpop` / `tl-filterpop` удалены |

## 2. Пользователи

- **Автор темы** (владелец или грант `manage`) — видит признаки в дереве, открывает статистику вопроса,
  получает дела «Вопросы банка на ревизию».
- **Автор теста** — видит ту же статистику в пределах доступных ему тестов; из вопроса в тесте переходит к
  вопросу банка.
- **Любой пользователь со списочным экраном** — пользуется единым фильтром.

## 3. Ключевые понятия

### 3.1 Признак «на ревизии»

Вопрос банка «на ревизии», если хотя бы в одном доступном читателю тесте он «под подозрением» по правилу
`isSuspicious` из `shared/psychometrics/question-flag.ts` — то же правило, что у таблицы «Вопросы» теста
(PRD-56 FR-12, уточнение 2026-10-05). Входы правила — психометрика теста и эвристики `reviewFlags()`
(`server/services/analytics/question-review.ts`: «часто и трудно», «быстро и неверно»).

Сегодня фоновый пересчёт (`suspicious-refresh.ts` → `suspiciousByPsychometrics`) зовёт `isSuspicious` БЕЗ
эвристик, а таблица теста — с ними, поэтому число в карточке очереди может не совпасть со списком. Этот трек
сводит входы к одному набору (FR-03).

У вопроса показывается самый важный признак (по `suspicionRank`) и сколько тестов его дают: «Сильные
ошибаются чаще — в 1 из 2 тестов · ещё 1 признак». Знаменатель — тесты, где у вопроса достаточно данных.

### 3.2 «Переэкспонирован»

В тесте со случайной выборкой из раздела (`drawMode = quota`) вопрос переэкспонирован, если доля прохождений
с ним за окно счётчика выдач (`config.delivery.exposureWindowMonths`, по умолчанию 12) не меньше
`k × ожидаемой`, где ожидаемая доля — `expectedExposure({ drawCount, poolSize })` из
`shared/draw/expected-exposure.ts` (квота раздела / размер пула), и прохождений в окне не меньше 10.

- `k` — `config.analytics.overexposureRatio`, по умолчанию `1.5`, в конфиге экземпляра.
- Разделы `all` (весь банк), `forms` (варианты) и `adaptive` признака не дают: ожидаемой доли там нет.
- Знаменатель доли — прохождения теста в окне, включая брошенные, как в профиле экспозиции
  (`server/routes/analytics/delivery.ts`).

У вопроса показывается «чаще ожидаемого 82 % при 40 % · 1 из 3 тестов» — по тесту с наибольшим превышением.

### 3.3 «Не выдавался»

Вопрос входит в пул выдачи хотя бы одного теста (не исключён из выдачи, PRD-56 FR-17a) и за окно счётчика
выдач не выдан ни в одном тесте. Вопрос, которого нет ни в одном пуле, не считается: выдать его нечем.

### 3.4 Ориентир сложности «По ответам»

Единственное исключение из К1 (решение владельца 2026-10-05). Над шкалой «Сложность» в ящике вопроса —
один маркер: наблюдаемая сложность в шкале редактора (0–100, больше — сложнее), сведённая по тестам.

- По тесту: `hardness = round((1 − p) × 100)`, где `p` — трудность вопроса по психометрике теста (то же
  преобразование, что в колонке «Сложность: задана → по ответам»).
- Входят тесты, где у вопроса не меньше `config.analytics.minObservations` наблюдений (по умолчанию 10).
- Свод — среднее, взвешенное числом наблюдений: `round(Σ hardnessᵢ × nᵢ / Σ nᵢ)`.
- Ни одного теста с достаточными данными — маркера нет.
- Учитываются все тесты, где вопрос выдавался, а не только доступные читателю: это свойство вопроса, а
  не данные теста; названия тестов в подсказке не раскрываются.

Подсказка: «По ответам: 40. Какой сложность оказалась у участников — сводно по 2 тестам, 626 прохождений.
Ориентир для заданной сложности; по каждому тесту — в «Статистике»». Переопределения сложности в тестах
(`test_question_scoring.difficulty`) на ориентир не влияют и в подсказке не упоминаются: маркер описывает
наблюдение, а не заданное значение.

### 3.5 Область видимости

- Строки статистики, признаки и их счётчики — только по тестам из `analyticsScope(req)`
  (`server/routes/analytics/helpers.ts`). Один и тот же вопрос у двух читателей может иметь разные признаки.
- Дела «Вопросы банка на ревизию» — только вопросы тем, которыми читатель управляет
  (`canManageTopicContent`). Множественной проверки сегодня нет — добавляется `manageableTopicScope` в `topic-access.ts`
  (FR-60).

## 5. Нефункциональные требования

- **Расчёт.** Признаки — результат фонового пересчёта (сегодня каждые 10 минут); экраны их только читают.
  Расчёт по тесту не дублируется: страница вопроса и пересчёт берут его из одного кэша.
- **Доступность.** Маркер ориентира фокусируется с клавиатуры, подсказка открывается по фокусу, у маркера
  есть подпись для чтения с экрана («Сложность по ответам: 40»). `FilterPanel` — `role="dialog"` с подписью,
  фокус при открытии — на первом поле, `Esc` возвращает фокус на кнопку «Фильтр».
- **Дизайн-система.** Только компоненты ui-kit; чего нет (`FilterPanel`, ориентиры `Slider`, `'xl'` у
  `Popover`) — добавляется в `vendor/ui-kit` с тестами и описанием в справочнике ДС.
- **Совместимость.** Сохранённые наборы условий аналитики (`registry/filter-state.ts`) читаются без
  миграции: меняется форма, а не состояние.

## 7. Проверка

- **Сервер (pglite, `npm run test:it`).** Признак по вопросу и теме в двух тестах с разными исходами;
  переэкспонированность на границах `k` и 10 прохождений, разделы `all` / `forms` / `adaptive` без признака;
  «не выдавался» для вопроса в пуле и вне пула; ориентир §3.4 (взвешивание, отсев малых выборок, `null`);
  область видимости (вопрос в чужом тесте не даёт признака читателю); сброс кэша.
- **Единое правило.** Тест на совпадение: для одного набора наблюдений фоновый пересчёт и таблица теста
  дают одинаковые признаки.
- **Клиент.** Наборы колонок и адрес, фильтр «Состояние», меню и кнопка «Статистика», маркер ориентира,
  `FilterPanel` (открытие, `Esc`, «Сбросить», «Применить», черновик теряется при закрытии).
- **Браузер.** Приёмка каждого этапа по эскизу под автором темы и под автором теста; единый фильтр — на
  всех шести экранах; тёмная тема.
