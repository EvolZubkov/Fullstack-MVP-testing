# PRD-31: Интервал между попытками и общая модель допуска

**Версия:** 1.0

**Статус:** РЕАЛИЗОВАН 2026-08-01 (фазы 1-6). Приёмка веба и SCORM-пакета пройдена, см. §12.1;
открытым остаётся один прогон с разведёнными часами для барьера B

**Связанные документы:** [PRD-6](../prd-6/retake-cooldown-gate.md),
[доверенная дата](../prd-6/cooldown-trusted-date.md), [PRD-12](../prd-12/web-runtime-parity.md),
[PRD-19](../prd-19/skip-return-navigation.md), [PRD-15](../prd-15/content-ownership.md)

**Зависимости:** PRD-6 (кулдаун и гейт), PRD-12 (единый рантайм и общие движки), PRD-19 (состояние кулдауна
на стартовом экране), назначения тестов (`test_assignments`)

## 1. Обзор

### 1.1 Контекст

Ограничение повторного прохождения (PRD-6) на двух хостах означает разное, хотя настраивается одним и тем же
переключателем.

В SCORM гейт срабатывает до `Initialize` и решает по записям обучения LMS: каждое назначение курса — отдельная
запись со своим статусом и датой. Кулдаун стоит на границе **назначения**. Внутри одного запуска пакет не
ограничен ничем: попытки живут в `suspend_data.attempts[]`, кнопка «Пройти ещё раз» доступна сразу после
экрана результатов.

В вебе тот же переключатель проверяется на старте **попытки** и считает от `attempts.finished_at` последней
завершённой попытки учащегося по тесту. Назначение в решении не участвует вовсе: у `attempts` нет ссылки на
назначение, поэтому веб физически не различает «повтор внутри назначения» и «первая попытка нового назначения».

Расхождение видно и в счётчике попыток: `maxAttempts` в SCORM считается внутри регистрации, а в вебе — за всю
историю учащегося по тесту.

Автору нужен второй, короткий барьер — минимальный интервал между попытками, — но вводить его поверх
разъезжающейся семантики нельзя: одна и та же настройка теста обязана означать одно и то же на обоих хостах.

### 1.2 Цель

1. Ввести единицу допуска — **назначение** — и описать обе границы одной моделью, общей для веба и SCORM.
2. Добавить переключатель «Ограничение между попытками» с интервалом в часах, действующий внутри назначения.
3. Привести веб к этой модели: связать попытку с назначением, перенести туда общий кулдаун и счётчик попыток.
4. Считать оба барьера одним движком, как это уже сделано для кулдауна (PRD-12).
5. Сохранить неизменным поведение тестов, где ни один барьер не включён (byte-identical экспорт, FR-02 PRD-6).

### 1.3 Метрики успеха

| Цель | Метрика |
| --- | --- |
| Семантика общая | Один и тот же набор фактов даёт один и тот же вердикт на обоих хостах (общие юнит-тесты движка) |
| Интервал применяется | 100% стартов внутри назначения раньше срока отклоняются на обоих хостах |
| Незатронутые тесты | Пакет теста без обоих барьеров совпадает байт в байт с текущим |
| Диагностируемость | Вердикт называет сработавший барьер и момент, с которого старт открыт |

## 2. Ключевые понятия

### 2.1 Назначение

Единица допуска: факт выдачи теста конкретному учащемуся. Внутри назначения учащемуся доступен комплект
попыток (`maxAttempts`), а соседние попытки разделяет барьер B.

| Хост | Чем представлено |
| --- | --- |
| Веб | строка `test_assignments` (личная или через группу), с которой связана попытка |
| SCORM | регистрация курса в LMS — та, чей `suspend_data` читает пакет |

### 2.2 Барьер A — общий кулдаун (существующий)

Ограничение **между назначениями**: первая попытка нового назначения открыта не раньше, чем через
`cooldownPeriodDays` календарных дней после завершения последней попытки предыдущего назначения. Единица —
календарный день в UTC, математика прежняя (`cooldownDecision`).

### 2.3 Барьер B — интервал между попытками (новый)

Ограничение **внутри назначения**: очередная попытка открыта не раньше, чем через `attemptInterval.hours` часов
после завершения предыдущей попытки этого же назначения. Единица — час, отсчёт абсолютный, календарь не
участвует.

### 2.4 Завершённая попытка

Веб — строка `attempts` с непустым `finished_at`. SCORM — запись в `suspend_data.attempts[]` (её создаёт
`saveAttemptResult`). Незавершённая попытка ни один барьер не сдвигает: возобновление прерванной попытки
барьерами не ограничивается.

## 3. Единая модель допуска

Решение принимается по трём фактам: текущее назначение, завершённые попытки внутри него, завершённые попытки
прочих назначений.

```text
current      = текущее назначение учащегося по этому тесту
inside       = завершённые попытки, привязанные к current
outside      = завершённые попытки, привязанные к любому другому назначению

если inside пусто:
    барьер A (дни)   от max(finished) по outside
иначе:
    барьер B (часы)  от max(finished) по inside

лимит попыток: count(inside) < maxAttempts
```

Барьеры действуют в непересекающиеся моменты: A — на первой попытке назначения, B — на второй и далее. Это и
означает «работают вместе»: одна политика описывает обе границы, а не два условия, проверяемых одновременно.
Одновременная проверка была бы бессмысленной — внутри назначения A по определению не применяется, иначе он снова
стал бы барьером между попытками и вернул бы исходное расхождение.

Источники фактов различаются, правило — нет:

| Факт | Веб | SCORM |
| --- | --- | --- |
| `current` | назначение, резолвленное на старте (§5.3) | текущая регистрация SCORM |
| `inside` | `attempts` с этим `assignment_id` | `suspend_data.attempts[]` |
| `outside` | `attempts` с другим `assignment_id` | записи обучения LMS (плагин PRD-6) |
| «сейчас» | часы сервера | доверенное время портала, откат на часы машины (§7.3) |

## 5. Модель данных

### 5.1 `tests.retake_policy_json`

Добавляется ветка `attemptInterval`; миграция не нужна — колонка `jsonb`.

```json
{
  "enabled": true,
  "cooldownPeriodDays": 30,
  "gateMode": "before_internal_start",
  "eligibilityPlugin": { "key": "webtutor_cooldown", "failPolicy": "failOpen" },
  "blockedPageId": "system.blocked",
  "attemptInterval": { "enabled": true, "hours": 24 }
}
```

Правки `retakePolicySchema` (`shared/schema.ts`):

- `cooldownPeriodDays` становится необязательным и требуется только при `enabled === true` — иначе нельзя
  включить один барьер B, не выдумывая значение для выключенного барьера A;
- `attemptInterval.hours` — целое 1–8760, обязательно при `attemptInterval.enabled === true`;
- отсутствие `attemptInterval` равно `{ enabled: false }`.

### 5.2 `attempts.assignment_id`

Новая колонка `varchar(36)`, nullable, с индексом по `(user_id, test_id, assignment_id)`. Миграция — следующий
свободный номер (на 2026-08-01 это `037`). Существующие строки получают `NULL`: восстановить принадлежность
задним числом нельзя, а домысливать её нельзя тем более. Внешнего ключа нет — так же, как у прочих ссылок в
схеме; удалённое назначение автоматически перестаёт быть текущим, и его попытки становятся «предыдущими», что
соответствует смыслу.

### 5.3 Резолв текущего назначения

На старте попытки берётся самое позднее по `assigned_at` назначение теста, применимое к учащемуся: личное
(`user_id`) или через группу (`group_id` входит в группы учащегося). Групповое назначение — одна строка на
группу, поэтому для всех её участников оно общее; повторная выдача той же группе создаёт новую строку и, значит,
новый комплект попыток.

Если применимых назначений нет (легаси-данные, прямой доступ), текущим считается легаси-бакет `assignment_id IS
NULL`. Репозиторий назначений получает метод, возвращающий сами назначения, а не только тесты
(`getAssignedTestsForUser` сейчас отдаёт `Test[]`).

### 5.4 Что уезжает в пакет

`retakePolicy` попадает в `TEST_DATA` также тогда, когда включён только барьер B — без плагина допуска и без
рантайма гейта. Условие запекания в `server/scorm/builders/test-json.ts` перестаёт быть единым: гейт и его
плагин запекаются по-прежнему только при `enabled` с разрешённым плагином, а `attemptInterval` — независимо.

## 6. Веб

### 6.1 Решение

`server/services/retake-gate.ts` перестаёт быть функцией одного барьера: `decideRetake` получает факты по
модели §3 (текущее назначение, попытки внутри и снаружи, момент «сейчас») и возвращает объединённый вердикт с
полем `blockedBy: "cooldown" | "attemptInterval"`, датой `availableDate` (барьер A) либо моментом `availableAt`
(барьер B).

### 6.2 Точки применения

- `POST /api/tests/:id/attempts/start` и `/start-adaptive` — отказ `403`; код прежний `RETAKE_COOLDOWN` для
  барьера A и новый `ATTEMPT_INTERVAL` для барьера B. Там же счётчик попыток считается по `inside` (FR-07).
- `GET /api/learner/tests` — блок `retakeGate` стартового экрана дополняется `availableAt` и `blockedBy`.
- `server/services/home/assigned.ts` — `blockedUntil` заполняется из того же вердикта.
- `GET /api/attempts/:id/result` — `canRetake` и `attemptsInfo` считаются внутри назначения.

### 6.3 Клиент

`client/src/pages/learner/take-test.tsx` показывает пришедшее с сервера значение: дату для барьера A и дату со
временем для барьера B. Локальные часы не читаются — инвариант FR-TD-06 сохраняется.

## 7. SCORM

### 7.1 Где проверяется барьер B

После `Initialize`, там где источник надёжен: `suspend_data.attempts[].completedAt` (пишется в
`saveAttemptResult`). Две точки:

- `buildScormStartContext` (`app/render/startPage.js`) — вход в курс, когда попытки уже есть: `canStartNew`
  учитывает и `hasAttemptsLeft()`, и истечение интервала; в контекст стартового экрана уезжает момент открытия;
- экран результатов — кнопка «Пройти ещё раз» неактивна по тому же признаку.

Гейт PRD-6 не трогается: NFR-01/NFR-02 (никакого `Initialize` и никаких `cmi.*` до вердикта барьера A)
остаются в силе. Барьер B действует внутри уже открытой сессии, где `Initialize` вызван законно.

### 7.2 Где проверяется барьер A и почему это открытый вопрос

Сейчас — в гейте до `Initialize`, по записям обучения LMS. Проблема в том, что на этом месте пакет вообще не
различает начало назначения и начало попытки.

Единственный физический признак «это новое назначение» — пустой `suspend_data`: новая регистрация SCORM всегда
получает чистый экземпляр модели данных. До `Initialize` он недоступен: по модели состояний SCORM 2004
`GetValue` в этот момент возвращает ошибку 122, а обёртка пакета (`server/scorm/assets/runtime.js`) состояние
не проверяет и отдаёт пустую строку. Именно поэтому PRD-6 §4.6 называет `suspend_data_cooldown` best-effort.

Опознать текущее назначение по идентификатору записи нельзя: это уже проверялось пробником
`scripts/wt-object-probe.js` 2026-07-16 (`docs/references/webtutor-learning-records-api.md`, раздел «Почему по
имени, а не по object_id»). Ни `session_id`, ни `part_code`, ни `pathId` из контекста запущенного SCO не
совпадают с `object_id` записей грида; грид ключуется только по `name`.

Отсюда следствие: пакет репортит `completed` в конце каждой попытки, поэтому после первой же попытки запись
назначения становится завершённой со свежей датой, и при следующем входе в ЭТО ЖЕ назначение гейт её увидит.
Учащийся с оставшимися попытками упрётся в барьер A. То есть при включённом кулдауне многопопыточное назначение
в SCORM не работает уже сегодня.

Пробник `scripts/wt-assignment-boundary-probe.js` прогнан на `testuniver.rt.ru` 2026-08-01 и подтвердил обе
посылки. Курс с ОДНИМ назначением (`object_id` 7313082720794276828, назначено 30.07.2026), по нему завершена
попытка — запись сразу перешла в состояние «Не пройден» с датой 30.07.2026, то есть стала для фильтра гейта
полноценной попыткой. При этом 01.08.2026 учащийся снова находится ВНУТРИ этого же назначения, курс открыт:
завершённое назначение WebTutor перезапускать даёт. Идентификаторы запуска (`session_id`, `launch_id`, id в
пути) с `object_id` записи по-прежнему не совпадают.

Сложение этих фактов и есть дефект: будь на тесте включён кулдаун, гейт при сегодняшнем входе увидел бы
завершённую запись от 30.07 и заблокировал бы учащегося, хотя тот остаётся внутри своего назначения и попытки
у него не исчерпаны.

Побочное наблюдение в пользу пути 1: `last_usage_date` записи не сдвинулась на 01.08 при сегодняшнем открытии
курса, то есть дата отражает завершение попытки, а не факт запуска. Значит пара `Initialize`/`Terminate` без
записей `cmi.*` дату последней попытки, скорее всего, не портит. Это наблюдение, а не доказательство:
подтверждается на приёмке.

Остаются два пути:

1. **Перенести вердикт барьера A за `Initialize`.** Порядок: `Initialize` -> чтение `suspend_data` -> если
   попытки есть, барьер A пропускается и работает только B; если пусто — применяется A, и при блокировке сразу
   `Terminate` без единой записи `cmi.*`. NFR-02 сохраняется. NFR-01 PRD-6 требует переформулировки: его смысл
   («заблокированный запуск не становится полноценной попыткой») остаётся, потому что фильтр полноценной
   попытки считает только записи в состоянии «Пройден»/«Не пройден», а голая пара `Initialize`/`Terminate`
   такой записи не создаёт. Цена — статус записи в портале сместится в «Начат».
2. **Признать ограничение:** в SCORM кулдаун несовместим с многопопыточным назначением, автору показывается
   предупреждение в редакторе при одновременно включённых кулдауне и `maxAttempts > 1`.

### 7.3 Источник «сейчас»

Барьер в часах, считанный по часам машины учащегося, снимается переводом системного времени — ровно та дыра,
которую для кулдауна уже закрыли доверенной датой. Поэтому `fetchPortalChrome`/`resolveToday` выносятся из
`app/eligibility/gate.js` в общий `app/utils/trusted-now.js`, отдающий полный timestamp (а не только
календарный день) с тем же таймаутом 2500 мс и той же деградацией на часы машины. Для теста без плагина
допуска endpoint — `/`, то есть один GET страницы портала на запуск SCO.

Из того же источника проставляется `completedAt` завершённой попытки; рядом пишется `completedAtSource`
(`network` / `client`) для диагностики. Старые записи в `suspend_data` несут дату по часам машины — они
читаются как есть, просто менее надёжны.

Отклонённая альтернатива: считать барьер B по часам машины. Дешевле на один запрос, но делает настройку
декоративной и противоречит уже принятому решению по доверенной дате.

## 8. UI автора

Панель «Повторное прохождение» (`basic-settings-section.tsx`, `RetakePane`) получает вторую группу:

- переключатель «Ограничение между попытками»;
- поле «Интервал, часов» (1–8760), активное при включённом переключателе;
- пояснение, разводящее два барьера: общий кулдаун — между назначениями, интервал — между попытками внутри
  назначения.

Перед реализацией нужен эскиз (Э0) в `docs/wireframes/approved/`, как для прочих правок авторского UI:
берётся существующая панель PRD-6 и к ней добавляется минимальная дельта.

## 9. Совместимость и миграция

- Тест без обоих барьеров не меняет поведение ни на одном хосте: `TEST_DATA` не получает ни `retakePolicy`,
  ни `retakePlugin`, а рантайм барьеров в пакет не запекается (FR-14).
- Существующие веб-тесты с включённым кулдауном меняют поведение: внутри одного назначения повтор перестаёт
  блокироваться, а счётчик попыток начинает считаться внутри назначения. Компенсирующая миграция сознательно не
  делается (решение 2026-08-01): автору, которому нужен барьер внутри назначения, нужно включить новый
  переключатель. Смена фиксируется в CHANGELOG и в пояснении редактора.
- `attempts.assignment_id` у старых строк остаётся `NULL`; они образуют один легаси-бакет.
- Снапшоты публикации (PRD-15) везут политику в составе строки теста — отдельной правки не требуется.
- Книга Excel настройки повторного прохождения не переносит ни сейчас, ни после этой правки.
- Отладочный прогон (PRD-18) изолирован: попыток в БД не создаёт, `suspend_data` у него свой на каждый запуск,
  назначения нет — барьеры отладке не мешают и специально не отключаются.

## 11. Риски и открытые вопросы

## 12.1 Результат приёмки 2026-08-01

Веб — реальный браузер (Chromium под управлением CDP), dev-сервер на отдельном порту, панель
«Повторное прохождение» в редакторе теста:

| Сценарий | Ожидание | Факт |
| --- | --- | --- |
| Оба барьера выключены | Два переключателя, поля скрыты | Совпало |
| Включён ТОЛЬКО интервал | Поле «Интервал, часов» = 24, подсказка 1–8760, пояснение в варианте «кулдаун выключен» | Совпало; кулдаун остался выключенным (FR-03) |
| Включены оба | Группа кулдауна целиком, разделитель, группа интервала, пояснение в варианте «оба» | Совпало |

SCORM — пакет `out/interval-demo.zip` (`scripts/_build-interval-scorm.ts`: оба барьера,
`cooldownPeriodDays: 30`, `attemptInterval.hours: 24`, `maxAttempts: 3`), стенд
`npm run scorm:player -- --server-date=2026-08-02T09:00:00Z`, в `suspend_data` засеяна одна
завершённая попытка с `completedAt = 2026-08-02T05:00:00Z` (то есть 4 часа назад по часам стенда):

| Проверяемое | Факт |
| --- | --- |
| Барьер A на повторном входе | НЕ сработал: экран блокировки не показан, отрисован штатный стартовый экран |
| Барьер B | Сработал: «Повторное прохождение пока недоступно. Повторный запуск будет доступен с 03.08.2026 в 08:00» |
| Момент открытия | Дата И время; счётчик «через N дн.» не показан |
| Кнопка старта | Неактивна, но видима |
| Счётчик попыток | «Попытка 2 из 3» — внутри регистрации |
| Прошлый результат | «Прошлая попытка: 64% · не пройдено · попытка 1 из 3», действия «Мой результат» и «Скачать отчёт» доступны |

Арифметика сходится и подтверждает, что решение принято по доверенным часам:
`05:00 UTC + 24 ч = 2026-08-03T05:00 UTC`, показано `08:00` в поясе браузера (UTC+3).

Не покрыто прогоном: полное прохождение попытки в пакете «руками» (проверялось засеянным
`suspend_data`) и сценарий с разведёнными часами машины и стенда для барьера B — для барьера A он
пройден в приёмке доверенной даты 2026-07-29.
