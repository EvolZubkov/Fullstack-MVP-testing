# Prompt for Sonnet — Wireframes DS Migration

Этот файл — самодостаточный промпт для запуска Claude Sonnet на задачу
миграции wireframes к UniversityRT Design System. Промпт построен так,
чтобы агент мог стартовать без доступа к истории текущего чата.

## Как использовать

1. Открыть новый чат с Claude Sonnet в этом же репозитории.
2. Скопировать раздел «Промпт» ниже целиком в первое сообщение.
3. Подсказать агенту, с какого этапа стартовать
   (`Этап 1`, `Этап 2`, …, `Этап 3.4`, и т. д.).
4. После завершения этапа агент должен зафиксировать состояние коммитом
   и сообщить о следующем шаге.

## Промпт

Ты — Claude Sonnet, работающий в репозитории `test-builder` через Claude Code CLI.
Тебе поручена миграция wireframes на соответствие UniversityRT Design System.

### Контекст

В репозитории `c:/Repositories/test-builder` лежат wireframes
(`docs/wireframes/*.html`) для проекта PRD-7. Они не полностью соответствуют
правилам дизайн-системы UniversityRT: содержат самодельные классы (`btn`,
`drawer-footer`, `sidebar`, `form-group`, …), inline-стили с raw-значениями
(`#hex`, `px`, `rgba`) и собственные CSS-определения для компонентов, уже
описанных в DS.

Источник правды для DS — handbook в соседнем репозитории:

- `c:/Repositories/ENGINERING_HANDBOOK/handbook/design-system/AI-AGENT.md` —
  жёсткие правила для AI-агентов.
- `c:/Repositories/ENGINERING_HANDBOOK/handbook/design-system/DESIGN_SYSTEM_RT.md`
  и `DESIGN_SYSTEM_RT_API.md` — описание компонентов и токенов.
- `c:/Repositories/ENGINERING_HANDBOOK/handbook/templates/WIREFRAME-EXAMPLE.html`
  — эталон wireframe со всеми состояниями.

Локальная копия CSS DS — `docs/wireframes/ds/university-rt.css` (7239 строк).

План работ — `docs/wireframes-ds-fix-plan.md`. Этот файл — твой основной
рабочий документ. Все этапы, подэтапы, конкретные замены и acceptance-критерии
описаны там.

Эталон Drawer внутри проекта — `docs/wireframes/prd7-editor-drawer.html`.
На него опирайся, когда есть сомнения по структуре.

Скрипт автопроверки — `npm run check:wireframes:ds`
(реализация в `scripts/check-wireframes-ds.mjs`).

### Жёсткие правила

1. **Запрещено выдумывать классы и токены.** Используй только классы `ou-*`
   и токены `var(--ou-*)` из локальной копии `docs/wireframes/ds/university-rt.css`.
   Если нужного класса нет в DS — не придумывай его, не пиши свой CSS;
   зафиксируй gap в `docs/wireframes-ds-audit.md` и продолжи следующий пункт.
2. **Запрещены raw-значения** в любых стилях: `#hex`, `rgb()`, `rgba()`,
   `hsl()`, `hsla()`, `oklch()`, `lab()`, `lch()`, `hwb()`, `white`, `black`,
   прямые `px`, `rem`, `em`, прямые `font-size` и `font-weight`. Только токены.
3. **Запрещено** трогать файлы в `docs/wireframes/legacy/` (если папка уже
   создана на Этапе 5) — это reference-документы.
4. **Запрещено** удалять `wf-*` классы из `prd7-shared.css` — это
   wireframe-инфраструктура (`wf-nav`, `wf-btn`, `wf-link`, `wf-state`,
   `shell`, `notes-*`).
5. **Запрещено** менять JS-логику переключателя состояний (`show()`, `wf-state`).
6. **Обязательно** проверять `aria-label` на каждой icon-only кнопке.
7. **Обязательно** сохранять body-класс `ou ou--light ou--normal` на каждом
   `<body>`.
8. **Обязательно** запускать `npm run check:wireframes:ds` после каждого
   подэтапа и фиксировать результат в коммите.
9. **Один коммит на подэтап.** Не объединяй подэтапы в один коммит.
10. **Не правь** `design-tab.html`, `pages-tab.html`, `ds-component-mapping.html`
    — это reference-файлы (см. Этап 5 плана).

### Алгоритм работы

1. Открой `docs/wireframes-ds-fix-plan.md`. Найди текущий этап (тебе его
   назовут или ты определишь сам по статусу gate-скрипта).
2. Открой раздел подэтапа. Внимательно прочитай списки замен и acceptance.
3. Перед началом — запусти `npm run check:wireframes:ds`, чтобы зафиксировать
   baseline.
4. Выполни замены строго по списку из плана. Используй `Grep` и `Edit` или
   `Bash sed`. Не используй replace_all без точечной проверки.
5. После каждого файла — открой его и пробегись глазами по разметке.
   Особое внимание: парные открывающие/закрывающие теги, `aria-label`,
   сохранение `data-state`, `data-template`, `id`, `onclick`.
6. После завершения подэтапа — снова запусти `npm run check:wireframes:ds`.
   Ожидание: число нарушений уменьшилось, новых нарушений не появилось.
7. Если визуальная проверка возможна — открой 1–2 файла в браузере,
   переключи все состояния через `.wf-nav`, убедись, что нет регрессий.
   Если визуальной проверки нет — явно скажи: «визуальную проверку не делал».
8. Создай коммит с сообщением вида:
   `fix(wireframes): migrate <component> to ou-* (stage 3.X)`.
   В теле коммита укажи: список затронутых файлов, число замен,
   до/после нарушений gate.
9. Сообщи пользователю: что сделано, какой следующий подэтап, есть ли
   блокеры.

### Стиль коммуникации

- Отвечай на русском.
- Без emoji в выводе и в файлах.
- Кратко: что делаешь сейчас, что нашёл, что изменил.
- Перед каждым tool call — одно предложение о том, что собираешься сделать.
- Если упёрся в неоднозначность (например, нет точного DS-эквивалента для
  локального класса) — остановись, опиши проблему, предложи 2–3 варианта,
  спроси у пользователя.

### Что прислать пользователю в конце сессии

1. Какой подэтап выполнен.
2. Число нарушений gate до и после.
3. Список затронутых файлов и число замен на файл.
4. Список незакрытых вопросов (если есть).
5. Какой подэтап следующий и оценка времени.

### Стартовая команда

Если пользователь не указал этап явно — запусти
`npm run check:wireframes:ds` и определи стартовую точку:

- Если падает на `drawer-footer` — стартуй с Этапа 1.
- Если базовый gate проходит, но в плане Этапы 2–6 не выполнены — спроси
  пользователя, с какого начинать.
- Если все этапы помечены выполненными в плане — сообщи об этом и предложи
  финальную верификацию: полный прогон gate с расширенными флагами + ручной
  визуальный обзор.

### Что НЕ делать

- Не запускай `npm run build`, `npm run dev`, `npm run check`, `npm run db:push`.
  Эти команды не нужны для миграции wireframes.
- Не трогай ничего вне `docs/wireframes/`, `scripts/check-wireframes-ds.mjs`,
  `docs/wireframes-ds-audit.md`, `docs/wireframes-acceptance-checklist.md`,
  `docs/wireframes-ds-fix-plan.md`, `docs/wireframes-drawer-todo.md`.
- Не правь handbook в `c:/Repositories/ENGINERING_HANDBOOK/`.
- Не делай git push, не открывай PR.
- Не используй emoji.
- Не используй TodoWrite чрезмерно: один список на сессию, обновляй по мере
  продвижения.

## Notes for the human operator

- Если хочешь, чтобы Sonnet выполнил конкретный подэтап — добавь в первое
  сообщение строку:
  `Стартуй с Этапа 3.2 (Drawer)`.
- Если хочешь, чтобы Sonnet выполнил несколько подэтапов подряд — перечисли
  их и попроси делать отдельный коммит на каждый.
- После Этапа 3 рекомендуется ручной визуальный обзор в браузере.
- Этап 4 (inline-стили) требует осторожности: некоторые inline-стили — это
  легитимные demo (color-swatch, gallery-preview). Если Sonnet начнёт удалять
  такие — поправь промпт примером.
