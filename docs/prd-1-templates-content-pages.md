**Статус:** Черновик  
**Связанные документы:** [BRD](brd-scorm-enhancements.md), [PRD-6](prd-6-retake-cooldown-gate.md), [Платформа SCORM-шаблонов](spec-template-platform.md)

## 1. Обзор

### 1.1 Контекст

Test Builder должен позволять авторам собирать корпоративные SCORM-пакеты с разными
визуальными оболочками и учебными страницами между вопросами. Шаблон в новой модели не
ограничивается цветами и шрифтами: он определяет оболочку, макеты страниц, частичные шаблоны,
ресурсы и опциональное поведение во время выполнения.

### 1.2 Цель PRD-1

Добавить первый продуктовый слой шаблонной платформы:

1. применение шаблона в браузере при запуске SCORM-пакета;
2. выбор и настройку шаблона автором;
3. стартовый набор встроенных шаблонов;
4. контентные страницы в общем потоке страниц;
5. подготовку Core к правилам курса и внешним шаблонам без создания отдельной механики.

Внешняя загрузка шаблонов описана в [PRD-3](prd-3-external-templates.md).
Гибкие режимы прохождения разделов описаны в [PRD-4](prd-4-course-flow-sections.md).
Ограничение повторного прохождения и страница блокировки описаны в
[PRD-6](prd-6-retake-cooldown-gate.md).

### 1.3 Метрики успеха

| Цель | Метрика |
| --- | --- |
| Авторы используют шаблоны | Доля тестов с выбранным шаблоном или изменёнными параметрами >= 30% через 3 месяца |
| Контентные страницы используются | Доля тестов с хотя бы одной контентной страницей >= 20% |
| Экспорт остаётся быстрым | P95 генерации не растёт более чем на 5 с |
| Runtime стабилен | Ошибки `TEMPLATE_RENDER_ERROR` < 1% запусков SCORM |

## 2. Пользователи и роли

### 2.1 Автор теста

Выбирает встроенный шаблон, настраивает параметры, добавляет контентные страницы. Не обязан
знать HTML/CSS/SCORM.

### 2.2 Администратор

В PRD-1 не является основным пользователем. Административный жизненный цикл шаблонов описан в
[PRD-3](prd-3-external-templates.md).

### 2.3 Разработчик шаблона

Для PRD-1 создаёт встроенные шаблоны в кодовой базе по общему контракту
[платформы SCORM-шаблонов](spec-template-platform.md).

## 3. Функция 1: платформа макетов и выбор шаблона

### 3.1 Пользовательский сценарий

1. Автор открывает тест и переходит на вкладку **"Оформление"**.
2. Видит галерею активных шаблонов.
3. Выбирает шаблон.
4. Видит форму параметров, построенную из `manifest.params`.
5. Меняет параметры: брендовые цвета, логотип, режим прогресса, поведение макета.
6. Нажимает **"Сохранить оформление"**.
7. При экспорте SCORM в пакет попадает выбранный шаблон и сохранённые параметры.
8. В браузере обучающегося Core загружает манифест, оболочку, макеты и рендерит страницы.

Альтернативный поток:

- **"Сбросить до умолчаний"** очищает `design_settings_json`; тест использует `default`.

### 3.2 Галерея шаблонов

Карточка шаблона содержит:

- изображение предпросмотра;
- название;
- описание;
- версию;
- метку `Встроенный`;
- состояние `Выбран`.

Автор может открыть живой предпросмотр на демонстрационном наборе данных, объявленном в
`manifest.preview.demoData` согласно контракту технической спецификации.

### 3.3 Параметры шаблона

Форма строится автоматически из `manifest.params` согласно технической спецификации.

Поддерживаемые типы MVP:

| Тип | UI-контрол |
| --- | --- |
| `color` | Выбор цвета + HEX-поле |
| `text` | Текстовое поле |
| `number` | Числовое поле |
| `boolean` | Переключатель |
| `select` | Выпадающий список |
| `image` | Загрузка изображения + предпросмотр |
| `font` | Загрузка/имя шрифта |
| `asset` | Загрузка файла |

Параметры используют ключи с точечной нотацией:

```json
{
  "brand.primaryColor": "#0066cc",
  "progress.mode": "questions",
  "layout.sidebarPosition": "left"
}
```

Если у параметра указан `cssVar`, Core публикует значение как CSS-переменную
(CSS custom property) в браузере.

### 3.4 Встроенные шаблоны MVP

Система поставляется минимум с тремя встроенными шаблонами.

| ID | Название | Назначение |
| --- | --- | --- |
| `default` | Стандартный | Обратная совместимость и базовый одноколоночный плеер |
| `corporate` | Корпоративный | Боковая панель, навигация по темам, брендирование |
| `minimal` | Минималистичный | Фокус на одном макете страницы, минимум элементов оболочки |

Каждый встроенный шаблон обязан соответствовать `spec-template-platform.md` и проходить ту же
браузерную smoke-проверку, что и внешний шаблон.

### 3.5 Граница PRD-1 и технической спецификации

PRD-1 не дублирует полный формат шаблона. Источник истины:
[платформа SCORM-шаблонов](spec-template-platform.md).

В рамках PRD-1 продуктово важно, что:

- встроенные шаблоны используют тот же контракт, что и будущие загружаемые шаблоны;
- Core в браузере загружает `manifest.json`, `shell.html`, макеты, частичные шаблоны и локальные ресурсы;
- форма параметров автора строится из `manifest.params`;
- `templateApiVersion` валидируется при сохранении настроек и экспорте;
- в SCORM ZIP попадает только выбранный шаблон.

## 4. Функция 2: контентные страницы

### 4.1 Пользовательский сценарий

1. Автор открывает тест и переходит на вкладку **"Структура"**.
2. Видит структуру теста по темам.
3. Нажимает **"+ Добавить страницу"** до или после темы.
4. Выбирает режим страницы: **по шаблону**, **стандартная**, **HTML**.
5. Для режима **по шаблону** выбирает page template по человекочитаемому названию из текущего
   SCORM-шаблона.
6. Заполняет форму placeholders, заданную выбранным page template.
7. Открывает предпросмотр страницы в текущем шаблоне.
8. Сохраняет страницу.
9. Страница появляется в общем потоке страниц и используется при экспорте SCORM.

### 4.2 Граница шаблона и содержимого

Контентная страница создаётся по PowerPoint-подобной модели slide layouts:

- **режим страницы** (`page.mode`) — `template`, `standard` или `html`;
- **тип варианта** (`variant.kind`) — `questions`, `router`, `summary`, `intro`, `info`
  (полная семантика и логика связывания — §4.3);
- **скелет данных** — набор placeholders, заданный шаблоном или Core;
- **значения placeholders** — контент, который вводит автор для конкретной страницы;
- **представление страницы** — layout выбранного варианта SCORM-шаблона.

Основной режим - `template`: автор выбирает один из page templates, объявленных текущим
SCORM-шаблоном в `manifest.contentTemplates[]`, и заполняет форму, построенную по placeholders этого
page template. Так шаблон задаёт допустимый скелет страницы, а автор заполняет только уместные для
него поля.

Каждый элемент `manifest.contentTemplates[]` обязан иметь человекочитаемое `label`; UI показывает
автору `label`, а технический `key` используется только для сохранения `templateKey`, совместимости
и диагностики.

Дополнительные режимы:

| Режим | Назначение |
| --- | --- |
| `template` | Страница заточена под выбранный SCORM-шаблон и его `contentTemplates[]` |
| `standard` | Переносимая страница по канонической схеме Core без привязки к конкретному шаблону |
| `html` | Технический escape hatch с санитизированным HTML |

Шаблон не хранит учебный текст и assets страницы. Он объявляет, какие placeholders уместны на
странице: например `title`, `subtitle`, `body`, `heroImage`, `leftImage`, `resultPercent`,
`primaryActionLabel`. Содержимое сохраняется в тесте как значения этих placeholders.

Содержимое сохраняется в данных теста и экспортируется в SCORM как часть runtime data:

```json
{
  "contentPages": [
    {
      "id": "page-1",
      "mode": "template",
      "templateKey": "intro.hero",
      "topicId": "topic-1",
      "position": "before_topic",
      "type": "intro",
      "values": {
        "title": "Введение в раздел",
        "subtitle": "Перед началом ответьте внимательно",
        "heroImage": {
          "assetId": "asset-123"
        }
      },
      "autoAdvance": false
    }
  ]
}
```

При смене шаблона **для пользовательских страниц `kind: info`**:

- варианты страниц, имена которых совпадают между старым и новым шаблоном, мигрируют
  автоматически (имя варианта — контракт между шаблонами для одного `kind`);
- страницы `html` сохраняют HTML и используют `content.html`/`content`;
- если в новом шаблоне нет варианта с тем же именем, авторский UI открывает модальный
  диалог замены (см. wireframe `s-mapping`): для каждой несовместимой страницы автор
  выбирает другой вариант нового шаблона **или** удаляет страницу. Сохранение шаблона
  без явного разрешения всех несовместимостей невозможно — runtime получает только
  страницы с валидными для текущего шаблона вариантами; механика автоматического
  fallback на `default`-шаблон применяется **только** к системным вариантам типов
  `questions` / `router` / `summary` / `intro` (см. §4.3.2), не к пользовательским
  страницам `kind: info`.

**Для системных страниц `kind: questions` / `router` / `summary` / `intro`** механика
другая — fallback на стандартный шаблон с warning-индикацией; диалог `s-mapping`
не применяется. Полная логика — §4.3.4.

#### Триггеры запуска диалога mapping

Диалог `s-mapping` открывается **автоматически** в следующих сценариях:

1. **Ручная смена шаблона** автором во вкладке «Оформление».
2. **Загрузка теста с дрейфом версий** — при открытии Drawer'а система сравнивает
   варианты страниц теста с актуальным snapshot'ом шаблона. Если шаблон был обновлён
   (`templateVersion` сменился, какие-то варианты удалены/переименованы), диалог
   запускается сразу после рендера вкладки «Структура».

В обоих сценариях кнопка **«Сохранить»** в footer drawer'а disabled до полного
разрешения всех несовместимостей.

#### Read-only / preview контексты

Если пользователь не имеет прав на редактирование (роль аналитик / наблюдатель, тест
открыт другим автором, и т. п.) или просматривает миниатюру теста в галерее, диалог
mapping не запускается. Вместо диалога:

- в списке тестов (см. `prd7-tests-list.html`) на карточке/строке теста с дрейфом
  отображается **статус-метка** «Требует обновления» рядом со стандартными бейджами
  состояния (`Черновик` / `Опубликован` / `В архиве`);
- при открытии такого теста в read-only Drawer вкладка «Структура» рендерится в
  обычном виде (без mapping-диалога), несовместимые страницы помечены
  warning-цветом заголовка; редактирование структуры заблокировано, автор-владелец
  должен открыть тест и пройти mapping.

### 4.3 Типы вариантов (`variant.kind`)

Манифест шаблона объявляет каждый вариант с обязательным полем `kind` —
функциональной ролью варианта в тесте. `kind` определяет, где и как этот
вариант применяется, и **не является визуальным enum'ом** (бейдж в авторском
UI остаётся нейтральным, палитра — собственность определения варианта в
шаблоне).

| `kind` | Назначение | Сущность в Drawer | Гранулярность | Влияние на оценку |
| --- | --- | --- | --- | --- |
| `questions` | Макет страницы вопроса (один ejs-вариант рендерит все типы интерактивов через `data-slot="question-interaction"`; разные варианты дают разные обёртки) | `page-row--system` (без insert/delete/drag), но с variant select, expand при непустой schema и `…` row-menu | В `linear_flat` — **одна** на тест (между зонами); в `linear_by_topics` / `router_by_topics` — **по одной на каждую тему**; variant локальный per-row | Не влияет напрямую; задаёт представление |
| `router` | Страница-маршрутизатор с меню тем | `page-row--system` в зоне «Внутри теста» | **Одна** на тест, только в `router_by_topics` | Не влияет |
| `summary` | Системная итоговая страница теста | `page-row--system` в зоне «После теста» | **Одна** на тест | Не влияет на оценку, использует результаты Core |
| `intro` | Системная вводная страница теста | `page-row--system` в зоне «До теста» | **Одна** на тест | Не влияет |
| `info` | Учебная/информационная страница (любой контент) | `page-row` в любой зоне | Сколько угодно | Не влияет |

Все четыре системных типа (`questions` / `router` / `summary` / `intro`) ведут себя в Drawer
одинаково: бейдж имени варианта, expand при непустой schema, `…` row-menu со «Сменить
вариант», хинт «Доступно N вариантов» при N > 1, warning fallback при 0 вариантов
нужного `kind`. Без insert-row до/после, без delete, без drag-handle. Отличия — только
в гранулярности (одна на тест vs одна на тему).

`html` — это **режим страницы** (`page.mode`), а не `kind` (см. §4.2). HTML-страница
может иметь любой `kind` из набора выше — режим определяет только источник
содержимого (заполненные placeholders / каноническая схема Core / санитизированный HTML).

Системная страница `system.blocked` используется для сценариев блокировки, включая retake cooldown
из [PRD-6](prd-6-retake-cooldown-gate.md). PRD-1 определяет только возможность отобразить такую
страницу через шаблон и контентные данные; решение о блокировке принимает Core.

#### 4.3.1 Логика связывания варианта

| `kind` | Логика выбора варианта в шаблоне |
| --- | --- |
| `questions`, `router`, `summary`, `intro` (типы 1-4 — **системные**) | **Тихая привязка**: автор не выбирает вариант явно при создании. Система привязывает default-вариант автоматически. См. §4.3.2 |
| `info` (тип 5 — **пользовательский**) | **Явный выбор**: автор выбирает вариант в `s-add-step1` модале при добавлении страницы (см. §4.5). |

#### 4.3.2 Тихая привязка системных вариантов (`questions` / `router` / `summary` / `intro`)

Системные варианты привязываются к тесту автоматически на основании режима
(`flowMode`) и роли страницы. Поведение системы зависит от количества вариантов
нужного `kind` в текущем шаблоне:

| Количество вариантов `kind` в шаблоне | Поведение системы | UI-индикатор |
| --- | --- | --- |
| **1 вариант** | Тихая привязка единственного варианта | Никакого UI выбора. Бейдж имени варианта в `page-row` (только для `router` / `summary` / `intro`); для `questions` — не отображается, ведь это не page-row |
| **N > 1 вариантов** | Тихая привязка default-варианта из шаблона (`isDefault: true` или первый по списку) | Хинт-метка возле бейджа: «Доступно N вариантов» (caption `--ou-fg-muted`). Смена через `…` row-menu (см. §4.3.3) |
| **0 вариантов** | **Fallback** на вариант того же `kind` из встроенного стандартного шаблона | Warning-индикация: «Используется вариант из стандартного шаблона» (caption `--ou-warning-on-soft`). Кнопка «Сменить шаблон» ведёт во вкладку «Оформление» |

При смене SCORM-шаблона теста система **пересчитывает** привязки системных
вариантов по той же логике. Если автор уже редактировал параметры и они
несовместимы с привязанным вариантом — сценарии mapping описаны в §4.3.4.

#### 4.3.3 Смена варианта на существующей странице

Триггер: `…` iconbtn в `page-row` → пункт «Сменить вариант». Доступно для
страниц `kind: router` / `summary` / `intro` (при наличии нескольких вариантов
этого `kind` в шаблоне) и `kind: info` (всегда, если доступен более чем один
info-вариант).

Контракт совместимости параметров: **«имя поля = контракт между вариантами
одного `kind` в одном шаблоне»** — симметрично контракту «имя варианта =
контракт между шаблонами». При смене:

- поля с тем же именем и совместимым типом — **переносятся**;
- остальные — **удаляются** с явным предупреждением.

UI: модал `ou-modal --m` (аналог `s-add-step1`) с дополнительным diff-блоком:

```text
Сменить вариант: «Информация» → «Контентная страница»

Будут удалены параметры:
- Цвет фона блока: «#0066cc»
- Текст кнопки «Далее»: «Продолжить»

Будут сохранены:
- Заголовок: «Введение»  (поле `title` есть в обоих вариантах)

[Отменить] [Сменить]
```

Состояния wireframe (см. отдельный файл `prd7-variant-replace.html`):

- `s-replace-modal` — модал выбора нового варианта с diff-блоком;
- `s-replace-empty-diff` — спокойный случай (нет потерь, все поля совместимы);
- `s-replace-no-fields` — у нового варианта пустая schema (просто подтверждение).

#### 4.3.4 Дрейф системных вариантов при смене шаблона

Если до смены шаблона автор настроил параметры системного варианта и в новом
шаблоне:

- нет варианта того же `kind` → срабатывает fallback на стандартный шаблон
  (warning-индикация в `page-row`, параметры теста сохраняются как есть в
  расчёте на возврат к совместимому шаблону);
- есть варианты того же `kind`, но default-вариант поменялся → система
  привязывает новый default и применяет ту же логику «имя поля = контракт»;
  несовместимые параметры удаляются молча (без диалога `s-mapping`), потому
  что системные страницы — единичные и пользователь не «терял» страницу,
  а только параметры. В журнале изменений теста фиксируется factual diff.

Диалог `s-mapping` (см. §4.2) **не применяется** к системным вариантам — он
обслуживает только `kind: info` (пользовательские страницы), где автор должен
явно решить судьбу каждой несовместимой страницы.

#### 4.3.5 Жизненный цикл записей `content_pages` для системных kind

Все четыре системных типа (`questions` / `router` / `summary` / `intro`)
хранятся в `content_pages` как обычные записи с особым `kind`. Различие — в
гранулярности и триггерах создания/удаления:

| `kind` | Когда создаётся system'ом | Когда удаляется system'ом |
| --- | --- | --- |
| `intro` | При создании теста (одна запись с `topicId: null`) | При удалении теста |
| `summary` | При создании теста (одна запись с `topicId: null`) | При удалении теста |
| `router` | При смене `flowMode` на `router_by_topics` (одна запись с `topicId: null`) | При смене `flowMode` обратно на любой `linear_*` (молча, без `s-mapping`) или при удалении теста |
| `questions` (в `linear_flat`) | При смене `flowMode` на `linear_flat` (одна запись с `topicId: null`) | При смене `flowMode` на `linear_by_topics` / `router_by_topics` (заменяется на N записей с `topicId`) или при удалении теста |
| `questions` (в `linear_by_topics` / `router_by_topics`) | При добавлении темы в `test_sections` (запись с `topicId: <topic-id>`); при смене `flowMode` с `linear_flat` (по одной записи на каждую существующую тему) | При удалении темы (каскад) или при смене `flowMode` на `linear_flat` (схлопывается в одну запись с `topicId: null`) |

Во всех случаях система при создании записи **тихо привязывает default-вариант**
по §4.3.2. При схлопывании / разворачивании записей `questions` при смене
`flowMode` параметры варианта одной из старых записей переносятся на новую
(по правилу «имя поля = контракт между вариантами одного `kind`» из §4.3.3),
остальные значения теряются с фиксацией в журнале изменений.

Авторский UI **не позволяет** удалять системные записи вручную (нет `delete`,
нет insert-row до/после, нет drag-handle). Эти записи отображаются как
`page-row--system` и отличаются от пользовательских (`kind: info`) поведением,
но не визуальной формой (бейдж имени варианта, expand при непустой schema,
`…` row-menu — одинаковые).

#### 4.3.6 Валидация обязательных параметров варианта

Schema варианта (`variant.schema.fields`) может содержать поля с `required: true`.
Для каждой записи `content_pages` система проверяет: все обязательные поля
заполнены (значение присутствует в `values_json.values` и не пустое).

**Поведение при незаполненном обязательном поле:**

- В соответствующей `page-row` отображается **inline-alert** (warning-баннер
  внутри `page-row-expand` со списком конкретных полей: «Заполните: Заголовок,
  Подзаголовок»; сама `page-row` помечается warning-цветом заголовка через
  модификатор `page-row--warn`).
- На вкладке «Структура» (`.ou-tabs__tab` с лейблом «Структура») показывается
  агрегированный **error-индикатор** (`.status-dot--error`), как описано в
  FR-25b / NFR-21 (индикаторы вкладок).
- Кнопка **«Сохранить»** в footer Drawer'а **disabled**; tooltip объясняет
  «Заполните обязательные поля на вкладке Структура».
- Действие **«Закрыть Drawer»** при таком состоянии показывает confirm-диалог
  «Сохранить с ошибками нельзя; выйти без сохранения?» (см. PRD-7 § Drawer
  confirmation dialogs).

Это правило применяется ко всем `kind` без исключения: `info` / `intro` /
`summary` / `router` / `questions`. Валидация на стороне сервера в API
`POST/PUT/replace-variant` также проверяет required-поля и возвращает
структурированную ошибку с указанием конкретных полей.

### 4.4 Page templates и placeholders

SCORM-шаблон объявляет доступные скелеты страниц:

```json
{
  "key": "intro.hero",
  "label": "Введение: заголовок и изображение",
  "pageKind": "content.intro",
  "layout": "content.intro",
  "placeholders": [
    {
      "key": "title",
      "type": "text",
      "label": "Заголовок",
      "required": true,
      "textFit": {
        "mode": "autoFitFont",
        "defaultFontSize": 36,
        "minFontSize": 24,
        "maxFontSize": 36,
        "allowAuthorFontSize": false,
        "overflow": "warn"
      }
    },
    {
      "key": "subtitle",
      "type": "text",
      "label": "Подзаголовок",
      "textFit": {
        "mode": "fixed",
        "defaultFontSize": 20,
        "allowAuthorFontSize": true,
        "allowedFontSizes": [16, 18, 20, 22],
        "overflow": "warn"
      }
    },
    { "key": "heroImage", "type": "image", "label": "Изображение" }
  ]
}
```

UI страницы строится по `placeholders[]`. Автор видит не HTML и не абстрактный WYSIWYG, а форму
заполнения конкретного скелета страницы.

Поддерживаемые типы placeholders MVP:

```text
text
textarea
richText
image
video
file
number
boolean
select
resultField
actionLabel
```

`richText` допускается только как значение конкретного placeholder и проходит ограничения,
заданные шаблоном: разрешённые marks/blocks, maxLength, запрет scripts/iframes/inline handlers.

Для текстовых placeholders шаблон задаёт политику размера текста `textFit`:

| Режим | Поведение |
| --- | --- |
| `fixed` | Размер шрифта и блока фиксированы; переполнение показывается как предупреждение/ошибка |
| `autoFitFont` | Runtime уменьшает размер шрифта в заданных пределах, чтобы текст поместился |
| `growBox` | Размер шрифта фиксирован, блок увеличивается по вертикали под текст |

Шаблон также задаёт `allowAuthorFontSize`. Если значение `false`, автор не может менять размер
шрифта для этого placeholder. Если `true`, UI показывает настройку размера шрифта в пределах,
заданных шаблоном через `minFontSize`/`maxFontSize` или `allowedFontSizes`.

Ручной размер шрифта сохраняется как `placeholderStyles[placeholderKey].fontSize` конкретной
страницы, а не как изменение layout. Для `richText` это размер контейнера placeholder; произвольный
inline font-size внутри richText не входит в MVP.

### 4.5 Авторский сценарий создания страницы

Сценарий применяется к **пользовательским** страницам `kind: info` (см. §4.3).
Системные страницы (`questions` / `router` / `summary` / `intro`) автор не
создаёт явно — они привязываются тихо по §4.3.2.

1. Автор нажимает **"+ Добавить страницу"** в `insert-row` соответствующей зоны.
2. Открывается модал `s-add-step1` с фильтром по `kind: info` вариантам
   текущего шаблона.
3. Автор выбирает variant из списка (имя варианта = контракт между шаблонами).
4. Выбирает режим: **по шаблону**, **стандартная**, **HTML**.
5. В режиме **по шаблону** UI показывает форму placeholders выбранного варианта.
6. Автор заполняет значения inline в `page-row-expand` (см. PRD-7).
7. Автор открывает предпросмотр в текущем шаблоне (модал `s-page-preview`).
8. Сохраняет страницу.

Для системных страниц `kind: router` / `summary` / `intro` (при наличии в
шаблоне нескольких вариантов одного `kind`) автор может сменить
привязанный системой default-вариант через `…` row-menu → «Сменить вариант»
(см. §4.3.3).

### 4.6 `summary`

`summary` не является статическим HTML-экраном. Шаблон может объявить page template для summary с
placeholders типа:

```text
title
passedText
failedText
resultPercent
resultStatus
recommendations
```

Core подставляет актуальный результат раздела/темы в placeholders типа `resultField`.

`resultField` поддерживает динамическую визуализацию через renderer plugins. Шаблон объявляет
`allowedPaths`, `allowedRenderers`, `defaultRenderer` и схему `rendererOptions`; автор выбирает
показатель и renderer, но не пишет HTML/SVG/JS диаграммы вручную.

Пример значения страницы:

```json
{
  "progressChart": {
    "path": "progress.active.percent",
    "renderer": "core.ringChart",
    "label": "Пройдено",
    "rendererOptions": {
      "showValue": true
    }
  }
}
```

Renderer plugins расширяют набор визуализаций без изменения Core. В MVP обязательны встроенные
`core.textMetric`, `core.badge`, `core.progressBar`, `core.ringChart`, `core.segmentedProgress`.
Дополнительные renderer plugins могут поставляться внутри SCORM-шаблона или подключаться из
администрируемого registry и копироваться в SCORM ZIP при экспорте.

### 4.7 HTML-страницы

`html` остаётся отдельным режимом для технических авторов и нестандартных случаев. Он не должен
быть основным способом создания контентных страниц. HTML проходит санитизацию; запрещены скрипты,
inline-обработчики событий, iframe, небезопасные SVG/URL и внешние ресурсы.

### 4.8 Структурный вид

```text
Тема 1
  [+ Добавить до темы]
  intro: "Введение"
  > 15 вопросов
  summary: "Итог"
  [+ Добавить после темы]

Тема 2
  [+ Добавить до темы]
  > 20 вопросов
  [+ Добавить после темы]
```

Drag-and-drop разрешён в рамках одной темы и одной позиции. Перемещение к другой теме выполняется
через редактирование привязки.

#### Изменение порядка тем

Автор должен иметь возможность изменить порядок тем в тесте непосредственно на вкладке
**"Структура"**.

**Механика:** каждый заголовок темы содержит видимую ручку захвата (⠿). Drag-and-drop позволяет
переместить тему на новую позицию; drop-zone отображается между темами во время перетаскивания.
Клавиатурная альтернатива: Tab на ручку, затем стрелки ↑↓ для перемещения, Enter для фиксации.

**Зависимость данных:** порядок тем хранится в поле `test_sections.sort_order`; без него порядок
недетерминирован. Поле `sort_order` требуется от [PRD-4](prd-4-course-flow-sections.md) и является
блокером для реализации перестановки тем на UI.

**Ограничения:**

- перемещение тем не является перемещением контентных страниц и не меняет привязку страниц к темам;
- смена порядка тем немедленно сохраняется через отдельный API-вызов (`PUT /api/tests/:id/sections/reorder`).

### 4.9 Поток страниц

Core строит общий поток страниц:

```text
start
контент до T1
вопросы T1
контент после T1
контент до T2
вопросы T2
контент после T2
results
системные страницы, если правила или runtime переводят на них
```

При включённом retake gate из [PRD-6](prd-6-retake-cooldown-gate.md) страница `system.blocked`
может отображаться до внутреннего старта курса и до SCORM `Initialize`.

Прогресс по вопросам и прогресс по страницам считаются отдельно. Шаблон получает оба значения и
выбирает `progress.active` через `progress.mode`.

## 5. Применение шаблона при экспорте

При генерации SCORM:

1. Система определяет `design_settings_json.templateId`; если он не задан, используется `default`.
2. Реестр шаблонов возвращает нормализованный источник шаблона.
3. Сервер проверяет совместимость `templateApiVersion`.
4. В SCORM ZIP копируется только выбранный шаблон в директорию `template/`.
5. В ZIP добавляются Core runtime, TEST_DATA, SCORM-манифест, локальные ресурсы теста,
   контентных страниц и контрактные preview-ресурсы шаблона.
6. Сервер не рендерит шаблон и не исполняет `template.js`.
7. В браузере Core загружает `template/manifest.json`, `shell.html`, нужный макет, частичные шаблоны и ресурсы.
8. Core рендерит макет через path-only DSL, заполняет контролируемые слоты и подключает Runtime API.

## 6. Runtime-поведение MVP

### 6.1 Оболочка и действия

PRD-1 требует, чтобы Core поддержал базовый контракт оболочки и действий из технической
спецификации. Минимально:

```html
<div data-slot="page"></div>
<button data-nav="next"></button>
<button data-action="answer-submit"></button>
<button data-action="test-finish"></button>
```

Остальные слоты и действия оболочки остаются опциональными и описаны в
[платформе SCORM-шаблонов](spec-template-platform.md).

### 6.2 Макеты вопросов

PRD-1 требует, чтобы макеты вопросов поддерживали слоты интерактивов, которыми владеет Core:

```html
<div data-slot="question-prompt"></div>
<div data-slot="question-interaction"></div>
```

Core рендерит стандартные интерактивы `single`, `multiple`, `matching`, `ranking`.
Переопределение механики вопросов не входит в PRD-1 и вынесено во вторую фазу технической
спецификации.

#### 6.2.1 Варианты `kind: questions`

Шаблон объявляет варианты `kind: questions` как обычные variant'ы в массиве
`variants[]` (см. §4.3) — каждый такой variant представляет собой **один
ejs-шаблон**, который рендерит макет страницы вопроса. Внутри шаблона условная
логика выбирает обёртку под конкретный тип интерактива (`question.kind ===
'single' | 'multiple' | 'matching' | 'ranking'`); сами интерактивы Core
вставляет в слот `question-interaction`.

```json
{
  "variants": [
    {
      "id": "questions-minimal",
      "kind": "questions",
      "name": "Минимальный",
      "description": "Компактный макет для коротких тестов",
      "isDefault": true,
      "templateFile": "questions-minimal.ejs"
    },
    {
      "id": "questions-extended",
      "kind": "questions",
      "name": "Расширенный",
      "description": "Двухколоночный макет с медиа-полем",
      "templateFile": "questions-extended.ejs"
    }
  ]
}
```

Внутри `questions-minimal.ejs`:

```ejs
<div class="question-page">
  <div data-slot="question-prompt"></div>
  <% if (question.kind === 'matching') { %>
    <div class="match-grid two-cols"><!-- matching wrapper --></div>
  <% } else if (question.kind === 'ranking') { %>
    <div class="rank-list"><!-- ranking wrapper --></div>
  <% } else { %>
    <div class="answer-list"><!-- single + multiple wrapper --></div>
  <% } %>
  <div data-slot="question-interaction"></div>
</div>
```

Никакой отдельной коллекции «комбо» в манифесте нет — типы вопросов внутри
одного варианта обрабатываются ejs-логикой автора шаблона (через if или
`<%- include('partials/answer-list') %>`).

**Гранулярность variant'а — локальная per-row:**

- В `linear_flat` есть одна questions-row на тест — у неё один variant.
- В `linear_by_topics` / `router_by_topics` — questions-row внутри каждой темы;
  **каждая тема может иметь свой variant**. Тема «Основы» — `questions-minimal`,
  тема «Углублённо» — `questions-extended`. Per-row выбор автора.

Variant хранится **в `content_pages`** как обычная запись с `kind: questions`,
`topicId: <topic-id>` (или `null` для `linear_flat`) и `templateKey: <variant-id>`
(см. §7.3). Логика связывания вариантов — общая §4.3.2: 1 → тихая привязка,
N > 1 → default + хинт, 0 → fallback на стандартный шаблон. Жизненный цикл —
§4.3.5 (auto-create при создании темы, auto-delete при удалении темы или смене
flowMode).

### 6.3 Макеты контентных страниц

Макеты контентных страниц объявляют placeholders через `manifest.contentTemplates[]`.
Runtime заполняет их через `data-placeholder`:

```html
<h1>{{ page.values.title }}</h1>
<div data-placeholder="body"></div>
<img data-placeholder="heroImage">
```

Обычные подстановки `{{ path }}` всегда экранируются. RichText/HTML значения вставляются только
как значения placeholders с типом `richText` или в режиме `html` после санитизации.

Для динамических placeholders типа `resultField` Runtime вызывает renderer через registry:

```html
<div data-placeholder="progressChart"></div>
```

Renderer выбирается из значения placeholder и должен быть разрешён в `allowedRenderers` page
template. Если renderer plugin отсутствует, несовместим или падает, Runtime показывает fallback
`core.textMetric` и пишет диагностическое сообщение.

### 6.4 Автопереход

Автопереход не является шаблонным HTML-трюком. Он выполняется через Core, правила и Runtime API:

- Core знает `page.autoAdvance` и `page.autoAdvanceDelayMs`;
- состояние таймера доступно макету и runtime-коду шаблона;
- по истечении таймера выполняется `nav.next`, если финальные защиты Core разрешают переход.

## 7. Модель данных

### 7.1 `tests.design_settings_json`

```json
{
  "templateId": "corporate",
  "templateVersion": "1.0.0",
  "templateApiVersion": "1.0",
  "params": {
    "brand.primaryColor": "#0066cc",
    "progress.mode": "questions"
  }
}
```

Привязки **системных вариантов** (`kind: questions` / `router` / `summary` /
`intro`) хранятся не здесь, а в `content_pages` как обычные записи с
`templateKey` (см. §7.3 и §4.3.5). `design_settings_json` хранит только
test-level параметры шаблона (`params`) и идентификатор самого шаблона.

### 7.2 `templates`

PRD-1 использует общий реестр шаблонов только для чтения активных/встроенных шаблонов.
Административные поля жизненного цикла (`status`, валидация, smoke test, upload/update/delete)
описаны в [PRD-3](prd-3-external-templates.md).

Минимально PRD-1 зависит от:

| Поле | Назначение |
| --- | --- |
| `id` | Технический ID шаблона |
| `name` | Название в галерее |
| `version` | Версия шаблона |
| `template_api_version` | Версия контракта шаблонов |
| `is_builtin` | Признак встроенного шаблона |
| `is_active` | Доступность для автора |
| `manifest` | Источник параметров, возможностей и метаданных макетов |
| `preview_path` | Предпросмотр в галерее |

### 7.3 `content_pages`

`content_pages` хранит авторское содержимое страниц конкретного теста. Эти данные не являются
частью шаблона и не должны удаляться при смене `design_settings_json.templateId`.

```sql
CREATE TABLE content_pages (
  id                    uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  test_id               uuid NOT NULL REFERENCES tests(id) ON DELETE CASCADE,
  topic_id              uuid NOT NULL REFERENCES topics(id),
  position              text NOT NULL CHECK (position IN ('before_topic', 'after_topic')),
  mode                  text NOT NULL DEFAULT 'template' CHECK (mode IN ('template', 'standard', 'html')),
  type                  text NOT NULL CHECK (type IN ('intro', 'info', 'summary', 'html')),
  template_key          text,
  sort_order            integer NOT NULL DEFAULT 0,
  values_json           jsonb NOT NULL DEFAULT '{}'::jsonb,
  auto_advance          boolean NOT NULL DEFAULT false,
  auto_advance_delay_ms integer CHECK (auto_advance_delay_ms BETWEEN 3000 AND 120000),
  created_at            timestamp NOT NULL DEFAULT now(),
  updated_at            timestamp NOT NULL DEFAULT now()
);
```

В UI задержка автоперехода задаётся в секундах. Поле `auto_advance_delay_ms` остаётся техническим
форматом хранения в миллисекундах.

`values_json` хранит структурированный контент страницы:

```json
{
  "values": {
    "title": "Перед началом раздела",
    "subtitle": "Короткое описание"
  },
  "placeholderStyles": {
    "subtitle": {
      "fontSize": 18
    }
  }
}
```

`placeholderStyles` допускается только для параметров, явно разрешённых placeholder в
`contentTemplates[]`. В MVP это ручной `fontSize` при `allowAuthorFontSize = true`.

## 8. API

### 8.1 Шаблоны

```text
GET /api/templates
```

Возвращает активные шаблоны для автора.

```text
GET /api/templates/:id
```

Возвращает манифест и метаданные шаблона.

### 8.2 Настройки дизайна теста

```text
GET /api/tests/:id/design
PUT /api/tests/:id/design
```

`PUT` валидирует:

- `templateId` существует и активен;
- `templateApiVersion` поддерживается;
- параметры соответствуют `manifest.params`;
- `test.navigationPolicy` не нарушается возможностями шаблона.

### 8.3 Контентные страницы

```text
GET /api/tests/:id/content-pages
POST /api/tests/:id/content-pages
PUT /api/tests/:id/content-pages/:pageId
DELETE /api/tests/:id/content-pages/:pageId
PUT /api/tests/:id/content-pages/reorder
```

API валидирует `values_json.values` по схеме placeholders выбранного `contentTemplate` и
`values_json.placeholderStyles` по ограничениям этих placeholders. RichText/HTML значения
санитизируются при создании/обновлении и повторно перед экспортом. Ответы API возвращают значения
placeholders и разрешённые style overrides, а не HTML, срендеренный выбранным шаблоном.

## 9. UI автора

В редакторе теста добавляются вкладки:

- **Оформление**: галерея шаблонов, параметры, предпросмотр, сброс.
- **Структура**: структура тем, добавление/редактирование/удаление контентных страниц.

До разработки UI должны быть подготовлены и согласованы wireframes для обеих вкладок:

- **Оформление**: галерея шаблонов, выбранное состояние, форма параметров, предпросмотр, ошибки
  валидации, сброс к умолчаниям;
- **Структура**: структура тем, пустое состояние, создание страницы, редактирование `intro`,
  `info`, `summary`, `html`, сортировка, удаление, ошибки санитизации и предпросмотр;
- общие состояния: загрузка, сохранение, несохранённые изменения, ошибка API, read-only режим,
  мобильная/узкая ширина при необходимости.

Согласованные wireframes являются входом для frontend-разработки. Если в ходе реализации требуется
изменить сценарий или состав полей, изменение возвращается на повторное согласование.

Во вкладке **"Структура"** автор редактирует экземпляры страниц: режим, page template, место в flow,
значения placeholders и автопереход. Выбор шаблона во вкладке **"Оформление"** не должен удалять
значения placeholders; если новый шаблон не содержит нужного `templateKey`, UI показывает состояние
сопоставления page template.

Настройка `navigationPolicy` относится к настройкам теста, а не к декоративным параметрам
шаблона. Шаблон может влиять на представление, но не может ослабить бизнес-ограничение теста.

## 10. Нефункциональные требования

| ID | Требование |
| --- | --- |
| NFR-01 | Сервер не исполняет код шаблона и не рендерит HTML шаблона |
| NFR-02 | В SCORM ZIP попадает только выбранный шаблон |
| NFR-03 | Тесты без настроек используют `default` |
| NFR-04 | Все встроенные шаблоны проходят структурную валидацию и браузерную smoke-проверку |
| NFR-05 | RichText/HTML значения placeholders санитизируются и вставляются только через контролируемый renderer/placeholder |
| NFR-06 | Внешние URL для ресурсов шаблона запрещены |
| NFR-07 | Runtime-ошибка шаблона показывает экран ошибки Core |
| NFR-08 | P95 экспорта не растёт более чем на 5 с |
| NFR-09 | Политика размера текста `textFit` применяется детерминированно и не должна ломать соседние элементы layout |
| NFR-10 | Renderer plugins не имеют доступа к SCORM API, не меняют runtime state и при ошибке заменяются fallback renderer |

## 11. Критерии приёмки

- [ ] Wireframes вкладок **"Оформление"** и **"Структура"** подготовлены и согласованы до разработки UI
- [ ] Wireframes покрывают перестановку тем: grip-ручка, DnD, drop-zone, клавиатурная альтернатива
- [ ] Wireframes покрывают основные, пустые, ошибочные и loading/saving состояния
- [ ] Галерея показывает встроенные шаблоны `default`, `corporate`, `minimal`
- [ ] Выбор шаблона сохраняет `templateId` и `params`; `templateVersion` и `templateApiVersion` отображаются как read-only диагностические значения выбранного шаблона
- [ ] Форма параметров строится из `manifest.params`
- [ ] Параметры с `cssVar` применяются в браузере как CSS-переменные
- [ ] При смене шаблона несовместимости вариантов страниц `kind: info` разрешаются
      модальным диалогом mapping (выбор замены из вариантов нового шаблона или
      удаление страницы)
- [ ] Системные варианты (`kind: questions` / `router` / `summary` / `intro`)
      привязываются тихо по логике §4.3.2: 1 вариант → молча; N > 1 → default +
      хинт «доступно N вариантов»; 0 → fallback на стандартный шаблон + warning
- [ ] Манифест шаблона объявляет `variant.kind` для каждого варианта (5 значений:
      `questions` / `router` / `summary` / `intro` / `info`); валидация шаблона
      отклоняет варианты без `kind` или с неизвестным `kind`
- [ ] Шаблон содержит хотя бы один вариант `kind: questions` (один ejs-файл, рендерящий
      обёртки под все четыре типа интерактивов через условную логику)
- [ ] Все системные варианты (`kind: questions` / `router` / `summary` / `intro`)
      хранятся в `content_pages` как обычные записи с особым `kind`; жизненный цикл
      записей описан в §4.3.5
- [ ] Гранулярность `kind: questions`: в `linear_flat` — одна запись с `topicId: null`;
      в `linear_by_topics` / `router_by_topics` — по одной записи на тему; variant
      выбирается **локально per-row**, разные темы могут иметь разные variant'ы
- [ ] Смена варианта существующей страницы через `…` row-menu → «Сменить вариант»;
      контракт «имя поля = контракт между вариантами одного `kind`» обеспечивает
      перенос совместимых полей и удаление остальных с предупреждением (diff-блок)
- [ ] **Валидация обязательных параметров** (§4.3.6): незаполненные `required: true`
      поля любой `page-row` подсвечиваются inline-алертом в самой row (warning-цвет
      заголовка + список конкретных полей в expand), агрегированным error-индикатором
      на табе «Структура» (`.status-dot--error`); кнопка «Сохранить» disabled до
      устранения; серверный API возвращает структурированную ошибку
- [ ] Бейдж имени варианта в авторском UI остаётся нейтральным; CSS enum-классы
      `.type-intro/.type-info/.type-summary/.type-html` не возвращаются
- [ ] SCORM ZIP содержит только выбранный шаблон в `template/`
- [ ] Core загружает оболочку/макеты в браузере без серверного рендера
- [ ] `question-prompt` и `question-interaction` заполняются Core
- [ ] Шаблон объявляет `contentTemplates[]` с `key`, человекочитаемым `label` и placeholders для контентных страниц
- [ ] UI строит форму страницы по placeholders выбранного page template
- [ ] Для текстовых placeholders применяется `textFit.mode = fixed/autoFitFont/growBox`
- [ ] `allowAuthorFontSize = false` скрывает ручную настройку размера шрифта в UI
- [ ] `allowAuthorFontSize = true` разрешает ручной размер шрифта только в пределах, заданных шаблоном
- [ ] Ручной размер шрифта хранится в `placeholderStyles`, а не меняет layout шаблона
- [ ] RichText/HTML placeholders проходят санитизацию и не ломают стандартизированную вёрстку шаблона
- [ ] Содержимое контентной страницы сохраняется как значения placeholders
- [ ] Смена шаблона не удаляет и не перезаписывает `content_pages`
- [ ] Если новый шаблон не содержит нужного `templateKey`, UI предлагает сопоставить страницу с новым page template
- [ ] `progress.mode = questions/pages/hidden` корректно меняет `progress.active`
- [ ] `intro` отображается перед вопросами выбранной темы
- [ ] `summary` отображает итог темы без влияния на оценку
- [ ] `resultField` поддерживает выбор renderer из `allowedRenderers`
- [ ] Runtime загружает renderer plugins из манифеста/SCORM ZIP и применяет fallback при ошибке
- [ ] UI строит настройки `rendererOptions` по схеме выбранного renderer
- [ ] `system.blocked` может быть отрендерена как системная страница шаблона без запуска вопросного flow
- [ ] Автопереход переводит дальше после задержки и не обходит финальные защиты Core
- [ ] Runtime-ошибка шаблона показывает экран ошибки Core, а не белый экран

## 12. Решённые вопросы

| Вопрос | Решение |
| --- | --- |
| Шаблон исполняется на сервере? | Нет. Только в браузере обучающегося |
| Нужен ли EJS? | Нет. Браузерный рендерер использует path-only DSL |
| Может ли шаблон менять механику вопросов в MVP? | Нет. Используется слот интерактива, которым владеет Core |
| Будет ли расширенное переопределение интерактивов? | Да, во второй фазе технической спецификации |
| Как вставлять rich HTML? | Только как значение placeholder типа `richText` или в режиме `html`, после санитизации; сырая интерполяция запрещена |
| Как хранить параметры? | Ключи с точечной нотацией в `design_settings_json.params` |
| Как выбирать прогресс? | `progress.mode` + `progress.active` |
| Где описан точный контракт? | `spec-template-platform.md` |
| Что такое `variant.kind`? | Функциональная роль варианта в манифесте шаблона (5 значений: `questions` / `router` / `summary` / `intro` / `info`); определяет, где допустим этот вариант и как срабатывает логика связывания. Не визуальный enum — бейдж нейтральный |
| Где выбирается макет вопросов? | В вкладке «Структура» в самой questions-row (page-row--system с variant select, expand при непустой schema и `…` row-menu). В `linear_by_topics` / `router_by_topics` variant локальный per-topic; в `linear_flat` — одна row на тест |
| Зачем variant `kind: questions` — это «комбо макетов под типы»? | Нет, это **один ejs-файл**, который рендерит обёртку под любой тип вопроса через условную логику (`question.kind === 'single' / 'multiple' / 'matching' / 'ranking'`). Никакой отдельной коллекции «комбо» в манифесте не нужно — типы обрабатываются ejs-логикой автора шаблона |
| Что если в шаблоне нет нужного `kind`? | Системные варианты (`questions`/`router`/`summary`/`intro`) — fallback на стандартный шаблон с warning. Пользовательские (`info`) — диалог `s-mapping` |
| Можно ли сменить вариант на существующей странице? | Да, через `…` row-menu. Контракт совместимости параметров: «имя поля = контракт между вариантами одного `kind`» |
| Что произойдёт при незаполненных обязательных параметрах варианта? | Inline-alert в самой row (warning-цвет заголовка, список полей в expand) + error-индикатор на табе «Структура» + Save disabled. Сервер возвращает структурированную ошибку. См. §4.3.6 |
