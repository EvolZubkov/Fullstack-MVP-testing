## Что изменилось с первичного аудита (2026-06-07)

Устранено:

- Утечка секретов (находка 1, единственная критическая): файлов с секретами в индексе git больше нет,
  `.gitignore` содержит правило `.env*` с исключением `!.env.example`. Фаза 0 плана закрыта.

Улучшения контура ИБ (не закрывают находки целиком, но усиливают защиту):

- Хэширование паролей переведено с `bcrypt` на `scrypt` (OWASP-профиль, `@vvlad1973/crypto`, PRD-9);
  legacy-хэши `bcrypt` лениво перехэшируются при входе.
- Вход сделан устойчивым к перечислению по времени ответа: при отсутствии УЗ выполняется фиктивная
  проверка (`dummyVerifyPassword`), `forgot-password` всегда отвечает единообразно.
- Введён слой конфигурации (`server/config.ts` + `config-loader.mjs` + `config/*.config.jsonc`)
  с предупреждением о слабом `SESSION_SECRET` в продакшене; secure-флаг cookie вынесен в конфиг.
- Подсистема логирования переведена на Pino (`@vvlad1973/pino-logger-tree`) с редактированием
  секретов (`password`/`token`/`secret`) в записях.
- Ролевая модель заменена на модель прав (PRD-13): 5 ролей и проверка возможностей
  (`requirePermission(capability)`).

Остаются открытыми находки 2-11 (см. таблицу критических находок). Смены стека: React 18 -> React 19,
Tailwind/Radix полностью удалены (UI на дизайн-системе `@universityrt/ui-kit`), Express 5, Drizzle ORM.

## Резюме

`test-builder` -- функциональное full-stack приложение (React 19 + Express 5 + PostgreSQL/Drizzle)
с усиленной за последний месяц базовой защитой: хэширование паролей `scrypt` (OWASP-профиль),
серверные сессии, ролевая модель на правах (PRD-13: 5 ролей), журнал аудита, редактирование секретов
в логах, graceful shutdown, health-check, параметризованные запросы к БД. Однако по корпоративному
стандарту сохраняется ряд несоответствий.

Главный вывод: единственная критическая находка первичного аудита (утечка секретов) устранена,
но код по-прежнему соответствует уровню рабочего MVP, а не уровню промышленной ИС по требованиям
[НФТ]/[ИБ v.4]. Наиболее серьёзные сохраняющиеся расхождения:

1. Парольная политика не отвечает разделу 7 (длина, категории символов, история, периодическая смена).
2. Корпоративная аутентификация (LDAPS/Kerberos/OIDC) отсутствует, обоснование не задокументировано.
3. Подсистема логирования без интеграции с SIEM и без защиты журналов от изменений.
4. Приложение не stateless (сессии в памяти, файлы на локальном диске) -- горизонтальное
   масштабирование в текущем виде невозможно.
5. TLS в приложении не реализован и не enforced; параметры шифрования не зафиксированы в репозитории;
   канал к PostgreSQL без SSL.
6. Изменение конфигурации требует перезапуска (нарушение req 82).
7. Security-заголовки (`helmet`) не подключены, `X-Powered-By` не отключён.

Многие требования (среды, RTO/RPO, сетевая сегментация, ЦОД, K8s-политики, WAF, Анти-DDoS,
пентест) относятся к инфраструктуре и оргмерам и не верифицируются по коду -- они помечены
как «Вне кода».

## Легенда статусов

- Соответствует -- требование выполнено в коде/конфигурации.
- Частично -- выполнено не полностью либо с оговорками.
- Не соответствует -- требование не выполнено.
- Вне кода -- инфраструктурное/организационное требование, не определяется по репозиторию.
- Требует проверки -- нельзя подтвердить статически (нужны сканирование/стенд).

## Детальный разбор по разделам

### 1. Среды развёртывания

Требования к набору сред (PROD/PrePROD/TEST/DEV), их изоляции и доступу разработчиков в PROD --
инфраструктурные и по коду не подтверждаются.

Что есть в репозитории:

- Переключение режима через `NODE_ENV` (`development`/`production`), читается в `server/index.ts`.
- Слой конфигурации: `server/config.ts` + `server/config-loader.mjs` загружают `.env.<NODE_ENV>`,
  затем `.env`, поверх -- некритичный `config/config.jsonc` и per-instance `config/production.config.jsonc`
  (последний выигрывает под `NODE_ENV=production`). Основа для разделения контуров.
- Docker-обвязка под развёртывание (`docker/Dockerfile`, `docker/build/config/docker-compose.yml`).

Статус: Вне кода. Изменение с 2026-06-07: добавлен слой `config/*.config.jsonc`, разделяющий
секреты (`.env`) и некритичные параметры. Рекомендация: зафиксировать матрицу сред в проектной документации.

### 2. Доступность, RTO и RPO

Значения доступности, RTO, RPO, резервного копирования и размещения в ЦОД -- инфраструктура (Вне кода).
Однако одно архитектурное следствие проверяется по коду -- горизонтальное масштабирование (req 31).

Препятствия масштабированию (приложение не stateless):

- Хранилище сессий в памяти процесса: `server/routes.ts:68` -- `new MemStore(...)` (`memorystore`).
  При нескольких экземплярах сессии не разделяются; при рестарте теряются.
- Загруженные файлы пишутся на локальный диск: `server/routes.ts:17-33` (`multer.diskStorage`,
  каталог `uploads/media`). На разных узлах файлы не видны.
- Положительное: пул соединений к БД с ретраями и health-check (`server/db.ts:35-56`, `62-77`).

Статус: Не соответствует (в части req 31). Изменение с 2026-06-07: без изменений. Рекомендация: внешнее
хранилище сессий (например, на PostgreSQL) и общее объектное хранилище для медиа.

### 3. Режимы функционирования

Реализованы технические предпосылки, но не управляемые режимы как состояния системы.

- Health-check: `server/index.ts:146-155` -- `GET /api/health` (проверка БД, ответ 200/503).
- Graceful shutdown: `server/index.ts:206-228` -- обработка `SIGTERM`/`SIGINT`, закрытие HTTP и БД,
  принудительный выход через 30 c.
- Обработка `uncaughtException`/`unhandledRejection`: `server/index.ts:18-29`.
- Периодический heartbeat состояния процесса (uptime/память) раз в 5 минут: `server/logger.ts:259-273`.
- Не реализовано: явный сервисный режим (плановая недоступность с уведомлением),
  аварийный режим и автоматический переход в него при сбое компонентов ИБ.

Статус: Частично. Изменение с 2026-06-07: добавлен heartbeat.

### 4. Совместимость и технологический стек

Серверная часть:

- Базовый образ -- `node:20-slim` (Debian), см. `docker/Dockerfile:13`. Это не РедОС и не «Альт Сервер»
  из списка разрешённых ОС; соответствие ОС требует подтверждения на уровне развёртывания.
- Среда исполнения -- Node.js 20 (JavaScript/TypeScript). Требование по Java (Axiom JDK) неприменимо.
- Жизненный цикл ПО (поддержка не менее 5 лет): Node.js 20 LTS по графику проекта выходит из поддержки
  30.04.2026, то есть на дату актуализации находится на границе/за пределами поддержки. Требуется переход
  на актуальный LTS (Node.js 22/24) до сдачи.
- Контейнеры: образ OCI-совместим (Docker), но манифестов Kubernetes (не ниже 1.2) в репозитории нет.

Клиентская часть:

- SPA на React 19 + Vite -- работает в Chromium-based браузерах (включая Яндекс.Браузер).
- Разрешение экрана/адаптивность -- UI построен на дизайн-системе `@universityrt/ui-kit`
  (Tailwind и Radix полностью удалены); минимальные разрешения отдельно не зафиксированы.
- VDI/терминальная ферма -- инфраструктура.

Статус: Частично. Изменение с 2026-06-07: React 18 -> 19, UI переведён на дизайн-систему; горизонт
поддержки Node 20 из «требует проверки» перешёл в «требуется обновление» (наступил срок EOL).

### 5. Сетевая архитектура и протоколы

#### 5.1. Сегментация

Сегменты (APP/WEB/DB/DMZ) и ограничение трафика -- инфраструктура (Вне кода).
В `docker-compose.yml` сетевые политики не заданы.

#### 5.2-5.3. Протоколы и TLS

- Приложение слушает по HTTP: `server/index.ts:4,32,201` (`createServer` из `http`).
  TLS делегирован обратному прокси (`app.set("trust proxy", 1)`, `server/index.ts:35`).
- В коде/конфиге репозитория нет настройки минимальной версии TLS, наборов шифров,
  редиректа HTTP->HTTPS и заголовка HSTS.
- Флаг `cookie.secure` вынесен в конфигурацию (`config.server.cookieSecure`, `server/routes.ts:73`) --
  можно включить secure-cookie за TLS-прокси, но сам TLS в приложении не enforced.
- Подключение к PostgreSQL без SSL: `server/db.ts:35-40` -- в `Pool` нет параметра `ssl`,
  в `DATABASE_URL` `sslmode` не задаётся. Требование «PostgreSQL SSL» не выполняется на уровне приложения.
- SMTP поддерживает защищённое соединение через `config.email.secure` (`server/email.ts:11-21`).

Статус: Частично/Не соответствует. Изменение с 2026-06-07: добавлен конфигурируемый `cookie.secure`;
остальное без изменений. TLS веб/API не enforced в коде, политика шифров не зафиксирована,
канал к БД незащищён. Если TLS терминируется на прокси -- это должно быть задокументировано
и подтверждено (раздел 13).

#### 5.4. Взаимодействие компонентов

- Адреса задаются через конфигурацию/переменные окружения (`API_BASE_URL`, `APP_URL`) -- основа
  для работы по FQDN.
- Привилегированный доступ через JumpHost/VDI/PAM -- инфраструктура.

Статус: Частично.

### 6. Аутентификация и управление доступом

#### 6.1. Корпоративная аутентификация

Реализована только локальная аутентификация (email + пароль), см. `server/routes/auth.ts:31-95`.
Поддержки LDAPS/Kerberos/OIDC нет. По [ИБ IBv004-IAF-005] требуется корпоративная аутентификация
(вне DMZ), а локальная допустима лишь при подтверждённой невозможности и соблюдении парольной политики
(которая здесь не соблюдена -- см. раздел 7).

Статус: Не соответствует (нет корп. аутентификации и задокументированного обоснования).
Изменение с 2026-06-07: без изменений.

#### 6.2. Учётные записи

- Учётные записи персонифицированные (по email), групповых/неперсонифицированных нет.
- Отдельные технологические УЗ на каждую интеграцию/службу не формализованы; в приложении нет
  понятия сервисной учётной записи или API-ключей.

Статус: Частично.

#### 6.3. Ролевая модель

- RBAC на модели прав (PRD-13): 5 ролей (`superuser`/`administrator`/`author`/`manager`/`learner`,
  `shared/access/roles.ts`); пользователь держит набор ролей, права -- объединение по ролям.
  Проверка через фабрику `requirePermission(capability)` (`server/middleware/auth.ts:68-`) поверх
  карты роль -> возможность (`shared/access/permissions.ts`); сохранены legacy-гварды
  `requireAuthor`/`requireLearner`.
- Объектные скоупы поверх ролей: владелец теста и `test_access_grants`, владелец/видимость темы
  и `topic_access_grants` (PRD-15).
- Назначение ролей через AD/IAM отсутствует (локальная модель).
- Серверная фильтрация списка пользователей по группам и по статусу (заблокирована/активна)
  в API `GET /api/users` (`server/routes/users.ts:24-39`) не реализована -- возвращаются все
  пользователи (req 50).

Статус: Частично. Изменение с 2026-06-07: 2 роли (`author`/`learner`) заменены на 5 ролей и модель
прав (PRD-13).

#### 6.4. Подключение приложения к БД

- Параметры подключения -- в конфигурации (`config.database.url`), не в коде: `server/db.ts:32-36`. Хорошо.
- Учётная запись БД из строки подключения; ограничение её привилегий -- задача развёртывания.
- SSL канала к БД не настроен (см. раздел 5).

Статус: Частично/Соответствует (хранение параметров в конфиге выполнено).

#### 6.5. Управление сеансами

- Деактивация пользователя блокирует новые входы (`server/routes/auth.ts:51-54`) и уничтожает сессию
  при следующем обращении к `/api/auth/me` (`server/routes/auth.ts:153-156`).
- Принудительное завершение уже активных сессий заблокированного пользователя не реализовано
  (хранилище в памяти не позволяет перечислять/закрывать чужие сессии).
- Мониторинг активных сессий (список сессий, уведомления о входе с нового устройства/IP) отсутствует
  (req 54, 60).

Статус: Не соответствует. Изменение с 2026-06-07: без изменений.

### 7. Парольная политика (встроенная аутентификация)

#### 7.1. Хранение паролей

- Хэширование `scrypt` (OWASP-профиль пакета `@vvlad1973/crypto`, PRD-9); в БД хранится только хэш,
  параметры кодируются в самом хэше (`server/utils/crypto.ts:121-152`).
- Случайная соль на каждый пароль (встроена в scrypt) -- одинаковые пароли дают разные хэши.
- Legacy-хэши `bcrypt` (`$2a$`/`$2b$`/`$2y$`) распознаются и лениво перехэшируются в scrypt при входе
  (`isLegacyBcryptHash`, `server/utils/crypto.ts:109-171`); `bcryptjs` -- временная зависимость.
- Вторая соль (pepper) из конфигурации не используется (она рекомендательная).

Статус: Соответствует. Изменение с 2026-06-07: алгоритм переведён с `bcrypt` (10 раундов) на `scrypt`.

#### 7.2. Требования к паролю

- Минимальная длина: сервер требует не менее 6 символов в смене пароля, сбросе и завершении первого
  входа (`server/routes/auth.ts:117,288,344`), клиент -- 8. Требование «минимум 10 символов»
  не выполняется, проверки рассинхронизированы.
- Категории символов (минимум 3 из 4) не проверяются.
- Имя/email как часть пароля -- не проверяется.
- Распространённые/словарные пароли -- не проверяются (пустой пароль отклоняется).
- История паролей (несовпадение с N предыдущими) -- не реализована (нет хранилища истории).
- Принудительная смена при первом входе -- реализована (`mustChangePassword`).
- Периодическая принудительная смена -- не реализована.

Статус: Не соответствует. Изменение с 2026-06-07: без изменений.

#### 7.3. UI поля пароля

- Маскирование ввода реализовано (`client/src/components/password-input.tsx`, переключатель видимости).
- Запрет копирования введённого пароля не реализован.

Статус: Частично.

#### 7.4. Защита от перебора

- Лимит входов по IP: 10 попыток за 15 минут (`server/routes/auth.ts:13-28`), хранилище в памяти
  (сбрасывается при рестарте, не на уровне УЗ).
- Блокировка УЗ после N неудачных попыток на M минут -- не реализована; параметры N/M не конфигурируемы.
- Сообщение об оставшихся попытках -- не выводится.
- CAPTCHA/MFA(TOTP) -- отсутствуют.
- Положительное: при отсутствии УЗ выполняется фиктивная проверка пароля (`dummyVerifyPassword`,
  `server/utils/crypto.ts:185-188`), выравнивая время ответа против перечисления пользователей.
- Положительное: сброс пароля по токену реализован надёжно -- 32 байта энтропии, хранится хэш SHA-256,
  одноразовость (`usedAt`), ограниченный срок, лимит 3 запроса в час (`server/routes/auth.ts:193-325`).

Статус: Частично. Изменение с 2026-06-07: добавлено выравнивание времени ответа при несуществующей УЗ.

### 8. Регистрация событий и аудит

#### 8.1. Обязательные события

Журнал аудита определён в `server/logger.ts:296-315`. Фиксируются:

- Вход (успех/неуспех), выход (`auth.login`, `auth.logout`).
- Смена/сброс пароля (`auth.passwordChange`, `auth.passwordReset`).
- Создание/деактивация/активация УЗ, массовый импорт (`user.create`, `user.deactivate`,
  `user.activate`, `user.bulkImport`).
- Сброс попыток прохождения (`attempts.reset`).

Не фиксируются: изменение привилегий/роли, изменение параметров безопасности, попытки
несанкционированного доступа к объектам (отказ 403), удаление УЗ.

Статус: Частично. Изменение с 2026-06-07: набор событий без изменений.

#### 8.2. Атрибуты событий

Запись аудита (`server/logger.ts:240-256`) содержит: тип события (`action`), дату/время (`ts`),
идентификатор запроса (`reqId`), субъект (`userId`); для входа дополнительно `email`, результат
(`success`), IP (`ip`). Отсутствуют обязательные атрибуты: идентификатор приложения (название+версия),
уровень критичности, сервис (протокол+название), IP источника для всех событий (он есть только у входа).

Статус: Частично.

#### 8.3. Подсистема логирования

- Стек: логирование на Pino через `@vvlad1973/pino-logger-tree` с per-source уровнями и редактированием
  секретов (`password`/`token`/`secret`) -- `server/logger.ts:116-130`.
- Хранение: журнал приложения пишется в фиксированный файл (ротация/ретенция -- ответственность
  среды исполнения); журнал аудита -- `logs/audit-YYYY-MM-DD.log` (JSON) с app-managed очисткой
  старше 90 дней (`MAX_AUDIT_DAYS`, `server/logger.ts:30,225-238`). Требование «не менее 3 месяцев»
  для аудита выполнено пограничнo (90 дней).
- Недавние события дополнительно держатся в кольцевом буфере в памяти (2000 записей) для просмотра в UI.
- Отправка в SIEM (Syslog/Elastic Beats) -- отсутствует.
- Защита журналов от изменений (неизменяемость/целостность) -- отсутствует (обычные файлы).
- Просмотр через интерфейс администратора: реализован для недавних событий приложения
  (`GET /api/logs`, гейт `requirePermission("logs.read")`, страница `client/src/pages/author/logs.tsx`);
  для журнала аудита UI и API отсутствуют -- только доступ к файлам.
- Настройка уровня/параметров логирования без перезапуска -- отсутствует (уровни строятся из конфига
  один раз при инициализации дерева логгеров).

Статус: Частично/Не соответствует. Изменение с 2026-06-07: логирование переведено на Pino, добавлено
редактирование секретов; журнал приложения перешёл на фиксированный файл (ротация -- у среды исполнения);
доступ к `/api/logs` переведён на модель прав.

### 9. Защита приложения

#### 9.1. Раскрытие информации

- Тип/версия компонентов: заголовок `X-Powered-By` Express не отключён (`app.disable('x-powered-by')`
  не вызывается, `helmet` не подключён) -- раскрывает фреймворк.
- При ошибке входа возвращается обезличенное «Invalid credentials» (`server/routes/auth.ts:48`) -- хорошо.
- `forgot-password` не раскрывает существование email (единый ответ, `server/routes/auth.ts:203-208`);
  вход выровнен по времени (см. 7.4). Однако эндпоинт `POST /api/auth/check-email`
  (`server/routes/auth.ts:177-190`) и ответ о деактивированной УЗ на входе (`server/routes/auth.ts:53`)
  по-прежнему раскрывают факт существования учётной записи (риск перечисления пользователей).
- Стек-трейсы наружу не отдаются: обработчик ошибок возвращает только `{ message }`
  (`server/index.ts:159-172`), полный стек пишется в лог.

Статус: Частично. Изменение с 2026-06-07: устранено раскрытие через `forgot-password` и таймингом входа;
`check-email` и ответ о деактивации остаются.

сканирования или фиксации отсутствия критических/высоких уязвимостей.
