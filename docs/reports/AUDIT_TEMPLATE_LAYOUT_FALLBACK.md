# Аудит: разрешение макета и fallback на стандартный шаблон

Дата: 2026-07-17. Статус: на согласование. Код по итогам аудита не изменялся.

## 1. Резюме

Правило «что делать, когда шаблон не объявил элемент» описано в спецификациях **тремя
взаимоисключающими способами** и реализовано в коде **пятью независимыми механизмами**, ни один
из которых не совпадает с другим полностью. Внешний шаблон, написанный строго по
`spec-template-platform`, не проходит гейт активации, потому что гейт проверяет контракт,
которого в спецификации нет.

Ключевые выводы:

- PRD-1 §4.3.2 **требует** fallback на стандартный шаблон с предупреждением в UI; PRD-3 NFR-06 и
  `spec-template-platform` §189-190 **запрещают** его. Код реализовал вариант PRD-1 и тем самым
  нарушает NFR-05/NFR-06.
- Разрешение макета — не контракт, а пять расходящихся реализаций (§4.1).
- Поле `contentTemplates[].layoutFile` объявлено в поставляемых шаблонах, задокументировано и
  валидируется, но **ни один рендерер по нему макет не ищет**.
- Слот `page-content` блокирует активацию, хотя все четыре источника (включая сам движок)
  считают его опциональным.

## 2. Повод

Пакет `certification2-1.2.0.zip` не проходит проверку работоспособности: экран `intro.hero`
(route `content.intro`) падает с ошибкой `Нет обязательного слота data-slot="page-content"`, и
кнопка активации остаётся заблокированной.

Воспроизведено локально на общем рендерере: из 12 экранов падает ровно один. Структурная
валидация ZIP при этом проходит без единого блокирующего замечания.

Непосредственная причина: шаблон объявил `layouts["content.intro"]`, следуя примеру манифеста
`spec-template-platform` §204-214 и таблице §859. Резолвер preview/smoke при точном совпадении
ключа предпочитает этот макет общему `content`, подставляет его на контентную страницу и не
находит там слот `page-content`. В рантайме этот ключ не читается вообще.

То есть шаблон следовал спецификации, а сломался о код.

## 3. Что говорят спецификации

### 3.1 Fallback на стандартный шаблон

| Источник | Утверждение |
| --- | --- |
| `prd-1/templates-content-pages.md:344` | 0 вариантов `kind` — **fallback** на вариант того же `kind` из встроенного стандартного шаблона; UI: «Используется вариант из стандартного шаблона» |
| `prd-1/templates-content-pages.md:236-238` | Fallback применяется **только** к системным вариантам `questions` / `router` / `summary` / `intro`, не к страницам `kind: info` |
| `prd-3/external-templates.md:458` | NFR-05: в SCORM ZIP попадает **только выбранный** шаблон |
| `prd-3/external-templates.md:459` | NFR-06: резервное поведение runtime — через **экран ошибки Core**, а не через default-шаблон |
| `prd-3/external-templates.md:496` | «Нужно ли класть резервный default-шаблон в SCORM ZIP? — Нет, используется экран ошибки Core» |
| `spec-template-platform.md:189-190` | Пакет включает только выбранный шаблон «и не резервный default-шаблон» |
| `spec-template-platform.md:1954` | «Пакет не включает резервный default-шаблон в MVP» |

Первые две строки таблицы прямо противоречат остальным пяти.

### 3.2 Разрешение макета

| Источник | Как задаётся макет экрана |
| --- | --- |
| `spec-template-platform.md:204-214` | Ключом в `layouts[]`, равным page kind: `"content.intro": "layouts/content-intro.html"` |
| `spec-template-platform.md:859` | Таблица: `content.intro` («Введение раздела», `before_topic`) — специфичный layout `layouts["content.intro"]`, fallback `layouts.content` |
| `spec-template-platform.md:956` | Путь к макету указывается полем `layoutFile` у элемента `contentTemplates[]`, **а не ключом `layout`, показанным в примерах выше** |

Спецификация противоречит сама себе: §204-214 и §859 задают ключ макета, §956 — поле варианта,
и §956 явным текстом отменяет примеры §204-214.

### 3.3 Блокирующие ошибки и предупреждения

| Источник | Утверждение про опциональные слоты |
| --- | --- |
| `prd-3/external-templates.md:213-214` | «Отсутствующие опциональные макеты» и «отсутствующие опциональные слоты» — предупреждения, **не блокируют активацию** |
| `spec-template-platform.md` §17.2 | «Слоты контентных страниц и результатов опциональны» |

| `docs/guides/template-development.md` §4.3 | «Слот `page-content` не обязателен формально… отсутствие даёт предупреждение» |

Здесь противоречий нет: все четыре источника единогласны.

## 4. Что делает код

### 4.1 Пять механизмов разрешения макета

| Механизм | Где | Как решает |
| --- | --- | --- |
| 1. Резолвер preview/smoke | `shared/template/preview-context.ts:133-143` | `layouts[route]` при точном совпадении, иначе общий (`content.* → content`) |
| 2. Рантайм контентных страниц | `server/scorm/template/app/render/contentPage.js:382` | Всегда `layouts["content"]`; ключ `content.intro` не читается |
| 3. Рантайм вступления раздела | `server/scorm/template/app/render/contentPage.js:222` | Всегда `layouts["section-intro"]` |
| 4. Рантайм системных экранов | `server/scorm/template/app/render/mainRender.js:15-20` | `state.fallbackLayouts[kind]` для fallback-kind, иначе `state.templateLayouts[kind]` |
| 5. Веб-хост | `server/routes/tests.ts:340-356` | Константы `SCREEN_LAYOUTS` (имя файла) + `SCREEN_KIND` (вид варианта) |

Мёртвое звено: `contentTemplates[].layoutFile` объявлен в `server/scorm/templates/default/manifest.json`
(`intro.standard → layouts/section-intro.html`) и в `templates/certification/manifest.json`,
задокументирован в §956 и валидируется на компиляцию DSL
(`server/services/template-validation.ts:167`) — но **ни один из пяти механизмов по нему макет не
резолвит**. Поле пишут, проверяют и игнорируют.

### 4.2 Fallback на стандартный шаблон

Реализован вопреки NFR-05/NFR-06 — и в двух хостах по-разному:

| Слой | Где | Набор kind |
| --- | --- | --- |
| SCORM | `server/scorm/index.ts:76-92` (`computeFallbackKinds`) | `["start", "results"]` |
| SCORM (доставка) | `server/scorm/index.ts:367-397` | Копирует в пакет макеты **и стили** стандартного шаблона |
| SCORM (рантайм) | `templateLoader.js:57-80`, `mainRender.js:15-35` | Подставляет макет и **подменяет таблицу стилей** на дефолтную |
| Веб-хост | `server/routes/tests.ts:353-356` | `start → start`, `question → questions` |
| Веб-хост (результаты) | `server/routes/attempts.ts:1086` | `results` |
| Привязка вариантов | `server/services/variant-binding.ts:71-98` | Любой `kind`; при 0 вариантов — `source: "default-fallback"`, `fallbackUsed: true` |

Наборы `["start", "results"]`, `["start", "questions"]`, `["results"]` не совпадают ни друг с
другом, ни с набором PRD-1 (`questions` / `router` / `summary` / `intro`).

Заметные оговорки реализации:

- `server/services/template-dir.ts:105-108` — `templateOwnsKind` возвращает `true` при
  отсутствии `contentTemplates` и при ошибке БД, то есть отказывает **в пользу** выбранного
  шаблона (fail-open).
- `server/routes/tests.ts:373-375` — брендинг и `cssVars` резолвятся против **активного**
  шаблона, даже когда макет взят из стандартного.
- `server/routes/tests.ts:352` — `blocked` не имеет вида варианта и не откатывается никогда.

### 4.3 Гейт активации

`client/src/features/templates/preview-check-modal.tsx:134` — `report.ok` гейтит кнопку
активации; предупреждения не гейтят (`:157` меняет только тон баннера). Значит перевод
`page-content` в предупреждения снимает блокировку активации, не ослабляя остальных проверок.

## 5. Конфликты

- **К-1. Fallback: требовать или запретить.** PRD-1 §4.3.2 требует, PRD-3 NFR-05/NFR-06 и
  `spec-template-platform` §189-190/§1954 запрещают. Код реализовал PRD-1 и нарушает NFR-05/NFR-06.
- **К-2. Набор kind для fallback.** PRD-1 называет `questions`/`router`/`summary`/`intro`; SCORM
  использует `start`/`results`; веб-хост — `start`/`questions`/`results`. Три разных набора.
- **К-3. Пространство имён макета и страницы.** §204-214 и §859 трактуют ключ `layouts[]` как page
  kind; §956 и поставляемые шаблоны — как `layoutFile` варианта; рантайм — как собственные ключи
  (`section-intro`, `content`). Одно понятие описано тремя способами.
- **К-4. `layoutFile` — мёртвое объявление.** Был объявлен, задокументирован, валидируется, но не
  читался ни одним рендерером. СНЯТ на этапах 2 и 5: превью резолвит по `layoutFile`
  (`resolveLayoutKey`), рантайм подтягивает эти макеты в `templateLoader.js` и предпочитает их в
  `renderContentPage`.
- **К-5. `page-content` блокирует вопреки четырём источникам.** `preview-context.ts:439/548/639`
  против PRD-3 §4.2:213-214, spec §17.2, guide §4.3 и самого движка
  (`render-screen.ts:121-122` молча пропускает отсутствующий слот; `contentPage.js:394`
  рендерит во весь контейнер).
- **К-6. Smoke проверяет не тот макет, который играет.** Резолвер preview (механизм 1) расходится
  с рантаймом (механизмы 2 и 3), поэтому проверка может провалить экран, который в рантайме
  рендерится другим макетом — ровно случай `certification2`.

## 6. Целевое правило

**Согласовано полностью 2026-07-17.** Решения: К-1 (пункт 1), OQ-01 (пункт 2), К-3/К-4 (пункт 3).

1. **Источником истины по fallback признан PRD-1 §4.3.2.** Отсутствие элемента даёт fallback на
   стандартный шаблон и предупреждение в UI, а не блокировку. NFR-06 отменяется; NFR-05
   переформулируется как «в пакет попадает выбранный шаблон плюс резервные макеты и стили
   стандартного для незакрытых системных экранов» — это уже фактическое поведение.
2. **Fallback распространяется на все системные экраны**: `start`, `results`, `questions`,
   `router`, `summary`, `intro`, `review`, `section-results`, `system.*`. Пользовательские
   страницы `kind: info` из fallback исключены (PRD-1:236-238, см. OQ-04). Это снимает К-2 и
   требует правки PRD-1:236-238.
3. **Канонический механизм привязки макета — `contentTemplates[].layoutFile`.** Ключи `layouts[]`
   остаются только для системных экранов без варианта (`shell`, `content`, `question`, `results`,
   `review`, `section-results`, `system.*`). Ключи вида `layouts["content.intro"]` из контракта
   убираются. Это снимает К-3 и оживляет К-4.
4. **Ввести один резолвер макета**, общий для рантайма, веб-хоста и preview/smoke, по правилу из
   пункта 3. Это снимает К-6.
5. **Блокирующими остаются только целостность пакета и безопасность**: отсутствующий или битый
   `manifest.json`, неподдерживаемый `templateApiVersion`, внешние URL и CDN, превышение лимита
   размера, невалидный DSL. Отсутствие макета или слота — предупреждение плюс fallback. Это
   снимает К-5.

## 7. План работ

Этап 1 — спецификации (по согласованному правилу раздела 6):

- `prd-3/external-templates.md` — отменить NFR-06; переформулировать NFR-05; §4.1 (отсутствующие
  макеты и обязательные слоты вопросов уходят из блокирующих в предупреждения); §4.2; FAQ `:496`.
- `spec-template-platform.md` — §189-190 и §1954 (пакет включает резервные макеты стандартного);

- `prd-1/templates-content-pages.md` — §4.3.2 и `:236-238`: набор kind расширяется до всех

Этап 2 — код. **Выполнен 2026-07-17.** Деления слотов на обязательные и опциональные не
потребовалось: по правилу 6.5 не блокирует НИ ОДИН, поэтому `ScreenSpec.requiredSlots` стал

- `shared/template/preview-context.ts` — `expectedSlots`; резолвер по `layoutFile` (правило

- `shared/template/smoke-runner.ts` — предупреждение вместо ошибки на слоте И на отсутствующем
  макете; новый вход `fallbackLayouts` рендерит такой экран из стандартного шаблона.
- `server/services/template-validation.ts` — `REQUIRED_FIELD_MISSING` для макетов,
  `SHELL_CONTRACT`, `QUESTION_CONTRACT` переведены в предупреждения.
- `server/services/template-package.ts`, `server/routes/admin-templates.ts` — карта макетов

- `server/scorm/index.ts` — `computeFallbackLayoutKeys` + карта `FALLBACK_KIND_LAYOUT`

- `server/scorm/template/app/` — `templateLoader`, `mainRender` (`isFallbackLayout`,

- `server/routes/tests.ts`, `server/routes/attempts.ts` — виды `review`/`section-results` плюс

- `server/services/template-dir.ts` — fail-safe вместо fail-open (OQ-05).

Проверено: `npm test` (4640 зелёных; 9 падений в аналитике ПРЕДШЕСТВУЮТ правкам и
воспроизводятся на чистом дереве), `tsc`, `lint:md`, приёмка на плеере :5050 —
`template-default.zip` играет без ошибок консоли; собранный из `certification2` пакет
поднимает `fallbackLayoutKeys = [start, results, review, section-results]`, рендерит старт из

Не сделано: `router`/`summary` намеренно вне набора (см. `FALLBACK_KIND_LAYOUT`); подмена CSS в

стандартный для fallback-экрана; `fallbackLayouts` в smoke-набор админского UI не прокинут
(вход в раннере есть, вызывающий код его не передаёт).

Этап 4 — паритет превью и дизайна шаблона. **Выполнен 2026-07-17.** Повод: превью
`certification` не имело ничего общего с реальным дизайном. Причин оказалось четыре, и все —
в платформе, а не в шаблоне:

- **Оболочка не монтировалась НИКОГДА.** Оба сборщика набора (`readTemplateBundle`,
  `smoke-bundle`) выбрасывали `shell` из карты макетов (`if (key === "shell") continue`), а все
  три превью читают `bundle.layouts.shell` — то есть всегда `undefined`. Для шаблона с фикс-сценой
  (`mountShell: true`, CSS привязан к `.tb-frame > .tb-stage > #app.tb-pad`) это означало рендер
  вне сцены. Исправлено: `shell` остаётся в карте (ни один экран по этому ключу не резолвится).
- **Галерея рендерилась пустой.** Её рантайм-конвейер (`renderGalleryPage`) даёт контекст
  `gallery.*` и слот `cardText`, а превью кормило её скелетом `page-content`, которого в макете
  нет. Добавлен `buildGalleryParts` — зеркало рантайма, с тем же условием отката к обычной
  странице при отсутствии выделенного макета.
- **Резолвер не знал про ключ варианта.** Рантайм ищет макет галереи как
  `layouts[contentTemplate.key]`; `resolveLayoutKey` учитывал только `layoutFile`. Добавлено.
- **Коллизия идентификаторов.** `certification` показывает ДВА слайда галереи, привязанных к
  ОДНОМУ варианту `gallery.card`; идентичность бралась из ключа варианта → дубликат, коллизия
  ключей React и общий статус на два экрана. Теперь идентичность берётся от привязанной страницы
  (`pageId`), ключ варианта остаётся запасным.

Плюс интерфейс: рельс показывал сырые `review`, `section-results`, `content.gallery` латиницей —
в `TYPE_LABELS` не было записей. Добавлены «Обзор раздела», «Итоги раздела», «Галерея».

Проверено на стенде: все 15 экранов `certification` рендерятся в сцене со своими корнями
(`.cover`, `.section-intro-page`, `.gallery`, `.layout-question-wrap`, `.results-page`), 15 из 15
зелёные; `default` (без `mountShell`) не затронут, 12 из 12. Латиницы в рельсе не осталось.

Гоча миграции: смена идентификаторов экранов делает СОХРАНЁННЫЕ отчёты проверки устаревшими —
точки статуса серые до нажатия «Перепроверить». Гейт активации (`report.ok`) при этом работает.

Этап 5 — рантайм читает `layoutFile` + шаблон `my-template`. **Выполнен 2026-07-17.**
Проверка `my-template` (экспорт из визуального конструктора, модель «один макет на страницу»)
вскрыла, что на Этапе 2 закрыли только ПРЕВЬЮ-половину правила 6.3: рантайм `layoutFile` не читал.

- **Все контентные страницы рендерились одним макетом.** `renderContentPage` резолвил экран через
  единственный `layouts["content"]`, а у `my-template` `content.html` — не обёртка, а свёрстанная
  обложка с зашитым текстом. В SCORM все info/summary/router показали бы один экран. Исправлено:
  загрузчик (`templateLoader.js`) подтягивает макеты по `contentTemplates[].layoutFile` под их
  путём как ключом, а `renderContentPage` предпочитает `layouts[contentTemplate.layoutFile]`,
  откатываясь к `content`. Подтверждено на плеере: страницы резолвят РАЗНЫЕ макеты.
- **Свои start/results не доедут + нет `mountShell`** — те же два дефекта, что у `certification2`
  (оболочка `.tb-player` несёт сцену 1280×720 и прогресс-бар, а `template.js` двигает
  `#tb-progress-fill`, живущий только в ней). Добавлены варианты `start`/`results` + `mountShell`.
  Результат — `templates/my-template-1.0.1.zip` (исходный на диске в `uploads/` не трогали).

Заодно исправлена эвристика вводной раздела из Этапа 2: она опиралась на `layoutFile` варианта,
а рантайм (`renderSectionIntro`) читает ФИКСИРОВАННЫЙ ключ `layouts["section-intro"]`. У
builder-шаблона вида `intro` привязан к обычной странице без такого ключа — по прежней эвристике

## 8. Открытые вопросы

- **OQ-01. Решён 2026-07-17: все системные экраны.** Под fallback попадают `start`, `results`,
  `questions`, `router`, `summary`, `intro`, `review`, `section-results` и `system.*`. Набор PRD-1
  (`questions`/`router`/`summary`/`intro`) буквально **не включает** `start` и `results`, для
  которых fallback уже реализован (`scorm/index.ts:91`), поэтому буквальное следование PRD-1
  потребовало бы откатить работающее поведение. Решение снимает К-2 (три расходящихся набора) и
  требует правки PRD-1:236-238. Следствие: `system.blocked`, который сегодня не откатывается
  никогда (`tests.ts:352`), под правило подпадает.
- **OQ-02. Рекомендация, решается на этапе кода.** Экран-fallback рендерится разметкой
  стандартного шаблона, поэтому и компонентный CSS (`base.css` + `theme.css`) должен браться из
  стандартного — как уже делает SCORM (`mainRender.js:26-35`). Токены брендинга (`cssVars`,
  логотип) остаются от активного шаблона (`tests.ts:373-375`): это не компонентный слой, а
  фирменные цвета и шрифт. Веб-хосту и preview/smoke нужна та же подмена — сейчас её нет.
- **OQ-03. Закрыт решением по К-1.** NFR-06 отменяется: резервное поведение — fallback на
  стандартный шаблон, а не экран ошибки Core. Остаточный край: когда экрана нет и в стандартном
  шаблоне, `bindSystemVariant` возвращает `null` (`variant-binding.ts:88`) и вызывающий код
  трактует это как жёсткую ошибку конфигурации. Схема манифеста стандартного шаблона
  (`defaultTemplateManifestSchema`) обязана этот край исключать, так что отдельного экрана
  ошибки не требуется.
- **OQ-04. Закрыт решением по К-1.** PRD-1 признан источником истины, а PRD-1:236-238 исключает
  `kind: info` из автоматического fallback осознанно и с обоснованием: несовместимости
  пользовательских страниц автор разрешает через диалог маппинга, сохранение без разрешения
  невозможно. Исключение сохраняется.
- **OQ-05. Дефект, чинится на этапе кода.** `templateOwnsKind` (`template-dir.ts:105-108`)
  возвращает `true` при ошибке БД, то есть при недоступной БД учебный экран отрисуется из
  шаблона, который нужного вида варианта не объявляет. Это отказ в сторону сломанного экрана,
  а не в сторону работающего; целевое поведение — fail-safe на стандартный шаблон.
