**Статус:** актуально (описывает текущую реализацию редактора теста)

прохождения PRD-19 (`allowReturnToUnanswered`, `allowAnswerChange`, `showSectionResults`),
режим «Варианты теста» PRD-17 (`test_sections.form_set_json`), опциональная сложность
вопроса PRD-16 (`questions.difficulty` nullable), код темы PRD-2 (`topics.code`) и
актуализирован перечень системных узлов `content_pages.kind` (`intro` / `review` /
`section-results`).

Точные контракты модели редактора (enum, JSON-shapes, API, маппинг legacy-полей) —

## 1. Принцип группировки

Единый редактор теста должен использовать структуру вкладок, уже закреплённую в wireframes:

```text
Состав | Настройки | Оформление | Структура
```

Редактор открывается из слоя действий теста, например через двойной клик по карточке или пункт
`Редактировать` в меню действий. Карточка теста не должна становиться местом для всех расширенных
настроек.

Редактор реализуется как **wide Drawer**, а не как узкая боковая панель. Рекомендуемая ширина для
desktop: `min(1120px, calc(100vw - 48px))`; минимально допустимая ширина для двухпанельного режима:
`960px`. Ниже `960px` редактор переходит в одноколоночный режим.

Во вкладке **"Настройки"** используется второй уровень структуры:

```text
Настройки
├─ Side nav секций
│  ├─ Основное
│  ├─ Режим и сценарий
│  ├─ Правила прохождения
│  ├─ Ограничения
│  ├─ Обратная связь
│  ├─ Интеграция
│  └─ Адаптивность
└─ Рабочая область выбранной секции
```

Для `>= 960px` используется двухпанельная верстка: side nav 220-260px и рабочая область формы.
Для `< 960px` side nav заменяется селектором секции сверху, а форма становится одноколоночной.
Header Drawer и footer с действиями сохранения должны оставаться стабильными.

Сохранение выполняется одной кнопкой **"Сохранить"** для всего редактора. Изменения копятся в
draft-модели редактора и сохраняются атомарно, без посекционного сохранения. Основные вкладки
показывают агрегированное состояние, а секции внутри вкладок показывают локальные индикаторы:
`изменено`, `warning`, `error`. Кнопка сохранения активна, если есть изменения и нет блокирующих
ошибок. При успешном сохранении Drawer остаётся открытым, список тестов и данные редактора
обновляются, индикаторы изменений сбрасываются.

При попытке закрыть Drawer с несохранёнными изменениями показывается confirmation dialog с
действиями **"Сохранить"**, **"Выйти без сохранения"**, **"Отмена"**. Если в draft-модели есть
блокирующие ошибки, кнопка **"Сохранить"** в этом dialog остаётся видимой, но становится disabled;
рядом показывается краткая причина и ссылка/действие перехода к первой ошибочной секции.
Постоянной кнопки **"Сбросить всё"** в footer нет, чтобы не размещать разрушительное действие рядом
с сохранением. Отмена всех несохранённых изменений выполняется через закрытие Drawer и действие
**"Выйти без сохранения"** в confirmation dialog.

Валидация в редакторе используется комбинированная. Поля проверяются локально после `blur` или
изменения значимого значения, а секции сразу получают статусы `warning` или `error`. Навигация между
вкладками и секциями не блокируется. Сохранение блокируется только при `error`; `warning` показывает
риск или неполноту настройки, но не запрещает сохранить draft.

Ошибки и предупреждения показываются на двух уровнях. Рядом с конкретным полем отображается точное
сообщение. Вверху рабочей области секции отображается компактная сводка, например
`2 ошибки, 1 предупреждение`, со ссылками-якорями на проблемные поля. Агрегированные статусы вкладок
и секций строятся из этих же результатов валидации.

Обязательного preview-step перед сохранением нет. В footer редактора показывается компактная строка
состояния изменений, например `Изменено: Настройки, Структура`. При необходимости автор может
открыть опциональную сводку изменений через действие **"Показать изменения"**, но это не отдельный
шаг wizard и не обязательное условие сохранения.

В первом релизе **"Показать изменения"** открывает grouped summary по вкладкам и секциям, а не
полный field-level diff. Примеры пунктов: `Название изменено`, `Добавлена тема`, `Изменён flowMode`,
`Скрыты настройки adaptive`. Детальный diff по каждому полю не входит в первый релиз.
Действие **"Показать изменения"** отображается только если в редакторе есть несохранённые изменения.
Если изменений нет, ссылка не показывается, а кнопка **"Сохранить"** остаётся disabled.

Переключение критичных режимов, например `standard/adaptive` или `flowMode`, применяется к
draft-модели сразу. Несовместимые настройки не удаляются автоматически: они сохраняются в скрытой
части draft и помечаются inline warning. Если автор возвращается к прежнему режиму, совместимые
настройки восстанавливаются.

Modal confirmation при каждом переключении режима не показывается, потому что само переключение не
удаляет данные. Предупреждение отображается inline рядом с переключателем и через индикаторы
изменённых/предупреждающих секций. Отдельное подтверждение требуется только для действий, которые
реально удаляют или необратимо сбрасывают данные.

Несовместимые с текущим режимом настройки скрываются и не визуализируются как поля текущего режима.
В соответствующей секции отображается только компактный warning-блок: `Есть настройки, не применимые
к текущему режиму`. Блок можно раскрыть и увидеть список скрытых групп/настроек, а также режим или
сценарий, при котором они снова станут доступными.
Отдельного действия ручной очистки скрытых несовместимых настроек нет. Если автор возвращается к
режиму, где эти настройки применимы, они снова отображаются.

В API payload отправляются только данные, применимые к текущему режиму, плюс системные метаданные
режима. Скрытые несовместимые настройки могут существовать во frontend draft до сохранения, но не
попадают в активную runtime-конфигурацию теста, экспорт или SCORM.

Скрытые несовместимые настройки живут только в текущей открытой draft-сессии редактора. После
успешного сохранения фиксируется применимая конфигурация текущего режима. При повторном открытии
редактора загружается только сохранённая конфигурация, без восстановления скрытых настроек прежних
режимов.

В первом релизе draft не автосохраняется в `localStorage` или `sessionStorage`. Защита от потери
изменений обеспечивается guard при закрытии Drawer или уходе со страницы. Автосохранение draft может
быть вынесено в отдельное будущее требование, если появится подтверждённая потребность.

Для первого релиза используется optimistic flow с проверкой версии при сохранении. Редактор хранит
версию теста, с которой был открыт draft, и перед сохранением проверяет, не изменилась ли серверная
версия. При конфликте UI не перезаписывает данные молча, а показывает conflict dialog с действиями
**"Обновить данные"** и **"Сохранить поверх"**. Рекомендуемое действие по умолчанию —
**"Обновить данные"**.

Действия над тестом остаются вне редактора. Карточка теста показывает только компактный слой
частых действий, а остальные команды раскрываются через меню `...`.

Видимые действия на карточке:

| Действие | Назначение |
| --- | --- |
| Меню `...` | Открывает полный список команд над тестом |
| Назначение | Управляет доступом пользователей/групп к тесту |
| Экспорт SCORM | Генерирует SCORM-пакет из текущей версии теста |
| Аналитика | Открывает отчётность по попыткам и результатам |

Дополнительный вход в редактирование:

| Действие | Назначение |
| --- | --- |
| Двойной клик по карточке | Открывает Drawer редактора |
| `Редактировать` в меню `...` | Явная команда открытия Drawer редактора |

Меню `...`:

| Команда | Назначение |
| --- | --- |
| Редактировать | Открыть Drawer редактора |
| Опубликовать | Перевести тест из `Черновик` в `Опубликован` |
| Снять с публикации | Перевести тест из `Опубликован` в `Черновик` |
| В архив | Перевести тест из `Черновик` или `Опубликован` в `В архиве` |
| Восстановить из архива | Перевести тест из `В архиве` в `Черновик` |
| Переместить в папку | Изменить организацию теста в списке |
| Удалить | Удалить тест; разрушающее действие, не должно быть первичным на карточке и требует подтверждения с вводом названия теста |

Команды изменения состояния показываются контекстно, только если переход допустим для текущего
статуса теста.

Удаление теста выполняется только через отдельный confirmation dialog. Для подтверждения автор
должен ввести точное название теста; кнопка удаления активируется только при полном совпадении.

## 2. Вкладка "Состав"

Назначение вкладки: определить состав теста: из каких тем он собирается и сколько вопросов
выбирается из каждой темы.

В wireframes вкладка "Структура" показывает пустое состояние: сначала нужно добавить темы во
вкладке состава. Поэтому выбор тем и вопросная выборка относятся именно сюда.

| Параметр | Текущая модель | Описание смысла |
| --- | --- | --- |
| Выбранные темы | `test_sections.topic_id` | Набор тем, из которых тест берёт вопросы |
| Количество вопросов из темы | `test_sections.draw_count` | Сколько вопросов выбрать из каждой темы при генерации варианта |
| Режим «Варианты теста» | `test_sections.form_set_json` (`FormSet`) | Опциональный набор предзаданных форм секции (PRD-17). При наличии секция переходит в режим вариантов: одна форма выбирается в начале темы и выдаётся целиком в случайном порядке; контролы обычной выдачи (`draw_count` / `draw_all` / `draw_blueprint_json`) не применяются |
| Обязательность темы | целевая модель: `test_sections.required`; текущая модель: отсутствует | Определяет, является ли тема обязательной для политик итогового решения и router-flow |
| Обратная связь темы | целевая модель: `test_sections.feedback_json`; текущая модель: отсутствует | Содержание обратной связи по теме: текст, ссылки и материалы, которые могут быть показаны на страницах результата/feedback |
| Материалы обратной связи темы | целевая модель: `feedback_assets` с привязкой к теме | PDF-документы и другие разрешённые материалы, доступные для скачивания из SCORM |
| Доступное число вопросов | вычисляется из topic/question count | Ограничивает максимальный `draw_count` |

Дополнительные UI-состояния:

| Состояние | Описание |
| --- | --- |
| Нет тем | Нельзя перейти к структуре content pages, потому что страницы привязаны к темам |
| Тема без вопросов | Тему нельзя выбрать или нужно показать warning |
| Много тем | Требуются поиск, сканируемый список и стабильное отображение выбранных тем |

Правила прохождения по темам не редактируются в "Составе". Они отображаются и сохраняются во
вкладке "Настройки" вместе с общим правилом прохождения теста. Признак обязательности темы
`test_sections.required` также относится к правилам принятия итогового решения: в "Составе" его
можно показывать как badge, но редактировать лучше в "Настройки" рядом с правилами по темам.

Обратная связь темы относится к содержанию выбранной темы в составе теста. В "Составе" можно
редактировать или открывать настройки feedback для темы, а во вкладке "Структура" определяется
только место, где эта обратная связь будет показана обучающемуся.

Порядок тем также не редактируется в "Составе". Он относится к вкладке "Структура", потому что
определяет сценарную последовательность прохождения и положение страниц относительно тем.

Режим «Варианты теста» (PRD-17) настраивается для конкретной темы состава через редактор
вариантов. Значение `test_sections.form_set_json` имеет форму `FormSet`:

```ts
type Form = { id: string; label: string; questionIds: string[] };
type FormSet = { forms: Form[] }; // не менее двух вариантов
```

Каждая форма (`Form`) — это авторски отобранный подмножество-вариант банка вопросов темы:
`id` — стабильный ключ (по нему сопоставляется история ротации, а не по позиции в списке),
`label` — авто-нумеруемое имя «Вариант N», `questionIds` — состав варианта. Набор должен
содержать не менее двух вариантов. При включённом режиме одна форма выбирается в начале темы
и выдаётся целиком в случайном порядке.

Ротация «другой вариант на повторной попытке» — поведение по умолчанию и работает только на
веб-хосте (история попыток хранится на сервере). В SCORM-пакете нет cross-attempt-стора
(`adl.data` недоступен), поэтому механика деградирует до случайного выбора варианта на каждую
попытку без ротации (документированная деградация, NFR-17).

Опциональный код темы `topics.code` (PRD-2, миграция 032) — авторский короткий слаг темы. Когда
он задан, формулы показателей результата (PRD-2) адресуют тему как `topicById("<код>")` вместо
непрозрачного UUID; при отсутствии (`NULL`) используется UUID. Уникальность на уровне БД не
навязывается — ссылки на тему разрешаются в пределах теста (редактор предупреждает о коллизиях
кодов внутри теста). Свойство самой темы, а не строки состава; здесь упомянуто как контекст для
показателей (см. секцию «Показатели» конструктора результатов).

## 3. Вкладка "Настройки"

Назначение вкладки: определить общие свойства теста и правила прохождения.

Эта вкладка объединяет базовые параметры, режим прохождения, ограничения попытки, pass rules,
адаптивные настройки и интеграционные настройки. Это не отдельные top-level вкладки, а секции
внутри "Настроек".

### 3.1 Основное

| Параметр | Текущая модель | Описание смысла |
| --- | --- | --- |
| Название | `tests.title` | Основное имя теста в авторском интерфейсе и для обучающегося |
| Описание | `tests.description` | Краткое пояснение назначения теста |
| Статус теста | целевая модель: `tests.status`; текущая legacy-модель: `tests.published` | Жизненный цикл теста: `Черновик`, `Опубликован`, `В архиве` |

`tests.published` как boolean недостаточен для UX и доменной модели. Это legacy-поле, заменённое
enum-статусом `tests.status`. Маппинг: `published=false` → `status='draft'`,
`published=true` → `status='published'`. Команды смены статуса (Опубликовать / В архив /
Восстановить) остаются вне редактора — на карточке теста и в меню действий.

Обратная совместимость: колонки `tests.published` и `tests.start_page_content` намеренно
**не удалены** из БД (отдельный релиз после стабилизации). Storage пишет
`published = (status === 'published')` для legacy-клиентов; `mapLegacyTest()` остаётся на
read-path. Новый код читает только `status` и content-pages.

Целевые состояния:

| Состояние | Смысл |
| --- | --- |
| Черновик | Тест редактируется и не доступен для прохождения как опубликованный материал |
| Опубликован | Тест доступен для прохождения/назначения согласно правилам доступа системы |
| В архиве | Тест выведен из активного использования; недоступен для назначения и скрыт из общего списка/поиска |

Команды изменения состояния:

| Команда | Переход |
| --- | --- |
| Опубликовать | `Черновик -> Опубликован` |
| Снять с публикации | `Опубликован -> Черновик` |
| В архив | `Черновик -> В архиве` или `Опубликован -> В архиве` |
| Восстановить из архива | `В архиве -> Черновик` |

Эти команды должны отображаться как действия изменения состояния, а не как самостоятельные
состояния. Перед публикацией желательно выполнять проверку готовности теста: состав, правила,
структура и оформление.

Архивные тесты:

- не показываются в общем списке тестов и общем поиске;
- не доступны для новых назначений;
- доступны только в отдельном разделе **"Архив"**;
- могут быть возвращены в активную работу командой **"Восстановить из архива"**, после которой
  переходят в состояние `Черновик`.

### 3.2 Режим теста

| Параметр | Текущая модель | Описание смысла |
| --- | --- | --- |
| Режим | `tests.mode`: `standard` или `adaptive` | Определяет механику прохождения и набор доступных настроек |

Требование к UX: переключение `standard/adaptive` не должно молча уничтожать настройки другого
режима. Пользователь должен видеть последствия переключения.

### 3.3 Сценарий прохождения

Этот параметр определяет flow теста: как обучающийся проходит вопросы и видит тематические блоки.
Он отличается от `tests.mode`: `standard/adaptive` определяет механику подбора вопросов, а
сценарий прохождения определяет структуру предъявления.

| Параметр | Текущая модель | Описание смысла |
| --- | --- | --- |
| Сценарий прохождения | целевая логическая модель: `flowMode`; текущая модель: отсутствует | Определяет, идет ли тест единым блоком или по тематическим блокам, и влияет на вид вкладки "Структура" |
| Политика завершения router-flow | целевая модель: `flowPolicy.router.completionPolicy` | Логическое условие, при котором становится доступен переход к итоговому результату в router-режиме |
| Условия разблокировки разделов router-flow | целевая модель: `flowPolicy.router.sectionUnlockRules` | Условия, при которых тематический блок становится доступен на странице-маршрутизаторе |

Рекомендуемые значения `flowMode`:

| Значение | UI-название | Смысл |
| --- | --- | --- |
| `linear_flat` | Последовательный | Вопросы из выбранных тем идут единым блоком (без группировки по темам); во вкладке «Структура» — зоны «До теста» и «После теста» для авторских страниц, между ними блок вопросов |
| `linear_by_topics` | По темам | Тест проходит последовательно по тематическим блокам; внутри каждой темы — свои зоны страниц до/после вопросов темы; порядок тем настраивается во вкладке «Структура» |
| `router_by_topics` | Через страницу-маршрутизатор | Обучающийся выбирает тематический раздел на router-странице, после прохождения возвращается на неё, видит статус/результат разделов и переходит к итоговому результату после выполнения условий завершения |

Рекомендация по модели хранения: для первого этапа достаточно enum-поля `flowMode`.
Если ожидаются более сложные сценарии, его можно хранить как `flowPolicy.mode`, оставив место для
будущих настроек порядка, ветвления и переходов.

Логические параметры router-flow (`completionPolicy` и `sectionUnlockRules`) **видны
только при `flowMode = router_by_topics`** — секция «Сценарий прохождения» во вкладке
«Настройки» условно разворачивает эти параметры. При других режимах они скрыты.

Во вкладке «Структура» эти параметры **не отображаются ни в каком виде** (включая
read-only индикаторы). Структура отвечает за «что внутри теста», логика выполнения
теста (включая разблокировку разделов и условия завершения) — собственность
вкладки «Настройки» (см. [test-editor-contracts.md §2.3b](./test-editor-contracts.md)).

Рекомендуемый MVP scope условий разблокировки разделов в router-flow:

| Вариант | Смысл |
| --- | --- |
| `always_available` | Раздел доступен сразу |
| `after_sections_completed` | Раздел доступен после завершения выбранных разделов |
| `after_sections_passed` | Раздел доступен после успешного прохождения выбранных разделов |

Для MVP условия лучше ограничить списком prerequisite-разделов и логикой `AND`: все выбранные
условия должны быть выполнены. Произвольные boolean-выражения, вложенные группы условий,
сравнение процентов и rule-builder вне охвата (требовали бы движка правил, снятого в BRD BR-03).

### 3.3b Навигация прохождения

Параметры PRD-19 определяют, как обучающийся перемещается внутри попытки: можно ли
пропускать и возвращаться к вопросам, менять уже данный ответ и показывать ли экран
промежуточных итогов раздела. Все три параметра хранятся прямо на строке теста и
редактируются в секции «Основное» вкладки «Настройки».

| Параметр | Текущая модель | Описание смысла |
| --- | --- | --- |
| Разрешить возврат к неотвеченным вопросам | `tests.allow_return_to_unanswered` (bool, default `true`) | Разрешает пропустить вопрос и вернуться к пропущенным в пределах попытки. Миграция 031 существующим тестам выставляет `false`, сохраняя их строго-линейную навигацию |
| Разрешить менять ответ | `tests.allow_answer_change` (bool, default `false`) | Разрешает изменить уже данный ответ до завершения раздела/теста. Доступно только при включённом возврате к неотвеченным; взаимоисключается с `show_correct_answers` |
| Показывать итоги раздела | `tests.show_section_results` (bool, default `true`) | Показывать экран промежуточных итогов раздела (опциональный системный узел). Не применяется к `linear_flat` (в нём нет разделов) — runtime игнорирует параметр |

Зависимости и ограничения:

- `allow_answer_change` зависит от `allow_return_to_unanswered = true` — без возврата
  изменение ответа невозможно; при выключении возврата параметр деактивируется;
- `allow_answer_change` взаимоисключается с `show_correct_answers` (нельзя одновременно
  показывать правильные ответы и разрешать переигрывать ответ); правило проверяется в
  слое редактора/сервиса, а не как DB CHECK;
- `show_section_results` управляет отображением системного узла `section-results`
  (итоги раздела) и связан с системным узлом `review` (обзор перед завершением, см. §5.1);
  для `linear_flat` узел итогов раздела не создаётся.

### 3.4 Правила прохождения

| Параметр | Текущая модель | Описание смысла |
| --- | --- | --- |
| Общее правило прохождения | `tests.overall_pass_rule_json` | Минимальный результат для прохождения теста целиком |
| Тип общего правила | `percent`, `absolute`, `none` | Процент, абсолютное число правильных ответов или отсутствие общего правила |
| Значение общего правила | `overallPassRuleJson.value` | Порог прохождения |
| Правила по темам | `test_sections.topic_pass_rule_json` | Дополнительные пороги прохождения по каждой выбранной теме |
| Обязательная тема | `test_sections.required` (NOT NULL, default `true`) | Признак, что тема участвует как обязательный gate в политиках, которые проверяют обязательные темы |
| Источник правила темы | целевая модель: `topicPassRule.source`; текущая модель: отсутствует | Определяет, использует тема общее правило теста или индивидуальное правило темы |
| Тип правила темы | `topicPassRuleJson.type` | Процент или абсолютное число правильных ответов по теме |
| Значение правила темы | `topicPassRuleJson.value` | Минимальный результат по теме |
| Политика итогового решения | `tests.pass_decision_policy` | Определяет, как общий проходной балл и правила по темам объединяются в итоговый статус теста `passed/failed` |

В текущем adaptive-режиме общее правило фактически выключается через `{ type: "none", value: 0 }`.
Целевое поведение должно быть явно описано в UI.

Требование к группировке: все правила прохождения должны редактироваться в одном месте. Нельзя
разносить общее правило теста и правила отдельных тем по разным вкладкам.

Признак `required` хранится в `test_sections.required` — это единственное поле БД.
Во frontend-модели (`TestEditorModel`) `required` хранится только в `sections[].required`
(source of truth). Объект `passRules.byTopic` не дублирует это поле: маппер
`editorModelToPayload()` проецирует значение из `sections[]` при построении payload
политик прохождения. Badge в "Составе" и gate в "Настройках" читают одно значение.

Правило прохождения темы должно иметь явный источник:

| `topicPassRule.source` | UI-название | Смысл |
| --- | --- | --- |
| `inherit_overall` | Как в тесте | Тема использует общий тип и значение правила прохождения теста |
| `custom` | Индивидуальное правило | Для темы задаётся собственный тип и значение правила прохождения |
| `none` | Не проверять тему отдельно | Тема не участвует как отдельный gate; допустимо только если выбранная `passDecisionPolicy` не требует прохождения этой темы |

Рекомендация по умолчанию для выбранных тем: `inherit_overall`. Это позволяет включить политики
по темам без ручного задания одинакового порога для каждой темы.

Если источник правила темы `inherit_overall`, поля типа и значения правила темы не редактируются и
вычисляются из общего правила теста. Если источник `custom`, тип и значение обязательны. Если
источник `none`, тема не имеет собственного критерия прохождения и не может использоваться в
политике, где эта тема должна быть пройдена.

Рекомендуемая логика итогового решения:

| `passDecisionPolicy` | UI-название | Итоговое решение |
| --- | --- | --- |
| `overall_only` | Только общий результат | Тест пройден, если выполнено общее правило прохождения. Результаты тем считаются и могут показываться, но не блокируют прохождение теста |
| `overall_and_required_topics` | Общий результат и обязательные темы | Тест пройден, если выполнено общее правило прохождения и все обязательные темы пройдены по индивидуальному или унаследованному правилу темы |
| `required_topics_only` | Только обязательные темы | Тест пройден, если все обязательные темы пройдены по индивидуальному или унаследованному правилу темы; общий балл показывается справочно |
| `all_topics_passed` | Все темы должны быть пройдены | Тест пройден, если каждая выбранная тема пройдена по индивидуальному или унаследованному правилу темы; общий балл показывается справочно или используется как дополнительный индикатор |

Рекомендация по умолчанию:

- если правила прохождения по темам не включены, использовать `overall_only`;
- если включено хотя бы одно правило прохождения по теме, использовать
  `overall_and_required_topics`;
- `required_topics_only` и `all_topics_passed` оставить как явные advanced-варианты, а не default.

Для политики `all_topics_passed` каждая выбранная тема должна иметь проверяемый критерий:
`topicPassRule.source = inherit_overall` или `custom`. Если общее правило имеет тип `none`, то
наследование невозможно: UI должен потребовать индивидуальное правило для каждой темы либо не
разрешить сохранить такую комбинацию.

Пример: если обучающийся прошёл Тему 1 на 100%, но не прошёл Тему 2 при включённой политике
`overall_and_required_topics`, тест в целом считается не пройденным, даже если общий процент выше
общего проходного порога. Если продуктово нужна компенсация сильным результатом в другой теме,
нужно выбрать `overall_only` и считать тематические результаты справочными.

Важно: `passDecisionPolicy` не заменяет `completionPolicy` router-flow. `completionPolicy`
определяет, когда можно перейти к итоговому результату, а `passDecisionPolicy` определяет, будет ли
итоговый результат статусом `passed` или `failed`.

### 3.5 Ограничения попытки

| Параметр | Текущая модель | Описание смысла |
| --- | --- | --- |
| Лимит времени | `tests.time_limit_minutes` | Максимальное время прохождения |
| Лимит времени темы | целевая модель: `test_sections.time_limit_minutes`; текущая модель: отсутствует | Опциональный лимит времени для прохождения конкретной темы/раздела |
| Источник лимита времени темы | целевая модель: `topicTimeLimit.source`; текущая модель: отсутствует | Тема использует общий лимит теста, индивидуальный лимит или не имеет отдельного лимита |
| Максимум попыток | `tests.max_attempts` | Ограничение числа попыток |
| Показывать правильные ответы | `tests.show_correct_answers` | Разрешает обучающемуся видеть правильные ответы после прохождения |

Рекомендуемые значения `topicTimeLimit.source`:

| Значение | UI-название | Смысл |
| --- | --- | --- |
| `inherit_test` | Как в тесте | Тема использует общий лимит времени теста |
| `custom` | Индивидуальный лимит | Для темы задаётся собственный лимит времени |
| `none` | Без отдельного лимита | Тема не ограничивается отдельным таймером; действует только общий runtime/attempt lifecycle, если он есть |

Если одновременно заданы лимит времени теста и индивидуальный лимит времени темы, работают оба
ограничения. В runtime нельзя показывать их как два равноправных непонятных таймера: они должны
быть подписаны по смыслу.

Рекомендуемая визуализация:

```text
Осталось в теме: 08:25     Всего в тесте: 42:10
```

На узких экранах:

```text
Тема: 08:25
Тест: 42:10
```

Правила UX:

- глобальный таймер теста показывается в runtime shell/header;
- таймер темы показывается только внутри прохождения темы/раздела;
- на router-странице показывается только таймер теста;
- визуальный приоритет получает ближайшее ограничение: если раньше истекает тема, выделяется
  таймер темы; если раньше истекает тест, выделяется таймер теста;
- если оба ограничения истекают одновременно или почти одновременно, приоритет у таймера теста;
- warning-состояние и критическое состояние должны иметь текстовую подпись, а не только цвет.

Правила поведения:

- истёк таймер темы -> завершается или блокируется текущая тема, дальше работает выбранный
  `flowMode`;
- истёк таймер теста -> завершается вся попытка;
- если истёк общий таймер теста, он имеет приоритет над локальным таймером темы.

### 3.8 Адаптивность

Показывается как секция внутри "Настроек" только при adaptive-режиме теста. Режим
`standard/adaptive` задаётся на уровне теста целиком; отдельная тема не может переключить тест в
adaptive-режим, но может иметь собственную adaptive-конфигурацию внутри adaptive-теста.

| Параметр | Текущая модель | Описание смысла |
| --- | --- | --- |
| Показывать уровень сложности | `tests.show_difficulty_level` | Управляет видимостью уровня сложности для обучающегося; параметр относится только к adaptive-режиму |
| Настройки adaptive на уровне теста | целевая модель: `tests.adaptive_settings_json`; текущая модель: частично отсутствует | Общие adaptive-параметры теста: стратегия выдачи, общие defaults, правила отображения уровней |
| Настройки темы | `adaptive_topic_settings.topic_id` | Связь adaptive-конфигурации с темой |
| Включение adaptive для темы | целевая модель: `adaptive_topic_settings.enabled` | Позволяет управлять adaptive-настройками конкретной темы внутри adaptive-теста |
| Обратная связь при провале темы | `adaptive_topic_settings.failure_feedback` | Текст для темы, если обучающийся не проходит адаптивный блок |
| Порядок уровня | `adaptive_levels.level_index` | Порядок adaptive-уровня внутри темы |
| Название уровня | `adaptive_levels.level_name` | Человекочитаемое имя уровня |
| Минимальная сложность | `adaptive_levels.min_difficulty` | Нижняя граница сложности вопросов уровня |
| Максимальная сложность | `adaptive_levels.max_difficulty` | Верхняя граница сложности вопросов уровня |
| Количество вопросов уровня | `adaptive_levels.questions_count` | Сколько вопросов выдавать на уровне |
| Порог прохождения уровня | `adaptive_levels.pass_threshold` | Минимальный результат на уровне |
| Тип порога уровня | `adaptive_levels.pass_threshold_type` | Процент или абсолютное число |
| Обратная связь уровня | `adaptive_levels.feedback` | Текст результата/рекомендации для конкретного уровня |
| Ссылки уровня | `adaptive_level_links.title`, `adaptive_level_links.url` | Рекомендованные материалы для уровня |
| Документы уровня | целевая модель: `feedback_assets` с `scope = adaptive_level` | PDF-документы, прикладываемые к обратной связи уровня |

Справочные данные, которые не являются параметрами теста:

| Данные | Смысл |
| --- | --- |
| Difficulty distribution | Помогает автору подобрать диапазоны сложности, но не сохраняется как настройка теста |

Требование к UX: параметр `tests.show_difficulty_level` показывается только если выбран режим
`adaptive`. В режиме `standard` он не должен отображаться как самостоятельная настройка.

Сложность вопроса `questions.difficulty` — свойство самого вопроса (не параметр теста), но
именно она задаёт диапазоны adaptive-уровней (`adaptive_levels.min_difficulty` /
`adaptive_levels.max_difficulty`). Начиная с PRD-16 (миграция 029) поле `questions.difficulty`
стало nullable: сложность опциональна, `NULL` означает «не задано». Дефолт `50` сохранён для
вставок, где значение не передано; явный `null` очищает сложность. Вопросы без заданной
сложности не попадают в диапазоны adaptive-уровней автоматически — автор должен учитывать это
при подборе диапазонов.

## 4. Вкладка "Оформление"

Назначение вкладки: выбрать SCORM-шаблон и параметры визуального оформления.

Эта вкладка соответствует [docs/wireframes/approved/prd7-design-tab.html](../wireframes/approved/prd7-design-tab.html).

| Параметр | Текущая модель | Описание смысла |
| --- | --- | --- |
| Выбранный шаблон | `tests.design_settings_json.templateId` | Какой SCORM-шаблон используется при экспорте и runtime |
| Параметры шаблона | `design_settings_json.params` | Значения параметров из `manifest.params` |

`templateVersion` и `templateApiVersion` не являются редактируемыми параметрами оформления. Это
read-only системные параметры выбранного шаблона для диагностики, совместимости и экспорта.

Типы параметров шаблона:

| Тип | Смысл |
| --- | --- |
| `color` | Цвет бренда, фона, акцента |
| `text` | Текстовое значение, например название компании |
| `number` | Числовая настройка макета или поведения |
| `boolean` | Включение/выключение опции |
| `select` | Выбор из списка |
| `multiselect` | Множественный выбор; значение хранится как array |
| `url` | Обычная ссылка |
| `image` | Изображение, например логотип |
| `font` | Шрифт |
| `asset` | Дополнительный файл шаблона |
| `file` | Загружаемый файл |
| `downloadLink` | Ссылка на скачивание файла, упакованного в SCORM |

Значения media-типов (`image` / `asset` / `file` / `downloadLink`) хранятся единым envelope
`MediaParamValue`: `{ url, name, mime?, size?, mediaId?, label? }`. Загрузка — через
`POST /api/media/upload` (multer disk storage); `mediaId` зарезервирован под медиатеку.
Валидация на frontend по полям манифеста `accept` (mime/расширения) и `maxSizeKb`.

"Группы" во вкладке "Оформление" — это UI-секции для организации параметров, а не отдельные
доменные параметры теста. Параметр привязывается к секции полем `manifest.params[].section`:

```ts
type ParamSection = "branding" | "layout" | "progress";
```

Default при отсутствии — `"branding"` (backward compat для старых манифестов). Sub-rail «Шаблон»
не содержит params — это карточка информации о шаблоне + действия.

| UI-секция | `param.section` | Примеры смысла |
| --- | --- | --- |
| Шаблон | — | Галерея шаблонов, выбранный шаблон, предпросмотр |
| Брендирование | `branding` | Цвета, логотип, название |
| Макет | `layout` | Сайдбар, позиционирование, плотность |
| Прогресс и шапка | `progress` | Режим прогресса, элементы header |

Предпросмотр шаблона и страниц рендерится из готового `preview.html` шаблона в iframe.
Маршруты: `GET /api/templates/:id/preview-page` (предпросмотр шаблона с применёнными
`design.params`) и `GET /api/tests/:id/content-pages/:pageId/preview-page` (предпросмотр
конкретной content-page). Общий helper встраивания — `server/scorm/preview-embed.ts`.
Ограничения: переопределяются только скалярные params (цвет/шрифт/boolean); object/array params
показываются с манифестными defaults.

## 5. Вкладка "Структура"

Назначение вкладки: визуализировать структуру прохождения и определить размещение контентных
блоков: страницы перед тестом, вокруг тематических блоков, на router-странице и после теста.

Эта вкладка соответствует согласованным эскизам по режиму прохождения:
[prd7-structure-linear-flat.html](../wireframes/approved/prd7-structure-linear-flat.html),
[prd7-structure-linear-by-topics.html](../wireframes/approved/prd7-structure-linear-by-topics.html),
[prd7-structure-router.html](../wireframes/approved/prd7-structure-router.html). Вкладка называется
именно "Структура", а не "Страницы". Внутри неё редактируются content pages.

Вид вкладки зависит от режима прохождения:

| Режим прохождения | Структура |
| --- | --- |
| `linear_by_topics` (по темам) | Показываются тематические блоки; страницы вставляются до/после каждой темы; порядок тем редактируется в «Структуре» |
| `linear_flat` (последовательный) | Тематические блоки не показываются как структура прохождения; показывается единый блок вопросов и зоны «До теста» / «После теста» |
| `router_by_topics` (через маршрутизатор) | Зоны «До теста» / «После теста» как в `linear_flat`, плюс системная page-row `kind: router` внутри теста и темы как ветки иерархии через tree-connectors. `completionPolicy` / `sectionUnlockRules` — в «Настройках → Сценарий», не в «Структуре» (см. §5.1) |

| Элемент структуры | Текущая модель | Описание смысла |
| --- | --- | --- |
| Текущий режим структуры | производное от `flowMode` | Read-only визуальный контекст вкладки; здесь не настраивается |
| Порядок тематических блоков | `test_sections.sort_order` (migration 007) | Порядок тем (DnD во вкладке «Структура»); `getTestSections` упорядочивает по `sortOrder`; применяется для `linear_by_topics` и порядка веток-тем в `router_by_topics` |
| Страница-маршрутизатор | `content_pages` запись с `kind: router`, единственная для теста при `flowMode = router_by_topics` | Системная page-row, привязывается тихой логикой §4.3.2 PRD-1; параметры (заголовок, инструкция, настройки меню) — в `page-row-expand` (inline); удаляется молча при смене режима |
| Общий блок вопросов | текущая модель строится из выбранных `test_sections` | Единый блок вопросов для `linear_flat`: вопросы всех выбранных тем идут одним потоком без группировки |
| Зона до теста | целевая модель content pages без topic binding или специальная позиция | Страницы, которые показываются до общего блока вопросов в `linear_flat` |
| Зона после теста | целевая модель content pages без topic binding или специальная позиция | Страницы, которые показываются после общего блока вопросов в `linear_flat` |
| Стартовый текст | `tests.start_page_content` | Legacy-поле стартовой страницы; относится к структуре прохождения и должно быть увязано с моделью start/content pages |
| Блок показа общей обратной связи | content page / result page placeholder | Место, где будет показано содержание `tests.feedback`; само содержание редактируется в "Настройках" |
| Тема страницы | `content_pages.topic_id` | К какой теме привязана страница |
| Позиция | `content_pages.position`: `before_topic` или `after_topic` | Где страница находится относительно блока вопросов темы |
| Режим страницы | `content_pages.mode`: `template`, `standard`, `html` | Как задаётся содержимое страницы |
| Тип варианта | `variant.kind` в манифесте шаблона: `start`, `results`, `questions`, `router`, `intro`, `info`, `review`, `section-results` (и legacy `summary`; см. PRD-1 §4.3, PRD-19) | Функциональная роль варианта; определяет, где допустим этот вариант и как срабатывает логика связывания |
| Шаблон страницы | `content_pages.template_key` | Page template из активного SCORM-шаблона |
| Порядок | `content_pages.sort_order` | Порядок страниц внутри темы и позиции |
| Значения placeholders | `content_pages.values_json.values` | Контент, который автор вводит в поля страницы |
| Стили placeholders | `content_pages.values_json.placeholderStyles` | Разрешённые локальные overrides, например `fontSize` |
| Автопереход | `content_pages.auto_advance` | Переходить дальше без ручного действия |
| Задержка автоперехода | UI: секунды; хранение: `content_pages.auto_advance_delay_ms` | Через сколько секунд выполнить автопереход; хранение в миллисекундах является технической деталью |

Режим структуры и порядок тем не являются самостоятельными параметрами формы. Режим структуры
производен от `flowMode` и может отображаться как read-only. Порядок тем задаётся самим порядком
расположения тематических блоков в структуре.

Если выбранный шаблон не содержит нужный template/system element для страницы или structural block,
runtime использует fallback этого элемента из шаблона `default`. Во вкладке "Структура" такой
элемент должен подсвечиваться warning-пиктограммой: элемент будет работать через fallback, но не
описан в выбранном шаблоне.

Типы placeholders:

| Тип | Смысл |
| --- | --- |
| `text` | Короткий текст |
| `textarea` | Многострочный текст |
| `richText` | Ограниченный форматированный текст |
| `html` | Санитизированный HTML |
| `number` | Число |
| `boolean` | Переключатель |
| `select` | Выбор из списка |
| `asset` | Ссылка или файл |
| `file` | Загружаемый файл |
| `url` | Обычная ссылка |
| `downloadLink` | Ссылка на скачивание файла из SCORM ZIP |
| `resultField` | Динамическое поле результата через renderer |

### 5.1 Визуализация router-режима

Для `flowMode = router_by_topics` вкладка «Структура» показывает иерархическую
композицию: зоны «До теста» / «После теста» как в `linear_flat`, плюс системная
page-row `kind: router` внутри теста и темы как ветки под router-row через
tree-connectors. Старая модель «сценарной карты» (`Router → Раздел → Возврат →
Итог` с угловыми соединителями) — устаревшая, не применяется.

```text
┌─ Зона «До теста» ────────────────────────────┐
│  page-row, kind: info × N                    │
│  + Добавить страницу                         │
└──────────────────────────────────────────────┘

┌─ Внутри теста ───────────────────────────────┐
│  page-row, kind: router (единственная)       │  ← корень иерархии
│    ├── topic-block «Тема 1»                  │  ← ветка
│    ├── topic-block «Тема 2»                  │
│    └── topic-block «Тема 3»                  │
└──────────────────────────────────────────────┘

┌─ Зона «После теста» ─────────────────────────┐
│  page-row, kind: info × M                    │
│  + Добавить страницу                         │
└──────────────────────────────────────────────┘
```

**Page-row `kind: router`:**

- единственная для теста, неудаляемая, без insert-row до/после;
- variant select виден всегда в самой строке (variant определяется тихой
  логикой §4.3.2 PRD-1);
- при N > 1 router-вариантах в шаблоне — хинт «Доступно N вариантов» возле
  бейджа; смена через `…` row-menu → «Сменить вариант»;
- при 0 router-вариантах — fallback на стандартный шаблон + warning
  «Используется маршрутизатор из стандартного шаблона»;
- параметры варианта (заголовок, инструкция, прочие schema-поля)
  редактируются inline в `page-row-expand` при раскрытии chevron'а (если
  schema варианта не пуста).

**Темы как ветки** — полноценные `.topic-block` из `linear_by_topics`: страницы
темы, пороги, inline-expand. DnD веток-тем под router-row меняет авторскую
организацию; runtime-порядок задаётся параметром
`flowSettings.router.sectionOrder` из «Настроек».

**Что НЕ показывается в Структуре:**

- `completionPolicy` и `sectionUnlockRules` — настройки сценария, живут во
  вкладке «Настройки → Сценарий», условно при `flowMode = router_by_topics`;
- состояния прогресса тем (`Не начат` / `В процессе` / `Завершён` / `Пройден` /
  `Не пройден` / `Заблокирован`) — это runtime-визуализация для обучающегося;
- финальный «Итоговый результат» как отдельный конечный блок — это runtime-
  концепция, в Drawer'е не отрисовывается; итоговая страница результата
  (`kind: results`) — единичный системный design-биндинг, а итоги раздела —
  системный узел `kind: section-results` (PRD-19), а не отдельная page-row в
  зоне «После теста».

### 5.2 Default-структуры и смена режима

Автор не должен создавать структуру с нуля. Для каждого `flowMode` система создаёт default-структуру:

| `flowMode` | Default-структура |
| --- | --- |
| `linear_flat` | «До теста» → блок вопросов (плоский поток из всех выбранных тем) → «После теста» |
| `linear_by_topics` | «До теста» → тематические блоки в порядке структуры → «После теста» |
| `router_by_topics` | «До теста» → page-row `kind: router` с темами как ветками → «После теста» |

Актуальный набор значений `content_pages.kind`: системные `start` (стартовая страница),
`results` (итоговый результат), `router` (страница-маршрутизатор), `questions` (блок
вопросов), `intro` (введение раздела, per-topic), а также узлы границы раздела PRD-19
`review` (обзор перед завершением) и `section-results` (итоги раздела). Авторский kind
`info` создаётся автором и не является системным. Узлы `review` и `section-results`
(миграции 034/035, PRD-19/1) — системные runtime-узлы: как `start`/`results`, это
единичные design-биндинги на уровне теста, они рендерятся собственной runtime-фазой и
исключены из потока content-page. Они заменили legacy per-topic системные страницы
`intro` (как «введение раздела») и `summary` («итоги раздела»): планировщик
content-pages больше не создаёт per-topic `intro`/`summary`, а миграция 034 удаляет уже
созданные и досоздаёт `review` (для всех тестов) и `section-results` (только для тестов
с разделами). Kind `summary` сохранён как допустимое значение только для обратной
совместимости со старыми записями/шаблонами и больше не управляется системой.

При смене режима структура пересобирается по default-структуре нового режима, но пользовательский
контент сохраняется по разным правилам в зависимости от типа варианта (см. PRD-1 §4.3):

- авторские страницы `kind: info` с совместимым именем варианта переносятся
  автоматически; если в новом режиме/шаблоне варианта с тем же именем нет —
  открывается диалог `s-mapping` (PRD-1 §4.2);
- системный узел `kind: intro` («введение раздела», per-topic) остаётся единичным на
  тему; при смене режима его вариант пересчитывается тихой логикой §4.3.2 PRD-1;
  системные узлы границы раздела `kind: review` (обзор) и `kind: section-results`
  (итоги раздела) — единичные на тест: `review` присутствует всегда, `section-results`
  создаётся только для секционных режимов (`linear_by_topics` / `router_by_topics`) и
  зависит от `tests.show_section_results` (см. §3.3b);
- системная страница `kind: router` появляется только при
  `flowMode = router_by_topics`. При смене режима обратно на любой `linear_*` —
  страница `kind: router` **удаляется системой молча** (без диалога `s-mapping`);
  при возврате к `router_by_topics` создаётся новая router-row с тихой
  привязкой default-варианта;
- страницы до/после темы (внутри `.topic-block`) скрываются при переходе из
  `linear_by_topics` / `router_by_topics` в `linear_flat` (там тематических
  подгрупп нет), но не удаляются — восстанавливаются при возврате.

Инвариант системных страниц: default-манифест обязан объявлять каждый системный kind
(`start` / `results` / `router` / `questions` / `intro`, а также узлы PRD-19 `review` и
`section-results`) — иначе тихая привязка соответствующего варианта не срабатывает.
`GET /api/tests/:id` идемпотентно вызывает `testSettingsService.reconcileExisting()`,
досоздавая отсутствующие системные страницы; для уже существующих `router_by_topics`-тестов
применена backfill-миграция 006, а узлы `review`/`section-results` доведены миграциями 034/035.

Особые состояния из wireframes:

| Состояние | Смысл |
| --- | --- |
| Нет тем | Для `linear_by_topics` нельзя создавать страницы внутри темы, пока во вкладке «Состав» не выбраны темы; для `linear_flat` без выбранных тем блок вопросов пуст; для `router_by_topics` под router-row показывается empty-state «В тесте нет тем» с CTA на «Состав» |
| `linear_flat` | Показываются зоны «До теста» / «После теста» и блок вопросов между ними, без тем как структурных блоков |
| `linear_by_topics` | Показываются темы как структурные блоки и зоны до/после каждой темы |
| `router_by_topics` | Показываются зоны «До теста» / «После теста» (как `linear_flat`) и системная router-row внутри теста с темами как ветками иерархии через tree-connectors (см. §5.1) |
| Page variant (`kind: info`) отсутствует после смены шаблона | Диалог `s-mapping` для авторских страниц (PRD-1 §4.2) |
| Системный вариант (`kind`: `start` / `results` / `router` / `questions` / `intro` / `review` / `section-results`) отсутствует в шаблоне | Fallback на вариант того же `kind` из стандартного шаблона + warning-индикация (PRD-1 §4.3.2) |
| Несколько вариантов одного системного `kind` в шаблоне | Хинт «Доступно N вариантов» возле бейджа; смена через `…` row-menu → «Сменить вариант» |
| Preview страницы | Предпросмотр текущей страницы с введёнными значениями (модал `s-page-preview`) |
| Runtime flow preview | Проверка последовательности страниц и вопросов |
| Read-only | Структура может быть доступна только для просмотра |
| Перетаскивание тем | Меняет порядок тематических блоков для `linear_by_topics`; для `router_by_topics` — порядок веток-тем под router-row (runtime-порядок задаётся `sectionOrder` из «Настроек») |

`tests.start_page_content` является deprecated legacy-полем. Целевое решение — миграция
в `content_pages` как запись типа `intro` без `topic_id` с позицией `before_all`.
SQL-миграция создаёт `content_pages`-запись для каждого теста с непустым `start_page_content`.
Новый редактор не читает и не пишет `start_page_content`; стартовая страница управляется
через тот же UI, что и остальные content pages во вкладке "Структура".

`tests.feedback` нужно считать legacy-представлением содержания общей обратной связи. Оно
редактируется в "Настройках"; во вкладке "Структура" задаётся только место показа этой обратной
связи на summary/result/content page.

## 6. Не параметры редактора

Эти элементы важны для работы с тестом, но не должны быть вкладками редактора параметров.

### 6.1 Экспорт SCORM

| Параметр действия | Где сейчас | Описание |
| --- | --- | --- |
| Разовый override telemetry при экспорте | export dialog, query `telemetry=true` | Legacy/технический override для экспорта; целевым источником должен быть параметр `tests.telemetry_enabled` в настройках теста |

Экспорт должен оставаться действием на карточке или в слое действий теста.

### 6.2 Назначение

| Параметр | Модель | Описание |
| --- | --- | --- |
| Пользователь | `test_assignments.user_id` | Индивидуальное назначение |
| Группа | `test_assignments.group_id` | Назначение группе |
| Дедлайн | `test_assignments.due_date` | Срок выполнения |
| Срок ссылки | `test_assignments.link_expires_at` | Срок жизни magic link |
| Токены доступа | `assignment_access_tokens` | Управление magic links |

Назначение остаётся отдельным действием, потому что это управление доступом, а не параметр
содержания или прохождения теста.

### 6.3 Аналитика

Аналитика открывает отчёты по попыткам и результатам. Она не меняет конфигурацию теста.

### 6.4 Организация списка

| Параметр | Модель | Описание |
| --- | --- | --- |
| Папка | `tests.folder_id` | Организация теста в списке |
| Сортировка, поиск, grid/list | local UI state | Предпочтения отображения списка |

Папка может редактироваться через меню действий или слой списка. В Drawer её стоит добавлять только
если продуктово решено считать папку частью карточки "Основное".

## 7. Итоговая структура

```text
Карточка теста:
  ... меню действий
  Назначение
  Экспорт SCORM
  Аналитика

Меню действий:
  Редактировать
  Опубликовать / Снять с публикации
  В архив / Восстановить из архива
  Переместить в папку
  Удалить

Дополнительный вход:
  Двойной клик по карточке -> Drawer редактора

Drawer редактора:
  Состав
    - темы
    - количество вопросов
    - режим «Варианты теста» (form_set_json)
    - feedback темы и материалы

  Настройки
    - основное (title, description, status: draft|published|archived)
    - режим теста
    - сценарий прохождения / flowMode
    - навигация прохождения (возврат к неотвеченным, изменение ответа, итоги раздела)
    - правила прохождения
    - правила по темам
    - ограничения попытки
    - обратная связь и материалы
    - интеграция
    - telemetry
    - адаптивность
      - показ уровня сложности

  Оформление
    - шаблон
    - параметры шаблона
    - read-only версия/API-версия шаблона
    - предпросмотр

  Структура
    - стартовая страница (content page типа intro, без topic_id — заменяет start_page_content)
    - read-only режим структуры: производный от flowMode
    - порядок тематических блоков как визуальное расположение
    - router-страница и карточки разделов для режима через маршрутизатор
    - read-only индикаторы статусов, результатов и условий
    - зоны До теста / После теста для `linear_flat`
    - стартовый legacy-контент
    - места показа обратной связи
    - content pages до/после темы
    - template/standard/html страницы
    - placeholders
    - порядок
    - autoAdvance
```

## 8. Системные параметры

Системные параметры не редактируются вручную в Drawer. Они могут отображаться как read-only
metadata, если это помогает диагностике, аудиту или поддержке.

| Поле | Модель | Смысл |
| --- | --- | --- |
| ID теста | `tests.id` | Технический идентификатор теста |
| Версия | `tests.version` | Read-only системная версия теста; увеличивается автоматически при изменениях, влияющих на прохождение или экспорт |
| Версия шаблона | `templateVersion` | Read-only версия выбранного шаблона для диагностики и совместимости |
| API-версия шаблона | `templateApiVersion` | Read-only совместимость выбранного шаблона с runtime API |
| Дата создания | `tests.created_at` | Когда тест был создан |
| Дата обновления | `tests.updated_at` | Когда тест был последний раз изменён |
