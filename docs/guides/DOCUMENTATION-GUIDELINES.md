# Правила создания и поддержки документации

Дата создания: 2025-12-14
Последняя актуализация: 2026-05-26
Применимость: TypeScript/JavaScript библиотеки, backend и frontend приложения, full-stack проекты

## Принципы документирования

### 1. Документация следует за кодом

**Правило**: Документация описывает текущее состояние кода, а не планы или историю разработки.

**Что документируем**:

- Текущую функциональность
- Актуальный API
- Реальные примеры использования
- Известные ограничения

**Что НЕ документируем**:

- Историю изменений (для этого есть CHANGELOG.md и git)
- Планы разработки (если они не влияют на текущее использование)
- Процесс реализации функций
- Анализ "до/после" оптимизаций

### 2. Один источник правды

**Правило**: Каждый факт документируется в одном месте.

**Плохо**:

- README описывает API
- Отдельный файл API.md дублирует информацию
- JSDoc повторяет то же самое
- Примеры показывают устаревший синтаксис

**Хорошо**:

- README - обзор и quick start
- JSDoc - детальная документация API
- TypeDoc - генерируется из JSDoc автоматически
- Examples - рабочие примеры, синхронизированные с API

### 3. Актуальность важнее полноты

**Правило**: Лучше минимальная, но актуальная документация, чем обширная устаревшая.

**Требования**:

- Удаляем документы сразу после того, как они стали неактуальными
- Обновляем документацию в том же коммите, что меняем код
- Не создаем документы "на будущее"

### 4. Актуализация важнее удаления

**Правило**: При обнаружении устаревшего документа сначала рассматриваем актуализацию,
удаление — только если документ нечего актуализировать.

**Удаляем**:

- Завершённые планы (результат уже в коде/merged PR)
- Снимки-анализы (отчёт от конкретной даты, заменённый новым)
- Дубликаты (содержимое уже есть в другом файле)
- Артефакты мёртвых процессов/платформ

**Актуализируем**:

- Документы, описывающие реально существующий аспект проекта (ROADMAP, PRD, спецификации)
- Гайды, ссылки и форматы в которых устарели
- Чек-листы открытых задач

## Применимость гайда

Гайд изначально создавался под TypeScript/JavaScript библиотеки. Для других типов
проектов часть правил применяется в адаптированном виде. Ниже — карта применимости.

### Типы проектов

- **Библиотека (npm-пакет)** — TypeDoc, `examples/`, полный набор полей `package.json`,
  публичный README с API Reference.
- **Backend-приложение** — JSDoc на routes/services/utils, опционально OpenAPI/Swagger,
  README ориентирован на разработчиков (запуск, env, архитектура). TypeDoc и `examples/`
  не нужны.
- **Frontend-приложение** — Storybook вместо TypeDoc (если используется), JSDoc на
  хуках/компонентах со сложной логикой, README с описанием UX-сценариев и команд запуска.
- **Full-stack-приложение** — применяются правила backend и frontend; единый README в
  корне; раздельная документация по слоям в `docs/`.

### Что применяется везде

- Принципы документирования (документация следует за кодом, один источник правды,
  актуальность важнее полноты, актуализация важнее удаления)
- Запрет emoji в `.md`, обязательность markdownlint
- Правила именования файлов
- Жизненный цикл документов (создание/обновление/удаление)
- Запрет дубликатов, документов истории разработки, мёртвых TODO/ROADMAP

### Что специфично

Артефакт vs тип проекта:

- **README с API Reference и Examples**: библиотека — обязательно; backend/frontend —
  сокращённо; full-stack — по слоям.
- **TypeDoc**: только библиотека.
- **Storybook**: опционально для frontend и full-stack.
- **`examples/`**: только библиотека.
- **`package.json` keywords/homepage/bugs**: библиотека — обязательно; остальные —
  опционально.
- **OpenAPI/Swagger**: опционально для backend и full-stack.
- **JSDoc на всех публичных API**: библиотека — обязательно; backend —
  обязательно для routes/services; frontend — для хуков/компонентов с нетривиальной
  логикой; full-stack — суммарно.
- **CHANGELOG.md**: обязательно везде, где есть релизы или версионирование.
- **ROADMAP.md**: допустим везде при выполнении условий (см. ниже).

## Структура документации

### Обязательные файлы

#### README.md (корень проекта)

**Назначение**: Точка входа для новых пользователей

**Обязательные секции**:

1. Краткое описание (1-2 предложения)
2. Ключевые возможности (список)
3. Installation
4. Quick Start (минимальный рабочий пример)
5. API Reference (краткий обзор с ссылками на детали)
6. Examples (ссылки на примеры)
7. License

**Опциональные секции**:

- Migration Guide (только если есть breaking changes)
- Performance (только ключевые метрики)
- TypeScript Support (если есть специфика)
- Testing (команда запуска, общая статистика)

**Ограничения**:

- Максимум 500 строк
- Если больше - выносим детали в отдельные файлы

#### CHANGELOG.md (корень проекта)

**Назначение**: История релизов

**Формат**: [Keep a Changelog](https://keepachangelog.com/)

**Правила**:

- Генерируется автоматически (например, через standard-version)
- Группировка: Added, Changed, Deprecated, Removed, Fixed, Security
- Версии в обратном хронологическом порядке

#### package.json

**Поля документации**:

```json
{
  "name": "@scope/package-name",
  "version": "1.0.0",
  "description": "Краткое описание (одна строка)",
  "keywords": ["ключевые", "слова"],
  "homepage": "https://github.com/user/repo#readme",
  "repository": {
    "type": "git",
    "url": "https://github.com/user/repo.git"
  },
  "bugs": {
    "url": "https://github.com/user/repo/issues"
  }
}
```

### Опциональные файлы в docs/

#### Когда создавать документы в docs/

**Создаем отдельный файл если**:

1. Информация объемная (>200 строк)
2. Тема специфическая (не нужна всем пользователям)
3. Информация редко меняется

**Примеры оправданных файлов**:

- `LOGGING_GUIDELINES.md` - правила для разработчиков
- `CONTRIBUTING.md` - процесс контрибуции
- `ARCHITECTURE.md` - архитектурные решения
- `MIGRATION_v1_to_v2.md` - гайд по миграции между мажорными версиями

**НЕ создаем файлы**:

- `PERFORMANCE-ANALYSIS.md` — если результаты уже в коде, удаляем такие файлы
- `IMPLEMENTATION-PLAN.md` — если план выполнен, удаляем; если активен — используем
  привязанные к PRD TODO (см. ниже)
- `TODO.md` (общий, без привязки к PRD) — используем Issues
- `ROADMAP.md` — допустим при выполнении условий (см. ниже)

#### ROADMAP.md: когда допустим

`ROADMAP.md` в `docs/` допустим, если выполняются ВСЕ условия:

1. Описывает не выполненные планы (выполненные фазы удаляются или помечены completed
   и со временем убираются).
2. Регулярно актуализируется (минимум раз в месяц при активной разработке).
3. Содержит ссылки на GitHub Issues/Milestones для каждой фазы или этапа.
4. В шапке указана дата последней актуализации.

ROADMAP неприемлем и подлежит удалению, если:

- Не обновлялся 3+ месяца.
- Содержит только описание уже выполненных фаз.
- Дублирует GitHub Projects/Milestones без добавления контекста.
- Содержит детали реализации (это уровень PRD/спецификаций, не ROADMAP).

#### TODO-файлы PRD

TODO-файлы, привязанные к конкретному PRD (`prd-N-implementation-todo.md`,
`prd-N-execution-strategy.md`, `prd-N-revision-todo.md`) допустимы как промежуточный
этап перед GitHub Issues.

**Правила**:

1. Файл живёт рядом с PRD в `docs/specs/` (или `docs/`), пока PRD активен.
2. Содержит детализацию шагов реализации с актуальными статусами.
3. Удаляется в одном коммите с merge соответствующего PRD.
4. В GitHub Issues уходит ТОЛЬКО то, что выходит за scope активного PRD (например,
   доработки на будущее или баги, обнаруженные при реализации).

**Не путать с общим `TODO.md`** — общие задачи без привязки к PRD используют Issues,
не файлы.

#### Именование файлов в docs/

**Формат**: `CATEGORY-TOPIC.md`

**Примеры**:

- `API-REFERENCE.md` - не нужен, используем TypeDoc
- `LOGGING-GUIDELINES.md` - правильно
- `CONTRIBUTING.md` - правильно (стандартное имя GitHub)
- `v1-to-v2-migration.md` - правильно

**Правила**:

- UPPERCASE для важных файлов (CONTRIBUTING, LICENSE)
- lowercase-with-dashes для обычных файлов
- Префикс категории, если файлов много

## Форматирование документов

### Markdown правила

**ОБЯЗАТЕЛЬНО**:

1. **Никаких emoji** в файлах `.md` (строгий запрет, без исключений)
2. **Пустые строки** перед и после:
   - Заголовков всех уровней
   - Списков (маркированных и нумерованных)
   - Блоков кода
   - Цитат и таблиц
3. **Списки**:
   - Маркированные: использовать `-` (не `*` или `+`)
   - Нумерованные: использовать `1.`, `2.`, `3.` (последовательно)
   - Вложенные списки: отступ 2 пробела
4. **Блоки кода**:
   - Всегда указывать язык: \`\`\`typescript, \`\`\`javascript, \`\`\`bash
   - Для примеров вывода использовать \`\`\`text или \`\`\`bash
5. **Заголовки**:
   - Только один H1 (`#`) в документе
   - Не пропускать уровни (после `##` не может быть `####`)
   - Не использовать символы в конце заголовка
6. **Ссылки**:
   - Формат: `[текст](url)` для внешних ссылок
   - Формат: `[текст](#якорь)` для внутренних якорей
   - Якоря в lowercase с дефисами
7. **Проверка качества**:
   - Все `.md` файлы ДОЛЖНЫ проходить проверку `markdownlint` без ошибок и предупреждений
   - Настроить pre-commit hook или CI для автоматической проверки
   - Использовать `.markdownlint.json` для конфигурации проекта

**Структура документа**:

```markdown
# Заголовок документа

Краткое описание (1-2 абзаца).

## Раздел 1

Текст раздела.

### Подраздел 1.1

Детали.

## Раздел 2

Продолжение.
```

### Примеры кода

**Требования**:

1. Все примеры должны быть рабочими
2. Код должен быть полным (не обрывки)
3. Комментарии объясняют "зачем", а не "что"

**Формат**:

```markdown
## Example: Basic Usage

\`\`\`typescript
import { Library } from '@scope/package';

// Create instance with configuration
const lib = new Library({
  option: 'value'
});

// Use the library
const result = await lib.doSomething();
console.log(result);
\`\`\`

**Output**:

\`\`\`
{ success: true, data: [...] }
\`\`\`
```

## JSDoc в коде

### Обязательная документация

**Все публичные элементы**:

- Classes
- Public methods
- Public properties
- Exported functions
- Exported types/interfaces

**Формат**:

```typescript
/**
 * Brief description of what this does (one line)
 *
 * Detailed description if needed (optional, multiple lines).
 *
 * @param paramName - Description of parameter
 * @param options - Configuration options
 * @returns Description of return value
 * @throws {ErrorType} Description of when error is thrown
 *
 * @example
 * ```typescript
 * const result = await myFunction('value', { option: true });
 * console.log(result); // Expected output
 * ```
 */
```

### Необязательная документация

**Не документируем**:

- Private методы (если они простые)
- Внутренние implementation details
- Очевидные геттеры/сеттеры
- Тесты

**Исключение**: Документируем private метод, если:

- Сложная логика
- Нужно объяснить "почему" (не "что")

## Генерируемая документация

### TypeDoc

**Применимость**: только библиотеки. Для backend и frontend приложений TypeDoc не
используется. Альтернативы:

- **Backend**: JSDoc inline на routes/services/utils + опционально OpenAPI/Swagger для
  HTTP-API (`server/routes.ts` → `openapi.yaml`).
- **Frontend**: JSDoc inline на хуках/компонентах со сложной логикой + опционально
  Storybook для UI-компонентов.

**Конфигурация** (`typedoc.json`):

```json
{
  "entryPoints": ["src/index.ts"],
  "out": "docs/typedoc",
  "exclude": ["**/__test__/**", "**/node_modules/**"],
  "plugin": [],
  "excludePrivate": true,
  "excludeInternal": true,
  "readme": "none"
}
```

**Правила**:

- Генерируется из JSDoc автоматически
- Выходная директория в `.gitignore` (кроме published packages)
- Регенерация перед каждым релизом
- Публикация на GitHub Pages (опционально)

### Coverage Reports

**Правила**:

- Генерируются автоматически в CI/CD
- Локальные отчеты в `.gitignore`
- Coverage badge в README (только финальная цифра)

## Жизненный цикл документов

### Создание документа

**Чек-лист**:

1. Действительно ли нужен отдельный файл? (может хватит секции в README?)
2. Будет ли этот документ актуален через 6 месяцев?
3. Кто будет поддерживать его в актуальном состоянии?
4. Есть ли дублирование с другими документами?

**Если хоть на один вопрос ответ "нет"** - не создаем документ.

### Обновление документа

**Правила**:

- Обновляем в том же PR, что меняем код
- Если документ устарел более чем на 20% - удаляем его
- Если документ не обновлялся 6+ месяцев - проверяем актуальность

### Удаление документа

**Удаляем немедленно если**:

1. Описываемая функциональность удалена
2. Документ описывает "как мы это сделали" (а не "как использовать")
3. Весь контент уже есть в другом месте
4. План/roadmap полностью выполнен
5. Анализ/исследование завершено, результаты в коде

**НЕ удаляем**:

- CHANGELOG.md (история релизов)
- Migration guides (пока есть пользователи старой версии)
- API reference (если API еще поддерживается)

## Примеры использования

### Структура examples/

```bash
examples/
├── README.md              # Описание всех примеров
├── basic-usage.js         # Минимальный пример
├── advanced-features.js   # Расширенный пример
├── with-typescript.ts     # TypeScript специфика
└── actions/               # Данные для примеров
    ├── example1.actions.js
    └── example2.actions.js
```

**Требования к примерам**:

1. Каждый пример - рабочий скрипт
2. Можно запустить: `node examples/basic-usage.js`
3. Используют абсолютные пути (не относительные)
4. Комментарии объясняют каждый шаг
5. Показывают вывод (console.log)

**Формат examples/README.md**:

```markdown
# Examples

Рабочие примеры использования библиотеки.

## Basic Usage

Файл: [basic-usage.js](./basic-usage.js)

Демонстрирует: минимальный setup и первый вызов.

\`\`\`bash
node examples/basic-usage.js
\`\`\`

## Advanced Features

Файл: [advanced-features.js](./advanced-features.js)

Демонстрирует: мониторинг, кеширование, error handling.

\`\`\`bash
node examples/advanced-features.js
\`\`\`
```

## Антипаттерны

### Что НЕ делать

#### 1. Документы "на будущее" без актуализации

```bash
Плохо:
- docs/FUTURE-FEATURES.md (wishlist без сроков и ответственных)
- ROADMAP.md, не обновлявшийся 3+ месяца
Почему: используйте Issues/Projects/Milestones
```

Исключение — актуальный `ROADMAP.md`: см. условия в секции "ROADMAP.md: когда допустим".

#### 2. Дублирование информации

```bash
Плохо:
- README.md описывает API
- docs/API.md описывает то же API
- JSDoc повторяет описания

Хорошо:
- README.md - краткий обзор + ссылка на TypeDoc
- JSDoc - полная документация
- TypeDoc - автогенерация
```

#### 3. Устаревшие примеры

```bash
Плохо: Пример использует старый API

Хорошо:
- Примеры - это тесты (examples/*.test.js)
- Автоматически проверяются при каждом изменении API
```

#### 4. Emoji в документации

```bash
Плохо: ## ✅ Features

Хорошо: ## Features
```

#### 5. История разработки в документации

```bash
Плохо: docs/IMPLEMENTATION-LOG.md

Хорошо: Используйте git log и PR descriptions
```

## Настройка линтера

### Конфигурация markdownlint

Создайте `.markdownlint.json` в корне проекта:

```json
{
  "default": true,
  "MD013": false,
  "MD033": false,
  "MD041": false,
  "MD024": {
    "siblings_only": true
  },
  "no-hard-tabs": true,
  "whitespace": true
}
```

**Пояснение правил**:

- `MD013: false` - отключаем проверку длины строки (может быть слишком строгой для кода в примерах)
- `MD033: false` - разрешаем HTML теги (иногда нужны для сложных таблиц)
- `MD041: false` - не требуем H1 в начале файла (может быть метаданные)
- `MD024: { "siblings_only": true }` - запрещаем дубликаты заголовков только среди
  соседей (siblings), разрешаем в разных секциях
- `no-hard-tabs: true` - запрещаем табы, только пробелы
- `whitespace: true` - проверяем trailing spaces

### Pre-commit hook

Добавьте в `package.json`:

```json
{
  "scripts": {
    "lint:md": "markdownlint '**/*.md' --ignore node_modules --ignore dist",
    "lint:md:fix": "markdownlint '**/*.md' --ignore node_modules --ignore dist --fix"
  },
  "devDependencies": {
    "markdownlint-cli": "^0.39.0"
  }
}
```

### CI/CD проверка

Добавьте в GitHub Actions workflow:

```yaml
- name: Lint Markdown files
  run: npm run lint:md
```

## Чек-лист перед релизом

### Документация

- [ ] README.md актуален
- [ ] CHANGELOG.md обновлен
- [ ] Все примеры работают
- [ ] JSDoc для новых публичных API
- [ ] TypeDoc сгенерирован
- [ ] Нет устаревших документов в docs/
- [ ] package.json: version, description актуальны
- [ ] Все .md файлы проходят markdownlint
- [ ] Нет emoji в .md файлах

### Очистка

- [ ] Удалены документы с планами/анализом
- [ ] Удалены TODO.md, ROADMAP.md

## Заключение

**Золотое правило**: Документация - это код. Относитесь к ней так же строго:

- Рефакторим устаревшее
- Удаляем неиспользуемое
- Тестируем примеры
- Ревьюим изменения
- Поддерживаем актуальность

**Помните**: Лучше 100 строк актуальной документации, чем 1000 строк устаревшей.
