# PRD-66. Психометрическая аналитика качества заданий — план реализации

> **Для исполнителя:** задачи выполняются по одной, сверху вниз, в режиме TDD: сначала падающий
> тест, потом минимальная реализация, потом прогон, потом коммит. Шаги отмечены чекбоксами
> (`- [ ]`).

**Цель:** посчитать психометрические показатели качества заданий и теста на трёх источниках
наблюдений и встроить их в существующий экран аналитики теста.

**Архитектура:** слой наблюдений PRD-56 (`server/services/analytics/observations.ts`) расширяется до
уровня ОТВЕТА; расчётный движок — чистые функции в `shared/psychometrics/`; API — расширение
`/api/analytics`; экран — вкладка «Качество заданий» рядом с «Обзором» и «Вопросами». Своего языка
отбора и своей оси разбиения трек не заводит: фильтр и срезы берутся у PRD-56.

**Технологии:** TypeScript, Drizzle ORM, PostgreSQL, Vitest, React.

**Спецификация:** [docs/specs/prd-66/psychometric-analytics.md](../specs/prd-66/psychometric-analytics.md).
Номера `FR-NN` ниже ссылаются на неё. Эскиз:
[docs/wireframes/prd66-item-quality.html](../wireframes/prd66-item-quality.html) (согласован 2026-09-24).

## Что нужно знать до начала

- **Vitest запускается ТОЛЬКО через npm:** `npm test -- <путь>`. Прямой `npx vitest run` падает.
- **Полный прогон (`npm test` без пути) не запускать** без явного разрешения владельца: около
  восьми минут и вся машина.
- **`npm run check` бывает ложно-зелёным:** кэш `tsc` общий для всех worktree. Если правка типов
  «не видна» — удалить `.tsbuildinfo` и повторить.
- **Дев-база общая для всех сессий.** Все миграции этого плана АДДИТИВНЫЕ; destructive-шагов нет.
- **Интеграционные тесты идут на pglite:** `npm run test:it`. Схема для них лежит отдельным DDL в
  `tests/it/schema.sql` и НЕ генерируется из модели — новые колонки дописываются туда руками,
  иначе `it`-тесты падают на «column does not exist».
- **Последняя миграция — `0038`**, новая будет `0039`.
- **`questions.content_hash` трогать нельзя.** Колонка уже есть, но её сравнивает PRD-15:
  `test_question_scoring.pinned_content_hash` пришпиливает цену задания к редакции. Изменение
  правила расчёта этого хеша разом пометит устаревшими ВСЕ пины цен — ложная тревога на каждом
  тесте. Психометрике нужна своя колонка с другой семантикой (задача 1).

Без него метрики считаются на неверных данных. Интерфейса не имеет.

### Задача 1. Отпечаток содержания задания `psycho_hash`

- [x] Колонку дописать в `tests/it/schema.sql` руками.

      хеш строится по паре «текст варианта -> верность», а не по индексам (BRD PA-15b).
- [x] Тесты: смена эталона меняет хеш; перестановка вариантов не меняет; правка текста меняет;
      цена и градуированная схема в хеш не входят (PA-15d).
- [x] Запись в слое storage на КАЖДОМ создании и изменении вопроса
      (`server/storage/questions-repository.ts`), а не только при импорте книги.
- [x] Существующий `computeQuestionHash` (`server/services/questions-import.ts:52`) НЕ трогать:
      он обслуживает `content_hash` для пинов PRD-15.
- [x] Бэкфилл: `psycho_hash` по текущему содержанию. Наблюдения, собранные раньше, остаются
      серией «версия неизвестна» (FR-09c) — это решение ОВ-04, не дефект.

**Отступление от плана, принятое при исполнении.** Бэкфилл сделан скриптом
`npm run psycho:backfill` (`scripts/db/backfill-psycho-hash.ts`), а НЕ запросом внутри миграции.
Причина: отпечаток считает `shared/questions/psycho-hash` — канонизация ключей плюс свёртка
вариантов в пары «текст -> верность» с сортировкой по тексту, — и повторить это правило на SQL
значит завести вторую реализацию. Первая же правка первой развела бы их молча: часть заданий
получила бы отпечаток по одному правилу, часть по другому, а расхождение читалось бы не ошибкой,
а разрывом серии наблюдений на ровном месте. Скрипт зовёт ту же функцию, что и слой хранения,
идемпотентен и не трогает строки с уже проставленным отпечатком.

**Найдено при засыпке дев-базы:** 1397 заданий, 1149 различных отпечатков. Около 250 заданий
повторяют содержание друг друга — копии по темам. Для психометрики это не дефект, а ровно то, ради
чего заводился отпечаток: одинаковое содержание даёт ОДНУ серию наблюдений, в какой бы теме
задание ни лежало. Числа заданий на экране и числа серий сойдутся не всегда, и Э6 обязан это
объяснять, а не прятать.

Сверх плана закрыты ещё три пути записи вопроса, которые иначе оставили бы отпечаток пустым:
копия темы (`topics-repository`, копия несёт ТОТ ЖЕ отпечаток — содержание не меняется), перенос
теста (`test-transfer-repository`, пакет без отпечатка получает его по содержанию) и засев
дев-базы (`seed-db`).

### Задача 2. Штамп редакции в веб-наблюдение

- [x] Штамп редакции хранится в форме попытки (`attempts.variant_json.psychoHashes`, карта
      «задание -> отпечаток»; миграции не нужно).
- [x] Попытки со снапшотом (PRD-15) берут хеш из снапшота, без снапшота — из живого банка; нет
      отпечатка на строке — считается по содержанию (FR-09b).
- [x] Завершение попытки сверяет редакцию с выданной; расхождение делает штамп неизвестным
      (FR-09b1). Адаптивный путь штампует в момент ответа — он же момент выдачи (FR-09b2).
- [x] Тесты: старт штампует выданное, невыданное не попадает, правка по ходу обнуляет штамп,
      попытка без штампа его не выдумывает.

**Отступление от плана, принятое при исполнении.** План говорил «сохранять рядом с ответом в
`answers_json`, в момент записи ответа». Так нельзя по двум причинам. Первая — форма: `answers_json`
это плоская карта «задание -> значение ответа», её целиком присылает клиент и читают движок
оценивания и аналитика; превращение значений в объекты сломало бы всех троих ради одного поля.
Вторая, и главная — смысл: в вебе содержание отдаётся ОДИН раз, на старте, и правка задания посреди
чужого прохождения не меняет того, что участник видит. «Текущая редакция в момент ответа» назвала бы
редакцию, которой он не видел. Штамп снимается в момент ВЫДАЧИ и живёт в `variant_json` — там же, где
лежит сам выданный состав. FR-09b переписан, добавлены FR-09b1 (сверка при завершении) и FR-09b2
(адаптивный путь).

### Задача 3. Разбор выгрузки LMS отличает «не выдано» от «оценивать нечего»

- [x] `shared/lms-export/parse.ts`: читать ВСЕ четыре подколонки блока взаимодействия, а не три.
- [x] Блок, где все четыре пусты, в наблюдения не попадает вовсе (`missing`); `neutral`
      сохраняется только за измерительным заданием (FR-10a).
- [x] `server/services/lms-export-import.ts`: убрать сведение `r.results[id] || "neutral"`.
- [x] Тесты на фикстуре выгрузки: невыданное задание, выданное и пропущенное, измерительное.
- [ ] **Задача общая с PRD-55** (BR-26-02a, этап Э5 того плана): разбор научился, но учёт
      экспозиции по импортированным строкам здесь НЕ включается — это отдельный шаг в плане
      PRD-55, и теперь он разблокирован.

**Что различает выданное и невыданное.** Признак — четвёртая подколонка «Тип»: пакет пишет
взаимодействие только по показанному заданию, и у невыданного пусты все четыре ячейки, а у
выданного и не отвеченного заполнен хотя бы тип. Разбор читал три подколонки, поэтому такого
признака не видел.

**Решение о пустом исходе принимает не разбор, а запись** — там известен ТИП задания. У
измерительного пустой исход законен и остаётся `neutral`: эталона у него нет вовсе. У
оцениваемого пустой исход значит, что файл его не сообщил; наблюдением он не становится, и партия
получает предупреждение с числом таких взаимодействий. Приписать «неверно» значило бы выдумать
ответ, которого участник мог не дать, а `neutral` — объявить измерительным то, что оценивается.

### Задача 4. Партия импорта: потери и учёт

- [x] Миграция `0039` (та же): `lms_import_batches` получает
      `rows_unmatched integer not null default 0` и `counted boolean not null default true`.
- [x] Импортёр пишет число несопоставленных взаимодействий в `rows_unmatched` (FR-11).
- [x] Ручка переключения `counted` и учёт флага при чтении наблюдений (FR-12).
- [x] Тесты: партия, снятая с учёта, исчезает из выборки, строки остаются в базе.

**Где стоит условие учёта.** В общем отборе строк из LMS (`analytics-repository`, `lmsWhere`), а
не внутри психометрики. Иначе снятая партия исчезла бы с одного экрана и осталась на другом, и два
экрана одного трека показывали бы разные числа по одним данным. Живой телеметрии условие не
касается: партии у неё нет по построению, и `coalesce(..., true)` это закрепляет — иначе одно
переключение выключило бы целый источник.

**Потери считаются по ВЗАИМОДЕЙСТВИЯМ, а не по колонкам.** Одна чужая колонка в файле на тысячу
прохождений — это тысяча потерянных наблюдений, и доля потерь выборки видна только так.

### Задача 5. Замер времени на задании в веб-хосте

- [x] Перенести замер в `shared/questions/question-time` — модуль без зависимостей, часы
      инъектируются (это и делает измерение проверяемым).
- [x] Пакет получает счётчик через общий бандл рантайма (`TBTemplate`); `questionTime.js` стал
      тонкой обёрткой, `TEST_DATA` не изменился.
- [x] Веб-плеер вызывает `show`/`leave` там, где монтирует вопрос; сумма по всем заходам едет с
      каждым сохранением прогресса и с завершением (FR-37a).
- [x] Тесты: возврат к вопросу суммирует время, а не заменяет; счётчики попыток независимы.

**Куда легло время.** В `attempts.variant_json.latencyMs`, а не в `answers_json` — по той же
причине, что и штамп редакции: карта ответов плоская, «задание -> значение», её целиком присылает
клиент и читают движок оценивания и аналитика. Аналитика веб-источника перестала подставлять
`null`: у попытки без карты времени по-прежнему нет, и это «не измерялось», а не ноль.

**Фабрика, а не singleton.** Страница прохождения переживает несколько попыток подряд, и общий
счётчик перенёс бы секунды одной в следующую. Показом считается экран задания: обзор, итоги раздела
и страницы содержания счёт останавливают.

## Этап Э2. Наблюдения уровня ответа

- [x] Расширить слой PRD-56 матрицей «задание -> доля балла, исход, редакция, время» (FR-06):
      `server/services/analytics/response-matrix.ts`, отбор целиком делегирован `loadObservations`.
- [x] Три адаптера — веб, телеметрия, импорт — различаются только тем, что источник ЗНАЕТ (FR-07).
- [x] Группа респондента берётся из существующего слоя, своя ось не заводится (FR-08).
- [x] Тесты на каждом источнике: одинаковые наблюдения дают одинаковую матрицу.

**Четыре состояния исхода против трёх в базе.** `neutral` — оценивать нечего (нет эталона), в CTT
не входит никогда; `missing` — задания участник не видел, оно вне ЗНАМЕНАТЕЛЯ трудности. Пропуск
(выдано, ответа нет) — это НЕ `missing`, а ошибка ценой в ноль (решение OQ-07): выкинуть его значило
бы завысить трудность, ведь задание, которое все пропускают, выглядело бы лёгким. Поэтому веб-адаптер
перебирает ВЫДАННЫЙ состав, а не карту ответов, и ответ на задание вне состава (его убрали из теста)
в наблюдения не идёт.

**Различие источников решает СТРОКА, а не название источника.** Балл сообщён — доля считается из
него; не сообщён (выгрузка отчёта) — остаётся бинарный исход. Проверка паритета в тестах: на задании
с точной оценкой три источника сходятся до знака.

**Редакция прохождения из LMS восстанавливается по снимку публикации.** Снимок заморожен (PRD-15),
значит содержание задания в нём — ровно то, что видел участник, сообщивший эту версию (PRD-56
FR-19a). Отпечаток считается ТОЙ ЖЕ функцией, что и при записи вопроса. Прохождение без версии
уходит в серию «версия неизвестна» — это сильнее PA-10d BRD, который считал редакцию импорта
неизвестной всегда.

**Порции у матрицы нет намеренно:** метрику нельзя посчитать по половине выборки, и «страница»
наблюдений была бы здесь не оптимизацией, а неверным числом. Добавлены три батч-запроса DAL
(`getAttemptsByIds`, `selectAnswersForAttempts`, `selectGroupsOfUsers`) — чтение по одной строке
дало бы запрос на каждое прохождение выборки.

## Этап Э3. Расчётный движок (не зависит от Э1 и Э2, ведётся параллельно)

- [x] `shared/psychometrics/`: трудность, поправка на угадывание, корреляция задание-остаток,
      индекс крайних групп, альфа и KR-20, SEM, Спирмен-Браун, дистракторы, уровни доверия.
- [x] Альфа: значение пункта — доля балла или вклад со знаком; выборка — только полные наборы
      (FR-19a, FR-19b).
- [x] Юнит-тесты на эталонных наборах с вручную посчитанными значениями (AC-01).

**Правило, проходящее через весь движок: пустота возвращается как отсутствие величины, а не как
ноль** (FR-44). Ноль — это утверждение. «Трудность 0» значит «не решил никто», «дискриминативность
0» — «задание никого не различает». У задания, которое решили ВСЕ, дискриминативности нет вовсе:
ряд без разброса корреляции не имеет, и списать такое задание по нулю было бы ложью — оно просто
ничего не измеряет. То же у альфы: три разные причины («пунктов меньше двух», «респондентов с
полным набором меньше двух», «все набрали поровну») возвращаются РАЗНЫМИ значениями, потому что на
экране это разные сообщения.

**KR-20 отдельной формулой не считается.** Для строго дихотомического набора альфа в точности ей
равна — это её частный случай, и вторая реализация была бы вторым источником одного числа. Движок
лишь помечает набор признаком `dichotomous`.

**Индекс дискриминации и дистракторный разрез делят выборку ОДИНАКОВО** — крайними 27 % по
способности. Два разных деления дали бы два разных ответа на вопрос «кто здесь сильный».

**Признаки дистрактора называют симптом, а не причину** — то же правило, что FR-31a у шкал.
Положительная корреляция неверного варианта значит ровно одно: его выбирают сильные. Частично
верен он, двусмыслен или ключ ошибочен — по числам не различить.

## Этап Э4. Шкалы и время

- [x] Альфа шкалы, корреляция пункта с остатком шкалы, распределение по градациям, ипсативность.
- [x] Альфа при перевёрнутом вкладе пункта (FR-31b).
- [x] Медиана и размах времени, флаги «отвечают не читая» и «задание тормозит прогон».

**Шкалы считаются ТЕМ ЖЕ движком надёжности**, что и тест: разница только во входе — значением
пункта служит вклад ответа со знаком, а не доля балла. Это и делает вопрос «что, если вклад
перевернуть» вычислимым: знак меняется, наблюдения остаются те же, и подпись даёт проверяемое
следствие вместо догадки о причине (FR-31a/31b).

**Ипсативность опознаётся по данным, а не по типу вопроса:** совпадающие суммы вкладов у всех
респондентов и есть фиксированный запас баллов. По одному респонденту вывод не делается — совпадать
там нечему.

**Время: медиана и межквартильный размах, а не среднее.** Одно наблюдение с оставленной вкладкой
сдвигает среднее сильнее, чем полсотни обычных; медиана его не замечает. Порог «отвечают не читая»
зависит от ДЛИНЫ текста задания: три секунды на однострочный вопрос нормальны, на абзац с условием
— нет. Признак «тормозит прогон» не срабатывает на трудном задании: он ищет перегруженную
формулировку, а не сложность предмета.

## Этап Э5. API и кэш

- [x] Расширение `/api/analytics`; ключ кэша — тест, версия содержания, состав партий, фильтр,
      режим попыток (FR-57). Ручка: `GET /api/analytics/psychometrics/:testId`.
- [x] Права — те же, что на аналитику теста (FR-58).

**Сведение живёт отдельно от расчёта.** `response-matrix` знает, ГДЕ взять наблюдения;
`shared/psychometrics` — КАК считать; `services/analytics/psychometrics` — что с чем сопоставить:
какому заданию сколько вариантов, какой порог к какому числу. Считать он не умеет ничего, и это
проверяется тем, что ни одной формулы в нём нет.

`resetPsychometricsCache(testId)` — он нужен продукту, а не тестам.

**Умолчание «только первая попытка»** (FR-51) применяется в ручке и возвращается в ответе: режим
должен быть виден читателю, а не подразумеваться.

выдано» от «нечего оценивать» (PA-12). Состояние `missing` в типе есть, но ни один адаптер его не

берутся по одной совокупности: человек, ответивший только на измерительные задания, в выборку не
входит.

Находка приёмки: в предупреждении про интервал стояло «16 участников из 60», тогда как сам

выборок в одной фразе; знаменатель исправлен, оговорка про полный набор названа словами.

Фикстура дополнена неравномерной выдачей (`skip` в `seedAttempt`): без неё доля невыданных равна
нулю у всех заданий, и проверить FR-41 в браузере не на чем. Теперь одно задание демо достаётся
трети участников — «не выдано 67 %» рядом с трудностью 0,80, посчитанной на двадцати наблюдениях.

**Решения FR-02 и FR-03, которых не было в плане:**

- **числа берутся из ТОГО ЖЕ расчёта, что питает вкладку «Качество заданий»**, а не считаются
  вторично в `test-details`: ключ запроса один на обе вкладки, поэтому переход между ними не платит
  за второй расчёт, а колонка и карточка не могут разойтись в числах. Следствие, названное подписью
  под таблицей: трудность считается по ПЕРВОЙ попытке участника, тогда как пропуски и время — по
  всем ответам. Считать коэффициент по всем попыткам значило бы складывать зависимые наблюдения;
- **авторская трудность переименована в «Замысел»** (так её называет эскиз): наблюдаемая величина
  заняла имя «Трудность», и две колонки с этим заголовком читались бы как поломка;
- **форматтер числа вынесен в общий модуль** `psychometrics-format`: два экрана печатают одни и те
  же величины, и копия разошлась бы на первой правке. Там же лечится находка приёмки — минус
  печатался дефисом.

**Что вскрыла приёмка FR-02/FR-03 (две находки):**

- **минус был дефисом.** В колонке чисел дефис читается как прочерк «величины нет», а у
  дискриминативности знак — главное, что о ней сказано. Теперь U+2212 на обоих экранах;
- **новая колонка отняла ширину у условия задания:** оно сжалось в столбик по три слова (270 px из
  1252). ГОЧА, обратная находке 6: доля в процентах на колонке при `table-layout: auto` — лишь
  пожелание, и `width` у ЗАМОРОЖЕННОЙ колонки ДС не доходит до ячейки вовсе. Предел, как и верхний,
  поставлен самому тексту (`min-width: 36ch`). Почему не 28 % эскиза: там действия строки убраны
  под меню-троеточие, а в таблице PRD-56 стоят две кнопки, и 28 % выталкивают правую за край.

**Что вскрыла приёмка на фикстуре (три находки, все закрыты):**

- **длинное задание вытесняло колонки.** `table-layout: auto` игнорирует проценты ширины, поэтому
  ограничение поставлено самому тексту, а не ячейке;
- **«Сильные ошибаются чаще» зажигалось на шуме:** r = −0,02 — это ноль, а не отрицательная
  дискриминация. Введён порог значимости −0,05;
- **у измерительного теста показывалась пустая таблица заданий** с надписью про нехватку
  наблюдений (FR-52). Оценивать там нечего в принципе, и говорить надо именно это.
