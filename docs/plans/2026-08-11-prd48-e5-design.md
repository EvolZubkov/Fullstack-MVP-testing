## Ограничения модели, ради которых план такой

Разведка по коду вскрыла семь фактов; каждый определяет решение.

1. **Оформление пишется своим маршрутом** `PUT /api/tests/:id/design`, а не общим сохранением
   теста. Он же — единственное место, где вообще проверяется набор ключей.
2. **Шаблон обязан существовать на приёмнике и быть АКТИВНЫМ.** Иначе маршрут отвечает 422
   «Template not found or inactive». Книга шаблон установить не может — их ставят отдельным
   контуром (ZIP через админку).
3. **Ключ `params`, которого нет в манифесте приёмника, роняет ВЕСЬ запрос** (422 со списком
   лишних ключей). Не тихая потеря — отказ. Фильтровать обязан импортёр.
4. **Значения `params` не типизирует никто.** Маршрут кладёт их как есть. Из ячейки Excel всё
   приходит строкой, а модель ждёт `boolean`, число, массив (`multiselect`) и медиа-конверт
   `{url, name, …}`. Аналога `normalizeSettingsForTemplate` (он есть у полей страниц) для
   оформления нет — свой слой нормализации по манифесту придётся написать.
5. **Цвет живёт в ДВУХ формах**: плоско в `params` либо по палитрам в `paramsByTheme`. В какой
   именно — зависит от истории правок теста: первая правка цвета в теме переносит его из
   `params` во все палитры. Книга обязана читать обе формы и писать ту же, что у источника,
   иначе после круга цвет продублируется или исчезнет. Сервер при этом принимает
   `paramsByTheme` только у шаблона с темами и только для параметров типа `color`.
6. **Версии шаблона переносить нельзя.** `templateVersion` из книги-источника даст автору
   баннер «Шаблон обновлён», а одна кнопка в нём выбросит все параметры, которых нет в новом
   манифесте. `templateApiVersion` из чужого билда может дать 422. Сервер проставляет обе сам —
   книга их не несёт вовсе.
7. **Настройки отчёта не проверяет НИКТО.** Ни при записи (zod пропускает любой `variantKey` и
   любой словарь), ни при чтении: `resolveReportVariant` на неизвестный ключ МОЛЧА берёт вариант
   по умолчанию. Книга может «успешно» перенести отчёт, а обучающийся получит документ другого
   вида без единого следа в логах. Всю сверку обязан выполнить импортёр.

## Что план НЕ делает

- Не переносит файлы (логотип, подложка отчёта, любые `image`/`file`/`asset`): книга несёт
  адрес, файл остаётся на источнике. Ссылка `/api/media/<uuid>` источника на приёмнике почти
  наверняка не разрешится, и картинка пропадёт молча — это следствие решения PRD-14.
- Не устанавливает шаблоны.
- Не чинит отсутствие индексации медиа в значениях отчёта (известный пробел модели).

## Контракт листа «Оформление»

Один лист, пять колонок. Оформление и отчёт держатся вместе, потому что оба — про облик и оба
зависят от одного манифеста.

| Колонка | Смысл |
| --- | --- |
| `Что` | `Шаблон` / `Тема теста` / `Параметр` / `Отчёт` |
| `Режим` | Для строк отчёта: `Стандартный` / `Адаптивный`; пусто для общих строк и для оформления |
| `Тема` | Для строк параметра: идентификатор палитры (переопределение цвета); пусто = значение лежит плоско |
| `Ключ` | Ключ параметра из манифеста; для строк `Шаблон`/`Тема теста` пусто; для отчёта — `Вид отчёта`, `Выдавать отчёт` или ключ поля вида |
| `Значение` | Значение |

### Правила применения

- Лист отсутствует — ни оформление, ни отчёт не меняются.
- **Шаблона нет на приёмнике или он неактивен — лист отвергается ЦЕЛИКОМ** с внятной ошибкой
  («шаблон «X» не установлен; поставьте его и повторите импорт»). Частично применённое
  оформление хуже неприменённого: тест получит чужие цвета поверх чужого макета.
- Ключ параметра, которого манифест приёмника не объявляет, отбрасывается с ПРЕДУПРЕЖДЕНИЕМ.
  Молчать нельзя: автор видит «оформление перенесено», а половины настроек нет.
- Значение приводится к типу, объявленному манифестом. Не приводится — ошибка строки.
- Строка `Параметр` с непустой `Тема` кладётся в `paramsByTheme`, с пустой — в `params`.
  Выгрузка пишет ту форму, в которой значение лежит у источника.
- **Вид отчёта, которого нет в манифесте приёмника, — ОШИБКА строки**, а не молчаливая подмена.
  Это единственное место, где книга строже продукта, и это сознательно: продукт молча
  подменяет вид, и обнаружить это можно только глазами в готовом PDF.
- Ветвь отчёта БЕЗ вида — законна (настройки, сохранённые до PRD-35) и обязана пережить перенос.
  Импортёр не вправе дозаполнить её видом по умолчанию: на приёмнике умолчание может быть другим.
- Обе ветви режимов переносятся независимо от текущего режима теста: ветвь неактивного режима
  рабочая и сохранена по замыслу.
- `Выдавать отчёт`: пустая ячейка — «оставить как есть». Отсутствие настройки означает
  «выдавать», и пустая ячейка НЕ должна читаться как «выключено».

## Задача 1. Контракт листа

**Файлы:** создать `server/utils/workbook-design.ts`, тест `tests/workbook-design.test.ts`.

Экспортирует заголовки, ширины, словари значений, `serializeDesignRows(design, report)` и
`parseDesignSheet(rows)` → структура с `templateId`, `theme`, `params`, `paramsByTheme`,
ветвями отчёта и `errors`.

Модуль НЕ знает манифеста: он разбирает ячейки. Приведение значений к типам и фильтрация по
манифесту — Задача 2, потому что требуют чтения шаблона из БД.

Свойства под тестом: круг для плоского параметра и для переопределения по палитре; обе ветви
отчёта; ветвь без вида; `Выдавать отчёт` в трёх состояниях (да/нет/пусто); неизвестные `Что`,
`Режим` — ошибка строки; строка `Параметр` без ключа — ошибка.

Коммит: `feat(workbook): контракт листа «Оформление»`

## Задача 2. Нормализация по манифесту

**Файлы:** создать `server/services/design-fields.ts`, тест.

Здесь живёт то, чего в продукте нет вовсе: приведение значения параметра оформления к типу,
объявленному манифестом (`boolean`, `number`, `select` по `options`, `multiselect` как массив,
`color`, медиа-конверт), и та же работа для полей отчёта по `settings[]` выбранного вида.

Образец для подражания — `server/services/content-page-fields.ts`: та же задача для полей
страницы, те же правила «незаявленный ключ не пишется», «`select` вне списка отбрасывается».

Коммит: `feat(design): нормализация параметров оформления по манифесту`

## Задача 3. Выгрузка

**Файлы:** `server/utils/workbook-sheets.ts`, `server/routes/tests-workbook.ts`, тест.

Лист встаёт ПОСЛЕ «Адаптивных уровней» и ПЕРЕД «Оценкой». Версии шаблона НЕ пишутся (см.
ограничение 6) — только `templateId`.

Коммит: `feat(workbook): выгрузка оформления и настроек отчёта`

## Задача 4. Загрузка

**Файлы:** `server/services/workbook-import.ts`, тест.

Оформление пишется своим путём (маршрут `PUT /:id/design` не годится — импорт не ходит в себя
по HTTP; повтори его проверки, вызвав общую нормализацию Задачи 2 и записав через хранилище).
Настройки отчёта — колонка `report_settings_json`, уходит вместе с прочим патчем теста.

Тесты: круг; отсутствующий шаблон — отказ листа с внятной ошибкой; лишний ключ — предупреждение;
неизвестный вид отчёта — ошибка; ветвь без вида переживает перенос; книга без листа ничего не
трогает.

Коммит: `feat(workbook): загрузка оформления и настроек отчёта`

## Задача 5. Шаблон и документы

Лист в шаблоне книги, выпадающие списки, примерные строки, справка на каждую колонку; контракт
в `format.md`; в спеке отметить статус Э5 и записать ограничение:

> Перенос оформления и отчёта точен ровно в объёме, который объявляет манифест ПРИЁМНИКА.
> Одинаковый идентификатор шаблона на двух стендах не гарантирует одинакового набора параметров:
> манифест — снимок в базе каждого стенда. Файлы (логотип, подложка отчёта) книга не несёт.

Коммит: `feat(workbook): шаблон и контракт листа оформления`
