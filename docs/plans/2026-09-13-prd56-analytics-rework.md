# PRD-56. Переработка аналитики — план работ

> **Для исполнителя:** задачи выполняются по одной, сверху вниз, в режиме TDD: сначала падающий
> тест, потом минимальная реализация, потом прогон, потом коммит. Шаги отмечены чекбоксами
> (`- [ ]`).

**Цель:** сделать из двух похожих экранов два инструмента — рабочее место оценщика (раздел
«Аналитика») и рабочее место автора (аналитика теста), — считающих по одному источнику
наблюдений.

**Спецификация:** [docs/specs/prd-56/analytics-rework.md](../specs/prd-56/analytics-rework.md).
Номера `FR-NN` ниже ссылаются на неё.

[раздел «Аналитика»](../wireframes/prd56-analytics-section.html),
[аналитика теста](../wireframes/prd56-test-analytics.html).

**Технологии:** TypeScript, Express, Drizzle ORM, PostgreSQL, React 19, `@skillum/ui-kit`, Vitest.

## Что нужно знать до начала

- **Vitest запускается ТОЛЬКО через npm:** `npm test -- <путь>`. Прямой `npx vitest run` в этом
  проекте падает.
- **Полный прогон (`npm test` без пути) не запускать** без явного разрешения владельца: он
  занимает около восьми минут и забирает машину.
- **Приёмка в браузере обязательна** на обоих экранах, в светлой и тёмной теме, и сверяется с
  эскизами выше. Учётка для приёмки — `acceptance@local.test`.
- **UI собирается только из компонентов ui-kit.** Не хватает компонента или пропа — правится
  `vendor/ui-kit`, а не обходится локально.
- **Дев-БД общая для всех worktree.** Разрушительные миграции применяются руками и осознанно.

## Э1. Единый источник наблюдений

**Что делаем:** заводим один серверный слой, который отвечает на вопрос «какие прохождения есть по
этим условиям», и переводим на него ВСЕ ручки аналитики. Интерфейс при этом не меняется — меняются
числа на странице теста, потому что она начинает видеть прохождения из LMS.

**Архитектура:** новый модуль `server/services/analytics/observations.ts`. Тип `Observation` —
одна запись прохождения независимо от источника: участник (пользователь либо псевдоним PRD-54),
тест, версия публикации, вариант выдачи, дата, длительность, результат, исход, источник
(`web` / `telemetry` / `import`), группы участника. Функция `loadObservations(filter, scope)`
читает веб-попытки и строки телеметрии с импортом, приводит их к `Observation`, применяет область
видимости и возвращает отсортированный список с общим числом. Ручки перестают знать, откуда
берутся данные.

**Почему первым:** пока источники разные, любая новая величина считается по неполным данным, а
FR-25 объявляет расхождение чисел между экранами дефектом.

## Риски

- **Числа на странице теста изменятся** сразу после Э1 — это и есть починка дефекта, но владельца
  стоит предупредить до выката: у тестов, которые проходят в LMS, вырастут и объём выборки, и
  средние.
- **Выборка на стороне БД** меняет поведение при больших объёмах; интеграционные тесты на pglite
  обязаны покрывать лимит, смещение и сортировку, иначе ленивая подгрузка Э2 встанет на неверном
  фундаменте.
- **`analyticsScope`** сейчас строит множество доступных тестов в памяти; при переносе фильтрации
  в БД область видимости должна попасть в условие запроса, а не остаться постфильтром — иначе
  лимит будет отсчитываться до отсечения недоступного.
