# План: перенос теста между инсталляциями без потерь

Дата: 2026-08-11. Ветка: `test-transfer-without-losses` (от локального `main`). Статус: НА
СОГЛАСОВАНИИ.

Повод: тест «Определение ведущего стиля человекоцентричного лидерства» выгружен книгой из
dev и загружен в прод. В проде показатель напечатал `vdo` — сырой ключ шкалы вместо названия
стиля, диаграммы нет, встал дефолтный порог 70%.

Эскиз нужен только на одну кнопку в меню действий теста (раздел 3, срез E); остальное —
серверный формат и приёмка.

## 1. Что проверено по коду 2026-08-11

Книга Excel пишет девять листов (`server/routes/tests-workbook.ts:217-225`). При импорте
тест создаётся с `flowPolicyJson`, `status` и содержимым листа «Настройки»
(`server/services/workbook-import.ts:727-739`), а лист «Настройки» знает РОВНО ОДИН
параметр — порядок выдачи вопросов (`server/utils/workbook-sheets.ts:695-708`).

Отсюда перечень того, что перенос теряет.

| Что теряется | Где живёт | Видимое следствие |
| --- | --- | --- |
| Исходы показателей | `result_variables.config_json` | печатается сырое значение формулы |
| Правило прохождения | `tests.overall_pass_rule_json` | дефолтный порог 70% |
| Вводный блок итогов | `tests.intro_json` | нет |
| Оформление, вид диаграммы | `tests.design_settings_json` | нет розы |
| Настройки отчёта | `tests.report_settings_json` | нет |
| Описание, обратная связь, стартовая страница | `description`, `feedback_json`, `start_page_content` | нет |
| Время, попытки, кулдаун, показ ответов | `time_limit_minutes`, `max_attempts`, `retake_policy_json`, `show_correct_answers` | дефолты |
| Навигация PRD-19 | пять полей `allow_*`/`quick_advance`/`show_section_results`/`skip_review_when_complete` | дефолты |
| Защита PRD-34 | `copy_protection`, `protection_watermark`, `protection_hide_on_blur` | дефолты |
| Поля раздела | `feedback_json`, `time_limit_minutes`, `draw_all` | нет |
| Контентные страницы | таблица `content_pages` | листа нет вовсе |
| Медиа вопросов и вложения | `media_assets`, ссылки `/api/media/<id>` | битые ссылки |

Почему это не поймала правка 2026-08-08. План
`docs/plans/2026-08-08-workbook-scale-interpretation.md:36-38` записал: «ПОКАЗАТЕЛЬ ведёт
себя иначе и правильно: `parseResultVariableRow` не кладёт `configJson` вовсе, поэтому
частичное обновление не трогает сохранённую интерпретацию». Вывод верен только для
ОБНОВЛЕНИЯ существующей записи, то есть для круга на одной базе. При переносе запись
создаётся с нуля, сливать не с чем, и «не кладёт» означает «не переносит». Приёмка того
плана — круг «выгрузил → загрузил» на одной БД — к этому сценарию слепа по построению.

Хорошая новость: полная сериализация теста в проекте уже есть. `TestSnapshotContent`
(`server/services/test-snapshot.ts:50-73`) несёт `test` целиком, разделы, темы, пул
вопросов, адаптивную конфигурацию, шкалы, вклады, показатели, контентные страницы и
переопределения оценки. Собирает её `buildSnapshotContent`. Изобретать формат не нужно.

## 2. Решения, которые нельзя пересматривать

1. **Полнота обеспечивается построением, а не перечислением.** Пакет сериализует строку
   таблицы ЦЕЛИКОМ. Новое поле попадает в перенос само; забыть его можно только удалив
   поле из строки.
2. **Книга остаётся форматом СОДЕРЖАНИЯ.** Она не станет форматом переноса: `design_settings_json`
   и `report_settings_json` в ячейках Excel не выражаются без уродства, а каждое новое поле
   требовало бы ручной колонки — ровно тот механизм, который уже отказал.
3. **Критерий приёмки — перенос в ЧИСТУЮ базу, а не круг на одной.** Круг на одной базе
   проходит даже тогда, когда пакет не несёт ничего: значения на месте, потому что их никто
   не трогал. Этот критерий и пропустил дефект.
4. **Гард полноты обязателен.** Тест сверяет список колонок таблицы со списком полей,
   которые пакет сознательно НЕ переносит. Появилась колонка — тест падает и требует
   решения. Без гарда правило 1 держится на внимательности.
5. **Медиа — часть пакета.** Иначе перенос «без потерь» отдаёт битые картинки, и мы
   повторяем ту же ошибку в другом слое.

## 3. Порядок работ

> применён к проду и после этого удалён — его работу выполняет штатный импорт. Подробности
> и отступления — в плане реализации `docs/plans/2026-08-12-prd48-selective-import.md`,

### Срез 0 — расшить прод сегодня

ВЫПОЛНЕН 2026-08-11. `scripts/db/transfer-test-settings.ts`: одноразовый перенос по двум
строкам подключения (`SOURCE_DATABASE_URL`, `TARGET_DATABASE_URL`) для ОДНОГО теста,
сопоставление по ключам, а не по идентификаторам: показатели по `name`, страницы по
`kind` + `sort_order`. Переносит `result_variables.config_json`, `tests.intro_json`,
`design_settings_json`, `report_settings_json`, `overall_pass_rule_json`. Скрипт живёт до
среза C, потом удаляется.

Два отступления от буквы плана, оба по ходу приёмки:

1. **Добавлены контентные страницы** (`content_pages`: `values_json`, `settings_json`,
   `template_key`, `auto_advance`, `auto_advance_delay_ms`). Первоначальный перечень их не
   называл, а именно там живёт конфигурация экрана итогов: `scalesChartKind: "rose"`, цвета
   и иконки шкал и `scoreSummary: "hide"`. Без них расшивка вернула бы тексты, но оставила
   экран без диаграммы и с ложной сводкой «0 из 0, порог 70%, Пройден». Настройки ОТЧЁТА
   (`tests.report_settings_json`) — отдельное место, переносятся независимо.
2. **Запись требует `--apply`, сухой прогон стал умолчанием.** План предполагал обратное
   (`--dry` для сухого прогона). Скрипт направляют на прод, и забытый флаг не должен
   означать запись.

Скрипт только ОБНОВЛЯЕТ существующие записи. Запись, которой на приёмнике нет, даёт
предупреждение и пропускается: создание — это перенос содержания, задача среза B/C.

**ГОЧА `sort_order` СТРАНИЦ.** Первая редакция сопоставляла страницы по `kind` + `sort_order`
и на настоящем проде не нашла НИ ОДНОЙ, кроме случайно совпавшей: импорт книгой оставляет
все страницы с `sort_order = 0`, а редактор расставляет их 0/2/4/6. Порядок — не
идентичность. Системная страница уникальна по ВИДУ в пределах теста, поэтому пара ищется по
`kind`, и лишь когда страниц такого вида несколько (авторские `content`), группа
доразбирается по `sort_order`. Цена ошибки была бы велика и тиха: скрипт отчитался бы об
успехе, перенеся тексты и не перенеся конфигурацию экрана итогов — то самое, ради чего
страницы и добавлялись.

Приёмка выполнена на настоящих данных: временная база в dev-кластере, тест ЧИЛ с ДРУГИМИ
идентификаторами теста, показателей и страниц и обнулёнными jsonb. Результат: 7 расхождений
найдено и применено, повторный прогон даёт ноль (идемпотентность), md5 всех перенесённых
документов совпадает с источником, скалярные колонки переносятся без лишнего экранирования.

### Срез A — формат пакета и экспорт

ВЫПОЛНЕН 2026-08-12.

1. `server/services/test-transfer/package.ts`: тип `TestTransferPackage` = `formatVersion` +
   `TestSnapshotContent` + манифест медиа (`address`, `path`, `checksum`, `mimeType`,
   `originalName`) + `missingMedia`.
2. `server/services/test-transfer/export.ts`: собирает пакет через `buildSnapshotContent`,
   складывает `test.json` и `media/<checksum><ext>` в zip. Расширение `.tbtest`.
3. Роут `GET /api/tests/:id/transfer`, отдельный роутер `server/routes/test-transfer.ts`.

Три отступления от буквы плана:

1. **Типы остались на сервере, а не в `shared/transfer/`.** Пакет собирает и читает только
   сервер (клиент жмёт кнопку), а `TestSnapshotContent` — серверный тип; ради размещения
   пришлось бы перетаскивать чужой модуль в `shared/` без выигрыша.
2. **Права — как у экспорта КНИГИ (`tests.read` + read-scope), а не как у SCORM.** Пакет не
   раскрывает ничего сверх того, что книга уже отдаёт тому же читателю, а
   `tests.export.scorm` — право developer-роли, и оно лишило бы автора возможности перенести
   собственный тест.
3. **Адрес медиа в манифесте хранится ВЕРБАТИМ**, а не переписывается на путь внутри пакета
   (как делает упаковщик SCORM). Импорту нужно знать исходное написание, чтобы найти все
   вхождения и переписать их на новый идентификатор; переписав дважды, мы потеряли бы ключ
   сопоставления.

Приёмка: 5 модульных тестов (писались до реализации), сборка из ЖИВОЙ dev-базы на двух
тестах — ЧИЛ (исходы 4+4, `scalesChartKind: rose`, `scoreSummary: hide`, вводный блок и
настройки отчёта на месте) и «PRD-38 приёмка композиции медиа» (3 файла, включая `.wav`;
sha256 распакованных файлов совпал с манифестом) — и живой HTTP-запрос к роуту:
`200 application/zip`, имя `*.tbtest`, содержимое совпало с локальной сборкой.

### Срез B — импорт с созданием нового теста

ВЫПОЛНЕН 2026-08-12. `services/test-transfer/plan.ts` (перенумерация, чистая),
`services/test-transfer/import.ts` (три прохода: медиа -> перенумерация -> запись),
`storage/test-transfer-repository.ts` (запись одной транзакцией, метод `writeImportedTest`
в `IStorage`), роут `POST /api/tests/transfer` под правом `tests.create`.

Решение, которое нельзя пересматривать: **перенумерация — СПЛОШНОЙ обход, а не список
полей.** План собирает исходные идентификаторы всех сущностей и заменяет любую строку,
равную одному из них, — и значения, и КЛЮЧИ объектов. Список «полей со ссылками» пришлось
бы поддерживать, и забытое поле указывало бы на чужой идентификатор: импорт успешен, тест
молча сломан. Сплошной обход уже ловит ссылки, которых схема не объявляет:
`form_set_json.forms[].questionIds` и идентификаторы тем в КЛЮЧАХ `questionsByTopic`.

Что сознательно НЕ перенумеровывается: всё, что адресуется по КЛЮЧУ. Формула показателя
зовёт шкалы по `key` (`topScale(['vdo'],1)`), оформление шкал на странице итогов ключуется
по ключу шкалы, тема в формулах зовётся по `code`. Перенумеровать их значило бы сломать
ровно те формулы, ради которых перенос и делается.

Коллизия имени темы: `(owner_id, name_normalized)` уникален, поэтому импортирующий не может
получить вторую тему с тем же именем. Тема ПЕРЕИМЕНОВЫВАЕТСЯ (« (импорт N)») и это попадает
в отчёт; молча присоединять к существующей теме нельзя — вопросы уехали бы в содержание,
которого автор не выбирал.

Строки в БД пишутся ЦЕЛИКОМ, а не по перечню колонок (единственное исключение — метки
времени, их ставит база). Перечень — та самая привычка, которая теряет новую колонку.

Приёмка: 18 модульных тестов (перенумерация, экспорт, круг «экспорт -> zip -> импорт») плюс
живой круг по HTTP на dev: экспорт ЧИЛ -> `POST /api/tests/transfer` -> `201`. Импортировано
14 вопросов, 4 шкалы, 56 вкладов, 5 показателей, 4 страницы; md5 `lead_style.config_json`,
`intro_json` и `report_settings_json` совпали с источником; `scalesChartKind: rose` и
`scoreSummary: hide` на месте; пересечение идентификаторов вопросов с источником — ПУСТО;
битых ссылок во вкладах — ноль; тема переименована в «… (импорт 2)».

1. `server/services/test-transfer/import.ts`: разбор пакета, проверка `formatVersion`,
   ремап ВСЕХ идентификаторов на новые (тест, разделы, темы, вопросы, шкалы, показатели,
   страницы, уровни адаптивности) с сохранением ссылочной целостности графа.
2. Темы: по умолчанию создаются новые, владелец — импортирующий, видимость `private`.
   Привязка к существующей теме по `name_normalized` — отдельным флагом, не умолчанием:
   молча присоединиться к чужой теме опаснее, чем создать свою.
3. Медиа: по `checksum` ищем в `media_assets` приёмника, найденное переиспользуем, остальное
   заливаем; ссылки `/api/media/<id>` в текстах переписываются на новые идентификаторы.
4. Транзакция на всю запись: пакет применяется целиком или не применяется вовсе.

### Срез C — импорт в существующий тест

Режим «обновить»: тот же разбор, но ремап опирается на ключи (`scales.key`,
`result_variables.name`, вопросы по содержательному хешу), а не на создание. Этим же
режимом штатно расшивается прод — срез 0 после этого удаляется.

### Срез D — лист «Исходы показателей» в книге

Новый лист: «Показатель», «Код», «Метка», «Текст», «Тональность». Читается и пишется по тем
же правилам, что «Шкалы»: колонка есть — книга задаёт поле целиком, колонки нет — не трогает

### Срез E — кнопки в интерфейсе

### Срез F — гард полноты и приёмка

ВЫПОЛНЕН 2026-08-12.

`server/__tests__/test-transfer-completeness.test.ts` — гард. Перебирает ВСЕ таблицы
drizzle-схемы, у которых есть `test_id`, и требует, чтобы каждая была либо в списке
переносимых, либо в списке сознательно исключённых С ПРИЧИНОЙ. Новая таблица, привязанная к
тесту, роняет тест — то есть решение «везём или нет» принимается сейчас, а не после
импорта в прод. Это единственное место, где список остался необходим: какие таблицы
принадлежат тесту, из строки не вывести.

`tests/it/test-transfer.it.test.ts` — приёмка в ЧИСТУЮ базу на pglite: тест создаётся,
экспортируется, база ОЧИЩАЕТСЯ, пакет импортируется в пустую, затем сверка ПОЛЕ В ПОЛЕ
(игнорируются только идентификаторы, метки времени и принадлежность инсталляции). Плюс два
случая: владельцем становится импортирующий и импорт откатывается ЦЕЛИКОМ при ошибке записи
(проверено пакетом с дублирующимся идентификатором темы — в базе не осталось ни теста, ни
темы).

Оба гарда проверены на ФАЛЬСИФИЦИРУЕМОСТЬ, иначе зелёный цвет ничего не значит:

- убранная из списка `content_pages` роняет гард с внятным сообщением о таблице;
- убранная из записи вставка `result_variables` роняет сверку с `resultVariables: []` —
  ровно тот дефект, который и случился в проде.

Попутно закрыт долг: `tests/it/schema.sql` отставал от `shared/schema.ts` на две колонки
(`intro_json`, `skip_review_when_complete`) — стенд не мог принять тест с вводным блоком.
Регенерирован штатной командой из шапки `db-harness.ts`.

1. Тест-гард: перечень колонок `tests`, `test_sections`, `scales`, `result_variables`,
   `content_pages`, `questions` против явного списка «переносится / сознательно не
   переносится» (`id`, `created_at`, `owner_id` и прочее, что принадлежит инсталляции).
2. Приёмочный тест на pglite: пакет из полностью заполненного теста разворачивается в
   ЧИСТУЮ базу, затем сверяется поле в поле, кроме идентификаторов и меток времени.
3. Приёмка вручную: перенос теста ЧИЛ dev → чистая база → отладочный плеер печатает
   название стиля, характеристику, рекомендации и розу.

## 4. Что остаётся за рамками

- Перенос попыток, назначений и телеметрии: это данные инсталляции, а не тест.
- Перенос прав доступа (`test_access_grants`): учётные записи на приёмнике другие.
- Дизайн-шаблон переносится идентификатором и версией; отсутствующий на приёмнике шаблон —
  ошибка импорта с внятным текстом, а не молчаливая подстановка `default`.

## 5. Риски

- Ремап идентификаторов в ТЕКСТАХ (ссылки на медиа, формулы показателей, ссылки на темы по
  коду) — самое вероятное место потерь. Каждый вид ссылки нуждается в отдельном тесте.
- Формулы показателей адресуют шкалы по ключу, а темы — по `topics.code` (PRD-2). Коллизия
  кода темы на приёмнике должна давать ошибку импорта, а не тихую переадресацию.
