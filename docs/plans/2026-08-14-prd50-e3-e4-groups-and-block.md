# PRD-50 Э3 и Э4: группы разделов, надписи вердикта, блок разреза по тесту

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task.
> Steps use checkbox (`- [ ]`) syntax for tracking.

**Требования:** [спека PRD-50](../specs/prd-50/result-breakdowns.md) — Э3: FR-11, FR-12,
FR-24 - FR-27, FR-29, FR-34, FR-43; Э4: FR-28 полностью, FR-44 в части блока области теста.

**Ветка:** отдельная от `prd-50-result-breakdowns`, ответвлять после вливания Э2.

**Goal:** дать автору двухблочную структуру итогов со счётчиком «пройдено N из M», свою
терминологию вместо зашитых «Пройдено»/«Не пройдено» и сводный блок разреза поверх разделов.

**Architecture:** оба этапа правят ОДИН контракт контекста и ОДНИ и те же две раскладки в двух
шаблонах, поэтому делаются подряд одной веткой: разнесённые во времени, они дважды заставят
пересобирать предпросмотры и дважды прогонять гард паритета шаблонов.

---

## Почему этот план крупнее по шагу, чем планы Э1 и Э2

Планы Э1 и Э2 расписаны построчно, с готовым кодом в каждом шаге. Здесь шаг задачи — файл и
проверка, а не строка. Причина одна и честная: обе задачи стоят на решениях Э2, которых пока нет
в коде.

- Счётчик группы (FR-26) считает разделы с ВЫНЕСЕННЫМ вердиктом. После Э2 вердикт темы зависит
  ещё и от порогов ключей, и знаменатель счётчика придётся брать из той же функции, которую Э2
  перепишет (`aggregateStandardResult`, перестановка порядка «вердикт темы — разрезы»).
- Строка разреза к Э4 уже несёт поля вердикта (`passed`, `passClass`, `statusLabel`, §8.1
  «с Э2»), и блок области теста обязан печатать их тем же способом, что карточка темы.

Писать сейчас построчный код против ещё не существующих сигнатур — это выдумывать, а потом
править. Задачи ниже полны по составу и по приёмке; шаги внутри задачи расписываются перед её
исполнением, когда Э2 влит.

## Э3

### Задача 1: хранение групп

- [ ] `tests.section_groups_json` — упорядоченный список `{ key, label, order }`;
      `test_sections.group_key` — необязательная ссылка (FR-11).
- [ ] Ссылка на несуществующий ключ трактуется как отсутствие группы, пустая группа не
      печатается (FR-12). Это правило проверяется тестом, а не комментарием.
- [ ] Миграция генерируется `npx drizzle-kit generate`, НЕ применяется: деплой применяет
      миграции сам (`scripts/deploy/deploy.sh`, одноразовый контейнер до старта приложения).
- [ ] Имя файла миграции — описательное, по образцу `0019_prd50_breakdown_display.sql`.

**Приёмка:** тест без групп даёт ровно прежний контекст (решение 6 спеки).

### Задача 2: счётчики группы в ядре

- [ ] `passedCount` — разделы группы с пройденным вердиктом, `totalCount` — разделы с
      ВЫНЕСЕННЫМ вердиктом; раздел без вердикта в знаменатель не входит (FR-26).
- [ ] Считает ядро, а не шаблон и не автор формулой.
- [ ] Разделы без группы печатаются после всех групп в своём порядке (FR-25).

**Зависимость от Э2:** брать вердикт темы из результата агрегата ПОСЛЕ того, как Э2 переставит
в нём порядок «вердикт темы — разрезы». Если Э2 ещё не влит, задача блокируется.

### Задача 3: `result.topicGroups` в контексте

- [ ] Имя именно `topicGroups`: `result.blocks` занято списком блоков итогов PRD-49 (FR-29).
- [ ] Поля: `key`, `label`, `topics[]`, `passedCount`, `totalCount`, `counterLabel`.
- [ ] `counterLabel` готовит ядро по формату надписи `group.counter` (см. задачу 4).
- [ ] Отсутствие групп = сегодняшний плоский список карточек (FR-27).

### Задача 4: надписи вердикта темы

- [ ] Новые ключи в существующем словаре PRD-49: `topic.verdict.passed`, `topic.verdict.failed`,
      `topic.verdict.unknown`, `group.counter` (формат вида `{passed} / {total}`), `results.breakdown`.
- [ ] Умолчания объявляет манифест шаблона, тест хранит только отклонения
      (`design_settings_json.labels`), выключение — тумблером. Механизм есть, нужны ключи.
- [ ] Зашитые строки уходят из кода: `shared/template/result-context.ts:664`
      («Пройдено»/«Не пройдено») и `:835` («Пройден»/«Не пройден» у адаптивной карточки).
- [ ] Оба поставляемых шаблона объявляют новые надписи в своих манифестах — иначе новый гард
      паритета настроек покраснеет, и правильно сделает.

**Приёмка:** тест, где автор не трогал надписи, печатает те же слова, что и до этапа.

### Задача 5: редактор — поле «блок» у раздела

- [ ] Список блоков теста редактируется рядом со структурой; у раздела появляется выбор блока.
- [ ] Только компоненты дизайн-системы `@skillum/ui-kit`; рукописных `ou-*` и Tailwind нет.
- [ ] Значение проходит в тело `PUT /api/tests/:id` и через белый список
      `server/services/test-settings.ts` — без последнего сервер молча отбросит поле.

### Задача 6: вёрстка групп в обоих шаблонах

- [ ] Заголовок группы и счётчик в `results.html` и `report.html` «Стандартного».
- [ ] То же в «Сертификации»: гард `tests/template-layout-parity.test.ts` требует побайтового
      совпадения раскладок и сверяет наборы селекторов стилей.
- [ ] Предпросмотры пересобираются `npm run scorm:previews`, руками `preview.html` не правится.

## Э4

### Задача 7: блок разреза по области теста

- [ ] Новый ключ `breakdown` в `ResultsBlockKey` (`shared/template/results-order.ts:13`) и в
      `DEFAULT_BLOCK_ORDER` (там же, строка 16).
- [ ] Ключ объявляется в `resultsBlockOrder` манифестов ОБОИХ поставляемых шаблонов.
- [ ] Заголовок блока — надпись `results.breakdown` из словаря PRD-49.
- [ ] Шаблон, не знающий ключа, блок не печатает и не ломается (FR-30) — это уже верно по
      построению, но должно быть закреплено тестом на стороннем манифесте.

### Задача 8: данные блока

- [ ] Записи области теста берутся из сохранённого результата, а не пересчитываются. Их
      сохранение — задача этапа «Э1-доделка» (FR-39); если он не влит, Э4 блокируется.
- [ ] Записи с одинаковым ключом из разных разделов в области теста уже сведены ядром
      (FR-04): блок печатает их как есть и НЕ пересуммирует.
- [ ] Управление показом блока — там же, где видимость разреза (FR-44), отдельным положением,
      чтобы автор мог включить вложенные полосы без сводного блока и наоборот.

### Задача 9: вёрстка блока в обоих шаблонах

- [ ] Блок в `results.html` и `report.html` обоих шаблонов, классы одинаковые.
- [ ] Группировка внутри блока по разделам — опция раскладки, не ядра: ключ, живущий в двух
      разделах, обязан быть виден и как одна сводная строка.
- [ ] Предпросмотры пересобираются генератором.

## Что этими этапами НЕ закрывается

- Дерево групп: уровень ровно один (FR-24), и это решение спеки, а не упрощение плана.
- Гейт в области теста: его нет и не планируется — тестовый вердикт выражается показателем с
  «Управляет статусом» (решение 7 спеки).
- Срок годности результата, нормирование порогов по пилотной выборке, повторение вёрстки
  референса — за границей PRD (§12).
