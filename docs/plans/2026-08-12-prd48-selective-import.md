# PRD-48. Выборочный импорт теста: план реализации

> Для исполнителя: задачи идут по порядку, каждая заканчивается зелёными тестами и коммитом.
> Шаги помечены чек-боксами. Спека — `docs/specs/prd-48/test-transfer.md`, эскиз формы —
> `.playwright-mcp/wf-transfer-import.html`.

**Цель:** автор выбирает, какие части переносимого теста принять, и видит перечень удаляемого
до того, как что-либо запишется.

**Подход:** три шага (`inspect` -> `plan` -> `apply`) поверх готового формата `.tbtest`.
Вся логика решений — в ЧИСТОЙ функции `diff`, поэтому проверяется таблицей случаев без базы.
Сопоставление сущностей — по идентификаторам, что требует сначала перевести импорт на
сохранение исходных id.

**Стек:** TypeScript, Express, Drizzle, vitest (модульные) + pglite (`npm run test:it`),
дизайн-система `@universityrt/ui-kit`.

## Задача 1. Импорт сохраняет исходные идентификаторы — ВЫПОЛНЕНА 2026-08-12

Сделано: `services/test-transfer/identity.ts` (`makeIdentityResolver`, `buildIdMap`),
`plan.ts` принимает готовую `idMap` и экспортирует `collectSourceIds`, `import.ts` получил
`takenIds`. Тесты: `test-transfer-identity.test.ts` (6) + два сквозных случая в
`test-transfer-roundtrip.test.ts`. Всего по переносу 30 модульных тестов, зелёные.

Отступление от буквы плана: занятые идентификаторы приходят в импорт ДАННЫМИ
(`takenIds: Set<string>`), а не портом-функцией. Вызывающий, который знает приёмник, всё
равно читает его состояние для `diff` — второй, построчный опрос базы был бы и медленнее, и
вторым источником правды. Пока `takenIds` не передан, импорт работает как прежде (режим
копии), поэтому существующее поведение не сломано.

Ниже — исходный текст задачи.

Без неё «тот же вопрос» опознать нечем: сейчас `plan.ts` перенумеровывает всегда.

**Файлы:** создать `server/services/test-transfer/identity.ts`, изменить `plan.ts`,
`import.ts`; тест — `server/__tests__/test-transfer-identity.test.ts`.

- [ ] **Шаг 1.** Написать падающий тест: пакет с `id: "src-q"`, в приёмнике такого id нет —
  запись создаётся С ТЕМ ЖЕ id; тот же id занят ЧУЖОЙ сущностью — выдаётся новый и попадает
  в отчёт как `remapped`.

```ts
it("keeps the source id when it is free", async () => {
  const resolve = makeIdentityResolver({ taken: new Set() });
  expect(await resolve("src-q")).toEqual({ id: "src-q", remapped: false });
});

it("issues a new id when the source one belongs to something else", async () => {
  const resolve = makeIdentityResolver({ taken: new Set(["src-q"]) });
  const r = await resolve("src-q");
  expect(r.id).not.toBe("src-q");
  expect(r.remapped).toBe(true);
});
```

## Задача 3. Ядро решений (`diff`) — ВЫПОЛНЕНА 2026-08-12

Сделано: `diff.ts` (`diffTransfer`, `TargetSnapshot`, `TransferOptions`,
`TEST_FIELDS_BY_PART`), тест `test-transfer-diff.test.ts` (11 случаев), правило свободного
имени темы вынесено в `shared/topics/naming.freeTopicName`. Коммит `5d6de83b`.

Четыре решения приняты сверх буквы спеки — они видны в перечне операций до применения, но
их стоит подтвердить:

1. **Строка теста пишется частями.** В `tests` пишут три части сразу, поэтому у операции
   появилось поле `omitFields`: снятая часть «Оценивание» удерживает
   `overallPassRuleJson`/`defaultQuestionPoints`, снятые «Итоги и оформление» —
   `introJson`/`designSettingsJson`/`reportSettingsJson`. Всё не перечисленное едет по
   умолчанию, поэтому новая колонка не теряется.
2. **Лишний раздел приёмника удаляется** при взятой части «Структура и вопросы»: состав
   теста сходится к пакету, иначе перенесённый тест отличается от источника. Удаление
   показывается в плане, как и всякое другое.
3. **Запасное сопоставление по ручке автора.** По идентификатору — первично; если его нет
   (тест собран руками), шкала ищется по `key`, показатель по `name`, страница по `kind`
   (и только когда вид на приёмнике один — `sort_order` идентичностью не является), вклад по
   паре «вопрос+шкала», переопределение оценки по вопросу. Вопрос — только по
   идентификатору.
4. **Политика «создать новую тему» выдаёт новые идентификаторы и вопросам** этой темы:
   исходные заняты темой, которую автор решил не трогать.

У операции появилось поле `sourceId` (строка пакета, из которой берётся содержимое) — при
сопоставлении по ручке идентификаторы источника и приёмника разные, и `apply` без этого не
знает, что куда писать.

Ниже — исходный текст задачи.

**Файлы:** создать `diff.ts`; тест — `test-transfer-diff.test.ts`.

- [ ] **Шаг 1.** Тест-таблица. Обязательные случаи:
  - часть выключена -> операций по ней НЕТ вовсе;
  - `upsert` шкал: совпавшая по `key` обновляется, отсутствующая создаётся, лишняя НЕ
    трогается;
  - `replace` шкал: лишняя попадает в `delete`;
  - тема «обновить и долить»: вопрос, совпавший ПО ИДЕНТИФИКАТОРУ, обновляется; которого нет
    — создаётся; лишний в теме остаётся;
  - тема «полная замена»: лишний вопрос темы попадает в `delete`;
  - тема «создать новую»: операций по существующей теме НЕТ, создаётся новая с другим
    названием;
  - «Итоги и оформление» и «Медиа» не порождают `delete` НИКОГДА.
- [ ] **Шаг 2.** Прогнать, убедиться в падении.
- [ ] **Шаг 3.** Реализовать сигнатуру:


## Риски

1. **Сопоставление по id ломается, если тест на приёмнике собран вручную, а не импортом.**
   Тогда идентификаторы не совпадут ни с чем и всё уедет в «создать». Форма обязана показать
   это честно: 32 создания вместо 32 обновлений — видимый сигнал, что выбран не тот тест.
2. **Удаление вопроса с историей попыток.** `diff` помечает такие операции
   (`usedInAttempts`), форма показывает отдельно. Запрета нет — решение за автором.
3. **Пересчёт плана на каждый чих.** Пакет уже разобран и лежит в памяти по токену, так что
   пересчёт — чистая функция над снимком; в базу на этом шаге не ходить.
4. **Права темы проверять на сервере.** Спрятать вариант в интерфейсе недостаточно: `apply`
   обязан отвечать `403` независимо от того, что прислал клиент.
