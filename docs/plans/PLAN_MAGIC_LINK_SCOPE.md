# План: область действия ссылки-приглашения (magic link)

Статус: предложен, не согласован. Дата: 2026-07-29.
Область: `server/routes/access.ts`, `server/routes/assignments.ts`,
`assignment_access_tokens`, сессия Express.

## 1. Что обнаружено

Ссылка, которая уходит учащемуся в письме о назначении теста
(`/access/<token>`), выполняет полноценный вход: обработчик ставит
`req.session.userId = record.userId` и перенаправляет на тест. Сессия ничем не
помечена и неотличима от входа по паролю.

Обнаружено при разборе обращения: получатель ссылки обрезал у неё хвост
`learner/test/<id>` и оказался в кабинете этого пользователя.

### 1.1. Что сделано правильно и менять не нужно

- токен — 32 случайных байта, в БД хранится только SHA-256;
- редирект уводит токен из адресной строки сразу после погашения;
- при перевыпуске ссылки прежние токены этого пользователя по этому назначению
  отзываются;
- cookie сессии: `httpOnly`, `sameSite=lax`, `secure` в проде, срок 24 часа.

### 1.2. Дефекты

| Ном. | Дефект | Следствие |
| --- | --- | --- |
| D-1 | Сессия по ссылке не ограничена ни тестом, ни назначением | Ссылка даёт весь личный кабинет пользователя, а не один тест |
| D-2 | Токен многоразовый: при погашении не выставляется ни `revoked_at`, ни `used_at` (колонки `used_at` в таблице нет) | Ссылка работает произвольное число раз до истечения срока |
| D-3 | Срок жизни по умолчанию — 30 дней либо до `due_date` | Эквивалент пароля живёт месяц; текст ошибки при этом уже обещает пользователю «возможно, она уже была использована» |
| D-4 | Назначение можно сделать на группу, ссылка выдаётся каждому участнику независимо от его ролей | Если в группе есть автор, менеджер или администратор — ссылка даёт вход в привилегированный аккаунт в обход пароля |
| D-5 | Погашение логируется без IP и User-Agent, отзыв ссылки не выведен в интерфейс | Скомпрометированную ссылку нечем расследовать и трудно погасить |

D-4 требует проверки на проде до начала работ: если ни одного назначения на
группу с непривилегированными участниками нет, приоритет ниже.

## 2. Целевое правило

Ссылка-приглашение — не вход в систему, а доступ к одному назначению.
Всё, что выходит за прохождение указанного теста, требует обычной
аутентификации.

## 3. Этапы

### Этап 1. Ограничить область сессии (закрывает D-1)

1. В сессию наряду с `userId` писать происхождение:
   `session.magic = { assignmentId, testId }`. Обычный вход по паролю поле не
   ставит; наличие поля — признак ограниченной сессии.
2. Guard в цепочке middleware: при наличии `session.magic` пропускать только
   - `GET /api/learner/tests` — ответ отфильтрован до одного `testId`;
   - `GET /api/tests/<testId>/screen-template/*`;
   - старт попытки, сохранение ответов, возобновление, завершение и результат
     ЭТОЙ попытки;
   - выход из системы;
   остальное — `403` с кодом `MAGIC_SCOPE`.
3. Клиент: по коду `MAGIC_SCOPE` показывает экран «Ссылка открывает только этот
   тест. Для остального войдите по паролю» со ссылкой на страницу входа.
4. Смена пароля, почты и любые операции с профилем недоступны ограниченной
   сессии независимо от списка выше.

Тесты: запрос вне области отдаёт 403; прохождение теста внутри области проходит
целиком; обычный вход по паролю областью не ограничен.

### Этап 2. Одноразовость и срок (закрывает D-2, D-3)

1. Миграция: колонка `used_at` в `assignment_access_tokens`.
2. Погашение отмечает токен использованным.
3. Срок по умолчанию — 24-72 часа вместо 30 дней. `due_date` остаётся сроком
   сдачи и перестаёт быть сроком жизни ссылки.
4. Перевыпуск: на странице «ссылка недействительна» — кнопка «прислать новую
   ссылку» (письмо на тот же адрес), чтобы сокращение срока не превратилось в
   поток обращений к администратору.

Развилка, требующая решения заказчика: строгая одноразовость ломает сценарий
«закрыл вкладку — вернулся по той же ссылке». Варианты:

- а) токен обменивается на сессию один раз, возврат — обычным входом;
- б) повторное погашение разрешено в пределах срока, но только с того же
  User-Agent и IP.

Вариант (а) строже и проще; (б) мягче к пользователю. По умолчанию предлагается
(а).

### Этап 3. Не выдавать вход по ссылке привилегированным аккаунтам (D-4)

Если у получателя есть любая роль, кроме `learner`, письмо о назначении уходит
без токена — с обычной ссылкой на страницу входа.

### Этап 4. Гигиена и наблюдаемость (D-5)

1. На `/access/:token` — заголовки `Referrer-Policy: no-referrer` и
   `Cache-Control: no-store`.
2. В запись о погашении добавить IP и User-Agent (сырой токен не логировать
   никогда).
3. В интерфейсе назначений — кнопка «отозвать ссылку» (серверный отзыв уже
   реализован).

## 4. Порядок

Этап 1 закрывает найденную дыру и делает остальные дефекты менее опасными,
поэтому идёт первым. Этап 3 — второй: он дёшев и снимает риск эскалации.
Этапы 2 и 4 — после согласования развилки из этапа 2.
