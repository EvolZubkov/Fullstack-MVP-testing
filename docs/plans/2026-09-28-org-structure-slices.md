# Оргструктура: поля профиля и срезы аналитики — план работ

> **Для исполнителя:** задачи выполняются по одной, сверху вниз, в режиме TDD: сначала падающий
> тест, потом минимальная реализация, потом прогон, потом коммит. Шаги отмечены чекбоксами
> (`- [ ]`). Эскизы согласованы 2026-09-28; код пишется после согласования плана.

**Цель:** дать аналитике оси «Организация», «Подразделение» и «Должность» — в срезах, в фильтре
реестра и в выгрузке. Для этого сначала дать этим полям жизнь в профиле пользователя: сегодня
колонки в базе есть, а заполнить их нечем.

**Спецификации:** [PRD-56 FR-06b и OQ-04](../specs/prd-56/analytics-rework.md) (поправка
2026-09-28), [PRD-54 BR-54-28 - BR-54-30](../specs/prd-54/lms-export-import.md).
**Эскизы (согласованы 2026-09-28):** [страница «Пользователи»](../wireframes/approved/org-users-profile.html);
[раздел «Аналитика»](../wireframes/prd56-analytics-section.html), состояния `slices-unit` и
`filter-org` (группа «Оргструктура» в переключателе).

## Что нужно знать до начала

- **Vitest только через npm:** `npm test -- <путь>`; полный прогон — по разрешению владельца.
- **Дев-сервер не подхватывает серверные правки** — после них перезапуск руками.
- **UI только из ui-kit**; не хватает пропа — правится `vendor/ui-kit`.
- **Миграций не будет:** все колонки уже есть — `users.organization` / `unit` / `position` /
  `lms_learner_id` (миграция `0043`), `scorm_attempts.lms_user_org` / `lms_user_unit` /
  `lms_user_position` (базовая схема и `0042`).

## Состояние на начало работ

- **Профиль.** Четыре поля пользователя не читаются и не пишутся ни одной ручкой, ни одним
  экраном. `createUser` пишет явный список колонок, `updateUser` пропускает поля через
  белый список (`pickDefined`) — ни там, ни там новых полей нет.
- **Массовая загрузка пользователей** (`/api/users/bulk-*`, окно «Загрузить CSV»): шаблон с
  колонками `email, name, role, group, external_key`.
- **Приглашение участников при назначении теста** (PRD-28, вкладка списком): шаблон с колонками
  `email, name`.
- **Импорт выгрузок** хранит подразделение и должность у прохождения всегда, организацию — только
  при выключенном обезличивании (PRD-54). Телеметрия приносит только организацию
  (`cmi.student_org`), подразделения и должности у неё нет.
- **Аналитика.** `Observation` не несёт оргполей; оси — семь (`slice-axis.ts`), условия отбора —
  группа, источник, исход, вариант, версия, период. Тест ручки срезов прямо проверяет, что ось
  `должность` отклоняется с кодом 400 — он будет переписан.

### Дефекты, найденные при разборе

Не входят в цель, но лежат на тех же файлах и чинятся первой задачей:

1. **Пароли уходят на клиент.** `GET /api/users` и `GET /api/users/:id` отдают строку целиком,
   включая `passwordHash` и `emailHash`. Сериализатора нет, режется только в одном месте
   (`assignments.ts`).
2. **«Внешний ключ» в редакторе пользователя не сохраняется.** Окно шлёт `email, name,
   mustChangePassword, expiresAt` без `externalKey`, а сервер читает ключ, только если он есть в
   теле запроса. Правка в интерфейсе молча теряется.
3. **Массовая загрузка теряет внешний ключ у НОВЫХ строк.** Предпросмотр его показывает,
   `createUser` его не получает.
4. **Клиент шлёт поля, которые сервер не читает:** `mustChangePassword` и `expiresAt` при
   создании и правке. Здесь только фиксируется: чинить или убирать — отдельное решение.

## Решения

Принятые владельцем 2026-09-28 (записаны в PRD-56 OQ-04):

- **Р-1.** Значение оси берётся у прохождения, если оно там есть, иначе из профиля связанного
  пользователя. Нет ни того, ни другого — срез «Не указано».
- **Р-2.** Импорт прохождений профиль пользователя не правит — ни при каких настройках.

Предлагаемые (на согласование вместе с планом):

- **Р-3. Поле профиля — выбор из существующих значений или создание нового, свободного ввода
  нет.** Образец — поле «Последовательность» PRD-22 (`Combobox` + `footerAction`
  «+ Создать «…»»), отказавшееся от свободного текста по той же причине: «Отдел продаж» и
  «Отдел продаж» с пробелом в конце тихо делят одно подразделение на два среза. Список значений — из профилей
  и из прохождений: так оператор видит написание, которое уже пришло из LMS, и повторяет его.
- **Р-4. Сравнение значений.** При сохранении профиля — обрезка краёв и схлопывание пробелов.
  В срезе и фильтре значения сравниваются без учёта регистра и лишних пробелов: импорт приносит
  написание LMS как есть, и `ОТДЕЛ ПРОДАЖ` из файла обязан совпасть с `Отдел продаж` из
  профиля. Подпись среза — самое частое написание в выборке.
- **Р-5. Подразделение — плоская ось, без привязки к организации.** Разрез «подразделения одной
  организации» получается фильтром по организации плюс осью подразделения. Составной ключ
  «организация + подразделение» ломается на обезличенном импорте, где организации нет, а
  подразделение есть.
- **Р-6. `lms_learner_id` уникален, как `external_key`.** Два пользователя с одним
  идентификатором LMS делают связывание телеметрии лотереей; совпадение — ответ 409 с именем
  владельца значения. Уникальность проверяется ручкой (тот же путь, что у внешнего ключа), а не
  индексом: индекс — миграция, которой этот план избегает.
- **Р-7. «Назначено» по оргосям считается по профилю назначенных.** Сегодня «Назначено»
  считается только для групп и внешних; для подразделения это главный вопрос менеджера
  («в отделе назначено 20, прошли 5»), и профиль на него отвечает.
- **Р-8. Обезличенный импорт.** Организации у такого прохождения нет (PRD-54), поэтому по Р-1
  она берётся из профиля связанного пользователя, а у несвязанного попадает в «Не указано». Это
  следствие, а не новое правило; в интерфейсе оно не объясняется, а видно по числам среза.

- Пересчёт уже импортированных строк.
