# Отчёт об аудите проекта test-builder на соответствие требованиям к архитектуре

## Метаданные

- Дата аудита: 2026-06-07
- Объект аудита: проект `test-builder` (SCORM Test Constructor), версия `1.0.0`, ветка `dev`
- Эталон: `ENGINERING_HANDBOOK/handbook/standards/ARCHITECTURE_REQUIREMENTS.md`
  (Обязательные требования к архитектуре и разработке ИС; источники [НФТ], [ИБ v.4])
- Метод: статический анализ исходного кода, конфигурации и документации репозитория
- Класс системы по [НФТ] в репозитории не зафиксирован (нужен для трактовки разделов 1-2)

## Резюме

`test-builder` — функциональное full-stack приложение (React 18 + Express 5 + PostgreSQL/Drizzle)
с разумной базовой защитой: хэширование паролей `bcrypt`, серверные сессии, ролевая модель
(`author`/`learner`), журнал аудита, graceful shutdown, health-check, параметризованные запросы
к БД. Однако по корпоративному стандарту выявлен ряд несоответствий, часть из которых критична.

Главный вывод: код соответствует уровню рабочего MVP, но не уровню промышленной ИС
по требованиям [НФТ]/[ИБ v.4]. Наиболее серьёзные расхождения:

1. В git отслеживается файл `.env copy` с реальными секретами; ранее в истории присутствовал `.env`.
2. Парольная политика не отвечает разделу 7 (длина, категории символов, история, периодическая смена).
3. Корпоративная аутентификация (LDAPS/Kerberos/OIDC) отсутствует, обоснование не задокументировано.
4. Подсистема логирования без интеграции с SIEM и без защиты журналов от изменений.
5. Приложение не stateless (сессии в памяти, файлы на локальном диске) — горизонтальное
   масштабирование в текущем виде невозможно.
6. TLS в приложении не реализован и не enforced; параметры шифрования не зафиксированы в репозитории.
7. Изменение конфигурации требует перезапуска (нарушение req 82).

Многие требования (среды, RTO/RPO, сетевая сегментация, ЦОД, K8s-политики, WAF, Анти-DDoS,
пентест) относятся к инфраструктуре и оргмерам и не верифицируются по коду — они помечены
как «Вне кода».

## Легенда статусов

- Соответствует — требование выполнено в коде/конфигурации.
- Частично — выполнено не полностью либо с оговорками.
- Не соответствует — требование не выполнено.
- Вне кода — инфраструктурное/организационное требование, не определяется по репозиторию.
- Требует проверки — нельзя подтвердить статически (нужны сканирование/стенд).

## Детальный разбор по разделам

### 1. Среды развёртывания

Требования к набору сред (PROD/PrePROD/TEST/DEV), их изоляции и доступу разработчиков в PROD —
инфраструктурные и по коду не подтверждаются.

Что есть в репозитории:

- Переключение режима через `NODE_ENV` (`development`/`production`), читается в `server/index.ts`.
- Конфигурация через `.env` (отдельные значения на среду) — основа для разделения контуров.
- Docker-обвязка под развёртывание (`docker/Dockerfile`, `docker/build/config/docker-compose.yml`).

Статус: Вне кода. Рекомендация: зафиксировать класс системы и матрицу сред в проектной документации.

### 2. Доступность, RTO и RPO

Значения доступности, RTO, RPO, резервного копирования и размещения в ЦОД — инфраструктура (Вне кода).
Однако одно архитектурное следствие проверяется по коду — горизонтальное масштабирование (req 31).

Препятствия масштабированию (приложение не stateless):

- Хранилище сессий в памяти процесса: `server/routes.ts:67` — `new MemStore(...)` (`memorystore`).
  При нескольких экземплярах сессии не разделяются; при рестарте теряются.
- Загруженные файлы пишутся на локальный диск: `server/routes.ts:13-32` (`multer.diskStorage`,
  каталог `uploads/media`). На разных узлах файлы не видны.
- Положительное: пул соединений к БД с ретраями и health-check (`server/db.ts:33-38`, `66-81`).

Статус: Не соответствует (в части req 31). Рекомендация: внешнее хранилище сессий
(например, на PostgreSQL) и общее объектное хранилище для медиа.

### 3. Режимы функционирования

Реализованы технические предпосылки, но не управляемые режимы как состояния системы.

- Health-check: `server/index.ts:133-142` — `GET /api/health` (проверка БД, ответ 200/503).
- Graceful shutdown: `server/index.ts:191-213` — обработка `SIGTERM`/`SIGINT`, закрытие HTTP и БД,
  принудительный выход через 30 c.
- Обработка `uncaughtException`/`unhandledRejection`: `server/index.ts:18-29`.
- Не реализовано: явный сервисный режим (плановая недоступность с уведомлением),
  аварийный режим и автоматический переход в него при сбое компонентов ИБ.

Статус: Частично.

### 4. Совместимость и технологический стек

Серверная часть:

- Базовый образ — `node:20-slim` (Debian), см. `docker/Dockerfile:13`. Это не РедОС и не «Альт Сервер»
  из списка разрешённых ОС; соответствие ОС требует подтверждения на уровне развёртывания.
- Среда исполнения — Node.js 20 (JavaScript/TypeScript). Требование по Java (Axiom JDK) неприменимо.
- Жизненный цикл ПО (поддержка ≥5 лет): для Node.js 20 LTS горизонт поддержки ограничен —
  требует проверки на момент закупки/сдачи.
- Контейнеры: образ OCI-совместим (Docker), но манифестов Kubernetes (≥1.2) в репозитории нет.

Клиентская часть:

- SPA на React 18 + Vite — работает в Chromium-based браузерах (включая Яндекс.Браузер).
- Разрешение экрана/адаптивность — UI на Tailwind/Radix; минимальные разрешения отдельно не зафиксированы.
- VDI/терминальная ферма — инфраструктура.

Статус: Частично (база ОС вне списка; ЖЦ Node 20 требует проверки; K8s не описан).

### 5. Сетевая архитектура и протоколы

#### 5.1. Сегментация

Сегменты (APP/WEB/DB/DMZ) и ограничение трафика — инфраструктура (Вне кода).
В `docker-compose.yml` сетевые политики не заданы.

#### 5.2-5.3. Протоколы и TLS

- Приложение слушает по HTTP: `server/index.ts:6,32,186` (`createServer` из `http`).
  TLS делегирован обратному прокси (`app.set("trust proxy", 1)`, `server/index.ts:35`).
- В коде/конфиге репозитория нет настройки минимальной версии TLS, наборов шифров,
  редиректа HTTP→HTTPS и заголовка HSTS.
- Подключение к PostgreSQL без SSL: `server/db.ts:33-38` — в `Pool` нет параметра `ssl`,
  в `DATABASE_URL` нет `sslmode`. Требование «PostgreSQL SSL» не выполняется на уровне приложения.
- SMTP поддерживает защищённое соединение через `SMTP_SECURE` (`server/email.ts`).

Статус: Частично/Не соответствует. TLS веб/API не enforced в коде, политика шифров не зафиксирована,
канал к БД незащищён. Если TLS терминируется на прокси — это должно быть задокументировано
и подтверждено (раздел 13).

#### 5.4. Взаимодействие компонентов

- Адреса задаются через переменные окружения (`API_BASE_URL`, `APP_URL`) — основа для работы по FQDN.
- Привилегированный доступ через JumpHost/VDI/PAM — инфраструктура.

Статус: Частично.

### 6. Аутентификация и управление доступом

#### 6.1. Корпоративная аутентификация

Реализована только локальная аутентификация (email + пароль), см. `server/routes/auth.ts:29-92`.
Поддержки LDAPS/Kerberos/OIDC нет. По [ИБ IBv004-IAF-005] требуется корпоративная аутентификация
(вне DMZ), а локальная допустима лишь при подтверждённой невозможности и соблюдении парольной политики
(которая здесь не соблюдена — см. раздел 7).

Статус: Не соответствует (нет корп. аутентификации и задокументированного обоснования).

#### 6.2. Учётные записи

- Учётные записи персонифицированные (по email), групповых/неперсонифицированных нет.
- Отдельные технологические УЗ на каждую интеграцию/службу не формализованы; в приложении нет
  понятия сервисной учётной записи или API-ключей.

Статус: Частично.

#### 6.3. Ролевая модель

- RBAC: роли `author`/`learner`, middleware `requireAuth`/`requireAuthor`/`requireLearner`
  (`server/middleware/auth.ts`).
- Назначение ролей через AD/IAM отсутствует (локальная модель).
- Админ-фильтрация пользователей по группам и по статусу (заблокирована/активна) в API
  списка пользователей не реализована (req 50).

Статус: Частично.

#### 6.4. Подключение приложения к БД

- Параметры подключения — в конфигурации (`DATABASE_URL`), не в коде: `server/db.ts:33-34`. Хорошо.
- Учётная запись БД из строки подключения; ограничение её привилегий — задача развёртывания.
- SSL канала к БД не настроен (см. раздел 5).

Статус: Частично/Соответствует (хранение параметров в конфиге выполнено).

#### 6.5. Управление сеансами

- Деактивация пользователя блокирует новые входы (`server/routes/auth.ts:49-52`) и уничтожает сессию
  при следующем обращении к `/api/auth/me`.
- Принудительное завершение уже активных сессий заблокированного пользователя не реализовано
  (хранилище в памяти не позволяет перечислять/закрывать чужие сессии).
- Мониторинг активных сессий (список сессий, уведомления о входе с нового устройства/IP) отсутствует
  (req 54, 60).

Статус: Не соответствует.

### 7. Парольная политика (встроенная аутентификация)

#### 7.1. Хранение паролей

- Хэширование `bcrypt` (`bcryptjs`) с 10 раундами; в БД хранится только хэш.
- Случайная соль на каждый пароль (встроена в `bcrypt`) — одинаковые пароли дают разные хэши.
- Вторая соль (pepper) из конфигурации не используется (она рекомендательная).

Статус: Соответствует.

#### 7.2. Требования к паролю

- Минимальная длина: сервер требует не менее 6 символов (`server/routes/auth.ts:114`),
  клиент — 8. Требование «минимум 10 символов» не выполняется, проверки рассинхронизированы.
- Категории символов (минимум 3 из 4) не проверяются (есть только белый список допустимых символов).
- Имя/email как часть пароля — не проверяется.
- Распространённые/словарные пароли — не проверяются (пустой пароль отклоняется).
- История паролей (несовпадение с N предыдущими) — не реализована (нет хранилища истории).
- Принудительная смена при первом входе — реализована (`mustChangePassword`).
- Периодическая принудительная смена — не реализована.

Статус: Не соответствует.

#### 7.3. UI поля пароля

- Маскирование ввода реализовано (`client/src/components/password-input.tsx`, переключатель видимости).
- Запрет копирования введённого пароля не реализован.

Статус: Частично.

#### 7.4. Защита от перебора

- Лимит входов по IP: 10 попыток за 15 минут (`server/routes/auth.ts:11-26`), хранилище в памяти
  (сбрасывается при рестарте, не на уровне УЗ).
- Блокировка УЗ после N неудачных попыток на M минут — не реализована; параметры N/M не конфигурируемы.
- Сообщение об оставшихся попытках — не выводится.
- CAPTCHA/MFA(TOTP) — отсутствуют.
- Положительное: сброс пароля по токену реализован надёжно — 32 байта энтропии, хранится хэш SHA-256,
  срок 30 минут, одноразовость, лимит 3 запроса в час (`server/routes/auth.ts:188-321`).

Статус: Частично.

### 8. Регистрация событий и аудит

#### 8.1. Обязательные события

Журнал аудита определён в `server/logger.ts:169-188`. Фиксируются:

- Вход (успех/неуспех), выход (`auth.login`, `auth.logout`).
- Смена/сброс пароля (`auth.passwordChange`, `auth.passwordReset`).
- Создание/деактивация/активация УЗ, массовый импорт (`user.create`, `user.deactivate`,
  `user.activate`, `user.bulkImport`).
- Сброс попыток прохождения (`attempts.reset`).

Не фиксируются: изменение привилегий/роли (операция обновления пользователя), изменение параметров
безопасности, попытки несанкционированного доступа к объектам, удаление УЗ.

Статус: Частично.

#### 8.2. Атрибуты событий

Запись аудита (`server/logger.ts:118-135`) содержит: тип события (`action`), дату/время (`ts`),
идентификатор запроса (`reqId`), субъект (`userId`); для входа дополнительно `email`, результат
(`success`), IP (`ip`). Отсутствуют обязательные атрибуты: идентификатор приложения (название+версия),
уровень критичности, сервис (протокол+название), IP источника для всех событий (он есть только у входа).

Статус: Частично.

#### 8.3. Подсистема логирования

- Хранение: файлы `logs/app-YYYY-MM-DD.log` (текст) и `logs/audit-YYYY-MM-DD.log` (JSON).
- Ротация: приложение 14 дней, аудит 90 дней (`server/logger.ts:7-8`). Требование «не менее 3 месяцев»
  для аудита выполнено пограничнo (90 дней); журнал приложения — 14 дней.
- Отправка в SIEM (Syslog/Elastic Beats) — отсутствует.
- Защита журналов от изменений (неизменяемость/целостность) — отсутствует (обычные файлы).
- Просмотр через интерфейс администратора: реализован для журналов приложения
  (`GET /api/logs`, защита `requireAuthor`, страница `client/src/pages/author/logs.tsx`);
  для журнала аудита UI и API отсутствуют — только доступ к файлам.
- Настройка уровня/параметров логирования без перезапуска — отсутствует.

Статус: Частично/Не соответствует.

### 9. Защита приложения

#### 9.1. Раскрытие информации

- Тип/версия компонентов: заголовок `X-Powered-By` Express не отключён (`app.disable('x-powered-by')`
  не вызывается) — раскрывает фреймворк.
- При ошибке входа возвращается обезличенное «Invalid credentials» (`server/routes/auth.ts:46`) — хорошо.
- Ответ о деактивированной УЗ и эндпоинт проверки email раскрывают факт существования учётной записи
  (риск перечисления пользователей).
- Стек-трейсы наружу не отдаются: обработчик ошибок возвращает только `{ message }`
  (`server/index.ts:146-159`), полный стек пишется в лог.

Статус: Частично.

#### 9.2. Уязвимости

Зависимости современные, но в репозитории нет инструментов SCA/контроля уязвимостей, отчётов
сканирования или фиксации отсутствия критических/высоких уязвимостей.

Статус: Требует проверки.

#### 9.3. Исходный код

Требование [ИБ IBv004-SP-006] (ПО собственной разработки не хранится вне ресурсов организации) —
организационное. Репозиторий размещён на внешнем GitHub — вопрос соответствия решается на уровне
политики хранения кода.

Статус: Вне кода (отметить риск).

#### 9.4. Обновления и зависимости

- Зависимости ставятся из публичного реестра npm; `.npmrc` с указанием внутреннего реестра нет.
- Локальная зависимость `@universityrt/ui-kit` подключена по файловому пути.
- Требование обновления только из внутренних репозиториев не выполняется.

Статус: Не соответствует/Частично.

#### 9.5. Изменение параметров без простоя

Переменные окружения читаются один раз при старте; механизма горячей перезагрузки конфигурации нет.
Изменение параметров требует перезапуска — нарушение req 82.

Статус: Не соответствует.

### 10. Публикация в Интернет

WAF (СОИБ Веб), Анти-DDoS, проверка кода на уязвимости, тестирование на проникновение, недоступность
админ-интерфейсов и портов СУБД из Интернета — инфраструктурные/организационные меры (Вне кода).

Существенная отметка по коду: приложение хранит персональные данные (email пользователей, хоть
и зашифрованные). По [ИБ IBv004-RA-008] серверы DMZ IN/OUT не должны содержать ПДн — это требует

### 11. Архитектура интеграций

- Исходящая интеграция: SMTP (отправка писем). При недоступности — деградация без блокировки
  (ссылки выводятся в консоль), что согласуется с req 35 (отказоустойчивость интеграций).
- Выгрузка SCORM: файловые пакеты для LMS (WebTutor) — офлайн-обмен.
- Входящая интеграция: приём телеметрии SCORM с разрешением `Access-Control-Allow-Origin: *`
  (`server/routes.ts:54-62`) — широкое разрешение источников, требует ограничения/обоснования.
- Направление инициации обмена, VPN с алгоритмами ГОСТ, транспортный сервис в DMZ — инфраструктура.

Статус: Частично/Вне кода.

### 12. Контейнеризация

- `docker/Dockerfile`: непривилегированный пользователь `nodejs` (UID/GID 1500), drop привилегий через
  `gosu`, `npm ci --omit=dev`, монтирование `uploads/`, `logs/`, `.env` как volume — хорошие практики.
- `docker/build/config/docker-compose.yml`: один сервис, `restart: unless-stopped`, healthcheck.
  Healthcheck обращается к `/api/me` (требует сессии и вернёт 401) вместо `/api/health` — дефект пробы.
- Манифестов Kubernetes, сетевых политик, Ingress, ограничений NodePort/hostNetwork в репозитории нет —
  требования раздела 12 для K8s проверяются на уровне платформы (Вне кода).

Статус: Частично/Вне кода.

## Рекомендованная очерёдность работ

1. Немедленно: устранить утечку секретов (находка 1) — это самый высокий риск.
2. Контур безопасности доступа: парольная политика, сессии, корпоративная аутентификация (2, 3, 5).
3. Транспорт и устойчивость: TLS/SSL, stateless-архитектура (4, 6).
4. Наблюдаемость и эксплуатация: SIEM и защита логов, горячая конфигурация, security-заголовки (7, 8, 9).
5. Мелкие дефекты и документация: проба healthcheck, CORS телеметрии, комплект документов раздела 13.
