## 2. Что вошло в трек

Источник правды — [plan-tests.md](../specs/sim-scenario/plan-tests.md) (этапы Э0-Э5б и раздел 6
«Технический долг трека») и журнал коммитов `git log --oneline main..sim-scenario`. Коротко:

- новый тип вопроса `simulation` и тест режима «Сценарий» (один пункт-сценарий);
- пункты-сценарии в роутере наравне с темами: порядок, обязательность, группы, правила открытия
  («после завершения / успешного прохождения»), порог сценария, повторный прогон по «менять ответ»;
- сценарии в обычном разделе стандартного теста;
- оценка сценария: доля цели по весам минус штрафы, частичное выполнение, цепочка «система → тест →
  вопрос в тесте»;
- протокол прогона и метаданные попытки через LMS (`sim_`, `meta_attempt`, `meta_duration`) и
  импорт их из выгрузки отчёта LMS;
- аналитика сценариев;
- вес сценариев в пакете в ящике теста;
- исправления роутера на вебе и в пакете, найденные по ходу (исход пункта, возобновление в хабе,
  «последний раздел» в роутере).

Отложено владельцем, в общий реестр техдолга при вливании: №1 (перенос сценариев книгой Excel),
№2 (одна функция выдачи пунктов). Открыто: №9 — приёмка пакета в WebTutor, ждёт входа владельца.

## 3. Проход по документации

Правило — ROADMAP [§0.0.5](../ROADMAP.md): слоёв ЧЕТЫРЕ, четвёртый (анализы конкурентов) забывают
чаще всего. Статус трека брать из журнала `main`, а не из ROADMAP.

| Слой | Что сделать |
| --- | --- |
| Спеки `docs/specs/` | Спеки трека — `docs/specs/sim-scenario/`. PRD-54 уже дополнен (решение 13, разделы 7.4-7.6). Проверить, что спеки роутера и PRD-19 не утверждают, будто «последний раздел» в роутере существует, и что исход пункта берётся только с экрана итогов |
| Руководства `docs/guides/` | В `test-authoring-guide.md` сценариев нет вовсе — нужен раздел: тест «Сценарий», пункт-сценарий роутера и его поля, порог, правила открытия, оценка и штрафы, вес в пакете. В `import-workbook-guide.md` — что книга сценарии не переносит и не стирает, а переносят `.tbtest` и `.scenario.zip`. В `template-development.md` — что обложка и окно правил сценария рисуются ядром встроенными стилями и шаблону ничего добавлять не нужно |

| Анализы конкурентов `docs/reports/ANALYSIS_*.md` | Новая СТРОКА возможности «симулятор / сценарий в информационной системе», а не только смена знака. Править только нашу сторону; цифры конкурентов остаются с датой своей редакции |

Скриншоты для руководства — по принятому в проекте порядку (`docs/guides/images/`). Markdown —
без эмодзи и чистый по `markdownlint`.

## 4. Вливание

1. `git fetch origin`; посмотреть, что появилось в `main` с 2.43.4.
2. Если в `main` появились миграции с номерами `0053` и выше — миграции трека перенумеровываются
   ВПЕРЁД, с новыми `when` позже последних в `main`; снимки `drizzle/meta` перецепляются по `prevId`.
   `when` в прошлое однажды уронил прод — только вперёд. Общая dev-база помнит миграции трека по
   `created_at` = `when`: после перенумерации эти записи в журнале базы правятся под новые значения
   (так сделано при прошлом перебазировании; было 4 записи, теперь 5).
3. Перебазирование, разрешение конфликтов, затем прицельные тесты по затронутым файлам.
4. Полный `npm test` и `npm run test:cov` — только с явного разрешения владельца и в одиночку
   (`test:cov` портит соседние прогоны).
5. Вливание — перемоткой: без PR, в `origin/main`, только свои коммиты.

## 5. Выпуск

- Подъём версии продукта — минорный: в треке новые возможности.
- Раздел в журнале изменений — отдельным коммитом, как у 2.43.x.
- Подъём версии продукта требует git-тега `vX.Y.Z`.
- После выкладки — сверка на стенде с согласованными эскизами
  (`docs/wireframes/sim-scenario-test-editor.html`, `docs/wireframes/sim-scenario-learner.html`),
  числа — из проектного слоя эскиза.
- Коммиты без трейлера `Co-Authored-By`.
