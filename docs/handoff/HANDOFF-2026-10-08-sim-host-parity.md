## 1. Какая модель нужна

| Шаг | Модель | Почему |
| --- | --- | --- |
| 1. Проект обвязки: что сравнивать, на каком уровне, как гонять веб и пакет на одном сценарии прохождения | Opus | Ошибка проекта даёт зелёный тест, сравнивающий не то. Нужно держать в голове оба хоста сразу |
| 2. Обвязка пакета (рантайм в `new Function`, как в существующих тестах) | Sonnet | Образцы есть, приём отработан |
| 3. Обвязка веба (`TakeTestPage` в jsdom с подменой `fetch`) | Opus | Веб оценивает пункт запросом к серверу; подмена ответа должна считать тем же кодом, что сервер, иначе паритет фиктивный |
| 4. Набор прохождений (сами сценарии шагов) | Sonnet | Механическая работа по списку из раздела 4 |
| 5. Разбор каждого найденного расхождения | Opus | Решить, какой хост прав, по плану и решениям владельца; не подгонять тест |
| 6. Итоговая проверка перед коммитом | Opus | Проверить, что тест действительно падает при внесённом расхождении |

Если работа идёт на Sonnet целиком — сначала шаг 1 на Opus отдельной сессией с записью проекта
в эту же записку, потом остальное.

## 3. Где реально расходятся хосты

Сам прогон сценария у обоих хостов один: общий `mountPlayer` (`shared/sim/player`), веб берёт его
в `client/src/features/questions/scenario/scenario-run.tsx`, пакет — через `TBTemplate`
(`server/scorm/template/app/render/simulation.js`). Расходится то, что хосты ДЕЛАЮТ с результатом.
2026-10-08 за одну приёмку нашлись три таких расхождения, и все были в логике вокруг хаба:

1. исход пункта знал только экран итогов раздела, на обоих хостах по-разному;
2. вход в пункт через заставку на вебе показывал обзор раздела, первого в выдаче;
3. «последний раздел» считался по выдаче: веб обещал «Завершить тест», пакет терял экран итогов;
   плюс веб не сохранял состояние хаба и возобновлял прогон внутри завершённой темы.

Отсюда уровни сравнения, от самого ценного:

| Уровень | Веб | Пакет |
| --- | --- | --- |
| Разметка хаба после каждого шага | `bodyHtml` экрана хаба (`TakeTestPage`, `buildRouterHubHtml`) | `renderRouterPage` в `routerFlow.js` (тот же `buildRouterHubHtml`) |
| Доступность «Завершить» | `isRouterReadyToFinish` с веб-состоянием | `RouterFlow.isRouterReadyToFinish` |
| Исход пункта | ответ `POST /api/attempts/:id/section-result` (`server/routes/attempts.ts`) | `buildSectionResult` (`render/resultsPage.js`) |
| Итог попытки | `POST /finish` → `aggregateStandardResult` на сервере | `calculateResults` (`render/resultsPage.js`) |
| Возобновление | `variantJson.routerState` (сервер) + восстановление в `handleResumeTest` | `sessionRecovery.js` (`rt`, `sc`, `sp`, `crt`) |

Разметку хаба оба хоста строят ОДНОЙ функцией, поэтому её сравнение побайтно осмысленно: разница
в строке значит разницу во входном состоянии.

Первая известная зацепка, не проверенная: пакет передаёт `buildRouterHubHtml` третий аргумент
`{ deadline: TEST_DATA.deadline }` (`routerFlow.js`, `renderRouterPage`), а веб зовёт его без него
(`take-test.tsx`, экран хаба). Если веб не показывает срок назначения где-то ещё, хаб с назначенным
сроком на хостах различается.

## 4. Набор прохождений

Каждое прохождение — последовательность шагов; после каждого шага снимок сравнивается.
Минимальный набор (роутер: две темы, два сценария, правила открытия и пороги, как в фикстуре
приёмки ниже):

1. тема пройдена → зависимый сценарий открылся;
2. тема провалена → зависимый сценарий «Недоступен», «Завершить» доступна (решение владельца
   2026-10-08 «недостижимое не ждут»);
3. сценарий: полное выполнение / частичное при включённом и выключенном «Засчитывать частичное» /
   досрочный выход / истечение времени;
4. повторный прогон сценария при «менять ответ»: досрочный выход не затирает завершённый прогон,
   истечение времени затирает;
5. политика «все обязательные пройдены» с провалом окончательным и с повторяемым;
6. перезагрузка в хабе и внутри пункта на каждом из шагов выше;
7. тест без экрана итогов раздела (`showSectionResults: false`) — тот случай, где была дыра 1.

## 5. Готовые приёмы и образцы

- Рантайм пакета в тесте: `tests/sim-router-section-passed.test.ts` (настоящий `routerFlow.js` с
  общим хабом), `tests/scorm-session-recovery.test.ts` (настоящий `sessionRecovery.js`).
- Веб в jsdom: `client/src/pages/learner/__tests__/take-test-router-hub.test.tsx` (заглушки шаблонов,
  подмена `fetch`, возобновление через `ts-resume`).
- Паритет разметки: `tests/scale-host-parity.test.ts`, `tests/result-context-parity.test.ts`.
- Данные пакета без сборки архива: `buildScormExportData` (`server/scorm/build-export-data.ts`).

Главная ловушка веба: оценку пункта делает сервер. Подмена `fetch` для `section-result` и
`finish` обязана считать тем же общим кодом (`aggregateStandardResult`, `resolveTopicRule`,
`simulationRatio`), что маршрут, — лучше вызвать сам обработчик маршрута через `supertest`, как в
`tests/routes.attempts-*.test.ts`. Подмена, возвращающая заранее заданный ответ, превращает паритет
в сравнение теста с самим собой.

## 7. Ограничения среды

- Полный `npm test` и `npm run test:cov` — только с явного разрешения владельца; работать прицельно
  `npm test -- <путь>`.
- `npx vitest run` напрямую падает — только через `npm test`.
- Клиентские тесты в worktree требуют junction `node_modules` (уже стоит).
- Приёмка интерфейса — в браузере (Playwright), не только тестами.
- Коммиты без трейлера `Co-Authored-By`.

## 8. Готово, когда

- есть тест, проигрывающий набор из раздела 4 на обоих хостах и сравнивающий снимки после каждого
  шага на уровнях из раздела 3;
- внесённое руками расхождение (например, вернуть `isLastSectionWeb` к счёту по выдаче) роняет тест;
  это проверено и описано в коммите;
- найденные расхождения исправлены отдельными коммитами, у каждого — какой хост был прав и почему;
- в [plan-tests.md](../specs/sim-scenario/plan-tests.md) техдолг №4 отмечен закрытым.
