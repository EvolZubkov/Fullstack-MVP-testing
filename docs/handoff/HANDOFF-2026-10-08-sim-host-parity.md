## 3. Где реально расходятся хосты

Сам прогон сценария у обоих хостов один: общий `mountPlayer` (`shared/sim/player`), веб берёт его
в `client/src/features/questions/scenario/scenario-run.tsx`, пакет — через `TBTemplate`
(`server/scorm/template/app/render/simulation.js`). Расходится то, что хосты ДЕЛАЮТ с результатом.
2026-10-08 за одну приёмку нашлись три таких расхождения, и все были в логике вокруг хаба:

1. исход пункта знал только экран итогов раздела, на обоих хостах по-разному;
2. вход в пункт через заставку на вебе показывал обзор раздела, первого в выдаче;
3. «последний раздел» считался по выдаче: веб обещал «Завершить тест», пакет терял экран итогов;
   плюс веб не сохранял состояние хаба и возобновлял прогон внутри завершённой темы.

Отсюда уровни сравнения, от самого ценного:

| Уровень | Веб | Пакет |
| --- | --- | --- |
| Разметка хаба после каждого шага | `bodyHtml` экрана хаба (`TakeTestPage`, `buildRouterHubHtml`) | `renderRouterPage` в `routerFlow.js` (тот же `buildRouterHubHtml`) |
| Доступность «Завершить» | `isRouterReadyToFinish` с веб-состоянием | `RouterFlow.isRouterReadyToFinish` |
| Исход пункта | ответ `POST /api/attempts/:id/section-result` (`server/routes/attempts.ts`) | `buildSectionResult` (`render/resultsPage.js`) |
| Итог попытки | `POST /finish` → `aggregateStandardResult` на сервере | `calculateResults` (`render/resultsPage.js`) |
| Возобновление | `variantJson.routerState` (сервер) + восстановление в `handleResumeTest` | `sessionRecovery.js` (`rt`, `sc`, `sp`, `crt`) |

Разметку хаба оба хоста строят ОДНОЙ функцией, поэтому её сравнение побайтно осмысленно: разница
в строке значит разницу во входном состоянии.

Первая известная зацепка, не проверенная: пакет передаёт `buildRouterHubHtml` третий аргумент
`{ deadline: TEST_DATA.deadline }` (`routerFlow.js`, `renderRouterPage`), а веб зовёт его без него
(`take-test.tsx`, экран хаба). Если веб не показывает срок назначения где-то ещё, хаб с назначенным
сроком на хостах различается.

Проверено на шаге 1: зацепка ложная. `TEST_DATA.deadline` не выпекает ни один построитель
(`server/scorm/builders/*`, `build-export-data.ts`) — аргумент в `routerFlow.js` всегда `null`, и
хаб пакета без срока, как и веб. Мёртвый аргумент — повод для уборки, не для паритета.

## 4. Набор прохождений

Каждое прохождение — последовательность шагов; после каждого шага снимок сравнивается.
Минимальный набор (роутер: две темы, два сценария, правила открытия и пороги, как в фикстуре
приёмки ниже):

1. тема пройдена → зависимый сценарий открылся;
2. тема провалена → зависимый сценарий «Недоступен», «Завершить» доступна (решение владельца

3. сценарий: полное выполнение / частичное при включённом и выключенном «Засчитывать частичное» /
   досрочный выход / истечение времени;
4. повторный прогон сценария при «менять ответ»: досрочный выход не затирает завершённый прогон,
   истечение времени затирает;
5. политика «все обязательные пройдены» с провалом окончательным и с повторяемым;
6. перезагрузка в хабе и внутри пункта на каждом из шагов выше;
7. тест без экрана итогов раздела (`showSectionResults: false`) — тот случай, где была дыра 1.

## 9. Проект обвязки (шаг 1, 2026-10-08)

### 9.1. Принцип

Паритет фиктивен, если какой-нибудь хост в тесте заменён тем, что тест написал сам. Поэтому:

1. **Один источник.** Оба хоста получают входы от НАСТОЯЩИХ сборщиков из ОДНОЙ базы: веб — ответ
   маршрута старта попытки, пакет — `buildScormExportData` → `generateScormPackage`. Ни
   `TEST_DATA`, ни ответ `/attempts/start` руками не пишутся.
2. **Чёрный ящик на границе интерфейса.** Шаг прохождения — действие участника: выбрал пункт,
   ответил, нажал «Далее», закрыл окно плеера, перезагрузил страницу. Состояние хоста в обход его
   логики не трогается: ответ не кладётся в `state.answers`, исход — в `sectionResults`.
3. **Сравнивается наблюдаемое.** Снимок после шага собирается из того, что видит участник и что
   уходит наружу (разметка хаба, кнопки подвала, экран, LMS, строка попытки в базе), а не из
   внутренних переменных. У веба они в React-состоянии и снаружи недоступны, а сравнение
   внутренностей пропускает расхождение в том, как хост их показывает.
4. **Подменяется только плеер сценария** — одинаково на обоих хостах (9.5). Сам плеер у хостов
   общий (`shared/sim/player`), его паритет — не предмет этого теста; предмет — что хост ДЕЛАЕТ с
   результатом.

### 9.2. Источник: pglite и настоящее сохранение

База — pglite (`createHarness` из `tests/it/db-harness.ts`), как у кругового теста №3
(`tests/it/sim-chain-roundtrip.it.test.ts`). pglite в основном наборе уже работает
(`tests/storage/*`), поэтому тест живёт в основном наборе (среда jsdom), а не в `test:it`: веб-хосту
нужен React. Тест создаёт свою базу в памяти; общую dev-базу и фикстуру приёмки он не трогает.

Тест сохраняется настоящим путём — `testSettingsService` с `ScenarioPayload`, как в №3; темы и
вопросы — вставкой в таблицы. Хранилище — настоящее `DatabaseStorage` под `vi.mock` модуля
`server/db`. Двойника хранилища нет: двойник, написанный для теста, мог бы отдавать то, чего прод не
отдаёт (например, разделы без пунктов-сценариев, которые добавляет `deliverySections`).

Фикстура обязана исключать случайность, иначе хосты выдадут разное и сравнивать будет нечего:

- у тем «взять все вопросы», фиксированный порядок вопросов (PRD-30), без перемешивания вариантов;
- пункты-сценарии — фиксированная выдача (`questionId` задан), не случайная;
- первым уровнем снимка (L0 ниже) сравнивается выдача: разошлась — дальше не идём.

Состав (покрывает набор раздела 4): роутер; тема А (2 вопроса одиночного выбора, порог 60%);
тема Б (2 вопроса); сценарий С1 — фиксированный, эталонный сценарий
`docs/specs/sim-scenario/example/scenario.json`, порог 80%, «Открывается после успешного
прохождения» темы А; сценарий С2 — необязательный, без правил. «Менять ответ», «Засчитывать
частичное», политика завершения и `showSectionResults` — параметры варианта фикстуры. Варианты
собираются одной функцией с параметрами, а не копиями.

### 9.3. Хост пакета: собранный пакет целиком в jsdom

Проба 2026-10-08 (одноразовый тест, удалён) показала: настоящий `app.js` исполняется в jsdom без
ошибок и проходит старт → хаб → тема → итоги раздела → хаб, а «перезагрузка» — новое окно с тем же
хранилищем `cmi` — восстанавливает хаб из `suspend_data`. Поэтому пакет исполняется ЦЕЛИКОМ, а не
по модулям через `new Function`. Модульная обвязка заглушает `render` и переходы `contentFlow.js`,
навигацию внутри пункта пришлось бы изображать самому тесту — а два из трёх расхождений, найденных
2026-10-08, сидели именно в навигации (вход через заставку, «последний раздел»).

Рецепт (проверен):

1. `generateScormPackage(await buildScormExportData(testId))` → `JSZip.loadAsync`. Файл
   `uploads/scorm/identifiers.json` сохранять и восстанавливать, как в `tests/prd-4-acceptance.test.ts`.
2. Общий бандл `TBTemplate` под vitest пустой: `getSharedRuntimeBundle` возвращает `""` при
   `VITEST`, а esbuild в среде jsdom падает. Бандл собирается дочерним процессом той же функцией —
   проверено в среде jsdom:

   ```ts
   const cli = resolve(process.cwd(), "node_modules/tsx/dist/cli.mjs");
   const bundle = execFileSync(process.execPath, [cli, "-e",
     "import('./server/scorm/builders/shared-runtime.ts')" +
     ".then(async (m) => process.stdout.write(await m.buildSharedRuntimeBundle()))"],
     { encoding: "utf8", maxBuffer: 64 << 20, env: { ...process.env, VITEST: "", NODE_ENV: "development" } });
   ```

   Собрать один раз на файл (`beforeAll`) и приклеить в начало `app.js` через `";"` — там он стоит и
   в настоящем пакете (первая часть `joinJsParts` в `server/scorm/index.ts`).
3. Окно: `new JSDOM(html, { runScripts: "dangerously", url: "http://localhost/index.html",
   pretendToBeVisual: true })`, где из `index.html` вырезаны теги `<script src>`. Скрипты (кроме
   `vendor/*` — PDF не нужен) вставляются элементами `<script>` с текстом. `window.eval` не годится:
   строгий режим прячет `var TBTemplate` в собственную область eval.
4. До скриптов: `window.API_1484_11` поверх объекта `cmi` (Initialize, GetValue, SetValue, Commit,
   Terminate, GetLastError); `window.fetch` отдаёт файлы из архива (`template/manifest.json`,
   макеты); `console.log` заглушить — обёртка SCORM пишет каждый SetValue.
5. Затем события `DOMContentLoaded` и `load`; первый экран готов примерно через секунду (шаблон
   грузится через fetch). Дальше — только щелчки: `[data-action=start-test]`,
   `router-select:<ключ>`, `select:N`, `answer-submit`, `answer-next`, `section-continue`, кнопки
   подвала.
6. Перезагрузка: `window.close()` и новое окно с тем же `cmi` и тем же бандлом.

### 9.4. Хост веба: `TakeTestPage` с настоящими маршрутами

Образец — `client/src/pages/learner/__tests__/take-test-router-hub.test.tsx`: двойники
`TemplateScreen` и `TemplateContentScreen`, заглушки `wouter`, `useAuth`, тостов. Отличие — `fetch`
не отвечает заготовками: всё под `/api/attempts/*` и `/api/tests/:id/attempts/start|resume`
пересылается в настоящий `attemptsRouter` (`supertest` поверх express с сессией, как в
`tests/routes.attempts-*.test.ts`), который читает ту же pglite. Так оценку пункта
(`/section-result`), сохранение хаба (`/save-progress`), возобновление (`/resume`) и итог (`/finish`)
считает серверный код, а не тест. Заготовками остаются только `/screen-template/*` (макеты не
сравниваются — сравниваются тело хаба и данные экранов) и `/api/learner/tests`.

Доработки двойников против образца:

- `TemplateContentScreen` отдаёт наружу ещё `onNext`, `onBack`, подписи и доступность обеих кнопок
  подвала: «Завершить» и «Назад» живут в подвале, вне `bodyHtml`, и это отдельный уровень снимка;
- `TemplateScreen` отдаёт `screen`, контекст (для итогов раздела — `sectionResult`) и `onAction`:
  ответ и переходы шлются теми же строками действий, что `data-action` в шаблоне (`select:N`,
  `answer-submit`, `section-continue`), — у хостов один словарь действий.

Шаг считается законченным, когда пусты очередь пересланных запросов и очередь React (`waitFor` по
счётчику запросов в полёте). Иначе снимок веба попадёт на `pending` оценки пункта: хаб в это время
заперт иначе, чем после ответа сервера.

Не проверено пробой: `TakeTestPage`, express и pglite вместе в одном процессе jsdom. Части по
отдельности в этой среде работают (маршрутные тесты, `tests/storage/*`, образец хаба); шаг 3
начинает с того, что поднимает их вместе на одном прохождении.

### 9.5. Прогон сценария: общий двойник плеера, результаты от настоящего движка

Плеер подменяется одинаково на обоих хостах:

- веб — `vi.mock` модуля `@shared/sim/player` (`ScenarioRun` берёт `mountPlayer` оттуда);
- пакет — после загрузки `window.TBTemplate = Object.create(orig, { mountPlayer: { value: double } })`.
  Экспорты бандла — геттеры, переписать свойство нельзя; переприсвоить глобальное имя можно, а
  `simulation.js` читает `TBTemplate.mountPlayer` в момент вызова.

Двойник `mountPlayer(host, options)` записывает `options` — это уровень L5 снимка: ограничение
времени, подпись кнопки, `showDetails`, подпись — и ждёт команды теста: `finish(result)` зовёт
`onFinish`, `close()` — `onClose(result)`, как настоящий плеер после окна результата.

`SimResult` для команд строится настоящим движком на эталонном сценарии — `createRun` и щелчки по
зонам, как `playSuccess` в `tests/sim-replay-scoring.test.ts` (вынести в помощник
`tests/helpers/sim-runs.ts`): успех, частичное, провал, досрочный выход (`run.exit()`), истечение
времени (`run.timeout()`). Самодельный объект результата не годится: `/finish` переигрывает протокол
(`replayRun`) и оценит не то, что передали, — веб и пакет разошлись бы по вине теста. Если эталон
не даёт частичного исхода (нужна некритичная проверка цели), фикстура получает свой маленький
сценарий с такой проверкой.

### 9.6. Язык шагов

Прохождение — массив шагов; у каждого хоста адаптер, переводящий шаг в действия участника:

| Шаг | Веб | Пакет |
| --- | --- | --- |
| `start` | `ts-start-test` | `[data-action=start-test]` |
| `pick(key)` | `onBodyAction("router-select:<key>")` | щелчок по карточке `router-select:<key>` |
| `next` | `onNext` двойника или `onAction("answer-next")` | кнопка подвала или `answer-next` |
| `answer(qid, n)` | `onAction("select:n")`, затем `answer-submit` | `select:n`, затем `answer-submit` |
| `sim(kind)` | двойник плеера: `finish`, затем `close` | то же |
| `sectionContinue` | `onAction("section-continue")` | `section-continue` |
| `finish` | `onNext` хаба («Завершить») | кнопка подвала хаба |
| `reload` | размонтировать, смонтировать, `ts-resume` | новое окно с тем же `cmi`, «Продолжить», если есть |

Шаг делает ровно одно действие участника. Заставки и страницы содержания пункта адаптер САМ не
пролистывает: прохождение пишет `next` явно. Иначе хосты, по-разному вставляющие заставку, совпали
бы на L1, а разница утонула бы в адаптере.

### 9.7. Снимок после шага: уровни

| Уровень | Что | Веб | Пакет |
| --- | --- | --- | --- |
| L0 Выдача | вопросы по пунктам в порядке выдачи | `variantJson.sections` попытки в базе | `state.flatQuestions` (`topicId`, `question.id`) |
| L1 Экран | `hub` / `content` / `question` / `sectionResults` / `scenario` / `results` | какой двойник смонтирован и с каким `screen` | `state.phase`, узел `.router-hub`, слой плеера |
| L2 Хаб | тело хаба, байт в байт | `bodyHtml` двойника | `innerHTML` узла `.router-hub` |
| L3 Подвал хаба | подпись и доступность «Завершить», есть ли «Назад» | пропсы двойника | кнопки `#app` вне `.router-hub` |
| L4 Итоги раздела | `passed`, `percent`, `earnedPoints`, `possiblePoints`, `correct`, `total` | контекст `TemplateScreen` экрана `section-results` | `state.sectionResults[key]` на этом экране |
| L5 Запуск плеера | `limitSeconds` сценария, `closeLabel`, `showDetails`, `caption` | записано двойником | записано двойником |
| L6 Ответ на сценарий | сжатый прогон без `protocol` | ответ попытки в базе, сжатый той же функцией | `state.answers[qid]` |
| L7 Итог попытки | балл, `passed`, по пунктам `passed` и `percent` | `resultJson` попытки после `/finish` | `cmi.score.*`, `cmi.success_status`, `cmi.objectives.*` |

L0 и L7 сравниваются по разу (после старта и после `finish`), L1 – L3 — после каждого шага, L4 — на
экране итогов раздела, L5 — при каждом монтировании плеера, L6 — после каждого `sim`.

Исход пункта, невидимый участнику (пункт без зависимых при политике «все завершены»), отдельным
уровнем не сравнивается: он либо проявится в L2 и L3 через замок и «Завершить», либо в L7.
Внутреннее состояние веба снаружи недоступно, а сравнивать его только у пакета несимметрично.

Сжатие для L6 — `TBSimRun.compact` пакета; для ответа веба вызывать ту же функцию (из окна пакета),
а не свою копию.

### 9.8. Как сравнивать и что печатать

Снимок — плоский объект с уровнями как ключами; сравнение — `expect(web).toEqual(pkg)` с подписью
«прохождение X, шаг N (`pick scenario:...`), уровень L2». Для L2 при расхождении печатать дифф по
карточкам (`data-topic-id`, `data-router-status`, `data-router-locked`, `data-action`): сырой дифф
двух строк по полтора килобайта нечитаем.

Тест паритета утверждает только «одинаково», ожидаемых значений не знает. Но одинаково неверное тоже
возможно, поэтому каждое прохождение несёт 1–2 опорных утверждения по смыслу на снимке ПАКЕТА
(«после провала темы А сценарий С1 заперт», «Завершить доступна»). Иначе хосты, сломанные
одинаково, давали бы зелёный тест.

### 9.9. Гипотезы для шага 5 (по чтению кода, прогоном не проверены)

| № | Уровень | Гипотеза |
| --- | --- | --- |
| Г1 | L2 | Число вопросов на карточке: веб считает ВЫДАННЫЕ (`hubSections` в `take-test.tsx`), пакет печатает настроенный `drawCount` (`effectiveDraw` в `test-json.ts`). Расходятся, если банк темы меньше `drawCount` или у темы набор вариантов (PRD-17) |
| Г2 | L4, L2 | Исход пункта считают разные функции: веб — `aggregateStandardResult` в `/section-result`, пакет — свой цикл `buildSectionResult` (`resultsPage.js`) с `resolveTopicRule` и `checkPassRule`. Под подозрением `breakdownGateEnabled` (сервер передаёт, итог раздела в пакете — нет) и измерительные вопросы в теме |
| Г3 | L4 | `/section-result` не переигрывает протокол сценария, `/finish` переигрывает. При честном результате безвредно; разбирать, только если разойдутся L4 и L7 |
| Г4 | L5 | `showDetails`: веб передаёт `showCorrectAnswers` теста, пакет — всегда `true` (`mountRun` в `simulation.js`) |
| Г5 | L5 | Ограничение времени плеера: пакет берёт остаток таймера РАЗДЕЛА, если он идёт, иначе теста (`playedScenario`); веб — только остаток теста. У пункта-сценария с лимитом времени хосты дают плееру разное |
| Г6 | L1, L3 | После перезагрузки пакет сразу в хабе (проба: `state.phase = router`, в подвале «Назад»), веб — через стартовый экран с «Продолжить». Сначала решить, расхождение ли это: экран возобновления у хостов разный по устройству (PRD-12, start-state). «Назад» в подвале хаба после перезагрузки — проверить |
| Г7 | L2 | Исход пункта после перезагрузки: пакет хранит зафиксированный при возврате (`sp`), веб пересчитывает запросом по текущим ответам. Совпадут, пока ответы пункта заморожены; проверить на повторном прогоне сценария, прерванном перезагрузкой |

Решение по каждой гипотезе — какой хост прав — принимается по плану и решениям владельца, а не по
тому, какой проще поправить.

### 9.10. Проверка мутацией (шаг 6)

Тест обязан падать на каждой из правок ниже, вносимых по одной и откатываемых тем же шагом руками
(не через git):

1. `isLastSectionWeb` снова считает по выдаче в роутере — L1 и L3 на теме, последней в выдаче;
2. `selectRouterTopic` веба не снимает прежний исход повторного сценария — L2 и L3;
3. `freezeSectionPass` пакета не фиксирует пункт без экрана итогов — L2 при
   `showSectionResults: false` (дыра 1);
4. веб не шлёт `routerState` в `/save-progress` — L1 после `reload` внутри пункта;
5. `simRunReplaces` в пакете всегда `true` — L6 после досрочного выхода из повторного прогона.

Какая мутация на каком шаге какого прохождения уронила тест — в сообщение коммита.
