## 2. Что сделано

### Э4 — движок сравнения (ветка `feat/prd57-e4-answer-rules`, 13 коммитов)

- `shared/answer-check/` — новый чистый модуль: `normalize.ts` (форма сравнения: регистр,
  пробелы, `ё`, кавычки, дефисы), `wildcard.ts` (обычное сравнение `*` и `?`
  двухуказательным проходом, БЕЗ `RegExp`), `number.ts` (разбор числа и допуск),
  `rules.ts` (набор, связка, исход по каждому правилу), `index.ts`.
- `shared/schema.ts` — `answerRuleSetSchema`: набор правил хранится в `questions.correct_json`.
- `shared/questions/question-type.ts` — тип `short` в перечне, признак `isTextEntry`, третий
  вход в `isMeasurementOnly` (текстовый ответ БЕЗ правил неоцениваем).
- `shared/scoring/engine.ts` — `Answer` принимает строку; ветки в `exactCorrect` и
  `countTallies`. Тот же тип расширен у движка шкал (`shared/scales/engine.ts`): они
  присваиваются друг другу в адаптивном пути.
- `shared/template/question-interaction.ts` — `renderShortAnswer`;
  `shared/template/short-answer-dom.ts` — привязка ввода делегированием.
- `server/scorm/template/app/scoring/engine.js` — ES5-двойник ДЕЛЕГИРУЕТ сравнение в
  `TBTemplate.checkRuleSet`, а не повторяет его;
  `server/scorm/template/app/render/questions/short.js` — обёртка над общим рендером;
  `app/actions/answers.js` — привязка ввода в пакете.
- `client/src/features/questions/answer-rules/` — блок «Проверка ответа» и модель черновика,
  держащая наборы ОБОИХ видов ответа; подключён в `question-editor-drawer.tsx`.

Приёмка на живом приложении. Сценарии лежат в каталоге черновиков сессии и в репозиторий не
клались; повторить их можно вручную:

1. Поднять приложение своим портом: `PORT=8136 npm run dev` из рабочего места.
2. Войти учётной записью приёмки (реквизиты — в памяти проекта,
   `reference_dev_acceptance_account`).
3. Завести короткий ответ с тремя правилами через связку «любое», убедиться, что свёрнутые
   строки называют, что правило проверяет, а переключение вида ответа на «Число» и обратно
   возвращает набранное.
4. Пройти тест ответом «федеральная служба по экологическому, технологическому и атомному
   надзору» при правиле `Федеральная служба по * надзору` — должен начислиться балл.
5. ИЗМЕНИТЬ эталон вопроса после прохождения и открыть разбор попытки: он обязан показать
   исход, который засчитала попытка, а не пересчитанный по новому эталону.

Пакет: `npm run scorm:template`, затем `npm run scorm:player` и прохождение того же вопроса.
Отладочный плеер открывается по `/author/tests/<id>/debug`.

## 6. Принятые решения

Все согласованы с владельцем в переписке 2026-09-19.

| Решение | Почему |
| --- | --- |
| Э4 заводит тип-заготовку «Короткий ответ», Э3 её достраивает | Иначе круг: блок правил некуда прицепить, а тип нечем проверить |
| Правила хранятся в `questions.correct_json` | Правила и ЕСТЬ эталон; миграции нет, снимки и выпечка везут колонку |
| Регулярные выражения отложены в Э7 вместе с бюджетом | Откат разворачивается на 24–30 символах; выпускать проверку без бюджета нельзя |
| Обычное сравнение считается БЕЗ `RegExp` | Двухуказательный проход не имеет катастрофического случая — это и делает выпуск до Э7 честным |
| По-ответный вердикт перенесён из Э4 в Э3 | Э4 трогает движок, а это правка формы результата и путей аналитики |
| Исходы хранятся в `result_json`, а не отдельной таблицей | Колонка `jsonb`, миграции нет, читатели и так идут по попыткам |
| Потолок длины 250 из стандарта, число в настройках | Замер на стенде должен менять настройку, а не код и не заведённые задания |
| Цена ответа при импорте — отдельной задачей #54 | Считать один раз при импорте по снимку, а не возить `meta_`-блоком |
| Э3 делается одним куском, без дробления на Э3а и Э3б | Решение владельца |

## 7. Грабли

- **Приёмка в браузере нашла то, чего не нашли тесты, — трижды.** Юнит-тесты проверяли
  модули, а не путь до хранения и не вызов из хоста. Конкретно: у пакета СВОЙ распределитель
  рендереров (`app/render/questions/index.js`), и `short` попадал в «Неизвестный тип
  вопроса»; привязка ввода брала поле один раз при подключении, а пакет подписывается на
  старте, когда вопроса ещё нет, — весь ввод терялся молча; `AttemptResult` перечисляет поля
  поимённо, и `questionOutcomes` пропадало между агрегатом и базой. Не пропускать живую
  приёмку.
- **`AttemptResult` — второй контракт результата.** `AggregateResult` считает, а в базу
  пишется отдельная форма из `shared/schema.ts` (`attemptResultSchema`). Новое поле надо
  объявлять В ОБОИХ, иначе оно срезается без ошибки. В том же файле про это есть
  предупреждение применительно к zod и настройке «Тест пройден, если».
- **Тип `Answer` объявлен дважды** — в `shared/scoring/engine.ts` и `shared/scales/engine.ts`,
  и они присваиваются друг другу в адаптивном пути. Расширять только вместе.
- **Дев-сервер не перезапускается сам** (`tsx` без `--watch`). Серверные правки не видны, пока
  процесс не убит и не поднят заново. Порт освобождать через `Get-NetTCPConnection` в
  PowerShell: `pkill` в Git Bash этот процесс не берёт.
- **Профиль браузера Playwright MCP занят другой сессией.** Приёмка велась своим экземпляром
  через готовый помощник `scripts/check/editor-conformance/cdp.mjs` (в нём есть `launch`,
  `sessionCookie` и `splitCookie`).
- **Имена полей в API не угадываются.** Завершение попытки отдаёт `totalCorrect`,
  `totalEarnedPoints`, а не `correct`/`earnedPoints`; старт попытки — это
  `POST /api/tests/:id/attempts/start`; статистика теста — `GET /api/analytics/tests/:id`, без
  `/details`. Неверный путь возвращает HTML страницы, а не ошибку, и выглядит как пустой
  ответ.
- **Удаление теста требует подтверждения названием**: `DELETE /api/tests/:id` с телом
  `{ "confirmTitle": "<название>" }`, иначе 400 `title_mismatch`.
- **Дев-база общая для всех рабочих мест.** Данные приёмки за собой удалены; при повторной
  приёмке прибирать так же.
