# Миграции базы данных (drizzle-kit generate + migrate)

Схема БД ведётся версионированными миграциями. Деплой применяет их командой
`drizzle-kit migrate`. Прежний механизм `drizzle-kit push --force` убран: он
приводил живую БД в соответствие `shared/schema.ts`, применяя разрушающий DDL
без подтверждения (дроп/пересоздание/`TRUNCATE` при дрейфе или неоднозначном
диффе), из-за чего деплой мог молча терять данные.

## Что где лежит

- `shared/schema.ts` — источник истины по схеме.
- `drizzle/NNNN_*.sql` — сгенерированные миграции (применяются по порядку).
- `drizzle/meta/` — журнал (`_journal.json`) и снапшоты схемы.
- `drizzle/baseline-existing-db.sql` — разовый бейзлайн существующей БД.
- `migrations/` — ЛЕГАСИ рукописные data/DDL-шаги эпохи `push`. Деплой их больше
  не запускает; оставлены как история и для разовых правок через
  `node scripts/db/run-sql.cjs <file>`.

## Изменение схемы

1. Правишь `shared/schema.ts`.
2. Генерируешь миграцию:

   ```bash
   node_modules/.bin/drizzle-kit generate --name=<краткое_имя>
   ```

3. ОБЯЗАТЕЛЬНО просматриваешь `drizzle/NNNN_<имя>.sql`. Особое внимание —
   `DROP COLUMN`, `DROP TABLE`, изменения типа, добавление `NOT NULL`/`UNIQUE`.
   Если данные надо сохранить — правишь миграцию руками: сперва бэкфилл, потом
   деструктив (или отдельная data-миграция, см. ниже).
4. Коммитишь `shared/schema.ts` + `drizzle/` вместе.

## Data-миграция (бэкфилл, перенос данных)

Пустая кастомная миграция, которую заполняешь произвольным SQL; она попадает в
журнал и катится тем же `migrate`:

```bash
node_modules/.bin/drizzle-kit generate --custom --name=<краткое_имя>
```

Учти: `migrate` выполняет каждую миграцию в транзакции — операции, которые не
работают в транзакции (например `CREATE INDEX CONCURRENTLY`), в кастомную
миграцию класть нельзя.

## Разовый бейзлайн существующих БД

Существующие БД (прод и клонированный тестовый инстанс) уже несут полную схему из
эпохи `push`. Перед их ПЕРВЫМ деплоем на `migrate` их надо забейзлайнить —
пометить `0000_baseline` применённым, иначе `migrate` попытается создать уже
существующие таблицы и упадёт. Свежая (пустая) БД бейзлайна НЕ требует: там
`migrate` сам применит `0000` и построит схему.

Порядок:

1. Убедиться, что схема БД совпадает со `shared/schema.ts` (после эпохи `push`
   это так). Проверка — прогон `drizzle-kit push` без применения покажет дифф;
   «No changes» = совпадает. При расхождении сперва выверить схему.
2. Прогнать `drizzle/baseline-existing-db.sql` против БД один раз. На сервере, из
   каталога инстанса (`/srv/app/<project>`), тем же подключением, что и деплой:

   ```bash
   docker compose run --rm --no-deps \
     -v /srv/app/<project>/../<путь>/drizzle/baseline-existing-db.sql:/tmp/baseline.sql:ro \
     --entrypoint sh <project> -c "node scripts/db/run-sql.cjs /tmp/baseline.sql"
   ```

   Файл также лежит в образе: `/app/drizzle/baseline-existing-db.sql`, поэтому
   проще без монтирования:

   ```bash
   docker compose run --rm --no-deps --entrypoint sh <project> \
     -c "node scripts/db/run-sql.cjs drizzle/baseline-existing-db.sql"
   ```

3. Дальше деплой идёт как обычно — `drizzle-kit migrate` катит только миграции
   новее бейзлайна.

Скрипт идемпотентен: если в `drizzle.__drizzle_migrations` уже есть запись,
вставка пропускается.

### Если журнал отстал больше чем на бейзлайн

`baseline-existing-db.sql` помечает применённой ТОЛЬКО `0000`. База из эпохи `push`
могла получить и более поздние миграции (их DDL накатывал сам `push`), и тогда
после бейзлайна `migrate` упрётся в следующую по счёту миграцию с ошибкой вида
`column ... already exists`.

Признак: `SELECT * FROM drizzle.__drizzle_migrations` пуст или короче журнала,
а изменения из недостающих миграций в схеме уже есть. Лечение — пометить
применёнными все миграции, чей DDL фактически в базе. `created_at` берётся из
`when` соответствующей записи `drizzle/meta/_journal.json`, `hash` — sha256
содержимого файла миграции:

```bash
node -e "const f=require('fs'),c=require('crypto');const p='drizzle/0001_x.sql';console.log(c.createHash('sha256').update(f.readFileSync(p,'utf8')).digest('hex'))"
```

Так была разово починена dev-БД перед PRD-25 (журнал пуст, схема — по `0001`).

## Как это применяется в деплое

`scripts/deploy/deploy.sh` — один скрипт для всех инстансов (прод и тест) —
выполняет `drizzle-kit migrate` в одноразовом контейнере до старта приложения.
Инициализация БД — единственное, что различается: тестовому инстансу без БД она
создаётся клонированием прода (`--clone-from`), дальше миграции одинаковы.
Тестовый клон наследует
`drizzle.__drizzle_migrations` от прода, поэтому отдельного бейзлайна не требует
(если прод забейзлайнен ДО клонирования).

## Data-шаги, которые нельзя выразить в SQL

Часть бэкфиллов — это код, а не SQL. Пример: приведение текста страниц к
канонической форме (типографика знает, где кончается тег и начинается проза; эта
логика живёт в `shared/text`). Переписывать её на SQL значило бы завести вторую,
расходящуюся копию.

Такие шаги оформляются отдельным скриптом:

1. Скрипт кладётся в `scripts/db/<имя>.ts` и пишется на общих модулях приложения.
2. `scripts/build/build.ts` собирает его esbuild-ом рядом с сервером — в
   `dist/<имя>.cjs`. Это обязательно: продовый образ ставится с
   `npm ci --omit=dev`, поэтому `tsx` в нём нет, а рукописный JS-двойник снова
   означал бы вторую копию логики.
3. `scripts/deploy/deploy.sh` запускает его в одноразовом контейнере СРАЗУ ПОСЛЕ
   `drizzle-kit migrate`.

Требования к такому скрипту:

- **идемпотентность** — деплой прогоняет его каждый раз; повторный запуск обязан
  ничего не менять;
- **запись только изменившихся строк** — чтобы повторный прогон был дешёвым и
  читаемым в логе (`updated: 0`);
- **режим `--dry-run`** — посчитать отчёт, ничего не записывая;
- **некритичность к падению**, если шаг косметический: деплой продолжается, а шаг
  повторится на следующем.

Текущие шаги:

- `dist/backfill-page-text.cjs` — каноническая форма текста `content_pages`
  (исходник `scripts/db/backfill-page-text.ts`).
