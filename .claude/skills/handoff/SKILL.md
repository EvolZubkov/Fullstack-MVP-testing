# Передача работы: HANDOFF.md

Документ пишется для того, кто продолжит работу и НЕ видел этой сессии. Он должен уметь
по нему воспроизвести состояние, понять принятые решения и продолжить с нужного места,
не задавая вопросов автору.

## Когда НЕ надо

- Задача закончена, закоммичена и приёмка пройдена — тогда достаточно коммита и changelog.
- Работа умещается в один коммит без незакрытых решений.

## Шаг 1. Собрать факты, а не воспоминания

Ничего не пиши по памяти. Сначала выясни фактическое состояние:

```bash
git status                       # что изменено и что не отслеживается
git diff --stat                  # объём правок по файлам
git log --oneline -10            # последние коммиты, точка отсчёта
git branch --show-current        # ветка
```

Дополнительно, если применимо:

- прогнать тесты и записать РЕАЛЬНЫЙ результат (сколько зелёных, сколько красных, какие
  падения предшествовали работе и не связаны с ней);
- проверить типы и линтеры;
- посмотреть, есть ли в `docs/plans/`, `docs/specs/` документ, к которому относится работа,
  и сверить его статусы с фактическим состоянием кода.

Если факт проверить не удалось — так и напиши: «не проверено». Не выдавай предположение за
проверенный результат.

## Шаг 2. Куда класть

- Основное место: `docs/handoff/HANDOFF-<ГГГГ-ММ-ДД>-<короткая-тема>.md`.
- Если работа целиком про один подпроект и там уже принят свой формат передачи (например
  `vendor/ui-kit/HANDOFF.md`) — дополняй его, не создавай второй.
- В корень репозитория файл НЕ класть.

## Шаг 3. Структура

Обязательные разделы. Пустые разделы удалять, а не оставлять с прочерком.

```markdown
# Передача работы: <тема>

Дата: <ГГГГ-ММ-ДД>. Ветка: <имя>. Базовый коммит: <хеш и заголовок>.
Статус: <в работе | приостановлено | готово к приёмке>.

## 1. Задача

Что требовалось и почему. Ссылки на PRD, план, отчёт. Если требование менялось по ходу —
что именно изменилось и по чьему решению.

## 2. Что сделано

По пунктам, каждый — с файлами и строками. Только то, что реально в дереве.

## 3. Что НЕ сделано

Незакрытые пункты плана, сознательно отложенное, известные пробелы. Для каждого — почему
не сделано: не успел, заблокировано, отложено решением.

## 4. Как проверить

Команды с ожидаемым результатом, адреса стендов, шаги ручной проверки.
Реквизиты доступа сюда НЕ писать — только указать, где они берутся.

## 5. Состояние проверок

Результат последнего прогона: сколько зелёных, какие падения и связаны ли они с работой.
Падения, существовавшие ДО работы, называть явно, чтобы преемник не искал их причину в ней.

## 6. Принятые решения

Развилки, выбор и обоснование. Отдельно — решения, согласованные с заказчиком, чтобы
преемник не переиграл их молча.

## 7. Грабли

Что уже сломалось и как обошли: неочевидные зависимости, порядок перезапуска, кэши,
данные стенда. Каждая строка экономит преемнику час.

## 8. Следующий шаг

Ровно с чего начинать: файл, функция, пункт плана.
```

## Шаг 4. Правила текста

- Русский язык. Комментарии и идентификаторы кода — как в коде.
- Никаких эмодзи. Файл должен проходить markdownlint.
- Ссылки на файлы — относительным путём от корня репозитория, со строкой, если она важна.
- Даты только абсолютные: «2026-07-22», не «вчера» и не «на прошлой неделе».
- Никаких паролей, токенов, строк подключения. Вместо значения — где его взять.
- Не пересказывай то, что и так видно в git-истории и коде; пиши то, чего в них НЕТ:
  причины, отвергнутые варианты, договорённости, ловушки.
- Формулировки честные: «не проверено», «падает», «сделано наполовину». Документ передачи
  ценен ровно настолько, насколько ему можно верить.

## Шаг 5. Проверить перед сдачей

- Все ли упомянутые файлы существуют, все ли строки на месте.
- Совпадает ли раздел «Что сделано» с `git status` и `git diff --stat`.
- Сможет ли человек без контекста выполнить раздел «Как проверить» дословно.
- Прогнать markdownlint по созданному файлу.
- Сообщить пользователю путь к файлу и одной фразой — что в нём главное.
